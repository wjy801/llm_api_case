# P0 迭代一：契约与身份详细开发方案

## 1. 文档定位

本方案用于指导 P0 迭代一“契约与身份”的代码开发，输入依据按以下层级理解：

1. `dev/P0与P1质量工程后续开发方向.md`：控制 P0/P1 总体目标、原则和阶段边界。
2. `dev/P0质量数据底座详细开发方案.md`：控制 P0 四次迭代的顺序、数据链路和最终验收。
3. `dev/P0迭代一契约与身份开发思路.md`：控制迭代一的功能范围和技术方向。
4. 本文件：把迭代一细化为字段级契约、算法规则、文件改动、测试矩阵和实施步骤。

当文档之间出现冲突时，不扩大本迭代范围，优先遵守“原始事实优先、稳定身份优先、零运行时影响、后续可兼容扩展”四项原则。

## 2. 需求复述

本迭代只建立后续质量事实链所依赖的基础语言和工具，不接入现有执行链路。

需要完成：

```text
版本化质量数据契约
-> 稳定且安全的身份规则
-> 哈希前脱敏与规范化
-> run/case 上下文传递
-> JSON/JSONL 存储基础
-> 单元测试冻结行为
```

明确不做：

- 不注册 pytest 插件。
- 不修改 `module/conftest.py`。
- 不修改 `common/request_context.py` 和 `common/request_middleware.py`。
- 不修改 `run_master.py`。
- 不修改 `Jenkinsfile`。
- 不生成真实 `reports/quality/` 产物。
- 不实现采集、归并、分类、报告或门禁逻辑。
- 不新增第三方依赖。

## 3. 第一性原理与因果链

P0 的最终目标不是生成更多日志，而是形成可以跨阶段、跨 worker、跨构建对账的质量事实。

契约不稳定的因果链：

```text
字段含义和类型未冻结
-> 采集器各自解释数据
-> 分片无法可靠归并
-> 报告与门禁统计口径漂移
-> P1 基线、Flaky 和成本治理失真
```

身份不稳定的因果链：

```text
case_id / interface_id 随动态值变化
-> 同一对象跨构建无法对齐
-> 历史趋势和失败复现没有稳定主键
-> 分类和门禁只能依赖文本猜测
-> 质量工程退回人工日志检索
```

安全边界不稳定的因果链：

```text
原始参数直接进入摘要或 ID
-> 密钥、Cookie 或用户数据进入产物
-> 哈希结果仍可能遭受低熵枚举
-> 质量能力带来新的泄露面
```

因此本迭代必须先冻结契约、身份和脱敏顺序，再允许迭代二接入采集。

## 4. TOC 约束决策

当前瓶颈是“质量数据能否被一致表达和唯一关联”，不是采集 hook 数量。

| 决策点 | 本迭代选择 | 原因 |
| --- | --- | --- |
| 首要约束 | 契约和身份稳定性 | 后续采集、归并、分类全部依赖 |
| 投入重点 | 模型、ID、脱敏、上下文、存储 | 构成事实链最小地基 |
| 风险控制 | 独立 `quality` 包 | 保持现有运行行为不变 |
| 兼容策略 | `schema_version=quality.v1` | 后续字段变化必须显式版本化 |
| 安全策略 | 先脱敏、再规范化、最后哈希 | 避免敏感原文进入身份链路 |
| 延后内容 | pytest、请求中间件、归并、门禁 | 防止范围提前耦合 |

## 5. 当前代码基线

仓库现状：

- 尚不存在 `quality/` 包。
- 已使用 Pydantic v2，现有冻结模型位于 `config.py`、`common/retry.py` 和 `common/polling.py`。
- 已有 `util/redaction.py`，可以处理敏感 header、敏感 key、JSON/form 文本和 URL 中的敏感 query。
- 现有脱敏不完全覆盖质量侧要求，例如全部 query 移除、任意 Bearer 文本、长随机秘密和哈希规范化。
- 已有 `ContextVar + Token.reset()` 使用模式，可复用其生命周期设计。
- 当前框架测试位于 `tests/`，迭代一测试应新增到 `tests/quality/`。

结论：复用现有技术风格，但质量侧增加独立薄层，不能修改现有请求日志的脱敏语义。

## 7. 公共模型设计

### 7.1 统一模型配置

在 `quality/models.py` 定义：

```text
SCHEMA_VERSION = "quality.v1"
```

所有数据契约模型继承内部公共基类，统一配置：

- 使用 Pydantic v2 `BaseModel`。
- 使用 `ConfigDict(frozen=True, extra="forbid")`。
- `schema_version` 默认且只允许 `quality.v1`。
- 所有模型必须支持 `model_dump(mode="json")`。
- 未定义字段直接报错，防止采集端拼错字段后被静默忽略。
- 可空字段显式使用 `T | None`，避免空字符串代替缺失语义。
- 时间字段必须为 timezone-aware `datetime`。
- 列表型字段优先使用 tuple 保存，JSON 模式仍输出数组，降低冻结模型内部被修改的概率。

### 7.2 枚举

使用 `str, Enum`：

| 枚举 | 值 |
| --- | --- |
| `RunStatus` | `finished`、`interrupted`、`partial` |
| `IntegrityStatus` | `complete`、`degraded`、`failed` |
| `CaseStatus` | `passed`、`failed`、`skipped`、`error`、`xfailed`、`xpassed` |
| `CasePhase` | `collection`、`setup`、`call`、`teardown` |
| `Protocol` | `http`、`sse`、`polling` |
| `BusinessStatus` | `success`、`failed`、`unknown` |
| `CostSource` | `none`、`estimated`、`billing` |
| `FailureCategory` | `PRODUCT_DEFECT`、`TEST_DEFECT`、`FRAMEWORK_DEFECT`、`ENVIRONMENT`、`CONFIGURATION`、`TRANSIENT`、`UNKNOWN` |
| `OwnerDomain` | `product`、`test`、`framework`、`environment`、`configuration`、`unknown` |
| `Confidence` | `high`、`medium`、`low` |
| `GateMode` | `shadow` |
| `GateResult` | `PASS`、`WARN`、`BLOCK`、`NO_DATA` |
| `IssueSeverity` | `info`、`warn`、`error` |

`CostSource` 是对总体方案中既有字段语义的补全，不改变成本统一按人民币记录且不新增 `currency` 字段的决策。

### 7.3 IntegrityIssue

字段：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `schema_version` | 固定字符串 | 默认 `quality.v1` |
| `run_id` | `str` | 非空 |
| `severity` | `IssueSeverity` | 必填 |
| `source` | `str` | 非空，保存产生问题的组件名 |
| `code` | `str` | 非空，保存稳定机器码 |
| `message` | `str` | 非空且必须为脱敏摘要 |
| `related_id` | `str | None` | 关联 case/request 等身份 |
| `created_at` | `datetime` | 必须包含时区 |

### 7.4 RunRecord

字段与总体 P0 方案保持一致：

- `run_id`
- `job_name`
- `build_number`
- `branch`
- `commit_sha`
- `trigger`
- `environment`
- `start_time`
- `end_time`
- `status`
- `integrity_status`
- `integrity_issues`

规则：

- `run_id`、`trigger`、`environment` 非空。
- Jenkins 专属字段在本地运行时允许为 `None`。
- `end_time` 在运行未结束时允许为 `None`。
- 同时存在开始和结束时间时，结束时间不得早于开始时间。
- `integrity_issues` 使用 `tuple[IntegrityIssue, ...]`，默认为空。

### 7.5 CaseResult

字段：

- `run_id`、`execution_id`、`worker_id`
- `case_id`、`invocation_id`、`nodeid`、`param_hash`
- `phase`
- `raw_status`、`final_status`
- `duration_ms`
- `start_time`、`end_time`
- `failure_id`
- `evidence_refs`

规则：

- 身份字段和 `nodeid` 非空。
- `duration_ms >= 0`。
- 时间必须包含时区，结束时间不得早于开始时间。
- `failure_id` 允许为空，不在模型层强制失败状态必须携带指纹。
- `evidence_refs` 为 `dict[str, str]`，只保存受控路径或引用，不保存载荷。
- 第一版保留 `raw_status` 与 `final_status` 两个字段，即使当前通常相同。

### 7.6 RequestUsage 与 RequestCost

`RequestUsage`：

- `input_tokens: int | None`
- `output_tokens: int | None`
- `media_count: int | None`
- 非空值必须大于或等于 0。

`RequestCost`：

- `amount: float | None`
- `source: CostSource = none`
- `price_version: str | None`
- `amount` 非空时必须大于或等于 0。
- `source=none` 时允许 `amount` 和 `price_version` 为空。
- 本迭代不增加复杂的跨字段业务强校验，避免提前约束后续账单适配。

### 7.7 RequestMetric

字段：

- `run_id`、`execution_id`、`worker_id`
- `case_id`、`invocation_id`
- `request_event_id`、`server_request_id`
- `interface_id`、`method`、`url_template`、`protocol`
- `attempt_index`
- `status_code`、`business_status`、`duration_ms`
- `timeout`、`retryable`、`error_type`
- `usage`、`cost`

规则：

- `request_event_id`、`interface_id` 和关联身份字段非空。
- `method` 在校验阶段统一转为大写。
- `attempt_index >= 1`。
- `duration_ms >= 0`。
- `status_code` 允许为空，用于网络异常和未取得响应的场景。
- 不保存原始 URL、header、请求体和响应体。
- `usage`、`cost` 使用默认空模型，调用方不需要传裸字典占位。

### 7.8 FailureRecord

辅助模型 `FailureFingerprintSource` 字段：

- `phase`
- `error_type`
- `message_hash`
- `interface_id`
- `assert_location`

`FailureRecord` 字段：

- `run_id`、`failure_id`
- `case_id`、`invocation_id`
- `phase`
- `category`、`owner_domain`、`confidence`
- `error_type`、`normalized_message`
- `fingerprint_source`
- `manual_override`

规则：

- `normalized_message` 只能保存脱敏和规范化后的消息。
- `manual_override` 第一版只预留为可空、扁平 JSON 字典，不实现治理和回写。
- 人工修正不能修改原始事实，只能作为后续报告和 P1 输入。

### 7.9 QualitySummary

字段沿用总体方案：

- case 总数及 passed/failed/error/skipped 数量。
- `raw_pass_rate`、`final_pass_rate`。
- `retry_passed`。
- request 总数、成功率、5xx 数、超时数。
- unknown failure 数量。
- `integrity_status`。

规则：

- 所有计数大于或等于 0。
- 比率位于 0 到 1 之间。
- 本迭代只冻结模型，不实现统计计算。

### 7.10 GateDecision

`GateRuleDecision` 字段：

- `rule_id`、`rule_version`、`target`
- `actual`、`threshold`
- `sample_size`
- `decision`
- `evidence`

`GateDecision` 字段：

- `run_id`
- `mode`
- `overall`
- `rules`

规则：

- `sample_size >= 0`。
- `actual` 和 `threshold` 支持数字、布尔值、字符串或空值，满足后续不同规则类型。
- `mode` 第一版只能为 `shadow`。
- 本迭代不实现规则执行。

## 8. 质量侧脱敏与规范化

新增 `quality/redaction.py`，职责是为质量身份和摘要提供比日志侧更严格的安全边界。

### 8.1 公共函数

```text
redact_quality_value(value)
canonicalize_for_hash(value)
sanitize_identifier_part(value)
strip_url_query(value)
```

### 8.2 处理顺序

```text
原始输入
-> 结构化识别
-> 敏感字段替换为固定占位符
-> 动态值规范化
-> canonical JSON
-> SHA-256
```

禁止先哈希敏感值再保存摘要。低熵密钥、账号和 token 必须先被固定占位符替换。

### 8.3 脱敏规则

至少覆盖：

- `authorization`、`cookie`、`set-cookie`、`x-api-key`。
- `api_key`、`token`、`access_token`、`refresh_token`、`secret`、`password`。
- `Bearer <token>` 文本。
- URL query。
- JSON、mapping、list、tuple 中的敏感字段。
- 符合高风险随机串特征的秘密值。
- repr 中的内存地址。

质量侧采用两种 query 策略：

- `interface_id` 和失败指纹：删除全部 query。
- `param_hash`：保留非敏感参数参与摘要，敏感参数替换为固定占位符。

### 8.4 Canonical JSON

- mapping 按字符串化 key 排序。
- list/tuple 保留顺序。
- set/frozenset 按各元素 canonical 结果排序。
- Enum 使用 value。
- datetime 转为 UTC ISO 8601。
- Path 转为 `/` 分隔形式。
- Pydantic 模型使用 `model_dump(mode="json")`。
- dataclass 转为字段 mapping。
- 不可序列化对象使用稳定类型名和已规范化 repr，不保留内存地址。
- JSON 输出使用 UTF-8、`ensure_ascii=False` 和稳定 separators。

## 9. 身份生成规则

### 9.1 run_id

函数：

```text
build_run_id(job_name, build_number, timestamp, random_uuid) -> str
```

建议格式：

```text
{safe_job}-{safe_build}-{utc_timestamp}-{uuid8}
local-{utc_timestamp}-{uuid8}
```

要求：

- 时间统一转换为 UTC，格式为 `YYYYMMDDTHHMMSSZ`。
- UUID 只取标准 hex 前 8 位。
- 输出只包含 ASCII 字母、数字、点、下划线和中划线。
- 函数参数可注入时间和 UUID，保证测试确定性。

### 9.2 execution_id

```text
build_execution_id(stage_name, index) -> str
```

- `index >= 1`。
- stage name 使用安全字符规范化。
- 建议输出 `{safe_stage}-{index}`，例如 `parallel-pool-1`。

### 9.3 case_id

```text
normalize_nodeid(nodeid) -> NormalizedNodeId
build_case_id(nodeid) -> str
```

`NormalizedNodeId` 至少包含：

- `stable_nodeid`
- `parameter_id: str | None`

规则：

- `\` 统一为 `/`。
- 压缩连续空白。
- 去除 nodeid 末尾 pytest 参数段。
- 保留文件路径、测试类和测试函数。
- `case_id` 直接使用可读的 `stable_nodeid`，不做哈希。
- 空 nodeid 或去参数后为空必须报错。

### 9.4 param_hash

```text
build_param_hash(value) -> str
```

- 先调用质量侧脱敏。
- 再生成 canonical JSON。
- 使用 SHA-256 小写十六进制。
- 建议固定截断为前 16 位。
- 未参数化用例使用 `None` 生成稳定摘要，不使用空字符串绕过。

### 9.5 invocation_id

```text
build_invocation_id(run_id, case_id, param_hash) -> str
```

建议规则：

- 输入按 `run_id + NUL + case_id + NUL + param_hash` 组合，避免边界歧义。
- 使用 SHA-256 前 24 位。
- 输出 `inv-{hash24}`。
- 同一 run、同一 case、同一参数摘要必须稳定。
- 任一输入变化必须生成不同结果。

### 9.6 request_event_id

```text
new_request_event_id() -> str
```

- 每次调用生成一个 UUID4。
- 每个 request attempt 独立生成。
- 返回标准 UUID 字符串，不混用服务端 request id。

### 9.7 interface_id

```text
build_interface_id(method, url_or_path, protocol="http") -> str
```

路径处理：

- 删除 scheme、host、query 和 fragment，只保留 path。
- 合并重复 `/`。
- 保证以 `/` 开头。
- 除根路径外移除末尾 `/`。
- 纯数字段替换为 `{id}`。
- UUID 段替换为 `{uuid}`。
- 长十六进制段或保守识别出的无分隔高熵段替换为 `{hash}`。
- 不对带明显业务语义的连字符模型名做激进模板化。

建议输出格式：

```text
POST /v1/tasks/{id} http
```

协议始终显式输出，避免 HTTP、SSE 和 polling 使用相同 path 时发生身份冲突。

### 9.8 failure_id

```text
build_failure_fingerprint(
    phase,
    error_type,
    message,
    interface_id=None,
    assert_location=None,
) -> str
```

规范化内容：

- 统一换行和连续空白。
- 移除 URL query。
- 替换 UUID、内存地址、ISO 时间戳、长随机值和临时路径随机段。
- 脱敏 token、key、authorization 和 cookie。
- 保留错误类型、阶段、接口模板和断言位置等稳定语义。
- 避免把所有三位数字替换，防止 HTTP 200/500 等关键差异被抹平。

建议输出：

```text
fail-call-assertionerror-{hash12}
```

同时返回或提供内部函数生成 `normalized_message` 与 `message_hash`，供 `FailureRecord` 使用。

## 10. 运行上下文设计

在 `quality/runtime_context.py` 定义冻结 dataclass：

```text
QualityRunContext
  run_id
  execution_id
  worker_id
  output_dir

QualityCaseContext
  case_id
  invocation_id
  nodeid
  param_hash
```

使用两个独立 `ContextVar`，默认值为 `None`。

公共 API：

```text
set_run_context(context) -> Token
get_run_context(default=None)
reset_run_context(token)
clear_run_context()

set_case_context(context) -> Token
get_case_context(default=None)
reset_case_context(token)
clear_case_context()
```

语义：

- `set_*` 返回 Token。
- 嵌套生命周期必须使用 `reset_*(token)` 恢复上层上下文。
- `clear_*` 明确设置为无上下文，用于最终兜底清理。
- run 和 case 上下文互不污染。
- 模块不依赖 pytest，也不负责写入文件。

## 11. 存储基础设计

在 `quality/storage.py` 提供：

```text
write_json_atomic(path, data)
append_jsonl(path, record)
read_jsonl(path)
ensure_quality_dirs(output_dir)
```

### 11.1 JSON 转换

统一内部转换函数支持：

- Pydantic 模型。
- dataclass。
- Enum、datetime、Path。
- 普通 JSON-compatible 对象。

输出使用 UTF-8、`ensure_ascii=False`，并在文件末尾保留换行。

### 11.2 write_json_atomic

- 自动创建父目录。
- 临时文件必须创建在目标文件同一目录，保证 `os.replace` 原子替换语义。
- Windows 下先关闭临时文件，再执行替换。
- 写入后 flush，并在可用时执行 `os.fsync`。
- 异常时清理临时文件，原目标文件保持不变。

### 11.3 append_jsonl

- 自动创建父目录。
- 每次追加恰好一行合法 JSON。
- 单条记录中不得包含物理换行破坏 JSONL 边界。
- 第一版不实现跨进程锁，不承诺多个 worker 写同一个文件安全。
- 迭代二必须通过 `{execution_id}-{worker_id}` 分片规避竞争。

### 11.4 read_jsonl

- 忽略空行。
- 返回按文件顺序解析的记录列表。
- 非法 JSON 抛出包含文件路径和行号的明确异常。
- 本迭代不做损坏行跳过；损坏容错和完整性记录属于迭代三。

### 11.5 ensure_quality_dirs

显式调用后创建：

```text
output_dir/
  shards/
  merged/
```

函数返回包含 root、shards、merged 的冻结目录布局对象，便于后续迭代复用。模块 import 时不得自动创建目录。

## 12. 包导出规则

`quality/__init__.py` 只导出稳定公共 API：

- schema version、枚举和契约模型。
- ID 生成函数。
- 上下文对象和生命周期函数。
- 存储函数。

内部正则、canonical helper 和低层转换函数不进入 `__all__`，避免后续无法调整实现。

本迭代包内依赖方向固定为：

```text
models
redaction
identifiers -> redaction
runtime_context
storage -> models/标准序列化接口
__init__ -> 公共导出
```

禁止形成循环依赖。

## 13. 测试方案

### 13.1 模型测试

`tests/quality/test_quality_models.py`：

- 所有模型可构造并执行 `model_dump(mode="json")`。
- 枚举输出稳定字符串。
- `schema_version` 自动填充且非法版本被拒绝。
- 模型 frozen，额外字段被拒绝。
- 空身份、负耗时、非法 attempt、负样本量被拒绝。
- method 自动转大写。

- 成本、usage 和 summary 的非负约束有效。
- evidence 和完整性问题能正确嵌套序列化。

### 13.2 脱敏测试

`tests/quality/test_quality_redaction.py`：

- header/key 大小写均能识别。
- Authorization、Cookie、API Key、token、secret、password 被固定占位符替换。
- Bearer 文本不泄露原值。
- interface/failure 使用场景删除全部 query。
- param hash 场景保留非敏感参数并移除敏感值。
- 嵌套 dict/list/tuple 正确脱敏且不修改调用方对象。
- datetime、Enum、Path、set、自定义对象 canonical 结果稳定。
- 原始敏感值不出现在 canonical JSON 和最终摘要中。

### 13.3 ID 测试

`tests/quality/test_quality_identifiers.py`：

- Windows 与 Unix nodeid 生成相同 `case_id`。
- 参数段变化不影响 `case_id`。
- 不同脱敏后参数生成不同 `param_hash`。
- 敏感值变化不改变固定占位后的摘要。
- run/execution ID 只包含安全字符。
- 相同输入稳定生成相同 invocation ID。
- request event ID 每次不同且可解析为 UUID。
- URL host 和 query 不影响 interface ID。
- 数字、UUID、长十六进制和保守随机段正确模板化。
- 业务语义路径段不会被过度模板化。
- failure fingerprint 去除时间戳、UUID、token、内存地址和 query。
- HTTP 状态码等稳定诊断语义得到保留。

### 13.4 上下文测试

`tests/quality/test_quality_runtime_context.py`：

- 默认读取为空。
- 设置后可读取。
- reset 恢复上层上下文。
- clear 后读取为空。
- run 与 case ContextVar 互不污染。
- 两个独立 `contextvars.Context` 之间隔离。
- 异常路径使用 `finally` reset 后不残留上下文。

### 13.5 存储测试

`tests/quality/test_quality_storage.py`：

- 原子 JSON 写入生成 UTF-8 合法文件。
- 已存在目标文件可被完整替换。
- 模拟替换失败时旧文件保持不变且临时文件被清理。
- Pydantic 模型可直接写入。
- JSONL 每条记录独占一行。
- 父目录不存在时自动创建。
- 空行读取被忽略。
- 损坏 JSONL 报告准确行号。
- `ensure_quality_dirs` 只在显式调用时创建目录。

## 17. 风险与控制

| 风险 | 影响 | 控制方式 |
| --- | --- | --- |
| 一次冻结过多业务语义 | 后续兼容成本高 | 只做低争议结构校验，复杂业务规则延后 |
| 模型接受额外字段 | schema 漂移被隐藏 | `extra="forbid"` 并测试 |
| frozen 模型内部容器可变 | 运行中事实被改写 | 列表优先 tuple，证据字典不共享输入引用 |
| ID 过度模板化 | 不同接口被错误合并 | 第一版使用保守随机段规则 |
| ID 模板化不足 | 指标高基数 | 用跨样本测试补充明确动态模式，版本化调整 |
| 哈希前泄露敏感值 | 形成安全风险 | 固定顺序：脱敏后才 canonical/hash |
| ContextVar 未 reset | 用例身份串联 | Token API、finally 测试和 clear 兜底 |
| JSON 原子写跨盘失效 | 文件可能损坏 | 临时文件始终与目标同目录 |
| JSONL 被多 worker 共写 | 行交错或覆盖 | 本迭代明确不支持；迭代二按 worker 分片 |
| 质量包被提前接入 | 扩大回归面 | 零运行时引用检查 |

## 18. 回退方案

```text
删除 quality/
删除 tests/quality/
```

由于不修改现有执行链路，回退不需要修改配置、Jenkins 或业务用例。

## 19. 与后续迭代的接口

迭代二只能通过本迭代公共 API 接入：

- pytest 插件使用模型和身份工具生成 case 分片。
- 请求指标中间件读取 runtime context，生成 request 分片。
- worker 使用 storage 写自己的 JSONL 文件。
- 采集异常转换为 `IntegrityIssue`，不得覆盖测试异常。

迭代三复用：

- `request_event_id` 去重请求。
- `invocation_id + phase` 去重用例阶段。
- `failure_id` 聚合相同失败。
- frozen 模型重新加载和校验分片数据。

迭代四复用：

- `QualitySummary` 和 `GateDecision` 输出 JSON/Markdown。
- `sample_size` 控制小样本结论。
- `GateMode.shadow` 保证 P0 不改变 CI 退出码。

## 20. 实施前阻断决策

以下格式一旦进入迭代二产物就会形成跨构建兼容约束。开始编码前需要确认，或明确接受本方案推荐值：
