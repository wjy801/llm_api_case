## 2. 已确认决策

### 2.1 身份语义

- 一个 pytest 测试函数对应一个稳定 `case_id`。
- 一个参数化实例对应一个 `invocation_id`。
- 同一参数化实例内部的串行请求和并发请求共享同一个 `case_id`、`invocation_id`。
- 每一次真实 HTTP 尝试拥有独立 `request_event_id`。
- 请求重试使用现有 `RetryExecutor` 的 `attempt_index`，首次为 1，后续按真实重试顺序递增。
- setup、call、teardown 可以生成不同阶段的 `CaseResult`，但共享同一个 `case_id` 和 `invocation_id`。

### 2.2 execution_id 语义

不增加没有业务含义的序号，固定使用：

| 执行场景 | `execution_id` |
| --- | --- |
| `run_master.py` 并行池 | `parallel-pool` |
| `run_master.py` 串行池 | `serial-pool` |
| 未启用并行、整体串行执行 | `serial-pool` |
| 直接执行 pytest | `manual-pytest` |

本迭代不使用 `parallel-pool-1`、`serial-pool-1`、`manual-pytest-1`。

### 2.3 请求状态语义

- 普通 HTTP：2xx 且请求链路未抛异常为 `success`；非 2xx 或请求异常为 `failed`。
- 普通 HTTP 200 中的业务错误正文，本迭代不做通用推断；请求层按 HTTP 成功记录，用例断言在 Case 层表达业务失败。
- 轮询请求通过现有 `PollingPolicy` 解释状态：等待中为 `unknown`，成功终态为 `success`，失败或未知终态为 `failed`。
- SSE 成功返回响应头时为 `unknown`；非 2xx 或传输异常为 `failed`。
- SSE 的 `duration_ms` 只表示请求发起到响应头返回的耗时，不消费响应流，不采集完整流耗时和首 Token 延迟。
- SSE 的 `usage` 保持空值，避免质量中间件读取或消费流。

### 2.4 缺失上下文语义

- 不新增 `orphan` 标识。
- 不把 `RequestMetric.case_id`、`RequestMetric.invocation_id` 改为可空。
- 请求发生时若没有真实用例上下文，不生成不合法或猜测归属的 `RequestMetric`。
- 改为生成 `IntegrityIssue(code='missing_case_context')`。
- 禁止使用“最后执行用例”、模块全局变量或进程级当前 case 作为回退。

### 2.5 并发语义

- 迭代二不引入新的业务线程池。
- 保留现有 `ThreadPoolExecutor` 的 worker 数量、任务提交顺序、Future、异常传播和完成顺序。
- 只增加通用 `submit_with_context()`，在提交任务时复制当前 `contextvars.Context`。
- 每个任务必须调用一次新的 `copy_context()`，不得多个并发任务复用同一个 Context。
- 不 monkeypatch 标准库执行器，不修改 `ThreadPoolExecutor.submit()`。

## 3. 需求复述

本迭代的目标不是直接生成最终质量报告，而是把已经冻结的契约接入两个真实事实源：

```text
pytest 生命周期
-> 采集 CaseResult
-> 按 execution_id + worker_id 写 case 分片

请求中间件生命周期
-> 采集 RequestMetric
-> 关联当前 case_id / invocation_id
-> 按 execution_id + worker_id 写 request 分片

采集异常
-> 写 IntegrityIssue
-> 不覆盖测试异常
-> 不改变 pytest 退出码
```

本迭代需要完成：

- 建立环境变量驱动的质量采集配置。
- 注册 fail-open pytest 插件。
- 建立进程内唯一、线程安全的分片采集器。
- 为 pytest 用例设置和清理 `QualityCaseContext`。
- 采集 setup、call、teardown 阶段结果。
- 把请求指标中间件接入现有 `BaseRequest` 默认链路。
- 采集 HTTP、SSE、轮询和重试 attempt。
- 为既有线程池调用补充 ContextVar 传播。
- 支持非 xdist、xdist worker、并行池和串行池分片。
- 对缺失上下文、写入失败和采集异常生成完整性问题。
- 保证 `QUALITY_ENABLE=0` 时原行为不变。

明确不做：

- 不实现分片归并和去重。
- 不生成最终 `run.json`。
- 不生成 `merged/` 下的事实集。
- 不实现 `FailureRecord` 分类和失败指纹落盘。
- 不生成 `summary.json`、`gate-report.json` 或 Markdown 报告。
- 不修改 Jenkinsfile。
- 不改变 CI 退出码。
- 不采集 SSE 首 Token、chunk 间隔和完整流耗时。
- 不新增通用业务响应规则引擎。
- 不把线程池替换为协程、串行循环或新的并发框架。

## 4. 第一性原理与因果链

### 4.1 双层采集的本质

质量数据需要同时回答两个不同问题：

- Case 层回答“测试目的是否成立”。
- Request 层回答“实现这个测试目的时，真实接口调用发生了什么”。

只采 pytest 的因果链：

```text
只知道用例成功或失败
-> 不知道调用了哪个接口、重试几次、是否超时
-> 无法计算接口稳定性和重试挽救率
-> 失败定位仍依赖日志人工分析
```

只采请求的因果链：

```text
只知道接口事件
-> 不知道请求属于哪个测试目的
-> 并发和参数化运行后无法归属
-> 请求指标无法解释用例结果
-> 接口事实无法进入质量门禁
```

因此双层采集不是重复记录，而是建立 `CaseResult -> RequestMetric` 的可验证事实关系。

### 4.2 ContextVar 传播的本质

pytest 在执行测试函数时设置的 ContextVar 只天然存在于当前执行上下文。标准线程池不会自动把该上下文复制到 worker 线程。

```text
测试线程设置 case_id / invocation_id
-> ThreadPoolExecutor 创建或复用 worker 线程
-> worker 线程没有当前 case 上下文
-> 请求中间件无法满足 RequestMetric 必填字段
-> 如果猜测归属，会产生比缺数据更危险的错误事实
```

真正需要解决的问题不是取消并发，而是让“提交任务”成为上下文跨线程的明确边界。

### 4.3 分片写入的本质

xdist worker 是独立进程，多个进程写同一个 JSONL 文件会形成竞争条件。

```text
多个 worker 共享输出文件
-> 行写入可能交错、覆盖或损坏
-> JSONL 无法稳定解析
-> 后续归并无法判断数据缺失还是业务缺失
```

因此写入所有权必须唯一：一个 `execution_id + worker_id` 只对应一个进程和一组分片。

### 4.4 fail-open 的本质

质量系统的优先级低于被观察的测试系统。

```text
质量采集异常向外抛出
-> BaseRequest 把中间件异常转换为 RuntimeError
-> 真实请求或真实测试结果被覆盖
-> 质量系统改变了被测对象
-> 所有质量结论失去可信度
```

因此采集异常必须被质量层内部吸收，并尽最大努力转化为 `IntegrityIssue`。

## 5. TOC 约束决策

当前约束已经从迭代一的“契约不稳定”转移到“事实能否在不改变原行为的前提下被完整归属”。

| 决策点 | 本迭代选择 | 原因 |
| --- | --- | --- |
| 首要约束 | 请求与用例的真实关联 | 关联错误会污染所有后续统计 |
| 采集入口 | pytest hook + 请求中间件 | 两处是现有事实生命周期的天然边界 |
| 并发策略 | 保留原线程池，只传播 Context | 并发属于业务验证语义，不是采集器职责 |
| 存储策略 | worker 独占 JSONL 分片 | 消除跨进程写竞争 |
| 失败策略 | fail-open + IntegrityIssue | 采集不得改变测试事实 |
| execution_id | 使用语义名称，不加序号 | 当前每个父级运行每类阶段最多一次 |
| SSE 策略 | 只采响应头阶段 | 完整消费流会改变原生行为 |
| 延后内容 | merge、分类、报告、门禁 | 避免迭代二承担父级结论职责 |

开发优先级按以下顺序执行：

```text
不改变原行为
> 不产生错误归属
> 不丢失已知事实
> 指标丰富度
```

## 6. 当前代码基线

### 6.1 迭代一已完成能力

当前已经具备：

- `quality/models.py`：冻结的 `quality.v1` 模型。
- `quality/identifiers.py`：run、execution、case、invocation、request、interface 等身份算法。
- `quality/runtime_context.py`：run 和 case 两类 ContextVar。
- `quality/storage.py`：原子 JSON、JSONL append/read、目录初始化。
- `quality/redaction.py`：质量侧脱敏、规范化和 canonical hash。
- `tests/quality/`：模型、身份、上下文、脱敏和存储测试。

迭代一没有接入 pytest、请求中间件、`run_master.py` 或 Jenkins，符合原阶段边界。

### 6.2 pytest 与运行器现状

- `run_master.py` 先通过 `master_service.collect_test_case_items()` 做 collect-only 预收集。
- 未指定 `-n` 时，`run_master.py` 只调用一次 `pytest.main()`。
- 指定 `-n` 时，先执行并行池，再执行串行池，最多调用两次正式 `pytest.main()`。
- pytest-xdist worker 是独立进程。
- `module/conftest.py` 已经承担资源收集、fixture、Allure 清理和报告生成，不应破坏其现有 hook。
- `master_service.py` 的 collect-only 预收集不能生成质量分片。

### 6.3 请求链路现状

- `BaseRequest._send()` 统一执行 before middleware、HTTP 请求、after/on_exception middleware。
- `RetryExecutor` 每次 retry 都通过 `context_factory()` 创建新的 `RequestContext`。
- 因此每次 retry 可以天然生成一条独立 `RequestMetric`，不需要重写重试循环。
- `BaseRequest._poll_get_with_policy()` 每次轮询都会调用 `_request_without_attach()`。
- 轮询状态在 HTTP 返回后由 `evaluate_polling_response()` 解释，质量层需要显式拿到 `PollingPolicy`。
- SSE 使用 `stream=True`，`requests` 在响应头完成后返回，质量中间件不能主动消费流。
- `BaseRequest` 会把 before/after middleware 异常转换为 `RuntimeError`，因此质量中间件必须自行捕获所有异常。

### 6.4 现有业务线程池

当前已有两处业务并发：

- `module/smoke/test_图片生成异步调用.py`
- `module/smoke/test_call_billing_correctness.py`

它们的作用是验证同一个测试目的下的并发业务行为。迭代二不删除线程池，不改变 `max_workers`，只把原始 `executor.submit()` 改为 `submit_with_context()`。

## 7. 迭代范围与非侵入边界

“保留原生语义”具体定义为：

- 不改变 pytest 收集到的 nodeid、marker 和执行顺序。
- 不改变 xdist 的 worker 数量、分发策略和调度算法。
- 不改变并行池先执行、串行池后执行的顺序。
- 不改变线程池 worker 数量、任务函数、Future 类型和异常传播。
- 不改变 HTTP 请求 method、URL、headers、body、timeout 和 session 行为。
- 不改变重试次数、重试条件、退避时间和最终异常。
- 不改变轮询间隔、超时、状态机和最终异常。
- 不读取或消费 SSE response body。
- 不修改原有 JUnit、Allure 和 pytest 退出码。

允许的最小改造：

- 在原生命周期旁路读取元数据。
- 在请求上下文中增加不发送到服务端的协议、重试和轮询元数据。
- 在默认中间件链中按配置增加 fail-open 质量中间件。
- 在任务提交边界复制 ContextVar。
- 在每次正式 `pytest.main()` 前临时注入质量身份，结束后恢复环境。

## 8. 总体架构

### 8.1 运行级数据流

```text
run_master.py
-> 读取 QUALITY_ENABLE
-> 生成或复用一个 run_id
-> 并行阶段注入 execution_id=parallel-pool
-> pytest-xdist worker 各自写分片
-> 串行阶段注入 execution_id=serial-pool
-> master 写串行分片
-> 返回原 pytest 合并退出码
```

直接执行 pytest 时：

```text
pytest
-> quality plugin 生成或读取 run_id
-> execution_id=manual-pytest
-> 非 xdist 使用 worker_id=master
-> xdist 使用 gw0/gw1/...
```

### 8.2 Case 层数据流

```text
pytest_runtest_protocol(item)
-> 生成 case_id
-> 生成 param_hash
-> 生成 invocation_id
-> set_case_context()
-> 原生 pytest protocol
   -> setup report
   -> call report
   -> teardown report
-> reset_case_context(token)
```

### 8.3 Request 层数据流

```text
QualityMetricsMiddleware.before_request
-> 记录 request_event_id 和 monotonic start

真实 HTTP 请求

after_response / on_exception
-> 读取 run context
-> 读取 case context
-> 生成 RequestMetric
-> collector append request shard
-> 任意异常内部转 IntegrityIssue
```

### 8.4 进程内组件关系

```text
quality.pytest_plugin
-> 初始化 QualityRunContext
-> 初始化进程级 QualityCollector
-> 管理 QualityCaseContext

common.request_middleware
-> 调用 quality.request_metrics
-> 使用同一进程级 QualityCollector

QualityCollector
-> 单进程唯一
-> 线程安全
-> 只写当前 worker 的三个分片
```

## 10. 质量配置设计

在 `quality/config.py` 定义独立配置解析，不把质量开关加入业务 `Settings`，避免质量能力与接口配置耦合。

### 10.1 环境变量

| 环境变量 | 默认值 | 语义 |
| --- | --- | --- |
| `QUALITY_ENABLE` | `0` | 是否启用迭代二采集 |
| `QUALITY_RUN_ID` | 空 | 父级运行 ID；缺失时生成 |
| `QUALITY_EXECUTION_ID` | 空 | 当前 pytest 正式执行阶段 ID |
| `QUALITY_OUTPUT_DIR` | `reports/quality` | 质量产物根目录 |

`QUALITY_ENABLE` 建议接受：

- 真值：`1`、`true`、`yes`、`on`，忽略大小写和首尾空白。
- 假值：空、`0`、`false`、`no`、`off`。
- 其他值视为配置错误，但不得中断 pytest；插件输出警告并禁用本次采集。

### 10.2 配置模型

建议定义冻结 dataclass：

```text
QualityRuntimeConfig
  enabled: bool
  run_id: str | None
  execution_id: str | None
  output_dir: Path
```

职责边界：

- 只解析配置，不创建目录。
- 不持有 pytest Config。
- 不写全局 ContextVar。
- 不在 import 时读取环境变量。
- 由 pytest plugin 或 `run_master.py` 在明确生命周期内调用。

### 10.3 身份补全规则

- `run_master.py` 正式执行时负责提供 `run_id` 和阶段 `execution_id`。
- 直接 pytest 且缺失 `run_id` 时，使用迭代一 `build_run_id()` 生成本地 ID。
- 直接 pytest 且缺失 `execution_id` 时固定使用 `manual-pytest`。
- `QUALITY_RUN_ID` 非空时优先复用，支持 Jenkins 或外部调度器注入。
- `QUALITY_EXECUTION_ID` 在直接 pytest 时可复用；通过 `run_master.py` 时由运行器按阶段覆盖，避免并行池和串行池写入同一分片。

### 10.4 输出目录解析

- 相对路径基于 pytest `rootpath` 或 `run_master.py` 的项目根目录解析。
- 插件和运行器必须得到同一个绝对输出目录。
- 配置读取阶段不删除目录。
- 每个 worker 只初始化属于自己的文件；不同 worker 之间没有清理或覆盖权限。

## 11. 分片采集器设计

在 `quality/collector.py` 建立单进程唯一的 `QualityCollector`。

### 11.1 职责

`QualityCollector` 只负责：

- 持有当前 `QualityRunContext`。
- 计算当前 worker 的分片路径。
- 线程安全写入 `CaseResult`、`RequestMetric`、`IntegrityIssue`。
- 把采集和写入异常转换为完整性问题。
- 向 pytest plugin 和请求中间件提供同一个进程内采集入口。

它不负责：

- 生成 case/request 身份。
- 判断 pytest 状态。
- 判断 HTTP、SSE 或轮询业务状态。
- 归并、去重、分类、聚合或报告。

### 11.2 分片路径

固定生成：

```text
{output_dir}/shards/cases-{execution_id}-{worker_id}.jsonl
{output_dir}/shards/requests-{execution_id}-{worker_id}.jsonl
{output_dir}/shards/integrity-{execution_id}-{worker_id}.jsonl
```

示例：

```text
reports/quality/shards/cases-parallel-pool-gw0.jsonl
reports/quality/shards/requests-parallel-pool-gw0.jsonl
reports/quality/shards/integrity-parallel-pool-gw0.jsonl
reports/quality/shards/cases-serial-pool-master.jsonl
```

迭代二不创建 `failures-*.jsonl`，因为 `FailureRecord` 属于迭代三。

### 11.3 初始化语义

- collector 初始化时调用 `ensure_quality_dirs()`。
- 当前进程拥有的三个分片文件在 session 开始时创建或清空一次。
- 初始化完成后只允许 append，不在单次 pytest session 中截断。
- 并行池与串行池使用不同 `execution_id`，因此串行阶段不会清空并行阶段分片。
- 每个 xdist worker 只清空自己的 `worker_id` 文件，不接触其他 worker 文件。
- collect-only 和禁用模式不创建目录、不创建空文件。

清空当前 session 自有分片的原因：固定文件名不包含 `run_id`，若直接 append 到上一次运行文件，会把不同运行的事实混在同一分片。初始化清空只作用于当前 `execution_id + worker_id`，不扩大删除范围。

### 11.4 线程安全

同一 xdist worker 内可能存在多个业务线程同时完成请求。collector 必须使用进程内锁保护“序列化 + 单行写入”。

建议使用一个 `threading.RLock` 或按文件拆分的锁，要求：

- 锁只覆盖质量记录写入，不包裹真实 HTTP 请求。
- 不改变业务线程调度。
- 一条 JSONL 在锁内完整写入。
- collector 必须是进程内唯一实例，避免多个实例持有不同锁却写同一文件。

### 11.5 进程级注册

提供最小 API：

```text
configure_collector(run_context) -> QualityCollector
get_collector(default=None) -> QualityCollector | None
reset_collector() -> None
```

这里允许进程级保存 collector，因为它代表“当前 worker 的文件写入所有权”；但禁止用同样方式保存当前 case，因为 case 会随测试函数变化并且需要线程上下文隔离。

### 11.6 写入 API

建议提供：

```text
record_case(result: CaseResult) -> bool
record_request(metric: RequestMetric) -> bool
record_integrity(issue: IntegrityIssue) -> bool
capture_integrity(source, code, message, related_id=None, severity=warn) -> bool
```

返回值只表达是否成功写入，调用方不得因为 `False` 改变测试结果。

### 11.7 双重失败处理

```text
写 case/request 失败
-> 尝试写 write_failed IntegrityIssue
-> integrity 写入也失败
-> 输出最小 terminal/stderr 警告
-> 不再向外抛出
```

警告内容必须脱敏，不输出请求正文、完整 URL query、Authorization、Cookie 或原始参数。

## 12. pytest 插件设计

在 `quality/pytest_plugin.py` 实现插件，通过 `module/conftest.py` 的 `pytest_plugins` 显式注册。插件始终可加载，但 `QUALITY_ENABLE=0` 时所有 hook 都是无副作用 no-op。

### 12.1 注册方式

`module/conftest.py` 增加：

```python
pytest_plugins = (quality.pytest_plugin,)
```

不把 `--quality-enable` 固化到 `pytest.ini addopts`，本迭代先使用环境变量控制，便于回退和分阶段接入 CI。

### 12.2 pytest_configure

职责：

1. 解析质量配置。
2. collect-only 时直接返回。
3. 判断当前进程是非 xdist master、xdist controller 还是 xdist worker。
4. 补全 run、execution、worker 身份。
5. controller 只保存配置并向 worker 传递，不创建 collector。
6. 非 xdist master 或 worker 初始化 `QualityRunContext` 和 collector。
7. 设置 run ContextVar，并保存 Token 用于最终恢复。

任何初始化异常都不得阻止 pytest configure。无法建立 collector 时，本进程禁用质量采集并输出一次警告。

### 12.3 xdist 配置传递

直接执行 `pytest -n ...` 且未提供 `QUALITY_RUN_ID` 时，run_id 必须由 controller 生成一次，再通过 `pytest_configure_node(node)` 写入 worker input。

建议传递：

```text
quality_runtime:
  enabled
  run_id
  execution_id
  output_dir
```

worker 优先读取 `workerinput` 中的质量配置，避免每个 worker 各自生成不同 run_id。

`run_master.py` 已显式注入身份时，controller 仍可传递相同值，但不得重新生成或改写。

### 12.4 controller 不落盘

xdist controller 会收到 worker 上报的测试报告。如果 controller 和 worker 都写 `CaseResult`，会产生重复事实。

规则：

- xdist worker 写 case/request/integrity 分片。
- xdist controller 不初始化 collector，不写任何分片。
- 非 xdist 执行时，当前 pytest 进程使用 `worker_id=master` 写分片。

### 12.5 pytest_runtest_protocol

使用 hookwrapper 包围完整原生 protocol：

```text
构建 QualityCaseContext
-> token = set_case_context(context)
-> yield 原生 runtest protocol
-> finally reset_case_context(token)
```

必须使用 Token reset，不能只在结束时 `clear_case_context()`，否则嵌套调用或测试工具内部上下文可能被破坏。

如果身份构建失败：

- 写 `case_context_build_failed` 完整性问题。
- 不设置错误上下文。
- 继续执行原测试。

### 12.6 pytest_runtest_logreport

每个真实 pytest phase 生成一条 `CaseResult`：

| pytest report | `CasePhase` |
| --- | --- |
| `setup` | `setup` |
| `call` | `call` |
| `teardown` | `teardown` |

不合成没有发生的 phase。例如 setup 失败后没有 call，就不伪造 call 记录。

`start_time` 和 `end_time` 使用 timezone-aware UTC 时间。可在 report 到达时取结束时间，再用 `report.duration` 回推开始时间；`duration_ms = report.duration * 1000`。

### 12.7 状态映射

| 条件 | `CaseStatus` |
| --- | --- |
| `report.passed` 且无 `wasxfail` | `passed` |
| `report.failed` 且 phase=`call` | `failed` |
| `report.failed` 且 phase=`setup/teardown` | `error` |
| `report.skipped` 且无 `wasxfail` | `skipped` |
| `report.skipped` 且有 `wasxfail` | `xfailed` |
| `report.passed` 且有 `wasxfail` | `xpassed` |

迭代二尚未实现重跑或策略修正，因此：

```text
raw_status = final_status
failure_id = None
evidence_refs = {}
```

### 12.8 collection 处理

`pytest_collection_modifyitems` 只做 nodeid 可规范化预检查，不生成测试函数 `CaseResult`。

collection failure 没有可靠的测试函数 invocation 身份，因此不伪造 case；通过 `pytest_collectreport` 记录：

```text
IntegrityIssue(code=collection_failed)
```

`CasePhase.COLLECTION` 保留在契约中，但本迭代不把模块、类 collector 冒充测试函数 case。

### 12.9 session 结束

- `pytest_sessionfinish` 只做 collector flush 或状态检查，不归并、不生成报告。
- `pytest_unconfigure` 在 finally 语义下 reset run ContextVar、reset collector 和清理插件进程状态。
- 清理失败只能产生警告，不能覆盖 pytest exit status。

## 13. case 与 invocation 身份构建

### 13.1 case_id

直接复用：

```text
build_case_id(item.nodeid)
```

参数段会被移除，因此：

```text
module/test_x.py::TestA::test_b[p1]
module/test_x.py::TestA::test_b[p2]
```

共享：

```text
case_id = module/test_x.py::TestA::test_b
```

### 13.2 param_hash

未参数化用例：

```text
build_param_hash(None)
```

参数化用例建议使用：

```text
{
  parameter_id: normalize_nodeid(item.nodeid).parameter_id,
  params: item.callspec.params,
}
```

然后交给 `build_param_hash()` 先脱敏、再 canonicalize、最后哈希。

同时包含 parameter id 和真实 params 的原因：

- 相同测试函数的不同参数值应产生不同 invocation。
- pytest 对重复参数值可能生成带序号的 parameter id，需要避免 invocation 冲突。
- parameter id 可能含敏感值，必须经过质量侧脱敏后才允许进入哈希。

不得把原始 params 写入 JSONL。

### 13.3 invocation_id

复用迭代一算法：

```text
build_invocation_id(run_id, case_id, param_hash)
```

同一父级 run 内，同一测试函数和同一参数实例的 setup/call/teardown 共享 invocation_id；并发请求也共享该 invocation_id。

### 13.4 phase 记录唯一键

迭代三归并时使用：

```text
invocation_id + phase
```

迭代二只负责稳定产出，不在 writer 中去重。插件自身不得对同一个 report 重复调用 collector。

## 14. 请求上下文扩展

`RequestContext.attributes` 已经承担中间件元数据，但协议和策略属于多个组件共同读取的稳定信息。建议在 `common/request_context.py` 增加显式、带默认值的字段：

```text
protocol: str = http
retry_policy: RetryPolicy | None = None
polling_policy: PollingPolicy | None = None
```

如果为避免类型依赖选择继续使用 attributes，也必须定义集中常量，禁止 `BaseRequest` 和质量层各自硬编码 key。两种实现只能选一种，优先显式字段。

这些字段：

- 不进入 `requests.Session.request()` 参数。
- 不改变公共 `get/post/request/poll_get` 调用形式。
- 不改变业务请求内容。
- 只服务于旁路观测和状态解释。

### 14.1 协议赋值

- 普通 `request/get/post/...` 默认 `protocol=http`。
- `stream=True` 的 BaseRequest 请求设置 `protocol=sse`。
- `_poll_get_with_policy()` 调用 `_request_without_attach()` 时显式设置 `protocol=polling` 和当前 `PollingPolicy`。
- polling 优先于 stream 自动判断，避免协议被错误覆盖。

### 14.2 retry_policy 传递

`_send_with_retry()` 创建每个 `RequestContext` 时写入当前 `RetryPolicy`，供质量层判断该响应或异常是否符合 retry 条件。

不修改 `RetryExecutor` 的循环和等待逻辑；现有 `attempt_index`、`max_attempts` 仍可保存在 context attributes 中。

### 14.3 BaseRequest 内部签名

允许给以下内部方法增加可选元数据参数：

- `_build_request_context()`
- `_send_with_retry()`
- `_request_without_attach()`

新增参数必须有默认值，不能改变现有业务调用方。

## 15. 请求指标适配器设计

在 `quality/request_metrics.py` 把“如何从 RequestContext、Response、Exception 构建 `RequestMetric`”集中管理。

建议拆分：

```text
start_request_capture(context)
record_response(context, response)
record_exception(context, error)
infer_protocol(context)
resolve_business_status(...)
extract_server_request_id(response)
extract_usage(response, protocol)
resolve_retryable(context, response_or_error)
```

### 15.1 before_request

写入仅存在于内存的 context metadata：

- `request_event_id = new_request_event_id()`
- `started_monotonic = time.perf_counter()`
- `metric_written = False`

不在 before 阶段写 JSONL，因为请求还没有结果。

### 15.2 after_response

构建字段：

| 字段 | 来源 |
| --- | --- |
| run/execution/worker | `QualityRunContext` |
| case/invocation | `QualityCaseContext` |
| request_event_id | before capture |
| server_request_id | 响应头或安全 JSON 字段 |
| interface_id | method + 模板化 path + protocol |
| method | `RequestContext.method` |
| url_template | 模板化 path，不含 host/query |
| protocol | request context |
| attempt_index | context attributes，缺失时为 1 |
| status_code | response.status_code |
| business_status | 协议状态规则 |
| duration_ms | 当前 monotonic - start |
| timeout | `False` |
| retryable | 现有 retry policy 判断 |
| error_type | `None` |
| usage | 安全提取结果 |
| cost | 默认 `source=none` |

### 15.3 on_exception

构建规则：

- `status_code=None`
- `business_status=failed`
- `timeout=isinstance(error, requests.Timeout)`
- `error_type=type(error).__name__`
- `retryable` 使用现有 `should_retry_exception()` 和 context 中的 policy。
- `usage` 为空，`cost.source=none`。

不得保存完整异常字符串，因为异常可能包含 URL query、header 或 body。完整性 message 和后续失败摘要必须走质量侧脱敏。

### 15.4 防重复

同一个 RequestContext 只能写一条 metric：

- after_response 成功写入后设置 `metric_written=True`。
- on_exception 写入后设置 `metric_written=True`。
- 重复调用时不再写入，可生成 `duplicate_request_metric` info 级完整性问题，或静默保护；优先避免重复而不是依赖迭代三去重。

### 15.5 缺失 case context

如果 run/collector 存在但 case context 缺失：

```text
不构造 RequestMetric
-> capture_integrity(
     source='request_metrics',
     code='missing_case_context',
     related_id=request_event_id
   )
```

该规则用于暴露未传播上下文的线程、测试生命周期外请求或框架缺陷。

### 15.6 url_template

`quality/identifiers.py` 当前内部已有路径模板化能力。建议新增公共函数：

```text
build_url_template(url_or_path) -> str
```

`build_interface_id()` 和 `RequestMetric.url_template` 共用该函数，避免两套路径规范化规则漂移。

输出禁止包含：

- scheme 和 host。
- query string。
- UUID、长数字、长十六进制和高基数资源 ID。

## 16. HTTP、SSE、轮询与重试口径

### 16.1 普通 HTTP

| 结果 | `business_status` |
| --- | --- |
| 200-299 | `success` |
| 非 2xx response | `failed` |
| transport exception | `failed` |

边界说明：HTTP 200 中的业务错误结构没有跨接口统一标准。迭代二不根据任意 `code/message/error` 字段做猜测，避免把正常响应误判为失败。业务断言失败由 pytest CaseResult 表达。

### 16.2 SSE

识别条件：`RequestContext.protocol == sse`。

| 结果 | 处理 |
| --- | --- |
| 2xx response headers 返回 | `business_status=unknown` |
| 非 2xx response | `business_status=failed` |
| transport exception | `business_status=failed` |

限制：

- `duration_ms` 只表示 header latency。
- 不遍历 `response.iter_lines()`。
- 不访问 `response.content`、`response.text` 或 `response.json()`。
- `usage` 全部为空。
- 不改变调用方关闭 response 或消费 stream 的责任。

### 16.3 轮询

质量层复用 `evaluate_polling_response(response, polling_policy)`，不实现第二套状态机。

| `PollingState` | `business_status` |
| --- | --- |
| `PENDING` | `unknown` |
| `SUCCESS` | `success` |
| `FAILURE` | `failed` |
| `UNKNOWN` | `failed` |

若质量层解释 polling response 失败：

- 不影响原 `BaseRequest` 随后的真实解释和异常。
- 当前 metric 使用 `business_status=failed`，`error_type` 记录安全的异常类型名。
- 写 `polling_metric_evaluation_failed` 完整性问题。

每次 `_request_without_attach()` 都产生独立 request event。每个新的 polling HTTP 请求在没有 transport retry 时 `attempt_index=1`；若该次 polling 请求内部触发 retry，则按该次请求的 retry 顺序递增。迭代二不新增 `poll_sequence_index` 字段，轮询全局序列继续由现有 `PollingTransition` 日志表达。

轮询总超时发生在若干真实 HTTP 请求之后，不额外伪造一条 HTTP RequestMetric；最终 `PollingTimeoutError` 由 Case 层记录为测试失败或错误。

### 16.4 重试

- 首次请求和每次 retry 都由新 `RequestContext` 触发质量中间件。
- 每个 context 生成新的 `request_event_id`。
- 直接使用现有 `attempt_index`。
- 首次失败记录不得被最终成功覆盖。
- `retryable` 表示当前事件按现有 policy 是否具备重试条件，不表示后续一定完成重试。
- 达到最大次数后仍可出现 `retryable=true`，因为“符合条件”和“还有剩余次数”是两个不同事实。

### 16.5 server_request_id

按顺序尝试安全、明确的来源：

1. `x-oneapi-request-id`
2. `x-request-id`
3. `request-id`
4. 非 SSE JSON body 中明确的 `request_id`

不把通用 `id` 字段当作 server request id，因为它可能是任务 ID、模型 ID 或资源 ID。

提取失败返回 `None`，不影响请求结果。

### 16.6 usage 与 cost

非 SSE JSON response 可安全尝试读取：

- `usage.input_tokens`
- `usage.prompt_tokens` 作为 input fallback
- `usage.output_tokens`
- `usage.completion_tokens` 作为 output fallback

只接受非负整数；类型不合法时忽略并写可选 info 级完整性问题，不中断请求。

`media_count` 本迭代不根据任意 `data` 数组长度推断，避免把分页列表误当媒体数量；缺少明确 usage 字段时保持 `None`。

成本采集不属于迭代二：

```text
amount = None
source = none
price_version = None
```

## 17. 请求中间件接入

### 17.1 QualityMetricsMiddleware

在 `common/request_middleware.py` 增加薄中间件，复杂转换逻辑委托给 `quality.request_metrics`。

```text
before_request -> safe_start_request_capture
after_response -> safe_record_response
on_exception -> safe_record_exception
```

三个方法自身必须 `try/except BaseException` 或至少 `Exception`，保证不会把采集错误传给 `BaseRequest`。不应捕获 `KeyboardInterrupt/SystemExit` 后完全静默；若采用 `BaseException`，必须对进程终止类异常做明确重新抛出策略。优先捕获 `Exception`。

### 17.2 默认中间件链

`default_request_middlewares()` 在 collector 已启用时增加质量中间件；禁用时返回与当前相同的原中间件列表。

建议顺序：

```text
QualityMetricsMiddleware
MediaResourceMiddleware
RedactionMiddleware
LoggingMiddleware
```

质量中间件放在首位可以尽早记录计时起点。它不读取原始 kwargs，不写请求载荷，因此不依赖 RedactionMiddleware 的输出。

若后续中间件在 before 阶段失败，`BaseRequest` 当前不会调用 on_exception；这种框架级失败由 CaseResult 体现，迭代三再分类，不在本迭代改写 `_send()` 异常结构。

### 17.3 自定义 middleware 列表

调用方显式传入 `middlewares=[...]` 时，保持“完全由调用方控制列表”的原有语义，不强行注入质量中间件。生产 SmokeRequest 使用默认链路，质量测试可直接测试适配器。

### 17.4 禁用模式

`QUALITY_ENABLE=0` 时：

- 不配置 collector。
- 默认中间件列表不增加质量中间件。
- 不创建质量目录。
- 不读取 response body。
- 不增加请求级锁。
- 原有中间件数量、顺序和行为保持不变。

## 18. 线程池上下文传播

在 `common/context_executor.py` 新增：

```python
def submit_with_context(executor, function, /, *args, **kwargs):
    context = copy_context()
    return executor.submit(context.run, function, *args, **kwargs)
```

### 18.1 设计约束

- 每次提交调用一次 `copy_context()`。
- 返回标准 `concurrent.futures.Future`。
- 不创建 executor。
- 不捕获任务异常。
- 不改变任务返回值。
- 不等待 Future。
- 不改变 `as_completed()` 行为。
- 不只复制质量 ContextVar，而是使用 Python 原生 Context 复制机制。

### 18.2 调用点改造

两处改为：

```text
executor.submit(fn)
-> submit_with_context(executor, fn)
```

目标文件：

- `module/smoke/test_图片生成异步调用.py`
- `module/smoke/test_call_billing_correctness.py`

不得改变任务函数、任务数量、index 映射或结果排序。

### 18.3 为什么不能共享同一个 Context

同一个 `Context` 不能被多个线程同时进入。若在循环外只调用一次 `copy_context()`：

```text
多个 worker 并发 context.run
-> RuntimeError: context is already entered
```

因此 fresh context per task 是正确性要求，不是性能优化。

### 18.4 未使用 helper 的线程

若未来新增线程池但仍直接 `executor.submit()`：

- 子线程请求没有 case context。
- 请求指标不落盘。
- integrity 分片出现 `missing_case_context`。

这使错误用法可见，同时避免错误归属。

## 19. run_master.py 最小接入

`run_master.py` 只负责父级身份编排，不承担迭代三的 merge。

### 19.1 run_id

在一次 `run()` 开始时：

1. 若 `QUALITY_ENABLE` 未启用，不生成质量身份。
2. 若存在非空 `QUALITY_RUN_ID`，整个 run 复用该值。
3. 否则调用 `build_run_id()` 生成一次。
4. Jenkins 环境同时存在 `JOB_NAME` 和 `BUILD_NUMBER` 时可传给 `build_run_id()`；缺一时按本地运行生成，避免半完整 Jenkins 身份。

无论后续执行一个还是两个 pytest 阶段，run_id 都不能变化。

### 19.2 execution_id

| 代码路径 | execution_id |
| --- | --- |
| `not numprocesses` 的单次执行 | `serial-pool` |
| `_run_pytest(parallel_cases...)` | `parallel-pool` |
| `_run_serial_pool(serial_cases...)` | `serial-pool` |

当前运行器每种阶段最多执行一次，因此不增加数字序号。若未来一个父级 run 中同类阶段需要执行多次，必须先扩展命名设计，不能静默复用导致分片覆盖。

### 19.3 临时环境注入

为 `_run_pytest()` 增加可选质量身份参数，或增加上下文管理器：

```text
temporary_quality_environment(
  QUALITY_RUN_ID,
  QUALITY_EXECUTION_ID,
  QUALITY_OUTPUT_DIR
)
```

要求：

- 调用 `pytest.main()` 前设置。
- `pytest.main()` 返回或抛异常后恢复原环境。
- 原环境不存在的变量应删除，不写成空字符串。
- 不永久覆盖用户 shell 环境。
- 不改变 pytest args。

### 19.4 collect-only 预收集

`master_service.collect_test_case_items()` 在正式 run_id 编排前执行也可以，因为插件检测 `collectonly` 后必须 no-op。

强约束：

- 预收集不创建 quality 目录。
- 预收集不清空正式分片。
- 预收集不写 case、request、integrity 文件。

### 19.5 迭代边界

本迭代 `run_master.py` 不执行：

- `quality.cli merge`
- `quality.cli report`
- `run.json` 写入
- Jenkins artifact 修改
- 影子门禁

函数最终仍返回现有 `_merge_exit_codes(results)`。

## 20. xdist 与并串混合责任边界

### 20.1 非并行执行

```text
run_id = R
execution_id = serial-pool
worker_id = master
```

输出：

```text
cases-serial-pool-master.jsonl
requests-serial-pool-master.jsonl
integrity-serial-pool-master.jsonl
```

### 20.2 并行池

```text
run_id = R
execution_id = parallel-pool
worker_id = gw0 / gw1 / ...
```

每个 worker 只写自己的三个分片。controller 不写 `master` 分片。

### 20.3 串行池

并行池结束后，同一父级进程再次调用 pytest：

```text
run_id = R
execution_id = serial-pool
worker_id = master
```

串行池不得清理 `parallel-pool-*` 文件。

### 20.4 直接 pytest -n

```text
run_id = controller 生成或环境提供
execution_id = manual-pytest 或环境提供
worker_id = gw*
```

controller 通过 workerinput 保证所有 worker 使用相同 run_id。

### 20.5 空池

- 并行池为空时不生成 `parallel-pool` execution。
- 串行池为空时不生成 `serial-pool` execution。
- 不为未执行阶段创建虚假空分片。

## 21. 完整性问题设计

迭代二建议冻结以下 code：

| code | source | 场景 | severity |
| --- | --- | --- | --- |
| `quality_config_invalid` | `pytest_plugin` | 环境变量不合法 | `warn` |
| `collector_init_failed` | `collector` | 目录或文件初始化失败 | `error` |
| `case_context_build_failed` | `pytest_plugin` | case/invocation 身份构建失败 | `error` |
| `case_write_failed` | `collector` | CaseResult 写入失败 | `error` |
| `request_write_failed` | `collector` | RequestMetric 写入失败 | `error` |
| `integrity_write_failed` | `collector` | IntegrityIssue 自身写入失败 | `error`，仅终端可见 |
| `missing_case_context` | `request_metrics` | 请求没有真实用例上下文 | `warn` |
| `request_capture_failed` | `request_metrics` | 请求指标构建异常 | `warn` |
| `polling_metric_evaluation_failed` | `request_metrics` | 轮询状态解释失败 | `warn` |
| `collection_failed` | `pytest_plugin` | pytest collection error | `error` |

### 21.1 message 规则

- message 只保存组件、异常类型和脱敏摘要。
- 不保存完整 traceback。
- 不保存请求 body。
- 不保存 URL query。
- 不保存 header 值。
- 不保存原始 pytest 参数。

### 21.2 related_id

优先关联：

- case 问题：`invocation_id` 或 `case_id`。
- request 问题：`request_event_id`。
- collection 问题：规范化 nodeid；无法规范化时保存脱敏短摘要。

### 21.3 无法写 integrity

如果输出目录不可写，`IntegrityIssue` 也无法落盘。此时只允许：

- 向 pytest terminal reporter 或 stderr 输出一条脱敏警告。
- 继续原测试。
- 不循环重试写文件。
- 不创建替代临时目录，避免产物位置不可预测。

## 26. 验收标准

### 26.1 Case 层

- 一个测试函数的所有参数实例共享稳定 `case_id`。

- setup/call/teardown 共享 invocation 身份并正确映射 phase。
- pass、fail、error、skip、xfail、xpass 状态正确。
- 上下文在每个测试 protocol 后恢复，不污染下一个用例。

### 26.2 Request 层

- 每个真实 HTTP attempt 有独立 `request_event_id`。
- retry attempt_index 与现有 RetryExecutor 一致。
- RequestMetric 能关联当前 case/invocation。
- 缺失上下文时不写非法 RequestMetric，只写 `missing_case_context`。
- 普通 HTTP、SSE、polling 状态符合已确认口径。
- SSE 未被质量层消费。
- 请求正文、敏感 header 和完整 query 不进入产物。

### 26.3 并发与 xdist

- 现有线程池数量和任务语义不变。
- 使用 helper 后子线程继承 case context。
- 多线程写同一 worker request 分片不产生损坏 JSONL。
- xdist 每个 worker 写独立文件。
- controller 不重复写 worker CaseResult。
- 并行池和串行池共享 run_id，execution_id 分别为 `parallel-pool`、`serial-pool`。

### 26.4 fail-open

- collector、模型构建、路径规范化和指标提取异常不能改变测试结果。
- 质量中间件异常不能替换真实请求异常。
- 无法写 integrity 时只输出警告。
- pytest 原退出码保持不变。

- `QUALITY_ENABLE=0` 时不产生质量目录和分片。

- smoke collection 数量不减少。

## 27. 风险与控制

| 风险 | 因果 | 控制 |
| --- | --- | --- |
| xdist controller 重复写 | controller 同样收到 logreport | controller 不初始化 collector |
| worker run_id 不一致 | worker 各自生成身份 | controller 生成并通过 workerinput 传递 |
| 线程请求缺少 case | ContextVar 不自动跨线程 | fresh `copy_context()` per submit |
| 多线程 JSONL 损坏 | 同进程并发 append | 进程级唯一 collector + 锁 |
| 串行阶段覆盖并行分片 | execution_id 相同或错误清理 | 固定不同语义 ID，只清理自有文件 |
| 采集异常覆盖业务异常 | middleware 异常向外传播 | 所有质量入口 fail-open |
| SSE 被提前消费 | 通用 usage/body 提取 | SSE 禁止访问 body |
| HTTP 200 业务失败误判 | 缺少统一业务协议 | 明确记录为 HTTP success，Case 层负责断言 |
| polling 状态重复实现漂移 | 质量层另写状态机 | 复用 `evaluate_polling_response()` |
| request id 误提取 | 把通用 id 当 request id | 只接受明确 header/request_id |
| 上次运行数据混入 | 固定 shard 名 append | session 初始化清空自有 shard |
| 直接 pytest xdist 身份分裂 | worker 独立 fallback | controller 配置下发 |

迭代二不得提前在 writer 中做跨 worker 去重或最终状态聚合。

## 30. 实施前决策关闭情况

| 问题 | 最终决策 |
| --- | --- |
| 一个 case 如何定义 | 一个测试函数一个稳定 case_id |
| 参数化如何区分 | 每个参数实例一个 invocation_id |
| 同一用例并发请求如何归属 | 共享 case/invocation，各自 request_event_id |
| 是否删除线程池 | 不删除，保留业务并发语义 |
| 如何跨线程传播 | `submit_with_context()` fresh copy per task |
| 缺失上下文是否写 orphan | 不写 RequestMetric，写 IntegrityIssue |
| 普通 HTTP 状态 | 2xx success，其他/异常 failed |
| polling 状态 | 复用 PollingPolicy |
| SSE 范围 | header latency，unknown，不消费流 |
| execution_id 是否带序号 | 不带，使用语义名称 |
| 迭代二是否 merge/report | 不做，留给后续迭代 |

当前方案不存在需要继续阻断开发的产品语义问题。若实际开发发现以下任一情况，必须停下来确认：

- 一个父级 run 内需要执行两次同名并行池或串行池。
- 需要把 HTTP 200 业务错误统一识别为 failed。
- 需要采集 SSE 首 Token 或完整流耗时。
- 需要修改 `quality.v1` 必填字段。
- 需要改变原 RetryExecutor、PollingPolicy 或线程池业务语义。
