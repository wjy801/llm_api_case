> 日期：2026-08-05
> 状态：待执行
> 所属总方案：`dev_plan/离线框架能力分类用例与黄金路径详细执行方案_20260805.md`
> 阶段性质：合同冻结，不实现本地服务和测试代码

## 1. 阶段目标

阶段0只解决一个问题：在实现开始前，让本地服务、分类用例、黄金路径和报告验收对同一场景只有一种解释。

需要冻结的内容包括：

- HTTP接口、请求、响应、Header和状态码；
- Retry与Polling的确定性响应序列；
- 每个分类用例的唯一责任；
- 黄金路径包含和排除的能力；
- 稳定nodeid、operation name、model ID和角色；
- Case级、Runner级和多轮级验收事实；
- 无外网、无真实密钥、无资源残留等非功能约束。

阶段0完成后，阶段1只能实现已冻结合同，不得在编码时临时发明接口、状态或验收规则。

## 2. 第一性原理与TOC判断

### 2.1 问题本质

离线示例的可信性来自因果可解释，而不是来自用例数量：

```text
给定明确场景
→ 本地服务返回唯一响应序列
→ 框架产生可预测请求、迁移和结果
→ 分类用例能够定位能力边界
→ 黄金路径能够证明能力组合
→ 报告能够消费同一执行事实
```

如果协议不冻结，则会出现：

```text
服务实现自行决定响应
＋ 用例自行决定预期
＋ 报告自行解释指标
→ 三套事实不一致
→ 失败无法归因
```

### 2.2 当前约束

TOC首要约束是“确定性离线协议”，而不是本地HTTP服务器的技术实现。阶段0必须先解除这个约束，阶段1之后的开发才有稳定输入。

### 2.3 决策原则

1. 合同优先于实现便利。
2. 使用显式Python数据结构，不引入YAML场景DSL。
3. 状态由计数器和固定序列驱动，不使用随机数。
4. 墙钟时间只用于框架真实deadline验证，不用于控制业务状态。
5. 分类用例负责互斥异常分支，黄金路径只负责成功组合链。
6. 报告层只消费事实，不反向影响业务用例设计。

## 6.3 任务0.3：冻结HTTP协议

合同必须为每个端点记录：

- 方法和路径；
- 请求Header和请求体；
- 响应状态码、Header、Cookie和响应体；
- 服务状态变化；
- 调用计数；
- 使用该端点的用例；
- 是否属于workload或control。

### 计划端点

| 方法 | 路径 | 角色 | 用途 |
|---|---|---|---|
| POST | `/v1/echo` | workload | Request、Header和payload不变性 |
| GET | `/v1/transient` | workload | GET 503/429重试 |
| POST | `/v1/idempotent-operation` | workload | POST幂等重试 |
| POST | `/v1/media/generations` | workload | 创建异步媒体任务 |
| GET | `/v1/media/tasks/{task_id}` | workload | Polling状态机 |
| DELETE | `/v1/media/tasks/{task_id}` | control | TestContext资源清理 |
| GET | `/v1/context` | control | JSON/Header/Cookie/Regex提取 |
| GET | `/v1/audit` | control | 并发上下文和Header隔离 |
| GET | `/v1/contracts/{mode}` | control | Assertions与Schema诊断 |
| GET | `/assets/input.png` | control | 输入资源捕获 |
| GET | `/assets/output.png` | control | 输出资源捕获 |

不使用完整外部URL作为业务路径。资源响应中的URL由本地服务按自身loopback base URL生成。

## 6.4 任务0.4：冻结请求和响应结构

### 通用Header

Request Client使用：

```text
Authorization: Bearer offline-example-key
Content-Type: application/json
Accept: application/json
User-Agent: 沿用BaseRequest默认值
```

`offline-example-key`只用于观察脱敏和服务认证传递，不具备任何真实权限。

### Echo请求

请求体：

```json
{
  "model": "offline-media-model",
  "prompt": "offline framework example",
  "metadata": {
    "case": "request_pipeline"
  }
}
```

响应：HTTP 200，返回服务实际收到的body和允许公开的Header摘要。Authorization不得原样返回到响应体，避免测试产物保存完整占位认证值。

### 创建任务请求

请求体：

```json
{
  "model": "offline-media-model",
  "prompt": "offline framework example",
  "input": {
    "media": {
      "url": "<loopback-base-url>/assets/input.png"
    }
  }
}
```

响应：HTTP 202。

```json
{
  "task_id": "offline-task-001",
  "status": "queued",
  "model": "offline-media-model",
  "trace_id": "offline-trace-001"
}
```

响应Header：

```text
X-Request-ID: offline-request-001
Set-Cookie: offline_session=offline-session-001; Path=/
```

### Polling成功响应

pending响应只变化`status`：`queued`、`running`。

最终HTTP 200响应：

```json
{
  "task_id": "offline-task-001",
  "status": "succeeded",
  "model": "offline-media-model",
  "trace_id": "offline-trace-001",
  "result": {
    "url": "<loopback-base-url>/assets/output.png"
  }
}
```

最终响应继续返回同一`X-Request-ID`和Cookie，保证黄金路径可从最终响应完成上下文提取。

### Polling失败响应

```json
{
  "task_id": "offline-task-001",
  "status": "failed",
  "error": {
    "code": "OFFLINE_TASK_FAILED",
    "type": "controlled_offline_failure",
    "message": "controlled failure"
  }
}
```

### Context响应

HTTP 200：

```json
{
  "data": {
    "task_id": "offline-task-001"
  },
  "message": "trace=offline-trace-001"
}
```

Header和Cookie使用与任务响应相同的固定值。

### Audit请求和响应

请求使用单次Header：

```text
X-Audit-Name: audit-a 或 audit-b
```

响应：

```json
{
  "audit_name": "audit-a",
  "task_id": "offline-task-001",
  "status": "recorded"
}
```

并发断言比较集合`{"audit-a", "audit-b"}`，不依赖完成顺序。

### DELETE响应

- 已存在任务：HTTP 204，无响应体；
- 不存在任务：结构化HTTP 404；
- 成功后`deleted_task_ids`包含任务ID，`tasks`不再包含任务。

### 静态资源

- 输入和输出使用不同的固定小型PNG内容；
- Content-Type为`image/png`；
- 固定Content-Length；
- 阶段0合同记录实施时计算的SHA-256，不手写未经验证的Hash；
- 大文件场景通过重复固定字节产生，大小明确，不使用随机数据。

## 6.5 任务0.5：冻结Retry与Polling场景

场景使用显式Python不可变数据描述，不引入字符串脚本或配置文件。

建议后续实现最小`OfflineServiceScenario`数据类，字段只表达固定响应序列、资源大小和少量延迟。不得演化为通用Mock DSL。

### Retry场景

| 场景 | Transport序列 | 策略 | 必须断言 |
|---|---|---|---|
| GET 503挽救 | 503 → 200 | max_attempts=2、delay=0、无jitter | 最终200，调用2次 |
| GET 429挽救 | 429(Retry-After=0) → 200 | max_attempts=2 | 最终200，调用2次 |
| 幂等POST | 503 → 200 | Idempotency-Key + max_attempts=2 | 最终200，调用2次 |
| 非幂等POST | 503 → 200可用但不应继续 | 无幂等Key | 最终503，调用1次 |

不通过真实长等待测试Retry；等待值为0或极小固定值。

### Polling场景

| 场景 | HTTP/业务序列 | 结果 |
|---|---|---|
| 成功 | 503 → queued → running → succeeded | 返回最终响应 |
| 失败 | queued → failed | `PollingFailedError` |
| 未知 | queued → paused | `PollingUnknownStateError` |
| 超时 | running持续返回 | `PollingTimeoutError` |

成功场景的关键计数：

```text
Transport请求：4次
Retry挽救：1个请求组
Polling业务迁移：queued、running、succeeded，共3次
```

其中503是Retry attempt，不是Polling业务状态，不应进入业务状态迁移列表。

超时场景受真实墙钟调度影响，不冻结精确请求次数，只冻结以下不变量：

- 至少获得一次running响应；
- deadline后不再开始新请求；
- 最后状态和最后响应被保留；
- 最终异常为`PollingTimeoutError`；
- 单用例目标耗时小于0.5秒。

## 6.8 任务0.8：冻结黄金路径

### 包含步骤

```text
1. 启动独立loopback服务
2. 创建四件套对象
3. 构建包含本地输入资源的payload
4. 注册ASYNC_TASK逻辑调用
5. POST创建任务并得到task_id
6. 首次Polling transport返回503
7. Retry在同一请求组内挽救
8. Polling观察queued、running、succeeded
9. 捕获本地输出文件
10. 从最终响应提取JSON、Header、Cookie和Regex值
11. submit_with_context并发执行audit-a和audit-b
12. 验证状态码、JSONPath、Schema和领域关系
13. DELETE清理任务
14. 验证服务状态、Session、线程和临时资源回收
```

### 排除步骤

- 不在黄金路径中验证failed、unknown和timeout；
- 不捕获并吞掉核心业务异常；
- 不直接读取Quality、Metrics或Flaky内部文件；
- 不运行真实接口；
- 不人为制造随机失败；
- 不添加`serial`；
- 不使用SSE。

### 固定事实

- 黄金路径最终pytest结果为PASSED；
- 存在一次可挽救503；
- 最终Polling状态为succeeded；
- audit结果不依赖线程顺序；
- 任务最终被删除；
- 原始payload执行前后相等；
- 所有请求主机为`127.0.0.1`。

## 6.9 任务0.9：冻结验收证据层次

### Case级证据

由业务用例直接断言：

- HTTP状态和响应体；
- 服务调用次数；
- Polling最后状态和迁移；
- TestContext提取结果；
- 文件Hash和大小；
- 审计集合；
- 清理后的服务状态；
- payload不变性。

### Runner级证据

通过`run_master.py`和产物验收：

- pytest原始退出码；
- 权威收集和分池集合守恒；
- JUnit总数和结果；
- Allure步骤、重试、Polling和附件；
- 自定义`--alluredir`；
- Quality关闭时Noop行为。

### Quality/Metrics级证据

由现有聚合链产生，不在业务用例内部断言：

- 请求成功率；
- 重试挽救率；
- 接口耗时Top；
- 请求、逻辑调用和Case归属；
- model ID和traffic role。

指标只断言“存在、来源正确、与请求事实一致”，不冻结本地毫秒耗时或Top精确顺序。

### 多轮Flaky证据

- 同一黄金路径nodeid连续运行；
- 同一独占数据库；
- 每轮只导入本轮可信样本；
- 状态按当前规则真实演进；
- 不冻结未经代码核对的迁移轮数。

### Jenkins证据

- Pipeline Summary；
- JUnit/Allure入口；
- 本轮质量观测；
- 产物归档；
- 断网条件下仍可完成。

## 7. 合同一致性审查

阶段0合同完成后执行以下审查。

### 7.1 双向覆盖审查

建立两张映射：

```text
能力 → 主要用例 → 服务场景 → Case证据 → 运行级证据
服务端点 → 使用用例 → 预期调用次数 → 清理责任
```

要求：

- 每项计划能力至少有一个主要用例；
- 每个服务端点至少有一个消费者；
- 每条用例使用的场景均有明确响应序列；
- 每个创建资源动作都有清理所有者；
- 没有只为“看起来完整”而存在的死接口或死用例。

### 7.2 冲突审查

检查合同是否存在：

- 同一路径在不同章节定义不同响应；
- 同一operation name承担不同业务语义；
- 同一用例同时承担分类和报告内部验证；
- 黄金路径包含互斥终态；
- 业务用例依赖执行顺序；
- 并发用例共享Session；
- cleanup发生在Request关闭之后；
- 临时文件在Allure附件读取前被删除。

### 7.3 范围审查

全文检索并确认不存在：

- 外部生产或预发布域名；
- 真实API Key或凭证样式；
- SSE或流式用例；
- 新Marker；
- Quality内部builder/repository/stage调用；
- DI容器、事件总线、注册器或新DSL；
- 未解释的`TODO`、`TBD`和“后续再定”。

## 9. 验证方式

阶段0不运行代码测试，但必须完成文档门禁：

1. `git diff --check`通过；
2. 输出文件UTF-8可读；
3. 合同不存在`TODO`或`TBD`；
4. 合同只包含loopback示例URL；
5. 不出现真实域名和凭证；
6. 所有计划nodeid唯一；
7. 所有operation name唯一且为snake_case；
8. 所有创建资源均映射清理动作；
9. 黄金路径只有一个成功终态；
10. 工作树保护清单中的文件未被修改。

## 10. 阶段0停止条件

出现以下任一情况必须暂停并询问用户：

1. 现有公共API无法表达计划能力，需要修改核心框架；
2. Capture临时目录无法在不修改生产代码的情况下隔离；
3. 本地服务无法产生Quality所需中性事实；
4. BaseTask现有媒体能力与冻结协议不兼容；
5. Polling或Retry实际语义与总方案相反；
6. 必须增加Marker或新配置开关才能收集离线模块；
7. 需要恢复SSE范围；
8. 发现同名文件或用户已有协议文档需要合并；
9. 发现阶段0之外的工作树冲突。

不得通过临时兼容层或新抽象绕过停止条件。
