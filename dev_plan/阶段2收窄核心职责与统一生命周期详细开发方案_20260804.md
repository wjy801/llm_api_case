## 1. 需求理解

阶段 2 要解决的不是“把大文件拆小”，而是让领域行为、请求执行、运行时观察、下载副作用和测试制品分别只有一个职责所有者。

本阶段必须完成：

1. 图片/媒体复合流程与账单流程迁出 `BaseTask`，旧类、方法、签名、Allure 步骤、异常和 `pytest.skip()` 行为继续兼容；
2. `BaseRequest` 不再直接编排 Operation、Request Group、Polling Lease 的 begin、bind、finish、detach 和 outcome 映射；
3. 建立中性的 `runtime_metadata` 入口，旧 `_quality_operation_name`、`_quality_traffic_role` 继续接受并兼容映射；
4. Polling 的 HTTP timeout、Retry、`Retry-After`/backoff 和轮询 sleep 共用同一个总 deadline；
5. 框架内部不再通过临时修改共享 `Session.headers` 实现单次协议或控制请求；
6. 输入媒体和输出结果下载共用一套底层原语，并可分别开启或关闭；
7. Runner 多池使用独立 Allure 原始目录，结束后合并一次并只生成一次 HTML/history；
8. 直接运行 pytest 仍自动生成报告，默认与自定义 `--alluredir`、附件和历史路径保持兼容；
9. 阶段 1 剩余 Polling 与 Header 两项 strict xfail 转为正常通过。

本阶段不做：

- 不取消统一预收集，不改变阶段 1 的 nodeid 计划、分池、退出码和报告事实优先级；
- 不实施 `quality/__init__.py` 懒加载、`QualityRunLifecycle` 或 Reporting 可选适配；这些属于阶段 3；
- 不合并配置校验、Artifact 校验和素材 CLI；这些属于阶段 4；
- 不删除或缩减 Quality、Metrics、Flaky、Retry、Polling、Middleware、TestContext、JUnit、Allure、邮件和历史能力；
- 不恢复、扩展或重新设计流式输出/SSE；已有兼容代码不作为本阶段重构目标和验收项；
- 不处理密钥泄露、Secret 扫描或安全治理；
- 不改变四件套强制创建规范，不用简单别名替代任何现有类；
- 不执行真实接口、付费 Smoke 或外部媒体下载。

## 2. 第一性原理与 TOC 约束

### 2.1 核心职责收敛的本质

可学习、可扩展的框架必须满足：

```text
业务语义由领域能力拥有
HTTP 控制流由 BaseRequest 拥有
观察生命周期由 RuntimeObserver 拥有
时间预算由同一个 deadline 拥有
下载副作用由 Capture Policy 明确授权
pytest 调用由 pytest_execution 拥有
Allure 制品生命周期由一个 Allure Lifecycle 拥有
```

文件数量不是目标。如果只是把相同控制流复制到新文件，职责仍然没有收敛。

### 2.2 当前因果链

```text
所有领域希望继承 BaseTask 后立即可用
-> 媒体、对话、余额、用量和环境控制不断进入公共基类
-> 公共基类同时修改 Session Header、发请求、轮询、sleep、skip 和输出日志
-> BaseRequest 又直接管理多种 Runtime Lease
-> 单次请求、Retry、Polling 和观察生命周期互相穿透
-> 并发 Header、总预算和异常收尾无法独立证明正确
-> 多池 pytest 再通过保存/恢复 Allure 目录维持制品
-> 每次新增能力都必须同时理解业务、网络、观察和报告副作用
```

### 2.3 TOC 决策

阶段 2 的首要约束是“核心路径存在多个状态与副作用所有者”。实施顺序固定为：

```text
行为合同先落地
-> Runtime metadata 与生命周期协作者
-> 单一 deadline 和请求级 Header
-> BaseTask 兼容门面委托领域能力
-> 下载原语与 Capture Policy
-> 多池 Allure 单一生命周期
```

先修 Runtime、预算和 Header，是因为后续领域能力要复用这些正确原语；先搬 `BaseTask` 会把缺陷原样迁移。Allure 生命周期独立且影响制品范围最大，放在核心请求回归稳定后实施。

## 8. 工作包 2B：RuntimeObserver 与中性 metadata

### 8.1 内部协作者

在 `common/runtime_hooks/` 新增窄职责 `RuntimeObserver`：

- `observe_operation(metadata)`：统一 Operation begin、response outcome、error outcome、detach 和只完成一次；
- `observe_request_group(...)`：统一 Request Group start、context bind、retry wait 汇总和 finally finish；
- `observe_polling()`：统一 Polling begin、state、sleep 和分类 outcome；
- 所有调用继续走现有 `RuntimeHooks`、Lease、Provider 和安全调用函数；
- 观察器异常保持 fail-open，不覆盖业务 Response 或原始异常；
- 不增加无类型 `emit(event)`、订阅器列表或广播总线。

`BaseRequest` 继续拥有 HTTP、Middleware、Retry 和 Polling 控制流，但只调用高层观察作用域，不再散落 Lease 细节。现有自由函数和强类型对象全部保留，作为公开兼容面和 `RuntimeObserver` 的底层实现。

### 8.2 metadata 规范化

复用中性的 `RuntimeOperationMetadata` 作为规范化结果：

```text
runtime_metadata（新入口）
  优先级最高

_quality_operation_name / _quality_traffic_role（旧入口）
  仅在中性字段未提供时补值

默认值
  由 HTTP / Polling 调用类型提供
```

实施要求：

- `request()`、`get/post/...` 和 `poll_get()` 的现有调用方式不变；
- 从 `**kwargs` 消费 `runtime_metadata` 和旧 `_quality_*`，绝不传给 requests；
- `kind`、`name`、`role`、`model_id` 在进入观察器前完成一次规范化；
- 同时传新旧值时，中性 metadata 明确优先，不产生双 Operation；
- 现有 Quality 适配器继续只依赖 Runtime Hooks，不让 BaseRequest 导入 `quality.*`；
- `tests/quality/test_runtime_fact_compatibility.py` 中旧 `_quality_*` 关系必须保持；
- 新领域代码改用 `runtime_metadata`，旧参数只作兼容，不继续扩散。

### 8.3 一次性收尾合同

至少保证：

| 路径 | Operation | Request Group | Polling |
| --- | --- | --- | --- |
| 2xx | SUCCESS 一次 | finish 一次 | SUCCESS 一次 |
| 非 2xx Response | FAILED 一次 | finish 一次 | 由状态策略决定 |
| Middleware/transport 异常 | 原异常对应 outcome 一次 | finally finish | FAILURE 或对应分类 |
| `PollingFailedError` | FAILED | 每次请求组均收尾 | FAILURE |
| `PollingUnknownStateError` | UNKNOWN | 每次请求组均收尾 | UNKNOWN |
| `PollingTimeoutError` | TIMEOUT | 已开始请求组均收尾 | TIMEOUT |
| KeyboardInterrupt/SystemExit | INTERRUPTED | finally finish | INTERRUPTED |

本阶段不新增或恢复 SSE 生命周期设计；现存不相关兼容分支不扩展。

## 9. 工作包 2C：单一 Polling deadline

### 9.1 预算定义

`poll_timeout` 是整个 `poll_get()` 的墙钟总预算，而不是每次 HTTP 的 timeout：

```text
poll_timeout
>= HTTP attempt time
 + Retry backoff / Retry-After
 + 同一次轮询内的后续 retry attempts
 + poll_interval sleep
 + 后续轮询请求
```

在 `poll_get()` 入口只计算一次绝对 `deadline`。Polling 与 `RetryExecutor` 使用同一个 monotonic clock 和 sleeper，不能各自重新计算 `max_elapsed` 起点来延长总预算。

### 9.2 请求与 Retry 规则

- 每次 transport 前计算 `remaining = deadline - monotonic()`；
- 无剩余预算时不再发请求，转为保留上下文的 `PollingTimeoutError`；
- 单次 `timeout = min(调用方显式 timeout 或 config.timeout, remaining)`；
- 原始 timeout 为 tuple 时分别约束 connect/read，不能把 tuple 错转为 float；
- RetryExecutor 增加可选绝对 deadline，普通非 Polling Retry 行为不变；
- backoff/`Retry-After` 大于剩余预算时不完整 sleep、不启动下一次 attempt；
- `RetryPolicy.max_elapsed` 与 Polling deadline 同时存在时取更早边界；
- 最后一条 Response、状态迁移和 Retry 记录继续保留；
- 日志/观察记录实际等待时间，不记录计划但未发生的完整等待。

### 9.3 时间源

优先复用注入给 `RetryExecutor` 的 monotonic/sleeper，使单测可用假时钟完整证明总预算。已有调用不传 RetryExecutor 时继续使用 `time.monotonic/time.sleep`。

不新增通用 Deadline 框架；如需要值对象，只包含 `remaining()`、`expired()` 和 timeout 截断三个最小职责。

## 10. 工作包 2D：请求级 Header 与 BaseTask 查询缺陷

### 10.1 Header 所有权

保留 `set_header()`、`update_headers()`、`remove_header()`、`reset_headers()`，用于客户端默认配置兼容；但框架内部单次请求不得再调用它们临时切换协议。

改造规则：

- 普通覆盖：请求级 headers 覆盖 Session 默认值；
- 完整替换：为 Anthropic 等协议生成当前请求的完整 Header 快照，并用删除标记避免 requests 再合并 Session 中不应存在的 Header；
- Multipart：单次请求移除 `Content-Type`，让 requests 生成 boundary，不清空共享 Session；
- 账单控制请求：只在当前 get/poll_get 中覆盖 Authorization 等 Header；
- Retry 的每次 attempt 复用同一不可变 Header 快照，不重新读取可能被并发修改的 Session；
- RequestContext 仍对 kwargs 做独立复制，日志与脱敏读取本次请求快照。

`ProtocolRequest.create_message()`、`create_image_edit()` 和 BaseTask/账单能力改为请求级 Header。阶段 0 的并发测试转正后，两个协议请求看到各自 Header，Session 默认 Header 在前后均不改变。

这里只承诺消除框架自身的临时 Header 共享写入，不宣称任意第三方并发修改 `requests.Session` 都是线程安全的。

### 10.2 查询参数正确性

以下两条请求删除空键：

```python
{"request_id": request_id}
```

- 普通用量查询；
- 等待用量记录结算的 Polling 查询。

测试必须直接断言传给 transport 的最终 params，不保留错误空键作为兼容行为。

## 11. 工作包 2E：BaseTask 冻结为兼容门面

### 11.1 领域能力拆分

新增两个明确能力边界：

```text
common/task_capabilities/media_generation.py
  MediaGenerationCapability

common/task_capabilities/billing.py
  BillingCapability
  ControlApiKeyLookup（中性配置查找结果）
```

媒体能力拥有：

- 同步图片创建；
- 对话创建；
- 异步媒体创建；
- task id 提取；
- 媒体结果轮询；
- 创建并轮询复合流程；
- 对应 Runtime operation metadata。

账单能力拥有：

- 余额查询；
- 结算等待；
- request id 提取；
- 用量记录查询与终态等待；
- 响应体格式化；
- 控制接口 Header 和 runtime metadata；
- 环境变量名称解析的中性结果。

能力对象不继承 `BaseTask`，不导入具体 `module/<domain>`，也不创建第五种业务基类。

### 11.2 BaseTask 兼容委托

`BaseTask` 保留：

- 当前全部方法和 class attributes；
- 当前默认 endpoint、task id field/aliases 和常量导入路径；
- 当前 Allure 装饰器及标题；
- 当前虚方法覆盖语义：复合流程调用子类覆盖后的创建/轮询方法；
- 当前打印、AssertionError、ValueError 和返回原始 Response 的语义。

旧方法体只完成参数适配、兼容控制和能力委托，不再复制领域实现。为避免改变子类构造合同，不强制新增 `BaseTask.__init__()`；通过私有能力工厂或惰性属性完成组合，并允许单测替换协作者。

### 11.3 skip 边界

新 `BillingCapability` 查询配置时返回中性结果：

```text
环境变量名
配置值或缺失
是否可用
```

它不调用 `pytest.skip()`。新 Task/fixture 可按场景决定 skip、失败或提供显式 key。

`BaseTask.get_required_control_api_key()` 继续把“缺失”转换成原有 `pytest.skip()` 和原消息，保证旧用例完全兼容。

### 11.4 新增模块规则

- 新业务模块仍必须创建 Request、Task、Assertions、Decorators 四件套真实类；
- 领域 Task 可以组合能力对象，不能因为能力对象存在而省略 Task；
- `ImageTask`、`VideoTask` 等现有类身份和 MRO 不变；
- 新领域逻辑进入对应 `module/<domain>/task.py` 或明确能力对象，不再进入 `BaseTask`；
- 本阶段不把已有薄类改成别名，也不为了目录整齐批量移动业务文件。

## 12. 工作包 2F：下载原语与 Capture Policy

### 12.1 单一底层实现

新增 `util/downloads.py`，只提供下载所需最小原语：

- URL 文件名解析与 fallback 名；
- Windows 非法字符清理；
- 唯一目标路径；
- 分块流式下载；
- 可选取消事件；
- 可选最大字节数；
- 临时文件写入和失败清理；
- 附件 MIME/Allure 类型识别。

`common/base_decorators.py` 与 `util/media_resources.py` 保留原入口、类方法和返回合同，内部委托同一原语。私有兼容方法可继续存在，但不能再维护第二套算法。

### 12.2 Capture Policy

新增小型冻结配置：

```text
CapturePolicy
├─ capture_input_media
├─ capture_output_results
├─ max_input_bytes（可选）
└─ max_output_bytes（可选）
```

预置语义：

| 策略 | 输入媒体 | 输出结果 | 外部下载 |
| --- | --- | --- | --- |
| 默认兼容 | 开 | 开 | 保持当前触发位置 |
| 仅输入 | 开 | 关 | 只在 POST 前捕获 |
| 仅输出 | 关 | 开 | 只在 Polling 成功后捕获 |
| 关闭 | 关 | 关 | 不调用 `requests.get`、不启动线程 |

`BaseRequest` 可通过新增的末尾可选构造参数或实例策略配置；现有三个构造参数的顺序、默认值和位置调用保持。`MediaResourceMiddleware` 与 `download_links_from_poll_get` 读取同一策略，不各自发明开关。

### 12.3 fail-open 与附件

- 单个输入下载失败继续记录 fallback 文本，不改变接口调用；
- 单个输出 URL 下载失败不得覆盖已经成功的 Polling Response；
- 多 URL 中一项失败不阻止其他项；
- 下载中断/超限删除部分文件；
- 附件失败不覆盖业务结果；
- 成功文件仍进入当前 ContextVar 收集和 Allure 步骤；
- 默认 `data/`、`data/pre_data/` 与现有附件标题保持。

不建设下载队列、重试平台、缓存、对象存储或通用 Artifact 注册中心。

## 13. 工作包 2G：pytest/Allure 单一生命周期

### 13.1 所有权

新增 `run_orchestration/allure_lifecycle.py`，`AllureRunLifecycle` 是框架内唯一拥有以下行为的组件：

- 解析最终 raw 目录；
- 清理本轮最终目录；
- 为池分配临时 raw 目录；
- 重写池级 `--alluredir`；
- 合并已执行池的原始结果与附件；
- 调用 Allure CLI 生成 HTML；
- 生成 history、更新 latest、执行保留清理；
- 输出一致的成功、跳过和失败诊断。

`pytest_execution.py` 继续是唯一调用 `pytest.main()` 的生产实现源，并通过 `PytestExecutionSession` 组合该生命周期。`runner.py` 只发出“执行池/结束执行”命令，不感知备份目录、复制规则或 Allure CLI。

`run_orchestration/artifacts.py` 保留原子文件和通用路径原语，不再拥有保存/恢复 Allure 目录的第二套生命周期。

### 13.2 Runner 多池流程

```text
resolve final alluredir
-> clean final raw once
-> allocate <run-temp>/parallel-pool
-> pytest parallel writes only its temp raw
-> merge parallel raw
-> allocate <run-temp>/serial-pool
-> pytest serial writes only its temp raw
-> merge serial raw
-> remove temp root
-> generate HTML once
-> generate history once（开关开启时）
```

要求：

- 不再使用 `preserve_allure_results()` / `restore_allure_results()` 维持多次 pytest；
- 空池不创建 pytest session，可不创建池目录；
- exit 2/3/4/5 提前止损后只合并已经执行池的产物；
- pytest exit 1 继续后续池并合并双方证据；
- Allure 合并/生成失败 fail-open，不能改写阶段 1 的 pytest 原始退出码；
- 文件冲突不得静默覆盖或重命名附件后破坏 JSON 引用；相同文件可按 hash 去重，非同内容冲突给出完整性警告并保留临时证据；
- collect-only 不清理、创建或生成任何 Allure 产物。

### 13.3 默认与自定义路径

- 未显式传入时，最终 raw 仍为项目根 `allure-results/`；
- 显式 `--alluredir path` 或 `--alluredir=path` 时，最终合并到该路径；
- 相对路径基于项目 root，绝对路径保持；
- 池级临时路径不能泄漏到最终报告链接或 execution-result；
- Jenkins 默认仍归档/展示 `allure-results`；自定义路径是调用方显式责任，行为与当前 CLI 一致。

### 13.4 直接 pytest

`module/conftest.py` 只保留轻量 Hook 适配：

- 直接 pytest：在 session start/finish 委托同一个 `AllureRunLifecycle`；
- Runner 管理模式：不清理最终目录、不在每池生成 HTML/history；
- xdist worker：不单独生成报告；
- collect-only：完全无制品副作用。

Allure 清理、CLI 查找、Java 环境、history 命名和清理实现迁出 conftest。`pytest.ini` 只声明稳定默认参数，不再作为另一套生命周期实现。

## 20. 风险与控制

### 20.1 能力迁移改变虚方法分派

风险：composite 直接调用能力内部方法，绕过子类 override。  
控制：BaseTask 兼容 composite 向能力传入 `self.create_*`/`self.poll_*` 回调；增加覆盖测试。

### 20.2 RuntimeObserver 形成重复观察层

风险：旧自由函数与新协作者都 begin/finish。  
控制：自由函数只作底层原语，BaseRequest 只调用协作者；用事件计数锁定一次性收尾。

### 20.3 deadline 改变 Retry 异常时机

风险：预算耗尽时丢失最后 Response 或变成普通 requests.Timeout。  
控制：Polling 边界统一转换为带最后状态/迁移的 `PollingTimeoutError`；普通 Retry 不传 deadline 时行为不变。

### 20.4 Header 完整替换语义漂移

风险：requests 自动合并 Session Header，导致声明“替换”实际仍继承。  
控制：使用请求级删除标记/准备后的 Header 集合测试真实 PreparedRequest，不只断言输入 dict。

### 20.5 下载默认行为回退

风险：策略接入后默认不再触发或附件标题改变。  
控制：默认策略明确全开，先冻结旧行为；新策略仅为显式选择。

### 20.6 Allure 附件引用冲突

风险：合并时重命名附件但未同步 JSON 引用。  
控制：不静默重命名非同内容冲突；按 UUID/hash 检查并保留诊断，测试 result/container/attachment 整体可解析。

### 20.7 Allure 收尾覆盖 pytest 事实

风险：finally 中的复制、CLI 或 history 异常改变返回码。  
控制：先保存 pytest 原始结果；Allure 生命周期捕获并报告自身错误，绝不修改 PoolExecutionResult/final exit。

### 20.8 阶段范围过大

风险：BaseRequest 与 Allure 同阶段造成难回滚。  
控制：按 2B～2G 独立提交和门禁执行；不跨工作包批量重写。

## 21. 回滚策略

- RuntimeObserver 可回滚到旧自由函数调用，但对应一次性收尾门禁会重新失败；
- deadline 和 Header 为正确性修复，不以恢复已知错误为兼容方案；必要时回滚单个提交并恢复 strict xfail 证据，不删除测试；
- BaseTask 能力迁移可独立回滚，旧门面测试保持；
- Capture Policy 可回滚策略接线，不能恢复下载失败覆盖业务响应；
- Allure 生命周期可独立回滚到阶段 1 制品路径，但必须明确重新出现的多所有者问题，不能用 `git reset --hard` 覆盖用户工作区；
- 任何回滚不修改阶段 1 的权威计划、退出码和结构化执行事实。
