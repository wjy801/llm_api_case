> 日期：2026-08-05
> 状态：待执行
> 所属总方案：`dev_plan/离线框架能力分类用例与黄金路径详细执行方案_20260805.md`
> 唯一协议输入：`dev/离线框架能力示例协议与验收合同_20260805.md`
> 阶段性质：建立并验证离线测试基础设施，不实现四件套业务逻辑和分类用例

## 1. 需求复述与阶段目标

阶段1只解决一个问题：提供一个可重复、可解释、无外网依赖的本地HTTP事实源，并通过pytest fixture把服务、临时捕获目录和loopback网络边界交给后续分类用例。

阶段完成后必须能够证明：

1. 同一场景每次产生相同的HTTP响应序列；
2. Retry和Polling所需的503、429及业务状态迁移全部由显式序列驱动；
3. 每条测试获得独立端口、独立状态和独立资源Event；
4. 并发请求不会丢失计数或串改其他服务实例；
5. 服务无论正常、断言失败还是fixture构造失败，都能关闭监听并回收线程；
6. 输入、输出和超限资源的字节、长度、SHA-256及PNG CRC可重复验证；
7. 后续用例只需选择冻结场景，不需要重新实现Mock逻辑或等待逻辑；
8. 本阶段不访问真实接口，不读取真实`.env`域名和凭证。

本阶段的成功标准不是“接口能返回200”，而是后续Request、Retry、Polling和Capture失败时，可以排除本地服务自身的不确定性。

## 2. 第一性原理与TOC判断

### 2.1 任务本质

离线示例要形成可信因果链：

```text
冻结场景
→ 唯一HTTP序列
→ 唯一调用次数和状态变化
→ 框架行为可被精确观察
→ 失败能够归因到具体能力
```

如果本地服务使用随机端口之外的随机行为、墙钟定时推进状态或模块级共享游标，则会形成另一条因果链：

```text
服务状态不可预测
→ Retry/Polling次数漂移
→ 用例断言和Metrics事实漂移
→ 无法区分框架缺陷与测试夹具缺陷
→ 离线示例失去学习和回归价值
```

因此，本阶段真正要交付的是“确定性事实源＋可证明的生命周期”，不是通用Mock Server。

### 2.2 TOC首要约束

当前首要约束是本地服务基础设施是否可信。四件套和黄金路径都依赖该约束，提前实现业务用例只会放大排障路径。

TOC处理顺序：

1. 识别约束：服务响应、共享状态和线程回收尚未被代码及测试证明；
2. 充分利用约束：只实现冻结协议需要的最小服务，不扩展为通用DSL；
3. 服从约束：先完成服务基础设施门禁，再进入阶段2；
4. 提升约束：用状态隔离、锁、Event、固定资源和重复启停测试消除不确定性；
5. 防止惯性：阶段1完成后停止继续抽象，业务能力转交阶段2～4验证。

### 2.3 设计原则

- 状态由固定序列和调用计数推进，不由随机数或后台定时器推进；
- 端口只使用操作系统分配的端口0，不维护端口池；
- 服务只绑定`127.0.0.1`，不使用`localhost`；
- 场景是不可变Python数据，不引入YAML、JSON场景文件或表达式DSL；
- HTTP Handler只做协议适配，状态变化集中在服务状态对象；
- 测试基础设施门禁不通过BaseRequest调用，避免服务与被测框架互相证明；
- 不增加DI容器、事件总线、Task注册器、Marker或新报告。

## 6. `offline_service.py`详细设计

## 6.1 固定常量

模块内定义合同固定值，避免Handler散落硬编码：

```text
OFFLINE_MODEL_ID = offline-media-model
OFFLINE_TASK_ID = offline-task-001
OFFLINE_REQUEST_ID = offline-request-001
OFFLINE_TRACE_ID = offline-trace-001
OFFLINE_COOKIE_NAME = offline_session
OFFLINE_COOKIE_VALUE = offline-session-001
OFFLINE_API_KEY = offline-example-key
OFFLINE_IDEMPOTENCY_KEY = offline-idempotency-001
```

固定资源从合同Base64解码为模块常量：

```text
INPUT_PNG_BYTES：70字节
INPUT_PNG_SHA256：f2bb5bbaca678ecad746b1fa5ecfa2c8a81dd18817be19f0187c036d25326317

OUTPUT_PNG_BYTES：70字节
OUTPUT_PNG_SHA256：49e1dad481e94dfab7c9573a9a81d56aa2ca629fe15a3f7a910aa4f47601c00d

OVERSIZED_OUTPUT_BYTES = OUTPUT_PNG_BYTES + OUTPUT_PNG_BYTES：140字节
```

不在运行时生成随机图片，不依赖Pillow或外部文件。

## 6.2 `OfflinePollStep`

使用冻结数据类：

```python
@dataclass(frozen=True)
class OfflinePollStep:
    http_status: int
    status: str | None = None
```

约束：

- `http_status=503`时`status`必须为`None`；
- `http_status=200`时`status`必须是非空字符串；
- 不接受函数、延迟、表达式、动态body或异常对象；
- transport 503只表示一次HTTP尝试，不属于业务状态迁移。

## 6.3 `OfflineServiceScenario`

使用冻结数据类，字段严格保持阶段0合同：

```python
@dataclass(frozen=True)
class OfflineServiceScenario:
    transient_statuses: tuple[int, ...]
    idempotent_post_statuses: tuple[int, ...]
    poll_steps: tuple[OfflinePollStep, ...]
    output_asset: Literal["normal", "oversized"] = "normal"
```

构造时执行最小校验：

- 三个序列不得为空；
- transient和POST状态只允许合同需要的200、429、503；
- `output_asset`只允许`normal`和`oversized`；
- poll step符合第6.2节约束。

不得增加回调、响应模板、路由字符串、延迟函数或任意metadata字段。

## 6.4 冻结场景常量

在模块中创建以下不可变对象：

| 常量 | transient | POST | poll steps | asset |
|---|---|---|---|---|
| `DEFAULT` | 200 | 200 | succeeded | normal |
| `GET_503_THEN_200` | 503, 200 | 200 | succeeded | normal |
| `GET_429_THEN_200` | 429, 200 | 200 | succeeded | normal |
| `POST_503_THEN_200` | 200 | 503, 200 | succeeded | normal |
| `POLL_SUCCESS_WITH_RETRY` | 200 | 200 | 503, queued, running, succeeded | normal |
| `POLL_FAILURE` | 200 | 200 | queued, failed | normal |
| `POLL_UNKNOWN` | 200 | 200 | queued, paused | normal |
| `POLL_TIMEOUT` | 200 | 200 | running | normal |
| `CAPTURE_OVERSIZED` | 200 | 200 | succeeded | oversized |

序列推进规则统一为：

```text
尚有下一步 → 返回下一步并推进游标
序列已耗尽 → 重复最后一步
```

该规则保证`POLL_TIMEOUT`持续返回`running`，也保证意外的额外请求不会抛出`IndexError`或产生随机响应。

## 6.5 `OfflineServiceState`

每个`OfflineService`构造自己的状态对象，禁止模块级可变状态。

最小状态：

```text
lock: threading.RLock
tasks: dict[task_id, task_poll_cursor]
endpoint_call_counts: Counter[str]
transient_index: int
idempotent_post_index: int
audit_records: list[str]
deleted_task_ids: list[str]
request_hosts: list[str]
input_asset_requested: Event
output_asset_requested: Event
oversized_asset_requested: Event
handler_errors: list[str]
```

状态规则：

- 所有计数、列表、任务和游标的读写都在`lock`内完成；
- Event只用于等待“请求已经发生”，不用于推进业务状态；
- `tasks`在创建任务时写入独立Polling游标，DELETE时删除；
- `request_hosts`记录服务实际收到的Host，供黄金路径证明全部请求指向loopback；
- Handler后台异常写入`handler_errors`，不能只打印到stderr后继续假通过；
- 测试读取复合状态时使用快照方法或持锁读取，避免并发中读取半状态。

计数键使用稳定语义名：

```text
echo_calls
transient_calls
idempotent_operation_calls
media_create_calls
media_poll_calls
media_delete_calls
context_calls
audit_calls
contract_calls
input_asset_calls
output_asset_calls
oversized_asset_calls
```

## 6.6 HTTP Server与Handler所有权

使用标准库`ThreadingHTTPServer`和`BaseHTTPRequestHandler`，不增加第三方Mock Server依赖。

所有权关系：

```text
OfflineService
├─ 唯一server实例
├─ 唯一serve_forever线程
├─ 唯一OfflineServiceState
└─ 每请求一个Handler实例，共享当前服务state
```

Handler通过当前server实例取得state和base URL，不使用模块全局`CURRENT_SERVICE`。覆盖`log_message()`为空实现，避免每次请求污染pytest输出；真正异常仍记录到`handler_errors`。

Server设置：

- 地址固定`("127.0.0.1", 0)`；
- request线程为daemon，避免异常退出阻塞Python进程；
- `serve_forever`线程名称包含分配后的端口，便于定位残留；
- 单次请求不启动新的业务定时器；
- 不启用TLS，不读取系统代理。

## 6.7 通用响应和请求解析

实现内部小函数统一协议，不建立公开Response Builder体系：

### JSON响应

- 使用UTF-8和稳定JSON序列化；
- `Content-Type: application/json; charset=utf-8`；
- `Content-Length`按最终字节计算；
- 需要时增加`X-Request-ID`和`Set-Cookie`；
- 204响应体为空，`Content-Length: 0`。

### 二进制响应

- `Content-Type: image/png`；
- `Content-Length`等于固定字节长度；
- 先更新计数并设置Event，再发送内容。

### JSON请求解析

- 仅按`Content-Length`读取本次请求体；
- 缺失、非法长度、非法UTF-8或非法JSON返回结构化400；
- 合同要求对象的端点收到非对象JSON时返回结构化400；
- 不把Authorization和完整原始Header写入错误响应。

建议错误体：

```json
{"error":{"code":"INVALID_JSON"}}
```

未知路径统一返回：

```json
{"error":{"code":"NOT_FOUND"}}
```

## 6.8 路由行为

### `POST /v1/echo`

- 解析JSON对象；
- `echo_calls += 1`；
- 返回收到的body、`authorization_present`布尔值和`status=accepted`；
- 不回显Authorization值；
- HTTP 200。

### `GET /v1/transient`

- `transient_calls += 1`并取得当前场景步骤；
- 503返回`TEMPORARY_UNAVAILABLE`；
- 429返回`RATE_LIMITED`并设置`Retry-After: 0`；
- 200返回`status=ok`和本次attempt；
- 重试场景的第二次请求稳定得到attempt 2。

### `POST /v1/idempotent-operation`

- 解析JSON对象，但服务端不替BaseRequest决定是否重试；
- 每次到达都执行`idempotent_operation_calls += 1`并推进服务序列；
- 503返回结构化临时错误；
- 200返回`operation=offline-write`和`status=committed`；
- 是否发送第二次请求由后续BaseRequest测试的Idempotency-Key资格决定。

### `POST /v1/media/generations`

- 解析JSON对象；
- `media_create_calls += 1`；
- 创建或重置`offline-task-001`的独立Polling游标；
- HTTP 202返回冻结任务、模型和trace字段；
- 增加固定`X-Request-ID`和Cookie；
- 不主动下载输入资源，输入下载由框架Capture发起。

### `GET /v1/media/tasks/{task_id}`

- 每次调用先执行`media_poll_calls += 1`；
- 任务不存在返回`TASK_NOT_FOUND`和HTTP 404；
- HTTP 503步骤返回`TEMPORARY_POLL_UNAVAILABLE`，不推进业务状态列表之外的任何状态；
- queued/running返回冻结任务、模型和trace；
- succeeded返回`result.url`；
- 普通场景URL指向`/assets/output.png`；
- 超限场景URL指向`/assets/oversized-output.png`；
- failed返回冻结业务错误；
- paused返回未知状态响应；
- 所有HTTP 200任务响应带固定request ID和Cookie。

### `DELETE /v1/media/tasks/{task_id}`

- `media_delete_calls += 1`；
- 存在时删除任务、追加`deleted_task_ids`、返回HTTP 204；
- 不存在时返回`TASK_NOT_FOUND`和HTTP 404；
- 重复DELETE不得追加重复的成功删除记录。

### `GET /v1/context`

- `context_calls += 1`；
- 返回固定task ID和包含trace的message；
- 设置固定request ID和Cookie；
- HTTP 200。

### `GET /v1/audit`

- 读取`X-Audit-Name`；
- 缺失或空值返回结构化400，不写入审计记录；
- 有效时持锁追加`audit_records`并执行`audit_calls += 1`；
- 返回audit name、固定task ID和`recorded`；
- 记录顺序可变，后续用例只比较集合。

### `GET /v1/contracts/{mode}`

阶段1将阶段0的语义响应落成最小稳定body：

| mode | HTTP | 最小稳定body |
|---|---:|---|
| `valid` | 200 | task_id、status=`succeeded`、model |
| `business_error` | 400 | error.code/type/message |
| `invalid_schema` | 200 | 只返回status，故意缺少后续Schema必填字段 |
| 其他 | 404 | `CONTRACT_MODE_NOT_FOUND` |

每次执行`contract_calls += 1`。响应不得包含Authorization或其他敏感值。

### 静态资源

| 路径 | 字节 | Event | 计数 |
|---|---:|---|---|
| `/assets/input.png` | 70 | `input_asset_requested` | `input_asset_calls` |
| `/assets/output.png` | 70 | `output_asset_requested` | `output_asset_calls` |
| `/assets/oversized-output.png` | 140 | `oversized_asset_requested` | `oversized_asset_calls` |

未匹配的GET、POST和DELETE路径全部返回结构化404，不重定向、不代理外部地址。

## 6.9 `OfflineService`生命周期

公开最小接口：

```text
OfflineService(scenario=DEFAULT)
.start() -> OfflineService
.stop() -> None
.base_url -> str
.state -> OfflineServiceState
.is_running -> bool
```

### 启动

```text
检查当前状态
→ 构造ThreadingHTTPServer并绑定127.0.0.1:0
→ 记录实际端口和base URL
→ 启动唯一serve_forever daemon线程
→ 等待短时ready Event
→ 返回self
```

规则：

- 同一实例运行中再次`start()`直接返回self，不创建第二个线程；
- 已经完整停止的实例不重新启动，调用时抛出明确RuntimeError；
- ready等待使用上限，不允许无限阻塞；
- 启动任一步失败时立即`server_close()`并清理半初始化字段。

### 停止

```text
取得并清空当前server/thread引用
→ shutdown()
→ server_close()
→ join(有限超时)
→ 检查线程不再存活
```

规则：

- `stop()`可重复调用；
- shutdown、close和join即使前一步异常也必须继续尝试；
- join超时必须抛出明确错误，不能静默遗留线程；
- Handler错误在fixture收尾或测试断言中暴露；
- 不使用`time.sleep()`猜测线程是否退出。

可选支持`with OfflineService(...) as service`，但上下文管理只委托`start/stop`，不得形成第二套生命周期。

## 6.10 loopback URL校验

提供纯函数，例如：

```text
assert_loopback_url(url) -> None
```

允许条件必须同时满足：

- scheme严格为`http`；
- hostname严格为`127.0.0.1`；
- 存在合法端口；
- 不包含userinfo；
- URL可被标准库正常解析。

`localhost`、IPv6 loopback、外部域名、无端口URL、HTTPS和非法URL都立即抛出包含目标host但不包含认证信息的`ValueError`。该函数只校验目标，不修改全局socket或requests行为。

## 7. `conftest.py`详细设计

## 7.1 `offline_service_factory`

函数级fixture，yield一个工厂 callable：

```text
factory(scenario=DEFAULT)
→ 创建OfflineService
→ start
→ assert_loopback_url(base_url)
→ 加入本用例服务清单
→ 返回运行中的service
```

teardown要求：

- 按创建逆序停止所有服务；
- 一个服务停止失败时继续停止其他服务；
- 最后聚合并报告停止失败和`handler_errors`；
- 已由测试主动停止的服务可安全重复停止；
- 不保留跨测试session的服务缓存。

工厂允许同一测试创建两个实例，用于证明状态隔离；不允许传入动态Handler或路由回调。

## 7.2 `offline_service`

默认函数级fixture：

```text
offline_service_factory(DEFAULT)
```

每条消费它的测试都获得新端口、新状态、新Event和新游标。该fixture不读取环境变量，不自动创建BaseRequest。

## 7.3 `offline_network_guard`

返回第6.10节的loopback校验函数，供阶段2以后Request fixture在构造客户端和使用资源URL前显式调用。

边界：

- 只校验离线示例即将使用的URL；
- 不永久patch`socket`、`requests`或DNS；
- 不影响仓库其他真实业务用例；
- 错误必须发生在请求发出前。

## 7.4 `offline_capture_dirs`

依赖`tmp_path`和`monkeypatch`，创建：

```text
<tmp_path>/input
<tmp_path>/output
```

并在当前用例范围内替换：

```text
util.media_resources.MEDIA_DOWNLOAD_DIR → input目录
common.base_decorators.DOWNLOAD_DIR → output目录
```

返回一个只读路径对象或明确字段对象：

```text
input_dir
output_dir
```

生命周期规则：

- fixture只恢复模块常量，不主动递归删除`tmp_path`；
- 下载文件必须存活到`module/conftest.py::pytest_runtest_teardown`完成附件挂载；
- 不修改`CapturePolicy`公共模型；
- 不新增环境变量或仓库固定捕获目录；
- xdist下每个worker依赖自身`tmp_path`，无共享目录。

## 7.5 后续fixture依赖顺序合同

阶段2～4新增Request和Context fixture时必须保持：

```text

→ OfflineFrameworkRequest
→ TestContext
→ 用例
→ TestContext.cleanup
→ Request.close
→ offline_service.stop
```

`offline_capture_dirs`文件应保持到pytest teardown hook完成。DELETE清理不能使用已经关闭的Request，服务也不能在Context cleanup前停止。

## 8. `tests/test_offline_service.py`基础设施门禁

基础设施测试放在`tests/`，不放进`module/offline_framework_example/`业务用例目录，原因是：

```text
服务自测属于框架基础设施证据
≠ 离线业务能力Case证据
```

这样后续Runner执行`module/offline_framework_example`时，不会把HTTP Server自测请求混入请求成功率、Retry挽救率和耗时Top。

测试直接使用`requests.Session`或标准库HTTP客户端访问服务，设置`trust_env=False`和短timeout，不经过BaseRequest、Middleware、Retry或Polling。否则会形成“用被测框架证明测试服务、再用测试服务证明被测框架”的循环证据。

## 8.1 固定资源测试

验证：

- input和output均为70字节；
- oversized为140字节且等于output字节重复两次；
- 两个SHA-256等于阶段0合同；
- PNG签名正确；
- 逐个解析IHDR、IDAT、IEND chunk并用`zlib.crc32`验证CRC；
- HTTP响应Content-Type和Content-Length正确；
- 对应计数和Event准确变化。

## 8.2 连续启停测试

在同一测试进程内连续创建、启动和停止20个服务实例：

- 每次base URL都是`127.0.0.1`加有效随机端口；
- 服务运行时可完成一次context请求；
- 每次停止后server线程不存活；
- 重复`stop()`不报错；
- 不断言20次端口必须互不重复，端口复用由操作系统决定。

## 8.3 两实例隔离测试

同时启动两个不同场景实例：

- 各自base URL独立；
- 对实例A发请求不改变实例B计数；
- A推进到第二步不改变B游标；
- A创建或删除任务不改变B的`tasks`和`deleted_task_ids`；
- 停止A后B仍可正常响应。

## 8.4 固定Retry序列测试

分别验证：

- `GET_503_THEN_200`严格返回503、200，额外调用继续返回200；
- `GET_429_THEN_200`严格返回429、200，429带`Retry-After: 0`；
- `POST_503_THEN_200`严格返回503、200；
- 服务只提供序列，不因是否携带Idempotency-Key自行重复请求；
- 端点计数与实际HTTP调用数一致。

## 8.5 Polling场景推进测试

每个场景先创建任务，再查询：

- 成功场景：503、queued、running、succeeded；
- 失败场景：queued、failed；
- 未知场景：queued、paused；
- 超时场景：多次请求都为running；
- succeeded的普通/超限资源URL与场景一致；
- 503不被记录为业务状态；
- 查询未知任务返回结构化404；
- DELETE后再次查询返回404。

该测试只验证服务序列，不在阶段1调用框架PollingPolicy。

## 8.6 JSON和错误路由测试

验证：

- Echo返回原JSON对象但不回显Authorization；
- 非法JSON、非法Content-Length或非对象body返回结构化400；
- audit缺失Header返回400且不写记录；
- 未知GET、POST、DELETE路径返回结构化404；
- 204 DELETE响应体和Content-Length正确；
- contract三种已知mode和未知mode符合第6.8节。

## 8.7 并发状态安全测试

使用有界`ThreadPoolExecutor`向同一服务并发发送多条audit请求：

- 每个worker创建并关闭自己的HTTP Session；
- 全部响应成功；
- `audit_calls`等于请求数，无丢计数；
- `audit_records`集合等于输入集合；
- 不断言完成顺序；
- `handler_errors`为空。

该测试证明服务锁正确，不验证阶段4的ContextVar传播。

## 8.8 异常清理和线程回收测试

验证：

- 上下文块内主动抛出测试异常后，服务仍被停止；
- `stop()`执行后有限时间内线程结束；
- stop前后不依赖固定sleep；
- 半初始化失败路径可以关闭已绑定socket；
- 测试结束没有名称匹配当前服务端口的存活线程。

## 12. 风险与控制

### 12.1 Windows端口和线程回收

风险：server线程未退出或socket未关闭会导致测试进程挂起。

控制：端口0、`shutdown → server_close → join`、有限超时、线程存活断言；不通过sleep掩盖竞态。

### 12.2 并发状态丢写

风险：`Counter`、列表和游标复合操作在并发Handler中发生丢失或顺序串改。

控制：所有复合状态在同一`RLock`中推进，并用并发audit测试验证准确计数。

### 12.3 fixture清理覆盖原始失败

风险：第一项停止失败使后续服务无法清理，或teardown异常完全掩盖用例失败。

控制：先尽力清理全部实例，再聚合报告；错误信息区分业务失败和清理失败。

### 12.4 Capture目录patch错误

风险：只patch配置表面值，真实下载仍写入仓库`data/`。

控制：直接patch当前实现实际读取的`util.media_resources.MEDIA_DOWNLOAD_DIR`和`common.base_decorators.DOWNLOAD_DIR`，阶段3再通过文件落点测试闭环验证。

### 12.5 基础设施测试污染业务指标

风险：将服务自测放进离线业务模块后，被Runner和Quality当作业务Case统计。

控制：基础设施测试放在`tests/test_offline_service.py`，业务模块只保留阶段2～4能力用例。

### 12.6 过度抽象

风险：为未来可能场景增加动态路由、模板、回调和配置语言，形成第二套测试框架。

控制：场景字段固定为四项；新增协议必须先更新阶段0合同，不允许通过通用回调绕过合同。
