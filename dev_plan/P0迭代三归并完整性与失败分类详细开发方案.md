## 2. 已确认决策

### 2.1 契约与版本

- 保留已经冻结的 `quality.v1` 公共模型，不给 `FailureRecord` 增加 `rule_version` 字段。
- 新增 `merged/manifest.json`，统一记录本次 merge 使用的归并、分类和指纹算法版本。
- 一次 merge 只能使用一套分类规则和一套指纹算法，禁止在同一个 failures 文件中混用版本。
- manifest 是派生事实集的提交清单，不替代 `run.json`、CaseResult、RequestMetric、FailureRecord 或 IntegrityIssue。

建议第一版版本常量：

```text
manifest_version = quality.merge.v1
merge_version = p0-merge.v1
classifier_rule_version = p0-classifier.v1
fingerprint_version = p0-fingerprint.v1
```

### 2.2 失败 occurrence 与失败指纹

- 每一次真实失败 occurrence 都必须保留。
- FailureRecord 唯一候选键为 `failure_id + invocation_id + phase`。
- `failure_id` 是相同失败模式的聚合键，不是删除其他受影响用例的唯一键。
- 完全相同的 occurrence 可在重复扫描时幂等去重。
- 同一 occurrence 内容冲突时生成完整性问题，不能静默覆盖。

### 2.3 JUnit 证据

- `QUALITY_ENABLE=1` 时，`run_master.py` 默认保证正式执行阶段存在 `--junitxml`。
- 调用方已提供 JUnit 路径时继续使用原路径和现有阶段后缀规则。
- 调用方未提供时，自动使用质量输出目录下的自有 JUnit 路径。
- pytest 插件向 JUnit testcase 增加 `quality_case_id` 和 `quality_invocation_id` property。
- JUnit 提供异常类型、消息、断言位置和用例级对账证据，但不取代 CaseResult 的身份和 phase 事实。
- 不根据 testcase 的 `classname + name` 猜测 invocation 归属；缺少显式 property 时标记完整性降级。

### 2.4 分类原则

- 第一版只做确定性、可解释规则，不做概率模型或 AI 归因。
- 普通 `AssertionError` 无法区分产品缺陷和测试预期错误时，归入 `UNKNOWN`。
- 分类优先级固定为：`CONFIGURATION`、`FRAMEWORK_DEFECT`、`ENVIRONMENT`、`TEST_DEFECT`、`TRANSIENT`、`PRODUCT_DEFECT`、`UNKNOWN`。
- 任何失败都必须生成 FailureRecord；证据不足时使用 `UNKNOWN`，不能丢失失败。
- 分类失败本身不得替换测试失败，必须转化为 IntegrityIssue。

### 2.5 迭代边界

- 本迭代生成 merged 事实集、manifest、run.json、FailureRecord 和 IntegrityIssue。
- 本迭代不生成最终 `summary.json`、`gate-report.json`、`gate-report.md`。
- 本迭代不实现影子门禁、不修改 Jenkinsfile、不改变 CI 退出码。
- 本迭代可以计算对账所需的内部计数，但不提前输出迭代四的最终质量报告。

## 3. 需求复述

迭代二已经解决：

```text
pytest 与请求事实如何采集
-> 如何关联 Case 与 Request
-> 如何在多线程和 xdist 下安全分片
```

迭代三要解决：

```text
多个分片是否属于当前 run
-> 每条记录是否合法
-> 重复记录是重复采集还是真实多次发生
-> Case 数量是否与预收集和 JUnit 一致
-> 每个失败能否提取证据并形成稳定指纹
-> 每个失败能否进入明确责任类别或 UNKNOWN
-> 最终事实集是否完整、可复算、可追溯
```

最终目标不是“把几个 JSONL 拼起来”，而是生成一个满足以下条件的唯一事实集：

- 只包含目标 `run_id` 的记录。
- 记录通过 `quality.v1` 模型重新校验。
- 重复和冲突有确定性处理方式。
- Case invocation 可以和 JUnit 显式对账。
- 每个 failed/error phase 都有 FailureRecord。
- 每个 FailureRecord 都可以追溯分类规则、指纹算法和证据来源。
- 数据缺失或损坏不会被误认为通过。
- merge 失败不会改变 pytest 原结果和 `run_master.py` 原退出码。

## 4. 第一性原理与因果链

### 4.1 分片存在不等于事实可信

```text
磁盘上存在 JSONL
-> 可能混入旧 run、半行、损坏 JSON、错误 schema 或重复数据
-> 直接拼接会把存储现象当成业务事实
-> 统计、分类和门禁建立在污染数据上
-> 质量结论失信
```

因此 merge 必须同时承担扫描、过滤、模型校验、去重、冲突检测和来源记录，不能使用简单文件拼接。

### 4.2 去重必须区分“重复数据”和“重复问题”

```text
多个用例出现相同 failure_id
-> 表示同一失败模式影响多个 invocation
-> 如果只按 failure_id 保留一条
-> 影响范围和发生次数丢失
-> 后续报告无法回答哪些用例受影响
```

因此 occurrence 层保留每次真实失败，problem 层使用 `failure_id` 聚合同类问题；merge 只删除完全相同的重复 occurrence。

### 4.3 分类是可升级算法，不是原始事实

```text
原始异常和请求事实不变
-> 分类规则可能因误判修正而升级
-> 同一原始事实可能得到不同 category
-> 如果没有规则版本
-> 无法解释历史差异，也无法可靠回放
```

因此 manifest 必须记录分类和指纹版本，原始 Case、Request、JUnit 证据保持不变，允许未来重新计算派生结论。

### 4.4 JUnit 是证据源，不是身份源

```text
JUnit 默认只有 classname + name
-> 参数化、类方法、路径转换可能产生歧义
-> 通过字符串反推 nodeid 可能错误关联
-> 错误证据进入错误 invocation
-> 分类和指纹全部失真
```

因此由 pytest 插件显式写入 `quality_case_id`、`quality_invocation_id`。JUnit 负责提供用例级结果和异常证据，CaseResult 负责 phase 和质量身份。

### 4.5 质量归并不能成为新的测试故障源

```text
测试已经执行完成
-> merge 或分类代码抛异常
-> 如果覆盖 pytest exit code
-> 真实测试结果被质量模块替换
-> fail-open 原则被破坏
```

因此嵌入 `run_master.py` 的 merge 必须 fail-open：记录问题、尽最大努力生成 partial 产物，但最终仍返回或抛出原测试链路结果。

## 5. TOC 约束决策

当前约束已经从“事实如何采集”移动到“事实如何被证明为唯一且完整”。

| 决策点 | 选择 | TOC 原因 |
| --- | --- | --- |
| 首要约束 | 唯一归并与可对账 | 未归并的数据不能稳定进入分类、报告和门禁 |
| 身份策略 | 显式 ID，不猜测关联 | 错误关联比缺失关联更危险 |
| 损坏数据策略 | 尽量回收合法行，同时显式降级 | 全文件失败会丢失已知事实，静默跳过会掩盖风险 |
| 分类策略 | 高确定性优先，无法判断归 UNKNOWN | 降低把测试、环境问题误判为产品缺陷的成本 |
| occurrence 策略 | 全量保留，指纹只聚合 | 保持影响范围和真实发生次数 |
| 输出策略 | 原子覆盖、manifest 最后提交 | 防止消费者读取半完成事实集 |
| 集成策略 | run_master 自动 merge，退出码不变 | 建立稳定父级生命周期但不提前门禁 |
| 延后内容 | summary、Markdown、影子门禁、Jenkins | 避免同时建设事实层和决策展示层 |

优先级固定为：

```text
不改变原测试行为
> 不产生错误归属
> 不丢失真实 occurrence
> 明确暴露完整性问题
> 分类覆盖率
> 聚合丰富度
```

### 6.2 当前缺口

- 没有 aggregator、classifier、JUnit parser 和 merge CLI。
- 没有最终 `run.json` 生命周期和 merged JSONL 原子重写。

## 8. 总体架构

### 8.1 运行级数据流

```text
run_master 启动正式运行
-> 创建 initial run.json(status=partial)
-> 预收集用例并记录 expected_case_count
-> 确保每个正式 pytest 阶段有 JUnit 路径
-> pytest/xdist 写 worker shards 和 JUnit
-> 所有计划阶段结束或父级异常进入 finally
-> aggregator 扫描当前 run 分片
-> JUnit parser 读取显式 invocation property
-> 去重、对账、完整性校验
-> classifier 生成 FailureRecord
-> 原子写 merged JSONL
-> 最后写 complete/failed manifest
-> 更新 final run.json
-> 返回原 pytest 退出码或重新抛出原异常
```

### 8.2 组件关系

```text
quality.pytest_plugin
  └─ JUnit properties

quality.junit
  └─ JUnitCaseEvidence

quality.aggregator
  ├─ shard scanner
  ├─ model validator
  ├─ deduplicator
  ├─ reconciler
  ├─ integrity evaluator
  └─ merged writer

quality.classifier
  ├─ error extractor
  ├─ deterministic rules
  ├─ owner/confidence mapping
  └─ FailureRecord builder

quality.cli
  └─ merge_quality_run()

run_master
  ├─ run lifecycle
  ├─ expected stage/case/JUnit inputs
  └─ fail-open final merge
```

### 8.3 职责边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `pytest_plugin.py` | 写 Case 分片、注入 JUnit identity property | 最终分类和 merge |
| `junit.py` | XML 解析、状态和异常证据提取 | 生成质量分类 |
| `classifier.py` | 单个 failure occurrence 的分类与指纹 | 扫描文件和写最终产物 |
| `aggregator.py` | 扫描、校验、去重、对账、调用分类器、写 merged | 门禁和 Markdown 报告 |
| `cli.py` | 参数解析和手工 merge | 复制核心算法 |
| `run_master.py` | 父级生命周期和 merge 调度 | 直接实现分类规则 |

## 10. 最终产物结构

```text
reports/quality/
  run.json
  junit/
    quality.xml
    quality-parallel.xml
    quality-serial.xml
  shards/
    cases-{execution_id}-{worker_id}.jsonl
    requests-{execution_id}-{worker_id}.jsonl

    manifest.json
    case-results.jsonl
```

说明：

- `junit/` 只用于调用方未显式提供 `--junitxml` 时的默认位置。
- 调用方显式提供的 JUnit 可以位于 `reports/` 其他路径，manifest 必须记录真实路径。
- merged 文件始终是当前目标 `run_id` 的唯一事实集，不追加历史 run。
- 原始 shards 永不因 merge 被删除或改写。
- `manifest.json` 是当前 merged 快照的提交标记，必须最后完成。

## 11. Merge Manifest 设计

### 11.1 建议结构

```json
{
  manifest_version: quality.merge.v1,
  schema_version: quality.v1,
  run_id: run-id,
  status: merging|complete|failed,
  merge_version: p0-merge.v1,
  classifier_rule_version: p0-classifier.v1,
  fingerprint_version: p0-fingerprint.v1,
  created_at: 2026-07-30T16:30:00+08:00,
  expected_execution_ids: [parallel-pool, serial-pool],
  expected_case_count: 90,
  source_shards: [],
  junit_files: [],
  output_counts: {
    case_results: 270,
    invocations: 90,
    request_metrics: 180,
    failure_occurrences: 3,
    failure_fingerprints: 2,
    integrity_issues: 1
  },
  output_hashes: {}
}
```

### 11.2 source_shards

每个扫描文件至少记录：

- 相对或规范化路径。
- 类型：`cases`、`requests`、`integrity`。
- SHA-256 文件摘要。
- 物理非空行数。
- 当前 run 合法记录数。
- foreign run 记录数。
- invalid JSON、invalid schema 数。
- exact duplicate 和 conflict duplicate 数。

不得把损坏原始行、请求 body、header 或完整异常写入 manifest。

### 11.3 提交语义

- merge 开始时先原子写入 `status=merging` 的 manifest。
- merged 文件逐个原子替换。
- 所有输出完成并计算 hash 后，再原子写入 `status=complete` manifest。
- 无法完成核心输出时写 `status=failed`；若 failed manifest 也无法写，只输出脱敏 warning。
- 消费者只有在 manifest 为 `complete` 且输出 hash 匹配时，才把 merged 目录视为完整快照。

## 12. RunRecord 生命周期

### 12.1 initial run.json

正式质量运行开始时写：

```text
status = partial
integrity_status = degraded
end_time = null
integrity_issues = []
```

这样进程被中断或 merge 未执行时，不能残留一个看起来已经完成的旧 run.json。

### 12.2 元数据来源

| 字段 | 来源 |
| --- | --- |
| `run_id` | 迭代二现有父级 run_id |
| `job_name` | `JOB_NAME`，可空 |
| `build_number` | `BUILD_NUMBER`，可空 |
| `branch` | `BRANCH_NAME`，回退 `GIT_BRANCH` |
| `commit_sha` | `GIT_COMMIT` |
| `trigger` | Job 和 Build 都存在时为 `jenkins`，否则为 `local`；CLI 回放为 `manual` |
| `environment` | `USE_CHINA_ENVIRONMENT=TRUE` 为 `china`，FALSE 为 `overseas`，无法判断为 `unknown` |
| `start_time` | 父级正式质量运行开始时间，timezone-aware UTC |

不得为了读取环境名而强制初始化业务 Settings，避免缺少 API Key 时连 run.json 都无法生成。

### 12.3 final run.json

- 所有计划 pytest 阶段正常返回，即使测试失败，运行状态仍为 `finished`。
- KeyboardInterrupt、SystemExit 或父级执行被明确中断时为 `interrupted`。
- 收集或执行发生非正常父级异常、只完成部分计划阶段时为 `partial`。
- `integrity_status` 由 aggregator 状态机给出，不根据 pytest exit code 推断。
- `integrity_issues` 保存本次 merged 后的完整性问题，按确定性顺序输出。
- `end_time` 在最终写入时记录。

测试失败和数据完整性失败是两个正交维度：

```text
pytest failed + integrity complete
  = 测试确实失败，但质量事实可信

pytest passed + integrity failed
  = 测试看起来通过，但质量事实不足以形成可信结论
```

## 13. 默认 JUnit 参数设计

### 13.1 参数补全

新增内部 helper：

```text
_ensure_quality_junit_args(pytest_args, quality_config)
```

规则：

- quality 禁用时原样返回。
- 已存在 `--junitxml path` 或 `--junitxml=path` 时原样保留。
- 未提供时追加 `--junitxml={QUALITY_OUTPUT_DIR}/junit/quality.xml`。
- 随后继续复用 `_replace_junitxml_suffix()`：parallel 使用 `quality-parallel.xml`，serial 使用 `quality-serial.xml`，整体串行使用 `quality.xml`。

### 13.2 路径跟踪

- 每个实际执行阶段从最终 pytest args 中解析精确 JUnit 路径。
- 相对路径按项目根目录解析。
- run_master 把实际执行过的 JUnit 路径传给 aggregator。
- aggregator 不使用通配符扫描所有 `reports/*.xml`，避免读入旧构建文件。
- JUnit 文件修改时间早于本次 run start 时视为 stale，不参与证据关联。

### 13.3 行为兼容

- 不删除调用方原有 JUnit 文件。
- 不改变 pytest 的 JUnit family 和 testcase 表达。
- 只增加 property，不修改 failure/error/skipped 节点。
- 默认 JUnit 只在 `QUALITY_ENABLE=1` 时出现。
- JUnit 生成或解析失败不修改 pytest exit code。

## 14. JUnit Identity Property

### 14.1 注入时机

在 `pytest_runtest_protocol` 成功构建 `QualityCaseContext` 后，把以下安全属性加入 `item.user_properties`：

```text
quality_case_id = case_context.case_id
quality_invocation_id = case_context.invocation_id
```

必须在 setup report 生成前完成，保证 setup error 也能进入 JUnit property。

### 14.2 安全约束

- 不写原始 pytest 参数。
- 不写 Authorization、Cookie、API Key、请求体或响应体。
- 不新增 `quality_nodeid`；JUnit 自身已有 testcase name，额外复制可能放大参数 ID 泄露。
- 已存在同名同值 property 时不重复追加。
- 同名 property 值冲突时保留质量插件生成值，并记录 `junit_property_conflict`。

### 14.3 xdist

pytest-xdist 会把 worker TestReport 的 `user_properties` 传回 controller，JUnit 插件在 controller 侧输出 property。必须增加真实 xdist 测试，不能只用单进程 mock 推断。

## 15. JUnit Parser 设计

### 15.1 技术选择

- 使用 Python 标准库 `xml.etree.ElementTree`。
- 不新增 lxml 或其他 XML 依赖。
- 只解析本地 pytest 生成的 JUnit，不支持外部不受控 XML 扩展。
- 禁止解析外部实体；标准 ElementTree 默认不展开网络外部实体。

### 15.2 内部证据结构

`quality.junit` 使用内部 frozen dataclass：

```text
JUnitCaseEvidence
  source_path
  suite_name
  invocation_id
  case_id
  classname
  name
  status
  duration_ms
  error_type
  message
  traceback_text
  phase_hint
```

该结构是解析过程数据，不作为 `quality.v1` 公共产物直接落盘。

### 15.3 状态映射

| JUnit 节点 | JUnit 状态 |
| --- | --- |
| 无 failure/error/skipped | `passed` |
| `<failure>` | `failed` |
| `<error>` | `error` |
| `<skipped>` | `skipped` |

如果同一 testcase 同时出现多个 failure/error 子节点，全部作为证据读取，并生成 `junit_multiple_failures`；不能只取第一个后静默丢弃。

### 15.4 异常类型提取优先级

1. failure/error 节点 `type` 属性。
2. `message` 中标准 `ExceptionType: message` 异常前缀。
3. setup/teardown failure message 内部的异常类型。
4. traceback 最后一个稳定异常行。
5. 无法提取时使用 `UnknownError`。

保存时统一使用稳定短类名：

```text
requests.exceptions.ReadTimeout -> ReadTimeout
builtins.AssertionError -> AssertionError
```

### 15.5 phase_hint

- message 明确包含 `failed on setup` -> setup。
- message 明确包含 `failed on teardown` -> teardown。
- `<failure>` 默认提示 call，但最终 phase 仍以 CaseResult 失败 phase 为准。
- 无法判断时为 null，不通过 traceback 文本猜测 phase。

### 15.6 缺少 identity property

- testcase 仍计入 JUnit 总数。
- 不根据 classname/name 猜测 invocation_id。
- 记录 `junit_identity_missing`。
- 该 testcase 不能用于单 invocation 分类证据，只能用于总量对账。

## 16. 分片发现与扫描

### 16.1 扫描范围

只扫描 `QUALITY_OUTPUT_DIR/shards/` 下：

```text
cases-*.jsonl
requests-*.jsonl
integrity-*.jsonl
```

不扫描 `merged/`、JUnit、Allure、日志、未知前缀文件或不存在的 failure shard。

### 16.2 当前 run 过滤

- 每条解析成功的记录必须先完成 `quality.v1` 模型校验。
- `record.run_id == target_run_id` 才进入当前事实集。
- foreign run 记录不进入 merged 输出。
- 每个文件只生成一条 foreign run 汇总问题，记录数量，不逐行制造噪声。
- foreign run 通常为 `info`，因为固定分片名可能保留未参与本次执行的旧 worker 文件。

### 16.3 分片三件套

同一个 `{execution_id}-{worker_id}` 初始化时应同时存在 Case、Request 和 Integrity 三个文件。

- Case 分片存在但 Request 或 Integrity 同 suffix 缺失，记录 `shard_peer_missing`。
- Request 分片可以为空，因为并非每个测试都发请求。
- Integrity 分片可以为空，但文件应存在。
- expected execution 没有任何当前 run Case 分片，记录 `execution_shards_missing`。
- xdist controller 不要求 master 分片。

### 16.4 逐行容错

现有 `read_jsonl()` 保持严格语义。aggregator 新增私有或存储层容错扫描能力：

```text
文件按二进制逐行读取
-> 单行 UTF-8 解码
-> json.loads
-> 对应 Pydantic 模型校验
-> run_id 过滤
-> 收集合法记录和问题
```

单行损坏不能阻止同一文件后续合法行恢复。

### 16.5 错误信息安全

完整性问题只记录文件名、行号、异常类型和脱敏字段级摘要。禁止记录损坏原始行全文。

同一文件同一错误代码最多生成一条聚合问题，message 保存总数和前若干行号，避免 run.json 被大量错误淹没。

## 17. 去重与冲突处理

### 17.1 CaseResult

唯一候选键：`invocation_id + phase`。

- 同键且 canonical 内容完全相同：保留一条，manifest 增加 exact duplicate 计数。
- 同键但内容不同：记录 `case_duplicate_conflict`。
- 冲突时按 `start_time` 最早、再按 source path 和 line number 排序选择 canonical 记录。
- 不因 execution_id 或 worker_id 不同保留两个同 invocation phase；这表示重复执行或身份冲突。

### 17.2 RequestMetric

唯一候选键：`request_event_id`。

- 同 ID 同内容：幂等去重。
- 同 ID 不同内容：记录 `request_duplicate_conflict`。
- RequestMetric 没有开始时间，冲突时按 source path 和 line number 确定性选取，不猜测哪个更真实。

### 17.3 IntegrityIssue

IntegrityIssue 没有 issue_id，exact duplicate key 使用全部规范化字段：

```text
run_id + severity + source + code + message + related_id + created_at
```

只有全部字段相同才去重。相同 code 的多次真实问题不能合并丢失；aggregator 自己产生的批量问题应在生成时聚合。

### 17.4 FailureRecord

唯一候选键：`failure_id + invocation_id + phase`。

- 同 failure_id 不同 invocation：全部保留。
- 同 invocation 不同 phase：全部保留。
- 相同 occurrence 同内容：幂等去重。
- 相同 occurrence 内容冲突：记录 `failure_duplicate_conflict`。

### 17.5 输出顺序

- CaseResult：`case_id, invocation_id, phase_order`。
- RequestMetric：`invocation_id, interface_id, attempt_index, request_event_id`。
- FailureRecord：`failure_id, invocation_id, phase_order`。
- IntegrityIssue：`created_at, severity, source, code, related_id`。

排序只用于稳定序列化，不表示 RequestMetric 的真实时间顺序。

## 18. Invocation 折叠与 JUnit 对账

### 18.1 为什么按 invocation 对账

CaseResult 是 phase 级事实，一个正常用例通常产生 setup、call、teardown 三条记录；JUnit testcase 是 invocation 级事实。因此不能比较 CaseResult 行数和 JUnit tests 数。

对账单位固定为：

```text
unique invocation_id
```

### 18.2 invocation 最终状态

聚合器从 canonical phase 记录计算内部 invocation 状态，优先级为：

```text
setup/teardown error
> call failed
> strict xpass 形成的 failed
> xpassed
> passed
> xfailed
> skipped
```

具体规则：

- setup error：invocation 为 error；通常没有 call。
- call failed：invocation 为 failed；若 teardown 同时 error，最终对账状态为 error，但两个 failure occurrence 都保留。
- teardown error：即使 call passed，invocation 仍为 error。
- xfailed 与普通 skipped 对 JUnit 都映射为 skipped，但质量内部继续保留差异。
- 非严格 xpassed 对 JUnit 映射为 passed；严格 xpass 在 pytest report 中已经表现为 failed。

### 18.3 三方数量对账

比较三个数字：

1. `expected_case_count`：run_master 预收集数量。
2. `merged_invocation_count`：当前 run canonical invocation 数量。
3. `junit_testcase_count`：本次实际 JUnit testcase 数量。

规则：

- 三者一致：数量完整。
- merged 少于 expected：可能丢分片或 case 写入失败，属于关键完整性错误。
- merged 多于 expected：可能重复执行、身份算法错误或混入错误 run。
- JUnit 与 expected/merged 不一致：记录 `junit_count_mismatch`。
- 调用阶段因 collection 或父级异常未完成时，expected 数仍保留，但 RunStatus 为 partial。

### 18.4 identity 对账

- 每个带 `quality_invocation_id` 的 JUnit testcase 应能找到 merged invocation。
- 每个 merged invocation 应有且只有一个 JUnit testcase。
- 一个 invocation 出现在多个 JUnit 文件时记录 `junit_invocation_duplicate`。
- JUnit case_id 与 CaseResult case_id 不一致时记录 `junit_case_identity_mismatch`。
- identity 缺失时不能使用 classname/name 回退。

### 18.5 状态对账

| 质量 invocation 状态 | 期望 JUnit 状态 |
| --- | --- |
| passed、xpassed | passed |
| failed | failed |
| error | error |
| skipped、xfailed | skipped |

不一致时记录 `junit_status_mismatch`，并同时保留 Case 和 JUnit 两侧状态。CaseResult 不被 JUnit 覆盖，JUnit 也不被质量模块改写。

## 19. Failure Candidate 生成

### 19.1 生成范围

以下 canonical phase 生成 failure candidate：

- `raw_status=failed`。
- `raw_status=error`。
- `final_status=failed` 或 `final_status=error`，即使未来 raw/final 不同。

以下不生成 FailureRecord：

- passed。
- skipped。
- xfailed。
- 非严格 xpassed。
- collection failure；它没有合法 case/invocation，继续作为 IntegrityIssue。

### 19.2 多 phase 失败

同一 invocation 可能同时发生：

```text
call failed
+ teardown error
```

必须生成两条 FailureRecord，并使用不同 phase 参与 failure fingerprint。不能只保留最终 invocation 状态。

### 19.3 证据选择

对每个 candidate 收集：

- CaseResult phase 和状态。
- 同 invocation 的 JUnit failure/error 证据。
- 同 invocation 的 RequestMetric 列表。
- 同 invocation 或 case 相关 IntegrityIssue。
- JUnit 文件和 Case 分片的安全证据引用。

JUnit phase_hint 与 CaseResult phase 一致时优先关联；无法唯一选择 JUnit evidence 时不猜测，使用缺失证据回退并记录 `failure_evidence_ambiguous`。

### 19.4 缺失证据回退

即使没有可关联 JUnit evidence，也必须生成：

```text
error_type = UnknownError
normalized_message = failure evidence unavailable
category = UNKNOWN
owner_domain = unknown
confidence = low
```

### 20.4 规则实现方式

- 分类规则使用有序、不可变的 rule 列表。
- 每条规则必须有稳定 `rule_id`，例如 `configuration.missing_required_env`。
- 第一条满足全部条件的规则获胜。
- 规则只读取结构化字段和规范化文本，不读取原始请求 body、header 或完整响应。
- 规则中的关键词集合集中定义，不散落在 if/else 中。
- 规则顺序和关键词变化必须升级 `CLASSIFIER_RULE_VERSION`。
- 每条规则至少有正例、反例和边界测试。

### 20.5 请求证据选择

- 只读取同 invocation 的 RequestMetric。
- 当且仅当存在唯一、明确相关的失败 interface 时，写入 fingerprint source 的 `interface_id`。
- 多个失败 interface 无法判断主因时，`interface_id=None`，不能根据文件顺序猜测。
- HTTP 2xx 普通请求仍保持 success；业务正文错误继续由 Case 断言表达。
- polling、retry、SSE 继续沿用迭代二的原始 business_status，不在 classifier 中重解释协议语义。

### 20.6 fail-open

单个 candidate 分类抛异常时：

1. 记录 `failure_classification_failed`。
2. 使用 UNKNOWN fallback 生成 FailureRecord。
3. 继续处理其他 failure occurrence。

禁止因为一条失败无法分类而放弃整个 merged 事实集。

## 21. 失败指纹与 Case 回填

### 21.1 规范化输入

继续复用迭代一现有：

- `normalize_failure_message()`。
- `build_failure_message_hash()`。
- `build_failure_fingerprint()`。

指纹输入固定为：

```text
phase
+ error_type
+ normalized_message
+ unambiguous interface_id
+ assert_location
```

### 21.2 assert_location

从 JUnit traceback 中提取最后一个稳定、仓库内 Python 位置：

```text
module/test_x.py:88
```

规则：

- 转换为相对项目路径并统一 `/`。
- 去除列号、临时目录前缀和随机段。
- 优先测试断言位置，不选择 pytest、site-packages 内部帧。
- 无法可靠提取时为 null。
- 不读取或落盘完整 traceback。

### 21.3 FailureRecord 构建

每个 occurrence 生成：

- `run_id`、`case_id`、`invocation_id`、`phase`。
- `failure_id`。
- `category`、`owner_domain`、`confidence`。
- `error_type`、`normalized_message`。
- `FailureFingerprintSource`。
- `manual_override=None`。

### 21.4 CaseResult.failure_id 回填

原始 shard 不改写。aggregator 在 merged CaseResult 中使用 `model_copy(update=...)`：

- failed/error phase 填入对应 `failure_id`。
- 非失败 phase 保持 null。
- 一个 phase 必须只对应一个 occurrence。
- 如果同一 phase 产生多个不可区分 evidence，仍只生成一个 UNKNOWN FailureRecord，并记录证据歧义问题。

### 21.5 聚合语义

`failure_id` 相同表示同一规范化失败模式，迭代四可以据此计算：

- occurrence 次数。
- 受影响 invocation 数。
- 受影响 case 数。
- 受影响 interface 数。

本迭代只保证数据可聚合，不提前生成问题排行榜或趋势报告。

## 22. 完整性问题设计

### 22.1 分片与模型

| code | severity | 状态影响 | 含义 |
| --- | --- | --- | --- |
| `shards_directory_missing` | error | failed | 没有可扫描分片目录 |
| `execution_shards_missing` | error | failed | 计划执行阶段没有当前 run Case 分片 |
| `shard_peer_missing` | warn/error | degraded | worker 三件套缺失成员 |
| `shard_read_failed` | error | degraded/failed | 文件无法读取 |
| `shard_utf8_invalid` | error | degraded/failed | 行无法 UTF-8 解码 |
| `shard_json_invalid` | error | degraded/failed | JSONL 行损坏 |
| `shard_schema_invalid` | error | degraded/failed | 记录不符合 `quality.v1` |
| `foreign_run_records_ignored` | info | 无 | 忽略其他 run 记录 |

是否 failed 取决于损坏是否导致关键 Case invocation 缺失；不能只根据 severity 机械映射。

### 22.2 去重与身份

| code | severity | 状态影响 | 含义 |
| --- | --- | --- | --- |
| `case_duplicate_conflict` | error | failed | 同 invocation phase 出现冲突事实 |
| `request_duplicate_conflict` | error | degraded | 同 request_event_id 内容冲突 |
| `failure_duplicate_conflict` | error | degraded | 同 failure occurrence 内容冲突 |
| `case_identity_inconsistent` | error | failed | invocation 对应多个 case_id/param 身份 |
| `request_case_missing` | error | degraded | RequestMetric 无法找到 merged Case invocation |

RequestMetric 模型本身要求 case/invocation 非空；这里校验的是引用对象是否存在。

### 22.3 JUnit 与对账

| code | severity | 状态影响 | 含义 |
| --- | --- | --- | --- |
| `junit_missing` | warn | degraded | 预期 JUnit 文件未生成 |
| `junit_stale` | warn | degraded | 文件早于本次运行 |
| `junit_parse_failed` | error | degraded | XML 无法解析 |
| `junit_identity_missing` | warn | degraded | testcase 缺少 quality invocation property |
| `junit_property_conflict` | error | degraded | 同名 quality property 值冲突 |
| `junit_invocation_duplicate` | error | failed | 同 invocation 出现多个 testcase |
| `junit_case_identity_mismatch` | error | failed | JUnit 和 Case 的 case_id 不一致 |
| `junit_count_mismatch` | error | failed | expected、merged、JUnit 数量不一致 |
| `junit_status_mismatch` | error | degraded | invocation 状态不一致 |
| `junit_multiple_failures` | warn | degraded | 单 testcase 存在多个失败证据 |

### 22.4 分类与输出

| code | severity | 状态影响 | 含义 |
| --- | --- | --- | --- |
| `failure_evidence_missing` | warn | degraded | 失败没有可关联 JUnit 证据 |
| `failure_evidence_ambiguous` | warn | degraded | 多份证据无法唯一选择 |
| `failure_classification_failed` | error | degraded | 分类器异常并使用 UNKNOWN fallback |
| `failure_record_missing` | error | failed | failed/error phase 没有 FailureRecord |
| `merged_output_write_failed` | error | failed | 核心 merged 文件写入失败 |
| `manifest_write_failed` | error | failed | manifest 无法提交 |
| `run_record_write_failed` | error | failed | run.json 无法初始化或完成 |
| `parent_collection_failed` | error | failed | run_master 预收集失败 |
| `parent_execution_interrupted` | error | degraded/failed | 父级执行被中断 |

### 22.5 message 和 related_id

- message 只写组件、计数、文件名、行号和脱敏错误摘要。
- 不写原始 JSONL 行、完整 traceback、XML failure body、请求 body 或 header。
- Case 问题优先 related_id=`invocation_id`。
- Request 问题优先 related_id=`request_event_id`。
- 文件级问题 related_id 使用规范化相对路径。
- run 级问题 related_id 使用 `run_id`。

## 23. IntegrityStatus 状态机

### 23.1 complete

同时满足：

- 所有 expected execution 有当前 run Case 分片。
- expected、merged invocation、JUnit testcase 数一致。
- 所有带 identity 的 JUnit testcase 一一对应 merged invocation。
- 所有 failed/error phase 有 FailureRecord，包括 UNKNOWN。
- Case 和 Request 唯一键无冲突。
- 核心 merged 文件和 complete manifest 写入成功。
- 没有影响可信度的 warn/error 完整性问题。

### 23.2 degraded

核心事实集仍可使用，但存在明确缺口，例如：

- JUnit 缺失、stale、部分 testcase 缺少 identity。
- 非关键 Request 分片损坏，但 Case 对账仍完整。
- failure evidence 缺失，已使用 UNKNOWN fallback。
- JUnit 状态与 Case 状态不一致，但 invocation 数量和身份仍可确认。
- classifier 单条规则异常但 FailureRecord 已回退生成。

degraded 不能被解释为 complete，迭代四报告必须展示问题。

### 23.3 failed

任一关键条件成立：

- expected case 大于 0，但没有可用 Case invocation。
- expected、merged invocation 数量不一致。
- 同 invocation phase 存在冲突 Case 事实。
- JUnit identity 指向错误 Case 或重复 invocation。
- failed/error phase 无法生成 FailureRecord。
- merged Case、Request、Failure、Integrity 任一核心输出无法提交。
- manifest 无法标记完整快照。

### 23.4 状态计算顺序

```text
先收集全部 IntegrityIssue
-> 根据 code 和实际影响判定 critical conditions
-> critical 存在则 failed
-> 否则存在影响可信度的 warn/error 则 degraded
-> 否则 complete
```

不能简单使用“存在 error 就 failed”，因为某条无效 Request 行可能不影响 Case 事实；也不能简单使用“merge 有输出就 complete”。

同时记录 `failure_evidence_missing`。这样“所有失败可路由”和“证据缺失可见”可以同时满足。

## 20. 确定性失败分类

### 20.1 分类输入

classifier 接收一个内部 `FailureEvidence`，至少包含：

```text
run_id
case_id
invocation_id
phase
error_type
normalized_message
assert_location
junit_status
request_metrics
related_integrity_codes
```

classifier 不读取文件、不直接写 JSONL，也不依赖全局 collector。

### 20.2 规则输出

每个规则返回：

```text
category
owner_domain
confidence
rule_id
reason_code
selected_interface_id
```

`rule_id` 和 `reason_code` 用于测试、日志和 manifest 统计，不写入已经冻结的 FailureRecord 字段。

### 20.3 分类优先级

#### CONFIGURATION

高确定性证据：

- 明确缺少必填环境变量、API Key、路由或环境选择。
- Pydantic/配置校验消息明确指向配置字段。
- 401/403 同时存在 credential、permission、authorization 等明确配置证据。
- 启动阶段出现已知配置异常类型。

不能只因为 HTTP 401/403 就直接判配置；缺少凭据证据时进入 UNKNOWN。

输出：

```text
owner_domain = configuration
confidence = high|medium
```

#### FRAMEWORK_DEFECT

高确定性证据：

- traceback/assert_location 明确位于 `quality/` 的 collector、plugin、aggregator、classifier、storage。
- 完整性代码明确为框架内部不变量破坏。
- 公共框架 API 出现确定性的 TypeError、AttributeError、模型构建或序列化错误，并且不是服务端响应导致。

不能把所有 `common/` 路径异常都判框架缺陷；请求超时、连接失败仍按环境或瞬态处理。

输出：

```text
owner_domain = framework
confidence = high|medium
```

#### ENVIRONMENT

高确定性证据：

- DNS/NameResolutionError。
- ConnectionRefused、HostUnreachable、NetworkUnreachable。
- ProxyError、SSL handshake/certificate、端口或依赖服务不可达。
- 资源不足、磁盘不可写、环境服务未启动，并且证据不指向质量代码自身。

输出：

```text
owner_domain = environment
confidence = high|medium
```

#### TEST_DEFECT

只接受明确测试侧证据：

- fixture 参数构造错误或测试数据 schema 明确不合法。
- 测试资源文件路径、清理逻辑或本地测试辅助函数确定性错误。
- 异常位置明确在业务测试代码，且错误与 API 响应无关，例如本地 KeyError、IndexError、测试数据转换错误。

普通 AssertionError、服务端错误后触发的测试断言不能直接判 TEST_DEFECT。

输出：

```text
owner_domain = test
confidence = high|medium
```

#### TRANSIENT

高确定性证据：

- HTTP 429 或明确 rate limit 错误。
- `retryable=true` 且错误为 ReadTimeout、ConnectTimeout、ConnectionReset 等瞬态类型。
- 服务明确返回可恢复、稍后重试语义。

DNS、持续连接拒绝等基础环境问题优先归 ENVIRONMENT。

输出：

```text
owner_domain = environment
confidence = high|medium
```

当前 OwnerDomain 没有 transient 枚举，因此 TRANSIENT 暂归 environment 责任域；后续如需独立责任域必须升级契约。

#### PRODUCT_DEFECT

只在存在明确产品或契约证据时匹配：

- API 已返回确定响应，JUnit 断言明确表达状态码、字段、类型或契约不符合预期。
- 同 invocation 存在唯一可关联的失败 RequestMetric，且不是配置、环境或瞬态规则。
- 明确业务失败终态或稳定错误响应触发断言。

只有 `AssertionError`、只有 HTTP 500、或多个请求都可能导致失败时，不直接判 PRODUCT_DEFECT。

输出：

```text
owner_domain = product
confidence = high|medium
```

#### UNKNOWN

以下情况统一进入 UNKNOWN：

- 普通 AssertionError 无法区分产品和测试预期。
- JUnit 证据缺失或无法唯一关联。
- 多类规则同时命中且优先级证据不足。
- 只有模糊错误文本，没有稳定异常类型、位置或请求证据。
- classifier 自身安全降级。

输出：

```text
owner_domain = unknown
confidence = low
```
