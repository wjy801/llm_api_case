# P0 迭代四：报告与影子门禁详细开发方案

## 1. 文档定位

本方案用于指导 P0 迭代四“报告与影子门禁”的代码开发，输入依据按以下层级理解：

1. `dev/P0与P1质量工程后续开发方向.md`：确定 P0/P1 的整体边界和质量工程顺序。
2. `dev/P0质量数据底座详细开发方案.md`：确定 P0 的事实链、报告、影子门禁和 Jenkins 接入目标。
3. `dev_plan/P0迭代三归并完整性与失败分类详细开发方案.md`：确定迭代四可以消费的 merged 事实集契约。
4. 当前代码基线：`quality/models.py`、`quality/aggregator.py`、`quality/cli.py`、`run_master.py`、`Jenkinsfile`。
5. 本文件：把迭代四细化为可直接开发的模块职责、输入校验、统计口径、影子门禁规则、Jenkins 邮件接入、测试矩阵和实施顺序。

本方案只做开发设计，不直接修改运行逻辑。后续执行开发时，应按本文件拆分任务并在完成后另写代码变更记录。

## 2. 需求复述

迭代四要在迭代三已经生成可信 merged 事实集之后，补齐 P0 最后一个闭环：

```text
merged 事实集
-> 输入可信校验
-> summary.json
-> gate-report.json
-> gate-report.md
-> run_master 自动生成
-> Jenkins artifact 与邮件摘要入口
```

它要回答四个问题：

- 本次执行的数据是否完整，报告是否消费了正确的 run。
- 本次测试结果、失败分类和接口请求指标分别是什么。
- 如果当前影子门禁规则生效，会得到 `PASS/WARN/BLOCK/NO_DATA` 中哪一种结论。
- 这个结论为什么产生，证据在哪里，是否因为样本不足而不能判断。

迭代四仍属于 P0，因此影子门禁只输出结论，不改变 pytest、run_master 或 Jenkins 的原退出码。

## 3. 第一性原理判断

报告不是目的，报告只是把事实转换成可复核结论的界面。门禁也不是目的，门禁是把可复核结论固化成可回放规则。

所以迭代四的本质不是“生成更好看的质量报告”，而是建立以下链路：

```text
可信归并事实
-> 确定性统计
-> 可解释规则
-> 可回放影子结论
-> 人和机器使用同一份结论
```

如果输入事实不可信，报告越完整，误导越大；如果统计口径不唯一，门禁结论无法复盘；如果样本量不足仍强行判定，影子门禁会快速失去公信力。

因此本迭代的关键不是展示层，而是三个不可放松的约束：

- 报告只消费 `manifest.status == complete` 且 hash 校验通过的 merged 快照。
- 用例统计必须按 `invocation_id` 折叠，不按 CaseResult phase 行数统计。
- 请求类比例规则必须检查 `sample_size`，样本不足时不能直接给强结论。

## 4. 目标障碍与因果链

### 4.1 报告消费旧数据或半成品

因果链：

```text
report 直接读取 JSONL
-> 没有校验 manifest 状态、run_id 和 output hash
-> 可能读到上次构建残留、merge 过程中的半成品或人工改过的文件
-> summary 与真实执行不一致
-> gate-report 给出错误结论
-> 后续 P1 基线和强门禁建立在污染数据上
```

真正要解决的问题不是“文件能不能读”，而是“这批文件是否属于同一次完整提交的质量事实集”。

### 4.2 phase 行数被误当作用例数

因果链：

```text
pytest 一个 invocation 可能有 setup/call/teardown 多条 CaseResult
-> 直接统计 CaseResult 行数
-> 一个用例被算多次
-> 通过率、失败率、跳过率全部偏移
-> JUnit 对账、门禁和邮件摘要口径不一致
```

真正要解决的问题是统一用例统计口径：`case_total` 永远等于唯一 `invocation_id` 数量。

### 4.3 样本不足导致误判

因果链：

```text
只执行 1 次请求且这次请求超时
-> timeout rate = 100%
-> 如果只看比例会触发 WARN/BLOCK
-> 观察期产生大量噪声
-> 团队开始忽略影子门禁
-> P1 强制门禁缺少可信基础
```

真正要解决的问题是让每条比例规则同时看 `actual`、`threshold` 和 `sample_size`。样本不足不是通过，也不是失败，而是 `NO_DATA` 或带说明的观察性风险。

### 4.4 报告生成异常影响原测试结果

因果链：

```text
pytest 已经得到原始退出码
-> report/gate 生成失败
-> 如果异常冒泡覆盖原退出码
-> 测试失败原因被质量工具失败替换
-> CI 调试方向错误
-> 团队降低质量工具启用意愿
```

真正要解决的问题是 fail-open：质量报告生成失败必须可见，但不能改变原测试结果。

## 5. TOC 约束分析

当前系统的约束已经从“是否有结构化事实”转移为“派生结论是否可信”。

| 决策点 | 约束判断 | 迭代四选择 |
| --- | --- | --- |
| 首要约束 | 报告和门禁不能误读 merged 事实 | 先做 manifest、run_id、hash 和模型校验 |
| 统计口径 | phase 事实天然多行 | 所有用例统计按 invocation 折叠 |
| 门禁策略 | 没有历史基线和 Flaky 状态机 | 只做影子门禁，不改变退出码 |
| 请求指标 | 当前只有 attempt 粒度事实 | 不推断逻辑请求链和重试挽救率 |
| 样本可信度 | 小样本比例不稳定 | 请求比例规则必须带最小样本量 |
| Jenkins 接入 | 已归档 `reports/**` | 只补环境变量和邮件摘要，不重复归档路径 |

本迭代不应该把精力放在趋势图、历史基线、AI 归因或强制阻断上。这些能力会放大当前仍在观察期的数据噪声。

## 9. 模块设计

### 9.1 `quality/report.py`

职责：

- 加载并校验 `merged/manifest.json`。
- 校验 `run_id`、`status`、`output_hashes` 和输出文件存在性。
- 使用现有 Pydantic 模型逐行读取 merged JSONL。
- 按唯一 `invocation_id` 生成用例统计。
- 生成请求统计、接口聚合、失败分类统计和完整性摘要。
- 调用 `quality.gate` 得到影子门禁结论。
- 原子写出 `summary.json`、`gate-report.json`、`gate-report.md`。

建议公开 API：

```python
@dataclass(frozen=True)
class QualityReportRequest:
    run_id: str
    output_dir: Path
    shadow_gate: bool = True
    min_request_samples: int = 20
    http_5xx_warn_rate: float = 0.02
    timeout_warn_rate: float = 0.05

@dataclass(frozen=True)
class QualityReportResult:
    run_id: str
    output_dir: Path
    summary_path: Path
    gate_report_json_path: Path
    gate_report_md_path: Path
    overall: GateResult
    integrity_status: IntegrityStatus

def generate_quality_report(request: QualityReportRequest) -> QualityReportResult:
    ...
```

### 9.2 `quality/gate.py`

职责：

- 接收已经计算好的 summary、失败分类统计、请求统计和输入校验状态。
- 按确定性规则生成 `GateRuleDecision`。
- 聚合得到 `GateDecision.overall`。
- 不读文件、不写文件、不依赖 Jenkins。

建议公开 API：

```python
REPORT_VERSION = "p0-report.v1"
GATE_RULESET_VERSION = "p0-shadow-gate.v1"

@dataclass(frozen=True)
class ShadowGateConfig:
    enabled: bool = True
    min_request_samples: int = 20
    http_5xx_warn_rate: float = 0.02
    timeout_warn_rate: float = 0.05

def evaluate_shadow_gate(context: ShadowGateContext, config: ShadowGateConfig) -> GateDecision:
    ...
```

`ShadowGateContext` 可以是内部 dataclass，不需要进入 `quality.v1` 模型契约。

## 10. 版本策略

不要修改 `SCHEMA_VERSION = "quality.v1"`。

新增派生产物版本：

```text
REPORT_VERSION = p0-report.v1
GATE_RULESET_VERSION = p0-shadow-gate.v1
```

版本写入位置：

- `summary.json.report_version`
- `summary.json.source_manifest.merge_version`
- `summary.json.source_manifest.classifier_rule_version`
- `summary.json.source_manifest.fingerprint_version`
- `gate-report.json.report_version`
- `gate-report.json.gate_ruleset_version`
- 每条 `GateRuleDecision.rule_version`
- `gate-report.md` 标题或基础信息区

版本的作用是支持后续回放：相同 merged 事实在不同 report/gate 规则版本下可能得到不同派生结论，必须可追溯。

## 11. 输入可信校验

报告生成必须先做输入校验。校验失败时，优先生成 `NO_DATA` gate report；如果连最小报告也无法写出，则 fail-open 只打印 warning。

### 11.1 必须校验项

| 校验项 | 失败处理 |
| --- | --- |
| `merged/manifest.json` 存在 | 生成 `NO_DATA` gate report |
| manifest JSON 可解析 | 生成 `NO_DATA` gate report |
| `manifest.run_id == request.run_id` | 生成 `NO_DATA` gate report |
| `manifest.status == complete` | 生成 `NO_DATA` gate report |
| `manifest.schema_version == quality.v1` | 生成 `NO_DATA` gate report |
| output 文件存在 | 生成 `NO_DATA` gate report |
| output hash 匹配 | 生成 `NO_DATA` gate report |
| JSONL 每行可被对应模型解析 | 记录 report 输入问题；关键文件无法解析则 `NO_DATA` |

### 11.2 可降级项

| 校验项 | 降级处理 |
| --- | --- |
| `run.json` 缺失 | summary 标记 run metadata missing，gate 可继续 |
| `run.json.run_id` 不一致 | summary 标记 run metadata mismatch，gate 规则 WARN 或 NO_DATA |
| `integrity-issues.jsonl` 缺失但 manifest 未列 hash | 输入不可完全解释，整体 `NO_DATA` |
| 单条非关键扩展字段缺失 | 不影响 `quality.v1` 解析时继续 |

### 11.3 不允许的行为

- 不允许跳过 manifest 直接消费 JSONL。
- 不允许 hash 不一致时仍输出 `PASS`。
- 不允许把 manifest `status=failed` 或 `merging` 当成完整输入。
- 不允许为了生成报告而修改 merged 文件。
- 不允许在 report 阶段重新分类 FailureRecord。

建议结构：

  "schema_version": "quality.v1",

  "summary": {
    "schema_version": "quality.v1",

## 13. 用例统计口径

### 13.1 invocation 折叠规则

用例统计必须先按 `invocation_id` 分组，再从组内 phase 事实折叠最终状态。

最终状态优先级：

```text
error
> failed
> skipped/xfailed
> passed/xpassed
```

解释：

- 任一 phase 为 `error`，该 invocation 计为 `case_error`。
- 否则任一 phase 为 `failed`，计为 `case_failed`。
- 否则如果状态只包含 `skipped` 或 `xfailed`，计为 `case_skipped`。
- 其他情况计为 `case_passed`，包括 `xpassed`。

必须满足：

```text
case_total = unique(invocation_id)
case_passed + case_failed + case_error + case_skipped = case_total
```

### 13.2 raw 与 final 通过率

- `raw_pass_rate` 使用 `raw_status` 按相同优先级折叠。
- `final_pass_rate` 使用 `final_status` 按相同优先级折叠。
- 当前没有可靠 rerun 生命周期，不推断重试挽救结果，`retry_passed` 第一版固定为 `0`。

如果后续接入 pytest-rerunfailures 或自研重跑，需要增加独立事实字段后再计算 `retry_passed`，不能从同一 run 内重复 case 猜测。

### 13.3 duration 口径

单个 invocation 的用例耗时可以按组内 phase `duration_ms` 求和，用于 Markdown 展示慢用例，但第一版不做耗时门禁。

## 14. 失败统计口径

失败统计只消费 `merged/failures.jsonl` 中的 `FailureRecord`。

第一版统计：

- 按 `category` 统计 occurrence 数。
- 按 `owner_domain` 统计 occurrence 数。
- 按 `confidence` 统计 occurrence 数。
- 按 `failure_id` 聚合问题数。
- 按 `failure_id` 输出 top failures，展示 affected invocation 数和示例 case。

必须区分：

| 指标 | 含义 |
| --- | --- |
| occurrence count | FailureRecord 行数，表示失败发生次数 |
| fingerprint count | 唯一 `failure_id` 数，表示失败模式数 |
| affected invocation count | 受影响的 invocation 数 |
| affected case count | 受影响的稳定 case_id 数 |

不要用唯一 `failure_id` 替代失败 occurrence。否则同一问题影响多个用例时，报告会低估影响面。

## 15. 请求统计口径

第一版只使用当前 `RequestMetric` 中可靠字段：

- `request_total`
- `request_success_rate`
- `http_5xx_count`
- `timeout_count`
- `duration_ms`
- `interface_id`
- `method`
- `url_template`
- `business_status`
- `status_code`

### 15.1 请求成功率

建议口径：

```text
request_success = business_status == success and timeout == false and error_type is None
request_success_rate = success_count / request_total
```

说明：

- `status_code` 为空的非 HTTP/SSE/POLLING 异常请求不应被当成成功。
- HTTP 5xx 单独统计，但不等同于所有失败。
- 业务失败与 HTTP 失败是两个维度，第一版优先保持可解释，不混合推断。

当 `request_total == 0`：

- `request_success_rate` 在 `QualitySummary` 中写 `0.0`。
- gate 请求规则输出 `NO_DATA`。
- Markdown 明确展示“本次没有请求样本”。

### 15.2 接口聚合

按 `interface_id` 聚合：

- `request_count`
- `success_count`
- `failure_count`
- `http_5xx_count`
- `timeout_count`
- `avg_duration_ms`
- `max_duration_ms`
- `method`
- `url_template`

排序建议：

1. `http_5xx_count + timeout_count` 降序。
2. `max_duration_ms` 降序。
3. `request_count` 降序。
4. `interface_id` 升序。

第一版不做：

- P95/P99。
- retry rescue rate。
- 逻辑请求链路识别。
- 成本门禁。

## 16. 完整性展示口径

完整性从三处读取：

- `manifest.integrity_status`
- `merged/integrity-issues.jsonl`
- `run.json.integrity_status`

优先级：

1. manifest 是 merged 快照是否可消费的提交依据。
2. `integrity-issues.jsonl` 是具体证据。
3. `run.json` 是父级运行状态和最终汇总记录。

如果 manifest 与 `run.json` 的完整性状态不一致：

- summary 展示差异。
- gate 规则至少 WARN。
- 如果 manifest 不可消费，整体 `NO_DATA`。

## 17. 影子门禁规则

第一版规则集必须小而确定，避免把观察期做成误判放大器。

### 17.1 规则列表

| rule_id | 判断 | 结论 |
| --- | --- | --- |
| `p0.integrity.available` | manifest 不完整、缺失、hash 不一致或无法解析 | `NO_DATA` |
| `p0.integrity.degraded` | manifest 可消费但 integrity_status 为 degraded | `WARN` |
| `p0.failure.product_defect` | 存在 `PRODUCT_DEFECT` occurrence | `BLOCK` |
| `p0.failure.configuration` | 存在 `CONFIGURATION` occurrence | `BLOCK` |
| `p0.failure.framework_defect` | 存在 `FRAMEWORK_DEFECT` occurrence | `WARN` |
| `p0.failure.unknown` | 存在 `UNKNOWN` occurrence | `WARN` |
| `p0.request.http_5xx_rate` | 样本不足 `NO_DATA`；否则 5xx rate 超阈值 `WARN` | `NO_DATA/WARN/PASS` |
| `p0.request.timeout_rate` | 样本不足 `NO_DATA`；否则 timeout rate 超阈值 `WARN` | `NO_DATA/WARN/PASS` |

### 17.2 暂不实现的规则

以下规则第一版不实现：

- “`CONFIGURATION` 导致大面积失败”比例判断。当前总纲没有定义大面积比例，直接用存在即 `BLOCK` 更确定。
- JUnit 与 case 数不一致规则。迭代三已经把对账问题转成 integrity issue，迭代四只消费 integrity 状态。
- P95/P99 性能门禁。当前没有稳定样本窗口和历史基线。
- 成本门禁。当前 P0 不做账单体系判断。
- Flaky 相关规则。没有跨构建状态机。

## 18. overall 聚合规则

基础风险优先级：

```text
BLOCK > WARN > PASS
```

`NO_DATA` 不是风险高低，而是可判断性状态。因此 overall 需要按输入状态处理。

建议聚合：

| 场景 | overall |
| --- | --- |
| 全局输入不可消费，如 manifest 缺失、非 complete、hash 不一致 | `NO_DATA` |
| 全局完整性为 failed | `NO_DATA` |
| 任一可执行规则 `BLOCK` | `BLOCK` |
| 任一可执行规则 `WARN` | `WARN` |
| 所有可执行规则 `PASS`，但请求比例规则样本不足 | `WARN`，并在 Markdown 标记“部分规则 NO_DATA” |
| 所有规则都可执行且全部 `PASS` | `PASS` |
| 无任何可判断数据 | `NO_DATA` |

说明：

- 不要让局部请求样本不足覆盖已经确定的 `BLOCK`。
- 不要在存在数据不足时展示“全绿”。
- `NO_DATA` 规则必须保留在 `rules` 中，让后续能复盘为什么没判断。

## 20. CLI 行为

`quality.cli` 从单命令 `merge` 扩展为多命令：

```powershell
python -m quality.cli merge --run-id <id> --output-dir reports/quality
python -m quality.cli report --run-id <id> --output-dir reports/quality
```

退出码建议：

| 场景 | 退出码 |
| --- | --- |
| report 成功生成，即使 overall 为 `BLOCK/WARN/NO_DATA` | 0 |
| 参数错误 | 2 |
| 无法生成任何 summary 或 gate-report | 2 |

CLI 退出码表达工具是否执行成功，不表达质量门禁是否通过。影子门禁结论只写入 report。

## 21. run_master 集成

当前 `_finalize_quality_run()` 已经：

```text
merge_quality_run()
-> write run.json
```

迭代四调整为：

```text
merge_quality_run()
-> write run.json
-> generate_quality_report()
```

关键要求：

- `generate_quality_report()` 只在 `QUALITY_ENABLE=1` 且存在 `quality_config.run_id` 时触发。
- report 生成异常必须被捕获并打印 `Quality report failed open: ...`。
- 不改变原 pytest exit code。
- 不替换 `KeyboardInterrupt`、`SystemExit` 等原异常。
- merge 返回 failed manifest 时，尽最大努力生成 `NO_DATA` gate report。
- report 失败不得覆盖已经写出的 `run.json`。

建议实现位置：

- `run_master.py` import `QualityReportRequest` 和 `generate_quality_report`。
- `_finalize_quality_run()` 在 `write_json_atomic(run.json)` 之后调用。
- 阈值配置解析封装成小函数，例如 `_load_quality_report_config()`。

## 23. Markdown 报告内容

`gate-report.md` 建议结构：

```text
# P0 质量影子门禁报告

## 结论
- Overall: WARN
- Mode: shadow
- Integrity: degraded
- Run ID: ...

## 为什么得到这个结论
| 规则 | 结论 | 实际值 | 阈值 | 样本量 | 证据 |

## 用例结果
| 总数 | 通过 | 失败 | 错误 | 跳过 | 通过率 |

## 失败分类
| 分类 | occurrence | affected invocation | 示例 |

## 请求指标
| 总请求 | 成功率 | 5xx | 超时 |

## 接口风险 Top
| interface_id | 请求数 | 5xx | 超时 | 平均耗时 | 最大耗时 |

## 完整性问题
| severity | source | code | message |
```

Markdown 必须避免输出：

- 原始 request/response body。
- Authorization、Cookie、API key。
- 完整异常堆栈。
- 高基数 request id 排行。

证据优先使用：

- `failure_id`
- `case_id`
- `invocation_id`
- `interface_id`
- `IntegrityIssue.code`
- `IntegrityIssue.related_id`

## 24. 安全与脱敏

迭代四不重新脱敏原始输入，只消费迭代二、三已经脱敏和规范化的结构化事实。

但 report 层仍要防二次泄露：

- Markdown 中不展示 `normalized_message` 的长文本，只展示截断摘要。
- integrity issue message 已经由 aggregator 限长，但 Markdown 再做长度限制。
- 接口展示用 `url_template`，不展示真实 URL query。
- 不按 `server_request_id` 做 Top 排行。
- JSON 报告可以保留结构化 evidence，但不新增 body/header 字段。

## 26. 实施顺序

### 阶段一：输入读取与 summary

1. 新增 `quality/report.py` 基础 dataclass 和加载函数。
2. 实现 manifest 校验、hash 复算和 JSONL 模型读取。
3. 实现 invocation 折叠。
4. 实现 `QualitySummary` 构建。
5. 写 `summary.json`。

退出条件：

- 合成 complete merged 目录可以生成正确 `summary.json`。
- phase 多行不会导致 case_total 偏大。

### 阶段二：gate 规则

1. 新增 `quality/gate.py`。
2. 实现 `ShadowGateConfig`。
3. 实现失败分类规则。
4. 实现请求样本量和比例规则。
5. 实现 overall 聚合。

退出条件：

- gate 单元测试覆盖 `PASS/WARN/BLOCK/NO_DATA`。
- 样本不足不会被误判为通过或阻断。

### 阶段三：Markdown 与 CLI

1. report 调用 gate。
2. 写出 `gate-report.json`。
3. 写出 `gate-report.md`。
4. `quality.cli` 新增 `report` 命令。
5. 补 CLI 测试。

退出条件：

- 本地可以用 CLI 从已有 merged 目录回放生成报告。
- Markdown 能解释每条规则命中原因。

### 阶段四：run_master 与 Jenkins

1. `run_master.py` merge 后调用 report。
2. 解析质量报告环境变量，异常 fail-open。
3. Jenkins Real Smoke 阶段设置质量环境变量。
4. Jenkins 邮件读取 summary/gate 并展示摘要。
5. 补 run_master 测试和 Jenkins 相关轻量验证。

退出条件：

- Real Smoke 构建后 artifact 中出现三份 report 文件。
- 邮件能展示影子门禁摘要。
- 原 pytest/JUnit 退出码不被 report/gate 改变。

## 27. 验收标准

迭代四完成必须同时满足：

- `reports/quality/summary.json`、`gate-report.json`、`gate-report.md` 稳定生成。
- report 只消费 `complete` manifest 且 output hash 匹配的 merged 快照。
- `case_total` 使用唯一 invocation 数，不使用 phase 行数。
- `QualitySummary` 可以被现有模型反序列化。
- `GateDecision` 可以被现有模型反序列化。
- `gate-report.md` 能解释每条 `PASS/WARN/BLOCK/NO_DATA` 的原因。
- 样本不足时请求规则输出 `NO_DATA`，不会直接触发强结论。
- manifest failed、缺失或 hash mismatch 时 overall 不会是 `PASS`。
- run_master 自动生成报告但 fail-open。
- Jenkins artifact 可下载质量报告。
- Jenkins 邮件在质量报告缺失或损坏时仍能发送。
- 关闭 `QUALITY_ENABLE` 后原行为不变。

## 28. 回退方案

### 28.1 功能回退

- 设置 `QUALITY_ENABLE=0`：关闭整个 P0 质量链路。
- 设置 `QUALITY_SHADOW_GATE=0`：保留 summary，关闭影子门禁结论或将 gate 标为 disabled。
- run_master 中 report 失败自动 fail-open，不需要人工回退才能恢复测试执行。

### 28.2 代码回退

如迭代四接入后出现问题，优先回退接入点：

1. Jenkins 去掉质量环境变量和邮件读取。
2. run_master 去掉 `generate_quality_report()` 调用。
3. 保留 `quality/report.py`、`quality/gate.py` 和 CLI，方便本地排查。

不要删除 merged 产物和迭代三能力，因为 P0 事实底座仍有排查价值。

## 29. 风险与控制

| 风险 | 后果 | 控制 |
| --- | --- | --- |
| manifest 校验不严 | 报告消费污染数据 | report 入口统一校验 manifest 与 hash |
| invocation 折叠错误 | 通过率失真 | 单元测试覆盖多 phase 状态组合 |
| 请求样本不足被误判 | 影子门禁噪声高 | 每条比例规则固定 `sample_size` |
| report 异常覆盖测试结果 | CI 行为回归 | run_master 全部 fail-open |
| Jenkins 邮件解析失败 | 邮件通知中断 | Groovy 读取函数捕获异常并返回默认摘要 |
| Markdown 泄露敏感数据 | 安全风险 | 只展示脱敏结构字段和截断摘要 |

## 30. 停下来确认的情况

实际开发中如遇以下情况，必须停下来确认：

- 必须修改 `quality.v1` 模型字段才能实现报告。
- 需要让影子门禁改变 Jenkins 构建状态。
- 需要把普通 AssertionError 默认判成 `PRODUCT_DEFECT`。
- 需要定义“大面积 CONFIGURATION 失败”的比例阈值。
- 需要按历史数据判断 Flaky、趋势或基线。
- 需要把请求 body、response body 或 header 写入报告。
- 需要把 Framework Unit Tests 也纳入当前质量插件采集。
- 需要从重复 `case_id` 猜测重跑或 retry rescue rate。

## 31. 最终完成定义

迭代四最终完成不是“多生成三个文件”，而是：

```text
报告确认自己消费的是可信 merged 快照
并且
统计口径与 pytest/JUnit/merged 事实一致
并且
影子门禁的每条结论都能解释证据、阈值和样本量
并且
数据不足不会被伪装成通过
并且
质量工具自身失败不改变原测试结果
```

这条边界守住后，P0 才真正完成从事实采集到观察性结论的闭环。P1 的 Flaky 治理、历史基线、成本/耗时/稳定性指标和强制门禁，才能基于这批可回放产物继续推进。
