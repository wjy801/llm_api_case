## 2. 第一性原理与TOC判断

### 2.1 并发分类的问题本质

并发测试的本质不是提高执行速度，而是验证所有权跨线程后仍然明确：

```text
主线程绑定Runtime Hooks和用例Context
→ submit_with_context为每次提交分别copy_context
→ 工作线程创建自己的Request和Session
→ 工作线程执行单次control请求
→ 工作线程finally关闭自己的Request
→ 主线程只汇总不可变结果
```

错误实现会产生两条因果链：

```text
ContextVar没有传播
→ 请求事实无法归属当前用例
→ Quality开启后出现孤立请求或完整性降级

Session跨线程共享
→ 请求级Header可能互相污染
→ 审计名称和响应无法建立一一对应
```

因此并发分类只验证Context传播、Session独立和Header隔离，不重复Retry、Polling、Capture与Assertions异常分支。

### 2.2 黄金路径的问题本质

黄金路径回答的是：

```text
已经分别通过的公共能力
→ 在同一成功链中是否保持一致事实
→ 是否可以被pytest、Allure和后续Quality链路共同消费
```

黄金路径不是异常分支全集。若把failure、unknown、timeout、Capture超限和Schema失败继续塞入同一用例，会导致失败归因模糊并重复阶段3分类。

因此黄金路径只走：

```text
创建成功
→ 503被Retry挽救
→ queued
→ running
→ succeeded
→ 输出Capture成功
→ Context提取成功
→ 并发审计成功
→ DELETE cleanup成功
```

### 2.3 TOC首要约束

阶段4的首要约束是跨线程和跨fixture的资源所有权：

```text
worker Request在线程内创建和关闭
→ ThreadPoolExecutor等待所有worker完成
→ TestContext执行DELETE cleanup
→ 主Request由fixture关闭
→ Service由fixture停止
→ Allure teardown hook复制仍存在的输出文件
→ tmp_path最终回收
```

TOC处理顺序：

1. 识别约束：线程、Session、Context、任务和文件由不同组件持有；
2. 利用约束：worker使用局部`try/finally`，主链使用既有fixture逆序收尾；
3. 服从约束：并发分类先独立通过，再进入黄金路径组合；
4. 提升约束：用ContextVar值、Session身份、关闭账本、服务快照、Runtime记录和文件Hash形成闭环；
5. 防止惯性：黄金路径通过后停止扩张业务用例，把运行产物验证交给阶段5。

### 2.4 决策原则

- 只通过`submit_with_context()`提交业务线程；
- 每次提交都独立调用`submit_with_context()`；
- worker直接创建`OfflineFrameworkRequest`并在自身`finally`关闭；
- worker不得调用`offline_request_factory`把关闭责任转回主线程fixture；
- worker不得共享主Request或彼此的Session；
- 并发同步使用`Barrier`或Future完成条件，不使用固定sleep；
- 并发结果只断言集合、数量和映射，不断言完成顺序；
- 黄金路径必须调用`create_and_poll_media_generation()`；
- 黄金路径使用`POLL_SUCCESS_WITH_RETRY`、`OFFLINE_RETRY_POLICY`和`OFFLINE_POLLING_POLICY`；
- 黄金路径只启用输出Capture，输入Capture已由阶段3证明；
- cleanup必须委托`Task.delete_media_task()`，不得直接修改服务state；
- Runtime证据只读取测试记录器，不读取Quality、Metrics或Runner内部文件；
- 不新增Marker、配置开关、报告、DSL、线程管理器或Session池。

### 3.3 当前公共并发语义

`common.submit_with_context()`当前执行：

```text
每次调用copy_context()
→ executor.submit(context.run, function, ...)
```

因此每个Future必须由一次独立`submit_with_context()`产生。不得保存一个Context后并发调用同一个`Context.run()`。

`OfflineFrameworkRequest`满足：

- 构造时拒绝非loopback base URL；
- 每个实例创建独立`requests.Session`；
- `session.trust_env=False`；
- `get_audit()`通过请求级Header传入`X-Audit-Name`；
- 请求级Header不会写入Session默认Header；
- `close()`可由当前worker在finally调用。

### 3.4 当前Runtime观察语义

`offline_runtime_recorder`通过ContextVar绑定。`submit_with_context()`传播该绑定后，worker请求应继续记录metadata、RequestGroup、RequestContext和Response。

Quality关闭时Noop delegate可能返回`owned=False`，测试记录器可能观察到外层和内层多个中性metadata。因此阶段4只断言：

- 存在`ASYNC_TASK / media_generation / workload / offline-media-model`；
- 存在两个`HTTP / offline_audit_query / control`；
- Polling为`pending → pending → success`且终态SUCCESS；
- 不断言Quality关闭时operation记录数量恰好为1。

“只有一个顶层逻辑调用”的产物语义由阶段5在Quality和Semantic开启后验收。

### 3.5 当前服务并发语义

`OfflineService`使用`ThreadingHTTPServer`，并通过锁保护计数器、tasks、audit records、deleted IDs、request hosts和handler errors。阶段4只读取公开`state.snapshot()`和Event。

## 4. 总方案与当前事实的细化处理

### 4.1 worker Request所有权

worker固定实现：

```text
OfflineFrameworkRequest(service.base_url, CapturePolicy.disabled())
→ try执行Task.query_audit()
→ finally调用request.close()
→ 持锁写入关闭session_id集合
```

不使用`offline_request_factory`创建worker Request，避免worker已经关闭、fixture又代关的双重所有权。

### 4.2 并发重叠方式

两个worker使用`threading.Barrier(2)`在发请求前汇合。Barrier等待设置短超时，任何异常通过Future暴露，Request仍在finally关闭。不得用sleep制造线程交错。

### 4.3 trace ID提取来源

阶段3已验证Regex来源。黄金路径最终响应包含稳定`trace_id`，因此使用：

```text
task_id：$.task_id
request_id：X-Request-ID Header
session_id：offline_session Cookie
trace_id：$.trace_id
```

不额外调用`GET /v1/context`，保证黄金路径请求数量与冻结合同一致。

### 4.4 创建响应与最终响应关系

`create_and_poll_media_generation()`只返回最终响应。黄金路径不得拆开调用；创建响应从`offline_runtime_recorder.responses`中按创建路径和HTTP 202筛选，必须恰好一条。

### 4.5 Capture范围

黄金路径使用`CapturePolicy.output_only()`。input目录必须为空，output目录只能存在完整`output.png`，Hash必须等于`OUTPUT_PNG_SHA256`。

### 4.6 连续20轮定义

不增加pytest-repeat插件和参数化ID。连续20轮通过PowerShell循环执行同一nodeid，每轮使用新的pytest进程、服务实例和系统临时Allure目录。

## 7. 并发测试辅助结构设计

### 7.1 测试内结果对象

`test_concurrency_context.py`可定义不导出的frozen dataclass：

```text
OfflineAuditWorkerResult
├─ audit_name
├─ response
├─ session_id
├─ inherited_owner
├─ trust_env
└─ audit_header_in_session
```

它只保存测试证据，不进入四件套和模块`__init__.py`。

### 7.2 worker函数

模块私有worker接收base URL、audit name、可选Barrier、可选ContextVar及受锁保护的关闭账本。

固定流程：

```text
创建CapturePolicy.disabled()的Offline Request
→ 保存session_id
→ 可选Barrier.wait(timeout=1)
→ 读取ContextVar
→ Task.query_audit()
→ 记录Session是否残留X-Audit-Name
→ 返回结果
→ finally关闭Request并记录session_id
```

worker不得吞掉Barrier、请求或断言异常，不得使用原始`requests.Session()`。

### 7.3 Future收口

每条并发测试使用2-worker线程池、两次独立`submit_with_context()`和`future.result(timeout=2)`。离开线程池context manager后，主线程再断言集合与关闭账本。

禁止原始`executor.submit()`、固定sleep、按完成顺序断言，以及worker返回后由主线程代关Request。

## 10. 黄金路径固定执行流程

场景：`POLL_SUCCESS_WITH_RETRY`。主Request使用`CapturePolicy.output_only()`。

固定流程：

```text
1. 启动独立POLL_SUCCESS_WITH_RETRY服务
2. 创建输出Capture主Request
3. Task构建全新媒体payload并deepcopy原值
4. 调用create_and_poll_media_generation()
5. 外层建立ASYNC_TASK media_generation操作
6. POST /v1/media/generations返回202
7. 第一次Polling transport返回503
8. OFFLINE_RETRY_POLICY在同一请求组挽救并得到queued
9. 后续Polling得到running、succeeded
10. 按$.result.url同步下载output.png
11. 从Runtime recorder定位唯一创建响应
12. 比较创建、最终和Context中的task ID
13. TestContext从最终响应提取4个稳定值
14. 注册DELETE cleanup回调
15. submit_with_context并发执行audit-a、audit-b
16. worker分别关闭Request，线程池shutdown
17. 执行状态码、字段、Schema、文件和领域关系断言
18. 手动执行TestContext.cleanup()
19. 验证服务tasks为空、DELETE一次、无handler错误
20. fixture按逆序关闭主Request和服务，Allure挂载输出文件
```

不得改变为手工“create + poll”两步调用，因为黄金路径必须证明BaseTask复合生命周期。

## 11. 黄金路径详细断言

### 11.1 创建与最终响应

- Runtime recorder中`/v1/media/generations`响应恰好一条；
- 创建响应HTTP 202；
- 创建响应满足`OFFLINE_CREATE_TASK_SCHEMA`；
- `Task.extract_task_id(create_response)`等于`offline-task-001`；
- 最终响应HTTP 200；
- 最终status为`succeeded`；
- 最终task ID与创建task ID一致；
- 最终响应满足`OFFLINE_POLLING_SUCCESS_SCHEMA`；
- 调用方原payload与deepcopy完全相等。

### 11.2 Retry与Polling

- `media_create_calls == 1`；
- `media_poll_calls == 4`；
- Polling transport HTTP序列为`[503, 200, 200, 200]`；
- HTTP 200业务状态为`queued → running → succeeded`；
- 503不进入业务状态迁移；
- 第一个Polling请求组attempt index为`[1, 2]`；
- Runtime Polling states为`pending → pending → success`；
- Runtime Polling outcome为SUCCESS；
- 不重复断言failure、unknown或timeout。

## 17. 风险与控制

### 17.1 ContextVar只在主线程有效

风险：误用`executor.submit()`使worker获得默认Runtime Hooks。

控制：代码审查禁止原始submit；worker返回ContextVar值；Runtime recorder必须观察两个audit请求。

### 17.2 复用同一个Context运行两个worker

风险：手工`copy_context()`一次后并发`Context.run()`会产生错误共享。

控制：每个Future单独调用`submit_with_context()`，由公共函数内部各自copy。

### 17.3 Session身份被Python复用

风险：worker顺序执行且前一个对象提前释放，`id(session)`可能复用。

控制：2-worker线程池和Barrier保证两个Session同时存活后再请求。

### 17.4 worker异常导致Request未关闭

风险：Barrier或HTTP异常在Future中抛出，Session遗漏。

控制：Request创建后立即进入try/finally；关闭账本在finally更新；Future异常向主线程传播。

### 17.5 Header隔离被独立Session掩盖

风险：响应正确但未证明请求级Header没有写入Session。

控制：worker在请求后显式记录`X-Audit-Name not in request.session.headers`。

### 17.6 Runtime recorder并发顺序不确定

风险：测试错误冻结两个worker的append顺序。

控制：Future全部完成后再读取，只断言过滤数量和集合；如稳定丢失记录且需要修改recorder，触发停止条件。

### 17.7 黄金路径拆开create和poll

风险：为取得创建响应而失去ASYNC_TASK复合生命周期。

控制：调用复合Task，创建响应从既有Runtime recorder按path筛选。

### 17.8 Quality关闭时operation数量不同

风险：Noop不拥有lease，误断言只有一个metadata。

控制：只断言存在外层ASYNC_TASK及两个audit CONTROL metadata，精确语义留到阶段5。

### 17.9 worker使用Capture默认策略

风险：worker意外依赖仓库Capture目录。

控制：worker Request显式使用`CapturePolicy.disabled()`。

### 17.10 cleanup晚于主Request关闭

风险：fixture结束时DELETE使用已关闭Session。

控制：测试主体内手动cleanup；fixture仍提供兜底顺序。

### 17.11 连续20轮产生假稳定

风险：失败轮次被忽略或使用同一进程遗留状态。

控制：每轮新pytest进程，任何非零退出立即throw，不重跑失败轮次覆盖证据。

### 17.12 黄金路径继续膨胀

风险：加入failure、timeout、输入Capture或Quality文件断言。

控制：只保留冻结成功链；互斥分支由阶段3负责，运行产物由阶段5负责。
