## 1. 需求理解

阶段 1 要解决的不是“pytest 能不能被调用”，而是一次流水线是否只有一份可验证的执行事实。

本阶段必须完成：

1. `test_path`、`-k`、`-m`、`--ignore` 等选择条件只在一次权威收集中决定最终 nodeid；
2. 串行、并行和未来分布式执行都消费同一份不可变计划，不在执行端再次选测；
3. 每个池保留 pytest 原始退出码、计划、时间、JUnit 路径和异常类型；
4. pytest 2/3/4/5 不得压缩成 1 或 0，基础设施/选择异常必须停止后续真实接口池；
5. Jenkins 显式阶段状态和 pytest 原始状态优先于 JUnit、Quality、Metrics、Flaky 和 Pipeline Conclusion；
6. Markdown 与邮件不再各自重新解释 JUnit，改为消费同一次 Python 解析形成的结构化结果；
7. `run_master.py`、`master_service.py`、CLI、serial 分池、JUnit、Allure、Quality 和当前产物路径保持兼容。

本阶段不做：

- 不取消统一预收集，也不为关闭并发建立另一条执行路径；
- 不建设远程 worker、队列、通用分片平台或 `runs/<run_id>` 全产物隔离；
- 不统一 pytest/Allure 完整生命周期，不改多池 Allure 临时目录合并；该项留在阶段 2；
- 不重构 BaseRequest、BaseTask、Polling、Retry、Header 或下载；
- 不实施 Quality 懒加载和生命周期接口；该项留在阶段 3；
- 不合并配置校验、Artifact 校验或素材 CLI；该项留在阶段 4；
- 不处理流式输出/SSE，不处理密钥泄露或 Secret 扫描；
- 不改变四件套强制创建规范和任何领域类型身份；
- 不执行真实接口或付费 Smoke。

## 2. 第一性原理与 TOC 约束

### 2.1 执行可信的最小闭环

一次执行只有满足以下等式才可信：

```text
最终选择集合
= 权威收集集合
= 并行池 ∪ 串行池
= 实际执行 nodeid 集合
= 可解释的 JUnit Case 集合
```

并且：

```text
进程成功
<=> 所有已执行池的 pytest 原始退出码均为 0
```

JUnit、Allure 和 Quality 都是执行后的证据消费者，不能反向改写 pytest 或 Jenkins 已经发生的事实。

### 2.2 当前因果链

```text
预收集只接收 test_path，且强制关闭插件自动加载
-> -k/-m/--ignore 和插件选择条件只在正式执行生效
-> 分池计划、expected_case_count 与实际执行集合不一致
-> 非空池可能在正式执行返回 exit 5
-> merge_exit_codes 把 5 当作可忽略并把 2/3/4 压成 1
-> Runner 继续启动串行真实接口池
-> Jenkins/JUnit/Quality/摘要围绕错误结果继续加工
-> 报告越丰富，错误结论越像真的
```

### 2.3 TOC 决策

当前唯一首要约束是“控制面计划与执行结论不可信”。阶段 1 的决策顺序固定为：

```text
选择参数进入同一次权威收集
-> 形成不可变计划
-> 纯算法分池
-> 池执行保留原始事实
-> 固定退出码聚合与提前止损
-> 报告链只消费事实，不重新判案
```

如果先优化报告展示、Quality 结构或 Allure 合并，只会更精细地展示错误事实，因此不允许调整顺序。

## 4. 当前实现差距快照

| 位置 | 当前行为 | 风险 | 阶段 1 目标 |
| --- | --- | --- | --- |
| `master_service.py` | 直接拥有 pytest 收集，并强制 `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` | 收集和执行插件环境不同 | 保留稳定入口，收集实现兼容委托给 `pytest_execution.py` |
| `collect_test_case_items()` | 只接收 `test_path` | `-k/-m/--ignore` 不进入计划 | 内部权威收集接收明确选择参数并返回原始退出码 |
| `_CaseCollector` | 对重复 nodeid 静默去重 | 计划冲突被隐藏 | 重复 nodeid 成为明确完整性错误 |
| `scheduling.py` | 只重导出 `master_service` 函数 | 没有真实算法所有权 | 只保留纯分池与集合守恒算法 |
| `runner.py` | 收集后把完整额外参数再次交给 pytest | 执行端二次选择 | 选择参数仅收集使用，执行端只接收最终 nodeid 与执行/产物参数 |
| 空权威集合 | Runner 返回 1 | pytest “无最终用例”事实丢失 | 返回 pytest exit 5 |
| `merge_exit_codes()` | 排除 5，并把其他错误压成 1 | `[5,5] -> 0`，2/3/4 丢失 | 固定矩阵保留首个终止码 |
| 多池执行 | exit 2/3/4/5 后仍可能继续串行池 | 基础设施错误后继续真实调用 | 2/3/4/5 和异常立即停止；1 可继续收集证据 |
| 池结果 | 只有 `list[int]` | 计划、时间、异常、JUnit 无法关联 | 引入轻量不可变池级结果 |
| Quality finalization | 位于 `finally`，异常存在覆盖返回值的可能 | 可选观测改变 pytest 事实 | 明确 fail-open，绝不覆盖原始退出码/异常 |
| `pipeline_reporting/builder.py` | JUnit 可用时先按 JUnit 判阶段 | 显式 FAILED + 绿色/部分 JUnit 可显示 PASSED | Jenkins 显式失败/阻断优先 |
| Jenkins 邮件 | Groovy 再次扫描并解析 JUnit | Markdown 与邮件形成两套统计 | 邮件消费 Python 同一次解析生成的结构化/渲染结果 |

## 5. 目标架构

```text
run_master CLI
  -> 参数分相（选择 / 执行 / 产物 / 兼容共享）
  -> pytest_execution 权威收集
       -> CollectionResult(raw exit + nodeids + markers)
  -> 不可变最终计划
  -> scheduling 纯分池
       -> parallel nodeids
       -> serial nodeids
  -> pytest_execution 执行各池
       -> PoolExecutionResult（保留 raw pytest 事实）
  -> runner 固定聚合与提前止损
       -> process exit code
       -> reports/execution-result.json

Jenkins 阶段状态 + execution-result.json + JUnit
  -> pipeline_reporting 只解析一次
  -> PipelineReport
       -> pipeline-summary.md
       -> pipeline-summary.json
       -> 邮件主题/HTML
```

所有权固定为：

- `pytest_execution.py`：pytest 权威收集、池执行、原始退出码事实；
- `scheduling.py`：不导入 pytest 的纯分池算法；
- `runner.py`：计划编排、提前止损、最终进程码、Quality/产物收尾；
- `master_service.py`：稳定兼容入口，不再拥有 pytest 实现；
- `pipeline_reporting`：读取既有事实并生成展示，不决定 pytest/Jenkins 结果；
- Jenkins：整条 Pipeline 最终状态机。

本阶段只收拢 pytest 的“选择与退出事实”所有权；Allure 清理、池间保存/恢复和 HTML/history 生成仍保持当前实现，阶段 2 再统一生命周期。

## 6. 核心内部数据合同

### 6.1 `CollectionResult`

建议在 `run_orchestration/pytest_execution.py` 定义内部冻结 dataclass：

```text
raw_pytest_exit_code: int
cases: tuple[CollectedTestCase, ...]
stdout: str
stderr: str
```

规则：

- exit 0：`cases` 必须非重复，可为空仅在 pytest 实际返回相应语义时处理；
- exit 5：`cases` 必须为空，Runner 返回 5；
- exit 1/2/3/4：不执行任何池，原码直接成为进程结果；
- 重复 nodeid 不再静默去重，转为明确 Runner 完整性错误；
- stdout/stderr 只用于诊断，不通过正则反推用例集合或退出码。

### 6.2 最终执行计划

最终计划使用 tuple 表达不可变性，至少包含：

```text
test_target
selection_args
cases(nodeid + markers)
```

计划生成后：

- Runner 不再追加新的选择条件；
- 并行、串行和未来 worker 只拿 nodeid；
- `expected_case_count` 只能来自计划长度；
- 任何池集合不守恒均在真实执行前失败。

不新增通用 Plan DSL、数据库或远程调度协议。

### 6.3 `PoolExecutionResult`

建议在 `pytest_execution.py` 定义轻量冻结 dataclass：

```text
stage_id: str
planned_nodeids: tuple[str, ...]
status: NOT_RUN | COMPLETED | ERROR
raw_pytest_exit_code: int | None
started_at: datetime | None
completed_at: datetime | None
exception_type: str | None
junit_path: Path | None
```

约束：

- 空池：`NOT_RUN`，不调用 pytest，raw code 为 `None`；
- 已执行池：保留 pytest 原码 0～5，不改写；
- 异常池：记录异常类型，停止后续池；
- `completed_at >= started_at`；
- JUnit 缺失不能把非零原码改成成功；
- Quality/报告消费者不得修改该对象。

### 6.4 机器执行事实

新增一个机器证据，不新增第二份人工报告：

```text
reports/execution-result.json
schema_version: runner-execution.v1
```

建议字段：

```text
test_target
selection_args
planned_case_count
collection_exit_code
pool_results[]
final_exit_code
```

写入规则：

- 真实 Runner 执行结束后原子写入、UTF-8、LF；
- collect-only 不创建该文件，保持阶段 0 无副作用合同；
- 文件写入失败视为 Runner 基础设施异常，不能留下成功结论；
- 如果 pytest 已有 2/3/4/5，报告写入失败不得把更具体的 pytest 原码压成 1；
- Jenkins 已归档 `reports/**`，不新增归档路径；
- 该文件只承载执行事实，不承载请求成功率、Flaky、耗时等观察指标。

## 7. 工作包 1A：冻结参数分相合同

### 7.1 明确支持的选择参数

第一批强支持并测试：

- CLI `target` / `--test-path`：目录、文件或 nodeid；
- `-k <expression>`；
- `-m <expression>`；
- `--ignore <path>` 与 `--ignore=<path>`；
- `--ignore-glob <pattern>` 与等号形式（当前 pytest 支持时）；
- `--deselect` 如确认当前调用方已经使用，则按同一选择参数处理。

### 7.2 参数分相

在 `pytest_execution.py` 增加最小参数分相函数，输出：

```text
selection_args     只用于权威收集
execution_args     只用于执行与产物
shared_args        为兼容插件同时进入两阶段
collect_only       Runner 控制模式，不直接传给池执行
```

已知产物/执行参数如 `--junitxml`、`--alluredir`、`--clean-alluredir`、xdist 参数不能触发收集期清理或写报告。

原则：

- 不编写覆盖 pytest 所有插件的万能解析器；
- 已明确会改变集合的参数只进入收集；
- 当前稳定使用的插件参数保留兼容；
- 新出现且无法安全判断阶段的选择型参数应明确报错并补适配测试，不能静默制造双集合；
- 参数值缺失、重复冲突和非法组合在真实接口执行前失败。

### 7.3 验收

- 选择参数不会出现在正式池执行参数中；
- JUnit/Allure 参数不会在收集期创建或清理制品；
- `--collect-only` 不进入真实池执行；
- 原有 `-q`、`-s`、`-x`、`--maxfail` 和稳定插件参数保持现有行为。

`run_orchestration/scheduling.py` 调整为真实实现源：

## 10. 工作包 1D：池级执行结果与退出码

### 10.1 单池执行

- 计划非空才调用 pytest；
- 返回 `PoolExecutionResult`，不只返回 int；
- 单池 Runner 的最终进程码等于 pytest 原始码；
- 计划非空但 pytest 返回 5 是执行计划异常，原样返回 5；
- 当前 `run_serial_pool()` 的 Allure 保存/恢复兼容逻辑暂时保留，不在本阶段重构。

### 10.2 多池执行与提前止损

| 当前池结果 | 是否运行后续池 | 最终规则 |
| --- | --- | --- |
| 空计划 | 否（当前池不调用 pytest） | `NOT_RUN`，不单独失败 |
| 0 | 是 | 若其他池也为 0，最终 0 |
| 1 | 是 | 可继续收集剩余池证据；无更高终止码时最终 1 |
| 2 | 否 | 立即返回 2 |
| 3 | 否 | 立即返回 3 |
| 4 | 否 | 立即返回 4 |
| 5（计划非空） | 否 | 立即返回 5 |
| Runner 异常 | 否 | 记录异常类型并返回明确非零 |

这里“exit 1 后继续”是有意规则：测试失败不等同于执行基础设施不可用；可以继续串行池收集更多失败证据。2～5 表示中断、内部错误、用法错误或计划漂移，不能继续真实接口池。

### 10.3 固定聚合算法

最低矩阵：

```text
[0] -> 0
[0, 0] -> 0
[1, 0] -> 1
[0, 1] -> 1
[1, 2] -> 2
[2] -> 2
[3] -> 3
[4] -> 4
[5] -> 5
[5, 5] -> 5（纯函数合同；真实编排在首个 5 后停止）
```

算法不使用 `max()`，也不把所有非零统一成 1；按执行顺序保留首个 2/3/4/5 终止事实，否则有 1 返回 1，全部 0 才返回 0。

### 10.4 Quality 收尾

- `expected_case_count` 使用最终计划长度；
- `expected_execution_ids` 只包含实际执行池；
- JUnit 路径来自对应池结果；
- collect-only 不解析 Quality 配置、不生成身份；
- Quality 合并、Metrics、Flaky 或文件写入异常继续 fail-open；
- 可选 Quality 收尾不能覆盖 pytest 原始退出码或 Runner 原始异常；
- 本阶段不改变 Quality Schema 和现有机器产物路径。

## 11. 工作包 1E：统一报告事实优先级

### 11.1 阶段状态判定顺序

修改 `pipeline_reporting/builder.py` 的测试阶段判定：

```text
参数未启用 -> NOT_RUN
Jenkins 显式 FAILED -> FAILED（无条件优先）
Jenkins 显式 BLOCKED/NOT_RUN -> BLOCKED（忽略陈旧 JUnit）
JUnit 可用且存在 failed/error -> FAILED
Jenkins 显式 PASSED + JUnit 可用且全绿 -> PASSED
已选择但 JUnit 缺失/不可解析 -> NO_DATA
```

特别保护：

- 显式 FAILED + 可解析全绿 JUnit，仍为 FAILED；
- 显式 FAILED + 部分 JUnit，仍为 FAILED；
- BLOCKED + 上轮残留 JUnit，仍为 BLOCKED；
- Quality/Metrics/Flaky 完整，不能把失败测试阶段改成 PASSED；
- `PIPELINE_BUILD_RESULT=FAILURE/ABORTED/NOT_BUILT` 始终得到 FAIL conclusion；
- Pipeline Conclusion 只是关注等级，不写回 Jenkins result。

### 11.2 读取 Runner 执行事实

`pipeline_reporting/sources.py` 增加对 `reports/execution-result.json` 的严格读取：

- 校验 schema、final exit、pool raw exit 和 nodeid 计数；
- 缺失或损坏只产生 warning/NO_DATA，不伪造成零或成功；
- Jenkins 显式状态仍是流水线阶段事实；
- execution result 用于解释“为什么失败/为何后续池未执行”，不覆盖 Jenkins；
- 不把 Quality 的 run status 当作 pytest exit。

### 11.3 一次 JUnit 业务解析

Python Reporting 在一次 `load_pipeline_sources()` 中解析 JUnit 并形成现有 `TestSummary`，随后：

- Markdown renderer 使用同一 `PipelineReport`；
- 新增 `reports/pipeline-summary.json` 作为同一对象的机器表示；
- 邮件主题与 HTML 由 Python 从同一 `PipelineReport` 渲染；
- Jenkins 只 `readFile` 已生成的主题/HTML，不再用 Groovy 正则扫描 JUnit；
- Jenkins `junit` Publisher 仍可独立解析并发布测试结果，这属于 Jenkins 平台职责；
- 不恢复已删除的旧质量人工报告或历史报告。

建议 Jenkins 生成文件：

```text
reports/pipeline-summary.md          唯一人工质量报告
reports/pipeline-summary.json        结构化展示输入
reports/pipeline-email-subject.txt   邮件主题
reports/pipeline-email.html          邮件正文
```

后三项是机器/投递制品，不是新增人工报告入口。

### 11.4 兜底策略

如果 Python 报告生成失败：

- Jenkins 兜底 Markdown 只写 Jenkins 构建结果和日志入口；
- 邮件兜底只写 Jenkins 状态和构建链接；
- 不重新解析 JUnit 猜测数量；
- 不把缺失报告解释为 0 用例或成功；
- 兜底失败仍不得修改原始 Jenkins 结果。

## 18. 风险与控制

### 18.1 pytest 参数分类不完整

风险：未知插件参数可能影响选择。  
控制：只承诺已使用选择参数；兼容参数用真实插件测试；无法安全分类的新增选择参数明确失败，不静默执行双集合。

### 18.2 多次 `pytest.main()` 的插件全局状态

风险：权威收集和多池执行仍位于同进程。  
控制：本阶段只统一事实，不扩大生命周期重构；增加同进程重复调用测试。若确认必须改子进程，停止并重新评估，不顺带建设分布式平台。

### 18.3 Allure 收集期副作用

风险：`pytest.ini --clean-alluredir` 在收集期清理结果。  
控制：收集阶段覆盖 addopts/剥离产物参数，并验证 Allure、JUnit、history 前后 Hash 不变。完整 Allure 所有权留阶段 2。

### 18.4 退出码修复改变 Jenkins 结果

风险：以前假绿的构建会变失败。  
控制：这是预期正确性变化；用固定矩阵和 Jenkins 测试证明，不增加兼容开关保留错误行为。

### 18.5 结构化结果形成第二套状态机

风险：Runner JSON 开始推导 Jenkins SUCCESS/FAILURE。  
控制：只保存 pytest 池事实和 Runner final exit；不记录 Jenkins 最终结论，不复制 Pipeline stage 状态机。

### 18.6 报告产物膨胀

风险：新增多个可读报告。  
控制：`pipeline-summary.md` 仍是唯一人工报告；JSON、邮件 HTML/subject 只作机器传递和投递，不增加人工入口。

### 18.7 Quality 收尾覆盖原始事实

风险：`finally` 中异常覆盖 pytest return。  
控制：先保存原始结果，再 fail-open 执行可选收尾；使用异常注入测试锁定。

## 19. 回滚策略

- 参数分相与收集所有权可作为独立提交回滚；回滚不得删除已转正前的 strict-xfail 证据；
- scheduling 纯算法可独立回滚到兼容委托，但阶段 1 门禁会重新失败；
- 池级结果和 execution-result 可独立回滚，不影响 JUnit/Allure 旧路径；
- Reporting/Jenkins 改动可独立回滚，但不能把显式失败优先级回滚为错误行为；
- 任何回滚都不得使用 `git reset --hard` 覆盖用户工作区；
- 若某工作包失败，保留已验证的前序工作包，重新定位约束，不把阶段 2～4 方案提前塞入修复。
