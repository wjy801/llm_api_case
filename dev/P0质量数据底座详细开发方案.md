# P0 质量数据底座详细开发方案

> 历史文档：本文记录旧 P0 报告与影子门禁方案，已被当前 Pipeline Summary 唯一人工报告架构替代，不作为现行实施指南。

## 1. 需求复述

本方案承接 `P0与P1质量工程后续开发方向.md`，只展开 P0 阶段。

P0 要解决的问题不是“再做一份更好看的测试报告”，而是让每一次 CI 或本地批量执行都能产出一条可信质量事实链：

```text
测试执行
-> 稳定身份
-> 结构化采集
-> 分片落盘
-> 唯一归并
-> 完整性校验
-> 失败分类
-> 聚合报告
-> 影子门禁
```

P0 完成后，应能稳定回答：

- 本次实际执行了哪些用例、哪些接口、哪些请求尝试。
- 原始结果、最终结果、请求重试过程分别是什么。
- 失败属于产品、测试、框架、环境、配置、瞬态还是未知。
- 数据是否完整，缺了什么，缺失是否影响判断。
- 如果当前门禁规则生效，会得到什么结论，但 P0 不改变流水线退出码。

## 2. 第一性原理判断

质量工程的底层目标是降低误判成本：不能把真实缺陷放过，也不能把环境、框架、测试数据问题误判为产品缺陷。

要降低误判成本，必须先有可追溯、可复算、可对账的数据。没有稳定身份和原始事实，后续 Flaky、基线、成本、耗时、强门禁都会失真。

因此 P0 的第一性原则是：

- 原始事实优先于派生结论。
- 稳定身份优先于统计图表。
- 完整性校验优先于门禁强制。
- 确定性分类优先于智能归因。
- 观察性门禁优先于改变 CI 结果。

## 3. 目标障碍与因果链

### 3.1 并行执行导致结果无法唯一归并

当前 `run_master.py` 会把用例拆成并行池、串行池，并多次调用 `pytest.main()`；同时 pytest-xdist 还可能产生多个 worker。

```text
多阶段 pytest.main()
-> 每个阶段都有独立 pytest 生命周期
-> xdist worker 并发写结果
-> 如果只在 pytest_sessionfinish 里生成最终报告
-> 会出现覆盖、重复、漏归并或只看到局部结果
-> 质量结论不可信
```

真正要解决的问题是：为一次父级运行建立统一 `run_id`，为每个 pytest 阶段建立 `execution_id`，为每个 worker 建立分片文件，最终由父级运行做唯一归并。

### 3.2 请求指标缺少用例归属

当前请求上下文能记录请求级信息，但没有稳定携带当前 pytest 用例身份。

```text
请求事件没有 case_id / invocation_id
-> 请求只能按时间或日志文本猜测归属
-> 一个用例多请求、并发请求、重试请求无法可靠关联
-> 接口耗时、失败和用例结果无法对账
-> 后续 P1 的稳定性、成本和 Flaky 判断失真
```

真正要解决的问题是：在 pytest 用例运行期间通过 `contextvars` 设置当前用例上下文，请求上下文创建时自动读取并写入请求指标。

### 3.3 重试会掩盖首次失败

当前已有请求级重试能力，但 P0 阶段不应把“重试后成功”等同于“首次成功”。

```text
只看最终成功
-> 首次失败证据消失
-> 不稳定接口被统计成稳定
-> 门禁误放行
-> 团队失去治理入口
```

真正要解决的问题是：每次 request attempt 单独记录，用例结果保留 `raw_status`、`final_status` 和 attempts 摘要。P0 暂不做用例级自动重跑，所以 `raw_status` 与 `final_status` 通常相同，但字段必须先预留。

### 3.4 采集错误可能覆盖真实测试结果

```text
质量采集代码抛异常
-> pytest 或请求链路被中断
-> 原始测试失败被采集失败替代
-> 质量模块反而制造噪声
```

真正要解决的问题是：所有采集路径 fail-open。采集失败只写入 `IntegrityIssue`，不得改变真实测试行为和退出码。

### 3.5 没有历史基线时强行门禁会失信

```text
缺少历史样本
-> 阈值只能拍脑袋
-> 正常波动频繁告警
-> 人工豁免增加
-> 门禁被绕过
```

真正要解决的问题是：P0 只生成影子门禁结论和回放数据，不改变 CI 状态。P1 再进入历史基线、Flaky 状态机和强制门禁。

## 4. TOC 约束决策

当前系统的约束不是展示层，而是质量事实链可信度。TOC 决策如下：

| 决策点 | 选择 | 原因 |
| --- | --- | --- |
| 首要瓶颈 | 数据可信链路 | 没有稳定身份、完整性和归并，任何报告或门禁都是不可信结论 |
| P0 投入重点 | 契约、采集、归并、分类、影子门禁 | 这些是 P1 的 Flaky、基线、成本指标和强门禁的前置条件 |
| 暂缓内容 | 历史趋势、强制门禁、AI 归因、质量大屏 | 会放大当前数据不可信的问题 |
| 风险控制 | fail-open 与影子模式 | 质量模块上线初期不能影响测试真实结果 |
| 验收重点 | 可对账、可复算、可追溯 | 比页面丰富度更重要 |

## 5. P0 范围与非目标

### 5.1 P0 范围

- 定义版本化质量数据契约。
- 生成稳定 `run_id`、`execution_id`、`case_id`、`invocation_id`、`request_event_id`、`interface_id`。
- 接入 pytest 生命周期，采集用例结果、阶段、耗时、异常摘要和证据引用。
- 接入请求中间件，采集 HTTP/SSE/异步轮询/重试请求的结构化指标。
- 支持串行、并行、并串混合、xdist worker 分片写入与最终归并。
- 生成运行级、用例级、接口级聚合结果。
- 做确定性失败分类、失败指纹和完整性校验。
- 生成 JSON、JSONL、Markdown 报告和影子门禁结论。
- 接入 Jenkins artifact 与邮件摘要入口，但不改变 CI 退出码。

### 5.2 P0 非目标

- 不做跨构建历史存储和趋势基线。
- 不做 Flaky 状态机、隔离、恢复和责任闭环。
- 不做强制门禁。
- 不做 MR 精准选测。
- 不做覆盖率矩阵或契约覆盖矩阵。
- 不做自动生成测试数据。
- 不做 AI 自动归因或智能审查。
- 不从 Allure HTML 反向解析业务指标。

## 6. 总体架构

建议新增独立 `quality` 包，避免把治理逻辑塞进业务用例、Jenkinsfile 或请求基础类。

```text
quality/
  __init__.py
  models.py
  identifiers.py
  runtime_context.py
  storage.py
  collector.py
  pytest_plugin.py
  request_metrics.py
  classifier.py
  aggregator.py
  gate.py
  report.py
  cli.py
```

模块职责：

| 模块 | 职责 |
| --- | --- |
| `models.py` | 版本化数据模型、枚举、字段默认值和兼容策略 |
| `identifiers.py` | 生成稳定 ID、路径模板化、参数摘要、失败指纹 |
| `runtime_context.py` | 基于 `contextvars` 保存当前用例上下文和运行上下文 |
| `storage.py` | 原子写入 JSON/JSONL、worker 分片、崩溃恢复、脱敏落盘 |
| `collector.py` | 统一采集入口，封装 fail-open 和完整性问题记录 |
| `pytest_plugin.py` | pytest 生命周期适配，采集用例结果和阶段信息 |
| `request_metrics.py` | 请求中间件适配，记录请求 attempt、耗时、状态码、用量 |
| `classifier.py` | 确定性失败分类、归因规则、指纹生成 |
| `aggregator.py` | 分片归并、去重、对账、完整性校验、指标聚合 |
| `gate.py` | 影子门禁规则评估，输出 PASS/WARN/BLOCK/NO_DATA |
| `report.py` | 生成 `summary.json`、`gate-report.json`、`gate-report.md` |
| `cli.py` | 提供本地归并、报告生成、回放校验命令 |

## 8. ID 规则

| ID | 规则 | 备注 |
| --- | --- | --- |
| `run_id` | Jenkins job、build number、时间戳和 UUID 组合；本地运行使用时间戳和 UUID | 一次父级运行唯一 |
| `execution_id` | `parallel-pool-1`、`serial-pool-1`、`manual-pytest-1` 等 | 每次 `pytest.main()` 唯一 |
| `worker_id` | xdist worker id；无 xdist 时为 `master` | 用于分片写入 |
| `case_id` | 规范化 pytest nodeid，去除动态参数值，保留测试函数稳定路径 | 跨构建稳定 |
| `invocation_id` | `run_id + case_id + param_hash` | 本次运行内唯一 |
| `request_event_id` | UUID | 每一次请求 attempt 唯一 |
| `server_request_id` | 响应头、响应体或服务端返回的 request id | 可空 |
| `interface_id` | `METHOD + templated_path + protocol` | 不使用完整 query 或高基数字段 |

参数摘要必须脱敏后哈希。禁止把 API Key、Authorization、Cookie、完整请求体、用户隐私数据写入 ID。

## 9. 落盘目录与分片命名

建议统一输出到：

```text
reports/quality/
  run.json
  shards/
    cases-{execution_id}-{worker_id}.jsonl
    requests-{execution_id}-{worker_id}.jsonl
    failures-{execution_id}-{worker_id}.jsonl
    integrity-{execution_id}-{worker_id}.jsonl
  merged/
    case-results.jsonl
    request-metrics.jsonl
    failures.jsonl
    integrity-issues.jsonl
  summary.json
  gate-report.json
  gate-report.md
```

写入要求：

- JSONL 采用 append-only，单行一个事件。
- 单 worker 只写自己的分片，避免并发争抢。
- JSON 文件使用临时文件加原子替换。
- 归并时按 `request_event_id`、`invocation_id + phase`、`failure_id` 去重。
- 崩溃或中断时保留分片，归并器标记 `partial` 和完整性问题。

## 10. pytest 接入方案

### 10.1 插件入口

在 `quality/pytest_plugin.py` 中实现 pytest 插件，并通过 `conftest.py` 或 `pytest.ini` 注册。

建议优先使用显式配置开关：

```ini
[pytest]
addopts =
    --quality-enable
```

也可以先在 `module/conftest.py` 中按环境变量启用，降低上线风险：

```text
QUALITY_ENABLE=1
QUALITY_RUN_ID=...
QUALITY_EXECUTION_ID=...
QUALITY_OUTPUT_DIR=reports/quality
```

### 10.2 Hook 设计

| Hook | 用途 |
| --- | --- |
| `pytest_configure` | 初始化运行配置、worker id、分片 writer |
| `pytest_collection_modifyitems` | 记录 collection 数量和 nodeid 规范化预检查 |
| `pytest_runtest_protocol` | 设置并清理当前 `case_id`、`invocation_id` context |
| `pytest_runtest_logreport` | 采集 setup/call/teardown 状态、耗时、异常摘要 |
| `pytest_exception_interact` | 补充异常类型、断言位置和证据引用 |
| `pytest_sessionfinish` | flush 分片，不生成父级最终报告 |

关键点：pytest 插件只负责采集和分片写入，不负责最终归并。最终归并必须由 `run_master.py` 在所有 pytest 阶段结束后触发。

### 10.3 用例上下文

`runtime_context.py` 提供：

```text
set_current_case(case_id, invocation_id)
get_current_case()
clear_current_case()
```

pytest 用例开始时设置；setup/call/teardown 结束后清理。请求上下文构造时读取当前值，并写入 `RequestMetric`。

## 11. 请求指标接入方案

### 11.1 接入点

优先接入现有：

- `common/request_context.py`
- `common/request_middleware.py`
- `common/base_request.py`
- `common/retry.py`
- `common/retry_executor.py`
- `util/api_call_logger.py`

请求链路不应要求业务用例手写埋点。采集逻辑应作为中间件或统一请求封装的旁路能力。

### 11.2 attempt 记录

每一次请求尝试都写一条 `RequestMetric`：

- 首次请求 `attempt_index = 1`。
- 重试请求按顺序递增。
- 超时、异常、限流、5xx 都保留单独事件。
- 重试后成功不能覆盖首次失败。

### 11.3 异常处理

请求指标采集必须内部捕获异常：

```text
try:
  write_request_metric()
except Exception as exc:
  write_integrity_issue()
```

采集失败不得中断真实请求，不得吞掉原业务异常。

## 12. run_master 归并方案

`run_master.py` 是父级运行生命周期的天然入口，应负责：

1. 生成或读取 `run_id`。
2. 为并行池、串行池每次 pytest 调用分配 `execution_id`。
3. 把 `QUALITY_*` 环境变量传给 pytest 进程或当前进程。
4. 所有 pytest 阶段结束后调用 `quality.cli merge`。
5. 调用 `quality.cli report` 生成摘要和影子门禁。
6. 保持原有测试退出码，不因 P0 影子门禁改变构建结果。

并行、串行、xdist 的责任边界：

| 层级 | 责任 |
| --- | --- |
| `run_master.py` | 父级运行、阶段编排、最终归并 |
| pytest 插件 | 用例事实采集、worker 分片写入 |
| 请求中间件 | 请求事实采集 |
| aggregator | 去重、对账、完整性校验、聚合 |
| gate | 影子规则判断 |

## 13. 聚合统计口径

P0 必须避免混合不同含义的指标：

| 指标 | 口径 |
| --- | --- |
| 测试原始通过率 | `raw_status=passed` 的用例数 / 总用例数 |
| 测试最终通过率 | `final_status=passed` 的用例数 / 总用例数 |
| 请求成功率 | 业务成功请求数 / 请求总数 |
| HTTP 成功率 | HTTP 2xx 请求数 / 请求总数 |
| 重试率 | `attempt_index > 1` 的请求数 / 请求总数 |
| 重试挽救率 | 首次失败但最终请求链路成功的请求组 / 首次失败请求组 |
| 超时率 | timeout 请求数 / 请求总数 |
| 接口 P95 | 单接口样本量达到阈值后才输出 |
| 数据完整率 | 成功采集的关键事件数 / 预期关键事件数 |

P0 不输出误导性 P99。样本不足时返回 `NO_DATA` 或在摘要中明确 `sample_too_small`。

## 14. 失败分类与指纹

### 14.1 分类优先级

第一版采用确定性规则，按优先级匹配：

| 优先级 | 分类 | 典型证据 |
| --- | --- | --- |
| 1 | `CONFIGURATION` | 缺少必填配置、密钥、权限、环境变量、路由配置 |
| 2 | `FRAMEWORK_DEFECT` | pytest 插件、公共请求封装、采集器、公共 fixture 异常 |
| 3 | `ENVIRONMENT` | DNS、网络、依赖服务不可用、资源不足、环境未就绪 |
| 4 | `TEST_DEFECT` | 测试数据错误、断言预期过期、清理逻辑错误 |
| 5 | `TRANSIENT` | 限流、偶发超时、明确可恢复的临时错误 |
| 6 | `PRODUCT_DEFECT` | 稳定业务错误、契约不符、错误响应、确定性断言失败 |
| 7 | `UNKNOWN` | 证据不足或规则无法判断 |

优先级可以通过配置微调，但必须记录 `rule_version`。

### 14.2 指纹规范化

失败指纹来源：

```text
phase
+ error_type
+ normalized_message
+ interface_id
+ assert_location
```

规范化时必须移除：

- UUID、时间戳、随机数、内存地址。
- URL query 参数。
- token、key、authorization、cookie。
- 文件临时路径中的随机段。
- 完整请求体和响应体。

### 14.3 人工修正预留

P0 可以预留 `manual_override` 字段，但不实现治理流。人工修正结果只作为报告展示和 P1 输入，不回写原始事实。

## 15. 完整性校验

P0 至少校验：

- `run.json` 是否存在且 `run_id` 一致。
- 分片文件是否可读、JSONL 是否逐行合法。
- case 汇总数量是否能与 JUnit 原始结果对账。
- 每个失败用例是否有 `FailureRecord`，无法分类时是否归入 `UNKNOWN`。
- 每条 `RequestMetric` 是否能关联 `run_id`，能关联用例时是否有 `case_id`。
- 聚合结果是否存在高基数字段泄露风险。
- 报告产物是否生成成功。

完整性状态：

| 状态 | 含义 |
| --- | --- |
| `complete` | 关键数据完整，可用于 P0 判断 |
| `degraded` | 有缺失但仍可阅读，报告必须显示缺失项 |
| `failed` | 关键数据缺失，门禁结论应为 `NO_DATA` |

## 16. 影子门禁

P0 门禁只输出报告，不改变 CI 退出码。

建议第一版规则：

| 规则 | P0 结论 |
| --- | --- |
| 聚合产物缺失或无法解析 | `NO_DATA` |
| JUnit 数量与结构化 case 数量不一致 | `WARN` |
| 存在 `FRAMEWORK_DEFECT` | `WARN` |
| 存在 `UNKNOWN` 失败 | `WARN` |
| 存在确定性 `PRODUCT_DEFECT` | `BLOCK` |
| 存在 `CONFIGURATION` 导致大面积失败 | `BLOCK` |
| 请求 5xx 或超时超过配置阈值 | `WARN` |
| 样本不足 | `NO_DATA` |

输出字段必须包含规则名、规则版本、样本量、实际值、阈值、证据和结论。`sample_size` 用来说明本次判断基于多少样本；低于规则要求的最小样本量时，即使比例看起来很高，也只能输出 `NO_DATA` 或观察性 `WARN`。

## 17. Jenkins 接入

### 17.1 Pipeline 调整

Jenkinsfile 第一版只需要做三类事情：

- 设置 `QUALITY_ENABLE=1`、`QUALITY_OUTPUT_DIR=reports/quality`。
- 归档 `reports/quality/**`。
- 邮件中增加 `gate-report.md` 或摘要链接。

不建议在 P0 修改 Jenkins 最终状态。原 pytest/JUnit 退出码仍是构建结果来源。

### 17.2 邮件摘要

邮件只放高信号内容：

- 本次影子门禁结论。
- 数据完整性状态。
- 用例总数、失败数、错误数、跳过数。
- `PRODUCT_DEFECT`、`FRAMEWORK_DEFECT`、`ENVIRONMENT`、`UNKNOWN` 数量。
- 最慢接口、错误最多接口、重试最多接口。
- 质量报告 artifact 链接。

## 18. 配置项

建议新增 `quality.yaml` 或使用环境变量覆盖：

```yaml
quality:
  enabled: true
  schema_version: quality.v1
  output_dir: reports/quality
  shadow_gate: true
  min_samples:
    p95: 20
  thresholds:
    request_timeout_warn_rate: 0.05
    http_5xx_warn_rate: 0.02
  redaction:
    header_denylist:
      - authorization
      - cookie
      - x-api-key
    body_capture: false
```

配置优先级：

```text
命令行参数
-> 环境变量
-> quality.yaml
-> 默认值
```

## 19. 脱敏与安全

P0 默认不采集：

- API Key、Authorization、Cookie。
- 完整请求体、完整响应体。
- 用户隐私数据。
- 原始账单明细。
- 高基数 request id 作为聚合维度。

可以采集：

- 脱敏后的 path template。
- HTTP method、status code、duration。
- 服务端 request id 作为证据索引。
- usage 摘要。
- 成本估算字段，统一按人民币口径记录；没有真实账单证据时必须标记 `estimated`。

## 20. 四个迭代计划

### 20.1 迭代一：契约与身份

目标：冻结 P0 数据契约，建立稳定身份和运行上下文。

建议改动：

| 文件 | 动作 |
| --- | --- |
| `quality/models.py` | 新增数据模型、枚举、schema version |
| `quality/identifiers.py` | 新增 ID、参数摘要、路径模板、失败指纹工具 |
| `quality/runtime_context.py` | 新增 `contextvars` 用例上下文 |
| `quality/storage.py` | 新增 JSON/JSONL writer 基础能力 |
| `tests/quality/` | 新增模型序列化、ID 稳定性、脱敏测试 |

验收：

- 相同 nodeid 和参数摘要在不同运行中生成稳定 `case_id`。
- 不同参数 invocation 可区分。
- 脱敏测试覆盖 key、token、cookie、query、body。
- JSON schema 示例可以序列化和反序列化。

回退：

- 只新增独立 `quality` 包，不影响现有执行链路。

### 20.2 迭代二：双层采集与分片写入

目标：接入 pytest 与请求中间件，生成完整分片。

建议改动：

| 文件 | 动作 |
| --- | --- |
| `quality/pytest_plugin.py` | 新增 pytest hook 采集 |
| `quality/collector.py` | 新增 fail-open 采集入口 |
| `quality/request_metrics.py` | 新增请求指标采集适配 |
| `module/conftest.py` | 注册或按环境变量启用 quality 插件 |
| `common/request_context.py` | 增加当前用例上下文字段读取 |
| `common/request_middleware.py` | 增加质量指标中间件，内部捕获异常 |

验收：

- 串行运行生成 `cases-*.jsonl` 和 `requests-*.jsonl`。
- xdist 运行每个 worker 写独立分片。
- 请求重试每次 attempt 都有独立记录。
- 采集器主动抛错时，不改变测试结果，只产生完整性问题。

回退：

- 关闭 `QUALITY_ENABLE` 后恢复原行为。

### 20.3 迭代三：归并、完整性、分类

目标：所有分片归并成唯一事实集，失败可路由，结果可对账。

建议改动：

| 文件 | 动作 |
| --- | --- |
| `quality/aggregator.py` | 新增分片扫描、去重、完整性校验、统计 |
| `quality/classifier.py` | 新增确定性失败分类和规则版本 |
| `quality/cli.py` | 新增 `merge` 命令 |
| `run_master.py` | 在所有 pytest 阶段结束后触发 merge |
| `tests/quality/` | 新增分片归并、重复数据、损坏 JSONL、JUnit 对账测试 |

验收：

- 并行池和串行池混合运行后只生成一份 `merged` 结果。
- case 总数能与 JUnit 对账。
- 所有失败都有 `FailureRecord`，不能判断时归入 `UNKNOWN`。
- 分片损坏或缺失会写入 `IntegrityIssue`。

回退：

- 保留分片，不影响原 JUnit、Allure、pytest 结果。

### 20.4 迭代四：报告与影子门禁

目标：输出人可读报告和机器可读门禁结论，接入 Jenkins artifact。

建议改动：

| 文件 | 动作 |
| --- | --- |
| `quality/gate.py` | 新增影子门禁规则 |
| `quality/report.py` | 新增 JSON 与 Markdown 报告 |
| `quality/cli.py` | 新增 `report` 命令 |
| `run_master.py` | 在 merge 后触发 report |
| `Jenkinsfile` | 归档 `reports/quality/**`，邮件展示摘要入口 |

验收：

- 生成 `summary.json`、`gate-report.json`、`gate-report.md`。
- `gate-report.md` 能解释为什么 `PASS/WARN/BLOCK/NO_DATA`。
- Jenkins artifact 中可下载所有质量产物。
- P0 影子门禁不改变原 CI 退出码。

回退：

- 关闭 `QUALITY_ENABLE` 或 `QUALITY_SHADOW_GATE`，保留原流水线行为。

## 21. 测试策略

| 测试类型 | 覆盖点 |
| --- | --- |
| 单元测试 | ID 稳定性、脱敏、模型序列化、失败指纹、分类规则 |
| 插件测试 | pytest hook、setup/call/teardown、skip、xfail、异常 |
| 并发测试 | xdist worker 分片、并串混合、重复归并 |
| 请求链路测试 | HTTP 成功、HTTP 失败、超时、重试、多 attempt |
| 完整性测试 | 分片缺失、JSONL 损坏、JUnit 数量不一致 |
| 回归测试 | `QUALITY_ENABLE=0` 时原行为不变 |

第一版不需要引入真实外部接口压测。请求指标可以用 mock response 和现有测试链路验证。

## 22. 完成定义

P0 完成必须同时满足：

- 串行、并行、并串混合执行都能稳定生成质量产物。
- xdist worker 不发生分片覆盖和写入冲突。
- 每个用例有稳定 `case_id`，每次执行有 `invocation_id`。
- 每个请求 attempt 有独立 `request_event_id`。
- 请求指标能关联当前用例；无法关联时明确标记 orphan request。
- 汇总 case 数能与 JUnit 对账；不一致时完整性失败可见。
- 所有失败都有分类；不能判断时显式 `UNKNOWN`。
- 报告不包含密钥、完整敏感载荷和高风险隐私字段。
- `gate-report.md` 能被 Jenkins 归档并进入邮件摘要。
- 影子门禁连续运行一段观察期，不改变 CI 退出码。

## 23. 进入 P1 的条件

满足以下条件后再进入 P1：

- P0 质量产物连续稳定生成，完整性问题低且可解释。
- 失败分类规则经过人工回放，误判和漏判有记录。
- `case_id`、`interface_id` 在多次构建中稳定。
- 请求耗时、错误、重试指标能按接口和环境聚合。
- 影子门禁已有足够回放样本。
- 团队确认 Flaky、豁免、隔离、强门禁的责任归属。

## 24. 开发顺序结论

P0 的开发顺序建议固定为：

```text
契约与身份
-> 双层采集与分片
-> 归并与完整性
-> 失败分类与指纹
-> 聚合统计
-> Markdown/JSON 报告
-> 影子门禁
-> Jenkins artifact 与邮件入口
```

这个顺序符合当前约束：先让事实可信，再让结论可解释，最后让门禁可回放。P1 的成本、耗时、稳定性基线和 Flaky 治理都依赖这条 P0 数据链路，不能提前替代它。
