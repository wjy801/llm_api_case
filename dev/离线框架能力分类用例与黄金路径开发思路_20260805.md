# 离线框架能力分类用例与黄金路径开发思路

> 日期：2026-08-05
> 状态：开发思路
> 目标：建立可离线运行、便于定位问题的框架能力分类用例，并提供一条覆盖大部分核心能力的黄金路径用例

## 1. 需求理解

本方案不追求把所有框架能力强行压入一条用例，而是采用两层结构：

1. **能力分类用例**：每条用例验证一个内聚功能集合，失败时可以直接定位能力边界。
2. **黄金路径总体用例**：将大部分核心能力组合成一条完整业务链，证明能力之间可以协同工作。

最终形成：

```text
分类用例验证单项能力集合
→ 黄金路径验证能力组合
→ Runner/Jenkins验证执行、报告和历史能力
```

## 2. 第一性原理分析

### 2.1 真正目标

离线示例的核心价值不是“代码里出现了多少框架类”，而是让学习者能够回答：

- 请求从哪里进入框架；
- Middleware、Retry、Polling分别在何时生效；
- 跨步骤变量和资源由谁管理；
- 断言失败如何定位；
- 请求事实如何进入Allure、JUnit、Quality、Metrics和Flaky链路；
- 单项能力正常时，组合链路是否仍然正常。

### 2.2 因果链

```text
依赖真实外部接口
→ 网络、账号、余额和服务状态不可控
→ 测试结果不可复现
→ 无法判断失败来自框架还是外部环境
```

因此必须使用本地环回HTTP服务：

```text
确定性本地服务
→ 请求和状态迁移可控制
→ Retry/Polling/耗时结果可预测
→ 分类用例能够准确定位问题
→ 黄金路径结果具备学习和回归价值
```

### 2.3 TOC约束判断

当前首要约束不是用例数量，而是本地模拟服务的确定性。Retry、Polling、Capture和Metrics都依赖它提供可控响应；如果模拟服务存在随机性，下游报告即使生成也不可信。

实施顺序应当是：

```text
先固定本地服务协议和状态机
→ 再实现模块四件套
→ 再编写分类用例
→ 最后编写黄金路径和报告验收
```

## 3. 设计边界

### 3.1 保留的框架规则

- 新模块必须创建Request、Task、Assertions、Decorators四件套，并保留真实类身份。
- 用例仍使用Python代码表达，不引入YAML、Excel或测试DSL。
- 不新增DI容器、事件总线、Task注册器或用例注册体系。
- 不新增无调度意义的Marker；只有真实共享资源场景才使用`serial`。
- 业务用例不得直接导入Quality聚合器、Flaky Store或Runner内部stage。
- Runtime和Quality信息只能通过中性Runtime Hooks进入观察链路。
- SSE/流式输出已移出当前范围，不纳入本离线示例。
- 所有密钥均使用明确的离线占位值，不使用真实凭证。

### 3.2 单轮单用例不能证明的能力

以下能力需要多用例或多轮执行，不应塞入黄金路径制造假覆盖：

- 同时验证并发池和串行池两个执行分支；
- Flaky历史状态迁移；
- Polling成功、失败、未知和超时四种互斥终态；
- Jenkins邮件、历史报告和产物归档；
- 所有业务协议和模型领域类型。

这些能力分别由分类用例、重复运行和流水线验收完成。

职责说明：

| 文件 | 职责 |

## 5. 本地服务设计

本地服务使用`ThreadingHTTPServer`绑定`127.0.0.1`随机端口。每条用例获得独立服务状态，不依赖执行顺序。

### 5.1 模拟接口

| 接口 | 用途 | 确定性行为 |
|---|---|---|
| `POST /v1/media/generations` | 创建异步任务 | 返回固定格式任务ID和请求Header |
| `GET /v1/media/tasks/{id}` | Polling | 按配置返回503、queued、running、succeeded等状态 |
| `GET /v1/transient` | Retry | 前N次返回503或429，之后返回200 |
| `GET /v1/context` | 上下文提取 | 返回JSON、Header、Cookie和可Regex提取文本 |
| `GET /assets/input.png` | 输入资源 | 返回小型本地二进制内容 |
| `GET /assets/output.png` | 输出资源 | 返回可捕获的本地结果文件 |
| `GET /v1/audit` | 并发控制请求 | 返回调用序号和线程安全审计数据 |
| `DELETE /v1/media/tasks/{id}` | 清理 | 删除本地任务并记录清理事实 |
| `GET /v1/contracts/{mode}` | 断言验证 | 返回正常、业务错误或不符合Schema的响应 |

### 5.2 服务约束

- 不监听公网地址；
- 不调用任何外部URL；
- 使用随机空闲端口，避免端口冲突；
- 状态由加锁计数器驱动，不使用随机数；
- 延迟使用可控的毫秒级固定值；
- teardown必须执行`shutdown()`、`server_close()`并回收线程；
- fixture结束时检查任务和临时资源已经清理。

## 6. 能力分类用例

### 6.1 Request与Middleware

文件：`test_request_pipeline.py`

建议用例：

1. `test_request_uses_default_middleware_and_runtime_metadata`
   - 验证相对路径和本地base URL拼接；
   - 验证模块Request通过BaseRequest执行；
   - 使用稳定operation name和workload/control角色；
   - 验证调用方原始payload未被Middleware修改。
2. `test_sensitive_headers_do_not_change_business_request`
   - 使用离线占位Authorization；
   - 验证服务端正常收到业务Header；
   - 日志和Allure脱敏结果由现有框架观察，不在业务模块复制脱敏算法。

### 6.2 Retry与总预算

文件：`test_retry.py`

建议用例：

1. `test_retry_rescues_transient_get_failure`
   - 第一次503，第二次200；
   - 验证请求最终成功和服务端实际调用次数；
   - 为重试挽救率提供确定性事实。
2. `test_retry_honors_retry_after`
   - 第一次429并返回短`Retry-After`；
   - 验证后续请求成功。
3. `test_post_retry_requires_idempotency`
   - 使用Idempotency-Key验证POST允许重试；
   - 不通过放宽全局策略绕过幂等约束。

### 6.3 Polling状态机

文件：`test_polling.py`

建议用例：

1. `test_polling_reaches_success_with_complete_transitions`
   - queued → running → succeeded；
   - 验证最终响应和状态迁移。
2. `test_polling_reports_business_failure`
   - queued → failed；
   - 验证`PollingFailedError`保留最后响应和错误字段。
3. `test_polling_rejects_unknown_state`
   - 返回未配置状态；
   - 验证`PollingUnknownStateError`。
4. `test_polling_enforces_total_deadline`
   - 使用固定延迟消耗总预算；
   - 验证deadline后到达的成功不会被接受。

### 6.4 TestContext与资源清理

文件：`test_context_cleanup.py`

建议用例：

1. `test_context_extracts_supported_sources`
   - 分别提取JSONPath、Header、Cookie和Regex；
   - 验证类型约束、transform和`require()`。
2. `test_context_runs_cleanup_in_lifo_order`
   - 注册多个本地任务清理回调；
   - 验证逆序清理。
3. `test_context_reports_cleanup_errors_after_continuing`
   - 一个清理动作失败时继续执行剩余清理；
   - 最终暴露聚合清理错误。

### 6.5 Capture、Assertions与Allure

文件：`test_capture_assertions.py`

建议用例：

1. `test_output_capture_and_contract_assertions`
   - 输出URL指向本地资源；
   - 使用临时目录隔离下载产物；
   - 验证状态码、JSONPath、关键值和Schema；
   - 生成Allure步骤和附件。
2. `test_capture_limit_is_fail_open`
   - 本地资源超过CapturePolicy上限；
   - 捕获失败不得覆盖业务成功响应。
3. `test_schema_error_contains_stable_diagnostics`
   - 受控构造不符合Schema的响应；
   - 验证诊断包含字段路径而不泄露敏感值。

### 6.6 并发与ContextVar

文件：`test_concurrency_context.py`

建议用例：

1. `test_submit_with_context_preserves_case_ownership`
   - 使用`ThreadPoolExecutor`和`submit_with_context()`；
   - 每个线程创建并关闭自己的Request Client；
   - 验证所有审计响应独立且完整。
2. `test_parallel_requests_do_not_share_session_headers`
   - 两个线程使用不同单次Header；
   - 验证Header不会跨Session泄漏。

## 7. 黄金路径总体用例

文件：`test_full_framework_flow.py`

建议稳定nodeid：

```text
module/offline_framework_example/test_full_framework_flow.py::TestFullFrameworkFlow::test_offline_async_media_flow
```

### 7.1 执行流程

```text
启动独立本地服务
→ 创建Request、Task、Assertions、Decorators
→ Task构建包含本地媒体URL的payload
→ BaseTask创建异步媒体任务
→ Runtime Hooks建立ASYNC_TASK逻辑调用
→ Polling首次请求返回503
→ RetryPolicy完成挽救
→ queued → running → succeeded
→ CapturePolicy捕获本地结果文件
→ TestContext提取task_id、request_id、cookie和trace_id
→ submit_with_context并发查询audit
→ BaseAssertions执行状态码、JSONPath、Schema和领域断言
→ TestContext执行DELETE清理
→ 关闭所有Session和本地服务
```

### 7.2 覆盖能力

黄金路径主要覆盖：

- Request、Task、Assertions、Decorators四件套；
- 默认Middleware链；
- HTTP、Retry、Polling和严格deadline；
- Runtime metadata、request group和operation scope；
- TestContext跨步骤传值与资源清理；
- CapturePolicy与Allure附件；
- `submit_with_context()`并发上下文传播；
- JUnit、Allure和Quality请求事实来源。

黄金路径只走成功终态。Failure、Unknown、Timeout等互斥路径由分类用例负责，避免总体用例难以阅读和定位。

## 8. 执行层与报告层验收

业务用例不直接断言Quality内部实现。执行层和报告层通过真实Runner产物验收。

### 8.1 Collect-only

验证：

- 用例全部可以被pytest权威收集；
- 集合守恒；
- 未标记用例进入并发池；
- 如后续存在真实共享资源用例，才增加serial用例验证串行池。

不把固定用例数量作为长期合同。

### 8.2 Quality关闭

要求：

- 全部离线用例通过；
- 不创建Quality run ID、JUnit默认文件或质量目录；
- 不访问外部网络；
- pytest退出码保持原始语义。

### 8.3 Quality与Metrics开启

要求本轮产物能够直接观察：

- 请求成功率；
- 重试挽救率；
- Polling状态迁移；
- 接口耗时Top；
- 稳定operation name和model ID；
- 请求、逻辑调用和Case归属关系。

### 8.4 Flaky

使用同一个黄金路径nodeid和同一个独占数据库连续运行多轮：

```text
第1轮：建立初始观察
→ 后续轮次：积累稳定通过样本
→ 观察实际状态迁移和历史记录
```

不通过故意制造随机失败来展示Flaky，否则示例本身会失去可信性。

### 8.5 Jenkins

现有Jenkins目标可以指向`module/offline_framework_example`，在断网条件下执行：

- 框架测试；
- 离线示例收集；
- 离线接口执行；
- JUnit、Allure、Pipeline Summary和质量机器证据发布。

不为示例新增专用流水线、报告类型或人工摘要。

## 9. 分阶段实施建议

### 阶段0：冻结离线协议

- 确定接口、响应Schema和状态机；
- 确定每种失败模式的调用次数和延迟；
- 确定禁止外网的验证方式。

### 阶段1：本地服务与四件套

- 实现服务生命周期；
- 创建模块四件套和`__init__.py`导出；
- 建立payload和响应Schema。

### 阶段2：基础分类用例

- Request/Middleware；
- Retry；
- Polling。

这三组是后续能力的共同前置条件，应优先稳定。

### 阶段3：资源与并发分类用例

- TestContext和清理；
- Capture、Assertions、Allure；
- 并发和ContextVar。

### 阶段4：黄金路径

- 组合已通过的分类能力；
- 保持测试方法只负责编排和最终断言；
- 不在黄金路径复制底层算法。

### 阶段5：Runner与报告验收

- Quality关闭完整回归；
- Quality/Metrics开启产物验收；
- 多轮Flaky历史；
- 本地Jenkins断网运行。

## 10. 完成标准

满足以下条件后，可以将该模块作为框架离线学习和组合回归基线：

- [ ] 四件套均为真实类且职责清晰；
- [ ] 分类用例互不依赖执行顺序；
- [ ] 本地服务无随机行为、无固定端口冲突；
- [ ] 所有HTTP和资源URL均为环回地址；
- [ ] Retry和Polling事实可预测；
- [ ] 每个分类用例只承担一个明确结论；
- [ ] 黄金路径覆盖大部分核心能力但不包含互斥异常分支；
- [ ] Request Session、线程、本地服务、任务和临时文件全部回收；
- [ ] Quality关闭与开启时均能稳定运行；
- [ ] JUnit、Allure、Metrics和Flaky产物来源一致；
- [ ] 不新增并行人工质量报告；
- [ ] README和FRAMEWORK_TEST_SPEC补充离线示例运行入口。

## 11. 最终形态

建议初版形成：

```text
6组可定位的能力分类测试
+ 1条大部分核心能力组合的黄金路径
+ 1套Runner/Jenkins离线验收方式
```

分类测试回答“哪项能力失效”，黄金路径回答“能力组合是否仍然成立”，运行与报告验收回答“本轮事实是否能够被可信地消费”。三层职责分离后，示例既适合学习，也可以长期作为框架回归基线。
