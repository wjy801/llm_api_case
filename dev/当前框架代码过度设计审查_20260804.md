# 当前接口自动化框架实际代码设计复审

> 复审日期：2026-08-04  
> 文档版本：V3  
> 用例目录：`module/`  
> 复审边界：已有能力和公开入口全部保留，只审查职责、依赖、重复、抽象层次和扩展方式  
> Marker 约束：不增加 `live`、`real` 等真实接口 Marker，仅保留确有调度意义的 `serial` Marker  
> 流式范围：流式输出/SSE 用例已删除，不纳入本轮评审、改造、学习示例和验收  
> 密钥范围：密钥泄露、明文凭证、凭证轮换、Secret 扫描和历史清理不纳入本轮评审、改造和验收  
> 本轮动作：只复审实际代码，不修改框架代码
> 文档职责：本文件保留设计证据与兼容边界；唯一实施基线见 [CI接口框架设计缺陷优先级评审_20260803.md](./CI接口框架设计缺陷优先级评审_20260803.md)

## 1. 结论

当前框架存在过度设计，但不能再把“功能多、文件多、当前业务消费者少”直接判为过度设计。

复审后的准确结论是：

1. **能力集合不过度**：Request、Middleware、Retry、Polling、Runtime Hooks、TestContext、Quality、Metrics、Flaky、报告、下载、JUnit、Allure 和 Jenkins 都有独立价值，应完整保留。
2. **部分实现位置过重**：`BaseTask` 混入多个业务领域，`BaseRequest` 直接管理过多运行时生命周期，Runner 和 Reporting 感知 Quality 内部细节。
3. **可选能力隔离不足**：Quality 关闭时仍因顶层导入加载大量模块；Pipeline Reporting 的轻量命令也会被 Quality 依赖链拖入。
4. **同一能力存在多份实现**：下载、配置校验、产物校验、JUnit 解析、执行结论归纳均有不同程度重复。
5. **四件套是模块规范**：Request、Task、Assertions、Decorators 必须作为新增业务模块的统一扩展位；薄子类是允许且有意保留的结构，不属于待删除的重复实现。
6. **执行可信性仍是首要约束**：选测集合、pytest 退出码和报告事实优先级不可信时，继续调整目录或抽象层不会产生真实收益。

因此，目标不是删功能，而是：

```text
保留全部能力与公开 API
→ 每项能力只有一个实现源
→ 核心只依赖中性扩展接口
→ 可选能力按需加载
→ 旧入口通过兼容委托继续工作
```

## 2. 第一性原理与 TOC 判断

### 2.1 框架可扩展的本质

可扩展不等于提前增加更多基类、注册中心或插件目录。接口测试框架真正需要控制的是变化传播范围：

- 新增业务接口，主要修改 `module/<domain>/`；
- 新增横切能力，实现 Middleware 或 Runtime Hook，不改每个 Request；
- 新增质量阶段，通过可选生命周期接入，不侵入 pytest 执行内核；
- 新增报告消费者，复用同一结构化执行结果，不重新解析日志；
- 旧调用方继续使用原有类名、函数名、CLI、Schema 和产物路径。

如果新增一个端点需要同时修改 `BaseTask`、Runner、Jenkins、Quality 和全局导出表，框架就不具备真正的可扩展性；反之，文件数量少但所有职责挤在一个类中，也不叫简洁。

### 2.2 当前约束的因果链

```text
预收集没有完整复用正式执行的选择条件
→ 分池依据可能不是用户最终选择集合
→ 正式执行可能得到 pytest exit 5
→ merge_exit_codes 又可能把 [5, 5] 合并为 0
→ Jenkins、JUnit、Quality 和 Pipeline Summary 围绕错误事实继续加工
→ 框架产物越丰富，错误结论反而越难识别
```

按 TOC，当前第一约束是“执行事实不够可信”，不是“缺少更多抽象”。重构顺序必须先修复事实源，再降低耦合和重复。

### 2.3 本版判定规则

- 低使用率只用于判断是否延迟加载或隔离，不构成删除依据，本轮也不据此改变现有默认开关。
- 公开 API、CLI、Schema、报告章节、产物和行为均保留。
- 有两个以上稳定实现重复时，提取一个最小内部实现源。
- 扩展点必须隔离已经存在的变化；不为想象中的消费者建设通用平台。
- 兼容入口可以很薄，但必须明确标注为兼容门面，避免继续承载新逻辑。
- 网络、线程、下载和文件写入等副作用必须可配置、可观察、可关闭；能力本身不删除。
- 结构测试应保护行为和依赖方向，不锁死文件数量、文件名和具体拆分形态。

## 3. 能力、扩展边界与兼容方式

| 能力 | 是否保留 | 合理扩展边界 | 精简方式 |
| --- | --- | --- | --- |
| `BaseRequest` | 完整保留 | HTTP 会话、URL、超时、Header、verbs 的稳定门面 | 生命周期细节委托内部协作者，签名保持兼容 |
| Request Middleware | 完整保留 | 日志、脱敏、资源捕获、运行时观察等横切行为 | 保留替换语义，并增加 additive 扩展入口 |
| Retry | 策略和参数完整保留 | `RetryPolicy` 与 `RetryExecutor` 分离，显式启用 | 内部只保留一个判定和执行实现源 |
| Polling | 完整保留 | 状态策略、迁移记录、deadline 和分类异常 | 修复总预算，不另建工作流引擎 |
| Runtime Hooks | 强类型能力完整保留 | `common` 的中性观察协议，Quality 提供适配器 | 收拢 Lease 管理，旧自由函数继续代理 |
| TestContext | 完整保留 | 多步骤用例变量提取、校验和逆序清理 | 按需 fixture，不进入无需求用例的默认路径 |
| 下载与附件 | 输入、输出下载全部保留 | 可配置 Capture/Download Policy | 合并两套底层下载实现，保留现有入口和兼容默认 |
| Assertions | 同步、异步、模块函数全部保留 | 基础契约与领域断言 | 多个入口委托同一同步实现源 |
| Decorators | 公共名称完整保留 | Allure step 和附件能力 | 公共类作为兼容扩展点，底层下载逻辑外移 |
| `BaseTask` | 所有方法和行为保留 | 兼容门面；新业务使用领域能力组合 | 领域实现迁出后由原方法委托 |
| 模块 Request/Task 等类型 | 原类对象、类型名和导入路径保留 | 每个新模块强制建立 Request/Task/Assertions/Decorators 四件套 | 允许薄子类，但必须保持真实类定义和统一导出 |
| Quality/Semantic/Metrics/Flaky | 能力、CLI、Schema、产物完整保留 | 可选 Quality Run Lifecycle | 轻量兼容入口常驻，重实现按需加载 |
| Runner | 命令和分池能力完整保留 | 唯一执行编排者 | 只依赖中性生命周期，不导入 Quality 内部模型 |
| Pipeline Reporting | 章节、邮件、历史和结论能力保留 | Jenkins/pytest 事实 + Quality 诊断 | 共享一次解析结果，明确事实优先级 |
| JUnit/Allure/Jenkins | 完整保留 | 测试事实、诊断制品、流水线事实 | 统一产物生命周期，避免多次清理和重复解析 |

## 4. 哪些复杂度是必要的

以下设计不能因为代码量或消费者数量而删除。

### 4.1 Middleware、Retry 与 Polling

`RequestMiddleware` 已有 Runtime Observation、Media Resource、Redaction 和 Logging 四个真实实现。三阶段接口对应请求前、响应后、异常三条真实路径，是合理的横切扩展缝。

`RetryPolicy` 与 `RetryExecutor` 分离，且支持 clock/sleeper 注入，既隔离策略变化，也方便离线测试。它是显式 opt-in，不会天然掩盖接口缺陷。

Polling 有真实图片、视频和异步任务消费者。状态集合、迁移记录、总 deadline 和分类异常属于协议复杂度，不是形式化分层。

### 4.2 Runtime Hooks

`common/runtime_hooks/` 已实现中性协议、Noop、Provider、ContextVar 和 Quality Adapter，依赖方向是：

```text
quality → common.runtime_hooks
common -X→ quality
```

这个方向正确。Operation、Request Group 和 Polling 的强类型生命周期也有真实语义，不能简单压缩成无类型 `emit(event)`。

需要调整的是调用位置和命名，不是删除 Hook 能力。

### 4.3 TestContext

变量仓库、JSONPath/Header/Cookie/Regex 提取、类型校验、来源兜底和逆序 cleanup 共同服务多步骤测试。当前业务用例消费较少，只能说明示例和接入不足，不能证明抽象无效。

正确做法是保留全部 API，让 fixture 按需创建，并提供一个真实多步骤示例。

### 4.4 Quality 内部分层

`quality/` 不能按目录规模整体判为过度设计：

- Collector 与 Aggregator 分离，对应 xdist worker shard 和父进程归并的真实边界；
- Semantic 需要区分 Operation、Request Group 和 Polling 生命周期；
- Metrics 的 case、operation、request_group、request_event 粒度计算规则不同；
- Flaky Store 的 Facade、Repository、Migration、Governance 和 Projection 分别承担事务、SQL、升级、规则和投影；
- Manifest、Schema、Hash 和原子写入用于保护跨进程、跨阶段产物完整性。

这些是已有能力成立所需的必要复杂度。真正过重的是加载方式、胶水代码和跨层依赖。

### 4.5 Pipeline Reporting 分层

Sources、Builder、Renderer 分别处理 I/O、纯计算和展示，分层本身合理。问题不是文件数，而是 Sources 顶层绑定 Quality，以及 Builder 对执行结果进行第二次解释。

## 5. 确认存在的设计问题

### P1-1：`BaseTask` 是业务 God Class

证据：`common/base_task.py` 同时包含图片、聊天、媒体任务、余额、用量、结算、环境配置读取和 `pytest.skip()` 控制流；约从 243 行后主要是账户与账单领域逻辑。

因果链：

```text
为了让所有模块继承后立即可用
→ 不同领域方法不断进入 BaseTask
→ 任一领域变化都修改 common
→ 所有子类同时暴露无关能力
→ 新模块继续向基类堆方法
```

兼容式改造：

1. 把媒体复合流程迁入媒体能力对象，把账单流程迁入账单能力对象。
2. `BaseTask` 所有现有方法、签名、Allure 步骤和行为继续保留。
3. 原方法改为委托领域实现，作为兼容门面。
4. `ImageTask`、`VideoTask` 等可组合对应能力，不再继续扩大 `BaseTask`。
5. 新领域实现返回中性结果，由新用例或 fixture 决定是否 skip；`BaseTask` 旧门面继续转换为原有 `pytest.skip()` 行为。

这不是删除继承体系，而是冻结宽基类，让新代码走组合边界。

### P1-2：可选 Quality 能力没有做到“关闭即不加载”

证据：

- `quality/__init__.py` 聚合导出约 176 个符号；
- 实测 `import quality.config` 会加载约 41 个 `quality.*` 模块；
- 无条件导入 pytest 插件时会加载约 45 个 Quality 模块；
- `module/conftest.py` 无条件注册插件，插件虽会在关闭后短路，但导入成本已经发生；
- `pipeline_reporting/sources.py:12-24` 顶层导入多个 Quality 模型。

兼容式改造：

1. 保留根包全部公开符号和 `__all__`，用映射驱动的 `__getattr__` 延迟导出。
2. 轻量兼容插件继续注册，现有 Hook、参数和导入路径不变；重型 Quality 实现按开关局部加载。
3. Reporting 通过局部导入的 Quality Source Adapter 读取可选产物。
4. `initialize-stages`、`set-stage` 等轻量命令不加载 Quality。
5. 有产物时完整展示全部章节；未启用显示 `NOT_RUN`；启用但产物异常才显示 `NO_DATA`。

不需要新增 entry point、插件市场或自动发现系统。一个显式生命周期工厂已经足够。

### P1-3：Runner 直接感知 Quality 内部类型和阶段

`run_orchestration/runner.py` 顶层导入 `quality.models.RunStatus`，并直接感知 Quality 配置、环境和收尾类型。现有 `quality_*_stage.py` 对应必要的阶段隔离，问题不在这些模块存在，而在 Runner 依赖具体 Quality 类型。

兼容式改造：

```text
Runner
├─ pytest 核心执行
└─ QualityRunLifecycle
   ├─ prepare
   ├─ stage_environment
   └─ finalize
```

- 保留全部阶段模块、函数、执行顺序和旧入口，由 Lifecycle 组合现有阶段。
- Runner 只依赖中性 Lifecycle 协议。
- Quality 关闭时工厂返回轻量 Noop，不加载 Semantic、Metrics 或 Flaky 实现。
- 不建设通用 DI 容器或多插件广播总线。

### P1-4：`BaseRequest` 直接管理过多 Runtime 生命周期

`BaseRequest` 在普通请求、重试和轮询路径中分别开始、绑定、结束 Operation、Request Group 和 Polling Lease。能力合理，但生命周期细节散落导致 HTTP 控制流难读、异常分支容易遗漏收尾。

同时 `_quality_operation_name`、`_quality_traffic_role` 把具体扩展名称泄漏到了通用请求层。

兼容式改造：

- 用一个内部 `RuntimeObserver`/context manager 统一 begin、finish、detach 和 outcome 映射；
- 保留现有强类型 Hook、Lease、Provider 和自由函数；自由函数作为兼容代理；
- 新增中性的 runtime metadata 入口；
- 旧 `_quality_*` 参数继续接受并映射，不立即删除；
- 当前只有一个消费者，不引入事件总线。

### P1-5：报告形成第二套执行事实

当前 Jenkins 发布 JUnit，Groovy 又解析 JUnit/控制台，Python Pipeline Reporting 再解析一遍并生成 `PASS/WARN/FAIL`。`pipeline_reporting/builder.py` 还会在 JUnit 可用时优先据此判阶段通过，即使 Jenkins 显式阶段已经失败。

应保留邮件、摘要、历史、Quality 章节和 Pipeline Conclusion，但明确语义：

```text
pytest 原始退出码：测试进程事实
Jenkins 阶段状态：整条流水线执行事实
JUnit：用例统计与失败详情
Quality/Metrics/Flaky：诊断与观察
PipelineConclusion：关注等级，不改写执行事实
```

建议生成一次结构化 `RunResult`/JUnit Summary，让 Markdown、邮件、历史和兜底报告共同消费。显式阶段失败必须优先于部分 JUnit；Quality 只能增加诊断，不能覆盖 Jenkins/pytest 结论。

### P1-6：下载能力有两套底层实现，触发策略隐藏

- 输出下载位于 `common/base_decorators.py`；
- 输入媒体下载位于 `util/media_resources.py`；
- 文件名清理、唯一路径、流式下载和附件类型判断存在重复；
- 默认 POST Middleware 和 `poll_get` 装饰器会隐式触发下载。

能力全部保留，建议：

1. 抽取一套内部下载、命名、大小控制和附件识别原语。
2. 现有 decorator、middleware、`start_media_downloads()` 及结果下载入口全部兼容委托。
3. 引入小型 Capture Policy，分别控制输入捕获、输出捕获和关闭捕获。
4. 当前默认行为先保持兼容；新调用方显式选择策略。
5. 下载失败继续 fail-open，不覆盖接口响应和断言结果。

不需要新增通用 Artifact 平台或下载任务中心。

### P1-7：执行层存在多个 pytest/Allure 生命周期所有者

- `master_service.py` 与 `pytest_execution.py` 都涉及 pytest 调用或收集；
- 多次 `pytest.main()` 之间通过备份/恢复 Allure 目录维持制品；
- `pytest.ini`、`module/conftest.py` 和 Runner 都参与 Allure 清理或生成。

统一先收集再执行不是缺陷，而是 Runner 的控制面边界：

```text
权威收集
-> 形成确定的 nodeid 与 marker 清单
-> 并串行分池或未来分布式分片
-> 执行节点只消费已分配 nodeid
```

即使关闭并发，Runner 模式也继续预收集，保证串行、并行和未来分布式执行共享同一种计划语义。真正的问题是收集和执行分别由多个模块拥有，且正式执行仍可能重新应用选择条件，导致控制面计划与实际集合漂移。

保留 CLI、分池、`serial`、JUnit 和 Allure 能力，调整所有权：

- `pytest_execution.py` 唯一拥有 pytest 收集和执行；
- `scheduling.py` 拥有纯分池算法，而不是只做重导出；
- `master_service.py` 保留稳定入口并兼容委托；
- Runner 串行和并行模式都消费同一份不可变 nodeid 计划，不绕过预收集；
- 未来分布式 worker 只执行控制面分配的 nodeid，不在 worker 端重新选择用例；
- 各池可写独立临时原始目录，结束后合并并只生成一次报告；最终继续提供现有 `allure-results`、HTML、历史路径与附件语义，并兼容自定义 `--alluredir`；
- 直接运行 pytest 时仍支持自动报告，Runner 模式由统一生命周期收尾。

### P2-1：配置验证有两个实现源

`config.py` 的 Pydantic validator 与 `util/config_validation.py` 的手工解析、错误聚合和反向转换同时存在。

应保留 `Settings`、`settings`、`load_settings()`、全部公开解析函数、异常类型、错误文本以及现有可观察的初始化和异常时机；内部让验证规则只实现一次，另一个入口做兼容代理。离线测试通过显式注入测试 Settings 隔离外部环境配置 I/O，不以“延迟加载”为名改变旧入口行为。

### P2-2：四件套是强制模块规范

- `BaseAssertions` 的同步方法、`async_assert_*` 和模块函数当前已经委托同一实现，属于合理兼容面，不是重复实现；
- `ImageRequest/Task/Assertions` 和 `VideoRequest/Task/Assertions` 已被业务用例实例化，是稳定的领域扩展点；
- 多个 `*Decorators` 当前逻辑较薄，但原类身份、MRO、`__name__` 和导入路径都可能被调用方依赖；
- `ProtocolTask` 有真实消费者，并承载场景入口和 Allure 步骤语义。

因此现有类型、方法和类对象全部保留，新增业务模块也必须创建 Request、Task、Assertions、Decorators 四件套：

- 四个类型分别继承对应公共基类，并保持真实类定义；
- `__init__.py` 统一导出四个模块类；
- 暂无专用逻辑时允许使用 `pass` 薄子类，作为稳定类型身份和后续扩展位；
- 不能用简单别名替代类型，也不能因为当前逻辑为空而省略文件；
- 去重只收敛底层实现，不改变四件套模块结构。

该规则以 `FRAMEWORK_TEST_SPEC.md` 的新模块最小必需结构和提交检查清单为准。

### P2-3：Artifact 完整性校验机械重复

Metrics、Flaky Importer 和 Pipeline Reporting 都需要验证 run ID、Schema、Manifest、状态和 Hash。各消费者在信任边界重新校验是正确的，但 JSON/JSONL 读取、基本字段和 Hash 校验代码不应重复。

只提取小型公共读取原语；Metrics 关系校验、Flaky 可导入规则和 Reporting 降级策略仍留在各自模块，避免形成万能 Repository。

### P2-4：结构测试锁死当前拆分形态

部分测试精确断言文件集合、导入 DAG、入口文件不得包含函数或 Jenkins 源码字符串。它们会让安全重构变成“测试保护目录摆放”。

覆盖目标保留，但改测：

- 原公开入口仍可导入和调用；
- Core 不静态依赖 Quality；
- Quality 关闭时不加载重实现；
- 选测、退出码、产物和报告事实正确；
- 扩展接口可插拔且 fail-open。

## 6. 普通缺陷：不要误判为过度设计

以下问题需要修复，但它们是正确性或并发缺陷，不是抽象层过多：

1. 预收集未完整使用 `-k`、`-m`、`--ignore` 和插件环境。
2. `merge_exit_codes()` 会把 `[5, 5]` 合并为成功，并把 pytest 2/3/4 压缩为 1。
3. 基础设施错误后仍可能继续执行串行真实接口池。
4. Polling 单次 HTTP timeout 与重试可能越过总 deadline。
5. Session Header 的临时修改在共享客户端并发时可能互相污染。
6. `BaseTask` 的部分查询参数存在空键名等实现错误。

这些问题应先用行为测试刻画，再修代码；不需要为它们新建平台级抽象。

## 7. 推荐改造顺序摘要

以下只表达设计依赖关系；具体任务、阶段门禁和验收以总体实施计划为准。

### 阶段 0：建立可信基线

- 固定 clean checkout 下的离线测试集合；
- 为选测、pytest 0～5、Polling、Header 并发和报告事实优先级补刻画测试；
- 确认全部公开 API、CLI、Schema、报告章节和产物路径的兼容清单。

### 阶段 1：修复唯一执行事实

- 收集与执行使用相同选择条件；
- 计划非空但执行 exit 5 必须失败；
- 保留 2/3/4 原始语义并立即停止后续真实接口池；
- Jenkins/pytest 状态优先于 JUnit 和 Quality 观察；
- 形成一份结构化池级执行结果，供报告链共享。

### 阶段 2：收窄核心职责

- 领域逻辑迁出 `BaseTask`，旧方法兼容委托；
- Runtime 生命周期收拢到内部协作者；
- `_quality_*` 映射为中性 metadata；
- pytest 和 Allure 生命周期归属唯一组件；
- 下载底层实现合并并引入可配置策略。

### 阶段 3：隔离可选扩展

- `quality/__init__.py` 兼容性懒加载；
- 轻量 pytest 兼容插件保持注册，重型 Quality 实现按开关加载；
- Runner 接入单一 `QualityRunLifecycle`；
- Reporting 的 Quality Source 局部加载；
- Quality 关闭时不导入重实现、不创建对应产物。

### 阶段 4：局部去重

- 配置规则单一实现源；
- Assertions 多入口共享实现；
- Artifact 基础校验共享；
- 素材 CLI 保留命令、参数、输出和退出码，内部复用 Request/Task/Assertions；
- 结构测试改为行为与依赖方向测试。

每个阶段都遵守：旧入口先保留、兼容测试先落地、新实现稳定后再冻结旧入口，不在同一提交混入无关目录整理。

## 8. 明确不做的事情

为避免从接口测试框架演变成质量平台，本轮及当前路线不做：

- 不删除现有 Quality、Metrics、Flaky、Retry、Middleware、TestContext 或下载能力；
- 不删除或缩减报告、邮件、历史、JUnit、Allure、Jenkins、独立 CLI 和现有公开类型；
- 不新增 `live`、`real` Marker；
- 不改变 `module/` 作为业务用例目录的定位；
- 不建设插件市场、通用注册中心、DI 容器或消息总线；
- 不建设 YAML/Excel/DSL 用例系统；
- 不把 Polling 扩展成通用工作流引擎；
- 不为 Quality 新增身份层、指标、规则、治理命令或人工报告入口；
- 不为了目录整齐大规模搬文件；
- 不以“当前没有业务消费者”为理由删除公共能力。

## 9. 验收标准

### 9.1 零能力回退

- 现有公共类、函数、参数、CLI 和导入路径继续可用；
- Quality、Metrics、Flaky、报告、邮件、历史、下载和附件内容全部保留；
- 现有 Schema、产物路径和兼容行为不得破坏；
- 素材独立 CLI 与 `run_master.py` 稳定入口继续工作。

### 9.2 核心可扩展

- 新增普通端点只需修改对应 `module/<domain>/`；
- 新增横切请求行为只实现 Middleware，不修改每个 Request；
- 新增观察实现只适配 Runtime Hooks，不修改 HTTP 内核；
- 新增 Quality 阶段只修改 Quality Lifecycle，不修改 pytest 执行器；
- 新增报告消费者复用结构化结果，不重新解析控制台文本。

### 9.3 核心路径简洁

- `BaseTask` 不再直接实现多个领域；
- `BaseRequest` 的 HTTP 主流程不再散落 Lease 细节；
- Quality 关闭时不加载 Semantic、Metrics、Flaky 重实现；
- 同一种下载、校验和 JUnit 解析只有一个实现源；
- 兼容门面不继续接收新业务逻辑。

### 9.4 执行结果可信

- 最终选择集合、分池集合、实际执行集合和 JUnit 集合一致；
- 只有所有已执行池都成功时进程结果才为 0；
- pytest 2/3/4/5 不被吞掉或错误压缩；
- 显式阶段失败不会被部分 JUnit、Quality 或 Summary 改写为通过；
- `serial` 只表达调度约束，不表达接口是否真实。

### 9.5 副作用可控

- 日志、附件、下载和 Hook 失败不覆盖原始响应或异常；
- 下载能力可按输入、输出分别配置，关闭后不访问外部资源；
- Polling、Retry 和 sleep 共用总预算；
- 并发请求不会因临时 Session Header 修改互相污染。

## 10. 最终定位

完成上述兼容式改造后，框架可以作为测开学习与实战框架：

> 一套代码式、可扩展的接口自动化框架，完整展示 Request、Task、Assertions、Middleware、Retry、Polling、TestContext、Runtime Hooks、并串行调度、JUnit、Allure、Jenkins 及可选质量观察能力；核心执行路径保持干练，扩展能力按需接入，现有功能不因精简实现而回退。

学习价值来自“边界清晰、事实可信、扩展方式可解释”，不是来自删掉高级能力，也不是来自继续堆叠抽象。

本次复审的最终判断是：

```text
框架能力可以完整保留
现有必要抽象大多成立
需要治理的是职责位置、加载时机、重复实现和兼容层扩张
```
