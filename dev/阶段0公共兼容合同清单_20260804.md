# 阶段 0 公共兼容合同清单

> 版本：2026-08-04  
> 目的：为 P0/P1 重构划定“必须兼容”与“允许内部变化”的边界。  
> 原则：保护消费者可观察行为，不把当前内部文件拆分和已知错误固化为合同。

## 1. 第一性原理与 TOC 判断

框架兼容性的本质不是文件不动，而是调用者的输入、输出、类型身份、错误时机和产物位置可预测：

```text
稳定入口与类型身份
-> 稳定执行事实和退出码
-> 稳定机器产物与人工入口
-> 内部实现才可以安全重构
```

当前 TOC 约束仍是执行事实不唯一，而不是 API 数量不足。因此阶段 0 只冻结已有正确合同，并用 strict xfail 标记错误行为；不能为了“兼容”继续保留选测漂移、退出码压缩、Polling 超预算或并发 Header 污染。

## 2. 强兼容公共入口

| 范围 | 必须保持的合同 | 允许变化 |
| --- | --- | --- |
| 根 Runner | `run_master.run`、`run_master.main`、`PROJECT_ROOT`、`DEFAULT_ALLURE_RESULTS_DIR` 可导入；`run()` 保持 `test_path, extra_pytest_args, numprocesses, dist, serial_marker` 参数面 | 内部模块拆分和委托关系 |
| CLI | `python run_master.py [target]`，以及 `--test-path`、`-n/--numprocesses`、`--dist`、`--serial-marker`、`--parallel-first` | 参数解析实现 |
| 稳定兼容入口 | `master_service.py` 的现有收集类型、收集函数和分池函数在迁移期继续可导入并兼容委托 | 最终实现所有权可迁至 `pytest_execution.py` / `scheduling.py` |
| Common 门面 | `common.__all__` 中现有非 SSE 导出；`BaseRequest`、`BaseTask`、`BaseAssertions`、`BaseDecorators` 的公开方法、签名和异常类型 | 私有 helper、生命周期内部对象及文件位置 |
| 断言兼容面 | `BaseAssertions` 同步方法、`async_assert_*` 和模块函数继续委托同一语义 | 内部复用方式 |
| Quality | `quality.__all__` 当前导出，Schema/枚举值、标识生成规则、CLI 命令及 fail-open 边界 | 聚合器、Collector、Semantic、Metrics、Flaky 的内部依赖方向 |

| 配置 | `Settings`、模块级 `settings`、`load_settings()`、现有解析函数与可观察异常时机 | 重复校验的内部去重 |

`common.__all__` 和 `quality.__all__` 的源码清单是精确导出事实源，本文件不复制数百个名字形成第二份易漂移列表。

## 3. 四件套与领域类型身份

四件套是用例创建强制规范，不是可选脚手架：

```text
<Domain>Request
<Domain>Task
<Domain>Assertions
<Domain>Decorators
```

兼容要求：

- 新增业务模块必须创建四个模块和四个真实类；即使初期逻辑较薄也保留类对象；
- 已有 `ImageRequest/Task/Assertions/Decorators`、`VideoRequest/Task/Assertions/Decorators`、`SmokeRequest/Task/Assertions/Decorators` 的模块、类身份、MRO、`__name__` 和包导出不变；
- `ProtocolRequest`、`ProtocolTask`、`ProtocolInterceptionAssertions` 等现有协议类型和导入路径保持，`ProtocolTask` 的场景入口及 Allure 步骤语义不得因去重消失；
- 不得用简单别名替换薄子类；可以向现有类逐步迁入真实领域逻辑；
- 阶段 0 不改变任何生产领域类型，只记录合同。

## 4. 执行语义合同

### 4.1 必须保留

- Runner 在串行、并行和未来分布式模式下都先形成一次权威 nodeid 计划；关闭并发不绕过预收集；
- serial marker 决定串行池，两个池互斥，并集等于最终计划，nodeid 唯一；
- collect-only 不创建真实客户端，不调用真实接口，不生成 Quality run 身份；
- 单池保留 pytest 原始退出码；多池保留池级原始码后按固定表聚合；
- pytest 是测试进程事实源，JUnit 是统计与失败详情，Allure 是步骤和附件定位，Summary 只汇总，Jenkins 决定整条流水线结论；
- 显式阶段失败不能被可解析或全绿 JUnit 覆盖；Quality 缺失或失败不能覆盖 pytest/Jenkins 结果。

### 4.2 已知错误不是兼容合同

以下行为已有 `tests/test_stage0_known_defects.py` 的 strict xfail，P0/P1 修复时必须转为正常通过：

- `-k`、`-m`、`--ignore` 在正式执行时二次筛选，导致预收集计划与实际集合不同；
- pytest 2/3/4/5 被聚合为 0/1；
- 计划非空但执行返回 5 被当成成功；
- Polling 单次请求和内部重试不受剩余总预算约束；
- 共享客户端通过修改 `session.headers` 临时切换协议 Header，造成并发污染。

## 5. 请求、任务与失败语义合同

- Middleware 与 Runtime Hooks 继续 fail-open：观测失败不覆盖业务 Response 或原始异常；
- Retry 保留方法安全限制、显式 `RetryPolicy`、尝试记录和终止异常；
- Polling 保留 `PollingPolicy`、状态迁移、分类异常和最终 Response；P1 只统一总 deadline；
- BaseTask 旧入口、参数默认值、`pytest.skip()` 条件和消息保持；内部可以委托给窄职责组件；
- 下载、附件和结果收集入口继续存在；下载或附件失败不得把成功业务响应改成失败；
- 临时 Header 的优先级保持，但实现应改为请求级合并，不能继续依赖共享 Session 的并发可变状态；
- 流式输出/SSE 已明确不纳入本轮学习和验收，本清单不新增相关合同。

## 6. CLI 合同

| CLI | 当前命令面 | 退出边界 |
| --- | --- | --- |
| Runner | `python run_master.py` | 修复后保留 pytest 0～5 事实；异常明确非零 |
| Quality | `python -m quality.cli` 下的 `merge`、`semantic-merge`、`metrics-aggregate` 和 Flaky 查询/治理命令 | 机器产物不可用时按各命令现有合同返回，不能改变 pytest 结果 |
| Reporting | `python -m pipeline_reporting initialize-stages/set-stage/generate` | 开关关闭时不生成报告；生成失败不伪造测试事实 |

命令名、现有参数、stdout/stderr 的用途和退出码属于兼容面；内部函数与 argparse 文件位置不是兼容面。

## 7. 产物与路径合同

| 产物 | 当前稳定位置/规则 | 语义 |
| --- | --- | --- |
| 框架 JUnit | `reports/unit-tests.xml` | 框架离线测试统计 |
| 接口 JUnit | 自定义 `--junitxml`；分池时添加 `-parallel` / `-serial` 后缀，Jenkins 发布 `reports/smoke-tests*.xml` | 用例统计与失败详情 |
| Allure 原始结果 | 默认 `allure-results/`，兼容自定义 `--alluredir` | 步骤、请求、响应和附件原始证据 |
| Allure HTML | `allure-report/` | 本地 HTML 报告 |
| Allure 历史 | `history_report/<timestamp>/` 与 `history_report/latest/` | 配置开启时生成并按保留数量清理 |
| 人工摘要 | `reports/pipeline-summary.md` | 唯一人工质量报告；适用于每轮流水线，不是 Smoke 专属报告 |
| Quality 根 | 默认 `reports/quality/`，可由 `QUALITY_OUTPUT_DIR` 改写 | 机器事实根目录 |
| Quality P0 | `run.json`、`shards/*.jsonl`、`merged/manifest.json`、`merged/*.jsonl` | 运行、Case、请求、失败和完整性事实 |
| Semantic | `reports/quality/semantic/merged/manifest.json`、`*.jsonl` | 操作、请求组和轮询会话事实 |
| Metrics | `reports/quality/metrics/manifest.json`、`run-metrics.json` | 请求成功率、耗时等可信聚合输入 |
| Flaky | `reports/quality/flaky-import.json`、`flaky-evaluation.json`；SQLite 位于 Job 外部配置路径 | 历史导入、状态迁移和治理证据 |

Jenkins 当前归档 `allure-results/**, reports/**`，发布框架/接口 JUnit，并通过 Allure 插件展示 `allure-results`。这些路径在 P0/P1 内部重构中必须保持；不得再增加第二份人工质量报告。

## 8. 环境变量合同

| 变量 | 合同 |
| --- | --- |
| `GENERATE_PIPELINE_SUMMARY` | 控制每轮流水线是否生成执行摘要；Jenkins 参数/进程环境优先于 `.env`，默认开启 |
| `QUALITY_ENABLE` | Quality 总开关；关闭时不应改变业务执行与 pytest 退出码 |
| `QUALITY_SEMANTIC_ENABLE` | 仅在 Quality 开启时启用语义事实 |
| `QUALITY_METRICS_ENABLE` | 依赖 Quality 与 Semantic；配置无效时按现有 fail-open 警告 |
| `QUALITY_FLAKY_HISTORY_ENABLE` | 控制可信历史导入 |
| `QUALITY_FLAKY_STATE_ENABLE` | 依赖 Flaky history，控制状态评估 |
| `QUALITY_FLAKY_DB_PATH` | 外部持久 SQLite 绝对路径，不改为仓库内运行产物 |
| `QUALITY_RUN_ID`、`QUALITY_EXECUTION_ID`、`QUALITY_OUTPUT_DIR` | 运行身份、池身份和产物根路径；Runner 临时注入后恢复外部环境 |

## 9. 允许内部重构的范围

- `pytest_execution.py` 成为 pytest 收集与执行的唯一所有者；
- `scheduling.py` 拥有纯分池算法；
- `master_service.py` 保留稳定入口并兼容委托；
- 各池可写独立临时 Allure 原始目录，结束后合并并只生成一次报告；
- BaseRequest、BaseTask、Quality Pipeline 可拆窄职责内部对象；
- 下载器、配置校验器和 Artifact 校验器可在行为测试保护下去重。

上述变化必须同时满足：公共签名不消失、类型身份不改变、退出码不失真、默认与自定义路径不变、异常时机不前移或后移到消费者可见的位置。

## 10. P0/P1 变更门禁

每项后续修改至少回答四个问题：

1. 修改映射到本清单哪一项强兼容合同？
2. 对应 strict xfail 是否转为正常测试，而不是删除？
3. pytest 原始事实、JUnit、Allure、Summary 和 Jenkins 的优先级是否仍正确？
4. 四件套类身份、CLI 和产物路径是否保持？

如果无法回答，说明变更仍跨越多个约束，应继续拆小，而不是扩大阶段范围。
