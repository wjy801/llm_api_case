# P0 与 P1 质量工程后续开发方向

## 1. 文档定位

本文只规划当前框架后续的 P0、P1 建设，不展开 MR 精准选测、覆盖矩阵、自动生成测试数据或智能审查。

结合仓库现状，后续工作的主线不是再增加一套测试报告，而是把已经存在的 Jenkins、JUnit、Allure、请求中间件、重试与轮询记录连接成一条可信的质量数据链路：

```text
测试执行
-> 结构化采集
-> 结果聚合
-> 失败归因
-> 历史基线
-> Flaky 治理
-> 质量门禁
-> 治理反馈
```

推荐阶段定义：

| 阶段 | 阶段名称 | 需要回答的问题 | 核心产出 |
| --- | --- | --- | --- |
| P0 | 质量数据底座 | 发生了什么，数据是否完整、可追溯 | 统一数据模型、结果聚合、失败分类、基础报告、原始指标、观察性门禁 |
| P1 | 质量信号可信化 | 结果是否值得相信，是否应阻止交付 | Flaky 治理、真实接口基线、成本/耗时/稳定性指标、分级门禁 |

## 2. 需求理解

P0 和 P1 需要覆盖原始方向中的四类能力：

1. 质量结果聚合和失败分类。
2. Flaky 识别、隔离、修复和恢复。
3. 真实接口成本、耗时、稳定性度量。
4. 可解释、可降级、可审计的质量门禁报告。

这些能力不能平行堆叠。失败分类依赖统一结果，Flaky 判断依赖可比较的历史结果，门禁依赖可信分类和稳定基线。因此必须按依赖顺序开发。

## 3. 第一性原理与因果链

质量工程的最终目标不是生成更多图表，而是：

> 用可信、及时、可行动的证据，以尽可能低的误判成本阻止高风险变更进入下游。

当前主要障碍及因果链如下。

### 3.1 标识和口径不统一

```text
用例、接口、执行批次缺少稳定标识
-> JUnit、Allure、请求日志无法可靠关联
-> 同一失败被重复统计或错误合并
-> 趋势和基线失真
-> Flaky 与门禁判断不可信
```

真正要解决的问题不是“解析更多报告”，而是先建立跨报告一致的数据身份与统计口径。

### 3.2 重试结果掩盖首次失败

```text
只记录最终通过
-> 首次失败证据消失
-> 瞬态问题看起来像稳定通过
-> 稳定性被高估
-> 门禁持续放过正在恶化的接口
```

因此必须同时保留原始结果、每次尝试和最终结果。`首次通过`、`重试后通过`、`最终失败`是三种不同质量信号。

### 3.3 失败没有可治理的归因

```text
所有失败都计为产品失败
-> 环境、数据、框架和产品问题混在一起
-> 门禁误拦增加
-> 团队开始人工绕过门禁
-> 门禁失去公信力
```

失败分类不是为了降低失败数，而是把失败路由给正确责任方。原始失败状态不可被分类结果覆盖。

### 3.4 没有历史基线就设置阈值

```text
先拍脑袋设置成功率或 P95 阈值
-> 不同接口、模型和环境被同一尺度衡量
-> 正常波动频繁触发告警
-> 告警疲劳和人工豁免增加
-> 强制门禁被架空
```

因此先采集，再观察，再形成基线，最后启用强制门禁。

### 3.5 成本口径混淆

```text
Token 或媒体用量直接乘单价
-> 估算成本被当成实际账单
-> 价格版本、折扣、失败退款等差异被忽略
-> 成本结论不可信
```

成本必须分为“账单实扣”和“规则估算”，并记录价格版本与计算依据。

## 4. TOC 约束与决策

当前系统的核心约束是质量数据可信度，而不是报告展示能力。

仓库已经具备：

- Jenkins 执行框架单测、Smoke 收集和可选真实 Smoke。
- JUnit 结果、Allure 原始结果与构建产物归档。
- 构建结果邮件及报告入口。
- 请求中间件、请求/响应耗时日志、重试记录与轮询状态迁移。
- 并行和串行用例执行基础。

当前缺口是：

- 缺少统一且版本化的结构化质量事件。
- 缺少跨构建历史数据和稳定身份。
- 缺少失败分类、失败指纹与证据完整度定义。
- 缺少 Flaky 状态机和治理闭环。
- 缺少按接口、模型、环境分组的真实指标基线。
- 缺少独立于 Jenkins 构建状态的可解释门禁判定。

基于 TOC，开发资源应集中在“可信数据链路”，而不是先建设大屏、复杂规则平台或 AI 自动归因。

## 5. 总体设计原则

### 5.1 原始事实与派生结论分离

- 原始事实：执行结果、请求耗时、状态码、异常、尝试次数、用量、账单记录。
- 派生结论：失败分类、失败指纹、Flaky 状态、基线、异常判断、门禁结论。
- 派生算法升级时，原始事实仍可重新计算。

### 5.2 统一标识先于统计

至少定义以下稳定标识：

| 标识 | 含义 | 建议来源 |
| --- | --- | --- |
| `run_id` | 一次测试运行 | Jenkins Job、构建号和运行 UUID |
| `case_id` | 稳定用例身份 | 规范化后的 pytest nodeid，不包含动态执行值 |
| `invocation_id` | 一次用例调用 | `run_id + case_id + 参数摘要` |
| `request_id` | 一次业务请求 | 服务端 request id；缺失时生成客户端关联 id |
| `interface_id` | 稳定接口身份 | HTTP 方法、模板化路径和协议类型 |
| `attempt_index` | 当前请求尝试序号 | 首次为 1，重试依次递增 |
| `schema_version` | 数据契约版本 | 所有结构化产物显式携带 |

参数摘要只能使用脱敏后的稳定哈希，不能将密钥、完整请求体或用户数据写入标识。

### 5.3 三层结果语义

每个用例至少保留：

- `raw_status`：首次执行的原始状态。
- `attempts`：所有执行或请求尝试及证据。
- `final_status`：策略执行后的最终状态。

`retry_passed` 必须独立展示，不得合并进普通通过率。

### 5.4 采集不掩盖测试结果

- P0 采集异常不能覆盖真实测试异常，应标记 `data_incomplete` 并保留原因。
- P1 强制门禁启用后，关键数据缺失不能被解释为通过，应进入 `NO_DATA` 或 `DEGRADED`。
- 数据缺失是否阻断，由环境和门禁级别决定，并留下审计记录。

### 5.5 控制敏感信息与指标基数

- 不采集 API Key、Authorization、Cookie、完整请求体和完整响应体。
- 模型、接口模板、环境、场景可以作为指标维度；request id、原始 URL、异常全文不能作为聚合标签。
- 证据明细继续保存在受控 Allure/归档中，聚合数据只保存脱敏摘要和证据链接。

## 6. P0：质量数据底座

### 6.1 P0 目标

P0 完成后，任意一次 CI 运行都应能稳定回答：

- 本次执行了哪些用例和真实接口？
- 原始结果、最终结果和重试结果分别是什么？
- 失败大致属于哪一类，证据是否完整？
- 哪些接口在耗时、错误、重试和用量上出现异常？
- 如果当前规则生效，门禁会作出什么判断？

P0 只做观察性门禁，不因为新规则改变流水线退出码。

### 6.2 P0.0：冻结质量数据契约

先定义版本化模型，不直接从 Allure 页面反向抓取业务数据。建议至少包括：

- `RunRecord`：构建、分支、提交、环境、开始/结束时间、执行器版本、完整性状态。
- `CaseResult`：用例身份、参数摘要、原始/最终状态、阶段、耗时、失败指纹、证据引用。
- `RequestMetric`：接口、模型、协议、状态码、业务状态、耗时、重试、用量、账单信息。
- `FailureRecord`：失败分类、错误类型、规范化消息、责任域、置信度、首次失败证据。
- `GateDecision`：规则、实际值、阈值、样本量、结论、豁免和证据。

统一枚举，避免使用自由文本作为核心统计字段。

### 6.3 P0.1：结构化采集

采集点分为两层：

1. pytest 层采集 collection、setup、call、teardown、skip、xfail、错误和用例耗时。
2. 请求中间件层采集 HTTP、SSE、异步轮询、重试、服务端 request id 和用量。

第一版建议生成机器可读产物：

```text
reports/quality/
  run.json
  case-results.jsonl
  request-metrics.jsonl
  summary.json
  gate-report.json
  gate-report.md
```

JSONL 便于并行 worker 分片写入，主进程结束时再去重、校验和合并。每个产物都包含 `schema_version`。

需要优先复用现有 `RequestContext` 和请求中间件，不在业务用例中散落埋点代码。

### 6.4 P0.2：结果聚合

聚合应提供四层视图：

| 层级 | 关注内容 |
| --- | --- |
| 运行级 | 总数、通过、失败、错误、跳过、重试后通过、数据完整度 |
| 用例级 | 原始/最终结果、失败阶段、历史身份、证据入口 |
| 接口级 | 请求量、业务成功率、状态码、耗时、重试率、超时率 |
| 维度级 | 环境、模型、协议、场景、分支，不使用高基数字段 |

统计口径需要明确：

- 测试通过率与接口请求成功率分开。
- HTTP 2xx 与业务成功分开。
- 首次通过率与最终通过率分开。
- 用例耗时、单次请求耗时、异步任务完成耗时分开。
- 样本量不足时不输出具有误导性的 P95/P99 结论。

### 6.5 P0.3：失败分类与失败指纹

第一版采用确定性规则，分类建议为：

| 分类 | 典型证据 |
| --- | --- |
| `PRODUCT_DEFECT` | 稳定可复现的业务错误、契约不符、错误结果 |
| `TEST_DEFECT` | 断言或测试数据错误、过期预期、清理逻辑错误 |
| `FRAMEWORK_DEFECT` | 框架异常、插件错误、采集或公共能力缺陷 |
| `ENVIRONMENT` | DNS、网络、依赖服务、资源不足、环境不可用 |
| `CONFIGURATION` | 必填配置、权限、密钥、路由或环境选择错误 |
| `TRANSIENT` | 限流、偶发超时、明确可恢复的临时错误 |
| `UNKNOWN` | 证据不足或规则无法判断，必须进入待治理列表 |

失败指纹建议由以下规范化字段生成：

```text
失败阶段 + 异常类型 + 规范化消息 + 接口模板 + 断言位置
```

动态 id、时间戳、URL 查询参数、内存地址和敏感值必须在生成指纹前清除。分类记录需要同时保存规则版本、置信度和人工修正结果。

### 6.6 P0.4：基础报告与观察性门禁

报告首页只回答有行动价值的问题：

- 本次质量结论及数据完整性。
- 新增失败、持续失败、重试后通过和未知失败。
- 最慢接口、错误最多接口、重试最多接口。
- 各规则的实际值、阈值、样本量和证据入口。

观察性门禁只生成 `PASS`、`WARN`、`BLOCK`、`NO_DATA` 结论，不改变构建状态。持续观察误判、漏判和数据缺失后，再进入 P1。

P0 不建议先做独立大屏。优先把 JSON、Markdown 摘要接入现有 Jenkins 构建产物和邮件入口。

### 6.7 P0 验收标准

- 串行、并行和并串混合执行均无重复、丢失或串写数据。
- 同一用例、接口在不同构建中得到稳定身份。
- 首次失败、重试过程和最终结果可以分别查询。
- 所有失败都有分类；无法判断的失败显式归入 `UNKNOWN`。
- JUnit、Allure 与结构化产物可通过 `run_id`、`case_id` 关联。
- 汇总数与 JUnit 原始结果一致，差异会导致完整性检查失败。
- 报告和产物通过脱敏测试，不包含密钥及完整敏感载荷。
- 观察性门禁至少稳定运行一个基线窗口，并记录规则命中与人工复核结果。

## 7. P1：质量信号可信化与门禁治理

### 7.1 P1 目标

P1 完成后，系统应能回答：

- 当前失败是新缺陷、持续失败还是不稳定失败？
- 接口稳定性、耗时和成本相对自己的历史基线是否退化？
- 证据是否足以阻断交付？
- 被隔离或豁免的问题由谁负责，何时恢复？

### 7.2 P1.0：历史存储与基线窗口

跨构建治理不能依赖单次 Jenkins Artifact。第一版可以选择轻量历史存储，但必须抽象存储接口：

- 单 Job、单执行器验证阶段可使用 SQLite。
- 多 Job、多执行器或并发写入阶段迁移到 PostgreSQL 等共享存储。
- 原始大附件仍留在 Jenkins/Allure，历史库只存索引、摘要和指标。

历史记录至少按环境、接口、模型、协议和场景隔离。不同环境的数据不能直接混为一个基线。

### 7.3 P1.1：Flaky 识别与治理

Flaky 的定义应是：在代码、配置和环境等关键条件等价时，同一用例或失败指纹出现非确定性结果。

不能仅因“重试后通过”就直接判定为 Flaky。建议状态机：

```text
STABLE
-> SUSPECTED
-> CONFIRMED
-> QUARANTINED
-> RECOVERING
-> STABLE
```

状态迁移由历史样本数、失败/通过交替、重试后通过率、失败指纹一致性和人工复核共同决定。阈值通过配置管理，在基线观察后确定，不写死在业务用例中。

治理规则：

- 永远保留首次失败证据。
- 只对明确瞬态错误执行受控重试，不做全量无差别重跑。
- 隔离只改变执行分组或门禁权重，不把失败改写为通过。
- 隔离必须包含责任人、原因、创建时间和到期时间。
- 到期未处理自动升级提醒；连续稳定达到恢复窗口后才能解除隔离。
- 输出新增 Flaky、存量 Flaky、恢复项和超期项，而不是只做排行榜。

### 7.4 P1.2：真实接口成本指标

成本分两级：

1. 实际成本：来自账单、余额或用量结算接口，以服务端 request id 对账。
2. 估算成本：来自 Token、媒体时长、分辨率、图片数量等用量乘以带版本的价格规则。

建议指标：

- 单请求、单用例、单模型、单构建的实际/估算成本。
- 输入 Token、输出 Token、缓存 Token及其他计费单位。
- 成功请求成本、失败请求成本、重试额外成本。
- 成本均值、总量和相对历史基线变化。
- 对账覆盖率以及估算与实扣差异。

所有成本记录统一按人民币口径记录，必须携带价格版本、计费来源和结算状态。没有账单证据时只能展示为估算。

### 7.5 P1.3：真实接口耗时指标

不同协议使用不同耗时语义：

- 普通 HTTP：端到端耗时、服务端响应耗时。
- SSE：首 Token 延迟、chunk 间隔、流式总耗时。
- 异步任务：排队耗时、执行耗时、总完成耗时、轮询开销。
- 重试请求：首次尝试耗时、重试等待、最终总耗时。

聚合输出 P50、P95；只有样本量和业务价值足够时再输出 P99。超时失败要计入稳定性和超时率，不能从耗时样本中静默删除。

### 7.6 P1.4：真实接口稳定性指标

建议至少包含：

- 首次请求成功率、最终请求成功率、业务成功率。
- 测试首次通过率、最终通过率。
- 超时率、重试率、重试挽救率。
- 4xx、429、5xx 和业务错误码分布。
- 连续失败次数、失败指纹复现次数。
- Flaky 率、隔离数量、平均修复时间。
- 数据完整率、对账覆盖率。

稳定性结论必须同时给出样本量和窗口，禁止只展示百分比。

### 7.7 P1.5：基线与异常判断

门禁同时支持三种规则：

- 绝对规则：例如出现确定的契约破坏或高危业务失败。
- 相对规则：相对同接口、同环境历史基线发生显著退化。
- 完整性规则：关键数据或证据缺失，无法作出可信判断。

基线需要处理冷启动、小样本和自然波动：

- 样本不足返回 `NO_DATA`，不伪造趋势。
- 按接口类型、模型和环境分别建立基线。
- 基线窗口与算法版本可配置、可追溯。
- 大版本或环境变更可以显式重建基线，不能静默清零。

### 7.8 P1.6：渐进式质量门禁

门禁按以下顺序启用：

```text
影子观察
-> 告警但不阻断
-> 只阻断确定性高风险问题
-> 扩大强制规则范围
```

每条门禁结论必须说明：

- 规则名称和版本。
- 统计对象、窗口和样本量。
- 实际值、基线或阈值。
- 判定结果和置信度。
- 失败分类、证据链接和建议责任方。
- 豁免人、豁免原因和到期时间。

分类不应直接把构建失败变成成功。门禁是现有测试退出码之外的补充判定：确定性测试失败仍按原始结果处理；环境异常、Flaky、性能或成本退化由分级规则决定 `WARN`、`BLOCK` 或 `DEGRADED`。

### 7.9 P1 验收标准

- 可以按稳定 `case_id` 查询跨构建历史和状态迁移。
- Flaky 判断有样本、规则版本和证据，不由单次重试武断决定。
- 隔离、豁免都有责任人和有效期，过期可被识别。
- 真实接口指标按环境、接口、模型隔离，统计口径经过自动化测试。
- 成本明确区分实扣与估算，并能按 request id 检查对账覆盖率。
- 门禁从影子模式积累了误判、漏判和人工复核记录。
- 强制规则启用前通过回放验证，并提供开关和降级路径。
- 门禁报告能够解释“为什么拦、证据在哪、由谁处理”。

## 8. 推荐开发顺序

| 迭代 | 主要工作 | 依赖 | 完成标志 |
| --- | --- | --- | --- |
| 1 | 数据字典、稳定标识、Schema 和结果语义 | 无 | 契约评审通过并有序列化/兼容测试 |
| 2 | pytest 与请求中间件结构化采集 | 迭代 1 | 串行、并行均生成完整 JSON/JSONL |
| 3 | 聚合、完整性校验、失败分类与指纹 | 迭代 2 | 汇总可与 JUnit 对账，失败全部可路由 |
| 4 | 基础报告与观察性门禁 | 迭代 3 | Jenkins 归档并连续积累门禁回放结果 |
| 5 | 历史存储与 Flaky 状态机 | 迭代 3 | 可跨构建查询、隔离和恢复 |
| 6 | 成本、耗时、稳定性基线 | 迭代 4、5 | 指标按维度形成可信基线 |
| 7 | 告警门禁与强制门禁 | 迭代 5、6 | 高置信规则可阻断，豁免和降级可审计 |

前四个迭代属于 P0，后三个迭代属于 P1。不得为了提前展示门禁而跳过数据契约、完整性校验和观察期。

## 9. 建议代码边界

后续实现时可新增独立 `quality` 包，避免把治理逻辑塞进 Jenkinsfile 或业务用例：

```text
quality/
  models.py          # 版本化数据模型与枚举
  collector.py       # 运行、用例、请求事件收集
  pytest_plugin.py   # pytest 生命周期适配
  classifier.py      # 失败分类与指纹
  aggregator.py      # 聚合和完整性校验
  storage.py         # JSONL/历史存储抽象
  flaky.py           # Flaky 状态机
  baseline.py        # 历史基线与异常判断
  gate.py            # 门禁规则与决策
  report.py          # JSON/Markdown 报告
```

现有模块的职责保持：

- `common/request_middleware.py` 只提供请求生命周期扩展点。
- `common/request_context.py` 传递请求级上下文和关联标识。
- `Jenkinsfile` 只负责执行、归档、发布和读取最终门禁退出码。
- Allure 保存详细证据，质量模块保存结构化事实和治理结论。
- 业务测试只声明必要元数据，不自行实现统计、历史查询或门禁。

## 10. 暂不纳入 P0/P1

- MR 变更影响分析与精准选测。
- 代码、接口、契约、用例覆盖矩阵。
- 自动生成测试数据或测试用例。
- AI 自动失败归因和智能审查。
- 独立质量大屏、复杂规则编排平台。
- 替代专业压测平台的高并发性能测试。

这些方向依赖可信质量数据，但不是当前约束。P0/P1 稳定后再评估，避免同时建设数据层、算法层和平台层造成范围失控。

## 11. 启动检查清单

进入编码前应先完成：

- 明确 P0 首批接入的真实 Smoke 范围和执行频率。
- 确认 `case_id`、`interface_id` 和环境标识规则。
- 确认实际账单接口能否通过 request id 对账。
- 确认 Jenkins 构建保留周期和历史存储方案。
- 选取一批历史失败样本，制定第一版分类规则和回放集。
- 约定失败分类、隔离、豁免和门禁规则的责任人。
- 约定观察期结束和强制门禁启用的评审条件。

这份清单未完成前，可以开发数据模型和本地采集，但不应承诺强制门禁上线日期。
