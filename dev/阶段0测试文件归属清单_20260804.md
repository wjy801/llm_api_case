## 1. 需求理解与约束

阶段 0 要恢复的不是“当前机器能跑”的表象，而是 clean checkout 可以复现的测试事实：

```text
Git 管理的文件集合唯一
-> pytest 可发现的框架测试集合唯一
-> fixture 字节在不同平台一致
-> 离线回归结果才可作为 P0/P1 重构基线
```

当前 TOC 约束是测试文件曾由 `.gitignore` 白名单控制。本地未跟踪测试会参与 pytest，却不会出现在新检出仓库中，因此必须逐文件决定纳管、合并或排除，不能批量加入 Git。

本轮保持以下边界：

- 保留 Runner 统一预收集，为后续分布式执行保留同一计划语义；
- 保留 Request、Task、Assertions、Decorators 四件套强制创建规范；
- 不处理流式输出/SSE，不恢复已删除的流式账单用例；
- 不处理密钥问题，不执行真实接口、真实等待或付费调用；
- 不覆盖 `module/smoke/test_call_billing_correctness.py` 中用户已做的删除；
- `module/test/` 继续视为本机实验目录，不在阶段 0 自动纳管。

## 6. 后续纳管规则

1. 新增业务模块时，四件套文件和真实类必须同时创建；薄类允许，但不能用改变类身份的别名替代。
2. 新增框架测试直接放入 `tests/`，不得重新引入逐文件白名单。
3. 新测试先证明离线、确定性和独有覆盖，再单文件纳管。
4. 本机实验放在明确的实验目录，不得让默认 `pytest tests` 收集到“忽略但会执行”的副本。
5. 测试数量变化不构成失败；集合可追溯、无重复 nodeid、分池互斥且并集守恒才是合同。
