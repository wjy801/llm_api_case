# P0 迭代一：契约与身份开发思路

## 1. 需求复述

本文件基于 `P0质量数据底座详细开发方案.md`，只展开 P0 迭代一“契约与身份”的开发思路。

迭代一不接入 pytest 生命周期，不接入请求中间件，不改 Jenkins，不做归并、分类、报告和门禁。它只解决后续所有质量数据能力的地基问题：

```text
稳定数据契约
-> 稳定身份规则
-> 运行上下文传递
-> 安全脱敏与哈希
-> 原子写入基础
-> 单元测试锁定契约
```

## 2. 第一性原理判断

P0 的最终目标是形成可信质量事实链。可信事实链的第一块不是采集器，而是“事实如何被命名、表达和校验”。

如果迭代一没有把数据契约和身份规则定住，后续会出现连锁问题：

```text
模型字段随意变化
-> 采集端和归并端理解不一致
-> 历史产物无法兼容
-> 报告和门禁口径漂移
-> P1 基线和 Flaky 治理失真
```

```text
case_id / interface_id 不稳定
-> 同一用例或接口跨构建无法对齐
-> 趋势、失败复现、Flaky 判断失去对象
-> 只能按文本和人工经验排查
-> 质量工程退回日志检索
```

所以迭代一的本质是冻结“质量事实的语言”。后续采集、归并、分类和门禁都只能基于这套语言继续扩展。

## 3. TOC 约束分析

当前约束不是缺少 hook，也不是缺少报告，而是缺少稳定可复用的数据底座。

| 约束点 | 如果不解决 | 迭代一决策 |
| --- | --- | --- |
| 数据契约不稳定 | 后续每个模块都要猜字段含义 | 先用 Pydantic v2 定义版本化模型 |
| 身份规则不稳定 | 跨构建无法对齐用例和接口 | 先实现确定性 ID 工具并用测试锁定 |
| 请求归属缺口 | P0.2 接入请求后无法关联用例 | 先提供 `contextvars` 上下文，不接入业务链路 |
| 脱敏边界不清 | 一接入采集就有泄露风险 | 先实现默认拒绝敏感字段的 redaction 工具 |
| 写入语义不清 | 分片采集阶段可能覆盖或写坏文件 | 先实现 JSON/JSONL writer 基础能力 |

资源应集中在模型、ID、上下文和安全边界，不提前做 pytest 插件和 Jenkins 集成。

## 4. 本迭代范围

### 4.1 做什么

- 新增独立 `quality` 包。
- 新增 P0 v1 数据模型和枚举。
- 新增稳定 ID 生成工具。
- 新增参数摘要、路径模板化、失败指纹规范化工具。
- 新增 `contextvars` 运行上下文。
- 新增 JSON/JSONL 原子写入基础能力。
- 新增脱敏工具或复用现有 `util.redaction` 封装质量侧红线。
- 新增单元测试，锁定模型序列化、ID 稳定性、上下文隔离、脱敏和 writer 行为。

### 4.2 不做什么

- 不注册 pytest 插件。
- 不修改 `module/conftest.py`。
- 不修改 `common/request_context.py` 和 `common/request_middleware.py`。
- 不修改 `run_master.py`。
- 不生成真实 `reports/quality` 产物。
- 不接入 Jenkins。
- 不实现归并、失败分类、报告、门禁。

迭代一必须保持零运行时影响。只有被测试或后续代码显式 import 时才生效。

## 5. 推荐文件结构

```text
quality/
  __init__.py
  models.py
  identifiers.py
  runtime_context.py
  storage.py

tests/
  quality/
    test_quality_models.py
    test_quality_identifiers.py
    test_quality_runtime_context.py
    test_quality_storage.py
```

可选新增：

```text
quality/
  redaction.py
```

如果现有 `util.redaction` 已能覆盖质量侧需求，则 `quality/redaction.py` 只做薄封装，不重复造规则。

## 6. 技术选型

仓库已在 `config.py`、`common/retry.py`、`common/polling.py` 使用 Pydantic v2，并且 `requirements.txt` 已包含 `pydantic>=2.0.0`。

因此迭代一建议：

- 数据契约使用 Pydantic v2 `BaseModel`。
- 模型配置使用 `ConfigDict(frozen=True)`，降低运行中被误改的风险。
- 枚举使用 `str, Enum`，保证 JSON 输出是稳定字符串。
- 时间字段使用 timezone-aware `datetime`，序列化为 ISO 8601。
- ID 和摘要使用标准库 `hashlib`、`uuid`、`re`、`urllib.parse`。
- 上下文使用标准库 `contextvars`。
- 写入使用标准库 `pathlib`、`json`、`tempfile`、`os.replace`。

不引入新依赖。

## 7. 数据模型开发思路

### 7.1 基础常量与枚举

在 `quality/models.py` 定义：

```text
SCHEMA_VERSION = "quality.v1"
```

建议枚举：

| 枚举 | 值 |
| --- | --- |
| `RunStatus` | `finished`、`interrupted`、`partial` |
| `IntegrityStatus` | `complete`、`degraded`、`failed` |
| `CaseStatus` | `passed`、`failed`、`skipped`、`error`、`xfailed`、`xpassed` |
| `CasePhase` | `collection`、`setup`、`call`、`teardown` |
| `Protocol` | `http`、`sse`、`polling` |
| `BusinessStatus` | `success`、`failed`、`unknown` |
| `FailureCategory` | `PRODUCT_DEFECT`、`TEST_DEFECT`、`FRAMEWORK_DEFECT`、`ENVIRONMENT`、`CONFIGURATION`、`TRANSIENT`、`UNKNOWN` |
| `OwnerDomain` | `product`、`test`、`framework`、`environment`、`configuration`、`unknown` |
| `Confidence` | `high`、`medium`、`low` |
| `GateMode` | `shadow` |
| `GateResult` | `PASS`、`WARN`、`BLOCK`、`NO_DATA` |
| `IssueSeverity` | `info`、`warn`、`error` |

### 7.2 Pydantic 模型

迭代一先定义模型，不要求采集端真实填充全部字段。

建议模型：

- `RunRecord`
- `CaseResult`
- `RequestUsage`
- `RequestCost`
- `RequestMetric`
- `FailureFingerprintSource`
- `FailureRecord`
- `QualitySummary`
- `GateRuleDecision`
- `GateDecision`
- `IntegrityIssue`

建模原则：

- 字段名与 P0 详细方案保持一致。
- `schema_version` 默认填充 `quality.v1`。
- 所有模型支持 `model_dump(mode="json")`。
- 可空字段必须显式标注 `None`，不能让调用方猜默认语义。
- 高风险字段不进入模型，例如完整 header、完整请求体、完整响应体。
- 证据字段只放路径、request id、摘要或引用，不放敏感载荷。

### 7.3 关键校验

第一版只做低争议校验：

- `attempt_index >= 1`。
- `duration_ms >= 0`。
- `sample_size >= 0`。
- `run_id`、`case_id`、`invocation_id`、`request_event_id` 不能为空。
- `method` 统一大写。
- `interface_id` 不能为空。
- `cost.source=none` 时 `amount/price_version` 允许为空；成本统一按人民币口径记录，不设计 `currency` 字段。

`sample_size` 用来记录某条规则或统计结论实际基于多少样本。它的作用是防止小样本误判：例如 1 次请求里有 1 次超时，超时率是 100%，但这个结果不足以证明接口整体不稳定。后续门禁应在 `sample_size` 低于最小样本量时输出 `NO_DATA` 或观察性 `WARN`，而不是直接 `BLOCK`。

不要在迭代一加入复杂业务校验。业务语义应留给采集、归并和门禁阶段。

## 8. 身份与哈希开发思路

### 8.1 run_id

函数建议：

```text
build_run_id(job_name, build_number, timestamp, random_uuid) -> str
```

规则：

- Jenkins 场景优先使用 job name 和 build number。
- 本地场景使用 `local-{timestamp}-{uuid_short}`。
- 输出只包含安全字符：字母、数字、点、下划线、中划线。
- run_id 不追求跨构建稳定，它表示一次父级运行。

### 8.2 execution_id

函数建议：

```text
build_execution_id(stage_name, index) -> str
```

规则：

- 示例：`parallel-pool-1`、`serial-pool-1`、`manual-pytest-1`。
- 只在一次 run 内唯一。

### 8.3 case_id

函数建议：

```text
normalize_nodeid(nodeid) -> NormalizedNodeId
build_case_id(nodeid) -> str
```

规则：

- 保留测试文件路径、类名、函数名。
- 去除 pytest 参数段中的动态值。
- Windows 路径统一为 `/`。
- 连续空白压缩。
- 输出不包含 API Key、token、完整 payload。

示例：

```text
module/test_x.py::TestA::test_case[user-123-token-abc]
-> module/test_x.py::TestA::test_case
```

注意：如果项目已有显式 pytest param id，比如 `case_id`，后续迭代可以纳入参数摘要，但 `case_id` 本身仍应代表稳定测试定义，不代表某次参数调用。

### 8.4 param_hash

函数建议：

```text
build_param_hash(value) -> str
```

规则：

- 先脱敏，再 JSON canonical dump，再 sha256 截断。
- 不可序列化对象转为稳定类型名和脱敏 repr。
- 默认截断 12 到 16 位即可，完整 hash 可按需保留。

### 8.5 invocation_id

函数建议：

```text
build_invocation_id(run_id, case_id, param_hash) -> str
```

规则：

- invocation_id 表示一次 run 内某个用例参数调用。
- 不要求跨构建稳定。
- 同一 run 内不同参数必须可区分。

### 8.6 request_event_id

函数建议：

```text
new_request_event_id() -> str
```

规则：

- 使用 UUID4。
- 每一次 request attempt 独立生成。

### 8.7 interface_id

函数建议：

```text
build_interface_id(method, url_or_path, protocol="http") -> str
```

规则：

- method 大写。
- path 去 query。
- 多余斜杠规范化。
- 动态路径段模板化。
- protocol 参与区分 HTTP、SSE、polling。

示例：

```text
POST https://host/v1/tasks/123456?token=abc
-> POST /v1/tasks/{id} http
```

路径模板第一版规则：

- 纯数字段替换为 `{id}`。
- UUID 段替换为 `{uuid}`。
- 过长随机段替换为 `{hash}`。
- query 永远不进入 `interface_id`。

### 8.8 failure_id

函数建议：

```text
build_failure_fingerprint(phase, error_type, message, interface_id=None, assert_location=None) -> str
```

规则：

- 先规范化 message，再 hash。
- 删除 UUID、时间戳、内存地址、URL query、token/key/cookie。
- 输出可读前缀加短 hash，例如 `fail-call-assertionerror-a1b2c3d4e5f6`。

## 9. 运行上下文开发思路

`quality/runtime_context.py` 用 `contextvars` 定义当前质量运行和当前用例。

建议对象：

```text
QualityRunContext
  run_id
  execution_id
  worker_id
  output_dir

QualityCaseContext
  case_id
  invocation_id
  nodeid
  param_hash
```

建议函数：

```text
set_run_context(context)
get_run_context(default=None)
clear_run_context()

set_case_context(context)
get_case_context(default=None)
clear_case_context()
```

原则：

- 不依赖 pytest。
- 不使用模块级普通全局变量保存当前用例。
- clear 必须恢复到无上下文状态，避免串用例。
- 支持嵌套 token 恢复，便于后续 pytest hook 使用。

上下文只负责传递身份，不负责采集写入。

## 10. 存储基础开发思路

`quality/storage.py` 第一版只提供基础能力：

```text
write_json_atomic(path, data)
append_jsonl(path, record)
read_jsonl(path)
ensure_quality_dirs(output_dir)
```

要求：

- `write_json_atomic` 使用临时文件和 `os.replace`。
- `append_jsonl` 每次写入一行合法 JSON。
- 写入前创建父目录。
- 默认 UTF-8。
- Pydantic 模型通过 `model_dump(mode="json")` 转换。
- 不在迭代一实现多进程锁；后续通过单 worker 单分片避免并发写同一文件。

迭代一测试只验证写入格式和原子替换语义，不验证 xdist 并发。

## 11. 脱敏开发思路

质量数据默认只存结构化摘要，不存敏感原文。

建议复用现有 `util.redaction`，质量侧新增更明确的函数：

```text
redact_quality_value(value)
canonicalize_for_hash(value)
sanitize_identifier_part(value)
```

脱敏规则至少覆盖：

- `authorization`
- `cookie`
- `x-api-key`
- `api_key`
- `token`
- `secret`
- `password`
- URL query
- Bearer token
- 长随机串

哈希前必须先脱敏，避免敏感值以 hash 输入形式进入可枚举字典攻击范围。对低熵敏感值，不能只 hash 后保存，应直接替换为固定占位符。

## 12. 测试设计

### 12.1 模型测试

文件：`tests/quality/test_quality_models.py`

覆盖：

- 每个模型能构造并 `model_dump(mode="json")`。
- 枚举输出为稳定字符串。
- `schema_version` 自动填充。
- 非法 `attempt_index`、负耗时、空 ID 会失败。

### 12.2 ID 测试

文件：`tests/quality/test_quality_identifiers.py`

覆盖：

- Windows 路径和 Unix 路径生成同一类稳定 `case_id`。
- 参数段变化不影响 `case_id`。
- 不同参数摘要生成不同 `param_hash`。
- `interface_id` 去 query，并模板化数字、UUID、长随机段。
- failure fingerprint 去除时间戳、UUID、token、内存地址。

### 12.3 上下文测试

文件：`tests/quality/test_quality_runtime_context.py`

覆盖：

- 设置后可读取。
- clear 后读取为空。
- 嵌套设置恢复正确。
- 两个 contextvars 不相互污染。

### 12.4 存储测试

文件：`tests/quality/test_quality_storage.py`

覆盖：

- `write_json_atomic` 生成合法 UTF-8 JSON。
- `append_jsonl` 一行一个 JSON 对象。
- Pydantic 模型可直接写入。
- 父目录不存在时自动创建。

## 13. 开发步骤

建议顺序：

1. 新增 `quality/__init__.py` 和 `quality/models.py`，先让契约可序列化。
2. 新增 `quality/identifiers.py`，实现稳定 ID、规范化和哈希。
3. 新增 `quality/runtime_context.py`，实现 run/case 上下文。
4. 新增 `quality/storage.py`，实现 JSON/JSONL 基础写入。
5. 新增 `tests/quality/` 单元测试。
6. 运行聚焦测试：`python -m pytest tests/quality -q`。
7. 如仓库尚无 `tests` 目录，可先创建；不应把迭代一测试放到业务 `module` 下。

## 14. 验收标准

迭代一完成后应满足：

- 不接入任何现有执行链路，默认运行行为不变。
- `quality` 包可以被 import。
- P0 v1 模型能稳定序列化为 JSON。
- ID 工具对相同输入输出稳定，对动态值输出收敛。
- 参数摘要先脱敏再哈希。
- 上下文设置、读取、清理和嵌套恢复可测。
- JSON/JSONL writer 输出 UTF-8 合法文件。
- 单元测试覆盖模型、ID、上下文、存储和脱敏关键路径。

## 15. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 模型一次设计过重 | 只放 P0 详细方案中的字段，不加入 P1 历史状态 |
| ID 规则过度模板化 | 第一版只处理数字、UUID、长随机段，保留明确路径语义 |
| 脱敏规则遗漏 | 先按 denylist 和 URL query 全量移除，宁可少采集 |
| Pydantic 校验影响运行 | 迭代一不接入运行链路，只在显式调用时生效 |
| writer 被误用成并发写 | 文档和命名明确第一版不提供跨进程锁 |

## 16. 与后续迭代的接口

迭代二会直接复用：

- `models.py`：pytest 插件和请求中间件写入统一模型。
- `identifiers.py`：生成 `case_id`、`invocation_id`、`request_event_id`、`interface_id`。
- `runtime_context.py`：pytest hook 设置当前用例，请求侧读取当前用例。
- `storage.py`：worker 分片写入 JSONL。

因此迭代一的输出不是文档概念，而是后续采集链路的代码契约。这个契约一旦被迭代二使用，就应通过 `schema_version` 管理兼容变化，不能随意改字段含义。
