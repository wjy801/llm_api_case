# CI 接口框架设计缺陷优先级评审

## 1. 评审范围

本评审不展开通用 Web 安全审计，也不处理任何真实密钥或凭证；但框架若要作为学习范本，自动访问外部 URL、下载文件和输出诊断信息所需的安全默认值必须纳入范围。评估维度包括：

- 执行与报告结论的正确性；
- 状态和事实模型的一致性；
- 模块职责及副作用边界；
- 测试体系的可维护性；
- 框架扩展性与运行可复现性；
- 学习路径的可解释性、可实验性和文档一致性；
- 外部资源访问、报告附件和示例配置的安全默认值。

## 2. 第一性原理与核心约束

CI 接口框架本质上是一条确定性的状态管道：

```text
执行计划 -> 实际执行 -> 原始事实 -> 完整性校验 -> 最终结论
```

每一层都必须满足两个基本条件：

1. 身份一致：下游事实可以准确追溯到唯一的运行、执行池和测试用例；
2. 状态单调：失败、部分执行或中断不能在下游重新解释为成功。

作为学习范本，还必须满足第三个条件：

3. 证据闭环：学习者可以在无凭证、无付费调用的环境中复现成功和失败路径，并从产物追溯框架为何得出当前结论。

当前最大的 TOC 约束不是重复代码，而是上述五层没有共享同一个状态和身份模型。该问题会让 Metrics、Flaky、JUnit 和 Pipeline Summary 建立在不稳定的事实基础上。

学习范本的完整主链应为：

```text
干净仓库
-> 确定性安装
-> 零凭证离线执行
-> 可观察的状态与机器事实
-> 可重复的故障注入
-> 与当前代码一致的课程解释
```

因此，“代码能运行”只是必要条件；只有主链可复现、失败语义可解释、课程与实现同步，才能称为学习范本。

## 3. 阶段 0：恢复可信基线并冻结现状

架构重构前必须先恢复现有离线回归，否则后续无法区分“旧缺陷”“重构回归”和“测试自身漂移”。

当前审计快照：

- `python -m pytest tests -q` 在收集阶段失败：`tests/test_protocol_request.py` 仍导入已经不存在的 `PROTOCOL_PROBE_PROMPT`；
- `run_master.py module/smoke --collect-only -q` 正常收集 `41` 项，其中并发池 `15`、串行池 `26`；
- collect-only 只能证明收集和分池，不代表离线回归已经通过。

阶段 0 工作：

1. 修复协议测试与公开 payload builder 的契约漂移；
2. 记录 Python、pytest、插件和依赖版本；
3. 固化当前公开入口、退出码、用例集合和产物 Schema 快照；
4. 为 P0/P1 将要修改的异常路径补充刻画测试，不提前改变行为；
5. 明确所有基线命令都不得访问真实接口或产生付费调用。

阶段 0 验收条件：

- `python -m pytest tests -q` 全部通过且无收集错误；
- Smoke collect-only 保持 `41 / 15 / 26`，或数量变化有明确、可审计的用例变更依据；
- 工作区外部配置、`.env` 和 Jenkins 凭证不是离线回归前置条件；
- 当前已知缺陷都有失败测试或行为快照保护；
- 阶段 0 只恢复可信基线，不混入 P0/P1 架构改造。

## 4. P0：统一执行状态与事实模型

### 4.1 建立唯一的 `RunOutcome`

需要统一表达：

- pytest 原始退出码；
- 并行池和串行池状态；
- 是否完整执行；
- 用例结果；
- 基础设施错误；
- 最终流水线结论。

`RunOutcome` 应是不可变结果对象，而不是把所有维度压缩成单一枚举。pytest 原始退出码、执行状态、完整性状态、用例统计和基础设施异常分别保留，最终流水线结论由纯函数单向派生。这样既保留原始证据，也能保证状态单调。

当前 `run_orchestration/runner.py`、`run_orchestration/pytest_execution.py` 和 Pipeline Reporting 分别解释执行状态，导致退出码和失败语义在层间丢失。

目标约束：

```text
FAILED / INTERRUPTED / PARTIAL
不能被任何 JUnit、collect 或历史产物重新解释为 PASSED
```

### 4.2 建立唯一的 `ExecutionPlan`

当前流程先按测试路径预收集，再把 `-k`、`-m`、`--ignore` 等选择参数交给正式执行。这会产生两个不同的用例集合：

```text
预收集集合 != 实际执行集合
-> expected_case_count 不准确
-> 执行池划分和完整性判断失真
```

应先生成不可变执行计划，并让以下内容全部从该计划派生：

- 最终 nodeid 集合；
- 并行池和串行池；
- expected case count；
- execution ID；
- JUnit 输出目标。

不能把全部 pytest 参数机械传给预收集。应先规范化并分类：

- 选择参数：路径、nodeid、`-k`、`-m`、`--ignore` 等，参与执行计划生成；
- 执行参数：并发、超时和失败策略，由 Runner 消费；
- 产物参数：JUnit、Allure 和日志路径，只影响输出，不改变用例集合。

不支持或无法安全归类的参数必须显式拒绝，不能静默产生不同集合。

### 4.3 完整性失败必须阻断派生计算

当前事实归并返回 `IntegrityStatus.FAILED` 后，Semantic、Metrics 和 Flaky 仍可能继续执行。

正确的数据依赖规则应为：

```text
原始事实不可信
-> 不执行 Semantic、Metrics 计算和 Flaky 历史导入
-> 各阶段仍写入 BLOCKED / NO_DATA 状态与原因
-> Pipeline Summary 展示“被完整性阻断”，而不是“产物缺失”或零值
```

### 4.4 补齐统一身份模型

Case、Request、JUnit 和 Operation 应共享明确的外键链：

```text
run_id
  -> execution_id
    -> invocation_id
      -> case_id
        -> request / request_group / operation
```

当前 Request 事实没有和 Case 做完整外键对账，JUnit 也没有严格核对 `case_id`。身份不可信时，请求成功率、接口耗时、失败分类和 Flaky 历史都无法形成可靠结论。

### 4.5 运行产物必须按 `run_id` 隔离

固定的 `reports/quality` 和 `allure-results` 只能依赖 Jenkins 禁止并发来避免覆盖，不能作为框架自身的不变量。执行计划确定 `run_id` 后，JUnit、Allure、Quality 和 Pipeline Summary 应写入同一运行根目录：

```text
runs/<run_id>/
  junit/
  allure-results/
  quality/
  pipeline-summary.md
```

单次运行完成后再原子更新 `latest` 指针或兼容入口。迁移期间必须保留 Jenkins 归档与用户入口兼容，不能让目录调整破坏现有流水线。

### 4.6 P0 验收条件

- pytest 0～5 原始退出码完整保留，并具有唯一、可逆的执行状态映射；
- 最终流水线结论只由 `RunOutcome` 纯函数派生；
- 任意执行池异常后不会继续产生“完整执行”结论；
- 预收集集合与实际执行集合完全一致；
- 孤立 Case、Request、JUnit 或 Operation 会产生完整性失败；
- `IntegrityStatus.FAILED` 时不执行派生计算和历史导入，但生成可解释的 `BLOCKED/NO_DATA` 阶段状态；
- 同一工作区连续或并发运行不会互相覆盖产物；
- 显式失败状态不能被可解析产物覆盖。

## 5. P1：保留 `BaseRequest` 门面并收紧职责边界

创建请求基类、抽取公共请求方法的方向本身是正确的。`BaseRequest` 应作为框架稳定的公共请求门面，统一承载不同接口都需要遵守的 HTTP 不变量。

当前需要解决的不是 `BaseRequest` 的存在，而是一次请求附带了过多隐藏行为：

```text
发送 HTTP
-> 记录 Quality Operation
-> 生成 Allure 附件
-> 解释轮询业务状态
-> 下载模型结果文件
-> 管理流式生命周期
```

请求基类的第一性原理边界是：抽取稳定、通用、可预期的请求行为，不直接承担具体业务解释，也不让报告和产物副作用改变接口调用结果。

### 5.1 `BaseRequest` 保持稳定公共接口

`BaseRequest` 应负责：

- Session 创建、复用和关闭；
- base URL 拼接；
- 默认请求头及请求级覆盖；
- `request/get/post/put/patch/delete`；
- 默认 timeout；
- 通用重试委托；
- 通用 middleware 执行；
- 返回原始 `requests.Response`。

建议保持简单、稳定的公共接口：

```python
class BaseRequest:
    def request(self, method, path, **kwargs): ...
    def get(self, path, **kwargs): ...
    def post(self, path, **kwargs): ...
    def put(self, path, **kwargs): ...
    def patch(self, path, **kwargs): ...
    def delete(self, path, **kwargs): ...
    def close(self): ...
```

业务请求类继续继承 `BaseRequest`，只封装端点、参数和请求体，不重写底层请求流程：

```python
class SmokeRequest(BaseRequest):
    def create_chat_completion(self, payload):
        return self.post("/v1/chat/completions", json=payload)
```

### 5.2 通过委托复用能力，避免类数量膨胀

现有 `RetryExecutor`、middleware 和 polling policy 可以继续复用。P1 的目标是明确职责边界，不要求把每项职责都拆成新的公开类。

建议关系为：

```text
BaseRequest                  # 稳定公共请求门面
├── Session / URL / Headers
├── HTTP verbs / timeout
├── 委托 RetryExecutor
├── 调用通用 Middleware
└── 可提供无副作用的 poll_get

BaseTask                     # 业务工作流
├── 提供具体 PollingPolicy
├── 解释业务状态和结果
└── 处理端点级任务响应契约

ArtifactCollector            # 报告和产物阶段
└── 独立下载并附加模型结果文件
```

这些名称表达的是职责，可以由现有对象、私有辅助函数或组合对象承担；不应为了形式上的分层制造不必要的公开抽象。

### 5.3 `poll_get` 可以保留，但必须无隐藏副作用

通用轮询属于可复用请求能力，可以继续由 `BaseRequest` 暴露，但应满足：

- 状态规则通过 `PollingPolicy` 由调用方传入；
- 只负责重复 GET、状态转换和截止时间；
- 不理解具体模型或业务字段；
- 不自动下载结果文件；
- 不因 Allure 或附件失败改变响应结果。

轮询应使用显式有限状态机，终态判断优先于结果字段判断：

```text
UNKNOWN -> PENDING -> SUCCESS
                   -> FAILURE
                   -> TIMEOUT
                   -> INTERRUPTED
```

每个响应只能产生一个确定状态；矛盾字段应进入 `UNKNOWN` 或协议错误，而不是依赖字段判断顺序。

轮询总预算必须覆盖请求、重试和等待时间。每次请求的 timeout 应使用剩余预算计算，而不是在请求返回后才检查是否已经超时。

### 5.4 流式响应使用无消费式观察逻辑

SSE 可以继续通过 `BaseRequest` 发起，但不能复用会读取完整响应体的普通日志逻辑。middleware 或观察器只能记录请求信息、状态码、响应头和流结束后的统计，不得为了生成附件提前访问 `response.text`。

流式生命周期必须覆盖完整消费、提前关闭、迭代异常、解码异常和调用方遗忘关闭等路径。无论哪条路径，都只能结束一次 Operation，并保留可解释的完成、失败或中断状态。

### 5.5 下载从请求装饰器中移出

模型结果文件下载属于报告和产物收集，不属于 HTTP 请求成功语义。

应形成两个独立结果：

```text
接口调用结果
产物收集结果
```

附件生成失败不能覆盖已经完成的接口断言结果。

### 5.6 产物下载必须具有安全默认值

把下载移到 `ArtifactCollector` 只解决职责归属，不自动解决安全问题。收集器至少需要：

- 默认只允许明确配置的 `http/https` 来源；
- 校验初始地址和每次重定向，拒绝 loopback、链路本地、私网及其他禁止网段；
- 支持主机 allowlist、连接/读取超时和最大重定向次数；
- 限制单文件大小、总下载大小和并发数；
- 校验 Content-Type，文件名只使用经过清洗的本地名称；
- 下载失败记录为独立产物状态，不改变接口测试结论；
- 所有安全边界使用本地离线测试覆盖，不访问真实外部地址。

### 5.7 Task ID 使用端点级响应契约

通用 `BaseTask` 不应通过 `task_id`、`id`、`request_id` 等别名启发式猜测任务 ID。不同端点应定义各自的响应模型和提取规则，并在提取前验证 HTTP 状态及响应结构。

### 5.8 P1 请求层验收条件

- `BaseRequest` 继续作为所有请求类的公共基类；
- 子类只新增端点方法，不复制 Session、Headers、timeout 和 HTTP verbs；
- 重试、middleware 和轮询通过委托复用，不依赖子类重写请求主流程；
- `request()` 返回原始响应，不自动解释业务结果或下载文件；
- SSE 日志不会消费响应流，提前关闭和迭代异常只结束一次生命周期；
- 未经过显式下载策略的外部 URL 不会被自动访问；
- 报告、附件或下载失败不会改变接口调用结论。

## 6. P1：重新划分测试层与编排层

### 6.1 业务服务层不得调用 `pytest.skip`

`BaseTask` 是业务操作封装，不应依赖 pytest 控制流。否则相同代码无法稳定复用于 CLI、脚本或其他测试框架。

配置检查、跳过和失败策略应位于 Runner 或 fixture 层。

### 6.2 明确测试层级与执行属性

“业务模块”和“测试类型”是两个正交维度，不能全部压入同一目录层级。建议划分为：

```text
tests/
  unit/                 # 单对象、纯函数和离线状态机
  integration/          # 多组件协作，使用本地可控依赖

module/<业务模块>/      # 真实业务和协议用例，继续按领域组织

markers:
  live                  # 会访问真实服务
  protocol              # 协议兼容或拦截场景
  serial                # 共享状态，必须串行
```

层级决定依赖范围，Marker 决定执行属性。不同组合使用独立配置、入口、超时策略和报告目录，但不能让同一用例因目录和 Marker 得出冲突分类。

### 6.3 Allure 结果按运行和阶段隔离

建议目录结构：

```text
runs/<run_id>/allure-results/unit
runs/<run_id>/allure-results/integration
runs/<run_id>/allure-results/live
runs/<run_id>/allure-results/protocol
```

所有 pytest 阶段结束后再统一合并，任何阶段都不应清理其他阶段的结果。

### 6.4 测试发现不依赖 `.gitignore` 白名单

测试文件应默认被版本控制，仅忽略运行产物。通过逐个放行文件控制测试集合，会让新增用例静默缺席 CI。

### 6.5 P1 测试层验收条件

- `tests/unit` 默认无网络、无真实等待、无 Jenkins 依赖；
- `tests/integration` 只使用本地可控依赖并能确定性复现异常；
- `module/` 继续按业务领域组织，真实网络访问必须由 `live` Marker 和显式开关共同授权；
- 协议、串行和 live 属性不会通过目录名重复表达；
- Allure/JUnit 结果按 run 和阶段隔离，任何阶段不清理其他阶段产物；
- 新增测试文件无需修改 `.gitignore` 才能进入版本控制和 CI。

## 7. P2：收敛重复实现

建议按以下顺序治理：

1. 删除两个 standalone 素材脚本，统一进入 `BaseRequest`、`BaseTask` 和 pytest 执行链；
2. 合并两套媒体下载器；
3. 合并文本、图片、视频三套协议拦截 CSV loader；
4. 统一 SHA256、原子写入和 Manifest 校验工具；
5. 合并 `BaseTask` 与 `SmokeRequest` 的重复端点封装；
6. 删除同步断言外套 `async def` 的空壳方法；
7. 精简 `quality/__init__.py` 的 eager re-export，消除循环依赖和函数内反向导入。

重复实现的因果链为：

```text
同一规则存在多份实现
-> 修复只覆盖部分路径
-> 行为和错误语义持续漂移
-> 回归测试难以覆盖全部组合
-> 维护成本继续增长
```

### 7.1 P2 验收条件

- 每项重复实现都有明确的唯一保留入口和调用方迁移清单；
- 被删除的公开入口先给出兼容层或明确破坏性变更说明；
- 等价测试证明合并前后的协议、错误语义和产物 Schema 一致；
- `quality/__init__.py` 不再因为 eager import 引入反向依赖；
- 重复实现扫描和依赖边界测试进入 CI，避免后续重新分叉。

## 8. P3：可复现性与工程一致性

- 明确支持的 Python 版本，并在本地与 Jenkins 使用相同版本；
- 使用可审计的 lock/constraints 文件固定完整依赖解析结果，`requirements.txt` 只表达顶层依赖意图；
- 固定 pip/安装工具版本，记录依赖锁定文件的更新流程；
- 增加 `.gitattributes`，统一跨平台文本换行；
- 使用 `pyproject.toml` 集中管理格式、静态检查和测试工具配置；
- 在 CI 增加格式/静态检查、离线单测、集成测试、文档边界和产物契约门禁；
- 固定 JUnit、Allure 和 Quality 产物 Schema，并提供版本迁移策略；
- 测试数量和关键产物清单由 CI 自动生成或校验，不再人工维护；
- 在干净环境执行安装和离线测试，证明结果不依赖开发机缓存。

P3 验收条件：

- 同一提交在支持的 Python 环境中解析到同一依赖集合；
- Windows 换行、路径和原子替换行为有回归测试；
- CI 的静态检查、离线测试、文档检查和产物契约全部通过；
- README、FRAMEWORK_TEST_SPEC、Jenkins 模板和课程不再手工声明无法验证的数量或路径；
- 删除本地虚拟环境和缓存后仍可按文档从零恢复。

## 9. P3：学习范本闭环

### 9.1 增加零凭证完整演示

提供一个默认不访问真实网络、不读取 `.env`、不产生费用的完整演示入口。它必须走真实 Runner、执行计划、质量归并和报告生成链，而不是只调用若干独立函数。

演示至少覆盖：

- 一次完整成功；
- pytest 用例失败；
- 收集或执行池异常；
- 事实完整性失败；
- SSE 提前关闭或迭代异常；
- Flaky 功能关闭和启用但无历史样本两种状态。

执行后应生成 JUnit、Allure 原始结果、Quality 机器事实和 Pipeline Summary，使学习者可以沿同一个 `run_id` 解释最终结论。

### 9.2 建立分层学习入口

现有 12 天课程面向已经理解初版框架的学习者，还需要一个 30 分钟最小入口：

```text
Quickstart：运行离线 Demo，读懂一次成功和一次失败
-> 基础路径：Request / Task / Assertion / Runner
-> 进阶路径：Retry / Polling / Runtime Hooks / Quality
-> 高级路径：RunOutcome / ExecutionPlan / Metrics / Flaky / CI
```

最小示例必须可执行，不能只存在于 Markdown 模板中；示例代码应展示推荐边界，不携带生产账号、真实模型和历史兼容负担。

### 9.3 课程和文档必须随代码同步

当前课程仍包含“当前分支没有 Flaky”的过期描述。P0/P1 完成后必须同步：

- 更新课程中的执行状态、并串行调度、请求副作用和 Flaky 边界；
- 校验课程引用的文件、符号、命令和历史提交仍可访问；
- 为 README、FRAMEWORK_TEST_SPEC、Jenkins 模板和课程增加活跃文档边界测试；
- 明确历史代码只代表当时阶段，当前行为以代码和测试为准。

### 9.4 公共发布治理

如果范本需要对外共享，还应增加：

- LICENSE；
- CONTRIBUTING；
- SECURITY 与漏洞报告边界；
- 支持的 Python/Jenkins/Allure 版本矩阵；
- 示例数据、截图和报告产物的脱敏检查。

### 9.5 学习范本最终验收

- 全新环境不提供 `.env`、API Key 或 Jenkins 凭证，也能完成离线主链；
- 一条入口命令可以生成可追溯到同一 `run_id` 的完整演示产物；
- 学习者可以按文档主动复现成功、失败、中断、完整性阻断和数据不足；
- Quickstart 在 30 分钟内完成，进阶课程能够解释设计取舍而不是只罗列类名；
- 课程引用、命令、测试数量和产物路径由自动化检查保护；
- 默认行为不会访问真实付费接口，也不会无策略下载外部资源；
- 离线回归、架构边界、静态检查和文档检查全部通过。

完成以上验收后，框架可以定位为“进阶 CI 接口自动化学习范本”；在此之前只能定位为架构演进案例。

## 10. 最终实施顺序

```text
阶段 0 恢复离线基线并冻结行为
-> P0 统一状态模型
-> P0 统一执行计划与身份
-> P0 按 run_id 隔离产物
-> P1 保留 BaseRequest 门面并移除隐藏副作用
-> P1 建立安全产物收集与流式生命周期
-> P1 重构测试层级和执行属性
-> P2 消除重复实现
-> P3 完善可复现性
-> P3 完成零凭证演示、课程同步和学习范本验收
```

核心判断：当前真正的架构 P0 是“单一事实源缺失”。只有先让执行状态、身份和完整性结论可靠，后续的请求层重构、Metrics、Flaky 和去重工作才具有稳定基础。成为学习范本的最终 TOC 约束则是“证据闭环缺失”：学习者必须能在零凭证环境中复现实验、读取产物并验证文档结论。
