## 1. 目标、定位与范围

### 1.1 框架定位

本框架继续服务现有接口自动化，保持以下技术路线：

- 使用 Python 代码表达真实业务链路，不引入 YAML、Excel 或隐式 DSL；
- 使用 pytest 负责发现、选择和执行用例；
- 使用 `BaseRequest`、`BaseTask` 和断言层承载可复用接口测试能力；
- 使用 JUnit、Allure 和 Jenkins 提供执行结果与问题定位入口；
- 支持重试、轮询、上下文传播、轻量 Mock、并发优先与串行收尾；
- `tests/` 承担离线框架回归，`module/` 作为业务接口测试用例目录；真实调用由执行目标和环境配置决定，不新增 `live` Marker。

完成本计划后，框架应适合作为“中高级测开实战学习框架”。学习重点是接口测试分层、异常语义、执行编排和 CI 闭环，而不是质量数据平台建设。

### 1.2 本轮纳入范围

本轮只解决直接影响框架正确性、可扩展性和学习价值的问题：

1. 测试文件是否被版本控制，以及 clean checkout 能否复现同一测试集合；
2. pytest 预收集、选择参数、并串行分池和实际执行集合是否一致；
3. pytest 原始退出码是否被正确保留，失败、中断和无用例是否可能假绿；
4. `BaseRequest`、`BaseTask`、Runtime Hooks、Polling、日志和下载副作用的职责边界；
5. `tests/` 离线框架回归与 `module/` 业务接口用例是否保持清晰目录边界；
6. Quality 可选能力能否保持完整功能并与核心执行路径隔离；
7. 已证明等价的下载、配置、产物校验和结果解析实现是否能够收敛；
8. Python 环境和依赖是否可复现；
9. 新人能否完成“运行、理解、扩展、排障”的最小学习闭环。

### 1.3 明确不做事项

以下内容不进入本轮主线：

- 新建统一质量身份图谱或继续扩展 Case、Request、Operation 的平台化关系模型；
- 扩展 Metrics、Flaky 状态机、质量 Schema、治理命令或质量报告体系；
- 把全部产物迁移到 `runs/<run_id>/` 并维护 `latest` 指针；
- 在 Python Runner 中复制 Jenkins 状态机或决定整条流水线最终结论；
- 建设可处理任意不可信 URL 的通用下载安全网关；
- 全量迁移 `tests/unit`、`tests/integration` 等目录或建立四套 Allure 目录；
- 建设 12 天课程、完整课程体系或文档教学平台；
- 流式输出/SSE 用例、相关实现重构及专项验收；
- 密钥泄露治理、凭证轮换、Secret 扫描和 Git 历史清理；
- LICENSE、CONTRIBUTING、SECURITY 等公共发布治理；
- MR 精准选测、覆盖率矩阵、性能基线、成本估算和智能用例生成。

现有 Quality、Semantic、Metrics、Flaky、Retry、Middleware、TestContext、Runtime Hooks、下载、报告、邮件、历史、JUnit、Allure、Jenkins、独立 CLI 和公开业务类型均不删除、不缩减。冻结的是外部能力边界，不是内部实现；允许为职责收敛、依赖隔离和懒加载重构内部代码，但不新增质量平台功能。

### 1.4 文档关系与零能力回退底线

代码设计复审负责说明“为什么改、哪些边界不能破坏”；本文负责说明“按什么顺序改、如何验收”。如实施细节与最新复审或用户要求冲突，以最新要求和设计复审的兼容边界为准，并先更新本文再实施。

本轮只调整内部职责位置、依赖方向、重复实现和可选实现的加载边界，不删除或缩减任何已有能力。

以下兼容项必须在阶段 0 建立清单和刻画测试：

- 公共类、函数、方法、参数、返回值和异常语义；
- 默认开关、默认行为以及可观察的初始化和异常时机；
- 类对象、MRO、`__name__`、`__module__`、继承关系和导入路径；
- CLI 路径、命令、参数、输出和退出码；
- Quality Schema、状态、产物、报告章节和治理命令；
- JUnit、Allure、HTML、history、邮件、摘要、附件及产物路径。

旧入口通过兼容委托或适配继续工作；新增策略只能作为 opt-in 能力，不能反向改变旧调用方。

## 2. 第一性原理与 TOC 约束

### 2.1 框架最小可信闭环

接口自动化框架最本质的职责是：

```text
确定要执行什么
-> 执行这些用例
-> 保留原始结果
-> 如实返回成功或失败
-> 提供足够的排障证据
```

对应五条不可破坏的不变量：

1. **集合一致**：用户选择的用例集合、预收集集合、分池集合和实际执行集合必须一致；
2. **状态单调**：失败、中断、内部错误、参数错误和意外无用例不能在下游变成成功；
3. **副作用隔离**：日志、附件、下载和可选观察器不得改变 HTTP 结果及原始异常；
4. **离线可复现**：框架测试和学习示例不依赖 `.env`、外部业务配置、外部服务或付费调用。
5. **能力零回退**：内部重构不得删除已有入口、改变默认行为、破坏类型身份或缩减报告与产物。

### 2.2 当前 TOC 核心约束

当前真正限制框架可信度的约束不是抽象类不够多，而是“测试清单与执行结果存在多个事实源”。

主要因果链为：

```text
tests 使用白名单式忽略规则
-> 本地工作区与 clean checkout 的测试集合不同
-> 预收集又没有应用 -k/-m/--ignore 等选择条件
-> expected count、并串行分池与实际执行集合不同
-> 非空计划池可能被筛选为空并返回 pytest exit 5
-> 当前并池逻辑可能把 exit 5 当作成功
-> Jenkins 存在假绿风险
```

第二条影响接口语义的因果链为：

```text
请求、日志、附件和下载绑定在同一调用路径
-> poll_get 或媒体中间件隐式访问外部 URL
-> 报告或下载失败可能覆盖成功响应
-> 测试结果不再只反映接口行为
```

### 2.3 TOC 决策顺序

本轮按以下顺序执行：

1. **识别约束**：先确定 clean checkout 中唯一、可信的测试集合；
2. **充分利用约束**：让选择、分池和执行全部从同一 nodeid 集合派生；
3. **从属其他环节**：JUnit、Allure、Pipeline Summary 和可选 Quality 只能消费结果，不能重解释结果；
4. **提升约束能力**：在结果可信后，再治理请求副作用、重复实现和学习入口；
5. **重新评估**：只有真实并发、外部消费者或平台需求出现时，才重启被延后的设计。

## 3. 当前事实与边界判断

### 3.1 测试清单并不可信

当前 `.gitignore` 使用 `/tests/*` 后逐文件放行。结果是：

- 本地 pytest 能发现部分未跟踪测试；
- Jenkins 执行 `deleteDir()` 和 clean checkout 后不会获得这些文件；
- 本地收集错误不一定代表仓库或 CI 基线错误；
- 新增测试可能静默缺席 Git 和 CI。

因此，不能直接把当前工作区中的测试数量或未跟踪失败测试冻结为架构契约。必须先决定哪些文件属于框架，再从 clean checkout 建立基线。

修正忽略规则前，必须审查当前被忽略和未跟踪文件。禁止批量 `git add tests module`，避免把本机实验脚本、响应样本或临时数据纳入仓库。

### 3.2 选择集合和执行集合不一致

当前 Runner 先按 `test_path` 预收集，再把额外 pytest 参数交给正式执行。`-k`、`-m`、`--ignore` 等参数可能让正式执行集合小于预收集集合，导致：

- `expected_case_count` 不准确；
- serial marker 分池基于错误集合；
- 质量完整性产生误报；
- 非空计划池可能在正式执行时变为无用例。

问题不在“先收集再执行”本身。统一预收集是 Runner 的控制面，用于形成确定的 nodeid/marker 清单、完成并串行分池，并为未来分布式分片提供稳定输入；需要修复的是预收集没有覆盖全部选择条件，以及执行阶段再次解释选择参数。

### 3.3 并池退出码存在假绿路径

当前并池合并逻辑把 pytest exit 5 排除在失败集合之外。对于“计划非空但执行阶段无用例”的情况，exit 5 不是正常跳过，而是选择集合或执行计划异常，整体必须返回非零。

### 3.4 请求层只需要窄修复

现有 `BaseRequest`、Middleware、`RetryExecutor`、`PollingPolicy`、Runtime Hooks 和 TestContext 方向正确，不需要整体重建。真实缺口集中在：

- 输入下载与结果下载维护两套底层实现，且触发策略没有统一表达；
- Polling 的单次请求 timeout 没有始终受剩余总预算约束；
- `BaseRequest` 直接管理过多 Runtime Lease，且 `_quality_*` 命名泄漏到通用请求层；
- `BaseTask` 同时承载媒体、账户、余额、用量和结算等多个领域；
- Task ID 的兼容别名没有清晰落到具体端点契约。

### 3.5 Quality 的正确位置

Quality、Semantic、Metrics、Flaky 的现有 API、CLI、Schema、产物、报告章节、默认开关和行为完整保留。关闭时轻量兼容入口继续存在，重型实现不加载、不创建产物；开启时完整能力继续工作并保持 fail-open。

内部允许进行以下兼容式重构：

- 根包公共符号和 `__all__` 不变，重实现改为懒加载；
- 轻量 pytest 兼容插件保持注册，现有参数和 Hook 不变；
- Runner 只依赖中性 Run Lifecycle，不直接依赖 Quality 内部模型；
- Pipeline Reporting 通过可选 Source Adapter 读取 Quality 产物；
- 共享基础 Artifact 校验原语，但保留各领域自己的关系校验和降级规则。

不建设 entry point、插件市场、自动发现、通用事件总线或 DI 容器。

## 4. 阶段 0：恢复 clean checkout 可信基线

阶段 0 的目标不是重构架构，而是得到一个不依赖外部业务配置、无真实网络的可重复仓库基线。

### 4.1 修正版本控制边界

1. 删除 `.gitignore` 中 `/tests/*` 和逐文件放行模式；
2. 只忽略缓存、报告、下载文件和其他运行产物；
3. 逐一审查当前未跟踪或被忽略的测试文件；
4. 对每个文件明确选择：纳入框架、移动到本机实验目录、转换为 fixture，或删除；
5. 在内容审查完成前不批量纳管文件；
6. 对已跟踪示例和配置执行内容归属检查，避免纳入本机响应样本或临时数据。

### 4.2 建立唯一测试清单

测试清单以 clean checkout 中受 Git 管理的 `test_*.py` 为准。阶段 0 应记录：

- 当前提交 SHA；
- Python、pytest 和关键插件版本；
- pytest 收集出的 nodeid 清单；
- 并行池和串行池清单；
- 收集错误及其对应的已跟踪文件。

数量只作为审计信息，不作为永久契约。自动化应验证：

```text
总收集集合 = 并行池集合 ∪ 串行池集合
并行池集合 ∩ 串行池集合 = 空集
每个 nodeid 唯一
```

### 4.3 刻画配置契约并隔离离线测试

保留 `Settings`、`settings`、`load_settings()`、全部公开解析函数、异常类型、错误文本以及现有可观察的初始化和异常时机。

阶段 0 不合并配置实现，只建立以下兼容合同：

- `BaseRequest` 继续支持显式注入 Settings 或测试配置；
- 离线测试和学习示例通过显式注入测试 Settings 隔离外部环境配置 I/O；
- 不以“延迟加载”为名改变旧入口的初始化、校验结果或异常时机；
- collect-only 不创建真实客户端、不调用真实接口；实际业务入口继续保持原有配置行为；
- Pydantic validator 与手工校验的重复实现记录为 P2 去重任务，完成兼容刻画后再合并。

### 4.4 为已知缺陷增加刻画测试

在修改行为前补充最小回归覆盖：

- `-k`、`-m`、`--ignore` 导致集合变化；
- 并行池或串行池返回 pytest 0～5；
- 计划非空但正式执行返回 5；
- 显式阶段失败但存在可解析 JUnit；
- 下载或附件失败不得覆盖原始响应；
- Polling 请求、重试和 sleep 共同消耗总预算；
- `BaseTask` 旧入口、`pytest.skip()` 条件与消息保持兼容；
- 公共 API、CLI、类型身份、默认行为和产物路径兼容。

### 4.5 阶段 0 验收条件

- 新增 `tests/test_example.py` 默认不会被 Git 忽略；
- clean checkout 中参与 pytest 的框架测试均受版本控制；
- `python -m pytest tests -q` 在不依赖 `.env` 和外部业务配置的条件下完成收集与离线执行；
- 离线基线不访问真实网络、不产生付费调用、不执行真实等待；
- 收集清单满足唯一性、互斥分池和集合守恒；
- 被确认纳入仓库的失败测试全部修复；
- 基线记录包含提交 SHA 和运行环境，不再引用无法复现的工作区快照；
- 已形成公共 API、CLI、默认行为、类型身份、Schema、报告章节和产物路径兼容清单。

## 5. P0：保证用例选择和执行结论可信

P0 只修复执行可信性，不建设通用执行平台。

### 5.1 建立唯一权威用例集合

一次权威 pytest 收集应产生最终 nodeid 和 marker，以下内容全部从它派生：

- 实际执行 nodeid；
- 并行池和串行池；
- 用例数量；
- 阶段标识；
- JUnit 输出目标。

正式执行按已经确定的 nodeid 运行，不再重新解释一套不同的选择条件。

Runner 无论串行、并行还是未来分布式模式都保留这次权威收集：

```text
控制面：权威收集 -> 不可变 nodeid 计划 -> 分池/分片
执行面：消费已分配 nodeid -> 返回原始 pytest 结果
```

关闭并发时只是把整个计划交给单一执行池，不绕过收集；未来分布式 worker 也只消费分配结果，不在 worker 端重新选测。

### 5.2 明确支持的选择参数

框架只承诺并测试当前实际使用的选择语义：

- 测试目录、文件和 nodeid；
- `-k`；
- `-m`；
- `--ignore`；
- `--ignore-glob`，如当前 pytest 版本支持且项目确有使用。

这些参数必须在权威收集阶段生效。收集完成后执行最终 nodeid，避免二次筛选。

不实现覆盖 pytest 和所有插件的通用参数分类器。现有已经接受和透传的 pytest/插件参数继续兼容；可能改变选择集合的参数必须进入同一次权威收集。只有此前从未支持、且无法安全判断阶段的新参数才显式拒绝，并在增加适配测试后支持；纯执行参数和产物参数继续只影响对应阶段。

### 5.3 使用轻量池级结果，不复制 Jenkins 状态机

Runner 只需要一个内部池级结果结构，至少保存：

```text
stage_id
planned_nodeids
raw_pytest_exit_code
started / completed
exception_type（如有）
junit_path（如有）
```

每个池的 `raw_pytest_exit_code` 必须永久保留，不能被最终聚合码覆盖。它不负责推导整条 Jenkins Pipeline 的最终结论。Jenkins 仍综合 Checkout、环境准备、框架测试、用例收集、接口测试、节点异常和超时决定最终构建状态。

### 5.4 明确分池执行和退出规则

执行规则保持简单：

| 池状态 | 后续池 | 整体结果 |
| --- | --- | --- |
| 计划为空 | 不调用 pytest，记为未执行 | 不单独导致失败 |
| pytest 0 | 继续 | 当前池成功 |
| pytest 1 | 可继续收集剩余池证据 | 整体非零 |
| pytest 2/3/4 | 停止后续池 | 保留原始码，整体非零 |
| 计划非空但 pytest 5 | 停止后续池 | 选择/执行异常，整体非零 |
| Runner 异常 | 停止后续池 | 保留异常类型，整体非零 |

单池执行直接返回 pytest 原始退出码。多池执行保留每个池的原始码，最终进程码按一张固定、经过测试的优先级表派生，并满足：只有所有已执行池均为 0 时，最终结果才是 0。

固定规则为：

1. 权威收集返回任何非零时立即停止；1/2/3/4 原样返回，5 按权威最终集合为空处理；
2. 权威最终选择集合为空时保留 pytest exit 5；
3. 分池后单个派生池为空时不调用 pytest，记录 `NOT_RUN`，不单独导致失败；
4. 已执行池返回 1 时可以继续收集后续池证据；没有更高优先级终止码时最终返回 1；
5. 已执行池返回 2/3/4 时立即停止后续真实接口池，并返回该原始码；
6. 计划非空但执行返回 5 时立即停止，并原样返回 5；
7. Runner 异常保留异常类型并返回明确非零，不从 JUnit 反向推导退出码。

最低组合矩阵：

```text
[0] -> 0
[0, 0] -> 0
[1, 0] -> 1
[0, 1] -> 1
[1, 2] -> 2
[2] -> 2
[3] -> 3
[4] -> 4
[5] -> 5
[5, 5] -> 5
权威最终集合为空 -> 5
单个派生池为空 -> NOT_RUN
```

### 5.5 明确事实边界

- pytest 原始退出码决定测试进程是否成功；
- JUnit 负责用例统计和失败详情，不覆盖显式阶段失败；
- Allure 负责步骤、请求、响应和附件定位，不决定进程退出；
- Pipeline Summary 汇总事实，不修改 Jenkins 构建结果；
- Jenkins 是整条流水线最终事实源；
- Quality 缺失或失败只能降级可选观测，不能覆盖 pytest/Jenkins。

事实优先级固定为：

```text
pytest 原始退出码：测试进程事实
Jenkins 阶段状态：流水线执行事实
JUnit：用例统计和失败详情
Quality / Metrics / Flaky：诊断观察
Pipeline Conclusion：关注等级
```

框架自有报告链只对 JUnit 做一次业务解析，形成结构化 `RunResult`/`JUnitSummary`，供 Markdown、邮件、历史和兜底报告共同消费；Jenkins JUnit Publisher 的必要独立解析不计入该限制。现有报告章节、邮件、历史、CLI 和 Pipeline Conclusion 全部保留；显式阶段失败优先于部分或成功 JUnit。

### 5.6 P0 验收条件

- `-k`、`-m`、`--ignore` 下收集集合与实际执行集合完全一致；
- 每个最终 nodeid 只执行一次；
- `expected_case_count` 来自最终选择集合；
- “并行失败 + 串行成功”最终非零；
- “并行池计划非空但 exit 5 + 串行成功”最终非零；
- `[5, 5]`、权威最终集合为空和单个派生池为空分别满足固定规则；
- exit 2/3/4 和 Runner 异常不会继续生成成功结论；
- 显式阶段失败不会被可解析但不完整的 JUnit 展示为阶段通过；
- Markdown、邮件、历史和兜底报告复用同一份结构化 JUnit 结果；
- 所有池返回 0 时最终才返回 0；
- `--collect-only` 不创建 run_id、不写 Quality 产物、不调用真实接口；
- `run_master.py` 的稳定命令入口保持兼容。

## 6. P1：收紧请求语义与兼容式职责边界

P1 保留现有架构，只修复隐藏副作用和边界错误。

### 6.1 保留 `BaseRequest` 稳定门面，收拢内部生命周期

`BaseRequest` 现有构造参数、公开方法、返回值、异常语义、Middleware 语义以及 Session、Header、Retry、Polling 默认行为全部保留。

HTTP 主流程继续负责：

- Session 创建、复用和关闭；
- base URL、Headers、HTTP verbs 和 timeout；
- 通用重试与轮询委托；
- Middleware 调用；
- 返回原始 `requests.Response`。

Operation、Request Group 和 Polling 的 begin、finish、detach、outcome 映射委托给一个内部 `RuntimeObserver` 或 context manager，不为此新增公开类层级。共享 Session 的临时 Header 使用请求级合并，避免并发修改共享状态，同时保持现有 Header 优先级和公开方法行为。

### 6.2 保留 Runtime Hooks、Middleware 和 fail-open 语义

- Operation、Request Group、Polling 的强类型 Hook、Lease、Provider、ContextVar 和现有自由函数全部保留；
- 旧 `_quality_*` 参数继续接受并映射到中性 runtime metadata；
- `RequestMiddleware` 三阶段接口以及 Runtime Observation、Media Resource、Redaction、Logging 实现全部保留；
- 现有 `middlewares=` 替换语义、默认组合、执行顺序和默认行为不变；另提供 additive 扩展入口；
- 日志或 Allure 附件失败不得改变成功响应；
- `on_exception()` 或 Runtime Hook 自身失败不得覆盖原始异常；
- Quality 关闭时重型实现不加载，Runtime Hooks 使用现有 Noop 语义；
- 失败诊断优先保留原始异常类型、消息和调用位置。

不建设事件总线、通用注册中心或 DI 容器。

### 6.3 流式输出不纳入本轮范围

流式输出/SSE 用例已经删除。本轮不重构、不扩展相关实现，不将其作为学习内容或验收对象；现存底层代码保持当前状态。未来重新引入真实用例时，应基于届时协议和消费者单独复审。

### 6.4 轮询总预算覆盖全部耗时

保留现有 `PollingPolicy` 和状态机，修复预算计算：

```text
总预算 = HTTP 请求 + 请求内部重试 + 轮询 sleep + 状态处理
```

- 每轮开始前计算剩余预算；
- 单次请求 timeout 不得超过剩余预算；
- 重试退避和轮询 sleep 都受同一 deadline 约束；
- 终态判断优先于结果字段判断；
- 矛盾字段返回协议错误或 UNKNOWN，不按字段判断顺序偶然成功；
- 超时只产生一个清晰的最终异常。

### 6.5 下载能力兼容式去重

输入媒体下载、结果下载、decorator、middleware、`start_media_downloads()` 等现有入口、附件内容和隐式触发行为全部保留。

内部只保留一套流式下载、安全文件名、唯一路径、大小控制和附件类型识别原语；原入口全部兼容委托。增加小型 Capture/Download Policy，分别控制输入捕获、输出捕获和关闭捕获。

- 未传入新策略时继续使用当前兼容默认值；
- 新调用方可以显式选择输入、输出或关闭捕获；
- 下载失败继续 fail-open，不覆盖接口响应、原始异常或断言结果；
- 在不破坏现有受信来源行为的前提下复用 TLS、超时、大小和安全文件名边界。

不新增第三套公开 `ArtifactCollector`，不建设 Artifact 平台、下载任务中心或通用下载安全网关。

### 6.6 Task ID 契约显式化

当前兼容行为不应被无依据破坏。处理原则为：

- 通用 `BaseTask` 不继续扩展新的猜测字段；
- 当前端点族确需兼容 `task_id`、`id`、`request_id` 时，由具体 Task 或显式配置声明；
- 提取前验证 HTTP 状态和 JSON 结构；
- 只有出现语义不同的端点族时，才引入独立响应模型；
- 每个受支持字段都有契约测试。

### 6.7 收窄 `BaseTask` 职责并保留兼容行为

媒体、账户、余额、用量和结算等领域实现迁入对应能力对象；`BaseTask` 所有现有方法、签名、返回值、异常、Allure 步骤和行为继续保留，由原方法兼容委托。

- 新领域实现返回中性结果，由新用例或 fixture 决定是否跳过；
- `BaseTask` 旧门面继续保持原有 `pytest.skip()` 条件、消息和行为；
- 现有 Task ID 别名及提取顺序保持兼容，只限制未来不再增加新的猜测字段；
- Image、Video 等现有 Task 继续作为领域扩展点；
- 新业务优先组合领域能力，不删除现有继承体系，也不继续扩大宽基类。

这样新能力可被 pytest、CLI、脚本和学习示例复用，旧调用方行为不变。

### 6.8 保持 `module/` 业务用例目录边界

不增加 `live` Marker，也不建立第二套真实接口分类体系：

- `module/` 是业务接口测试用例目录，继续按业务领域组织；
- `tests/` 是离线框架回归目录，不调用真实接口；
- `run_master.py` 继续以 `module/`、其子目录、文件或 nodeid 作为业务用例执行目标；
- `--collect-only` 只验证 `module/` 用例收集和分池，不发送真实请求；
- Jenkins 继续通过 `RUN_REAL_SMOKE` 和 `SMOKE_TARGET` 决定是否执行对应 `module/` 目标；
- 本地执行以用户运行 `run_master.py` 及其目标参数为明确入口；
- `serial` Marker 只表达共享状态和串行约束，不表达接口是否真实；
- collect-only 不创建真实客户端或发送请求；真实业务入口继续保持现有配置初始化、校验和错误语义。

目录、运行目标和 Jenkins 阶段已经能够表达执行边界，不再通过额外 Marker 重复建模。

### 6.9 收窄 Runner 与 Quality 的依赖

执行编排收敛为：

```text
Runner
├─ pytest 核心执行
└─ RunLifecycle
   ├─ prepare
   ├─ stage_environment
   └─ finalize
```

- Runner 只依赖中性 Lifecycle 协议，不直接导入 `quality.models.RunStatus` 等内部类型；
- Quality 提供 `QualityRunLifecycle`，关闭时返回轻量 Noop；

- `quality/__init__.py` 保留全部公共符号和 `__all__`，改用映射驱动的 `__getattr__` 懒导出；
- 轻量 pytest 兼容插件保持注册，现有参数和 Hook 不变，重型实现按当前开关加载；
- Pipeline Reporting 保留 Sources、Builder、Renderer 分层，Quality Source 通过局部加载 Adapter 接入；
- `initialize-stages`、`set-stage` 等轻量 Reporting CLI 保留路径、参数、输出和退出码，执行时不加载 Semantic、Metrics、Flaky；
- 不建设通用插件总线、自动发现或 DI 容器。

### 6.10 统一 pytest 与 Allure 生命周期并保持产物契约

- `pytest_execution.py` 唯一拥有 Runner 模式下的 pytest 收集与执行；
- `scheduling.py` 只负责纯分池算法；
- `master_service.py`、`run_master.py` 和现有 CLI 继续作为兼容入口；
- Runner 串行、并行模式都先形成同一份不可变 nodeid 计划，串行模式不因关闭并发而绕过预收集；
- 计划结构保持可分片，未来分布式 worker 只执行控制面分配的 nodeid，不重新执行选择逻辑；
- 各池可以写入内部临时结果目录，但这些目录不是新的公开产物路径；
- 执行结束后合并一次，并只生成一次最终报告；
- 未传入 `--alluredir` 时继续使用现有 Allure results、HTML、history 和附件路径；
- 显式传入 `--alluredir` 时，最终结果准确写入用户指定目录，不擅自追加池级子目录；
- Runner 模式只在生命周期开始时清理一次有效目标目录；直接运行 pytest 时继续保持现有自动报告和 `--clean-alluredir` 语义；
- Jenkins 继续发布现有 JUnit、Allure、摘要、邮件、历史和构建产物。

### 6.11 P1 验收条件

- 新增 `test_*.py` 无需修改 `.gitignore` 即可进入 Git 和 CI；
- 首次接触项目的人能在约 30 分钟内运行示例、解释失败并新增一个端点用例；
- Quality 不是主链前置条件。

“30 分钟完成”只作为发布前人工体验验收，不伪装成稳定的 CI 数值指标。

## 8. 现有 Quality 能力的保留与隔离边界

冻结的是外部能力和契约，不是内部实现。Quality、Semantic、Metrics、Flaky 的 API、CLI、Schema、状态机、治理命令、报告章节、机器产物、默认开关和行为全部保留。

内部按以下边界重构：

- 当前默认开关及 Jenkins 启用行为不变；关闭时 Runtime Hooks 保持 Noop，开启时完整能力继续工作；
- `quality/__init__.py` 保留现有公共符号和 `__all__`，通过映射驱动的懒导出避免加载重实现；
- 轻量 pytest 兼容插件继续注册，参数、Hook 和导入路径不变；
- Quality 关闭时 Lifecycle 工厂返回轻量 Noop，不加载 Semantic、Metrics、Flaky；
- Quality 开启后继续 fail-open，不改变业务响应、原始异常和 pytest 退出码；
- `QualityRunLifecycle` 组合现有阶段，`quality_*_stage.py` 模块、函数、阶段顺序和旧入口不变；
- Reporting 的基础 Jenkins/JUnit Source 与可选 Quality Source Adapter 分离；
- 未启用 Quality 时对应章节显示 `NOT_RUN`，已启用但产物异常时显示 `NO_DATA`，产物正常时完整展示现有章节；
- Manifest、Schema、Hash、原子写入和 Flaky SQLite 迁移机制继续保留；
- 机器产物继续拒绝不兼容输入，但不建设万能迁移平台。

本轮不新增身份层、Metrics 指标、Flaky 规则、状态机、治理命令或人工报告入口，也不建设插件市场、自动发现、通用注册中心或 DI 容器。

隔离验收：

- Quality 关闭时重实现不进入 `sys.modules`，不创建质量产物；
- Quality 开启时现有 API、CLI、Schema、产物和报告内容不减少；
- Runtime Hooks 的强类型事件、Lease、Provider、ContextVar 和 fail-open 语义保持；
- `common -X-> quality` 依赖边界保持；
- Jenkins/pytest 显式失败不能被 Quality、JUnit 或 Summary 覆盖；
- 本轮没有新增 Quality 用户功能或新的人工报告入口。

## 9. 延后项与重新启动条件

| 延后项 | 重新启动条件 |
| --- | --- |
| `runs/<run_id>` 全产物隔离 | 明确支持同一工作区并发运行，并出现真实覆盖问题 |
| 原子 `latest` 指针 | 存在多个本地/外部消费者需要稳定读取最近完成运行 |
| 完整下载安全网关 | 业务明确要求处理任意不可信 URL，且不能通过网络出口或白名单解决 |
| 五层身份与外键平台 | 出现跨系统消费者，现有 case/invocation 对账无法满足真实查询 |
| 全量测试目录迁移 | 现有 `tests/` 与 `module/` 边界持续导致误执行或维护成本 |
| 多 Python 版本矩阵 | 框架明确承诺支持多个 Python minor 版本 |
| Quality 新能力 | 形成独立产品目标、负责人、消费者和验收指标 |
| 课程与公共发布治理 | 框架被正式定位为对外教学或开源产品 |

延后不是永久否定，而是避免在没有约束证据时提前支付复杂度成本。

## 10. 实施顺序与阶段门禁

```text
阶段 0：建立兼容清单，审查忽略文件并恢复 clean checkout 离线基线
-> P0：选择集合单一事实源和 pytest 原始退出码
-> P0：结构化池级结果及 JUnit、Summary、Jenkins 事实优先级
-> P1：BaseRequest / Runtime Hooks / Polling 职责收敛
-> P1：下载底层去重、Capture Policy 与 BaseTask 兼容委托
-> P1：pytest / Allure 所有权收敛并保持现有产物契约
-> P1：Quality Lifecycle 隔离、懒加载与 Reporting 可选适配
-> P2：Assertions、类型身份、独立 CLI、配置和 Artifact 校验去重
-> P2：依赖锁定、行为边界测试和最小离线学习闭环
-> 最终验收
```

阶段门禁：

- 阶段 0 未形成公共 API、CLI、Schema、报告、默认行为、产物路径和类型身份兼容清单，不开始重构；
- P0 先完成权威选择集合和原始退出码，再在同阶段修复报告事实优先级；P0 未通过，不优化报告展示和学习入口；
- P1 职责迁移必须先保留旧门面；任何旧方法、参数、类型、CLI、路径或默认行为消失，本阶段不得通过；
- P1 Allure 所有权调整必须通过默认路径、自定义 `--alluredir`、HTML、history、附件和直接 pytest 模式合同测试；
- P1 Quality 隔离必须证明关闭时重实现不加载、开启时现有能力和产物不减少；
- P2 去重只能替换内部实现源，不得删除兼容入口，也不得与 P0/P1 行为修复混在同一提交；
- 每一阶段都必须更新 README、自动化测试和 `code_history/` 变更记录。

## 11. 最终验收矩阵

| 维度 | 最终标准 | 验证方式 |
| --- | --- | --- |
| 测试清单 | clean checkout、Git 和 pytest 使用同一测试集合 | Git 检查、collect-only、集合守恒测试 |
| 选择正确性 | 支持的选择参数在收集和执行阶段得到同一 nodeid | 子进程/刻画测试 |
| 退出正确性 | 任一池失败、中断、异常或意外 exit 5 均不会返回 0，原始码不丢失 | 0～5 与组合矩阵测试 |
| 结果边界 | 框架自有报告链只业务解析 JUnit 一次，JUnit/Allure/Quality/Summary 不覆盖 pytest/Jenkins 失败 | Pipeline Reporting 回归测试 |
| 零能力回退 | 公共 API、参数、默认行为、CLI、Schema、报告章节和现有能力不减少 | 兼容清单与刻画测试 |
| 类型身份 | 已有类的对象关系、名称、模块、MRO、继承和导入路径不变 | 类型合同测试 |
| 离线隔离 | 离线测试不依赖外部业务配置、无真实网络、无付费调用；不改变业务默认捕获行为 | 网络封锁、注入配置与故障测试 |
| HTTP 语义 | 报告、附件和观察器失败不改变响应或原始异常 | Middleware/Runtime Hooks 测试 |
| Header 并发 | 共享客户端的请求级临时 Header 不污染其他并发请求，原优先级不变 | 并发屏障与请求捕获测试 |
| Polling | 请求、重试和等待共同受 deadline 约束 | fake clock/sleep 测试 |
| 下载兼容 | 默认捕获行为不变，显式策略可分别控制输入、输出和关闭捕获 | 默认路径与 Capture Policy 测试 |
| BaseTask 兼容 | 原方法、签名、结果、Allure 步骤和 `pytest.skip()` 行为不变 | 旧入口合同测试 |
| 用例目录边界 | `tests/` 保持离线，`module/` 作为业务接口用例目录且不增加 `live` Marker | 收集、CLI 与 Jenkins 合同测试 |
| Allure 契约 | 默认路径、自定义 `--alluredir`、HTML、history、附件和直接 pytest 模式兼容 | 产物生命周期测试 |
| 独立 CLI | 素材等 CLI 的路径、命令、参数、输出和退出码不变 | CLI 合同测试 |
| 可复现性 | 支持的 Python 环境使用锁定依赖完成 clean install | CI clean environment 验证 |
| 可扩展性 | 新端点主要修改业务模块；横切行为走 Middleware/Hook；质量阶段走 Lifecycle | 示例扩展与依赖边界测试 |
| 可排障性 | 控制台、JUnit、Allure 能逐层定位首要失败原因 | 成功/失败示例验收 |
| Quality 边界 | 当前开关语义不变；关闭时重实现不加载，开启时能力完整且 fail-open | 开关、导入、产物与依赖边界测试 |

## 12. 完成后的框架定位

全部验收通过后，框架可定位为：

> 一套面向中高级测开的代码式接口自动化实战框架，覆盖请求封装、契约断言、Middleware、重试、轮询、TestContext、Runtime Hooks、Mock、并串行调度、JUnit、Allure、Jenkins 及现有可选质量观察能力；离线示例可复现、执行结论可信，并提供最小可运行的学习和扩展路径。

它不是质量平台，也不要求学习者先理解 Metrics、Flaky、质量身份或持久化治理。框架的长期演进继续遵循同一原则：先证明真实约束，再增加解决该约束所必需的最小复杂度。
