# CI 接口框架设计缺陷优先级评审

## 1. 评审范围

本评审排除密钥、凭证、SSRF 等安全问题，只从以下维度评估当前 CI 接口框架：

- 执行与报告结论的正确性；
- 状态和事实模型的一致性；
- 模块职责及副作用边界；
- 测试体系的可维护性；
- 框架扩展性与运行可复现性。

## 2. 第一性原理与核心约束

CI 接口框架本质上是一条确定性的状态管道：

```text
执行计划 -> 实际执行 -> 原始事实 -> 完整性校验 -> 最终结论
```

每一层都必须满足两个基本条件：

1. 身份一致：下游事实可以准确追溯到唯一的运行、执行池和测试用例；
2. 状态单调：失败、部分执行或中断不能在下游重新解释为成功。

当前最大的 TOC 约束不是重复代码，而是上述五层没有共享同一个状态和身份模型。该问题会让 Metrics、Flaky、JUnit 和 Pipeline Summary 建立在不稳定的事实基础上。

## 3. P0：统一执行状态与事实模型

### 3.1 建立唯一的 `RunOutcome`

需要统一表达：

- pytest 原始退出码；
- 并行池和串行池状态；
- 是否完整执行；
- 用例结果；
- 基础设施错误；
- 最终流水线结论。

当前 `run_orchestration/runner.py`、`run_orchestration/pytest_execution.py` 和 Pipeline Reporting 分别解释执行状态，导致退出码和失败语义在层间丢失。

目标约束：

```text
FAILED / INTERRUPTED / PARTIAL
不能被任何 JUnit、collect 或历史产物重新解释为 PASSED
```

### 3.2 建立唯一的 `ExecutionPlan`

当前流程先按测试路径预收集，再把 `-k`、`-m`、`--ignore` 等选择参数交给正式执行。这会产生两个不同的用例集合：

```text
预收集集合 != 实际执行集合
-> expected_case_count 不准确
-> 执行池划分和完整性判断失真
```

应先生成不可变执行计划，并让以下内容全部从该计划派生：

- 最终 nodeid 集合；
- 并行池和串行池；
- expected case count；
- execution ID；
- JUnit 输出目标。

### 3.3 完整性失败必须阻断派生计算

当前事实归并返回 `IntegrityStatus.FAILED` 后，Semantic、Metrics 和 Flaky 仍可能继续执行。

正确的数据依赖规则应为：

```text
原始事实不可信
-> 派生指标统一为 NO_DATA
-> 不进入 Semantic、Metrics 和 Flaky 强结论
```

### 3.4 补齐统一身份模型

Case、Request、JUnit 和 Operation 应共享明确的外键链：

```text
run_id
  -> execution_id
    -> invocation_id
      -> case_id
        -> request / request_group / operation
```

当前 Request 事实没有和 Case 做完整外键对账，JUnit 也没有严格核对 `case_id`。身份不可信时，请求成功率、接口耗时、失败分类和 Flaky 历史都无法形成可靠结论。

### 3.5 P0 验收条件

- pytest 0～5 退出码均有唯一且可逆的状态映射；
- 任意执行池异常后不会继续产生“完整执行”结论；
- 预收集集合与实际执行集合完全一致；
- 孤立 Case、Request、JUnit 或 Operation 会产生完整性失败；
- `IntegrityStatus.FAILED` 时所有派生阶段停止；
- 显式失败状态不能被可解析产物覆盖。

## 4. P1：拆分请求层职责与副作用

当前 `BaseRequest` 同时承担 HTTP 传输、重试、轮询、日志、Allure、Quality Hooks、流式生命周期和结果文件下载。多个变化原因集中在同一对象，是请求层复杂度持续增长的主要原因。

建议拆分为：

```text
HttpTransport
RetryExecutor
PollingEngine
ResponseObserver
ArtifactCollector
```

### 4.1 轮询改为显式有限状态机

终态判断应优先于结果字段判断，避免失败响应中存在残留结果时被判定为成功。

建议状态转换：

```text
UNKNOWN -> PENDING -> SUCCESS
                   -> FAILURE
                   -> TIMEOUT
                   -> INTERRUPTED
```

每个响应只能产生一个确定状态；矛盾字段应进入 `UNKNOWN` 或协议错误，而不是依赖字段判断顺序。

### 4.2 总超时使用硬截止时间

轮询总预算必须覆盖请求、重试和等待时间。每次请求的 timeout 应使用剩余预算计算，而不是在请求返回后才检查是否已经超时。

### 4.3 流式响应使用专用观察器

SSE 响应不能复用普通 HTTP 响应日志逻辑。日志层不得为了生成附件访问 `response.text`，否则会提前消费流并改变调用方行为。

### 4.4 下载从请求装饰器中移出

模型结果文件下载属于报告和产物收集，不属于 HTTP 请求成功语义。

应拆分为两个独立结果：

```text
接口调用结果
产物收集结果
```

附件生成失败不能覆盖已经完成的接口断言结果。

### 4.5 Task ID 使用端点级响应契约

通用 `BaseTask` 不应通过 `task_id`、`id`、`request_id` 等别名启发式猜测任务 ID。不同端点应定义各自的响应模型和提取规则，并在提取前验证 HTTP 状态及响应结构。

## 5. P1：重新划分测试层与编排层

### 5.1 业务服务层不得调用 `pytest.skip`

`BaseTask` 是业务操作封装，不应依赖 pytest 控制流。否则相同代码无法稳定复用于 CLI、脚本或其他测试框架。

配置检查、跳过和失败策略应位于 Runner 或 fixture 层。

### 5.2 明确测试类型

建议划分为：

```text
tests/unit
tests/integration
tests/live
tests/protocol
```

不同测试类型使用独立的配置、Marker、入口、超时策略和报告目录。

### 5.3 Allure 结果按运行和阶段隔离

建议目录结构：

```text
allure-results/<run_id>/unit
allure-results/<run_id>/smoke
allure-results/<run_id>/protocol
```

所有 pytest 阶段结束后再统一合并，任何阶段都不应清理其他阶段的结果。

### 5.4 测试发现不依赖 `.gitignore` 白名单

测试文件应默认被版本控制，仅忽略运行产物。通过逐个放行文件控制测试集合，会让新增用例静默缺席 CI。

## 6. P2：收敛重复实现

建议按以下顺序治理：

1. 删除两个 standalone 素材脚本，统一进入 `BaseRequest`、`BaseTask` 和 pytest 执行链；
2. 合并两套媒体下载器；
3. 合并文本、图片、视频三套协议拦截 CSV loader；
4. 统一 SHA256、原子写入和 Manifest 校验工具；
5. 合并 `BaseTask` 与 `SmokeRequest` 的重复端点封装；
6. 删除同步断言外套 `async def` 的空壳方法；
7. 精简 `quality/__init__.py` 的 eager re-export，消除循环依赖和函数内反向导入。

重复实现的因果链为：

```text
同一规则存在多份实现
-> 修复只覆盖部分路径
-> 行为和错误语义持续漂移
-> 回归测试难以覆盖全部组合
-> 维护成本继续增长
```

## 7. P3：可复现性与工程一致性

- 固定 Python、pip 和依赖版本；
- 增加 `.gitattributes`，统一跨平台文本换行；
- 固定 JUnit、Allure 和 Quality 产物 Schema；
- 文档测试数量由 CI 自动生成，不再人工维护；
- 所有质量产物写入 `runs/<run_id>/...`；
- 单次运行完成后再原子更新 `latest` 指针，避免并发运行互相覆盖。

## 8. 最终实施顺序

```text
P0 统一状态模型
-> P0 统一执行计划与身份
-> P1 拆分请求副作用
-> P1 重构测试分层
-> P2 消除重复实现
-> P3 完善可复现性
```

核心判断：当前真正的架构 P0 是“单一事实源缺失”。只有先让执行状态、身份和完整性结论可靠，后续的请求层重构、Metrics、Flaky 和去重工作才具有稳定基础。
