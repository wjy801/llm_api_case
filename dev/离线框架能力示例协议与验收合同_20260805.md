# 离线框架能力示例协议与验收合同

> 日期：2026-08-05
> 合同版本：V1
> 状态：已冻结，可进入阶段1
> 适用模块：`module/offline_framework_example/`

## 1. 合同目的

本合同是离线框架能力示例阶段1～6的唯一场景事实来源，统一规定：

- 本地服务提供什么接口和响应；
- Retry与Polling以什么确定性序列运行；
- 每个分类用例负责验证什么；
- 黄金路径包含和排除哪些能力；
- Case、Runner、Quality、Metrics、Flaky和Jenkins分别消费什么证据；
- 网络、凭证、线程、Session、任务和文件如何隔离与回收。

后续实现不得在代码中形成未记录的第二套协议。若实现发现合同不可行，应先修订合同并记录原因，再修改代码。

## 2. 范围与边界

### 2.1 本合同覆盖

- BaseRequest及默认Middleware；
- RetryPolicy与请求组；
- PollingPolicy、状态迁移和严格总deadline；
- BaseTask媒体创建、轮询及复合逻辑调用；
- BaseAssertions、BaseDecorators和Allure资源附件；
- TestContext提取、类型检查和资源清理；
- `submit_with_context()`并发上下文传播；
- Runtime Hooks中性metadata；
- Runner权威收集、JUnit、Allure和Quality生命周期；
- Metrics请求成功、重试挽救和耗时事实；
- 多轮Flaky历史和现有Jenkins报告链路。

### 2.2 本合同不覆盖

- SSE和流式输出；
- 真实外部接口、账号、余额和账单；
- OpenAI、Anthropic、图片和视频等所有业务协议变体；
- 新Marker、新报告、新执行器或新扩展注册机制；
- 单条用例同时验证并发池和串行池；
- 通过随机失败制造Flaky迁移。

## 3. 公共能力实际语义

本节来自当前代码审计，后续实现必须以此为准。

| 能力 | 当前实际语义 | 示例使用规则 |
|---|---|---|
| BaseRequest配置 | 构造函数读取`base_url`、`api_key`、`timeout` | 模块Request注入离线配置，不使用真实环境域名 |
| 默认Header | 自动包含JSON Accept/Content-Type、User-Agent和Bearer Authorization | API Key固定为无权限占位值 |
| 请求参数 | 构造RequestContext时尽力深拷贝kwargs | 用Echo接口验证原payload不变 |
| 默认Middleware | RuntimeObservation → MediaResource → Redaction → Logging | 不在模块内复制任何Middleware |
| Runtime metadata | `runtime_metadata`从kwargs移除，不发送给服务端 | 单请求方法使用稳定名称和角色 |
| Retry默认状态 | 429、500、502、503、504 | 本合同只使用429和503 |
| Retry默认方法 | GET、HEAD；POST需幂等Header或`allow_post` | POST用例只通过Idempotency-Key取得重试资格 |
| Retry等待 | 支持固定/指数、Retry-After、jitter和max_elapsed | 离线场景关闭jitter并使用0等待 |
| Polling策略 | 必须显式提供；error path和result path可直接决定终态 | 合同使用自定义`$.result.url` |
| Polling总预算 | HTTP timeout、Retry等待和poll sleep共享同一deadline | 超时场景不冻结精确请求次数 |
| 严格deadline | 响应观察时已经超时则优先报告PollingTimeoutError | deadline后成功不得被接受 |
| 输入捕获 | POST前异步下载`input.media`中的URL | 用Event确认服务收到资源请求 |
| 输出捕获 | `poll_get()`成功后按`result_json_path`同步下载URL | 输出目录在fixture中重定向至临时目录 |
| Capture失败 | 输入/输出捕获失败不得覆盖业务响应 | 上限场景仍断言HTTP业务成功 |
| BaseTask复合流程 | `create_and_poll_media_generation()`建立ASYNC_TASK操作 | 黄金路径直接复用，不复制流程 |
| 嵌套operation | 已存在活动操作时内层lease不拥有生命周期 | 黄金路径只有一个顶层`media_generation`操作 |
| task_id提取 | 优先`task_id`，再尝试`id`、`request_id` | 创建响应固定返回`task_id` |
| TestContext | 支持JSONPath、Header、Cookie、Regex和transform | 每种来源由分类用例验证 |
| Cleanup | 回调按后进先出执行；全部执行后聚合错误 | 清理Request必须晚于context cleanup关闭 |
| submit_with_context | 使用`copy_context()`提交线程任务 | 每线程仍必须创建独立Session |
| Assertions | 同步实现是唯一事实源；异步和模块函数委托 | 模块领域断言继续委托同步公共实现 |
| Allure资源 | module/conftest在teardown hook统一附加输入和输出资源 | 临时文件必须存活到hook完成 |
| Quality关闭 | Runtime Hooks为Noop，不改变业务控制流 | 同一业务用例必须照常通过 |

## 4. 本地网络合同

### 4.1 网络边界

- 服务只绑定`127.0.0.1`和操作系统分配的随机端口；
- base URL格式固定为`http://127.0.0.1:{port}`；
- 禁止使用`localhost`，避免DNS和IPv4/IPv6差异；
- 所有业务路径使用相对路径；
- 所有资源URL由服务根据自身base URL生成；
- 模块Request设置`session.trust_env = False`，避免代理环境改变loopback请求；
- 任何非`127.0.0.1`目标在发出请求前立即失败；
- 本模块不读取真实`.env`域名或凭证。

### 4.2 服务生命周期

每条测试用例获得独立服务实例和独立状态：

```text
创建状态
→ ThreadingHTTPServer绑定随机端口
→ 后台daemon线程serve_forever
→ 用例执行
→ shutdown
→ server_close
→ join线程
→ 验证线程停止
```

状态更新必须持锁。业务状态只由固定响应序列和调用计数推进，不由后台定时器或随机数推进。

## 7. HTTP协议合同

## 7.1 通用Header

Request Client发送：

```text
Authorization: Bearer offline-example-key
Content-Type: application/json
Accept: application/json
User-Agent: 沿用BaseRequest默认值
```

服务端可以验证Authorization存在且等于离线占位值，但不得把完整Authorization写入响应体、失败文本或测试参数ID。

## 7.2 `POST /v1/echo`

用途：Request、默认Middleware、Header传递和payload不变性。

请求：

```json
{
  "model": "offline-media-model",
  "prompt": "offline framework example",
  "metadata": {
    "case": "request_pipeline"
  }
}
```

成功响应：HTTP 200。

```json
{
  "received": {
    "model": "offline-media-model",
    "prompt": "offline framework example",
    "metadata": {
      "case": "request_pipeline"
    }
  },
  "authorization_present": true,
  "status": "accepted"
}
```

服务计数：`echo_calls += 1`。

## 7.3 `GET /v1/transient`

用途：GET 503和429重试。

响应由场景固定：

- 503步骤：HTTP 503，`{"error":{"code":"TEMPORARY_UNAVAILABLE"}}`；
- 429步骤：HTTP 429，同步返回`Retry-After: 0`和`{"error":{"code":"RATE_LIMITED"}}`；
- 成功步骤：HTTP 200，`{"status":"ok","attempt":2}`。

每次调用：`transient_calls += 1`。

## 7.4 `POST /v1/idempotent-operation`

用途：POST幂等资格。

请求体：

```json
{
  "operation": "offline-write",
  "value": 1
}
```

允许重试场景必须发送：

```text
Idempotency-Key: offline-idempotency-001
```

服务响应序列固定为503 → 200。成功响应：

```json
{
  "operation": "offline-write",
  "status": "committed"
}
```

每次调用：`idempotent_operation_calls += 1`。

非幂等用例使用相同服务序列但不发送Idempotency-Key，BaseRequest只执行第一次请求并返回503。

## 7.5 `POST /v1/media/generations`

用途：异步任务创建和输入资源捕获。

请求体：

```json
{
  "model": "offline-media-model",
  "prompt": "offline framework example",
  "input": {
    "media": {
      "type": "image",
      "url": "http://127.0.0.1:{port}/assets/input.png"
    }
  }
}
```

成功响应：HTTP 202。

```json
{
  "task_id": "offline-task-001",
  "status": "queued",
  "model": "offline-media-model",
  "trace_id": "offline-trace-001"
}
```

响应Header：

```text
X-Request-ID: offline-request-001
Set-Cookie: offline_session=offline-session-001; Path=/
```

服务变化：

- `media_create_calls += 1`；
- `tasks[offline-task-001]`写入当前场景的Polling序列。

## 7.6 `GET /v1/media/tasks/{task_id}`

用途：Polling状态机、Retry挽救和输出资源捕获。

### 503 transport步骤

HTTP 503：

```json
{
  "error": {
    "code": "TEMPORARY_POLL_UNAVAILABLE",
    "type": "transport"
  }
}
```

该响应由Retry消费，不进入Polling业务迁移。

### pending响应

HTTP 200，状态分别为`queued`或`running`：

```json
{
  "task_id": "offline-task-001",
  "status": "queued",
  "model": "offline-media-model",
  "trace_id": "offline-trace-001"
}
```

### 成功响应

HTTP 200：

```json
{
  "task_id": "offline-task-001",
  "status": "succeeded",
  "model": "offline-media-model",
  "trace_id": "offline-trace-001",
  "result": {
    "url": "http://127.0.0.1:{port}/assets/output.png"
  }
}
```

### 失败响应

HTTP 200：

```json
{
  "task_id": "offline-task-001",
  "status": "failed",
  "error": {
    "code": "OFFLINE_TASK_FAILED",
    "type": "controlled_offline_failure",
    "message": "controlled failure"
  }
}
```

### 未知响应

HTTP 200：

```json
{
  "task_id": "offline-task-001",
  "status": "paused"
}
```

所有HTTP 200任务响应继续返回固定`X-Request-ID`和Cookie。每次transport调用：`media_poll_calls += 1`。

## 7.7 `DELETE /v1/media/tasks/{task_id}`

用途：TestContext清理。

- 任务存在：删除任务，记录`deleted_task_ids`，HTTP 204，无响应体；
- 任务不存在：HTTP 404，返回`{"error":{"code":"TASK_NOT_FOUND"}}`；
- 每次调用：`media_delete_calls += 1`。

## 7.8 `GET /v1/context`

用途：JSONPath、Header、Cookie和Regex提取。

HTTP 200：

```json
{
  "data": {
    "task_id": "offline-task-001"
  },
  "message": "trace=offline-trace-001"
}
```

Header：

```text
X-Request-ID: offline-request-001
Set-Cookie: offline_session=offline-session-001; Path=/
```

服务计数：`context_calls += 1`。

## 7.9 `GET /v1/audit`

用途：并发上下文和单次Header隔离。

请求Header：

```text
X-Audit-Name: audit-a 或 audit-b
```

HTTP 200：

```json
{
  "audit_name": "audit-a",
  "task_id": "offline-task-001",
  "status": "recorded"
}
```

服务端持锁追加`audit_records`并执行`audit_calls += 1`。结果只断言集合，不断言线程完成顺序。

## 7.10 `GET /v1/contracts/{mode}`

用途：Assertions和诊断。

| mode | HTTP | 响应 |
|---|---:|---|
| `valid` | 200 | 满足成功Schema |
| `business_error` | 400 | 标准error code/type/message |
| `invalid_schema` | 200 | 故意缺失必填字段 |
| 其他 | 404 | `CONTRACT_MODE_NOT_FOUND` |

`invalid_schema`响应不包含认证或其他敏感值。

## 7.11 静态资源

| 路径 | HTTP | 内容 |
|---|---:|---|
| `/assets/input.png` | 200 | 固定输入PNG |
| `/assets/output.png` | 200 | 固定输出PNG |
| `/assets/oversized-output.png` | 200 | 140字节固定内容 |

每次请求设置对应Event并增加独立计数。资源请求失败不改变业务任务状态。

`OfflinePollStep`只表达HTTP状态和可选业务状态，不提供回调、表达式、动态脚本或文件配置。

## 9. Retry与Polling策略合同

### 9.1 Retry

分类用例统一使用：

```text
max_attempts = 2
base_delay = 0
max_delay = 0
jitter = False
respect_retry_after = True
max_elapsed = 1
```

不设置`allow_post=True`。幂等POST只通过`Idempotency-Key`取得资格。

### 9.2 Polling

成功、失败和未知场景：

```text
status_json_path = $.status
pending = {queued, running}
success = {succeeded}
failure = {failed, cancelled}
result_json_path = $.result.url
error_json_path = $.error
unknown = fail
poll_interval = 0.01秒
poll_timeout = 1秒
```

超时场景：

```text
poll_interval = 0.01秒
poll_timeout = 0.03秒
服务持续返回running
```

超时只冻结不变量：至少一次running、最终PollingTimeoutError、保留最后状态和响应、deadline后不开始新请求、目标耗时小于0.5秒。由于真实墙钟调度差异，不冻结精确poll次数。

### 9.3 成功带重试的准确事实

```text
Transport序列：503 → queued → running → succeeded
Transport请求数：4
Retry请求组挽救数：1
Polling迁移：queued → running → succeeded
Polling迁移数：3
```

## 10. TestContext与清理合同

### 10.1 提取映射

| 变量名 | 来源 | 预期值 |
|---|---|---|
| `task_id` | `$.data.task_id`或最终响应`$.task_id` | `offline-task-001` |
| `request_id` | Header `X-Request-ID` | `offline-request-001` |
| `session_id` | Cookie `offline_session` | `offline-session-001` |
| `trace_id` | Regex `trace=([a-z0-9-]+)` group 1 | `offline-trace-001` |

类型均为`str`。分类用例另外验证transform和错误类型，但不改变黄金路径固定值。

### 10.2 清理顺序

```text
注册DELETE任务回调
→ 用例完成主要断言
→ TestContext.cleanup()
→ 确认任务已删除
→ 关闭Request Session
→ 停止本地服务
```

模块fixture必须保证Context先于Request和Service清理。不得让自动cleanup使用已关闭Session。

LIFO分类用例使用本地回调列表验证逆序；聚合错误用例必须证明后续回调仍被执行。

## 11. Capture与附件合同

### 11.1 目录隔离

测试fixture只在本模块用例生命周期内将：

- 输入媒体目录重定向至`tmp_path/input`；
- 输出结果目录重定向至`tmp_path/output`。

不修改CapturePolicy公共模型，不新增全局配置项。临时文件保持到`module/conftest.py`的teardown附件hook完成。

### 11.2 输入捕获

- payload必须包含`input.media.type=image`和loopback URL；
- 输入下载异步启动；
- 用服务端Event确认资源请求已经发生；
- 不通过固定sleep等待线程；
- 正常场景文件Hash必须等于输入资源合同。

### 11.3 输出捕获

- PollingPolicy必须设置`result_json_path=$.result.url`；
- 最终响应URL指向loopback输出资源；
- `poll_get()`返回前同步完成下载或完成fail-open处理；
- 正常场景文件Hash必须等于输出资源合同。

### 11.4 超限场景

- CapturePolicy输出上限100字节；
- 服务返回140字节固定资源；
- 业务Polling响应仍为成功；
- 不产生成功输出文件；
- 捕获失败记录不得覆盖业务结果和pytest原始结论。

## 12. 分类用例合同

用例数量是初版设计快照，不作为永久验收数量。类名、职责和黄金路径nodeid属于稳定入口。

### 12.1 Request与Middleware

文件：`test_request_pipeline.py`

| nodeid尾部 | 场景 | 主要证据 |
|---|---|---|
| `TestRequestPipeline::test_request_uses_default_middleware_and_runtime_metadata` | DEFAULT | Echo 200、调用1次、稳定metadata |
| `TestRequestPipeline::test_sensitive_headers_preserve_business_request` | DEFAULT | 服务认证通过、响应不回显Authorization |
| `TestRequestPipeline::test_middleware_does_not_mutate_original_payload` | DEFAULT | 请求前后payload深度相等 |

## 13. 黄金路径合同

稳定完整nodeid：

```text
module/offline_framework_example/test_full_framework_flow.py::TestFullFrameworkFlow::test_offline_async_media_flow
```

使用场景：`POLL_SUCCESS_WITH_RETRY`。

### 13.1 固定流程

```text
1. 启动独立服务和临时捕获目录
2. 创建OfflineFrameworkRequest/Task/Assertions/Decorators
3. Task构建新payload
4. BaseTask建立media_generation ASYNC_TASK操作
5. POST创建任务并提取task_id
6. GET Polling首次返回503
7. Retry在同一请求组内挽救并得到queued
8. 后续Polling得到running、succeeded
9. 输出捕获下载固定output.png
10. TestContext从最终响应提取task_id/request_id/session_id/trace_id
11. submit_with_context并发执行audit-a、audit-b
12. 校验状态码、JSONPath、Schema、Hash和领域关系
13. TestContext调用DELETE清理任务
14. 验证tasks为空、deleted_task_ids正确
15. 关闭各线程Request、主Request和服务线程
```

### 13.2 必须断言

- pytest结果PASSED；
- 原payload未改变；
- 创建调用1次；
- Polling transport调用4次；
- 最终状态`succeeded`；
- task_id、request_id、session_id和trace_id均等于合同值；
- 输出文件Hash等于合同Hash；
- audit集合为`{"audit-a", "audit-b"}`；
- audit调用2次；
- DELETE调用1次；
- tasks最终为空；
- 所有请求主机为`127.0.0.1`。

### 13.3 明确排除

- 不走failed、paused和timeout；
- 不捕获并吞掉核心业务异常；
- 不读取Quality、Metrics或Flaky内部实现；
- 不使用随机参数和随机失败；
- 不增加serial；
- 不使用SSE；
- 不断言本地毫秒耗时的精确数值。

- cleanup失败明确暴露，但继续执行剩余回调；
- Quality和Allure失败不改写pytest原始结论。
