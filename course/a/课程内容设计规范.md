# API 测试框架课程内容设计规范

## 1. 规范目的

本规范用于指导 26 节框架亮点课程的实际编写，确保课程能够被具备 Python、HTTP、JSON 和 pytest 基础的初学者独立阅读和理解。

课程不是功能清单、源码注释、接口手册或课堂讲稿。正文必须替代授课教师完成所有必要解释：问题为什么出现、概念为什么需要、机制怎样运行、数据怎样变化、结论为什么成立，以及框架明确不能保证什么，都必须在课程中直接说明。

读者不应依赖额外讲解，也不应依靠自行尝试或猜测才能补全关键推理。

## 2. 总体设计原则

### 2.1 按知识依赖组织，而不是按功能目录组织

课程遵循以下事实链：

```text
Retry / Polling 的正确终止
            ↓
Runner、权威 Case 集合与稳定身份
            ↓
非侵入式 Runtime Hooks
            ↓
可信质量账本
           ├─→ LLM 业务语义指标
           └─→ Flaky 历史治理
            ↓
事实所有权与设计边界收束
```

每一课都必须建立在前一课已经解释清楚的概念之上。不能因为某个功能在源码中相邻，就提前引入尚无认知基础的概念。

### 2.2 每课只回答一个核心问题

每课围绕一个具体问题组织，例如：

- 为什么一次请求设置了 timeout，整个轮询仍可能没有时间上限？
- 为什么 Case 名称相同，仍不能证明两份事实属于同一次执行？
- 为什么 Hook 异常不能改变业务结果？
- 为什么 Schema 合法和哈希一致仍不足以证明事实完整？

一节课最多新增 2～3 个核心概念。与主问题没有直接关系的设计推迟到后续课程，不能在同一课中横向铺开。

### 2.3 先展示现象，再给概念命名

课程必须从具体业务现象或具体数据开始。推荐顺序为：

```text
看见现象
→ 发现现有解释不足
→ 区分相关对象
→ 给对象命名
→ 理解框架机制
→ 推导结果
→ 明确成立前提和能力边界
```

不能从类图、源码目录、配置项列表或术语定义开始。抽象概念必须在读者已经看到它所解释的问题之后出现。

### 2.4 所有关键推理均由正文完成

正文必须完整给出：

- 初始输入与上下文。
- 事件发生顺序。
- 每一步采用的判断规则。
- 状态或数据怎样变化。
- 最终输出。
- 从输入到结论的推导过程。
- 结论能够成立的前提。
- 当前信息无法支持的结论。

异常情况同样由正文推导完成。不能使用“读者可以自行思考”“运行后即可发现”或“从源码容易看出”等方式省略解释。

### 2.5 始终区分“事实”和“对事实的解释”

课程应清楚标出：

- 原始执行事实是什么。
- 哪个组件产生或拥有该事实。
- 哪个组件只负责校验事实。
- 哪个组件根据事实产生派生结论。
- 派生结论依赖哪些前提。

例如，pytest 原始退出事实、Worker 分片、merged 输出、业务语义指标和 Flaky 治理状态属于不同层次，不能在叙述中相互替代。

## 3. 贯穿全书的统一案例

所有课程统一使用一个异步 LLM 业务案例：

```text
pytest 收集 Case
→ Runner 形成权威 Case 集合
→ Case 进入串行池或并行池
→ Worker 执行 Case
→ POST 提交 LLM 任务
→ 请求可能发生 Retry
→ 获得 job_id
→ Polling 查询业务状态
→ Runtime Hooks 记录运行事实
→ Worker 生成独立事实分片
→ Aggregator 校验并归并
→ Semantic/Metrics 解释业务语义
→ 多次 Run 的 Case 历史进入 Flaky 治理
```

### 3.1 案例一致性要求

全书应固定使用：

- 同一种 LLM 业务，例如异步图像生成。
- 同一组 Run、Execution、Case 和业务调用示例身份。
- 同一种时间表示方式，例如 `T0、T1、T2……`。
- 同一组核心状态名称。
- 同一套示例分片和 merged 数据结构。

后续课程在已有案例上增加一个新变量，不能随意更换业务背景或身份命名。

### 3.2 案例展开要求

每个案例必须直接提供：

1. 初始输入和关键配置。
2. 完整时间线或数据流。
3. 每一步新增、改变或拒绝的事实。
4. 对应的框架判断。
5. 最终输出及其含义。
6. 能够得出的结论。
7. 不能由该案例推出的结论。

失败场景用于解释机制边界，而不是留给读者寻找答案。错误发生的位置、传播过程和最终影响都必须由正文写明。

## 4. 每课固定内容结构

### 4.1 本课在事实链中的位置

开篇先回答三个问题：

- 上一课已经解释了什么？
- 本课继续解决哪个遗留问题？
- 本课结论将被后续哪个环节使用？

这一部分只回接必要的上游概念，不重复通用基础，也不提前展开后续主题。

### 4.2 本课核心问题

使用一句具体问题确定本课范围。问题应指向可观察的矛盾，不使用“了解某某功能”“掌握某某模块”一类宽泛表述。

示例：

> 每次请求都设置了 timeout，为什么整个 Polling 过程仍可能无限持续？

### 4.3 具体业务现象

先展示正常路径，再加入一个最能暴露问题的复杂条件。现象应包含明确的输入、顺序和结果。

示例：

```text
T0：发送第一次状态查询，2 秒后返回 PENDING
T1：等待 3 秒
T2：发送第二次状态查询，2 秒后返回 PENDING
T3：等待 3 秒
T4：继续下一轮查询
```

随后直接指出：单次请求虽然最多持续 2 秒，但请求与等待可以不断重复，因此完整过程仍然没有统一时间边界。

### 4.4 概念模型

从已经展示的现象中提取概念。每个新概念必须包含：

- 中文解释。
- 英文名称。
- 它解决的问题。
- 生命周期或适用范围。
- 与相邻概念的区别。

例如 timeout 与 deadline 必须放在同一时间线上对照，不能分散成两个互不关联的定义。

### 4.5 框架运行机制

按照真实执行顺序解释：

```text
输入事实
→ 条件判断
→ 状态变化
→ 新产生的事实
→ 继续或停止
→ 最终输出
```

每一个判断都应说明：

- 判断使用了什么输入。
- 判断结果有哪些可能。
- 不同结果分别走向哪里。
- 该判断缺失时会产生什么后果。

### 4.6 正常路径与复杂路径

先完整讲清正常路径，再增加重试、超时、并发、缺失或冲突。复杂路径不能同时加入过多变量，每次只增加一个主要变化，并明确它改变了哪一步判断。

推荐使用并排结构：

| 对比项 | 正常路径 | 复杂路径 |
| --- | --- | --- |
| 输入 | 明确列出 | 明确列出变化 |
| 执行过程 | 按顺序展开 | 标出出现分叉的位置 |
| 最终事实 | 完整说明 | 完整说明 |
| 能否形成结论 | 说明理由 | 说明理由 |

### 4.7 源码映射

源码只能出现在概念模型和运行机制之后。源码选择遵循以下要求：

- 每段只展示一个关键分支。
- 展示调用该代码所需的上下文。
- 解释关键输入来自哪里。
- 解释返回值或异常流向哪里。
- 解释代码执行前后状态发生了什么变化。
- 说明该方法存在是否等于真实调用链经过它。

不能整段粘贴大型类，也不能按文件顺序逐个介绍方法。

### 4.8 保证、前提与边界

每课结尾固定使用三部分陈述：

| 部分 | 写作要求 |
| --- | --- |
| 能够保证 | 只描述当前实现明确承诺的结果 |
| 成立前提 | 写明标准入口、上下文、身份、Schema 或外部契约要求 |
| 不能保证 | 主动澄清最容易被扩大理解的能力 |

边界必须出现在正文结论中，不能只放在脚注。

### 4.9 下一课衔接

结尾指出本课解决后自然出现的一个新问题，并让下一课直接承接。

示例：

> Retry/Polling 已经使复杂调用能够在明确条件下结束，但一次业务动作由此产生了多条请求事实。下一课将解决这些事实怎样归属于稳定的 Case 集合。

## 5. 四层解释深度

每个关键机制必须依次覆盖四层：

### 第一层：外部可见现象

读者能够看到什么，例如请求次数、业务状态、输出文件或 pytest 退出结果。

### 第二层：概念关系

应当用哪些对象解释该现象，这些对象怎样区分，例如 Operation 与 Request Event、timeout 与 deadline。

### 第三层：内部机制

框架怎样作出判断、传播身份、生成事实、执行校验或形成派生信息。

### 第四层：承诺边界

该机制真正保证什么，依赖什么前提，哪些结论仍需其他组件或外部系统保证。

不能只讲其中一层。只有外部现象会变成使用说明；只有内部机制会变成源码导读；只有概念定义会变成术语表；缺少边界则容易形成错误承诺。

## 6. 各模块的专用讲解要求

### 6.1 Retry/Polling

每个调用案例同时展示两条状态线：

| HTTP 层 | 业务层 |
| --- | --- |
| 请求、响应、状态码、异常、timeout | 任务是否创建、当前业务状态、是否到达终态 |

时间线必须标出：

- 每次请求开始和结束。
- 退避或轮询等待。
- 剩余 deadline。
- 方法资格与结果资格判断。
- 继续或停止的原因。
- 新增的 Request Event。

POST 重试必须明确区分客户端资格与服务端幂等契约。Polling 必须明确区分提交任务与查询已有任务。

### 6.2 Runner 与身份

身份应逐层引入：

```text
单个 Case
→ 一个 Run 中的多个 Case
→ 多个 Execution
→ 多个 Worker
→ 多份事实产物
→ 完整五级身份
```

每增加一层，都要先说明原有身份为什么不再足以区分事实，再引入下一层。最终五级身份必须使用框架真实字段，不能根据概念自行创造字段名称。

Case 集合、执行池、Worker 分配和实际完成顺序应分栏展示，说明调度变化不等于 Case 定义或事实归属发生变化。

### 6.3 Runtime Hooks

业务路径与观察路径始终分开：

| 场景 | 业务结果 | 观察事实 | pytest 原始结果 |
| --- | --- | --- | --- |
| Noop | 原样保留 | 不记录 | 原样保留 |
| 正常 Hook | 原样保留 | 正常记录 | 原样保留 |
| Hook 异常 | 原样保留 | 可能缺失 | 原样保留 |

调用图应明确标出业务响应和业务异常的所有权。fail-open 必须同时解释业务连续性和诊断事实缺失，不能只描述其中一面。

### 6.4 Aggregator

使用同一组简短分片依次经过完整校验链：

```text
Worker 分片
→ 当前 Run
→ Schema
→ 重复与冲突
→ 预期 Execution 的 Case 分片
→ 预期 Case 数量
→ JUnit identity
→ merged 输出
→ output SHA256
→ 下游消费前验证
```

每一道关卡都展示：

- 当前输入。
- 判断依据。
- 通过后保留的数据。
- 不通过时的拒绝原因。
- 该校验没有覆盖的范围。

源分片 SHA256 和 output SHA256 必须按照生成时点分别讲解，不能合并为笼统的“哈希校验”。

### 6.5 Semantic/Metrics

使用同一条事件时间线逐层标注：

```text
Operation
└─ Request Group
   ├─ Request Event
   └─ Polling Session
      ├─ Request Event
      └─ Request Event
```

每项指标都必须同时说明：

- 在哪个语义层计算。
- 分子来自哪些事实。
- 分母来自哪个权威集合。
- 缺失数据怎样表达。
- 指标不能解释什么。

至少提供两个 HTTP 请求数量相同、但业务结构不同的完整案例，并由正文直接算出不同结果，说明请求数量不能替代业务语义。

### 6.6 Flaky

始终保持三层结构：

```text
可信 P0 Case 历史 → 自动检测信号
                         ↓
                     人工治理决定
                         ↓
                     实际执行行为
```

分别说明每层的输入、输出、责任和审计信息。`QUARANTINED` 必须放回执行链中解释，明确它当前不会自动改变 pytest 选例。

Flaky 与 Metrics 的依赖关系必须画成两条从可信事实出发的分支，不能将 Metrics 画成 Flaky 的上游。

## 7. 图示规范

图示必须帮助理解关系，不能只用于装饰。

### 7.1 时间线

适用于 Retry、Polling、异步业务状态和长期 Case 历史。时间线必须标明事件、状态、判断依据和停止原因。

### 7.2 状态机

适用于 Polling 业务状态。必须区分等待态、成功终态、失败终态和未知状态，并标出每类状态的处理方向。

### 7.3 身份树

适用于五级身份与事实归属。每个节点说明唯一性范围和父级关系。

### 7.4 数据流

适用于 Worker 分片、Aggregator 和下游消费。每条边说明传递的是原始事实、校验结果还是派生信息。

### 7.5 对照表

适用于相邻概念辨析。表格必须比较同一组维度，不能只把定义并排放置。

## 8. 术语与表达规范

### 8.1 术语首次出现

首次出现时同时给出：

- 中文含义。
- 英文名称。
- 在本框架中的具体指代。
- 与相邻概念的差别。

后续课程沿用同一名称，不随意更换同义词。

### 8.2 避免省略推理

正文不使用以下表达跳过关键过程：

- “显然”。
- “不难发现”。
- “从源码可以看出”。
- “相信读者已经理解”。
- “这里不再赘述”。

如果某个结论对后续课程成立至关重要，就必须在当前上下文中完整解释，或者给出明确的前文链接和必要回顾。

### 8.3 区分四类陈述

正文必须严格区分：

1. 框架存在某项能力。
2. 当前业务模块已经启用该能力。
3. 当前真实调用链确实经过该能力。
4. 外部服务兑现相应契约。

不能从第一项直接推导后三项。

## 9. 必须贯穿课程的能力边界

以下边界在首次相关课程中完整解释，并在综合课程中统一收束：

1. 框架具备某项能力，不等于业务模块已经启用，也不等于真实调用链经过该能力。
2. POST 具备客户端重试资格，不等于服务端保证幂等。
3. 单次请求具有 timeout，不等于整个 Retry/Polling 过程具有统一 deadline。
4. fail-open 保护业务路径，但不能保证诊断事实完整。
5. Schema 合法或哈希一致，不等于事实完整、来源正确或业务结论正确。
6. Aggregator 不保证发现每个 Worker 的全部缺失分片。
7. 归并时记录源分片 SHA256，与 merged 输出写完后生成并由下游验证的 output SHA256，不是同一阶段的保证。
8. Semantic/Metrics 依赖标准入口和上下文传播；缺失数据不能解释成零。
9. Flaky 直接消费可信 P0 Case 历史，不依赖 Metrics。
10. 自动检测、人工治理和执行行为是三个不同层次。
11. `QUARANTINED` 当前不会自动改变 pytest 选例。
12. pytest 原始退出事实不能被附属组件或派生结论覆盖。

边界使用肯定陈述和完整案例说明，不能只放在注意事项或脚注中。

## 10. 每课成稿模板

```markdown
# 第 N 课：课程标题

## 本课在事实链中的位置

说明上一课的结论、本课解决的问题及其下游用途。

## 核心问题

使用一句具体问题限定本课范围。

## 从一个具体现象开始

给出输入、关键配置、时间线和最终现象。

## 为什么原有解释不够

指出需要区分的新对象或新边界。

## 核心概念

逐个解释本课新增的 2～3 个概念及其关系。

## 完整运行过程

按照真实顺序解释输入、判断、状态变化和输出。

## 正常路径

完整展开正常情况下的事实变化。

## 复杂路径

每次加入一个失败、超时、并发、冲突或缺失因素，并直接推导结果。

## 对应的框架实现

在概念模型之后展示必要源码，并逐段解释。

## 能够保证什么

陈述当前机制明确提供的保证。

## 保证成立的前提

陈述入口、上下文、身份、Schema 或外部契约要求。

## 不能保证什么

澄清容易被扩大理解的能力。

## 与下一课的关系

总结本课结论，并自然引出下一课唯一需要解决的问题。
```

模板中的标题可以根据内容略作调整，但信息结构和解释顺序不得缺失。

## 11. 不纳入课程正文的内容

课程正文不设置：

- 要求读者运行环境后自行发现结论的实验。
- 需要读者补全代码或数据的练习。
- 问答式自检、测验或评分。
- 阶段开发项目及交付物要求。
- 依赖教师现场解释的课堂活动。
- 与核心事实链无关的大段背景知识。
- 按源码目录进行的完整类和方法巡览。
- 没有直接解释的整段日志、JSON 或代码。

可以保留完整代码、日志和数据，但它们必须作为已解材料出现，并由正文逐步解释其意义。

## 12. 成稿质量要求

一节课程只有同时满足以下条件，才算形成完整的独立自学内容：

1. 读者无需外部讲解即可知道本课为什么存在。
2. 新概念均由具体现象自然引出。
3. 输入、过程、输出和结论形成闭环。
4. 关键状态变化和身份传播没有跳步。
5. 源码用于解释机制，而不是替代机制说明。
6. 正常路径与至少一种典型复杂路径均已完整推导。
7. 框架保证、成立前提和能力边界均被明确说明。
8. 术语、身份和贯穿案例与前文保持一致。
9. 本课结论能够自然支撑下一课。
10. 读者不会因为缺少操作环境而失去理解该课核心内容的必要信息。

整套课程最终应让读者沿同一条事实链持续建立理解：

```text
看见具体现象
→ 分清相关对象
→ 理解机制为何存在
→ 沿时间或数据推导结果
→ 知道结论成立的前提
→ 清楚机制的能力边界
→ 带着自然产生的问题进入下一课
```
