# API 测试框架亮点独立自学课程建议

## 1. 课程定位

本课程面向第一次系统学习该框架、但已经具备 Python、HTTP、JSON 和 pytest 基础的读者。课程不再补充通用基础知识，而是集中解释框架六项亮点背后的问题、机制、事实关系和能力边界。

建议将六项亮点拆分为 **26 节核心课**。课程材料应当能够脱离授课教师独立阅读：所有关键推理、状态变化和数据关系都由正文完整展开，不把理解所必需的步骤留给读者自行补全。

课程按照知识依赖关系组织：

```text
Retry / Polling 的正确终止
            ↓
Runner、权威 Case 集合与稳定身份
            ↓
非侵入式 Runtime Hooks
            ↓
可信质量账本
           ├─→ LLM 业务语义指标
           └─→ Flaky 历史治理
            ↓
事实所有权与设计边界收束
```

Metrics 和 Flaky 是可信账本之后的两条分支。Flaky 直接消费可信 P0 Case 历史，不依赖 Metrics。

## 2. 独立自学材料的核心写法

### 2.1 每课只回答一个核心问题

每课标题和开篇都应指向一个具体问题，例如：

- 为什么一次请求设置了 timeout，整个轮询仍可能永远不结束？
- 为什么 Case 名称相同，仍不能证明两份事实属于同一次执行？
- 为什么 Hook 失败不能让业务请求失败？
- 为什么 Schema 合法和哈希一致仍不足以证明事实完整？

正文围绕这个问题逐步推进，不同时铺开多个相互独立的主题。每课最多引入 2～3 个新概念，其余概念从前文自然承接。

### 2.2 固定采用“现象—模型—机制—边界”的解释顺序

每课按以下结构编写：

1. **承接前文：**说明上一课已经解决了什么，本课接着处理哪个遗留问题。
2. **具体现象：**先展示一次完整调用或一组具体数据，让读者看到问题怎样发生。
3. **概念模型：**为现象中的不同对象命名，并说明它们之间的区别。
4. **运行机制：**沿时间线、调用链或数据流解释框架如何处理。
5. **复杂情形：**加入失败、重试、超时、并发、冲突或缺失后，完整推导结果。
6. **能力边界：**明确框架能保证什么、依赖什么前提、不能保证什么。
7. **自然过渡：**指出本课解决后仍然留下的问题，并由此引出下一课。

术语应当在具体现象之后出现。先让读者看见问题，再给问题命名；不要从类图、目录结构或大段源码开始讲解。

### 2.3 使用一个贯穿全书的已解案例

全书统一使用同一个异步 LLM 任务：

```text
Runner 收集测试 Case
→ Case 被分配到不同执行池和 Worker
→ POST 提交 LLM 任务
→ 请求可能重试
→ 获得 job_id 后进入异步轮询
→ Runtime Hooks 记录运行事实
→ Worker 分别生成事实分片
→ Aggregator 校验并归并
→ Semantic/Metrics 解释业务含义
→ 多次 Run 的 Case 历史进入 Flaky 治理
```

后续课程只在这条主线上增加一个新变量，始终沿用相同的示例身份、Case 名称和业务背景。每个案例由正文直接给出：

- 初始输入和关键配置。
- `T0、T1、T2……` 时间线。
- 每一步产生或改变的状态与事实。
- 最终输出和完整推导过程。
- 正确结论及其成立边界。

异常情形也必须是已经讲解完成的案例。正文应直接说明错误从哪里产生、怎样沿事实链传播、最终为什么只能得到某种结论。

### 2.4 图示先于源码

不同模块使用与其认知难点相匹配的图示：

| 模块 | 主要图示 | 用途 |
| --- | --- | --- |
| Retry/Polling | 带时间刻度的调用时间线、状态机 | 解释继续、停止和时间预算 |
| Runner/身份 | Case 集合图、身份归属树 | 解释权威集合与事实归属 |
| Runtime Hooks | 业务路径与观察路径分流图 | 解释非侵入和 fail-open |
| Aggregator | 分片到可信输出的数据流图 | 解释校验顺序和数据血缘 |
| Semantic/Metrics | 四层对象关系图、逐事件统计表 | 解释业务动作与发送事件的区别 |
| Flaky | Case 历史时间线、三层治理图 | 解释检测、治理和执行的分离 |

源码只用于解释已经建立的模型。每段源码只承载一个关键分支，并在代码前说明调用背景，在代码后逐项解释输入、输出、状态变化和异常路径。不能用“可以从源码看出”代替正文推理。

## 4. 26 节课的递进设计

### 模块一：有正确性边界的 Retry/Polling

#### 第 1 课：Retry 不是“失败就再试”

从最朴素的重试循环开始，先展示“任何失败都继续发送”会造成的错误，再依次引入方法资格、异常资格和结果资格。使用同一条调用时间线说明三个判断发生的先后顺序，以及任一资格不满足时为什么必须停止。结尾只留下一个问题：即使请求具备重试资格，POST 是否真的可以安全重发？

#### 第 2 课：POST 重试资格与服务端幂等

承接第 1 课的重试资格，分别解释 `allowed_methods`、`allow_post=True` 和 `Idempotency-Key` 怎样让 POST 获得客户端重试资格。随后完整展开一个服务端没有兑现幂等契约的案例：第一次响应丢失但业务对象已经创建，客户端重试后又创建第二个对象。由此明确“客户端允许重试”和“服务端保证不会重复执行”属于两个系统的承诺。

#### 第 3 课：单次 Timeout 为什么限制不了总时长

先画出多次请求与多次退避组成的完整时间线，再区分单次请求 timeout 和整体 deadline。沿时间线解释退避为什么同样消耗时间预算，以及两个 deadline 检查点分别阻止哪一种越界。最后说明次数上限、单次 timeout 和整体 deadline 各自解决不同问题，不能相互替代。

#### 第 4 课：Polling 是业务状态机

先区分“重新提交任务”和“查询已有任务”，再定义等待态、成功终态、失败终态和未知状态。用 `PENDING → RUNNING → SUCCEEDED` 的完整轨迹说明 HTTP 成功与业务成功不是一回事，并解释为什么整个 Polling Session 只能共享一个 deadline。本课结束时指出：一次业务动作已经产生多次请求事实，下一步必须解决这些事实属于谁。

### 模块二：单一权威执行事实

#### 第 5 课：为什么必须先形成权威 Case 集合

从 pytest 收集出的 Case 列表开始，说明它为什么同时是执行输入、完整性参照和质量指标的稳定分母。对照展示“Runner 统一收集后划分”和“各 Worker 自行发现用例”两种数据演变，直接说明后一种方式怎样导致重复、遗漏或分母漂移。

#### 第 6 课：并行池与串行池只改变调度

保持第 5 课的权威 Case 集合不变，逐步展示 Case 如何进入并行池与串行池，再如何分配给 Worker。用一张“预期集合—调度位置—实际完成顺序”对照表说明：执行位置和完成次序可以变化，Case 身份和权威集合不能因此改变。

#### 第 7 课：五级身份怎样保护事实归属

使用框架实际采用的五级身份字段，从最上层运行逐级下钻到最小事实。每一级分别说明生命周期、唯一性、父子关系和传播位置，再展示两个局部名称相同的 Case 为什么仍可被完整身份区分。讲解中不使用 Worker 编号、线程号、文件名或显示名称代替完整身份。

#### 第 8 课：pytest 原始退出事实不能被覆盖

区分 pytest 原始退出、Case 结果和框架派生质量结论。完整展开“用例本身失败，同时附属质量组件也失败”的控制流，说明为什么框架可以增加诊断信息，却不能把 pytest 原始失败改写成另一种结果。由此建立后续观察设计的底线。

### 模块三：非侵入式质量观测

#### 第 9 课：为什么请求核心只依赖中性 Runtime Hooks

从“请求层直接调用质量模块”造成的耦合开始，分开业务路径与观察路径。随后说明请求核心只负责发布中性运行事实，具体质量模块负责解释和保存事实。调用链图应明确标出谁拥有业务响应、谁只能旁观，以及 Hook 为什么不能成为业务成功的必要条件。

#### 第 10 课：Quality 关闭时为什么使用 Noop

在完全相同的调用链中分别放入真实 Hook 和 Noop，逐步解释两者只改变是否记录事实，不改变请求执行结构。正文直接给出三列对照：业务响应、原始异常和 pytest 结果在开关前后保持一致，而观察产物可以不同。

#### 第 11 课：Fail-open 保护什么，又牺牲什么

先说明身份上下文怎样穿过 Worker、重试和轮询，再展开 Hook 在调用前、调用后和异常路径中失败时的控制流。明确只有 Hook 自身异常被隔离，业务异常不能被吞掉或转换成伪成功。最后说明 fail-open 保护业务连续性，却可能留下诊断缺口；缺失事实必须保持未知。

### 模块四：可信质量账本

#### 第 12 课：为什么每个 Worker 独立记录事实分片

从多个 Worker 同时写入同一产物可能产生的竞争开始，解释 Worker 独立分片怎样建立清晰的事实所有权。沿一条 Case 事实展示它从 Hook 进入 Worker 分片时保留的身份和来源，并区分事实生产者、归并者和下游消费者的责任。

#### 第 13 课：Run 与 Schema 构成归并入口

先展示一份其他 Run 的分片混入当前目录会怎样污染事实，再展示 Schema 不兼容怎样造成字段含义错位。随后解释 Aggregator 为什么必须先确认当前 Run 和 Schema。正文同时说明：Schema 合法只证明结构满足约定，不证明数据完整或业务结论正确。

#### 第 14 课：重复与冲突不能用同一种方式处理

并排展示内容完全一致的重复副本，以及身份相同但内容矛盾的两条事实。逐字段解释二者的差异，并说明简单去重为什么可能掩盖事实冲突。归并机制必须让读者看清哪些内容可以识别为重复，哪些内容必须拒绝进入可信输出。

#### 第 15 课：Case 完整性与 JUnit Identity

沿固定顺序解释预期 Execution 的 Case 分片、预期 Case 数量和 JUnit identity。为每一步给出校验前数据、校验依据和拒绝原因。最后单独说明能力范围：Aggregator 明确检查预期 Execution 的 Case 分片，但不能据此声称发现每个 Worker 的全部缺失分片。

#### 第 16 课：源分片哈希与输出哈希不是一回事

按照真实时间顺序展开：归并时记录源分片 SHA256，完成所有校验并写出 merged 文件，然后对最终输出生成 output SHA256，最后由下游消费前重新验证。通过“写完后改变一个字符”的已解案例说明下游为什么会拒绝消费，同时明确哈希只能证明内容是否变化，不能证明事实本身真实、完整或业务含义正确。

### 模块五：LLM 业务语义指标

#### 第 17 课：为什么需要四层业务语义

从一条包含提交、重试和轮询的完整时间线开始，依次定义 Operation、Request Group、Polling Session 和 Request Event。每引入一层，就说明它回答什么问题、包含哪些事件以及与上下层是什么关系。最后得到“一次业务 Operation 可以对应多次 Request Event”的完整模型。

#### 第 18 课：异步轮询指标应该归到哪一层

将第 17 课中的 Polling Session 单独展开，逐次标出查询事件、业务状态和时间消耗。说明轮询次数、轮询终态、业务耗时分别依赖哪些事实，并解释为什么不能把每次 HTTP 200 都计算成一次独立业务成功。

#### 第 19 课：什么叫一次重试挽救

并排展开“首次成功”“首次失败后最终成功”“所有尝试最终失败”三条时间线。分别给出 Request Event 层和 Operation 层的结果，再说明请求成功率与业务成功率为什么拥有不同分母。重试挽救必须落到业务动作的最终结果，而不是只统计多发送了几次请求。

#### 第 20 课：Token、媒体用量与缺失语义

从单个 Request Event 的用量字段开始，逐步归属到 Request Group 和 Operation。再展示部分事件缺少 Token 或媒体字段时，统计结果为什么必须保留 unknown 或覆盖范围，而不能填零。最后回接标准入口和上下文传播：只有身份与上下文完整，用量才能被正确归属。

### 模块六：Flaky 检测与治理

#### 第 21 课：单次失败为什么不能说明 Flaky

从同一个稳定 Case 的多次可信结果开始，依次对照稳定通过、稳定失败、通过与失败交替以及明显环境异常。说明 Flaky 描述的是可比历史中的结果波动，不是某一次失败的别名；稳定身份和可信历史是讨论 Flaky 的前提。

#### 第 22 课：可信 P0 Case 历史怎样形成

沿多个 Run 展示同一 Case 事实怎样持久化、怎样通过身份关联、怎样保留审计信息。随后画出明确的数据依赖：Flaky 直接读取可信 P0 Case 历史，Metrics 是另一类消费者，不是 Flaky 的前置环节。

#### 第 23 课：自动检测不等于人工治理

先展示自动检测怎样产生候选信号，再说明人工治理怎样基于证据形成决定。使用“事实记录—检测结果—治理决定”三列数据逐步展示每层新增了什么信息，强调统计判断不能直接替代人的治理结论。

#### 第 24 课：治理状态不等于执行行为

在第 23 课的基础上加入 Runner/pytest 执行层，完整展示检测、治理和执行三层关系。重点说明 `QUARANTINED` 当前只是治理状态，不会自动改变 pytest 选例；下一次运行中该 Case 仍然执行。任何超出这一边界的执行效果都不能写成现有承诺。

### 模块七：综合收束

#### 第 25 课：事实所有权决定组件能说什么

沿完整事实链逐一说明 Runner、Worker、Runtime Hooks、Aggregator、Semantic/Metrics 和 Flaky 分别生产、校验或消费什么事实。每个组件都使用同一张三列表述：能够保证什么、保证成立需要什么前提、明确不能保证什么。由此解释为什么组件之间不能越权替对方作出结论。

#### 第 26 课：从一次 LLM 调用走到长期治理

使用全书同一案例完成一次端到端解析：权威 Case 集合形成，POST 首次失败后重试，任务进入异步轮询，Hooks 记录事件，Worker 写入分片，Aggregator 完成校验和哈希，Semantic/Metrics 恢复业务含义，Case 历史进入 Flaky 治理。正文同时加入跨 Run 分片、Hook 事实缺失、输出被改动和 `QUARANTINED` 状态等复杂情形，逐步给出最终结论。

本课应同时提供三张完整视图：

1. 按时间排列的调用与状态变化。
2. 按层级排列的身份与事实归属。
3. 从原始事实到质量结论的数据流。

最后将同一结论分别追溯到来源事实、成立前提和能力边界，完成整套课程的认知闭环。

## 5. 模块之间怎样自然衔接

| 已经解决的问题 | 尚未解决的问题 | 因此进入下一模块 |
| --- | --- | --- |
| Retry/Polling 让复杂调用具有正确终态 | 一次业务动作产生的多份事实属于谁？ | Runner 与身份 |
| Runner 建立权威集合和稳定身份 | 怎样在不改变业务结果的情况下记录事实？ | Runtime Hooks |
| Hooks 产生具有上下文的观察事实 | 多个 Worker 的分片是否足以形成可信结论？ | Aggregator |
| Aggregator 形成可验证的可信账本 | 请求事实在业务层到底代表什么？ | Semantic/Metrics |
| 可信账本保存可归属的 Case 事实 | 同一 Case 长期表现不稳定时怎样治理？ | Flaky |
| 当前 Run 和长期历史都已得到解释 | 各组件的事实所有权和承诺边界是什么？ | 综合收束 |

每个模块开头先回接左栏，结尾明确提出中栏。这样读者不会感觉课程突然换题，而会看到下一个模块是解决上一个模块自然产生的问题。

## 6. 高难概念的解释要求

### 6.1 Retry/Polling：始终同时展示两条状态线

每个案例都同时展示：

- HTTP 层：请求、响应、异常、timeout。
- 业务层：任务是否创建、当前状态、是否到达业务终态。

只有同时展示这两条线，读者才能理解 HTTP 200 不等于业务完成，以及客户端重试资格不等于服务端幂等。

### 6.2 身份：逐层增加，不一次展示全部字段

先展示一个 Run 中的一个 Case，再增加多个 Case、多个 Execution 和多个 Worker。每增加一层，都说明旧身份为什么不再足以区分事实，然后才引入下一层。最终再给出框架实际五级身份的完整树。

### 6.3 Hooks：业务路径和观察路径永远分栏

所有调用图都将业务结果与观察结果分开。正文明确展示：

| 场景 | 业务结果 | 观察事实 | pytest 原始结果 |
| --- | --- | --- | --- |
| Noop | 原样保留 | 不记录 | 原样保留 |
| 正常 Hook | 原样保留 | 正常记录 | 原样保留 |
| Hook 异常 | 原样保留 | 可能缺失 | 原样保留 |

这张关系表贯穿 Hook 相关内容，避免把 fail-open 误解成事实仍然完整。

### 6.4 Aggregator：每经过一道关卡都展示数据变化

使用同一组简短分片逐级通过以下流程：

```text
Worker 分片
→ 当前 Run
→ Schema
→ 重复与冲突
→ 预期 Execution 的 Case 分片
→ 预期 Case 数量
→ JUnit identity
→ merged 输出
→ output SHA256
→ 下游消费前验证
```

每一步都直接展示输入、判断依据、保留的数据或拒绝原因。不要只列校验名称，也不要把所有失败情况压缩在一个大表中。

### 6.5 Semantic/Metrics：所有指标都回到来源事实和分母

解释任何指标时都同时写出：

- 它在哪一层计算。
- 分子来自哪些事实。
- 分母来自哪个权威集合。
- 缺失事实怎样表达。
- 该指标不能解释什么。

建议使用两个拥有相同 HTTP 请求数、但业务结构不同的完整案例，直接算出两套结果，说明请求数量相同并不代表业务含义相同。

### 6.6 Flaky：保持三层结构不合并

所有历史案例都按以下三层排列：

```text
可信历史事实 → 自动检测信号
                    ↓
                人工治理决定
                    ↓
                实际执行行为
```

正文分别说明每层的输入、输出和责任，避免把“检测到”“被隔离”和“执行时跳过”写成同一件事。

## 7. 必须直接给出的能力边界

以下内容应在对应课程首次出现时完整解释，并在第 25、26 课集中收束：

1. 框架具备某项能力，不等于业务模块已经启用，也不等于真实调用链经过该能力。
2. POST 具备客户端重试资格，不等于服务端保证幂等。
3. 单次请求具有 timeout，不等于整个 Retry/Polling 过程具有统一 deadline。
4. fail-open 保护业务路径，但不能保证诊断事实完整。
5. Schema 合法或哈希一致，不等于事实完整、来源正确或业务结论正确。
6. Aggregator 不保证发现每个 Worker 的全部缺失分片。
7. 归并时记录源分片 SHA256，与 merged 输出写完后生成并由下游验证的 output SHA256，不是同一阶段的保证。
8. Semantic/Metrics 依赖标准入口和上下文传播；缺失数据不能解释成零。
9. Flaky 直接消费可信 P0 Case 历史，不依赖 Metrics。
10. 自动检测、人工治理和执行行为是三个不同层次。
11. `QUARANTINED` 当前不会自动改变 pytest 选例。
12. pytest 原始退出事实不能被附属组件或派生结论覆盖。

这些边界应使用肯定陈述和完整案例直接说明，不能只放在脚注或让读者自行推断。

## 8. 每课成稿应包含的内容

为了让课程可以独立阅读，每课正文统一包含：

1. 本课在完整事实链中的位置。
2. 本课唯一要解释的核心问题。
3. 与上一课直接相关的已知结论。
4. 一个输入、过程、输出齐全的已解案例。
5. 一张最适合本课关系的时间线、状态图、身份树或数据流图。
6. 首次出现术语的中文解释、英文名称及相邻概念区别。
7. 机制在正常路径和复杂路径下的完整运行过程。
8. 必要源码片段及逐段解释，源码位于概念模型之后。
9. “能够保证、成立前提、不能保证”三部分结论。
10. 本课结论怎样自然引出下一课。

写作中避免：

- 未定义术语、缩写或身份字段。
- 使用“显然”“容易看出”等省略推理的表达。
- 只罗列配置项、类、方法或文件位置。
- 给出代码却不解释输入、输出、状态变化和异常路径。
- 使用新的业务故事替换已经建立的贯穿案例。
- 把框架能力、业务启用状态、真实调用路径和外部服务承诺混为一谈。

按照这一结构编写后，读者的理解路径将稳定保持为：

```text
看见具体现象
→ 分清相关对象
→ 理解机制为何存在
→ 沿数据或时间推导结果
→ 知道结论成立的前提
→ 清楚该机制的能力边界
→ 带着一个自然问题进入下一课
```

这正是本课程适合独立自学的核心条件。
