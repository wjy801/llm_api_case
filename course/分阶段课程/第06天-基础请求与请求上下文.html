Week 2 · Day 6

基础请求与请求上下文

今天从模块Request一路下钻到Session。重点不是记住BaseRequest的所有方法，而是理解：业务意图如何被翻译、框架控制项在哪里被消费，以及RequestContext怎样成为整条请求管线共享的事实载体。

建议用时 180～220分钟难度：基础主干学习方式：单用例逐函数前置：通过第1周门禁
本课结果：你将能画出模块Request → BaseRequest → RequestContext → Middleware → Session → Response主线，并写出成功请求和传输异常请求的生命周期差异。

01 · 目标与核心约束

请求内核的第一课：先分清数据属于谁

请求失败往往不是HTTP本身复杂，而是业务参数、框架开关和传输参数在边界处混淆。

1

理解唯一执行源

所有模块HTTP最终都进入BaseRequest与同一Session执行链。

2

读懂RequestContext

识别方法、原始路径、完整URL、传输kwargs、策略和attributes。

3

完成参数分流

区分模块业务输入、框架控制项和requests传输参数。

4

解释两种终点

Response成功返回与传输异常重新抛出共享哪些阶段、从哪里分叉。

参数混淆的因果链

业务与控制项混传
框架字段进入HTTP
服务端协议被污染
日志与观察失真
失败难以归因
本课范围护栏今天只理解Middleware经过哪些钩子、Retry会创建多个Context；具体中间件顺序与fail-open在第7课，Retry资格与等待算法在第9课。

03 · HTTP唯一实现源

模块描述差异，BaseRequest统一执行

上一节的模块Request已经交出method、相对path与kwargs。这里第一次进入公共执行源，并立即展开BaseRequest.request()，确认它消费什么、保留什么以及把什么交给Context。

模块Request

保存相对路径；把payload、业务ID和单次Header翻译成post/get/delete调用。

委托 →

BaseRequest

拥有URL构造、默认Header、Context、Middleware、Session、Retry/Polling入口与运行观察。

执行 →

requests.Session

只接收已经归一化的method、完整URL与标准传输kwargs。

3

BaseRequest.request()是第一个必须精读的关键函数

它不直接发送HTTP，而是消费控制参数、建立Operation、选择发送策略并负责最终收口。

common/base_request.py::BaseRequest.request
def request(self, method: str, path: str, **kwargs: Any) -> requests.Response:
    attach_log = kwargs.pop("_attach_log", True)
    retry_policy = kwargs.pop("retry_policy", None)
    inherit_session_headers = bool(kwargs.pop("_inherit_session_headers", True))
    stream = bool(kwargs.get("stream"))
    operation_kind = RuntimeOperationKind.SSE if stream else RuntimeOperationKind.HTTP
    metadata = self._runtime_observer.normalize_metadata(
        kwargs,
        kind=operation_kind,
        default_name="sse_request" if stream else "http_request",
    )
    operation = self._runtime_observer.start_operation(metadata)
    try:
        if retry_policy is not None:
            response = self._send_with_retry(
                method,
                path,
                retry_policy,
                attach_log=attach_log,
                inherit_session_headers=inherit_session_headers,
                **kwargs,
            )
        else:
            context = self._build_request_context(
                method,
                path,
                attach_log=attach_log,
                inherit_session_headers=inherit_session_headers,
                **kwargs,
            )
            response = self._send_single_group(context)
    except BaseException as error:
        operation.finish_error(error)
        raise
    operation.finish_response(response, stream=stream)
    return response

承接对象

method=POST、path=/v1/echo以及包含json和runtime_metadata的kwargs。

职责

request()是公共编排入口。它不直接调用Session，而是先分离框架控制参数、建立顶层Operation，再决定走单次发送还是Retry。

处理顺序

  1. 弹出_attach_log、retry_policy和_inherit_session_headers。
  2. normalize_metadata()从kwargs中消费runtime_metadata。
  3. start_operation()创建必须最终收口的Operation。
  4. 根据retry_policy选择_send_with_retry()或单Context发送。
  5. 成功时finish_response()；异常时finish_error()后原样抛出。

输入与输出

输入HTTP method、相对path、业务传输参数和框架控制参数。
交给下一层已经移除Runtime控制元数据的传输kwargs，以及构造Context所需的控制值。
最终输出Response，或原始异常。

字段变化影响

runtime_metadata不再存在于待发送kwargs中，而是变成Operation身份；json=payload继续向Context流转。
阅读重点：request()拥有编排和Operation生命周期，不拥有具体HTTP传输。下一节接收的是“清理后的传输参数”。
不要混淆：Operation表示顶层操作；Request Group表示一次逻辑请求；RequestContext表示其中一次attempt。
模块各自建Session
Header与超时不一致
日志/脱敏分叉
Retry行为不可比
故障证据碎片化
练习禁止项不要为了“看清requests”另建一个requests.Session()。那会绕过你正要学习的Context、Middleware、观察与资源所有权。

模块层必须坚持相对路径

BaseRequest兼容绝对URL并不等于模块可以硬编码环境域名；模块路径只表达API合同，环境地址来自Settings。

Session必须有唯一所有者

BaseRequest构造Session并提供close；测试通过fixture或teardown关闭，延续第4课的所有权规则。

04 · 三类参数分流

同一个函数调用里，参数有三个不同终点

承接刚刚展开的BaseRequest.request()：先区分payload、runtime_metadata和json分别属于谁，再确认控制项为什么必须在构造Context之前被消费。

模块业务输入

payload、task_id、audit_name等领域参数。模块Request负责把它们翻译成路径、json或单次Header。

框架控制参数

requests传输参数

json、params、data、headers、timeout、stream等标准参数，进入Context后传给Session。

payload传入OfflineFrameworkRequest.echo()
json=payload传入BaseRequest.post()
runtime_metadata
retry_policy
headers={"X-Audit-Name": audit_name}
timeout=1进入Context
关键证据示例module请求管线明确断言runtime_metadata不在最终RequestContext.kwargs中；它已被RuntimeObserver消费，不会成为HTTP传输参数。

05 · RequestContext解剖

Context是一次HTTP attempt的共享事实包

BaseRequest.request()在单次发送路径中调用_build_request_context()。现在第一次展开这个函数，再按字段归类说明Middleware、日志和Runtime Hooks为什么能围绕同一个Context协作。

4

_build_request_context()把零散参数冻结为一次attempt事实

重点不是创建dataclass，而是标准化数据并形成Middleware和Session共享的唯一载体。

common/base_request.py::BaseRequest._build_request_context · 完整函数体
url = self._build_url(path)
request_kwargs = self._copy_request_kwargs(kwargs)
request_kwargs.setdefault("timeout", self.config.timeout)
request_kwargs["timeout"] = self.retry_executor.clamp_timeout(
    request_kwargs["timeout"],
    deadline,
)

headers = dict(request_kwargs.pop("headers", None) or {})
request_kwargs["headers"] = self._merge_headers(
    headers,
    inherit_session_headers=inherit_session_headers,
)

return RequestContext(
    method=method.upper(),
    path=path,
    url=url,
    kwargs=request_kwargs,
    attach_log=attach_log,
    request_step_name=request_step_name,
    response_step_name=response_step_name,
    protocol=protocol or ("sse" if request_kwargs.get("stream") else "http"),
    retry_policy=retry_policy,
    polling_policy=polling_policy,
)

承接对象

method、相对path、清理后的传输kwargs，以及BaseRequest持有的默认配置和Session Header。

职责

_build_request_context()把分散参数标准化为一个只属于当前attempt的RequestContext。这一阶段仍未发送HTTP。

处理顺序

  1. 由path构造完整url。
  2. 复制kwargs，避免后续Middleware直接修改调用者数据。
  3. 补默认timeout，并在存在deadline时夹紧到剩余预算。
  4. 取出本次headers，与Session默认Header合并。
  5. 确定protocol，构造并返回Context。

输入与输出

输入method/path/kwargs、默认timeout、Session Header及可选deadline。
输出一个包含身份字段、传输kwargs和策略引用的RequestContext。
尚未产生Response、异常结果、Request Group结束状态和Operation终态。

字段变化影响

path → urlpath保留稳定业务身份；url加入环境地址，供Session传输。
kwargs形成当前attempt独有的传输副本。
timeout缺省值被补齐；外部deadline可以缩短本次请求预算。
headers本次Header与Session Header合并，结果只属于当前Context。
阅读重点：Context不是“随便装参数的字典”，而是下一阶段唯一接收的attempt事实对象。

构造Context时发生的标准化

复制kwargs标准dict/list尽量deepcopy，保护调用方输入
补齐timeout没有显式值时使用Settings默认值
裁剪剩余预算存在deadline时不能超过剩余时间
合并HeaderSession默认值 + 单次请求Header
可变性边界普通payload会被深拷贝后交给Middleware；这正是test_middleware_does_not_mutate_original_payload能够验证调用方字典不变的基础。

06 · 成功请求主线

一次无Retry POST穿过八个阶段

Context已经构造完成。现在第一次进入发送阶段，立即展开Group绑定、Middleware钩子与Session.request()，再用八阶段视图整理主线。

5

Group管理逻辑请求，_send()真正进入Middleware与Session

最后一跳要分清：Group归并attempt、Context携带事实、Session执行HTTP。

common/base_request.py::BaseRequest._send_single_group
group = self._runtime_observer.start_request_group(
    method=context.method,
    path=context.path,
    protocol=context.protocol,
    configured_max_attempts=1,
)
group.bind(context)
try:
    return self._send(context)
finally:
    group.finish()
common/base_request.py::BaseRequest._send
self._run_before_middlewares(context)

try:
    response = self.session.request(
        method=context.method,
        url=context.url,
        **context.kwargs,
    )
except Exception as error:
    self._run_exception_middlewares(context, error)
    raise

self._run_after_middlewares(context, response)
return response

承接对象

上一节输出的单个RequestContext，其中已经包含Session所需的method、完整url与标准化kwargs。

职责

_send_single_group()为这次逻辑请求创建Request Group并绑定Context；_send()负责执行Middleware与Session。

处理顺序

  1. 创建configured_max_attempts=1的Request Group。
  2. group.bind(context)把当前attempt事实挂入Group。
  3. before Middleware读取或补充同一个Context。
  4. Session.request(method, url, **kwargs)执行HTTP。
  5. 有Response时进入after Middleware；Session抛异常时进入exception Middleware。
  6. 无论结果如何，Group都在finally中结束。

输入与输出

输入一个标准化后的RequestContext。
成功输出Session返回的原始Response。
异常输出Session抛出的原始传输异常，不伪造Response。
运行事实Group保存当前Context；Middleware记录请求、响应或异常事实。

分支影响

HTTP 200、400或503只要Session返回了Response，都属于Response路径；只有Session直接抛异常且没有Response时，才属于传输异常路径。

阅读重点：Request Group归并attempt，_send()执行传输，两者通过同一个Context连接。Response或异常随后回到request()完成Operation收口。
Request Group与Context不是同一层一次无Retry请求只有一个Context；启用Retry后，一个逻辑Request Group会绑定多个attempt Context。第8课再展开资格与等待。

07 · 成功与异常分叉

传输异常没有Response，但仍有完整观察终点

两条路径共享Context和before_request，分叉点是session.request()返回Response还是抛异常。

成功响应路径

1

Session返回requests.Response。

2

全部Middleware执行after_response。

3

Request Group在finally结束。

4

Operation记录Response与流式标记。

5

同一个Response返回模块Task/Test。

分叉

传输异常路径

1

Session抛ConnectionError/Timeout等异常。

2

Middleware执行on_exception。

3

观察附件故障只作为note附加，不替换原异常。

4

Request Group仍在finally结束。

5

Operation finish_error并重新抛出原异常。

不要把HTTP 4xx/5xx混同为传输异常只要Session成功返回Response，仍走after_response路径；状态码是否可接受由业务断言或Retry策略继续判断。

五处源码在对应章节展开后，再统一提炼

  1. Task表达业务动作，模块Request翻译端点和协议参数。
  2. BaseRequest.request()消费框架控制项并拥有顶层Operation。
  3. _build_request_context()标准化一次attempt的事实与传输参数。
  4. Request Group归并逻辑请求，Context只属于一个attempt。
  5. _send()是Middleware和Session的真实执行边界。

→ Task.submit_echo(request, payload)
→ OfflineFrameworkRequest.echo(payload)
→ BaseRequest.post("/v1/echo", json=payload, runtime_metadata=...)
→ BaseRequest.request("POST", path, **kwargs)
→ RuntimeObserver消费runtime_metadata并创建Operation
→ _build_request_context()生成单次attempt的RequestContext
→ _send_single_group()创建Request Group并绑定Context
→ before Middleware
→ Session.request(context.method, context.url, **context.kwargs)
→ after Middleware
→ Request Group.finish()
→ Operation.finish_response(response)
→ Response返回Task、Test与Assertions

关键结论：Response沿原调用栈返回；Request Group和Operation只负责记录运行事实，不替换业务Response。

答案二：传输异常的完整顺序

Session.request(...)抛出ConnectionError或Timeout
→ _run_exception_middlewares(context, error)
→ _send()重新抛出原异常
→ _send_single_group()在finally中执行group.finish()
→ BaseRequest.request()执行operation.finish_error(error)
→ 原异常继续抛回Task与Test

关键结论：只有Session直接抛异常且没有形成Response时，才属于传输异常路径。HTTP 4xx或5xx只要返回了Response，仍属于Response路径。

答案三：本用例中的RequestContext快照

字段整理后的值作用
methodPOST由post()转换为公共请求方法。
path/v1/echo保留模块定义的业务相对路径。
urlSettings.base_url + /v1/echo由BaseRequest拼接后交给Session。
kwargsjson、默认或显式timeout、合并后的headers这是Session真正接收的标准传输参数。

attributes初始为空，后续可由Middleware或Runtime Hooks补充保存诊断和attempt扩展事实，不进入服务端协议。

答案四：输入参数最终去了哪里

输入消费位置是否进入Context.kwargs
runtime_metadataRuntimeObserver创建Operation身份否
retry_policyrequest()选择单次发送或Retry分支否
_attach_logBaseRequest转换为Context的报告控制字段否

最终答案Task表达业务动作，模块Request翻译协议，BaseRequest消费框架控制项并组织生命周期，RequestContext保存一次attempt事实，Request Group归并逻辑请求，Session只执行标准HTTP参数，Response或原异常最终沿调用栈返回。

10 · TOC边界决策

当前约束：参数能传进去，却不知道应该在哪里被消费

把每个变化放回唯一所有者。错误归属通常不会立刻报错，而会把控制字段泄漏到Session或把环境差异硬编码进模块。

决策顺序

先问“它表达业务、控制框架还是控制传输”，再问“消费后是否应继续向下”。框架控制项必须在Session边界之前消失。

把audit_name翻译成X-Audit-Name单次Header
相对路径与Settings.base_url拼成完整URL
消费runtime_metadata并建立Operation身份
为Middleware保存脱敏副本、Logger和attempt属性
执行已经标准化的method、url和kwargs
测试结束后关闭BaseRequest持有的Session

Design Choice · Boundary

设计选择与适用边界：每次HTTP attempt拥有独立RequestContext

现
当前方案

BaseRequest统一执行HTTP；每次attempt创建并复制一份RequestContext，承载真实kwargs、响应、异常、计时和诊断attributes。

替
替代方案

在函数间传递松散参数，或把当前请求状态写入模块级/Session级可变对象。

因
选择理由

attempt级上下文让Middleware共享同一事实，又把Retry不同尝试隔离开；复制输入可防止诊断或并发路径反向污染调用者。

界
不适用条件

纯函数或无HTTP生命周期的本地转换不需要RequestContext；若对象跨attempt复用，必须改用更高层只读operation状态而不能复用当前上下文。

12 · 完整复述

不用看源码，用一段话讲清这次请求

复述不是背函数名，而是检查你能否连续说明输入对象如何变化、每层拥有哪部分责任，以及成功和异常在哪里分叉。

业务输入Task委托Request协议翻译BaseRequest编排Context标准化Group与SessionResponse或异常
测试先构造业务payload，并调用Task的submit_echo()。Task只表达“提交Echo”这个业务动作，把Request对象和payload交给模块Request；模块Request决定使用POST、相对路径/v1/echo、JSON body和Runtime元数据。随后BaseRequest.request()消费框架控制项与Runtime元数据，创建Operation，并在本用例中选择无Retry分支。_build_request_context()生成完整URL、默认timeout和合并后的Header，把一次attempt的传输参数冻结到RequestContext。Request Group绑定这个Context，_send()依次经过before Middleware、Session和after Middleware。Session返回Response后，Operation按Response收口并交给Assertions；如果Session直接抛异常，则走exception Middleware、Group finally和Operation错误收口，再原样抛出。
对象连续能从payload一直讲到Context、Response和运行事实，中间不跳层。
所有权准确Task不拥有HTTP执行，Session不拥有Operation，Context只属于一次attempt。
边界保守不把HTTP 503说成传输异常，也不把运行元数据说成服务端JSON字段。
