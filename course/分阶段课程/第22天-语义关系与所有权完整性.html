WEEK 5 · DAY 22

语义关系与所有权完整性

学习P1 Semantic如何归并Request Group、Polling Session与Operation分片，并准确描述当前P0来源门禁：只检查Manifest可解析、run_id、status=complete和request-metrics原始bytes Hash，不校验P0版本，也不拒绝integrity_status=failed。

建议时长 3 小时OperationRequest GroupLimited P0 gate
可核验产出：语义实体关系图、所有权完整性表、当前P0门禁/未检查项对照表，以及本轮Semantic Manifest核验记录。

前序输入

直接上游是Day21已完成写入的P0 Manifest与request-metrics；当前Semantic门禁只绑定run、提交状态和目标文件Hash。

本日新增

Operation、Request Group、Polling Session与通过当前有限门禁的P0请求事件之间可双向核对的所有权图。

能力缺口

P0 manifest/schema版本和integrity_status没有在_load_p0_evidence中校验，因此不能把输入称为完整性可信P0。

2

merge_semantic_run()拥有整轮归并编排和提交分支

入口先写merging Manifest，再按固定顺序扫描分片、加载P0、验证关系；成功与异常都转换为可观察的Semantic结果。

编排与所有权

输入

SemanticMergeRequest只声明run和根目录；函数自行派生分片目录、合并目录与Manifest路径。

状态所有者

_MergeState持有本轮加载的Group、Session、Operation、P0 RequestMetric、来源统计和全部Issue；后续函数都在同一个state上读写。

成功分支

四类JSONL先原子写入，再从磁盘计算Hash，最后以status=complete提交Manifest并返回结果摘要。

异常分支

未处理异常被转换成semantic_merge_failed，函数尽力写status=failed Manifest并返回强制FAILED结果，不把原异常继续抛给调用者。

有限准入的准确答案

输入

P0 merged/manifest.json、merged/request-metrics.jsonl以及本轮run_id。

通过条件

Manifest可读取、run_id一致、status=complete、目标文件存在，并且磁盘bytes Hash等于Manifest的output_hashes["request-metrics"]。

未检查边界

代码没有读取P0的integrity_status，也没有校验P0 manifest/schema/merge版本。因此即使integrity_status=failed，只要上述条件成立，函数仍继续解析。

输出与失败方式

有效记录按request_event_id进入state.p0_requests；缺失、Hash不符、解析错误或冲突被记录为Issue。多数分支是return或continue，不是抛异常。

4

_validate_relationships()不创建关系，只验证引用能否闭合

关系记录已经由Semantic分片加载到state；本函数只检查正向引用、反向引用、唯一所有者、attempt顺序和作用域身份，并把问题追加为Issue。

    for group in state.request_groups.values():
        referenced_operation = state.operations.get(group.operation_id)
        if referenced_operation is None:

        else:
            if group.request_group_id not in referenced_operation.request_group_ids:

                    state,
                    "group_missing_from_operation_references",
                    group.request_group_id,

            if group.invocation_id != referenced_operation.invocation_id:

输入

提交语义答案

输入

同一_MergeState、Manifest路径、调用者选择的status以及已落盘目标文件的output_hashes。

两个状态轴

status由编排函数传入，可能是merging、complete或failed；integrity_status由Issue严重级别计算。两者不是同义词。

关键分支

归并流程没有抛异常时，即使关系Issue使integrity_status=failed，调用者仍会写status=complete，表示“写入事务完成但内容完整性失败”。

输出所有权

write_json_atomic()拥有最终Manifest字节；Manifest把P0证据Hash、分片统计、实体计数、Issue计数和四类输出Hash绑定到同一run。

完成第一遍代码阅读后，你应能直接回答

  1. merge_semantic_run()拥有整轮路径、顺序、成功提交与异常收口。
  2. _load_p0_evidence()只证明P0已提交且request-metrics目标bytes与Manifest声明Hash匹配，不检查P0 integrity_status。
  3. _validate_relationships()验证现有记录的引用与唯一所有者，只生成Issue，不修复关系。
  4. _write_manifest()分别记录写入status与内容integrity_status，因此complete和failed可以同时出现。
  5. 本节测试证明一个具体fixture完成归并并写出证据，不等价于证明所有输入来源都完整性可信。

01 · Second-pass concepts

第二遍总结：Hash绑定不等于P0完整性可信

完成代码主线后再抽象概念：P0只回答每次attempt发生了什么；Semantic把请求事件组织成所有权图。当前实现能证明所读request-metrics属于指定run的complete Manifest且bytes Hash匹配，但没有读取P0 integrity_status，也没有验证P0 manifest/schema版本。

实际检查

Manifest存在且JSON可解析、run_id一致、status=complete、request-metrics存在且Hash匹配。

未检查

P0 manifest_version、schema_version、merge_version和integrity_status。

准确结论

来源已提交并与Manifest声明的目标bytes一致；不能推出P0完整性状态可接受或发布者可信。

TOC约束：课程必须把“当前代码实际门禁”与“更完整的理想准入模型”分开。若P0为status=complete且Hash匹配，即使integrity_status=failed，当前Semantic仍会继续读取并建立关系。

02 · Semantic entities

三类主实体回答不同粒度的问题

实体核心身份与引用回答的问题
RequestGroupRecordgroup_id、operation_id、可选polling_session_id、attempt_event_ids一次逻辑请求经历了几次真实attempt，首尾传输结果如何？
PollingSessionRecordsession_id、operation_id、request_group_ids轮询了几次、观察了哪些状态、sleep多久、最终为何结束？
OperationRecordoperation_id、group_ids、session_ids、evidence_refs一次业务意图的结果、总耗时、usage和证据范围是什么？

三类实体都继承run、execution、worker、case、invocation和created_at身份。关系验证不仅比较ID是否存在，还比较这些作用域身份是否一致。

03 · Collection chain

运行时上下文逐步积累关系，结束时固化记录

begin Operation→start Group→bind RequestContext→collect attempt event IDs→finish Group→finish Operation

semantic_context.py使用ContextVar维护当前Operation、Request Group与Polling Session。Runtime Adapter只拿到handle并调用上下文函数；SemanticCollector负责把完成的不可变模型写到worker分片。

嵌套Operation通过owned语义复用父操作；并发请求使用独立上下文与唯一ID；未正常结束的pending对象由finalize_pending()写为INCOMPLETE，而不是假装成功。

04 · Ownership graph

Operation是业务边界，Group是P0事件的唯一语义所有者

关系必须满足
Operation → Groupoperation.request_group_ids包含Group，且group.operation_id反向一致
Group → Request Event每个attempt_event_id存在于P0 request-metrics，且不能被多个Group拥有
Operation → Sessionoperation.polling_session_ids包含Session，且session.operation_id一致
Session → Groupsession引用的Group存在、属于同一Operation，且group.polling_session_id指回Session
Operation usage → Eventsource与missing event都来自该Operation拥有的Group，两个集合不重叠

evidence_refs是Operation最终引用的证据集合，不允许引用图外事件。所有权规则让后续指标能够精确回答分母来自哪里。

05 · Polling semantics

poll_count、Request Group数量和attempt数量是三个不同事实

一次轮询调用通常每轮产生一个Request Group，而每个Group又可能因Retry产生多个attempt event。因此：

poll_count

业务状态查询次数。

group count

Polling Session引用的逻辑请求次数。

attempt count

所有Group实际发出的HTTP attempt总数。

Polling Session还保存状态序列、首次观察偏移、sleep总时长、terminal_status与final_outcome。Operation的polling_total_ms和polling_sleep_ms来自Session事实，不从请求数量猜测。

06 · SSE and async task

SSE与异步任务把跨阶段请求收口到一个Operation

SSE

HTTP Group提供响应头阶段事实，Stream事件补充首数据、首内容、流持续时间和complete/interrupted/error/not_consumed终态。

Async task

创建请求、多个轮询Group和媒体结果usage共同属于一个async_task Operation，Polling Session只是其中的子关系。

Operation的usage保存input/output token、媒体数量或时长、来源event IDs、缺失event IDs和完整度。缺失不会变成0；CONTROL流量角色也不会被伪装成WORKLOAD。

07 · Semantic merge

先扫描Semantic分片，再载入P0证据验证关系

  1. 写status=merging的Semantic Manifest。
  2. 扫描request-groups、polling-sessions、operations和semantic integrity分片，执行run过滤、Schema验证与重复处理。
  3. 读取P0 merged/manifest.json并解析JSON，只检查run_id与status=complete；再读取request-metrics原始bytes并核对Manifest声明的Hash。当前路径不检查P0版本或integrity_status。
  4. 建立P0 request_event索引，执行关系与身份验证。
  5. 原子写出四类Semantic合并文件并计算Hash。
  6. 提交status=complete Manifest，保存p0_evidence的Manifest Hash和Request Metrics Hash。

扫描顺序不改变硬依赖：Semantic最终使用已提交且request-metrics Hash匹配的P0建立关系；这不是完整性可信声明。在阶段图上，它的直接上游是P0，产物只向Metrics输出；Flaky Import从同一份已完成提交的P0独立起步，但会执行自己的准入策略，不串接在Semantic或Metrics之后。

08 · Relationship integrity

存在性、唯一性、反向引用和身份必须同时成立

验证层典型问题后果
存在性Group引用不存在的P0 event或Session生成ERROR Issue
唯一性同一个event被两个Group拥有所有权冲突
反向引用Operation列出Group，但Group.operation_id不一致关系不闭合
作用域身份run相同但case、invocation或execution不一致跨上下文污染
用量证据usage引用Operation之外的event或source/missing重叠usage来源不可解释

最终完整性状态仍采用complete、degraded、failed。关系问题通常是ERROR，因为它会破坏后续指标的成员资格；采集阶段显式标记的不完整记录可以形成WARN和degraded。

11 · Design choice

设计选择与适用边界

现方案用稳定身份显式建模Operation、Request Group和Polling Session，并验证正向引用、反向引用与唯一所有者。
替代方案按时间邻近、URL相同或日志顺序推断请求属于哪个业务操作。
选择理由重试、轮询和异步任务会打乱时间与顺序；显式身份和所有权能给出确定关系，并允许发现孤儿与多重归属。
不适用条件完全无跨请求语义的一次性调用可只保留事件事实；若以分布式Trace为权威来源，则需要接入trace/span模型而非重复造身份。
