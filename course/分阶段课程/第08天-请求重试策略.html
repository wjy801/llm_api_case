DAY 08 · RETRY BY CONTRACT

请求重试策略

重试不是“失败后再跑一次”，而是在业务意图可安全重复、故障具备瞬时性、次数与等待仍在预算内时，显式地再次执行同一请求。

建议 1.5～2.5 小时前置：完成第07天门禁只运行确定性离线测试核心：common/retry*.py
完成标志：面对 GET 500、GET 400、POST 有无幂等键、Timeout、SSL 和断言失败，你能先判断是否有重试资格，再解释等待、终止结果和证据。

01 · First principles

先回答“为什么可以再执行”，再讨论“重试几次”

一次失败只说明当前 attempt 没有得到期望结果，不自动证明再次发送是安全、有效或值得的。成熟重试机制首先约束副作用和错误类型，其次才计算等待。

1

区分失败与资格

显式策略、方法资格、故障类别和预算缺一不可。

2

守住幂等边界

解释 GET/HEAD、POST 幂等键与 allow_post 的风险差异。

3

计算真实等待

掌握 fixed/exponential、jitter、Retry-After 和 max_elapsed。

4

解释终止事实

区分最后响应、原异常、attempt 记录和实际等待。

TOC 约束链：瞬时失败 → 习惯性“全都重试” → POST 重复副作用、确定性缺陷被隐藏、执行时间失控 → 用例偶尔通过但证据失真。真正约束不是重试代码不会写，而是没有先建立恢复资格的决策顺序。

02 · Mental model

RetryExecutor 前有资格闸门，循环内还有故障与预算闸门

继续下一次 attempt = 显式策略 ∧ 方法有资格 ∧ 故障可恢复 ∧ 次数和等待仍在预算内任意一项不成立，就不能把“再试一次”当成默认动作。
闸门 1

策略显式传入

BaseRequest 默认不重试。RetryPolicy 自身虽有默认字段，请求没有传 retry_policy 仍只执行一次。

闸门 2

方法可安全重复

默认允许 GET/HEAD；POST 需要请求级幂等键，或明确设置 allow_post=True。

闸门 3

故障可能瞬时恢复

默认状态为 429、500、502、503、504；异常为 ConnectionError、Timeout，SSL 被排除。

闸门 4

仍有次数与时间

尚未达到 max_attempts，且下一段等待不会突破 max_elapsed 或外层 deadline。

业务调用一个 operation
→
Request Group聚合 attempts
→
Attempt 1独立 Context
→
分类 + 等待记录并查预算
→
Attempt N新 Context
→
最终事实Response 或原异常
计数语义：max_attempts=3 表示最多三次总尝试，不是首次请求后再重试三次，因此最多只有两段等待。

03 · Policy contract

RetryPolicy 是冻结策略对象，不是全局自动开关

策略位于 common/retry.py，以 frozen Pydantic model 表达，避免同一调用过程被其他代码悄悄改写。

字段默认值真实含义
max_attempts3包含首次请求的最大总尝试数，最小为 1。
retry_statuses429, 500, 502, 503, 504400、404 默认不触发恢复。
retry_exceptionsConnectionError, TimeoutSSL、TooManyRedirects 显式禁止。
backoffexponential支持 fixed 与 exponential。
base_delay / max_delay0.5 / 10.0 秒计算基数与单段等待上限。
jitterTrue普通退避在 0 到上限间随机，降低并发惊群。
respect_retry_afterTrue优先读取秒数或 HTTP-date，有效时不施加 jitter。
max_elapsed30.0 秒局部恢复的已耗时加下一段等待预算。
allowed_methodsGET, HEAD默认有方法资格的集合，忽略大小写。
allow_postFalse无幂等键时是否仍显式允许 POST。
idempotency_headerIdempotency-Key识别 POST 资格的 Header 名称。

最小显式用法

from common import RetryPolicy

response = self.request.get(
    "/v1/models",
    retry_policy=RetryPolicy(
        max_attempts=3,
        base_delay=0.5,
        jitter=False,
    ),
)
不要混淆：“RetryPolicy 默认 max_attempts 为 3”与“BaseRequest 默认重试三次”是两件事。没有传策略时，BaseRequest 走单次请求路径。

04 · Idempotency boundary

幂等键赋予 POST 重试资格，但不会凭空创造幂等性

1. 规范方法名转为大写
2. 查 allowed_methods默认 GET / HEAD
3. POST 特判allow_post 或幂等 Header
4. 其他方法默认只发一次

推荐：请求级幂等键

每个写操作使用稳定、唯一且可追踪的键，由服务端保证同一键只提交一次。Header 只作用于本次请求，不污染 Session。

response = self.request.post(
    "/v1/idempotent-operation",
    json=payload,
    headers={"Idempotency-Key": operation_key},
    retry_policy=policy,
)

高风险：allow_post=True

这只是客户端“允许再次发送”的声明，不会生成幂等键，也不会阻止重复扣费、创建或写入。

启用前必须证明：接口天然幂等，或服务端另有去重合同，并有测试保护。

安全边界：框架以 Header 名称存在作为资格信号，不验证值是否唯一，也不验证服务端是否真的去重。资格判断不能替代业务合同。

05 · Failure classification

响应、传输异常和确定性缺陷的终止方式不同

默认可恢复

  • HTTP 429
  • 500 / 502 / 503 / 504
  • ConnectionError
  • Timeout

默认不可恢复

  • HTTP 400 / 404
  • SSLError
  • TooManyRedirects
  • 断言失败和代码错误

终止结果

  • 响应耗尽：最后 Response
  • 异常耗尽：最后原异常
  • 不可恢复响应：立即返回
  • 不可恢复异常：立即抛出
场景是否等待最终事实原因
GET + 400否400 Response不在默认状态集合。
GET + 503，下一次成功是200 Response状态、次数和预算都允许。
GET + 503，attempt 用尽此前可能等待最后 503 Response响应路径不制造新异常。
GET + Timeout，attempt 用尽此前可能等待最后一次 Timeout保留原失败类型与堆栈。
POST 无幂等资格 + 503否第一次 503 Response方法闸门在循环前阻止重试。
断言失败为何不重试：业务断言通常在请求返回之后，不属于传输恢复循环；用重试掩盖断言失败会把确定性缺陷伪装成瞬时波动。

06 · Backoff and budget

等待由来源优先级与预算共同计算

指数模式为 base_delay × 2^(attempt_index - 1)，再受 max_delay 限制。有效 Retry-After 优先，非法值回退到普通退避。

当前计算结果
0 ～ 1 秒
来源：指数退避，再应用 jitter

Retry-After 优先

支持非负秒数和 HTTP-date。有效时无 jitter，但仍受 max_delay 截断。

max_elapsed 预判

比较“当前已耗时 + 下一段等待”，越界便不 sleep、不进入下一 attempt。

响应路径越界

返回当前可恢复 Response，例如 503。

异常路径越界

重新抛出当前原异常，不用通用超时覆盖它。

与第9天衔接：max_elapsed 是一次 RetryExecutor 的局部预算；Polling 还有覆盖 HTTP attempt、Retry 等待和 poll sleep 的总 deadline。

07 · Execution lifecycle

每次 attempt 都有新 RequestContext，但共享一个 Request Group

选择路径观察执行器。新 Context 使中间件与 attempt 属性隔离；Group 把同一业务请求的实际尝试聚合起来。

职责边界：每个 attempt 都通过 BaseRequest._send() 执行中间件与 transport。RetryExecutor 只拥有编排，不接管 Context 构建、中间件和 HTTP 传输。

08 · Observable evidence

Attempt、RetryAttemptRecord 与实际等待是三种事实

RequestContext

每次发送都有独立 Context，包含 attempt_index 和 max_attempts。

回答：第几次真实发送？

RetryAttemptRecord

记录促使恢复判断的失败、原因、计算等待、状态码或异常。

回答：为什么考虑继续？

Request Group

聚合所有 Context、配置上限和真实执行的累计等待。

回答：调用实际尝试多少次？

Allure / Quality

日志挂载 records；Runtime Hooks 在 Quality 开启时映射事实，关闭时为 Noop。

回答：如何下钻与聚合？
细粒度陷阱：RetryAttemptRecord 在预算检查前生成，所以 max_elapsed 否决 sleep 后仍可能有“计算等待”；Request Group 的 retry_wait_seconds 只在真实 sleep 后增加。提议等待不等于已执行等待。

10 · Decision lab

重试决策表：先判资格，再判故障

统一前提：均显式传入默认 RetryPolicy，尚有剩余 attempt 且预算充足。选择当前失败是否触发下一次 attempt。

GET 返回 500：方法与状态都符合。
GET 返回 400：方法有资格，状态不可恢复。
POST 返回 503，无幂等键：状态可恢复，方法无资格。
POST 返回 503，有 Idempotency-Key：框架资格通过。
GET 抛 ConnectTimeout：属于 requests.Timeout。
GET 抛 SSLError：被显式排除。
响应后的业务断言失败：不是传输恢复信号。

11 · Knowledge check

知识自测

答对 5 题视为达标。沿四道闸门判断，不以“提高成功率”为理由。

1. 创建 RetryPolicy 但没有传给请求，BaseRequest 执行几次？
答案 C。只有显式收到 retry_policy 才进入 RetryExecutor。
2. max_attempts=3 的准确含义？
答案 B。最多三次 transport attempt、两段等待。
3. POST 带 Idempotency-Key 后，框架证明什么？
答案 A。Header 是客户端资格信号，不是服务端去重证明。
4. 有效 Retry-After 与普通退避同时存在时如何处理？
答案 C。非法 Retry-After 才回退到 fixed/exponential。
5. 503 后等待会突破 max_elapsed，响应路径返回什么？
答案 B。max_elapsed 的响应路径保留当前 Response。
6. 哪个事实最能证明等待真的执行过？
答案 A。Record 可能在预算否决前生成，Group 只累计真实 sleep。
