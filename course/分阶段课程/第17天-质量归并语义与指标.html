DAY 17 · TRUST BEFORE AGGREGATION

质量归并、语义与指标

第16天回答“发生了哪些原始事件”，今天回答“这些事件是否可信、彼此如何关联、最终能计算什么”。指标不是事实的替代品，而是建立在可信事实和完整关系之上的派生视图。

Case / Request / FailureOperation / Group / PollingManifest / Hash / SchemaMetrics Completeness
今日结果：能够从一个pytest invocation出发，沿P0归并、Semantic关系和Metrics来源验证，解释为什么请求失败数、逻辑调用失败数、测试失败数不能互相替代。

01 · Learning contract

目标与核心约束

今天不是学习如何把更多数字塞进报告，而是学习一条更严格的推导链：原始事实可信、关系完整、语义明确之后，数字才有解释价值。

1

区分事实层级

明确Case、Request、Failure和Operation分别回答什么问题，避免用请求结果替代测试结果。

2

理解语义关系

解释Request Event、Request Group、Polling Session和Operation的所有权与引用关系。

3

证明来源可信

理解Manifest、Schema版本、原始文件Hash、run_id和跨产物证据为什么必须一致。

4

保留缺失语义

掌握complete、partial、missing、no_data和not_applicable，禁止把未知值悄悄变成0。

第一性原理：Metrics是派生结论，不是原始事实。若来源不可信，正确行为是FAILED；若来源可信但覆盖不完整，正确行为是DEGRADED或部分完整；只有证据和关系都满足合同，才允许AGGREGATED。
原始分片→P0归并→Semantic关系→来源验证→Metrics视图
TOC约束：本课最容易卡住的不是聚合公式，而是把不同层级的“成功/失败”混为一谈。先解除事实层级约束，再讨论成功率、重试挽救率和usage覆盖率。

02 · Fact hierarchy

四类事实：谁都不能替代谁

事实核心模型回答的问题不能推出
Case事实CaseResultpytest某个setup/call/teardown阶段发生了什么，最终用例是否通过。不能仅凭通过断定所有HTTP请求成功。
Request事实RequestMetric一次真实HTTP attempt的状态码、耗时、超时、可重试性、业务状态和usage。不能仅凭500断定pytest用例失败。
Failure事实FailureRecord失败用例的稳定分类、责任域、置信度和可比较指纹。不会为每个失败请求都生成测试Failure。
Semantic事实OperationRecord等多个attempt、轮询请求和流式消费共同构成了哪个业务动作。不能覆盖CaseResult或修改pytest退出码。

典型因果链

服务返回预期的 400 ├─ RequestMetric.business_status = failed ├─ Operation.outcome = failed ├─ 测试断言 error.code 与 error.type 正确 └─ CaseResult.final_status = passed 因此：请求失败数 ≠ 逻辑调用失败数 ≠ 测试失败数
负向用例并不矛盾：被测业务调用按真实语义失败，但测试目标正是验证该失败契约，所以pytest可以通过。Metrics必须保留业务失败，不能为了让成功率好看而改写成success。

HTTP成功

通常指transport获得响应且状态码满足某种区间，不等于业务字段成功。

业务成功

来自稳定业务状态或Operation outcome，不等于测试断言通过。

Pipeline成功

由pytest原始退出码和Jenkins阶段事实决定，不由Metrics反推。

03 · Stable identity

稳定身份让分片能够归并

并发worker各自写文件，归并器并不依赖文件顺序猜测归属，而是依赖同一套稳定身份把记录重新连接起来。

run_id └─ execution_id └─ worker_id └─ case_id：去掉参数后的稳定nodeid └─ invocation_id：run_id + case_id + param_hash ├─ CaseResult：按phase记录 ├─ RequestMetric：每次attempt一个request_event_id └─ Semantic：operation_id / group_id / polling_session_id
身份稳定性用途
case_id跨运行稳定表示测试定义；参数部分从nodeid中分离。
param_hash相同参数稳定基于脱敏后的规范化参数生成，避免把密钥写进身份。
invocation_id单次run内稳定连接Case、Request、JUnit与Semantic事实。
request_event_id每次attempt唯一重试时每次真实请求独立记录，不能复用。
interface_id接口模板稳定由method、脱敏url_template和protocol组成，动态路径段模板化。
为什么不能按文件名或时间戳关联：xdist并发顺序不稳定，时间接近也不代表同一业务动作；只有显式身份和引用关系才能证明所有权。

04 · P0 merge

P0事实归并：先提交清单，再写最终事实

merge_quality_run()把execution-worker分片和JUnit证据归并为当前run的可信基础事实。它采用“先写merging Manifest，完成后再写complete Manifest”的提交协议。

扫描分片

读取cases-*.jsonl、requests-*.jsonl、integrity-*.jsonl，记录物理行、当前run记录、外来run、非法JSON、非法Schema和重复情况。

读取JUnit

验证文件存在性与新鲜度，解析quality身份；JUnit提供统计和失败详情，但不能覆盖Case分片。

对账

核对权威计划的expected_case_count、invocation数量和JUnit身份，发现缺失、陈旧或状态不一致。

分类失败

仅对Case raw/final状态为failed或error的记录，组合JUnit、RequestMetric与integrity证据生成FailureRecord。

原子写出

输出case-results、request-metrics、failures、integrity-issues，并按原始文件bytes计算SHA256后提交complete Manifest。

去重不是简单丢弃

记录唯一键相同重复冲突重复
CaseResultinvocation_id + phase计入exact_duplicatesERROR：case_result_conflict
RequestMetricrequest_event_id计入exact_duplicatesERROR：request_metric_conflict
IntegrityIssuesource、code、related_id、message计入exact_duplicatesERROR：integrity_issue_conflict

complete

没有WARN或ERROR，事实和对账完整。

degraded

存在WARN，仍可保留事实，但使用者必须知道覆盖或一致性下降。

failed

存在ERROR或归并异常，高阶消费者不得假装来源可信。

Manifest不是目录索引：它同时声明run身份、版本、状态、来源统计、输出数量、输出Hash和完整性结论。只有status=complete且Hash匹配的产物才是已提交证据。

05 · Failure classification

失败分类与稳定指纹

FailureRecord服务于历史比较和责任定位，因此必须先脱敏、规范化动态内容，再生成稳定指纹；它不能直接复用每次变化的异常全文。

失败Case→JUnit错误详情+Request证据+Integrity代码→分类与指纹
优先规则分类典型证据
1CONFIGURATION缺少环境变量、API Key、权限、Settings校验错误。
2FRAMEWORK_DEFECT错误位置在quality目录，或相关integrity code以quality开头。
3ENVIRONMENTDNS、连接拒绝、代理、SSL、磁盘空间。
4TEST_DEFECT测试代码中的KeyError、IndexError、TypeError等本地错误。
5TRANSIENT429、rate limit、可重试timeout或连接重置。
6PRODUCT_DEFECT唯一接口上的契约、Schema、响应或状态码断言问题。
兜底UNKNOWN证据不足，保留低置信度而不是强行猜测。
failure_id 输入 ├─ phase ├─ error_type ├─ normalized_message │ ├─ URL查询参数脱敏 │ ├─ 时间戳 / UUID / 内存地址归一化 │ ├─ 动态长数字与路径ID模板化 │ └─ 临时目录替换 ├─ 唯一 interface_id（若证据唯一） └─ assert_location
不要倒因为果：一次RequestMetric失败不会自动生成FailureRecord。只有pytest Case失败或错误时，归并器才尝试分类；否则负向用例、重试中间失败和轮询pending都会被错误地当成测试缺陷。

06 · Semantic graph

语义关系不是一条直线，而是一张有所有权的图

Operation表示业务动作；Request Group表示一次逻辑请求及其重试attempt；Polling Session表示一段轮询会话；Request Event表示一次真实网络尝试。

pytest case / invocation └─ logical operation ├─ request_group_ids：Operation直接引用全部Group │ ├─ create group │ │ └─ request_event_id(s) │ └─ polling group(s) │ └─ request_event_id(s) └─ polling_session_ids └─ request_group_ids：只引用本次轮询的Group 轮询Group同时满足： group.operation_id = operation.operation_id group.polling_session_id = session.polling_session_id
模型关键内容主要约束
RequestGroupRecordattempt事件、重试等待、首尾transport/status、总耗时。attempt_count等于事件数；final event属于事件集合。
PollingSessionRecordpoll次数、状态序列、sleep、终态和首次观察偏移。poll_count等于所引用Group数量。
OperationRecordkind、name、role、model、outcome、timing、usage和证据。SSE必须有stream_outcome；非SSE不得携带该字段。
OperationUsagetoken、媒体用量、已知与缺失来源事件。missing/not_applicable不能携带伪造数值；complete不能仍有缺失事件。
总纲中的关键细节：Operation的request_group_ids包含轮询Session中的Group。Polling Session不是把Group从Operation中“拿走”，而是在Operation所有权之上增加轮询会话归属。

07 · Relationship integrity

关系完整性：每个引用都必须能被证明

Semantic归并器先验证P0 Manifest和request-metrics Hash，再检查图关系；Metrics加载时会再次执行更严格的来源合同。重复验证不是浪费，而是在不同消费者边界阻止错误扩散。

Event → Group

  • 一个request_event只能属于一个Group。
  • attempt_index必须从1连续增长。
  • 接口、协议、method和URL模板必须一致。
  • Group首尾结果必须与首尾Event证据一致。

Group → Operation

  • Group引用的Operation必须存在。
  • Operation也必须反向包含该Group。
  • run、case、invocation身份必须一致。
  • 一个Group不能被多个Operation拥有。

Session → Group

  • Session引用的轮询Group必须存在。
  • Group的polling_session_id必须匹配。
  • Session和Group必须属于同一Operation。
  • poll_count必须等于Group数量。

Usage → Event

  • 已知与缺失Event集合不能重叠。
  • Usage Event必须位于该Operation内。
  • 一个Usage Event不能属于多个Operation。
  • 缺失必须显式记录，不能补0。
孤儿事实必须阻断：只要存在未分配Group、缺失Event、跨invocation引用或Hash不匹配，Metrics不能继续把这些数据当成可信样本。

08 · Source trust

Metrics先验证证据链，再读取数字

load_sources()不是普通文件读取器。它执行的是一份信任合同：身份、版本、提交状态、Hash、跨层引用和关系必须全部成立。

读取run.json

RunRecord必须合法且run_id等于本次聚合目标。

验证P0 Manifest

manifest_version、schema_version、run_id和status必须精确匹配；P0完整性为failed时直接拒绝。

验证P0 Request Hash

按原始文件bytes计算SHA256，必须与Manifest的request-metrics输出Hash一致。

验证Semantic Manifest

检查semantic版本、complete状态和完整性；还要确认Semantic记录的P0 Manifest与Request Hash正是当前P0证据。

验证全部Semantic输出

request-groups、polling-sessions、operations和integrity-issues逐个校验Hash、Schema与记录内容。

重新验证关系

构建唯一索引，检查所有权、身份、attempt序列、首尾证据、usage归属和孤儿记录。

run.json + merged/manifest.json + merged/request-metrics.jsonl + semantic/merged/manifest.json + semantic/merged/request-groups.jsonl + semantic/merged/polling-sessions.jsonl + semantic/merged/operations.jsonl + semantic/merged/integrity-issues.jsonl ───────────────────────────────────── 通过身份 / 版本 / status / Hash / 关系验证 = MetricsSources
Metrics结果含义典型原因
aggregated来源可信、有workload Operation、没有降级原因。正常完成且覆盖完整。
degraded来源仍可用，但运行或覆盖存在已知缺口。run未完成、P0/Semantic降级、operation或usage不完整。
no_data来源可信，但没有可聚合的workload Operation。只有control流量或本轮没有业务调用。
failed来源合同不成立，不能发布指标。Manifest不可信、Hash不匹配、Schema错误、关系断裂。
陈旧文件不是兜底：只要run_id、提交状态或Hash不属于本轮，就必须拒绝；不能因为旧文件可解析、数字看起来正常，就拿它替代本轮缺失证据。

09 · Metrics semantics

指标分三层，缺失值永远不偷偷变成0

Builder只把TrafficRole.WORKLOAD纳入业务指标。CONTROL、UNKNOWN、not_applicable usage和未分配Event都会进入Exclusions或Issue，而不是混入成功率分母。

粒度回答的问题代表性指标
Operation一个业务动作整体是否成功、耗时多少、用了多少token或媒体资源。outcome、success rate、total timing、usage、retry extra usage。
Request Group一次逻辑请求是否重试、首尾结果如何、重试是否挽救。attempt count、retry rate、HTTP/business rescue rate、retry wait。
Request Event真实attempt层面发生了多少timeout、429、5xx和业务失败。transport分布、HTTP 5xx/429 rate、duration、usage coverage。

覆盖率模型

NumericAggregate

eligible_count = sample_size + missing_count

sample_size = 0
→ total / mean / min / max = null
→ completeness = no_data 或 not_applicable

RatioAggregate

value = numerator / sample_size

sample_size = 0
→ value = null
→ completeness = no_data

unknown_count > 0
→ completeness = partial
语义应该如何表达禁止做法
真实值为0sample_size包含该样本，数值字段为0。与“没有观测到值”混淆。
值缺失missing_count增加，聚合完整性为partial或no_data。把缺失token写成0。
不适用使用not_applicable，例如明确不产生usage的Operation。算入usage缺失率。
未知角色进入Exclusions与unknown_traffic_role Issue。默认当作workload。
指标的可解释性来自分母：任何成功率都必须同时保留numerator、sample_size、unknown_count和completeness。只展示一个百分比，会隐藏样本为空或覆盖不完整的事实。

步骤3：还原一个含轮询的Operation

function Read-JsonLines([string]$Path) {
  @(Get-Content -LiteralPath $Path | Where-Object { $_.Trim() } | ForEach-Object {
    $_ | ConvertFrom-Json
  })
}

$events = Read-JsonLines 'reports/quality/merged/request-metrics.jsonl'
$groups = Read-JsonLines 'reports/quality/semantic/merged/request-groups.jsonl'
$sessions = Read-JsonLines 'reports/quality/semantic/merged/polling-sessions.jsonl'
$operations = Read-JsonLines 'reports/quality/semantic/merged/operations.jsonl'

$operation = $operations |
  Where-Object { @($_.polling_session_ids).Count -gt 0 } |
  Select-Object -First 1
if ($null -eq $operation) { throw 'No polling operation found' }

$ownedGroups = @($groups | Where-Object {
  $operation.request_group_ids -contains $_.request_group_id
})
$ownedSessions = @($sessions | Where-Object {
  $operation.polling_session_ids -contains $_.polling_session_id
})
$ownedEventIds = @($ownedGroups | ForEach-Object { $_.attempt_event_ids })
$ownedEvents = @($events | Where-Object {
  $ownedEventIds -contains $_.request_event_id
})

[pscustomobject]@{
  Operation = $operation.operation_id
  Kind = $operation.operation_kind
  Outcome = $operation.outcome
  Groups = $ownedGroups.Count
  PollingSessions = $ownedSessions.Count
  Attempts = $ownedEvents.Count
  UsageCompleteness = $operation.usage.completeness
}

逐个核对：每个轮询Group既在Operation的request_group_ids中，也在对应Session的request_group_ids中；每个Event只属于一个Group。

12 · Exit gate

本课门禁：没有可信来源，就没有可信指标
