WEEK 4 · DAY 18

Flaky历史、状态机与Artifact信任边界

Flaky不是“这次失败了”的别名，而是同一可比较身份在可信历史中呈现不稳定结果。只有样本身份、epoch、产物完整性和状态职责都清楚，治理动作才不会变成掩盖问题。

Comparable identityEvidence windowDetection stateGovernance stateRaw bytes SHA-256
今日交付：能解释单次失败为什么不能确认Flaky，能区分detected_state与current_state，并能判断一个Artifact错误应该由通用读取器还是领域消费者负责。

01 · Learning contract

目标与核心约束

第一性原理：Flaky判断是在回答“相同条件下是否出现相互矛盾的可重复结果”。如果“相同条件”未被证明，后面的概率、状态和治理都没有意义。

1

证明样本可比较

从case、参数、环境、执行画像和epoch构造稳定身份，不把不同实验条件混成历史。

2

分开检测与治理

自动状态描述证据判断；人工状态描述组织决策。两个维度不能互相覆盖。

3

守住产物边界

通用工具验证字节与结构，消费者解释Manifest、版本和领域失败。

TOC约束链：产物不可信 → Observation不可用 → 历史不可比较 → 自动状态无意义 → 人工治理可能误伤。因此今天的瓶颈不是状态枚举，而是“可信且可比较的证据”。

阅读顺序

flaky_models.py→flaky_importer.py→flaky_store facade / projection / governance→repository公开边界→artifact_io.py→metrics/validation.py

阅读quality/flaky_store/repository.py时只追踪公开输入输出、事务边界和约束，不逐行研究SQL。

02 · Comparable identity

可比较样本不是“同名用例”，而是同一实验条件

把不同参数、环境或并发模型下的结果混在一起，会制造假Flaky；把同一身份拆得过细，又会永远积累不到证据。身份设计是在两类错误之间建立边界。

epoch_scope_key = hash(case_id, environment, execution_profile) flaky_key = hash(case_id, param_hash, environment, execution_profile, state_epoch) observation_id = hash(run_id, flaky_key)
字段回答的问题边界
case_id是否是同一个逻辑用例身份。不能只靠显示名称或执行顺序猜测。
param_hash是否是同一组参数化输入。不同参数结果不能互相证明Flaky。
environment是否运行在同一目标环境。测试、预发、生产镜像不能默认可比。
execution_profile是否处于同一串并行执行画像。并发竞争问题不能混入串行稳定历史。
state_epoch是否属于同一段可比较历史。重大基线变化后必须显式切断旧历史。
run_idObservation来自哪一次运行。同一run对同一flaky_key形成稳定Observation身份。
比较谓词：只有case_id + param_hash + environment + execution_profile + state_epoch一致，并且规则版本兼容，两个结果才应进入同一Flaky证据窗口。

03 · Execution profile and epoch

执行画像描述运行方式，epoch描述历史边界

同一用例在串行与并行下可能具有不同竞争条件；同一画像在实现或规则发生不兼容变化后，也不能继续消费旧历史。

运行来源规范化执行画像意义
serial-poolserialRunner串行池。
parallel-poolparallelRunner并行池。
manual-pytest + mastermanual-serial直接pytest主进程。
manual-pytest + gwNmanual-parallel直接pytest的xdist worker。
其他稳定组合custom:*未知来源不会随意坍缩为同一画像。

什么时候需要新epoch

应该reset

  • 执行语义或被测基线发生明确不兼容变化。
  • Flaky规则版本不兼容，导入器要求显式切段。
  • 旧历史已不能回答当前实验条件下的问题。

不应该reset

  • 为了让一个难看的状态消失。
  • 仅仅因为本轮失败或人工判断不舒服。
  • 存在ACTIVE或RECOVERING治理时绕过恢复流程。
epoch 0可信基线改变 → 显式resetepoch 1新历史重新积累
epoch不是删除历史：reset针对已有scope执行previous_epoch + 1并写override审计。旧Observation仍可追溯，只是不再与新样本混算。

04 · P0 artifacts to Observation

Flaky导入先验证整条P0信任链

导入器不是从一个pytest结果直接写数据库。它先证明本轮Quality产物完整、同源、版本兼容，才能把Case生命周期折叠为Observation。

确认必需产物

run.json、merged/manifest.json、case-results.jsonl、failures.jsonl和integrity-issues.jsonl必须存在。

验证run与Manifest

核对身份、状态、Schema/版本、输出清单、原始bytes Hash和完整性问题，拒绝未完成或被篡改的来源。

折叠Case生命周期

collection、setup、call、teardown必须能形成完整生命周期；破碎阶段不能被猜成最终结果。

建立结果证据

skip、xfail、xpass不进入Flaky观察；failed/error必须关联唯一FailureRecord与failure_id。

幂等写入历史

Observation、导入记录、状态投影和审计必须在明确事务边界内完成。

source_digest防止“同一来源被改写”

已有记录再次导入结果
同一run_id、同一digest完全相同来源NOOP 幂等返回，不重复制造Observation。
同一run_id、不同digest运行身份相同但产物内容变化CONFLICT 拒绝历史改写。
不同run_id、同一digest复制一套产物伪装成新运行CONFLICT 拒绝来源重放。
禁止捷径：不能只读取JUnit中的pass/fail就写Flaky库。缺少Failure指纹、Manifest与完整性验证时，“历史”只是无法审计的猜测。

05 · Evidence window

证据窗口比较的是结果签名，不只是通过率

默认窗口最多保留20个可比较样本。每个样本形成稳定结果签名，状态机用签名切换、pass/fail数量和连续稳定段共同判断。

结果签名

pass

fail:<failure_id>

两个失败如果failure_id不同，签名也不同；这能暴露失败模式漂移，但仅有失败指纹变化仍不足以自动确认Flaky。

窗口语义

total_observation_count = 历史总数
sample_size = 当前窗口样本数
evidence_window_size = 20

总历史可继续增长，状态判断只使用规则定义的可比较窗口。

默认规则阈值作用
稳定最小样本3OBSERVING连续同签名后进入STABLE。
确认最小样本4避免极少样本直接定性。
确认pass / fail至少2 / 2必须存在相互矛盾的结果证据。
确认outcome切换至少2次不是“一次失败后一直失败”。
SUSPECTED清除连续5个同签名重新证明当前行为稳定，可稳定为pass或同一失败。
恢复稳定连续5个同签名RECOVERING用独立恢复阈值判定。
为什么单次失败不能确认Flaky：Flaky需要“同一身份下相互矛盾且重复出现”的证据。一个失败只说明本轮失败，既没有2个pass和2个fail，也没有足够outcome切换。

07 · Projection

detected_state与current_state回答不同问题

一个用例可以在证据上仍被确认Flaky，同时在组织决策上处于隔离或恢复。Projection必须同时保留这两个事实，而不是用一个字段覆盖另一个。

字段所有者允许状态回答的问题
detected_state自动证据规则OBSERVING、STABLE、SUSPECTED、CONFIRMED历史证据判断是什么？
current_state投影后的当前治理视图自动状态加QUARANTINED、RECOVERING当前应该按什么治理状态展示和决策？

ACTIVE隔离

detected: CONFIRMED+governance: ACTIVE

current_state = QUARANTINED，但检测事实仍保留CONFIRMED。

恢复观察

detected evidence+governance: RECOVERING

current_state = RECOVERING；连续稳定可到STABLE，签名再次切换则回CONFIRMED。

模型约束：detected_state不能写入QUARANTINED或RECOVERING。否则自动算法会被迫解释owner、到期时间和组织风险，这些都不是证据能推导出的事实。

09 · Artifact trust boundary

通用Artifact工具负责机械事实，领域消费者负责业务合同

util/artifact_io.py

  • 读取UTF-8 JSON对象。
  • 逐行读取JSONL并报告行号。
  • 对文件原始bytes计算SHA-256。
  • 比较Hash和精确字段。

不负责：Manifest版本、Schema兼容性、状态机与领域错误类型。

领域消费者

  • Metrics翻译为MetricsSourceError。
  • Flaky翻译为FlakyImportError。
  • Reporting按自身合同生成中文warning或局部降级。
  • 各自决定版本、状态和必需输出。

负责：解释“这个机械错误对本领域意味着什么”。

Hash保护的是文件字节，不是解析后的JSON语义

Manifest登记的文件

{"a":1}\n

对这组原始UTF-8 bytes计算SHA-256。

被重新格式化后

{
  "a": 1
}\n

解析结果可能等价，但bytes已经变化，Hash必须不匹配。

禁止重新序列化再Hash：如果先解析JSON、排序字段、统一空白后再计算Hash，就会把文件被改写的事实抹掉，Manifest失去防篡改价值。

10 · Safe practice

临时数据库实践：验证公开边界，不碰Jenkins持久化库

本课实践只运行CLI帮助与框架已有Flaky测试。测试夹具会提供隔离数据库和受控产物；不要为了观察状态直接连接或修改Jenkins使用的长期SQLite文件。

安全边界：不运行真实Smoke、不调用付费接口、不复用Jenkins持久化数据库、不手工修改Flaky表来“制造状态”。

步骤1：确认CLI公开命令

.\.venv\Scripts\python.exe -m quality.cli --help

重点识别flaky-import、flaky-history、flaky-reset-epoch、flaky-db-check、flaky-state-evaluate、flaky-state、flaky-state-rebuild和治理命令。参数以实际--help为准，不凭记忆拼接。

步骤2：运行Flaky专项测试

.\.venv\Scripts\python.exe -m pytest tests/quality -k flaky -q

测试重点保护身份生成、导入幂等、epoch切段、状态投影、治理前置条件、事务审计和错误翻译。

步骤3：用因果链复盘失败

测试失败→先定位产物/身份/规则/治理哪一层→检查最早失真的事实→修复根因→重跑专项测试

12 · Exit gate

本课门禁：治理不能超越证据与职责边界

一句话验收：Flaky导入只接受身份、版本、状态和原始bytes Hash均可信的P0产物；自动状态只根据同一epoch内的可比较签名判断证据，人工治理通过current_state表达隔离与恢复并留下审计，任何治理都不应篡改Observation或暗中改变pytest结果。
