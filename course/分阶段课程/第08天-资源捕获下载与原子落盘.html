01 · 问题与策略边界

Capture增强证据，但不能重新定义业务结果

业务创建、task_id提取、轮询终态和断言已有所有者。Capture只决定是否下载输入/输出资源以及大小上限；下载失败必须可见并清理残留，但不能替代业务Response。

本节借主用例确定策略边界，不把该用例解释成对所有Capture生命周期的覆盖。

CapturePolicy只表达开关与上限

策略不执行下载，也不判断业务成功

@dataclass(frozen=True)
class CapturePolicy:
    capture_input_media: bool = True
    capture_output_results: bool = True
    max_input_bytes: int | None = None
    max_output_bytes: int | None = None

    def __post_init__(self) -> None:
        for name in ("max_input_bytes", "max_output_bytes"):
            value = getattr(self, name)
            if value is not None and value <= 0:
                raise ValueError(f"{name} must be greater than 0")
源码精讲

04 · 输出Capture控制流

wrapper先接管调用，但只有内层poll_get成功返回后才开始下载

装饰器调用发生在进入poll_get之前；真正的输出Capture门槛是response = func(...)成功完成。若轮询抛异常，后续URL提取和下载不会执行。

本节入口

用例文件tests/test_capture_downloads.py测试方法test_output_download_failure_does_not_replace_polling_response关键实现函数common.base_request.BaseRequest.poll_get → common.base_decorators.BaseDecorators.download_links_from_poll_get

download_links_from_poll_get()的时间顺序

先得到业务Response，再执行可降级副作用

def download_links_from_poll_get(self, func: F) -> F:
    @wraps(func)
    def wrapper(instance: Any, path: str, *args: Any, **kwargs: Any) -> requests.Response:
        capture_policy = getattr(instance, "capture_policy", DEFAULT_CAPTURE_POLICY)
        polling_policy = kwargs.get("polling_policy")
        result_json_path = getattr(polling_policy, "result_json_path", None)
        response = func(instance, path, *args, **kwargs)
        if result_json_path is None or not capture_policy.capture_output_results:
            return response
        try:
            link_value = self._extract_json_path_value(response, result_json_path)
            for url in self._extract_urls(link_value):
                try:
                    file_path = self._download_url(
                        url, DOWNLOAD_DIR,
                        max_bytes=capture_policy.max_output_bytes,
                    )
                    self._record_model_result_file(file_path)
                except Exception as error:
                    self._attach_download_failure(url, error)
        except Exception as error:
            self._attach_download_failure("<result-json-path>", error)
        return response
源码精讲

wrapper先读取策略与结果路径，再调用内层poll_get；只有拿到Response后才决定跳过、提取URL或下载。下载与提取错误被附件化，最后仍返回原Response。

承接对象

被装饰的poll_get、实例、path、轮询策略和Capture策略。

职责

在业务轮询完成后追加输出下载副作用。

处理顺序

进入wrapper → 读策略 → 调内层poll_get → 得Response → 提取URL → 下载 → 返回Response。

输入输出

输入为poll_get调用；输出始终是内层成功返回的同一个Response。

字段/状态变化

成功下载时记录文件；失败时附加失败文本，Response引用不变。

边界

内层poll_get抛异常时不会进入输出Capture；装饰器不把下载失败提升为业务失败。

05 · 原子下载事务

download_url()拥有从临时文件到最终发布的完整事务

最终路径不是写入起点，而是提交结果。函数先写唯一.part，在响应和文件上下文关闭后执行replace；任何异常都删除临时路径与目标路径。

本节入口

用例文件tests/test_capture_downloads.py测试方法test_download_limit_removes_partial_file关键实现函数util.downloads.download_url

该测试直接证明流式超限后的目录清理；成功replace时机来自生产函数控制流，不扩写为该测试已覆盖。

流式下载、大小判定与原子发布

事务边界全部位于同一个生产函数

def download_url(
    url: str,
    download_dir: Path,
    *,
    fallback_name: str = "download",
    timeout: float | tuple[float, float] = 600,
    cancel_event: Event | None = None,
    max_bytes: int | None = None,
) -> Path:
    if cancel_event is not None and cancel_event.is_set():
        raise DownloadCancelled()
    download_dir.mkdir(parents=True, exist_ok=True)
    file_path = unique_file_path(
        download_dir / filename_from_url(url, fallback_name=fallback_name)
    )
    temporary_path = file_path.with_name(
        f".{file_path.name}.{uuid.uuid4().hex}.part"
    )
    written = 0
    try:
        with requests.get(url, stream=True, timeout=timeout) as response:
            response.raise_for_status()
            content_length = response.headers.get("Content-Length")
            if max_bytes is not None and content_length and int(content_length) > max_bytes:
                raise DownloadLimitExceeded(f"download exceeds {max_bytes} bytes")
            with temporary_path.open("wb") as output:
                for chunk in response.iter_content(chunk_size=1024 * 1024):
                    if cancel_event is not None and cancel_event.is_set():
                        raise DownloadCancelled()
                    if not chunk:
                        continue
                    written += len(chunk)
                    if max_bytes is not None and written > max_bytes:
                        raise DownloadLimitExceeded(f"download exceeds {max_bytes} bytes")
                    output.write(chunk)
        temporary_path.replace(file_path)
        return file_path
    except Exception:
        temporary_path.unlink(missing_ok=True)
        file_path.unlink(missing_ok=True)
        raise
源码精讲

头部长度可提前拒绝；流式累计值可处理中途超限；取消在请求前和每个分块前检查。两个with都退出后才replace，失败路径统一双清理。

承接对象

URL、下载目录、可选取消事件和字节上限。

职责

拥有.part → close → replace事务与异常回滚。

处理顺序

预检查 → 建临时路径 → 打开响应 → 流式写入/校验 → 关闭资源 → replace。

输入输出

输入为下载参数；成功输出最终Path，失败重新抛异常。

字段/状态变化

written递增；临时文件出现；成功后最终路径出现且临时路径消失。

边界

源码说明事务顺序；当前超限测试只直接证明流式超限后目录为空。

def start_media_downloads(payload: Any, *, policy=DEFAULT_CAPTURE_POLICY):
    if not policy.capture_input_media:
        return []
    tasks = []
    for media_type, url in _extract_media_entries(payload):
        task = MediaDownloadTask(
            media_type=media_type,
            url=url,
            max_bytes=policy.max_input_bytes,
        )
        thread = threading.Thread(
            target=_run_download,
            args=(task,),
            name=f"media-download-{media_type}",
            daemon=True,
        )
        thread.start()
        tasks.append(task)
    _record_media_download_tasks(tasks)
    return tasks

07 · 取消与线程边界

设置cancel_event只是请求取消，不是完成确认

当前teardown收集tasks并调用附件函数；未完成任务只设置取消事件和附加回退文本。代码没有保存线程句柄，也没有执行任何同步等待。

本节入口

用例文件module/offline_framework_example/test_capture_assertions.py测试方法TestCaptureAndAssertions.test_input_capture_uses_only_loopback_resource关键实现函数module.conftest._attach_collected_test_resources → util.media_resources.attach_media_download_steps → util.media_resources._run_download

覆盖边界：该用例观察输入Capture成功落盘；取消请求、done、join与线程终止结论来自生产代码阅读，不声称存在直接取消测试。

teardown只消费任务状态并请求取消

附件收口不等于线程同步收口

源码精讲

teardown停止收集并把tasks交给附件函数；已完成且文件存在时附文件，未完成时只调用cancel_event.set()并附加“未完成”文本。

承接对象

当前测试收集到的list[MediaDownloadTask]。

职责

根据当下状态附加文件或回退诊断，并对未完成任务发出取消请求。

处理顺序

停止收集 → 遍历task → 判断is_done/file_path → 附件或set取消。

输入输出

输入为tasks；输出为附件副作用，无完成状态返回值。

字段/状态变化

边界

当前teardown不能证明worker已观察取消、done_event已设置或线程已经终止。

done_event只能由worker的finally设置

取消请求与完成事实之间仍隔着worker执行

@dataclass
class MediaDownloadTask:
    media_type: str
    url: str
    cancel_event: threading.Event = field(default_factory=threading.Event)
    done_event: threading.Event = field(default_factory=threading.Event)
    file_path: Path | None = None
    error: str | None = None
    max_bytes: int | None = None

    @property
    def is_done(self) -> bool:
        return self.done_event.is_set()

def _run_download(task: MediaDownloadTask) -> None:
    try:
        task.file_path = _download_media_url(
            task.url,
            MEDIA_DOWNLOAD_DIR,
            task.cancel_event,
            max_bytes=task.max_bytes,
        )
    except (MediaDownloadCancelled, DownloadCancelled):
        task.error = MEDIA_DOWNLOAD_STEP_FALLBACK
    except Exception as error:
        task.error = f"{type(error).__name__}: {error}"
    finally:
        task.done_event.set()
源码精讲

worker只有在下载调用返回或抛错并进入finally后才设置done_event。取消事件只是供下载循环轮询的输入，不会异步强杀线程。

承接对象

包含URL、取消事件和上限的MediaDownloadTask。

职责

执行下载，把结果写入file_path或error，并在退出时标记done。

处理顺序

调用下载 → 成功写file_path / 异常写error → finally设置done_event。

输入输出

输入为task；无函数返回值，结果回写task字段。

字段/状态变化

file_path或error被赋值；最后done_event被设置。

边界

done_event表示worker走到finally；当前API仍没有线程句柄和join证据。teardown也没有等待done_event。

必须分开的五个事实：调用cancel_event.set()；worker观察到取消；响应/文件上下文退出；异常清理完成并设置done_event；线程真正终止。当前teardown只直接证明第一项。

09 · 整理答案

直接给出五个判断与依据

创建轮询所有者

MediaGenerationCapability。它按create → task_id → poll编排；BaseTask只是legacy facade。

输出Capture起点

wrapper先进入，下载后发生。只有内层poll_get成功返回Response后才提取URL。

最终文件可见时机

两个上下文关闭且replace成功之后。写入过程中只有唯一.part。

取消请求是否等于线程停止

不等于。cancel_event.set()只是协作式信号，worker需要之后观察并退出。

当前teardown能否证明done/join

不能。代码没有等待done_event，没有保存线程句柄，也没有调用join。

Design · 设计选择与边界

把业务结果、下载事务和后台任务状态分开

业务结果

Capability与poll_get拥有最终Response；输出Capture失败只附加诊断，不替换Response。

下载事务

download_url()拥有临时路径、资源关闭、replace和异常回滚。

后台任务

MediaDownloadTask保存协作式事件与结果字段，但没有线程句柄。

当前约束

teardown追求快速附加当前状态，因此只能请求取消；若要同步终止保证，API必须额外持有线程并等待。

10 · 课后流转总图

业务Response、输出下载与输入后台任务是三条相交但不等价的事实链

先沿中央主链得到最终Response，再从Response分出输出Capture；左侧输入Capture独立运行。图中的每条分支都标明交接对象，避免把“已请求取消”误读成“线程已结束”。

读图规则：final Response先成立，输出Capture才开始；无URL时直接返回Response，不产生下载诊断。输入Capture由create请求经过MediaResourceMiddleware.before_request()触发；worker finally先设置done_event，teardown才能观察完成。cancel_event.set()只证明请求取消。

11 · 完整复述

用一段连续叙述讲清三条事实链

测试把Request、payload、Polling策略和CapturePolicy交给BaseTask。BaseTask只是兼容门面，真正按create、task_id提取、poll_get顺序编排的是MediaGenerationCapability。create请求进入公共发送管线时，MediaResourceMiddleware.before_request读取输入URL并按CapturePolicy决定是否启动后台下载任务，Capability本身不拥有线程。输出Capture装饰器先进入wrapper，但必须等内层poll_get成功返回final Response后，才从Response提取URL；无URL时直接返回Response，有URL时才调用download_url。download_url先写唯一的.part文件，只有Response上下文和文件上下文都退出后才执行replace，因此最终路径只在完整下载并关闭资源后可见；失败、超限或取消会清理.part，诊断信息不能替换已经成立的业务Response。输入worker结束时在finally设置done_event，teardown之后才能观察完成；若teardown先看到任务未完成，只调用cancel_event.set()请求协作式取消，不能证明worker已观察信号、done_event已设置或线程已经终止。

12 · 验收结论

满足以下事实，才算真正掌握Day8

编排所有者准确

能说明BaseTask只是facade，MediaGenerationCapability才拥有create → task_id → poll顺序。

双终点准确

能区分业务Response终点与文件落盘终点，并说明Capture失败不能覆盖Response。

原子发布准确

能说明.part写入、资源关闭、replace和异常清理的先后关系。

取消边界准确

能明确cancel_event.set()只证明请求取消，不证明done_event、join或线程终止。

验收句：业务编排先产生Response，输出Capture再尝试产生文件；输入Capture的取消请求只是中间事实，不能被提升为完全收口证明。
