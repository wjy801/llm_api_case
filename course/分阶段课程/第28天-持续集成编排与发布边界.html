01 · Question

CI的本质是编排，不是复制业务判断

如果Groovy再次解析JUnit、Quality并计算结论，Python与Jenkins会形成两套规则。项目让Jenkins只维护阶段执行事实，并调用pipeline_reporting生成统一结论。

边界：只静态阅读Jenkinsfile与迁移模板，不触发真实Job、真实Smoke、付费接口或持久Flaky状态。

02 · Source entry

主流水线与迁移合同

当前实现

根目录Jenkinsfile包含参数、阶段、post与辅助函数。

迁移模板

JENKINS_MIGRATION_TEMPLATE.md说明接入新Job时必须保持的边界。

报告入口

python -m pipeline_reporting初始化、更新阶段并生成视图。

执行入口

run_master.py拥有收集、分池、JUnit、Allure与Quality生命周期。

03 · Stages

阶段顺序体现依赖约束

Checkout→Check Runtime Env→Prepare Python Env→Framework Unit Tests→Collect Smoke Cases→Real Smoke→post发布

Prepare阶段清理并重建reports/，随后初始化pipeline-stage-status；可选测试阶段由参数控制。

04 · Parameters

危险动作必须显式开启

RUN_FRAMEWORK_TESTS默认true，运行离线tests。
RUN_COLLECT_ONLY默认true，只收集Smoke并统计分池。
RUN_REAL_SMOKE默认false，会产生真实外部调用与费用。
GENERATE_PIPELINE_SUMMARY控制统一报告生成。
TEST_PARALLEL_WORKERSoff/auto/固定worker数。
安全默认：静态学习不改变这些参数；Smoke只允许collect-only。

05 · Stage status

Jenkins记录执行事实，Python解释状态

initializePipelineStageStatus把未启用阶段写成NOT_RUN、启用但未完成阶段写成NO_DATA；各阶段post再调用set-stage更新PASSED或FAILED。Groovy不计算最终PipelineConclusion。

阶段开始

先置NO_DATA，避免阶段中断后被误判成功。

阶段结束

success/failure/unstable/aborted显式更新。

06 · Publish

post负责统一生成、归档和通知

JUnit由Jenkins junit步骤发布测试结果。
Allure发布allure-results，Runner仍拥有原始生命周期。
Artifacts归档allure-results/**与reports/**。
Summary调用Python生成Markdown、JSON和邮件文件。
Email优先读取Python邮件视图，缺失时使用有限fallback。

07 · Boundary

哪些判断属于Python，哪些动作属于Jenkins

Python拥有

收集、分池、pytest退出码、Quality聚合、来源信任、PipelineReport结论与视图。

Jenkins拥有

参数、agent、超时、凭据环境、阶段调度、插件发布、归档和通知时机。

允许fallback

报告生成失败时写有限摘要并继续归档。

禁止复制

Groovy不应重写Metrics、Flaky或Report结论算法。

11 · Design choice

设计选择与适用边界

现方案Jenkins只负责编排阶段、环境、归档和通知，Python拥有测试状态、质量语义与报告结论。
替代方案在Jenkinsfile/Groovy中重复实现测试结果解析、质量阈值和业务状态判断。
选择理由领域规则保留在可单测、可本地复现的Python代码中，CI平台只处理执行动作，减少平台锁定和双份规则漂移。
不适用条件组织没有Python运行环境或发布必须经过独立审批/签名服务时，应调用版本化领域服务与发布控制面，而不是把规则临时塞回Groovy。
