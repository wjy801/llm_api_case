WEEK 4 · DAY 19

Pipeline Reporting与Jenkins

报告不是另一套测试结论，而是把Runner、Jenkins、JUnit与Quality事实装配成可阅读视图。Markdown、机器JSON和邮件必须共享同一个解析结果，任何摘要都不能反向改写pytest或Jenkins。

Stage truthNOT_RUN ≠ NO_DATAFact priorityOne PipelineReportJenkins post
今日交付：能解释阶段状态的来源，能判断陈旧全绿JUnit为何不能覆盖显式失败，并能从同一个PipelineReport追踪Markdown、JSON、邮件与Jenkins归档。

01 · Learning contract

目标与核心约束

第一性原理：报告只能重新组织事实，不能创造事实。一个可靠报告系统必须先区分“是否执行”“是否有产物”“执行是否失败”，再把同一个模型渲染给人和机器。

1

统一解析结果

来源只解析一次，形成不可变报告模型，Markdown、JSON和邮件不各算一遍。

2

保持状态语义

NOT_RUN、NO_DATA、BLOCKED和FAILED回答不同问题。

3

守住事实层级

pytest退出码与Jenkins阶段是执行事实；JUnit和Quality提供统计、详情与诊断。

TOC约束链：阶段状态不明确 → 产物缺失被写成0条测试 → 陈旧JUnit可能伪装成功 → 报告与邮件产生冲突 → Jenkins决策失真。因此本课瓶颈是“来源事实的优先级和缺失语义”，不是HTML样式。

阅读顺序

contracts.py→sources.py→quality_sources.py→builder.py→renderer.py→service.py→Jenkinsfile→迁移模板

03 · Source map

报告来源各自回答一个问题

来源回答的问题缺失时如何表达
pipeline-stage-status.jsonJenkins明确选择、阻断、开始和完成了哪些阶段。记录中文warning，继续由其他事实判断，但不猜阶段成功。
execution-result.jsonRunner计划了什么、分池如何执行、pytest最终退出码是什么。ExecutionSummary.available=false，不伪造退出码0。
unit-tests.xml框架单测统计、失败与跳过详情。选中阶段进入NO_DATA，不写成0总计。
smoke-tests*.xml串并行Smoke的JUnit统计和失败详情。选中阶段无可用JUnit时进入NO_DATA。
smoke-collect.txt收集总数以及parallel/serial分池数。已选收集但清单不可用时进入NO_DATA。
reports/quality/**请求健康、重试挽救、接口耗时和Flaky变化。按子来源局部降级并记录warning。
加载显式阶段状态

校验pipeline-stage-status.v1与允许的三个阶段名。

解析JUnit与收集清单

JUnit按invocation_id、case_id或类名/用例名去重，多文件不会重复计数同一Case。

验证Runner执行事实

检查Schema、planned nodeid唯一性、数量一致性、pool结构和0～5退出码。

按需加载Quality

只有真实接口测试和Quality同时启用时才消费质量产物，避免读取陈旧历史。

汇总warning

可选来源损坏时局部降级；报告展示最多10条提示，不吞掉来源错误。

04 · Stage semantics

NOT_RUN、BLOCKED与NO_DATA不是同一个“没结果”

状态执行意图事实含义正确动作
NOT_RUN未选择参数明确关闭，本轮没有执行义务。不追产物，不把它当失败。
BLOCKED已选择阶段原计划执行，但被前序失败、中断或尚未推进阻止。先处理前序约束，再重跑。
NO_DATA已选择且已开始本轮应有结果，但测试或收集产物不可用。检查阶段日志、产物路径和解析错误。
FAILED已执行Jenkins显式失败、Runner退出非0，或JUnit含失败/错误。保留原始失败事实并定位证据。
PASSED已执行阶段完成且可用执行证据未显示失败。继续检查跳过、重试和Flaky关注项。

Jenkins如何推进状态

初始化：启用阶段=BLOCKED→进入steps前=NO_DATA→post success=PASSED或failure/unstable/aborted=FAILED

未启用阶段从初始化开始就是NOT_RUN。启用阶段先写BLOCKED是fail-closed设计：如果流水线在到达该阶段前停止，报告不会把“尚未执行”误写成成功。

最危险的混淆：把NO_DATA展示成“0总计 / 0失败”。这会把“证据不存在”伪装成“执行了0条且全部成功”，破坏流水线审计。

05 · Fact priority

高层摘要不能覆盖底层执行事实

pytest原始退出码

测试进程事实。Runner的final_exit_code非0时，即使JUnit全绿，接口阶段仍失败。

Jenkins显式阶段状态

流水线事实。阶段failure、unstable或aborted写入FAILED；前序阻断保持BLOCKED。

JUnit

提供统计、失败详情和跳过详情，但不能推翻进程或阶段失败。

Quality / Metrics / Flaky

提供请求健康、重试、耗时与稳定性诊断，不改写pytest结果。

Pipeline Conclusion

把以上事实压缩为PASS、WARN或FAIL关注等级，不反向修改Jenkins。

“优先级”不是丢弃低层证据：JUnit仍用于计数和失败详情，Quality仍用于诊断；只是当它们与进程/阶段事实冲突时，不能用“看起来更绿”的信息覆盖更直接的失败。

06 · Quality degradation

Quality来源按子域降级，不用一个坏文件拖垮整份报告

Reporting消费Quality时仍验证run、Manifest、版本、状态和原始bytes Hash，但它的领域选择是生成中文warning并尽可能保留其他可信部分。

边界验证失败影响
P0核心事实run.json与merged/manifest.json的run_id、Schema、版本、complete状态、integrity和Hash清单。quality_facts_available=false，质量阶段为NO_DATA。
请求健康request-metrics.jsonl原始bytes Hash与run_id过滤。请求健康小节不可用；P0核心可信时质量阶段仍可保持PASSED。
MetricsManifest和run-metrics的run_id、版本、聚合版本、状态与Hash。重试挽救和耗时Top不可用，其他小节继续。
Flaky评估run_id、Schema、可用status和列表字段。显示“未启用或未生成Flaky评估”，不伪造0次迁移。

局部warning

  • 请求指标Hash不匹配；
  • Metrics版本或状态不可信；
  • Flaky run_id不属于本轮；
  • JSONL具体行不可解析。

禁止扩散

  • 不能把接口阶段从PASSED改成FAILED；
  • 不能把缺失指标写成0%；
  • 不能读取未启用真实Smoke留下的陈旧Quality；
  • 不能用warning覆盖Jenkins构建结果。
降级粒度原则：最小化不可信数据的影响半径。请求文件损坏只关闭请求健康；Metrics损坏只关闭重试与耗时；只有P0核心合同断裂才让质量阶段进入NO_DATA。

07 · Conclusion and actions

Pipeline Conclusion是关注等级，不是新的构建结果

Builder先构造框架单测、用例收集、接口测试和质量观测四个阶段，再根据Jenkins结果、阶段状态、覆盖缺口和诊断事项计算结论。

条件结论原因
Jenkins为FAILURE / ABORTED / NOT_BUILTFAIL构建事实已失败。
任一阶段FAILEDFAIL选中任务存在明确失败。
没有选择任何测试任务WARN流水线运行了，但没有验证价值。
存在BLOCKED或NO_DATAWARN执行链或证据链不完整。
Jenkins UNSTABLE、JUnit跳过、重试挽救或Flaky待治理WARN执行未失败，但需要关注覆盖或稳定性。
选中阶段通过且无关注项PASS本轮按配置完成。

08 · Shared rendering

Markdown、机器JSON和邮件共用一次构建结果

读取配置

进程环境优先于.env；开关关闭时删除陈旧输出并返回None。

构建上下文

从Jenkins环境变量读取build result、分支、提交、耗时、参数与Quality开关。

加载来源并构建Report

load_pipeline_sources()只执行一次，build_pipeline_report()只产生一个不可变模型。

渲染多个输出

Markdown、JSON、邮件主题与HTML都读取同一个Report，使用临时文件加原子替换写入。

输出定位生成条件
pipeline-summary.md唯一人工质量入口，包含阶段、统计、诊断与建议动作。Reporting开启时默认生成。
pipeline-summary.json完整PipelineReport机器序列化结果。必须显式传--machine-output。
pipeline-email-subject.txt由同一结论和测试数量生成的邮件主题。必须显式传邮件主题输出路径。
pipeline-email.html构建、统计、最多5个失败用例和报告入口。必须显式传邮件HTML输出路径。

09 · Jenkins responsibilities

Jenkins编排执行与发布，Python拥有报告语义

Jenkins阶段职责关键边界
Checkout清理Workspace、拉取SCM并保存commit/branch。旧reports不会跨构建冒充新证据。
Check Runtime Env准备.env并检查Python、Node和关键配置。敏感值不写入迁移模板或课程。
Prepare Python Env安装依赖、清理并创建reports、初始化阶段状态。启用阶段先BLOCKED，未启用阶段NOT_RUN。
Framework Unit Tests执行离线测试、写JUnit、在post更新阶段状态并发布JUnit。失败状态不能被JUnit统计覆盖。
Collect Smoke Cases只收集Smoke并记录分池统计。不调用真实接口。
Real Smoke按目标和并发配置调用Runner，开启Quality；存在外部Flaky DB时才启用历史与状态。默认关闭，会产生外部调用和费用。
Pipeline postalways生成摘要，再发布Allure、归档reports，最后按结果发送邮件。报告生成早于归档和邮件。
阶段显式状态+Runner / JUnit / Quality产物→post always生成统一报告→Allure与archiveArtifacts→失败/不稳定/恢复邮件

报告生成失败

Jenkins记录错误并写最小兜底Markdown，只保留构建号、真实Jenkins结果和定位建议，不猜用例数。

不会：赋值currentBuild.result或把失败改成功。

邮件渲染文件缺失

使用Groovy兜底HTML，明确提示以Jenkins阶段状态和构建日志为准。

不会：重新解析JUnit建立第二份测试结论。

失败开放不等于事实开放：阶段状态辅助写入失败时Jenkins继续主任务，报告生成失败时仍尝试兜底；但所有兜底都必须明确“不完整”，不能伪造通过数量或改写原始状态。

迁移模板的作用

JENKINS_MIGRATION_TEMPLATE.md记录Controller、Windows Agent、插件、Job参数、SMTP、持久Flaky数据库、产物保留和验收顺序。它是可迁移配置清单，不包含账号、Token、密钥等敏感信息。

10 · Same-run practice

本轮产物实践：Runner之后显式调用Reporting

Runner只写execution-result.json、JUnit、Allure与Quality产物，不生成pipeline-summary.md/json。继续使用第16天同一个PowerShell会话，把本轮Runner退出事实写入阶段状态后，再显式调用Reporting CLI。

证据边界：只消费当前会话本轮产物。如果execution-result.json不是本轮文件，不要用陈旧全绿JUnit生成摘要；也不要为了本课重新执行真实付费Smoke。

步骤1：从Runner事实初始化并更新本地阶段状态

$executionResult = Get-Content `
  -LiteralPath 'reports/execution-result.json' `
  -Encoding utf8 `
  -Raw | ConvertFrom-Json
$realSmokeStatus = if ([int]$executionResult.final_exit_code -eq 0) {
  'PASSED'
} else {
  'FAILED'
}
$env:PIPELINE_BUILD_RESULT = if ($realSmokeStatus -eq 'PASSED') {
  'SUCCESS'
} else {
  'FAILURE'
}

.\.venv\Scripts\python.exe -m pipeline_reporting initialize-stages `
  --framework-tests false `
  --smoke-collect false `
  --real-smoke true

.\.venv\Scripts\python.exe -m pipeline_reporting set-stage `
  --name real_smoke `
  --status $realSmokeStatus

步骤2：生成Markdown和机器JSON

.\.venv\Scripts\python.exe -m pipeline_reporting generate `
  --workspace . `
  --output reports/pipeline-summary.md `
  --machine-output reports/pipeline-summary.json `
  --dotenv .env

if ($LASTEXITCODE -ne 0) {
  throw "Pipeline summary generation failed with exit code $LASTEXITCODE"
}
if (
  -not (Test-Path -LiteralPath 'reports/pipeline-summary.md') -or
  -not (Test-Path -LiteralPath 'reports/pipeline-summary.json')
) {
  throw 'Pipeline summary outputs are missing'
}
必须显式写--machine-output：它没有默认值。只写--output时，CLI成功但仅生成Markdown，这不是机器JSON丢失，而是调用合同不同。

步骤3：从最终视图向上追溯来源

reports/execution-result.json ← Runner进程与分池事实 reports/smoke-tests*.xml ← JUnit统计与详情 allure-results/ ← 交互式失败证据 reports/quality/** ← Quality / Metrics / Flaky诊断 reports/pipeline-stage-status.json ← 显式流水线阶段事实 reports/pipeline-summary.json ← PipelineReport机器视图 reports/pipeline-summary.md ← 人工阅读视图

步骤4：运行离线合同测试

.\.venv\Scripts\python.exe -m pytest `
  tests/quality/test_pipeline_reporting.py `
  tests/quality/test_pipeline_reporting_dependency_boundaries.py `
  tests/quality/test_quality_jenkinsfile.py `

这些测试不调用真实接口，保护阶段语义、事实优先级、同一Report多视图、Jenkins生成顺序和依赖边界。

12 · Exit gate

本课门禁：报告只能解释事实，不能重写事实

一句话验收：Jenkins先记录执行意图与阶段事实，Runner和JUnit提供进程及用例证据，Quality按可信子来源补充诊断；Python只构建一次PipelineReport并渲染Markdown、JSON和邮件，Pipeline Conclusion只表达关注等级，任何摘要、warning或兜底都不能修改pytest退出码与Jenkins结果。
