DAY 10 · OWNERSHIP BEFORE CONCURRENCY

测试上下文、资源清理与并发隔离

并发安全不是“加一把锁”这么简单。先把变量、客户端、Session、Header、Runtime Hooks 和业务状态的所有者说清楚，再决定复制、独占、清理还是串行。

建议 1.5～2.5 小时前置：完成第09天门禁只运行 loopback 离线测试核心：test_context.py / context_executor.py
完成标志：能用 TestContext 完成提取、类型校验和 LIFO 清理；能解释普通线程池为何丢失 ContextVar；能为 Client、Session、Header 划定所有权，并判断什么时候必须标记 serial。

01 · First principles & TOC

真正的问题不是“能不能并发”，而是“并发后证据还属于谁”

接口用例的价值来自因果可追溯：输入、请求、响应、清理和报告必须归属于同一个 case。只要一个可变对象跨越所有权边界，速度越快，污染也越快。

1

变量可追溯

跨步骤值只活在当前用例，来源、缺失与类型错误都显式。

2

资源可回收

创建成功即登记清理，按依赖逆序执行，单点失败不阻断后续清理。

3

线程可归属

每次提交复制 ContextVar 快照，让 run、case、operation 与 Runtime Hooks 不丢失。

4

调度可解释

可隔离的状态并发；无法隔离且会污染断言的共享状态串行。

边界未声明共享变量或 Session
→
写入互相覆盖Header、Cookie、Hook 串案
→
响应仍可能 200表面成功掩盖归属错误
→
证据不可置信报告与清理指向错误用例
当前系统约束：TOC 不是把所有测试都改为串行。真正的约束是所有权不明确；先以“用例级上下文 + 线程级客户端 + 请求级 Header”消除可隔离冲突，只把不可隔离的共享业务状态送进 serial 池。

02 · Scope model

先画作用域，再写代码

并发问题通常不是对象本身“线程不安全”，而是对象实际寿命超过了它应有的作用域。最小安全单元是：谁创建、谁读写、谁关闭。

可靠并发 = 不可变共享 + 可变状态独占 + 必要上下文按提交快照复制“能访问”不等于“有权修改”；“线程局部”也不等于“自动继承父线程语义”。
CASE

TestContext

每个 pytest case 一个实例，保存跨步骤变量与清理栈。禁止用模块全局字典代替。

SUBMISSION

ContextVar 快照

submit_with_context() 在每次提交时 copy_context()，随后在 worker 中运行。

WORKER

Request Client / Session

每个 worker 创建自己的 Client，也负责在 finally 中关闭；不跨线程共享 Session。

REQUEST

单次 Header

通过 get/post(..., headers={...}) 传入，只影响当前请求，不修改共享默认 Header。

PROCESS / ACCOUNT

共享业务状态

余额、账单、usage、账号配置与延迟结算无法靠线程局部对象隔离，必要时标记 serial。

IMMUTABLE

可安全共享的定义

只读配置或不可变值可以共享；一旦需要 clear/update/reset，就应重新审视所有权。

03 · TestContext contract

TestContext 是用例级状态容器，不是隐藏的全局数据库

module/conftest.py 的 fixture 每次构造新 TestContext，并在 finally 调用 cleanup()。它把“传值”和“资源收口”绑定到同一个 case 生命周期。

fixture：生命周期兜底

@pytest.fixture
def test_context() -> TestContext:
    context = TestContext()
    try:
        yield context
    finally:
        context.cleanup()

用例：先保存，再带类型读取

response = task.create_resource(request, payload)
resource_id = test_context.extract(
    "resource_id",
    response,
    json_path="$.data.id",
    expected_type=str,
)
test_context.add_cleanup(
    task.delete_resource, request, resource_id
)
assert test_context.require(
    "resource_id", expected_type=str
) == resource_id
API合同常见误解
set(name, value)校验变量名后保存并返回原值。不是跨用例共享；每个实例有独立字典。
get(name, default)缺失时可返回 default，但不会把 default 写回上下文。读取默认值后 has(name) 仍为 false。
require(..., expected_type)缺失或类型不符立即抛出清晰异常。不是普通 assert；错误值会按敏感字段脱敏。
snapshot()返回变量字典的浅拷贝。用于检查当前快照，不是可写回的共享存储。
delete / clear删除变量状态，不执行 cleanup 回调。变量清空与业务资源释放是两条不同生命周期。
add_cleanup / cleanup登记回调并 LIFO 执行；fixture 会最终兜底。手动 cleanup 后再次调用是安全的，因为栈已弹空。
禁止模式：用模块全局变量传递 request_id，或依赖“上一个测试先创建资源”。xdist、随机顺序或单独运行 nodeid 都会打断这种隐式前置条件。

04 · Extraction contract

提取不是字符串搬运，而是把响应边界转成类型合同

extract() 一次必须且只能选择一种来源。提取成功后还要经过缺失策略、allow_none、转换与类型校验，最后才存入上下文。

JSONPathHeaderCookieRegex

恰好一个来源

同时传 json_path 与 header 会抛 ContextExtractionError，避免来源含糊。

JSONPath 必须以 $ 开始。

优先来源

extract_first() 依次尝试 sources，使用第一个非空命中；不是并行猜测。

每个 source 也必须只声明一种来源。

缺失与空值

required=False 且无 default 时返回 None，但不保存变量；JSON null 只有 allow_none=True 才能保存。

转换再验型

transform=int 先把字符串转为整数，然后 expected_type=int 验证结果。

转换失败包装为提取异常。

多值 JSONPath

multiple=True 返回全部匹配列表；默认只返回第一个匹配值。

诊断仍需脱敏

缺失时包含变量名、来源、状态码、Header 名与截断响应体，但不能泄漏 Header/Cookie/密钥值。

四种来源

ctx.extract("task_id", response,
            json_path="$.data.task_id",
            expected_type=str)
ctx.extract("request_id", response,
            header="X-Request-ID")
ctx.extract("session_id", response,
            cookie="session_id")
ctx.extract("trace_id", response,
            regex=r"trace=([a-z0-9-]+)", group=1)

缺省、转换与优先来源

count = ctx.extract(
    "count", response,
    json_path="$.count",
    default="2", transform=int,
    expected_type=int,
)
task_id = ctx.extract_first(
    "task_id", response,
    sources=[
        {"json_path": "$.task_id"},
        {"header": "X-Task-ID"},
    ],
    expected_type=str,
)

05 · Resource cleanup

LIFO 不是实现偏好，而是依赖图的逆序

如果 B 的创建依赖 A，那么销毁必须先 B 后 A。清理栈让登记顺序自然转换为逆序释放，并保证中间一个回调失败后仍继续回收剩余资源。

Cleanup stack

③ close child / last最先弹出执行
② delete task即使上一步失败仍执行
① close parent / first最后释放基础资源
POP ↓ last → delete → first

四条真实合同

创建成功后立即登记不要等所有断言通过才想起清理。
失败不短路每个异常被收集，后续回调继续执行。
结束后聚合抛出ContextCleanupError.errors 保留原异常列表，消息做脱敏。
可重复调用回调弹出后不会再次执行，第二次 cleanup 是空操作。
业务创建成功得到 resource_id
→
立即 add_cleanup把释放义务入栈
→
业务断言成功或中途抛错
→
fixture finally无条件 cleanup
→
聚合诊断资源尽力回收且错误可见
边界：BaseException 也会被清理器捕获，以保证其余回调执行；全部回调结束后再用一个 ContextCleanupError 呈现失败。不要在回调中吞掉删除失败，否则“测试绿了但资源还在”。

06 · Context propagation

线程池继承执行能力，不继承提交线程的 ContextVar 语义

ContextVar 适合表达当前 run、case、operation 与 Runtime Hooks 绑定，但 ThreadPoolExecutor.submit() 不会自动把调用者上下文复制进 worker。框架用每次提交一个独立快照解决。

提交线程

runrun-42
casecase-a
hooksrecorder-a
copy_context() →

Worker 中运行快照

runrun-42
casecase-a
hooksrecorder-a

错误：直接提交

future = executor.submit(call_one, payload)
worker 可能得到默认 ContextVar：请求执行了，但 operation、响应与观察事件无法归到当前 case。

正确：提交时复制

future = submit_with_context(
    executor, call_one, payload
)
内部先 context = copy_context()，再提交 context.run(function, ...)。
def submit_with_context(executor, function, /, *args, **kwargs):
    context = copy_context()  # 每次提交独立快照
    return executor.submit(context.run, function, *args, **kwargs)
快照语义：第一个任务提交前 value=first，第二个提交前 value=second，即使复用线程，两个任务仍分别看到 first 与 second。不能把同一个 Context 对象并发重入；当前实现每次提交都复制，避免此问题。

07 · Concurrent ownership

Client、Session、Header：从大到小划三层所有权

框架黄金示例让每个 worker 创建并关闭自己的 OfflineFrameworkRequest；每个 Client 因而有独立 Session；X-Audit-Name 只作为当前请求参数传入。

Worker A创建 Client A
→
Session ACookie / connection pool A
→
Request Aheaders={X-Audit-Name:a}
‖
Worker BClient B → Session B → Header b

安全：worker 独占 Client

在线程函数内构造，在 finally 关闭。两个 session_id 应不同，且都出现在 closed_session_ids。

所有权与线程寿命一致。

风险：跨 worker 共享 Session

连接池、Cookie、认证刷新和默认 Header 都是可变状态；调用加锁也难证明整个生命周期不串案。

框架规范直接禁止。

安全：请求级 Header

self.get(path, headers={"X-Audit-Name": name}) 只影响一次调用，测试还验证它未写入 session.headers。

风险：临时改 Session.headers

update → request → reset 是三个步骤，另一线程可在中间读到错误值；异常还可能跳过 reset。

worker 自己创建和关闭

def call_one(base_url, audit_name):
    client = ExampleRequest(base_url)
    try:
        return ExampleTask().query_audit(
            client, audit_name
        )
    finally:
        client.close()

单次 Header 不进入 Session

def get_audit(self, audit_name):
    return self.get(
        self.audit_path,
        headers={"X-Audit-Name": audit_name},
        runtime_metadata=...,
    )

assert "X-Audit-Name" not in client.session.headers

08 · Scheduling decision

serial 是不可隔离共享状态的保护栏，不是并发恐惧症

决策顺序：先识别可变状态，再尝试缩小所有权；只有状态由外部账号/服务共享且并发会污染断言时，才进入串行池。

1 · 找状态

断言依赖哪个可变事实？本地对象、服务资源、账号余额还是结算账单？

2 · 问能否隔离

能否每 case 唯一 ID、每 worker Client、请求级 Header 或独立账号？

3 · 选择调度

可隔离则保持并发；外部共享且无法隔离则标记 serial。

两个 worker 分别创建 Client/Session，只读同一 loopback 服务，不断言全局顺序。
两个 worker 共用一个 Session，并临时 update/reset session.headers。
用例断言共享账号调用前后的余额差与本次账单完全相等。
每个 case 使用唯一资源 ID，清理登记在自己的 TestContext 中。
服务端异步结算，共享 usage 只有最终总量，无法区分并发请求贡献。
Runner 语义：传入 -n 后先执行未标记用例的并发池，再单进程执行 serial 池。marker 保护的是业务共享状态；它不能修复线程内错误共享 Session 的设计。

09 · Causal diagnosis

从症状向下追三层，不在表面补 sleep 或锁

并发故障常表现为偶发值错、报告缺事件或 teardown 失败。定位时先问“错误证据归谁”，再看对象寿命，最后看外部共享状态。

症状：请求成功，但报告少一条 operation

直接 executor.submit() → worker 未继承 Runtime Hooks ContextVar → 事件落到默认 Noop/错误归属。

修复：所有用例内线程任务使用 submit_with_context()。
症状：A 请求偶尔带着 B 的 Header

共享 Session → 并发修改默认 headers → request 时序交叉 → Header 泄漏。

修复：worker 独占 Client；动态 Header 作为请求参数。
症状：测试失败后资源残留

清理写在断言之后 → 中途异常跳过删除 → 后续用例看到脏状态。

修复：创建成功立刻 add_cleanup()，由 fixture finally 兜底。
症状：一个删除失败后其余资源也没清

手写 teardown 串行调用 → 第一个异常短路 → 后续回收义务丢失。

修复：cleanup 栈继续执行并最终聚合错误。
症状：加锁后余额断言仍偶发失败

锁只覆盖本进程 → 账号仍被其他任务/流水线共享 → 服务端结算窗口重叠。

修复：独立账号/可关联 usage；做不到时标记 serial 并治理外部并发。
症状：缺失变量时日志泄漏密钥

直接打印 response 全量内容 → 诊断越详细，泄漏面越大。

修复：使用框架提取异常，其摘要只列 Header 名并对正文脱敏、截断。

11 · Knowledge check

知识自测

答对 5 题视为达标。不要只记 API 名称，要按所有权和失败边界判断。

1. ctx.get("count", default=2) 在变量缺失时会怎样？
答案 B。get 的 default 只控制本次读取，不修改上下文。
2. cleanup 回调依次登记 first、delete、last，delete 抛错。真实执行结果是什么？
答案 C。LIFO 且单个失败不阻断剩余回调。
3. 为什么不能直接用 executor.submit() 执行框架请求？
答案 A。请求可能成功，但观察证据失去当前用例归属。
4. 两个并发 worker 需要不同 X-Audit-Name，最佳做法是什么？
答案 B。Client/Session归worker，动态Header归单次请求。
5. 哪个场景最应标记 serial？
答案 C。外部共享状态无法通过本地对象隔离，且并发会污染断言。
6. extract(..., required=False) 未命中且没有 default 时怎样？
答案 A。JSON null 若要保存则需显式 allow_none=True，这是不同语义。
