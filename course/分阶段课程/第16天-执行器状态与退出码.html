WEEK 4 · DAY 16

执行器状态与退出码

沿着runner.run()追踪一次权威收集、分池执行、停止决策、退出码归并和机器事实提交，理解Runner为什么只保存执行事实，而不替Quality或流水线解释业务结论。

建议时长 2.5～3 小时Runner状态机PoolExecutionResultexecution-result.json
可核验产出：一张Runner阶段状态图、一张退出码决策表，以及本轮reports/execution-result.json字段核验记录。

01 · Learning goals

先观察三个结果：池是否执行、pytest返回什么、Runner最终提交什么

先不背状态枚举。完成本课后，你应能从一个Runner测试追踪到池结果、最终退出码和execution-result.json，并说明三者为何不能互相替代。

输入事实

pytest参数、权威收集结果、nodeid计划、并发配置和串行标记。

过程事实

每个池是否计划、是否真正执行、原始pytest退出码、起止时间和JUnit路径。

输出事实

最终退出码与execution-result.json，但不在Runner内推导质量等级或流水线结论。

TOC约束：如果只看最终退出码，就丢失了“哪个池执行、哪个池未运行、是否因终止码短路”的关键信息；因此本课的核心约束是事实保真，而不是让结果看起来更简洁。

03 · Fact layers

四层事实不能互相替代

层级对象或字段回答的问题不能替代
收集层CollectionResult.raw_pytest_exit_code、cases选择表达式能否形成可执行集合？不能说明测试是否执行成功
计划层planned_nodeids、并发池、串行池本轮准备执行哪些nodeid？不能证明这些nodeid已经运行
池执行层PoolExecutionResult每个池发生了什么？不能单独代表整轮结果
进程层final_exit_code调用方应该把进程视为哪类pytest结果？不能还原池级细节

第一性原理上，Runner不能从“计划过”推导“执行过”，也不能从“某池失败”推导“后续池一定未运行”。这些结论必须由池状态、停止策略和原始退出码共同证明。

04 · Pool result model

NOT_RUN、COMPLETED、ERROR描述执行器自身发生了什么

NOT_RUN

池为空或前序终止码要求停止。没有开始、结束时间，也没有原始pytest退出码。

COMPLETED

pytest.main()已经返回；即使返回1表示用例失败，执行器调用本身仍然完成。

ERROR

执行器封装层捕获到异常，无法得到可信的pytest原始退出码；exception_type保存异常类型。

PoolExecutionResult同时保存stage_id、planned_nodeids、状态、原始退出码、起止时间、异常类型和JUnit路径。状态与退出码是两个维度：COMPLETED + 1表示pytest完成且存在测试失败，ERROR + null表示连pytest结果都未形成。

判断规则：先问“执行器是否完成调用”，再问“pytest返回了什么”；不要把ERROR和测试失败退出码1混成同一种失败。

05 · Runner state machine

一次运行按阶段迁移，不靠隐式回退

  1. 参数分区：partition_pytest_args()拆出收集参数、执行参数和collect_only；非法参数直接返回pytest usage error 4。
  2. 权威收集：collect_test_case_items()只执行一次收集；非0收集码直接成为本轮原始事实。
  3. 分池：对唯一的cases调用split_test_cases()，形成互斥并集。
  4. collect-only短路：只打印池数量并返回0，不启动Allure、Quality或执行产物生命周期。
  5. 生命周期准备：正式运行才准备Allure与Quality。
  6. 执行池：无-n时全部作为serial-pool执行；有并发配置时先parallel-pool，再根据停止策略决定serial-pool。
  7. 归并与提交：计算最终退出码，原子写入机器产物，最后在finally收口可选生命周期。
ARGUMENTS→COLLECTED→PLANNED→PARALLEL?→SERIAL?→COMMITTED

06 · Exit semantics

终止码优先，测试失败其次，未知非零保守归一

pytest码语义Runner行为
0成功允许继续后续池
1测试失败仍可继续串行池，以收集更多真实测试事实
2用户中断终止后续池，最终码保持2
3pytest内部错误终止后续池，最终码保持3
4命令行使用错误终止后续池，最终码保持4
5没有收集到测试终止后续池，最终码保持5

merge_exit_codes()先返回第一个终止码2～5；没有终止码但存在1时返回1；出现未知非零值时保守归一为1；全部为0或没有可归并码时返回0。_final_exit_code()还有一层保护：只要任一池状态是ERROR，最终码至少为1。

设计取舍：普通用例失败后继续串行池，是“继续收证”；内部错误、参数错误或无测试时停止，是“避免在无效前提上继续执行”。

07 · Machine artifact

execution-result.json是Runner事实的提交记录

字段来源核验重点
schema_versionRunner合同常量消费方先按版本解析
test_target、selection_args本轮输入证明结果属于哪次选择
planned_case_count、planned_nodeids权威收集结果数量与nodeid集合一致
collection_exit_code收集阶段与执行池退出码分离
pool_results每个池的结果对象状态、时间、异常和JUnit路径不可互相推导
final_exit_code归并规则与进程返回码一致

write_execution_result_atomic()在目标目录创建临时文件，写入并刷新后再replace到正式路径。若提交失败且原结果不是终止码，Runner返回1，避免出现“进程成功但机器证据缺失”的假成功。

08 · Ownership boundary

Runner只编排，不接管报告与质量业务实现

Runner拥有

  • 参数阶段划分与权威收集
  • 池执行顺序和停止策略
  • 原始退出码归并
  • Runner机器事实原子提交

Runner不拥有

  • Allure HTML与history生成细节
  • Quality事实模型、语义关系和指标
  • 流水线阶段结论与展示
  • 业务接口成功语义

tests/test_run_orchestration_boundaries.py通过静态依赖门禁保证Runner不直接导入Quality业务实现；Runner只调用中性的生命周期边界。后续Day17、Day18会分别展开Allure与Quality的实现所有权。

Design decision

设计选择与适用边界

现方案替代方案选择理由不适用条件
用显式池状态、原始pytest退出码和原子execution-result.json共同提交执行事实。只返回一个成功布尔值，或用最后一个池的退出码覆盖前序收集、终止和写盘错误。NOT_RUN、COMPLETED、ERROR能区分“未发生”“已执行”和“执行器故障”，机器产物让流水线可重放退出码决策。跨机器长任务需要更细的排队、租约、取消和心跳状态，应升级为事件日志/工作流状态机，而非继续扩充单文件枚举。

基于已执行池触发可选Quality收尾；普通异常失败开放。

→

Quality事实边界

Quality可产生P0/Semantic产物，但不得覆盖pytest原始退出事实。

5

_final_exit_code() / merge_exit_codes()

先处理Runner ERROR，再按终止码优先级归并pytest退出码。

→

进程决策

得到单个final_exit_code；它服务Shell控制流，不承载全部证据。

6

_write_execution_result() / 原子替换

组装收集、池和最终退出事实，临时写入后替换正式文件。

→

产物状态

reports/execution-result.json成功提交；提交失败时成功码转为1，终止码仍保留。

最终守恒关系

Runner事实回答执行发生了什么；Quality事实回答采集与归并得到什么；进程码回答Shell下一步怎么走；机器产物状态回答本轮事实是否提交。
