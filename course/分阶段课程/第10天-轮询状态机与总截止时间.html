Week 2 · Day 10

轮询状态机与总截止时间

Polling的本质不是重复GET，而是在一个由Polling拥有的总deadline内，把每轮最终HTTP响应提取、归一化并判定为业务状态，再记录观察证据并选择终态。Retry只提高其中一轮HTTP传输的可靠性，不能拥有整轮等待预算。

建议用时 180～220分钟难度：可靠性主干学习方式：主用例逐函数前置：Day09 Retry
本课结果：从已有task_id追到Facade、Capability、装饰后的poll_get、状态求值、单轮Retry与总deadline；准确解释4个HTTP Response为何只有3次Polling observation，以及deadline后观察到success为何仍然超时。
+

01 · 目标与核心约束

当前约束不是“不会循环”，而是三种时间与两种状态被混在一起

第一性原理上，框架必须分别回答：本轮HTTP是否可靠、业务任务处于什么状态、整轮承诺是否已经到期。任何一个所有权混淆，都会让停止原因失真。

1

区分计数

HTTP Response数量不等于Polling observation数量，Retry attempt属于某一轮观察内部。

2

拆开求值

按状态提取、语义归一化、终态判定、迁移记录四步阅读。

3

锁定所有权

Polling创建唯一deadline；请求timeout、Retry等待与轮询sleep只能消费remaining。

4

证明停止

success、failure、unknown、pending、timeout都有独立且可核对的停止或继续条件。

错误建模的因果链

把每个Response都算成一轮
Retry 503被误当业务状态
迁移序列与attempt混杂
deadline责任漂移
超时后success被错误接受
本课范围护栏主线从已经存在的task_id开始。离线用例只提供稳定载体，不展开任务创建、载体初始化或网络地址；页面只追踪与正常module相同的Polling调用链。

03 · 装饰入口与轮询会话

Capability调用到的是装饰后的poll_get，但状态机仍由函数体内核负责

装饰器包住公开方法，公开方法负责参数合法性和Polling会话收口；真正创建deadline并循环观察的是下一节的_poll_get_with_policy()。

def download_links_from_poll_get(self, func: F) -> F:
    @wraps(func)
    def wrapper(instance: Any, path: str, *args: Any, **kwargs: Any) -> requests.Response:
        capture_policy = getattr(instance, "capture_policy", DEFAULT_CAPTURE_POLICY)
        polling_policy = kwargs.get("polling_policy")
        result_json_path = getattr(polling_policy, "result_json_path", None)
        response = func(instance, path, *args, **kwargs)
        if result_json_path is None or not capture_policy.capture_output_results:
            return response
common/base_request.py::BaseRequest.poll_get
@download_links_from_poll_get
def poll_get(
    self,
    path: str,
    *,
    poll_interval: float = 2,
    poll_timeout: float | None = None,
    polling_policy: PollingPolicy,
    retry_policy: RetryPolicy | None = None,
    **kwargs: Any,
) -> requests.Response:
    if poll_interval <= 0:
        raise ValueError("poll_interval must be greater than 0")

    timeout = self.config.timeout if poll_timeout is None else poll_timeout
    if timeout <= 0:
        raise ValueError("poll_timeout must be greater than 0")

    metadata = self._runtime_observer.normalize_metadata(
        kwargs,
        kind=RuntimeOperationKind.POLLING,
        default_name="polling",
    )
    polling = self._runtime_observer.start_polling(metadata)
    try:
        response = self._poll_get_with_policy(
            path,
            poll_interval=poll_interval,
            timeout=timeout,
            polling_policy=polling_policy,
            retry_policy=retry_policy,
            runtime_polling=polling,
            **kwargs,
        )
    except BaseException as error:
        polling.finish_error(error)
        raise
    polling.finish_success()
    return response

05 · 状态迁移与终态顺序

内核先记录本次观察，再检查deadline，最后才接受SUCCESS

这是全课最重要的控制顺序：请求完成并求值后先追加Transition，随后计算remaining；只要remaining <= 0，即使state已经是SUCCESS也必须抛出PollingTimeoutError。

承接对象

承接公开poll_get()解析后的timeout、path、PollingPolicy、可选RetryPolicy与运行时Polling对象。

职责

创建整轮唯一deadline；循环获得每轮最终Response；调用求值器；冻结Transition；按deadline和状态决定返回、异常或继续。

处理顺序

  1. 只创建一次deadline = started_at + timeout。
  2. 每轮调用_request_without_attach()。
  3. Retry耗尽总预算时翻译为PollingTimeoutError。
  4. 对最终Response求值。
  5. 记录runtime state与PollingTransition。
  6. 先检查remaining。
  7. remaining仍为正时再判断SUCCESS、FAILURE、UNKNOWN。
  8. PENDING落到sleep(min(interval, remaining))后进入下一轮。

输入输出

输入总timeout、轮询间隔、path、策略与请求参数。
成功输出deadline内观察到SUCCESS的最终Response。
失败输出领域终态为PollingFailedError、PollingUnknownStateError或PollingTimeoutError；非deadline请求异常原样传播，求值器异常在附加当前Response日志后原样抛出。

字段/状态变化

attempt_index按Polling observation递增；每轮追加一条Transition，包含elapsed、归一化state、raw_status和HTTP状态码；last_status/last_response更新为最近观察事实。

边界

两个关键边界：Transition是观察记录，不是迁移合法性校验器；RetryDeadlineExceeded翻译分支把已有transitions放入超时异常，但不会执行其他终态分支共有的_attach_polling_transitions()。

06 · 单轮Retry与总deadline

Retry可以消费Polling预算，但不能重新定义预算

调用链在_request_without_attach()处分叉：无Retry时单发一次；有Retry时进入_send_with_retry()。两条路都接收同一个deadline，请求timeout和Retry等待都必须服从remaining。

承接对象

承接Polling当前while迭代的GET意图、可选RetryPolicy和由Polling创建的deadline。

职责

选择单次发送或Retry发送，并把当前观察最终使用的Context与logger交还Polling内核。

处理顺序

  1. 先构造基础Context。
  2. 无Retry时发送一个Request Group。
  3. 有Retry时创建Context记录器并调用RetryExecutor。
  4. 选择最后一次attempt Context作为响应上下文。
  5. 返回最终Response与logger；异常则记录并重新抛出。

输入输出

输入当前观察的请求参数、RetryPolicy或None、共享deadline。
输出当前观察最终Response与ApiCallLogger。

字段/状态变化

Retry时context_recorder可出现多个attempt Context；但外层Polling的attempt_index尚未再次增加，也没有追加多条Transition。

边界

Retry只负责：当前观察内的HTTP attempt、等待和记录。它不读取业务status、不决定pending/success，也不创建或延长Polling deadline。

职责

边界

承接对象

承接状态机已经确定的停止原因，以及最近Response、raw_status和transitions。

职责

用类型区分业务明确失败、未知业务状态和总预算超时，让上层可以按原因处理。

处理顺序

  1. FAILURE分支构造PollingFailedError。
  2. UNKNOWN分支构造PollingUnknownStateError。

公共事实path、last_status、last_response、transitions。

边界

继承关系：Failed与Unknown属于PollingError；Timeout直接属于TimeoutError，不是PollingError子类。

PollingFailedError

PollingError → AssertionError

表示明确业务失败，可携带error_value。

PollingUnknownStateError

PollingError → AssertionError

表示raw_status未被Policy识别，且unknown策略选择fail。

PollingTimeoutError

TimeoutError

表示总deadline耗尽；来源可以是观察后越界，也可以是Retry内部预算耗尽的翻译。

非领域异常

requests异常或求值器异常原类型

非deadline请求失败直接传播；求值失败先附加当前Response日志，再重新抛出，不生成PollingTransition。

08 · 直接答案

不做选择题，不运行命令，直接读取本课结论

为什么4个Response只有3次观察？

第一次while迭代内部Retry得到503和200 queued；_request_without_attach()只把最终queued Response交给求值器，因此只追加一条pending Transition。

为什么success仍可能超时？

求值和Transition记录之后，代码先计算remaining并处理remaining <= 0，然后才检查SUCCESS。时间合同优先于业务内容。

Retry与Polling怎样分工？

Retry只负责当前观察内的HTTP attempt、backoff和传输记录；Polling负责观察循环、业务状态、Transitions、poll sleep和唯一deadline。

RetryDeadlineExceeded去了哪里？

它在Polling内核被翻译为PollingTimeoutError。已有transitions进入异常对象，但该except分支不调用其他终态共有的_attach_polling_transitions()。

UNKNOWN一定终止吗？

不一定。Policy的unknown为pending或ignore时会归一化为PENDING；主用例策略为fail，因此未知值成为UNKNOWN并终止。

Transition证明了什么？

证明每次Polling observation的序号、累计耗时、归一化state、raw_status与HTTP状态码；它不证明业务迁移是否合法。

09 · 第2周静态复盘

把Day06～Day10收束成一条可靠请求主线

层次直接答案本课边界
RequestContext每个HTTP attempt拥有独立Context。一次Polling observation内的Retry可产生多个Context。
Middleware / Session每个attempt仍经过同一发送管线。它们观察传输，不决定业务PollingState。
Retry提高单轮HTTP传输可靠性。不拥有Polling总deadline，不追加PollingTransition。
Polling对每轮最终Response求值、记录迁移并决定继续或停止。只要总deadline耗尽，就不能接受晚到success。
证据HTTP responses、Retry attempts、Polling transitions是三种粒度。统计与图示必须保持三者分离。

Design Choice · Boundary

设计选择与适用边界：Polling拥有唯一deadline

当前方案

内核开始时创建一次绝对deadline，向请求Context、RetryExecutor和poll sleep侧向注入同一个预算。

替代方案

每轮重新计算timeout，或只限制轮询次数而不限制请求与Retry等待。

选择理由

唯一deadline把所有耗时放进同一承诺，避免嵌套Retry和sleep重复透支。

不适用条件

当结果不是由定时查询获得时，应使用对应的主动通知消费模型，而不是复用本轮Polling状态机。

TOC约束结论系统瓶颈是总时间承诺，不是单次请求速度。优化局部Retry不能破坏全局deadline；任何局部等待都必须先证明remaining足够。
