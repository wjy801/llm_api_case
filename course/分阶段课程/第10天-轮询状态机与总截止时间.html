DAY 10 · ONE DEADLINE, EXPLICIT TERMINAL STATES

轮询状态机与总截止时间

Polling 不是“每隔几秒 GET 一次”，而是在一个总时间预算内，把每次响应解释为稳定状态、记录迁移证据，并在成功、业务失败、未知状态或超时四类终点上确定停止。

建议 2～2.5 小时前置：Day09 Retry只运行离线现有测试核心：polling.py / base_request.py
完成标志：能从 poll_get() 追踪到策略求值和状态迁移；能解释唯一 deadline 如何约束请求、Retry 与 sleep；能用 transitions 证明本轮为何停止。

01 · First principles & TOC

核心不是循环，而是可证明地停止

异步任务接口会不断返回“还没完成”。框架真正要解决的是：如何把开放式等待变成有状态、有预算、有证据的有限过程。

1

状态稳定

把不同业务字段映射为统一的 pending、success、failure、unknown。

2

预算唯一

整轮只创建一个 deadline，内部动作都消费剩余时间。

3

终点明确

成功返回响应，其余三类终点抛出可区分异常。

4

证据连续

每次观察都冻结 attempt、耗时、原始状态和HTTP状态码。

只写 while + sleep无状态合同
→
Retry与Polling各自计时预算重复承诺
→
实际耗时失控无法解释停止点
→
测试不可审计只有最后一条响应
TOC 当前约束：不是请求发送能力，而是“停止条件与剩余预算”是否只有一个权威来源。本课只学习已有 Polling 实现，不新增状态或改写策略。

02 · Source entry

从公开入口追到两个实现所有者

common/polling.py 负责状态语言和求值；common/base_request.py 负责循环、时间预算、HTTP调用、等待与异常终止。

入口职责不负责
BaseRequest.poll_get()校验参数、启动观察、进入策略轮询不直接解释业务JSON
_poll_get_with_policy()建立deadline、执行观察循环、记录迁移、决定停止不定义业务状态集合
evaluate_polling_response()按策略把一条响应映射为 PollingEvaluation不sleep、不发送请求
PollingPolicy冻结JSONPath、状态集合和unknown策略不保存运行时状态

公开入口

response = client.poll_get(
    path,
    poll_interval=0.1,
    poll_timeout=3,
    polling_policy=PollingPolicy(),
    retry_policy=retry_policy,
)

主调用链

poll_get
  → _poll_get_with_policy
    → _request_without_attach
      → RetryExecutor（可选）
    → evaluate_polling_response
    → append PollingTransition
    → return / raise / sleep

03 · Policy contract

PollingPolicy 把业务词汇翻译成框架状态

策略是冻结的 Pydantic 模型。状态字段默认取 $.status，同时允许结果路径、错误路径以及三组业务状态值。JSONPath 必须从 $ 开始。

字段默认/含义实现约束
status_json_path$.status提取原始业务状态
pending/success/failure冻结集合按成员关系归一为三种稳定状态
result_json_path可选命中非None值时优先判成功
error_json_path$.error命中非None值时最高优先判失败
unknownfail只接受 fail、pending、ignore
边界：DEFAULT_MEDIA_POLLING_POLICY 是媒体任务的默认业务映射；通用 PollingState 并不要求所有接口使用相同的原始状态字符串。

04 · Evaluation priority

求值优先级先看明确内容，再看状态集合

同一响应可能同时存在 status、result 和 error。实现用固定优先级消除歧义，避免不同调用者凭感觉解释。

1. error命中FAILURE，保留error_value
→
2. result命中SUCCESS，保留result_value
→
3. 状态集合pending/success/failure
→
4. unknown策略PENDING或UNKNOWN

稳定求值对象

PollingEvaluation(
    state=PollingState.PENDING,
    raw_status=running,
    result_value=None,
    error_value=None,
)

输入异常边界

response.json() 失败
  → AssertionError

JSONPath未命中
  → None

unknown=fail
  → PollingState.UNKNOWN
不要混淆：raw_status 是服务端事实，state 是框架解释。异常和报告必须尽量保留两者。

05 · State transitions

每次观察冻结一条 PollingTransition

循环不是隐形过程。每次响应求值后，框架记录序号、相对耗时、稳定状态、原始状态和HTTP状态码，形成可打印的迁移序列。

字段来源用途
attempt_indexPolling观察序号，从1开始区分第几次业务观察
elapsed_secondsobserved_at - started_at证明迁移发生时刻
state响应求值结果驱动后续分支
raw_status业务JSONPath值保留服务端原始语义
response_status_code最后一次HTTP响应关联协议层事实

成功路径

queued → running → succeeded
PENDING → PENDING → SUCCESS
最终返回最后一个 Response

三类异常路径

failed    → PollingFailedError
paused    → PollingUnknownStateError
deadline  → PollingTimeoutError

06 · One budget

整轮只创建一次 deadline = started_at + timeout

每次观察后重新计算 remaining。若余额耗尽立即超时；否则等待时间取 min(poll_interval, remaining)，因此最后一次sleep不会主动越过总截止时间。

真实预算骨架

started_at = monotonic()
deadline = started_at + timeout

response = request(..., deadline=deadline)
observed_at = monotonic()
remaining = deadline - observed_at

if remaining <= 0:
    raise PollingTimeoutError(...)
sleep(min(poll_interval, remaining))

预算账本

总预算
  - HTTP attempt耗时
  - Retry等待耗时
  - Polling间隔等待
  - JSON求值与记录耗时
= 当前remaining
第一性原理：timeout 不是“循环次数 × 间隔”，而是一条绝对停止线。循环次数只是请求、响应速度和剩余预算共同产生的结果。

07 · Retry cooperation

一次 Polling 观察可以包含多个 HTTP attempts

Polling 关心业务状态；Retry 关心一次观察请求能否从暂时性HTTP故障恢复。两者嵌套但不能各自拥有独立的总预算。

维度PollingRetry
判断对象业务响应状态HTTP响应或传输异常
计数单位一次业务观察一次HTTP attempt
等待poll_intervalRetry backoff / Retry-After
预算来源创建唯一deadline消费传入的同一deadline
预算耗尽PollingTimeoutErrorRetryDeadlineExceeded 被翻译为Polling超时
所有权结论：Polling 创建总 deadline，Retry 只能遵守它。这样“恢复一次HTTP观察”不会把整轮异步等待无限延长。

08 · Errors & evidence

异常对象携带最后事实，而不是只给一句“超时”

三类Polling异常都保留路径、最后状态、最后响应和完整迁移；失败异常额外保留error值，超时异常额外保留timeout。响应文本进入错误前会脱敏并限制长度。

异常触发条件关键证据
PollingFailedError求值为FAILUREerror_value、last_status、transitions
PollingUnknownStateErrorunknown策略产生UNKNOWN未识别原始状态与迁移序列
PollingTimeoutError请求内或观察后预算耗尽timeout、last_response、transitions
日志连接：_attach_polling_transitions() 把格式化迁移附加到最后一次请求日志；本课只识别该已有接口，完整运行时观察在后续课程展开。

Design Choice · Boundary

设计选择与适用边界：整轮Polling共享唯一deadline

当前方案

Polling开始时创建唯一deadline；每次请求、Retry等待和Polling sleep都读取同一remaining，并冻结状态迁移证据。

替代方案

每次观察重新计算timeout，或只限制最大轮询次数而不约束单次请求与内部Retry。

选择理由

唯一deadline把所有耗时纳入同一承诺，避免嵌套Retry和sleep重复透支；迁移记录能解释最终停止点而非只给“超时”。

不适用条件

服务通过Webhook、SSE或消息队列主动推送终态时，不应继续使用定时Polling；应把连接/订阅生命周期交给对应推送消费者。
