WEEK 4 · DAY 20

质量适配与运行事实采集

三日职责必须分开：Day18只在公共控制流发出中性事件，Day19管理Quality的disabled/collect-only/enabled接入与阶段，Day20才由QualityRuntimeHooks适配事件并在实际worker中采集P0、Semantic和Case事实。

建议时长 3 小时Runtime AdapterWorker ShardsCase Context
可核验产出：中性事件到质量事实映射表、worker采集生命周期图、分片命名说明和本轮shards/merged证据记录。

01 · First principles

适配器的职责是翻译，不是重新拥有HTTP控制流

QualityRuntimeHooks实现中性Protocol，但不发起请求、不决定Retry、不推进Polling，也不消费SSE。它只把已经发生的运行事件转换为质量层已有模型。

Day18：发中性事件→Day19：管理Quality接入→Day20：适配并采集事实

P0事实

一次真实请求attempt的耗时、状态、业务结果和usage。

Semantic事实

Operation、Request Group、Polling Session和Stream之间的关系。

pytest事实

setup、call、teardown三个阶段的CaseResult和JUnit身份。

TOC约束：本层最容易出现的错误是把三类事实揉成一个结论。采集阶段只记录各自事实，Day21～23再按顺序归并、建关系和计算指标。

02 · Worker binding

controller传配置，真正执行测试的进程拥有采集器

  1. 轻量插件确认Quality开启后动态注册quality.pytest_plugin_runtime。
  2. xdist controller不创建Collector，只通过pytest_configure_node把run_id、execution_id、输出目录和Semantic开关传入workerinput。
  3. worker或非xdist进程构造QualityRunContext：run、execution、worker三层身份齐备。
  4. runtime plugin配置P0 Collector、可选SemanticCollector，并绑定QualityRuntimeHooks。
  5. pytest_unconfigure按逆序完成pending记录并reset hooks、run context和collector。
Runner stage env→controller workerinput→worker RunContext→Collectors→Hooks bind

03 · Adapter mapping

每个中性方法映射到现有采集入口

Runtime HookQuality目标结果
begin/finish_operationsemantic_context创建或完成OperationHandle
start/finish_request_groupsemantic_context记录一次可重试请求组
request_started/succeeded/failedrequest_metrics开始attempt捕获并形成RequestMetric
Polling methodssemantic_context状态、sleep与Polling终态
Stream methodssemantic_context绑定Operation、记录行与Stream终态

适配器用isinstance验证native handle，只把类型正确的handle交给质量上下文；枚举通过value映射到质量枚举，避免公共层导入质量类型。

04 · Request attempt facts

RequestMetric回答一次真实attempt发生了什么

request_started调用start_request_capture()，在RequestContext attributes中保存事件身份和开始信息；成功时record_response()读取响应，失败时record_exception()读取异常，最终构造不可变RequestMetric并交给Collector。

事实维度典型字段语义
身份run、execution、worker、case、invocation、request_event_id
接口method、规范化URL/接口身份、protocol
传输响应、超时或错误，状态码与耗时
业务业务成功、失败、未知或不适用
用量token、媒体数量或时长；缺失保持缺失

一次Retry会产生多个RequestMetric，而不是修改第一次attempt。这样后续既能看最终结果，也能保留中间失败和重试成本。

05 · Semantic entry

SemanticCollector记录关系草稿，不替P0保存请求事实

Operation由业务能力或通用HTTP入口创建；Request Group把多个attempt event id组织成一次逻辑调用；Polling Session引用轮询期间的多个Group；SSE把流终态和首数据时机补到Operation。

P0引用

Semantic记录保存RequestMetric的request_event_id，不复制整条请求事实。

Pending收口

用例协议结束或插件卸载时，finalize_pending()把未显式完成的关系标记为不完整，而不是静默丢弃。

本课只关注采集入口。关系所有权与完整性验证将在Day22展开。

06 · Worker-owned shards

每个execution与worker写独立分片

QualityCollector根据RunContext建立三个文件：

分片内容命名
casesCaseResult阶段事实cases-{execution_id}-{worker_id}.jsonl
requestsRequestMetric attempt事实requests-{execution_id}-{worker_id}.jsonl
integrity采集与写入问题integrity-{execution_id}-{worker_id}.jsonl

初始化时只清空当前worker拥有的三个文件，不影响同run其他worker。进程内用RLock串行化JSONL append，保证并发请求不会交叉写坏一行。Collector注册表本身也有锁，配置与reset是明确生命周期动作。

07 · Pytest case facts

每个用例先建立稳定CaseContext，再记录三个阶段

  1. pytest_runtest_protocol根据nodeid和参数构造case_id、param_hash与invocation_id，并写入ContextVar。
  2. autouse fixture把case_id和invocation_id写入JUnit properties，供P0归并对账。
  3. pytest_runtest_logreport只接受setup、call、teardown，按report状态映射passed、failed、error、skipped、xfail和xpass。
  4. 每个阶段形成独立CaseResult，保存duration、起止时间、raw_status和final_status。
  5. 协议结束时finalize pending语义记录，并reset CaseContext。

CaseResult不是“用例最终一行”。setup、call和teardown事实先分别保存，Day21再用fold_case_status()归并为invocation终态。

08 · Integrity and fail-open

采集错误进入完整性事实，不得替换业务结果

问题处理
Request捕获函数异常适配器捕获并写request_capture_failed
Case或Request主分片写失败Collector尝试写ERROR级完整性问题并返回False
完整性分片自身写失败只向warning sink报告，避免递归写失败
CaseContext构造失败记录case_context_build_failed，pytest继续
SemanticCollector初始化失败关闭Semantic采集并警告，P0仍可继续

fail-open不等于“采集成功”。业务控制流保持原样，采集完整性通过显式Issue表达，后续归并据此判定complete、degraded或failed。

Design decision

设计选择与适用边界

现方案替代方案选择理由不适用条件
由Quality适配器把Day18事件翻译为P0/Semantic模型，Collector按execution与worker写独立JSONL分片，失败进入完整性事实。让common直接构造Quality模型，或所有worker并发写同一共享文件并在写失败时中断业务请求。适配层隔离模型依赖，worker本地分片避免锁与交叉污染，fail-open保留业务结果同时显式报告采集退化。需要实时全局聚合、严格跨worker顺序或事务查询时，本地分片不足，应使用中心化Collector、消息队列或事务数据库。

10 · Current-run artifact

生成本轮Quality采集分片并核对身份

$python = '.\.venv\Scripts\python.exe'
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$root = Join-Path 'reports/course' ('day20-quality-' + $stamp)
$runId = 'course-day20-' + $stamp
$names = @('QUALITY_ENABLE','QUALITY_SEMANTIC_ENABLE','QUALITY_METRICS_ENABLE','QUALITY_FLAKY_HISTORY_ENABLE','QUALITY_FLAKY_STATE_ENABLE','QUALITY_OUTPUT_DIR','QUALITY_RUN_ID','GENERATE_ALLURE_REPORT','GENERATE_HISTORY_REPORT')
$old = @{}; foreach ($name in $names) { $old[$name] = [Environment]::GetEnvironmentVariable($name) }
try {
  $env:QUALITY_ENABLE = '1'; $env:QUALITY_SEMANTIC_ENABLE = '1'; $env:QUALITY_METRICS_ENABLE = '0'
  $env:QUALITY_FLAKY_HISTORY_ENABLE = '0'; $env:QUALITY_FLAKY_STATE_ENABLE = '0'
  $env:QUALITY_OUTPUT_DIR = $root; $env:QUALITY_RUN_ID = $runId
  $env:GENERATE_ALLURE_REPORT = 'FALSE'; $env:GENERATE_HISTORY_REPORT = 'FALSE'
  $allure = Join-Path $root 'allure-results'
  & $python run_master.py module/offline_framework_example -n 2 --alluredir=$allure
  if ($LASTEXITCODE -ne 0) { throw ('Runner exit=' + $LASTEXITCODE) }
  $run = Get-Content -LiteralPath (Join-Path $root 'run.json') -Raw | ConvertFrom-Json
  $p0 = Get-Content -LiteralPath (Join-Path $root 'merged/manifest.json') -Raw | ConvertFrom-Json
  $semantic = Get-Content -LiteralPath (Join-Path $root 'semantic/merged/manifest.json') -Raw | ConvertFrom-Json
  $shards = @(Get-ChildItem -LiteralPath (Join-Path $root 'shards') -File)
  [pscustomobject]@{ Run=$run.run_id; P0=$p0.status; Integrity=$p0.integrity_status; P0Shards=$shards.Count; Cases=$p0.output_counts.case_results; Requests=$p0.output_counts.request_metrics; Semantic=$semantic.status }
}
finally { foreach ($name in $names) { [Environment]::SetEnvironmentVariable($name,$old[$name]) } }

Week 4 review · 30～45分钟

按一条职责链复盘：Day16提交执行事实，Day17管理报告所有权，Day18发事件，Day19管理Quality接入，Day20适配采集。不要把相邻层的职责互相代做。

时间动作验收信号
0～10分钟画Day16～20职责链并标出每层输入/输出。Day18/19/20三段职责无重叠。

30～45分钟复用本周主成果完成一次综合更新并进行六维0～2评分。总分至少9/12，所有权和证据映射均不为0分。

可选草稿：详细拆分记录

六维0～2统一评分

统一维度为源码定位、调用链与状态、所有权、证据映射、设计边界和迁移能力。总分至少9/12，且所有权、证据映射不得为0分。

维度评分2分判据
源码定位能从Runner入口独立定位Allure、Hooks、Quality生命周期与Adapter。
调用链与状态能解释执行、报告、事件、接入和采集五段状态转换。
所有权能区分Runner、Allure、common Hooks和Quality的唯一写入与收口责任。
证据映射能说明execution-result、Allure raw和Quality分片分别证明什么。
设计边界能比较中性Hooks与common直连Quality的耦合后果。
迁移能力能把事件到事实映射独立迁移到相邻已有场景。
