DAY 07 · REQUEST DIAGNOSTIC PIPELINE

请求中间件、脱敏日志与资源捕获

昨天你追踪了 HTTP 主干；今天沿主干旁边的“诊断支线”前进。目标不是背四个类名，而是能判断：什么可以观察，什么可以复制，什么绝不能改变业务结果。

建议 2.5～3 小时先测试后实现不访问真实外部接口不修改框架代码
当日产出：选择一个脱敏或 Capture 用例，用“原始业务结果 → 附加诊断结果 → 诊断失败时的优先级”三段式说明其合同。

01 · First principles

先锁定本课真正要解决的问题

HTTP 请求的第一目标是获得可信业务结果；日志、指标和资源附件都是次级观察。成熟框架的难点，是在增加可诊断性的同时，不泄密、不篡改、不遮蔽原始故障。

1

解释真实顺序

能说清 before、after、on_exception 都按默认列表正序执行，而非臆想成逆序洋葱。

2

区分两条数据轨

业务请求保留真实凭据；日志只消费脱敏副本，两者不能混用。

3

追踪两类 Capture

输入资源由 POST 前置中间件启动，输出结果由 poll_get 装饰器在成功响应后触发。

4

判断失败优先级

用代码证据区分 fail-open 已覆盖范围与仍会中断请求的中间件边界。

TOC 约束链

需要更多诊断信息
诊断必须接触请求数据
接触可能泄密或引入新失败
诊断副本 + 明确失败边界
本课瓶颈如果只记“观察失败必须 fail-open”，你会错读实现。真正要掌握的是：哪一层捕获了异常、保留了什么返回值、失败发生在 Session 前还是后。

02 · Composition

默认顺序是一条依赖链，不是装饰清单

后一个中间件可以消费前一个中间件写入的 Context 属性，因此顺序本身就是合同。尤其是 Logging 必须排在 Redaction 后面。

1 · RuntimeObservation记录请求事实，钩子内部安全调用
2 · MediaResourcePOST 前异步启动输入媒体下载
3 · Redaction生成 redacted_kwargs 副本
4 · Logging用脱敏副本创建 ApiCallLogger
中间件before_requestafter_responseon_exception不负责什么
RuntimeObservationMiddlewarerequest_startedrequest_succeededrequest_failed不生成报告结论，不依赖 quality
MediaResourceMiddleware仅 POST：从 json.input.media 提取 URL 并启动线程无操作无操作不等待下载完成，不负责输出结果
RedactionMiddleware把脱敏副本写入 attributes无操作无操作不修改 context.kwargs
LoggingMiddleware构造 logger 并记录开始时间按 attach_log 决定是否附加成功日志按 attach_log 决定是否附加失败日志不决定状态码是否通过

03 · Lifecycle player

三个阶段都正序，但失败语义不同

点击阶段，观察谁被调用、HTTP 位于哪里，以及异常最终由谁持有。注意：before 位于 Session 的 try 之外。

关键纠偏这里不是 Web 框架常见的“请求正序、响应逆序”洋葱模型。三个循环都直接遍历 self.middlewares，所以均为正序。

04 · Isolation

脱敏不是改请求，而是建立诊断副本

同一条请求需要同时满足两个看似冲突的条件：服务端必须收到真实 Authorization；报告中不能出现 API Key。解法不是“先删再发”，而是把业务数据轨与诊断数据轨分开。

业务数据轨 · 真实性优先

调用者 payload进入 BaseRequest 后先被安全复制
context.kwargs保留真实 Header 与业务 JSON
session.request只消费这条轨道
业务 Response由服务端真实处理结果决定
并行
不互换

诊断数据轨 · 安全优先

redact_request_kwargs递归生成脱敏副本
attributes.redacted_kwargs保存诊断视图
ApiCallLogger消费诊断视图
Allure / cURL再次对 PreparedRequest 做防御性脱敏
context.kwargs = { "headers": {"Authorization": "Bearer offline-key"}, "json": {"token": "abc", "prompt": "hello"} }
复制
→
attributes["redacted_kwargs"] = { "headers": {"Authorization": "<redacted>"}, "json": {"token": "<redacted>", "prompt": "hello"} }
✓ Header 名和敏感字段名大小写不敏感✓ URL 查询参数与 PreparedRequest body 也会处理△ 键匹配是明确名单，不是任意包含 token 的字符串
可执行证据test_sensitive_headers_preserve_business_request 验证业务 Header 仍在 Session 中；test_middleware_does_not_mutate_original_payload 验证调用者 payload 保持不变。

05 · Input capture

输入 Capture：请求前启动，测试结束时收口

输入资源可能很大，不能阻塞 POST 主请求。框架把下载交给 daemon 线程，把任务状态放入测试级 ContextVar 集合，再由 pytest teardown 统一附加。

测试 fixture开始任务集合
POST before解析 json.input.media
daemon 线程流式下载资源
业务请求无需等待下载
teardown停止集合并检查任务
Allure文件或失败文本

成功时

任务完成且文件存在，按扩展名识别附件类型并附加文件。

尚未完成时

teardown 设置 cancel_event，并附加“未完成”的文本诊断；不会等待无限时长。

下载失败时

线程把异常文本写入 task.error 并设置 done_event，异常不跨线程覆盖 POST 结果。

适用范围

仅 POST、仅 JSON 中合法的 input.media URL，并受 CapturePolicy 控制。

06 · Output capture

输出 Capture：轮询成功后，从结果字段提取链接

输出资源不属于请求前中间件。download_links_from_poll_get 装饰 poll_get：先让轮询返回最终 Response，再依据 PollingPolicy 的 result_json_path 提取 URL。

poll_get完成轮询
最终 Response业务结果已获得
JSONPath取结果字段
URL 去重递归收集链接
流式下载受输出上限控制
记录/附加结果文件

CapturePolicy 是一个能力开关，不是断言

默认CapturePolicy()输入与输出均开启，无字节上限。
完全关闭disabled()不捕获资源，业务请求仍照常。
仅输入input_only(max_bytes=...)只设置 max_input_bytes。
仅输出output_only(max_bytes=...)只设置 max_output_bytes。
不要混淆Capture 成功不等于业务断言通过，Capture 失败也不等于接口失败。它是证据增强层；状态码、Schema 和业务字段仍由 Assertions 判断。

07 · Failure semantics

“必须 fail-open”要落到具体异常捕获点

第一性原理要求原始业务事实优先；代码审查则要求我们只声称已经实现的保障。下面矩阵把原则、机制和剩余边界放在一起。

失败位置当前机制业务结果优先级结论
Runtime Hooks 的 started / succeeded / failed生命周期函数内部 _safe_call 捕获 Exception请求或响应继续fail-open
输入资源下载线程异常写入 task.error，finally 设置 done_event不覆盖 POST Responsefail-open
输出 URL 提取或下载装饰器捕获异常并尝试附加失败文本，随后返回原 Response最终轮询 Response 保留fail-open
传输异常后的 on_exception 附件收集中间件异常，把说明 add_note 到原 request_error重新抛原始传输异常fail-open
before_request 中间件自身抛错包装为 RuntimeError；此时 Session 尚未调用业务请求不会发出会中断
成功响应后的 after_response / 日志附件抛错包装为 RuntimeError已取得的 Response 不会正常返回调用者会遮蔽
pytest teardown 附件过程自身抛错资源下载状态可降级；但外层附加流程没有统一吞错取决于具体附件失败点有限保护
审阅结论“观察或附件失败必须 fail-open”是正确设计原则，但不能把它误写成全链路现状。定位问题时必须先回答：失败发生在哪个阶段？异常由哪一层捕获？原始 Response 或 error 是否还在？

08 · File integrity

下载负责安全落盘，artifact_io 负责可信读取

这两个模块位于证据生命周期的两端。一个避免留下“看似完整”的半文件，另一个让后续质量层验证格式、行号与哈希。

原子落盘的最小链路

分配唯一目标名
写入隐藏 .part 临时文件
校验 Content-Length 与累计字节
replace 为最终文件
异常时清理临时与目标

写入侧 · downloads

  • 文件名清洗与同名避让
  • 分块流式写入，支持取消
  • 头部预检 + 实际字节双限额
  • 成功后才暴露最终文件名
证据
→

读取侧 · artifact_io

  • JSON 必须是 object
  • JSONL 错误携带准确行号
  • SHA-256 比较基于实际字节
  • 精确字段不一致返回字段名集合
边界判断util/artifact_io.py 不触发 Capture，也不附加 Allure；它提供的是后续读取和完整性核验原语。

11 · Knowledge check

知识自测

答对 5 题视为达标。提交后会显示解释。

1. 为什么 LoggingMiddleware 必须位于 RedactionMiddleware 之后？
正确答案是 B。顺序建立了数据依赖；不存在响应自动逆序。
2. 哪个对象最终传给 session.request？
正确答案是 C。脱敏副本只进入诊断轨，不替代真实请求参数。
3. 输入媒体下载由谁触发？
正确答案是 A。输出结果下载才由 poll_get 装饰器在最终响应后触发。
4. 下载为何先写 .part 文件？
正确答案是 C。异常路径还会清理临时文件与目标文件。
5. after_response 的日志附件失败，当前实现一定 fail-open 吗？
正确答案是 B。Session 的 try 已结束，after_response 自身有显式 RuntimeError 包装。
6. artifact_io 在本课链路中的定位是什么？
正确答案是 A。它是证据读取侧，不是Capture触发器。
