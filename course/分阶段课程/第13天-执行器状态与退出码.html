DAY 13 · PRESERVE RAW FACTS, DECIDE EXPLICITLY

Runner状态机、退出码与执行事实

一个可靠Runner不能把“pytest正常返回”“用例通过”“池已执行”“报告生成成功”混成一个布尔值。它必须保存原始事实，再用明确策略决定继续、停止与最终退出。

建议 1.5～2.5 小时前置：第12天唯一计划核心：runner.py / artifacts.py实践：离线执行事实
完成标志：能区分pytest原始退出码、池状态与Runner最终码；能解释exit 1为何继续、2/3/4/5为何停止；能逐字段核对 execution-result.json，并说明原子写入失败为何不能产生假成功。

01 · First principles & TOC

退出码是事实压缩，不是错误文案

进程最终只能返回一个整数，但一轮执行包含收集、多个池、基础设施异常和产物写入。正确做法不是丢掉细节，而是先保存结构化事实，再把决策压缩为最终码。

1

保留原码

池级pytest返回什么就记录什么，不被Quality、Allure或报告重写。

2

状态与结果分离

COMPLETED表示调用返回，raw exit才说明pytest结果。

3

停止有规则

用例失败继续收证；中断、内部/用法错误、空集合立即停。

4

事实可传递

原子JSON把计划、池事实与最终码交给后续报告，不推导Jenkins结论。

把所有非零都当同一种失败丢失中断/用法/空集语义
→
后续池继续或停止靠猜证据收集行为不稳定
→
报告覆盖原始事实绿灯可能来自工具成功
→
无法审计不知道谁改变了结果
TOC 当前约束：真正限制可靠性的不是执行分支数量，而是“终止事实是否仍然可辨认”。先冻结raw exit和池状态，再让Runner做最小、显式的停止与归并决策。

02 · Fact layers

四层事实不能互相替代

每层回答不同问题。混用字段是产生假结论的主要来源。

PYTEST RAW

pytest原始退出码

回答本次pytest调用返回了0、1、2、3、4还是5。它是池级最接近执行源的结果事实。

POOL STATE

池有没有被运行

NOT_RUN、COMPLETED、ERROR描述执行器状态；不直接等于测试通过/失败。

RUNNER FINAL

进程最终退出决策

合并已执行池原码，并考虑Runner异常与执行事实写入是否成功。

MACHINE FACT

execution-result.json

把权威计划、每池事实和最终码结构化保存，供后续流水线与报告读取。

Pool status ≠ pytest outcome ≠ Runner final ≠ Jenkins status它们有关联，但任何一层都不能擅自冒充另一层。
典型误读：status="COMPLETED" 且 raw_pytest_exit_code=1 的含义是“pytest完整返回了用例失败事实”，不是“池执行成功”。

03 · Pytest exit semantics

0～5是六种不同事实

Runner按pytest公开语义保留原码。停止策略不是简单的“非零即停”。

码pytest事实池状态有后续串行池时Runner原则
0全部通过COMPLETED + raw 0继续所有已执行池均0才可能最终0。
1测试失败COMPLETED + raw 1继续继续串行池，尽量收集完整失败证据；最终1。
2用户中断若pytest以码返回则COMPLETED + raw 2停止保留2，不把中断伪装成普通失败。
3pytest内部错误COMPLETED + raw 3停止执行基础已不可信。
4pytest命令行用法错误COMPLETED + raw 4停止参数合同错误，后续池同样不可信。
5没有收集到测试收集阶段通常直接返回5不启动空集合不是成功，必须原样暴露。
为什么exit 1例外：它说明pytest基础设施仍正常，只是业务断言失败。继续独立串行池能多获得失败证据；最终码仍然是1，不会因后续池通过而被冲掉。

04 · Pool state model

NOT_RUN、COMPLETED、ERROR描述“执行器发生了什么”

PoolExecutionResult 同时保存计划、状态、raw exit、时间、异常类型和JUnit路径。字段组合比单一状态更有意义。

NOT_RUN

没有调用pytest

空池，或因前序池出现终止码/ERROR而跳过。

raw exitnull
timestampsnull
planned nodeids可能非空
COMPLETED

pytest正常返回

raw可以是0、1、2、3、4或5；必须再看原码。

raw exitinteger
timestamps有值
exceptionnull
ERROR

执行器抛出异常

例如调用pytest时发生OSError；没有pytest返回码。

raw exitnull
timestamps有值
exception异常类型
planned_nodeids非空不等于已执行：前序池终止时，串行池会保留原计划nodeid，但状态为NOT_RUN、raw为null。这正是“计划事实”和“执行事实”分开的价值。

空池直接返回

if not nodeids:
    return PoolExecutionResult(
        stage_id=stage_id,
        planned_nodeids=(),
        status=PoolExecutionStatus.NOT_RUN,
        junit_path=junit_path,
    )

异常不是pytest raw

except Exception as error:
    return PoolExecutionResult(
        stage_id=stage_id,
        planned_nodeids=nodeids,
        status=PoolExecutionStatus.ERROR,
        exception_type=type(error).__name__,
        raw_pytest_exit_code=None,
    )

05 · Runner state machine

从参数到机器事实的状态迁移

Runner按固定顺序推进；早期失败不会伪造后续阶段已运行。

主状态机
参数分相非法缺值 → exit 4
权威收集异常 → exit 1；非0保留原码
计划分池collect-only在此返回
Parallel可选，得到PoolResult
停止决策ERROR或raw 2/3/4/5？
归并并写事实final code + atomic JSON
否：raw 0或1 → 若有serial计划则继续执行。
是：后续serial记为NOT_RUN，不再调用pytest。
Collect OK冻结计划
→
P: COMPLETED/1业务失败但基础仍可信
→
S: COMPLETED/0继续收集证据
→
Final 1失败不被后池覆盖
KeyboardInterrupt/SystemExit边界：它们不被池内 except Exception 转成ERROR；外层将运行状态标为INTERRUPTED后重新抛出，同时仍执行生命周期finalize。不要把强中断与普通池异常混为一谈。

06 · Continue or stop

继续收证与立即止损的边界

决策基于“后续执行是否仍然可信”，而不是基于错误看起来是否严重。

0 / 1

允许进入后续池

  • 0：当前池通过，正常继续。
  • 1：断言失败，但pytest和参数合同仍工作。
  • 继续不代表忽略失败；最终至少为1。
2 / 3 / 4 / 5 / ERROR

停止所有后续池

  • 2：用户已要求中断。
  • 3：pytest内部状态不可信。
  • 4：命令参数合同错误。
  • 5：不存在可执行集合。
  • ERROR：Runner未获得pytest原始结果。
exit 1业务失败是有效证据
→
继续serial获得更多独立证据
→
merge=1任何后续成功都不漂白失败
　
exit 2～5 / ERROR执行前提失效 → 立即停止
停止不是丢计划：被跳过池仍在机器事实中保存 planned_nodeids 和 status=NOT_RUN，从而区分“本来没有用例”和“有计划但未执行”。

07 · Exit merge

最终退出码只归并已执行池的原始事实

NOT_RUN没有raw码，因此不参与数值归并。若任一池状态为ERROR，Runner先返回1；否则按终止码、失败码、未知非零、全零的优先级归并。

真实归并顺序
if any(pool.status is ERROR):
    return 1

codes = [
    pool.raw_pytest_exit_code
    for pool in pool_results
    if pool.raw_pytest_exit_code is not None
]

if not codes:
    return 0
for code in codes:
    if code in {2, 3, 4, 5}:
        return code
if 1 in codes:
    return 1
if any(code != 0 for code in codes):
    return 1
return 0

决策优先级

1 · Pool ERROR没有pytest结果，Runner返回1。
2 · 终止型原码保留遇到的2/3/4/5。
3 · 业务失败任一1使最终为1。
4 · 未知非零保守归一为1。
5 · 全部0最终才是0。
Parallel raw/statusSerial是否运行Serial raw/statusFinal
0 / COMPLETED是0 / COMPLETED0
1 / COMPLETED是0 / COMPLETED1
0 / COMPLETED是1 / COMPLETED1
2 / COMPLETED否NOT_RUN / null2
ERROR / null否NOT_RUN / null1
无并发计划 / NOT_RUN是0 / COMPLETED0

08 · Machine evidence

execution-result.json 保存Runner事实，不推导流水线结论

Schema版本为 runner-execution.v1。它让后续消费者不必解析控制台文本，同时保留计划与实际执行的差异。

{
  "schema_version": "runner-execution.v1",
  "test_target": "module/offline_framework_example",
  "selection_args": [],
  "planned_case_count": 23,
  "planned_nodeids": ["...23 nodeids..."],
  "collection_exit_code": 0,
  "pool_results": [
    {
      "stage_id": "parallel-pool",
      "planned_nodeids": ["...23 nodeids..."],
      "status": "COMPLETED",
      "raw_pytest_exit_code": 0,
      "started_at": "...+00:00",
      "completed_at": "...+00:00",
      "exception_type": null,
      "junit_path": "...parallel.xml"
    },
    {
      "stage_id": "serial-pool",
      "planned_nodeids": [],
      "status": "NOT_RUN",
      "raw_pytest_exit_code": null,
      "started_at": null,
      "completed_at": null,
      "exception_type": null,
      "junit_path": "...serial.xml"
    }
  ],
  "final_exit_code": 0
}

字段对照

planned_case_count权威收集计划长度，不是Quality的expected_case_count字段。
planned_nodeidsRunner打算执行的完整身份集合。
collection_exit_code权威收集的pytest原始码。
pool_results每池计划、状态、raw、时间、异常类型和JUnit路径。
final_exit_code写入动作之前计算出的Runner最终决策。
它负责：权威计划、池级原始执行事实、Runner最终码。
它不负责：推导Jenkins SUCCESS/FAILURE、质量指标或业务解释。
它是：机器传递证据，适合结构化消费。
它不是：新的人工报告首页，也不是Allure/JUnit替代品。
路径提示不等于文件证明：junit_path 记录池对应的计划路径；尤其在NOT_RUN池中，它不证明该JUnit文件实际存在。

09 · Atomic commit & simulator

写入必须原子；写失败必须阻止假成功

机器证据先写同目录临时文件，flush并fsync，再用 os.replace() 原子替换目标。异常时清理临时文件。

mkdir parent确保reports目录存在
→
NamedTemporaryFile与目标同目录
→
JSON + newlineUTF-8、排序、缩进
→
flush + fsync提交文件内容
→
os.replace原子替换目标

终止型码2/3/4/5

若执行事实写入失败，仍返回原终止码。否则磁盘问题会掩盖更具体的中断/内部/用法/空集事实。

原final为0或1

写入失败一律返回1。尤其不能在关键机器事实未落盘时仍返回0，制造假成功。

陈旧文件边界：原子替换失败时，新证据不可信；目标位置可能仍是上一轮文件。消费者必须结合本轮上下文和退出码判断新鲜度，不能把“路径存在”当作本轮写入成功。

11 · Knowledge check

知识自测

答对5题视为达标。每题都要求区分状态、原始结果与最终决策。

1. Pool状态COMPLETED且raw=1表示什么？
答案C。COMPLETED描述调用返回，raw 1描述业务结果。
2. 并发池raw=1时，存在串行计划应如何处理？
答案B。exit 1不代表执行基础失效。
3. 哪组结果会停止后续池？
答案A。它们是终止型或无pytest原码的基础设施异常。
4. 两池都raw=0，但execution-result写入失败，进程返回什么？
答案C。关键机器事实未落盘时不能产生假成功。
5. execution-result中的planned_case_count是什么？
答案B。它属于Runner机器事实，不能跨层改名。
6. 串行池status=NOT_RUN但planned_nodeids非空说明什么？
答案A。计划存在与实际执行是两种事实。

12 · Exit gate

本课门禁：原始事实只能被保存，不能被美化

一句话验收：Pool状态描述调用是否发生，raw exit保存pytest结果，Runner依据可信度决定继续或停止并归并final；execution-result原子记录这些事实，写失败绝不能把不完整运行变成成功。
