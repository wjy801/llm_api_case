common/test_context.py::TestContext.add_cleanup / cleanup · 连续源码第226至241行
def add_cleanup(self, callback: Callable[..., Any], *args: Any, **kwargs: Any) -> None:
    if not callable(callback):
        raise TypeError(f"cleanup callback must be callable, actual: {callback!r}")
    self._cleanup_callbacks.append(_CleanupCallback(callback=callback, args=args, kwargs=dict(kwargs)))

def cleanup(self) -> None:
    errors: list[BaseException] = []
    while self._cleanup_callbacks:
        cleanup_callback = self._cleanup_callbacks.pop()
        try:
            cleanup_callback.callback(*cleanup_callback.args, **cleanup_callback.kwargs)
        except BaseException as exc:
            errors.append(exc)

    if errors:
        raise ContextCleanupError(errors)

最终收口

输入从哪里来

回调栈由用例执行过程中多次add_cleanup()累积。

当前消费什么

pop()逐个消费最后注册的回调及其冻结参数。

输出写到哪里

成功回调作用于外部资源；失败异常先进入局部errors列表。

谁负责收口

cleanup()必须清空栈；ContextCleanupError在全部回调结束后统一交还上层。

分支

无错误正常返回；有错误聚合抛出；栈为空时直接返回，因此重复cleanup不重复释放。

代码先行结论

  1. 值生命周期的提交点只有self.set()，此前任何失败都不得污染上下文。
  2. 资源生命周期的提交点是add_cleanup()，此后cleanup()必须把责任栈排空。
  3. 两条链都属于单个测试用例；TestContext不是跨用例共享数据库。

01 · Question

为什么上下文既要保存值，也要拥有清理顺序

跨步骤测试需要复用ID、Header、Cookie等值，同时必须保证中途断言失败后已创建资源仍被释放。TestContext把两类责任限制在单个用例作用域内。

03 · Scope

TestContext只属于当前测试用例

fixture创建→步骤写入变量→后续步骤读取→teardown运行cleanup

它不能作为跨用例数据库，也不能隐藏共享账号、余额或环境状态。用例结束后变量与资源责任同时结束。

04 · Extract

提取把响应边界转换成稳定输入

来源用途
JSON path取得任务ID、结果字段等结构化值。
Header读取请求追踪或分页信息。
Cookie保存当前用例会话返回值。
Regex从受控文本中提取匹配内容。

提取后先处理缺失语义：有default则把default作为后续输入；required缺失则报出变量名、来源和路径；非required且无default则返回None且不写入上下文。不能把缺失值静默改成空字符串。

05 · Transform

transform负责转换，expected_type只负责校验

原始字符串或JSON值需要变成整数、布尔值或业务结构时，必须由transform显式转换。expected_type只用isinstance语义检查transform后的结果是否符合声明类型，不会调用目标类型，也不会替代转换器。

严格顺序：提取/缺失与默认处理 → transform转换 → expected_type类型校验 → 写入TestContext。transform失败、类型不匹配和提取缺失是三类不同错误；只有前三步全部成功后才允许写入。

06 · Cleanup

LIFO按依赖图逆序释放资源

创建服务→创建Client→创建临时资源→使用→资源→Client→服务

后创建的对象通常依赖先创建对象，因此cleanup栈必须后进先出。LIFO不是偏好，而是依赖关系的逆序。

07 · Error handling

一个cleanup失败不能阻止后续清理

收口阶段应继续执行剩余cleanup并汇总错误。否则第一个关闭异常会遮挡后续Session、线程或临时资源泄漏。

业务已失败

保留原测试失败，同时附加cleanup错误信息。

业务已通过

cleanup错误仍说明资源合同未完成，不能静默忽略。

Design decision

设计选择与适用边界

现方案替代方案选择理由不适用条件
每个用例拥有独立TestContext，按“提取/默认处理 → transform转换 → expected_type校验 → 写入”形成稳定值，再把清理动作按注册顺序入栈、按LIFO执行。使用进程级全局字典保存变量，或按FIFO执行统一teardown。用例作用域阻断串值；LIFO与资源依赖图的逆序一致，且单个cleanup失败不会吞掉后续清理事实。跨用例只读配置应放入会话级配置对象；需要跨进程共享的可变状态必须使用外部存储和显式一致性协议。

阅读问题一个回调失败后，为什么仍继续弹出其余回调？

    def cleanup(self) -> None:
        errors: list[BaseException] = []
        while self._cleanup_callbacks:
            cleanup_callback = self._cleanup_callbacks.pop()
            try:
                cleanup_callback.callback(*cleanup_callback.args, **cleanup_callback.kwargs)
            except BaseException as exc:  # noqa: BLE001 - cleanup must continue after any callback failure.
                errors.append(exc)

        if errors:
            raise ContextCleanupError(errors)
阅读答案

结论：cleanup按LIFO执行全部回调，单个失败不会阻断后续清理。机制：持续pop栈顶并捕获BaseException，将错误累积；栈清空后若有失败，再统一抛出ContextCleanupError。

源码执行依据

持续pop形成LIFO，捕获每个BaseException并继续，栈耗尽后统一抛ContextCleanupError。

状态结果

清空回调栈；成功时幂等，失败时聚合全部已捕获错误。

证据结论

清理采用LIFO、失败继续和最终聚合，而不是首错即停。

答案边界
