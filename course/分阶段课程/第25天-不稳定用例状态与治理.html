输入与验收

输入事实

三个run已由Day24链导入为同一flaky_key的Observation序列。

状态变化

第一次建立OBSERVING transition，第二次只更新证据，第三次达到阈值进入STABLE。

持久化所有权

FlakyStore保存state与transition，check_database()证明没有漏投影或陈旧投影。

失败边界

状态值正确但transition数量或projection完整性错误，仍属于失败。

replay_observations()只做确定性规则投影

def replay_observations(
    observations: Sequence[FlakyHistoryEntry],
    config: FlakyRuleConfig = DEFAULT_FLAKY_RULE_CONFIG,
) -> FlakyProjection:
    ordered = sort_observations(observations)
    if not ordered:
        raise ValueError("at least one observation is required")

    state: FlakyState | None = None
    stable_signature: str | None = None
    transitions: list[FlakyTransitionDecision] = []
    for index, observation in enumerate(ordered, start=1):
        prefix = ordered[:index]
        evidence = derive_evidence_window(prefix, config)
        previous = state
        reason: str | None = None
        if state is None:
            state = FlakyState.OBSERVING
            reason = "first_observation"
        elif state is FlakyState.OBSERVING:
            if evidence.signature_switch_count > 0:
                state = FlakyState.SUSPECTED
                reason = (
                    "outcome_changed"
                    if evidence.outcome_switch_count > 0
                    else "failure_fingerprint_changed"
                )
            elif evidence.sample_size >= config.stable_min_samples:
                state = FlakyState.STABLE
                stable_signature = evidence.latest_signature
                reason = "consistent_signature_threshold_met"
        elif state is FlakyState.STABLE:
            if stable_signature is None:
                stable_signature = evidence.latest_signature
            latest_signature = build_result_signature(observation)
            if latest_signature != stable_signature:
                state = FlakyState.SUSPECTED
                reason = "stable_signature_broken"

纯规则边界

输入验证

至少一条Observation；排序键固定为observed_at、run_end_time、run_id、observation_id。

证据

每一步都重新计算窗口、signature switch、outcome switch与连续签名。

产出

返回FlakyProjection和transition decisions，便于测试与重建复用。

所有权边界

该函数不拥有detected/current列写入；不能用它单独解释QUARANTINED或RECOVERING。

数据库状态变化

输入验证

run必须已导入；无eligible Observation返回NO_DATA而不是伪造STABLE。

计划

每个flaky_key独立生成ProjectionPlan，包含候选状态、证据、transition与治理上下文。

事务

所有计划在同一repository事务中写入；state、transition和projection status保持一致。

失败边界

任何计划或写入失败都回滚本次评估，但Day24已提交的Observation历史不被删除。

def quarantine(
    connection: sqlite3.Connection,
    repository: FlakyRepository,
    request: FlakyQuarantineRequest,
) -> FlakyGovernanceRecord:
    now = datetime.now(UTC)
    if request.expires_at.astimezone(UTC) <= now:
        raise FlakyStoreError("invalid_expiry", "expires_at must be in the future")
    state = repository.require_state(connection, request.flaky_key)
    if state.current_state is not FlakyState.CONFIRMED:
        raise FlakyStoreError(
            "invalid_state_transition",
            "quarantine requires current_state=CONFIRMED",
        )
    repository.require_no_open_governance(connection, request.flaky_key)
    governance_id = f"governance-v1-{uuid.uuid4().hex}"
    repository.insert_governance(
        connection,
        governance_id=governance_id,
        flaky_key=request.flaky_key,
        owner=request.owner,
        reason=request.reason,
        actor=request.actor,
        created_at=now,
        expires_at=request.expires_at,
    )
    transition = manual_transition(
        connection,
        repository,
        state,
        to_state=FlakyState.QUARANTINED,
        reason_code="manual_quarantine",
        actor=request.actor,
        now=now,
    )
    repository.update_state_transition(
        connection,
        request.flaky_key,
        state=FlakyState.QUARANTINED,
        transition_id=transition.transition_id,
        updated_at=now,
    )

治理边界

验证

过期时间、允许来源状态、开放治理唯一性、actor/reason都在写入前检查。

状态变化

QUARANTINED/RECOVERING主要表达current有效状态；manual override还可能重锚后续自动投影，因此不能按字段名猜写入者。

审计所有权

governance、manual transition、override和state更新处于同一事务，可追溯谁在何时为何改变有效状态。

失败边界

治理动作不删除Observation和历史证据；非法转换必须拒绝，而不是强行覆盖。

01 · Question

双状态的关键是转换规则，不是机器/人工二分

detected_state限制在OBSERVING、STABLE、SUSPECTED、CONFIRMED自动状态域，current_state还能进入QUARANTINED与RECOVERING。但人工confirm、mark-not-flaky、取消隔离或恢复完成会同步或重新锚定detected_state；隔离和开始恢复则主要只改变current_state。

边界：课程必须逐动作核对仓储更新列，不能再宣称两列互不覆盖。写操作仅由隔离测试库完成。

03 · Call chain

自动投影先给出候选基线，治理上下文再决定有效状态

Observation历史→自动projection候选→读取现有anchor与治理上下文→按转换规则计算detected/current→仓储提交与Transition审计

CLI人工命令同样经过Store门面、前置状态校验和显式事务；不同命令调用不同更新方法，因此不能用一条

04 · Automatic state

纯规则投影由Observation推导，持久化detected仍可能被人工路径重锚

OBSERVING样本不足。
STABLE窗口呈现一致结果签名。
SUSPECTED出现值得关注的切换，但未满足确认阈值。
CONFIRMEDPASS、FAIL和切换次数满足规则，或由允许的人工裁决重锚到确认基线。

FlakyRuleConfig描述纯自动候选；最终写入记录还会读取已有evaluation anchor和治理生命周期，因此数据库中的detected_state不能简单称为未经人工影响的原始机器事实。

05 · Dual state

detected是自动状态域基线，current是当前有效状态

detected_state

值域不含QUARANTINED/RECOVERING；保存当前评估基线，但confirm、mark-not-flaky、取消隔离和恢复完成等路径可同步或重锚。

current_state

叠加自动投影、人工裁决与治理阶段后的有效状态，可进入QUARANTINED或RECOVERING。

projection_status

CURRENT/STALE标识投影新鲜度，不代表两列由不同主体永久拥有。

Transition

记录from/to、trigger、reason、actor和证据引用，用于解释是哪条规则改变了哪些状态。

06 · Governance

人工动作对两列的影响必须逐项核对

动作current_statedetected_state
confirm_flaky写CONFIRMED同步写CONFIRMED
mark_not_flaky写STABLE并建立评估anchor同步写STABLE
quarantine写QUARANTINED保留自动状态域基线
start_recovery写RECOVERING保留检测基线
cancel_quarantine恢复CONFIRMED同步CONFIRMED
recovery projection完成写STABLE或CONFIRMED同步到同一自动状态域目标

治理记录仍保存owner、reason、expires_at和恢复anchor；状态列更新与治理审计是两组相关但不同的事实。

12 · Design choice

设计选择与适用边界

现方案detected_state限制在自动状态域，current_state表达当前有效状态；自动投影、人工override和治理生命周期按各自转换规则决定同步或分离。
替代方案维护单一state，或严格规定detected永远只由纯自动规则写入、人工永不重锚。
选择理由当前模型既支持QUARANTINED/RECOVERING治理阶段，也允许人工裁决成为后续自动评估anchor；代价是必须阅读动作级更新规则，不能依赖字段名猜测语义。
不适用条件若业务要求不可变的原始机器结论，应新增独立不可变检测事件或计算列，而不是把当前detected_state宣传成该证据。
