DAY 09 · RETRY BY CONTRACT

请求重试策略

重试不是“失败后再跑一次”，而是在业务意图可安全重复、故障具备瞬时性、次数与等待仍在预算内时，显式地再次执行同一请求。

建议 1.5～2.5 小时前置：完成第08天门禁学习方式：沿调用链就地精讲核心：common/retry*.py
完成标志：面对 GET 500、GET 400、POST 有无幂等键、Timeout、SSL 和断言失败，你能先判断是否有重试资格，再解释等待、终止结果和证据。

01 · First principles

先回答“为什么可以再执行”，再讨论“重试几次”

一次失败只说明当前 attempt 没有得到期望结果，不自动证明再次发送是安全、有效或值得的。成熟重试机制首先约束副作用和错误类型，其次才计算等待。

1

区分失败与资格

显式策略、方法资格、故障类别和预算缺一不可。

2

守住幂等边界

解释 GET/HEAD、POST 幂等键与 allow_post 的风险差异。

3

计算真实等待

掌握 fixed/exponential、jitter、Retry-After 和 max_elapsed。

4

解释终止事实

区分最后响应、原异常、attempt 记录和实际等待。

TOC 约束链：瞬时失败 → 习惯性“全都重试” → POST 重复副作用、确定性缺陷被隐藏、执行时间失控 → 用例偶尔通过但证据失真。真正约束不是重试代码不会写，而是没有先建立恢复资格的决策顺序。

先确认调用者交出了什么，不提前展开执行器

本节唯一主线：瞬时GET失败后的显式恢复

先把验收事实分成三层

业务入口

测试只调用一次task.request_transient(request)，因此“重试”不是pytest重跑测试，而是这一次业务调用内部的恢复行为。

最终业务结果

框架运行事实

一个Request Group配置最多2次attempt，并绑定两个Context；观察到的响应顺序是503 → 200。

不要误读

configured_max_attempts == 2是上限；真正发生两次由group.contexts和响应序列共同证明。

03 · Public entry and gates

公共入口先建立逻辑请求，再把恢复决策委托给执行器

上一节只交出了GET、path和RetryPolicy。这里第一次进入公共内核，先展开谁拥有Operation、Request Group与Context工厂，再提炼四道闸门。

3

BaseRequest拥有逻辑请求，并把重试编排委托给执行器

先看公共入口选择Retry分支，再看它如何创建Group和Context工厂。

common/base_request.py::BaseRequest.request · 完整函数 
def request(self, method: str, path: str, **kwargs: Any) -> requests.Response:
    attach_log = kwargs.pop("_attach_log", True)
    retry_policy = kwargs.pop("retry_policy", None)
    inherit_session_headers = bool(kwargs.pop("_inherit_session_headers", True))
    stream = bool(kwargs.get("stream"))
    operation_kind = RuntimeOperationKind.SSE if stream else RuntimeOperationKind.HTTP
    metadata = self._runtime_observer.normalize_metadata(
        kwargs,
        kind=operation_kind,
        default_name="sse_request" if stream else "http_request",
    )
    operation = self._runtime_observer.start_operation(metadata)
    try:
        if retry_policy is not None:
            response = self._send_with_retry(
                method,
                path,
                retry_policy,
                attach_log=attach_log,
                inherit_session_headers=inherit_session_headers,
                **kwargs,
            )
        else:
            context = self._build_request_context(
                method,
                path,
                attach_log=attach_log,
                inherit_session_headers=inherit_session_headers,
                **kwargs,
            )
            response = self._send_single_group(context)
    except BaseException as error:
        operation.finish_error(error)
        raise
    operation.finish_response(response, stream=stream)
    return response

两个函数分别拥有不同生命周期

request()

消费retry_policy，启动顶层Operation，根据策略是否存在选择发送分支，并对最终Response或异常收口。

_send_with_retry()

启动一个逻辑Request Group，把configured_max_attempts记录为策略上限，并在finally中保证Group完成。

context_factory()

每次被执行器调用都会重新运行_build_request_context()，先写入本轮索引并绑定到同一个Group；随后RetryExecutor._prepare_context()最终写入索引、上限和共享retry_records。

依赖反转

执行器不直接认识Session：BaseRequest把self._send作为send_once传入，把Context创建、记录附加和等待事实也作为回调交给执行器。

规划Context不是attempt

first_context只用于取得标准化method、path、protocol和含Session Header的资格参数；它不会发送、不会绑定Group，也不计入attempt数量。

继续下一次 attempt = 显式策略 ∧ 方法有资格 ∧ 故障可恢复 ∧ 次数和等待仍在预算内任意一项不成立，就不能把“再试一次”当成默认动作。
闸门 1

策略显式传入

BaseRequest 默认不重试。RetryPolicy 自身虽有默认字段，请求没有传 retry_policy 仍只执行一次。

闸门 2

方法可安全重复

默认允许 GET/HEAD；POST 需要请求级幂等键，或明确设置 allow_post=True。

闸门 3

故障可能瞬时恢复

默认状态为 429、500、502、503、504；异常为 ConnectionError、Timeout，SSL 被排除。

闸门 4

仍有次数与时间

尚未达到 max_attempts，且下一段等待不会突破 max_elapsed 或外层 deadline。

业务调用一个 operation
→
Request Group聚合 attempts
→
Attempt 1独立 Context
→
分类 + 等待记录并查预算
→
Attempt N新 Context
→
最终事实Response 或原异常
计数语义：max_attempts=3 表示最多三次总尝试，不是首次请求后再重试三次，因此最多只有两段等待。

04 · Policy contract

RetryPolicy 是冻结策略对象，不是全局自动开关

策略位于 common/retry.py，以 frozen Pydantic model 表达，避免同一调用过程被其他代码悄悄改写。

4

RetryPolicy冻结一次调用的恢复合同

策略字段在这里第一次成为决策输入，因此在字段表之前直接展开。

common/retry.py::RetryPolicy
class RetryPolicy(BaseModel):
    model_config = ConfigDict(frozen=True, arbitrary_types_allowed=True)

    max_attempts: int = 3
    retry_statuses: frozenset[int] = DEFAULT_RETRY_STATUSES
    retry_exceptions: tuple[type[BaseException], ...] = (
        requests.ConnectionError,
        requests.Timeout,
    )
    backoff: str = "exponential"
    base_delay: float = 0.5
    max_delay: float = 10.0
    jitter: bool = True
    respect_retry_after: bool = True
    max_elapsed: float | None = 30.0
    allowed_methods: frozenset[str] = DEFAULT_ALLOWED_METHODS
    allow_post: bool = False
    idempotency_header: str = "Idempotency-Key"

承接对象

上一节交来的不是“重试开关”，而是一份随本次GET调用显式传入的策略对象。

职责

策略只声明资格、故障集合、次数和等待边界；它不创建Context、不发送HTTP，也不拥有循环。

处理顺序

  1. 模型校验次数、延迟和Header名称。
  2. frozen=True阻止执行过程中被悄悄修改。
  3. 执行器在每个决策点读取同一份策略。

输入与输出

输入调用方选择的恢复参数。
输出不可变RetryPolicy，交给方法资格、分类、等待和预算判断。

边界

不要混淆：类字段有默认值，不等于所有请求默认重试；没有传retry_policy时仍走单次发送。
字段默认值真实含义
max_attempts3包含首次请求的最大总尝试数，最小为 1。
retry_statuses429, 500, 502, 503, 504400、404 默认不触发恢复。
retry_exceptionsConnectionError, TimeoutSSL、TooManyRedirects 显式禁止。
backoffexponential支持 fixed 与 exponential。
base_delay / max_delay0.5 / 10.0 秒计算基数与单段等待上限。
jitterTrue普通退避在 0 到上限间随机，降低并发惊群。
respect_retry_afterTrue优先读取秒数或 HTTP-date，有效时不施加 jitter。
max_elapsed30.0 秒局部恢复的已耗时加下一段等待预算。
allowed_methodsGET, HEAD默认有方法资格的集合，忽略大小写。
allow_postFalse无幂等键时是否仍显式允许 POST。
idempotency_headerIdempotency-Key识别 POST 资格的 Header 名称。

最小显式用法

from common import RetryPolicy

response = self.request.get(
    "/v1/models",
    retry_policy=RetryPolicy(
        max_attempts=3,
        base_delay=0.5,
        jitter=False,
    ),
)
不要混淆：“RetryPolicy 默认 max_attempts 为 3”与“BaseRequest 默认重试三次”是两件事。没有传策略时，BaseRequest 走单次请求路径。

05 · Idempotency boundary

幂等键赋予 POST 重试资格，但不会凭空创造幂等性

执行器准备进入attempt循环前，先调用方法资格判断。本节在资格规则首次出现时展开该入口。

5

RetryExecutor.execute()先判方法资格，再进入attempt循环

策略存在不等于一定会多次发送；方法闸门在循环之前。

common/retry_executor.py::RetryExecutor.execute · 函数体首个连续选段 
retry_records: list[RetryAttemptRecord] = []

    self._record_context(context_recorder, context)

进入Session之前已经发生四件事

方法资格

is_method_retry_allowed()先看method；GET/HEAD默认允许，POST必须由allow_post或幂等Header取得资格。

无资格路径

即使传了Policy，也只创建attempt 1并调用一次send_once(context)；响应状态不会让它重新进入循环。

次数语义

range(1, max_attempts + 1)证明max_attempts包含首次发送，不是“首次后再重试N次”。

独立Context

循环每轮先调用context_factory(attempt_index)；_prepare_context()再附上当前索引、上限和当时已有的Retry记录。

真实发送

send_once就是上一步传入的BaseRequest._send，因此每次attempt都完整经过Middleware → Session → after/exception Middleware。

1. 规范方法名转为大写
2. 查 allowed_methods默认 GET / HEAD
3. POST 特判allow_post 或幂等 Header
4. 其他方法默认只发一次

推荐：请求级幂等键

每个写操作使用稳定、唯一且可追踪的键，由服务端保证同一键只提交一次。Header 只作用于本次请求，不污染 Session。

response = self.request.post(
    "/v1/idempotent-operation",
    json=payload,
    headers={"Idempotency-Key": operation_key},
    retry_policy=policy,
)

高风险：allow_post=True

这只是客户端“允许再次发送”的声明，不会生成幂等键，也不会阻止重复扣费、创建或写入。

启用前必须证明：接口天然幂等，或服务端另有去重合同，并有测试保护。

安全边界：框架以 Header 名称存在作为资格信号，不验证值是否唯一，也不验证服务端是否真的去重。资格判断不能替代业务合同。

06 · Failure classification

响应、传输异常和确定性缺陷的终止方式不同

方法具有恢复资格后，当前Response或原始异常才进入分类。这里先展开纯判断，再阅读场景表。

6

响应与异常分类只回答“是否可能恢复”

分类函数不拥有次数、等待或最终终止结果。

common/retry.py::should_retry_exception / should_retry_response
def should_retry_exception(error: BaseException, policy: RetryPolicy) -> bool:
    if isinstance(
        error,
        (requests.exceptions.SSLError, requests.exceptions.TooManyRedirects),
    ):
        return False
    return isinstance(error, policy.retry_exceptions)


def should_retry_response(response: requests.Response, policy: RetryPolicy) -> bool:
    return response.status_code in policy.retry_statuses

承接对象

一次真实attempt产生的Response或原始传输异常。

职责

响应分支比较状态集合；异常分支比较异常类型，并显式排除SSL和重定向过多。

处理顺序

  1. 先保留Response与异常的事实类型。
  2. 再判断它是否属于策略允许的恢复候选。
  3. 候选仍要经过次数和预算闸门。

输入与输出

输入当前Response或异常、同一RetryPolicy。
输出布尔候选结果，不修改Response，不包装异常。

字段变化

分类阶段不写Context；只有确定准备下一attempt时，执行器才新增RetryAttemptRecord。

默认可恢复

  • HTTP 429
  • 500 / 502 / 503 / 504
  • ConnectionError
  • Timeout

默认不可恢复

  • HTTP 400 / 404
  • SSLError
  • TooManyRedirects
  • 断言失败和代码错误

终止结果

  • 响应耗尽：最后 Response
  • 异常耗尽：最后原异常
  • 不可恢复响应：立即返回
  • 不可恢复异常：立即抛出
场景是否等待最终事实原因
GET + 400否400 Response不在默认状态集合。
GET + 503，下一次成功是200 Response状态、次数和预算都允许。
GET + 503，attempt 用尽此前可能等待最后 503 Response响应路径不制造新异常。
GET + Timeout，attempt 用尽此前可能等待最后一次 Timeout保留原失败类型与堆栈。
POST 无幂等资格 + 503否第一次 503 Response方法闸门在循环前阻止重试。
断言失败为何不重试：业务断言通常在请求返回之后，不属于传输恢复循环；用重试掩盖断言失败会把确定性缺陷伪装成瞬时波动。

07 · Backoff and budget

等待由来源优先级与预算共同计算

指数模式为 base_delay × 2^(attempt_index - 1)，再受 max_delay 限制。有效 Retry-After 优先，非法值回退到普通退避。

按“分类 → 记录 → 预算 → 等待 → 终点”阅读

故障分类

should_retry_response()只比较状态集合；should_retry_exception()只比较异常类型并排除SSL与重定向过多。它们只说明故障是否可能恢复。

记录候选

只有准备进入下一attempt时才新增RetryAttemptRecord，记录原因和计划等待；最终200本身不会新增一条“重试记录”。

两种时间约束

max_elapsed只在准备等待前检查“当前已耗时 + 下一段等待”，不夹紧单次HTTP timeout，也不能中断正在执行的请求；外层deadline才是共享的绝对截止时间。

本用例路径

attempt 1得到503，命中状态集合，等待为0且预算允许；attempt 2得到200，不再重试，于是200 Response沿Request → Task返回Assertions。

响应终点

状态不匹配、次数耗尽或max_elapsed不足时，返回当前Response；框架不把503自动改造成异常。

异常终点

异常不可恢复、次数耗尽或max_elapsed不足时，用裸raise重抛当前原异常；只有外层deadline不足时改抛RetryDeadlineExceeded并保留异常链。

输入事实计算来源计划等待预算结论
attempt 1，base=0.5，exponential0.5 × 2^00.5秒；启用jitter时为0～0.5秒再检查max_elapsed和外层deadline
attempt 2，base=0.5，exponential0.5 × 2^11秒；再受max_delay截断预算不足则不sleep
有效Retry-After: 3服务端提示优先3秒，无jitter，仍受max_delay截断预算不足仍不能等待
非法Retry-After回退fixed/exponential按本地策略计算不会因Header非法而制造异常

Retry-After 优先

支持非负秒数和 HTTP-date。有效时无 jitter，但仍受 max_delay 截断。

max_elapsed 预判

比较“当前已耗时 + 下一段等待”，越界便不 sleep、不进入下一 attempt。

响应路径越界

返回当前可恢复 Response，例如 503。

异常路径越界

重新抛出当前原异常，不用通用超时覆盖它。

与第10天衔接：max_elapsed 是一次 RetryExecutor 的局部预算；Polling 还有覆盖 HTTP attempt、Retry 等待和 poll sleep 的总 deadline。

08 · Execution lifecycle

每次 attempt 都有新 RequestContext，但共享一个 Request Group

选择路径观察执行器。新 Context 使中间件与 attempt 属性隔离；Group 把同一业务请求的实际尝试聚合起来。

8

_prepare_context()把共享恢复事实挂到当前attempt

Context由BaseRequest创建，attempt元数据的最终写入由RetryExecutor完成。

common/retry_executor.py::RetryExecutor._prepare_context
@staticmethod
def _prepare_context(
    context: RequestContext,
    policy: RetryPolicy,
    attempt_index: int,
    retry_records: list[RetryAttemptRecord],
) -> None:
    context.attributes["attempt_index"] = attempt_index
    context.attributes["max_attempts"] = policy.max_attempts
    context.attributes["retry_records"] = retry_records

承接对象

context_factory(attempt_index)新建并绑定到Group的当前attempt Context。

职责

执行器补齐当前索引、策略上限和共享记录列表，使Middleware和日志能够解释本轮处于哪一次恢复尝试。

处理顺序

  1. BaseRequest创建独立Context并绑定Group。
  2. 执行器写入attempt级恢复元数据。
  3. send_once=self._send执行完整传输链。
  4. 如果真实sleep发生，Group再累计retry_wait_seconds。

输入与输出

输入当前Context、Policy、attempt索引与共享records。
输出原地更新后的attempt扩展事实；不产生Response。

边界

不要混淆：RetryAttemptRecord.wait_seconds是计划等待；只有on_wait=group.add_retry_wait在真实sleep后调用，才证明等待已经发生。

503 → 200

attempt 1创建Context并得到503；记录候选与计划等待，预算允许后真实sleep；attempt 2使用新Context得到200并返回。

Timeout → Timeout

每次异常均保留原类型；最终次数耗尽时裸raise重抛当前Timeout，不制造统一异常。

POST无幂等资格

Policy存在也只创建attempt 1；状态分类不会获得进入循环的机会。

职责边界：每个 attempt 都通过 BaseRequest._send() 执行中间件与 transport。RetryExecutor 只拥有编排，不接管 Context 构建、中间件和 HTTP 传输。

10 · Organized answers

按真实执行顺序整理三条确定结论

答案一：503为什么能够被第二次attempt挽救

Test只调用一次Task
→ Task把示例RetryPolicy交给模块Request
→ BaseRequest消费Policy并建立Operation与Request Group
→ first_context只用于规划，不发送、不计attempt
→ RetryExecutor确认GET有资格
→ attempt 1新Context → _send() → Response 503
→ 分类命中 → 生成RetryAttemptRecord → 预算允许 → 真实等待0秒
→ attempt 2新Context → _send() → Response 200
→ Group.finish() → Operation.finish_response() → Response返回Assertions

答案二：响应和异常为什么有不同终点

响应否决或次数耗尽时返回当前Response；异常否决或次数耗尽时重抛当前原异常。只有外层绝对deadline不足时才抛RetryDeadlineExceeded。

答案三：max_elapsed不是什么

max_elapsed不是硬总截止时间：它只在准备下一段等待前检查“已耗时 + 下一段wait”，不会夹紧单次HTTP timeout，也无法中断正在执行的请求。硬deadline由第10天Polling主循环拥有。

11 · Decision answers

重试决策答案：先判资格，再判故障与预算

场景结论判断链
GET返回500允许成为重试候选策略显式 + GET有资格 + 500命中；仍需次数与预算。
GET返回400不重试方法有资格，但400不在默认状态集合，直接返回Response。
POST返回503，无幂等键不重试方法闸门在循环前否决，只发送一次。
POST返回503，有Idempotency-Key可成为候选Header只证明客户端资格；服务端去重仍需业务合同。
GET抛ConnectTimeout可成为候选属于requests.Timeout；仍需次数与预算。
GET抛SSLError不重试异常分类明确排除SSL。
Response返回后业务断言失败不进入Retry断言位于传输循环之外，属于确定性业务判定。

Design Choice · Boundary

设计选择与适用边界：重试必须显式、可判资格且受预算约束

当前方案

调用方显式传入RetryPolicy；执行前检查方法与幂等资格，循环内按故障类型、attempt和max_elapsed决定是否继续。

替代方案

在Session或适配器层为所有请求默认开启自动重试，只按状态码或异常类型再次发送。

选择理由

显式策略避免隐藏额外副作用；幂等资格保护POST；统一预算让退避等待与真实attempt都能被证据记录和审计。

不适用条件

非幂等操作缺少服务端去重合同、确定性4xx/断言失败，或剩余预算不足时，当前方案必须停止而不是“尽量再试”。

13 · 完整复述

不用回看源码，连续讲清一次503 → 200

测试只调用一次Task。示例Task把显式RetryPolicy交给模块Request，模块Request形成GET、相对path与Runtime元数据。BaseRequest消费Policy、创建Operation，并在_send_with_retry()中建立规划用first_context、一个Request Group和Context工厂。RetryExecutor先判断GET资格，再创建attempt 1的独立Context，由_prepare_context()写入索引、上限与共享记录，随后通过BaseRequest._send()完成Middleware和Session。503只是Response，命中状态集合后生成计划等待记录；max_elapsed和外层deadline均允许时才真实sleep并创建attempt 2的新Context。attempt 2返回200，不再形成下一次恢复候选，于是Group和Operation收口，原Response返回Assertions。若响应预算否决就返回当前Response；若异常预算否决通常重抛原异常；只有外层deadline不足才抛RetryDeadlineExceeded。
