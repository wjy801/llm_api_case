逐函数阅读

输入事实

_build_sources()准备同一run的P0、Semantic与request facts；被测函数只接收run_id和Quality输出目录。

验证

测试要求Operation、Request Group、Request Event三层各有一个可信WORKLOAD成员，且usage来自成员事实而不是报告文本。

状态与产物

成功终点必须同时出现RunMetricsStatus.AGGREGATED、write_status=complete和非空run_metrics Hash。

失败边界

若来源被篡改，测试族中的相邻用例要求在数据库或下游消费前拒绝，而不是计算一个“看起来合理”的数字。

事务与所有权

输入验证

空run_id在任何写入前直接拒绝；目录所有权固定在output_dir/metrics。

状态变化

Manifest从aggregating转到complete或failed，因此消费者不会把半写文件误认成已提交产物。

产物所有权

服务函数拥有run-metrics.json与metrics/manifest.json的同轮提交；Hash只在目标文件写完后生成。

失败边界

聚合异常被转换成FAILED结果；即使失败Manifest自身写入也失败，函数仍不伪造成功状态。

来源加载先验Manifest与Hash，再验关系闭合

load_sources()建立文件信任；validate_source_relationships()建立成员所有权信任，两者缺一不可。

def load_sources(run_id: str, output_dir: Path) -> MetricsSources:
    run_path = output_dir / "run.json"
    p0_manifest_path = output_dir / "merged" / "manifest.json"
    request_metrics_path = output_dir / "merged" / "request-metrics.jsonl"
    semantic_dir = output_dir / "semantic" / "merged"
    semantic_manifest_path = semantic_dir / "manifest.json"

    run = read_model(run_path, RunRecord, "run_record_invalid")
    if run.run_id != run_id:
        raise_source_error(
            "run_id_mismatch", "run.json belongs to a different run", run.run_id
        )

    p0_manifest = read_json_object(p0_manifest_path, "p0_manifest_invalid")
    require_manifest(
        p0_manifest,
        run_id=run_id,
        status="complete",
        versions={
            "manifest_version": P0_MANIFEST_VERSION,
            "schema_version": SCHEMA_VERSION,
        },
        code_prefix="p0",
    )
    p0_integrity_status = str(p0_manifest.get("integrity_status") or "unknown")
    if p0_integrity_status == IntegrityStatus.FAILED.value:
        raise_source_error(
            "p0_integrity_failed", "P0 merged facts failed integrity validation"
        )
    p0_request_hash = validated_source_output_hash(
        request_metrics_path,
        (p0_manifest.get("output_hashes") or {}).get("request-metrics"),
    )
quality/metrics/validation.py::validate_source_relationships · 连续选段
def validate_source_relationships(run_id: str, sources: MetricsSources) -> None:
    events = unique_index(
        sources.requests,
        lambda item: item.request_event_id,
        "request_event_duplicate",
    )
    groups = unique_index(
        sources.groups,
        lambda item: item.request_group_id,
        "request_group_duplicate",
    )
    sessions = unique_index(
        sources.sessions,
        lambda item: item.polling_session_id,
        "polling_session_duplicate",
    )
    operations = unique_index(
        sources.operations,
        lambda item: item.operation_id,
        "operation_duplicate",
    )
    for record in (
        *sources.requests,
        *sources.groups,
        *sources.sessions,
        *sources.operations,
    ):
        if record.run_id != run_id:
            raise_source_error(
                "foreign_run_record", "a source record belongs to another run"
            )

两层验证

文件层

run.json、P0 Manifest、Semantic Manifest和目标文件Hash必须属于同一run并处于可消费状态。

关系层

Event、Group、Polling Session、Operation先按稳定ID建立唯一索引，再拒绝重复ID和外来run记录。

状态变化

验证成功只产生不可变MetricsSources输入；此阶段不写Metrics，也不修改上游Artifact。

失败边界

任何版本、状态、Hash或所有权断裂都抛MetricsSourceError，后续Builder没有降级猜测权限。

Builder只对WORKLOAD成员建分母，Writer拥有最终字节

聚合器先构造三层成员集合，再计算排除、问题与状态；Writer原子写JSON并返回磁盘字节Hash。

quality/metrics/builder.py::build_run_metrics · 连续选段
def build_run_metrics(
    run_id: str,
    sources: MetricsSources,
    *,
    generated_at: datetime,
) -> RunMetricsResult:
    events = {item.request_event_id: item for item in sources.requests}
    event_owner = {
        event_id: group
        for group in sources.groups
        for event_id in group.attempt_event_ids
    }
    workload_operations = tuple(
        sorted(
            (
                item
                for item in sources.operations
                if item.traffic_role is TrafficRole.WORKLOAD
            ),
            key=lambda item: item.operation_id,
        )
    )
    workload_groups = tuple(
        sorted(
            (
                item
                for item in sources.groups
                if item.traffic_role is TrafficRole.WORKLOAD
            ),
            key=lambda item: item.request_group_id,
        )
    )
    workload_events = tuple(
        sorted(
            (
                item
                for item in sources.requests
                if (
                    (owner := event_owner.get(item.request_event_id)) is not None
                    and owner.traffic_role is TrafficRole.WORKLOAD
                )
            ),
            key=lambda item: item.request_event_id,
        )
    )
    exclusions = build_exclusions(sources, event_owner)
    issues, degraded_reasons = build_issues(sources, exclusions)
    status = metrics_status(
        sources.run.status,
        workload_operation_count=len(workload_operations),
        degraded_reasons=degraded_reasons,
    )

分母与提交

成员资格

Operation和Group直接按traffic_role筛选；Event必须先找到所属Group，再继承WORKLOAD资格。

状态变化

排除项和degraded reasons决定aggregated/no_data/degraded，不是由“文件是否存在”决定。

产物所有权

write_json_atomic()拥有最终JSON字节；Hash在落盘后读取，因此Manifest引用的是可复核磁盘事实。

边界

Flaky导入不依赖本Metrics产物；Pipeline Reporting可以消费可信Metrics，但不得回写指标事实。

01 · First principles

指标是对可信成员集合的函数，不是对文件中数字求平均

任何成功率、均值或usage总量都隐含两个前提：来源属于同一run且未被篡改，分母中的成员确实属于该指标。Metrics首先验证前提，再计算数字。

来源可信

版本、run_id、状态、Hash和P0证据链成立。

成员可信

Operation、Group、Event关系闭合且流量角色明确。

表达可信

缺失、未知和不适用保留语义，不偷换为0。

TOC约束：指标系统的约束不是计算公式，而是分母资格。分母不透明，再精确的小数也无法解释。

02 · Service contract

aggregate_run_metrics按提交协议生成两份产物

quality/metrics/service.py是公开服务入口。它验证非空run_id，先写metrics/manifest.json为write_status=aggregating，然后加载来源、构建指标、原子写run-metrics.json，最后提交complete Manifest。

模块职责
sources.py读取run、P0和Semantic产物并建立SourceEvidence
validation.py验证Manifest、Hash、路径、身份和关系
builder.py筛选WORKLOAD成员、构建排除、Issue和总体状态
operation.py等按Operation、Group、Event和Case维度聚合
writer.py写run-metrics与Metrics Manifest及Hash

服务捕获来源或计算异常，写write_status=failed与metrics_status=failed，不会留下看似完整但Hash为空的成功Manifest。

03 · Source trust chain

读取顺序本身就是信任顺序

  1. 读取并验证run.json模型与run_id。
  2. 读取P0 Manifest，要求status=complete、版本匹配且integrity不是failed。
  3. 验证P0 request-metrics.jsonl实际Hash等于Manifest声明。
  4. 读取Semantic Manifest，要求status、Schema、Manifest与merge版本匹配且integrity不是failed。
  5. 验证Semantic声明的P0 Manifest Hash和Request Metrics Hash与当前P0一致。
  6. 逐个验证request-groups、polling-sessions、operations、integrity-issues文件Hash并解析模型。
  7. 将所有路径限制在Quality输出根目录内，防止Manifest把读取指向外部文件。

通过后构造SourceEvidence，把每个输入的相对路径、SHA-256和版本写入最终指标，使消费方能够反查来源。

04 · Relationship validation

Metrics在计算前再次验证关系和成员资格

Semantic Manifest complete不意味着Metrics盲目信任内存对象。validate_source_relationships()重新建立唯一索引，并验证：

  • 所有记录run_id与请求run一致，身份不重复。
  • Group引用的Operation、Session和P0 Event存在且作用域一致。
  • Session引用的Group存在，反向关系闭合。
  • Operation引用的Group、Session和evidence属于自身。
  • usage source与missing事件属于Operation，且集合不重叠。
  • 每个P0 Event最多有一个语义Group所有者。

任一硬关系错误抛出带code和related_id的MetricsSourceError，整轮Metrics状态为failed，而不是跳过坏成员继续算。

05 · Workload denominator

CONTROL排除，UNKNOWN保留为降级证据

traffic_role是否进入WORKLOAD指标如何表达
workload进入参与Operation、Group和Event分母
control不进入ID写入exclusions，防止余额、usage或管理查询污染分母
unknown不进入写入exclusions并产生unknown_traffic_role降级原因

Builder先由Group建立event owner，再筛选WORKLOAD Operation、Group和Event。没有Group所有者的P0 Event进入unassigned_event_ids并导致降级，而不是自动归到某个接口。

06 · Three aggregation layers

Operation、Request Group和Request Event不能互相替代

层典型指标分母单位
Operation业务操作成功率、超时率、总耗时、usage、按kind/name/model分桶一次业务意图
Request GroupRetry率、首尾传输/HTTP/业务成功率、Retry rescue、等待与attempt耗时一次逻辑请求
Request Event超时、HTTP 5xx、429、业务成功、状态分布和单attempt耗时一次真实HTTP attempt
Case Invocation该用例关联的Operation数量、终态、usage和模型集合一次pytest invocation

例如Retry后成功：Operation可以成功；Request Group显示first失败、final成功和rescue；Request Event层仍保留失败attempt。三个结论同时成立。

07 · Missing and denominator

0、缺失、未知和不适用是四种不同语义

NumericAggregate

同时保存eligible_count、sample_size、missing_count、total、mean、min、max与completeness。均值分母是有值样本，不是eligible总数。

RatioAggregate

保存numerator、sample_size、unknown_count、value与completeness。未知成员不进入比例分母，但必须显式计数。

语义示例指标表达
真实0媒体数量明确为0进入sample与total
missing响应未提供token usage增加missing_count，不当作0
unknown业务状态无法判定增加unknown_count，不进入成功率分母
not_applicable该Operation没有usage语义记录排除身份，不算缺失

这套表达让使用者能够同时看到数值和覆盖率，避免“平均值正常”掩盖大量缺失样本。

08 · Status and manifest

四种Metrics状态表达可信度与数据可用性

状态条件
aggregatedrun完成、无降级原因且至少一个WORKLOAD Operation
no_data来源可信且无降级，但没有WORKLOAD Operation
degradedrun未完成，或P0/Semantic降级，或存在不完整Operation、usage缺失、未归属Event、未知流量角色
failed来源缺失、版本/Hash/关系验证失败，或聚合异常

metrics/manifest.json区分write_status和metrics_status：前者说明产物提交过程，后者说明指标语义状态。complete写入可以承载aggregated、no_data或degraded；failed写入没有有效输出Hash。

11 · Design choice

设计选择与适用边界

现方案先验证P0与Semantic的run、版本、状态、Hash和成员关系，再按Operation、Request Group、Request Event三个分母计算精确指标。
替代方案直接扫描结果文件或报告表格，对所有可见耗时做平均并把缺失值填成0。
选择理由指标只对可信成员集合有意义；分层分母与显式缺失语义避免控制请求、未知成员和无数据状态污染结论。
不适用条件实时监控的近似窗口、跨run趋势仓库或高基数在线查询需要流式指标与专用存储，本方案面向单run可审计聚合。
