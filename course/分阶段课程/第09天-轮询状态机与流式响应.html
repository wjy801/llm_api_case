DAY 09 · BOUNDED ASYNC OBSERVATION

轮询状态机与流式响应

异步任务的可靠性不在于“多查几次”，而在于用明确状态机解释每个响应，让 HTTP attempt、Retry 等待和 poll sleep 共同服从一个不可突破的总 deadline；SSE 则用一条受控长响应持续交付事件。

建议 1.5～2.5 小时前置：完成第08天门禁只运行离线测试核心：polling.py / streaming.py
完成标志：能为 success、failure、unknown 画出迁移；能说明 timeout 为什么不是第五种状态；能证明预算耗尽后不会再发请求，并正确关闭 SSE Response。

01 · First principles

真正的问题是“有限时间内如何可靠观察”，不是循环语法

Polling 与 SSE 都处理“结果不会一次完整返回”的场景。Polling 获取多个离散响应；SSE 消费一个持续响应。两者共同约束是：必须知道何时完成、何时失败、何时停止以及谁负责释放资源。

1

区分状态与结果

掌握 pending、success、failure、unknown，并把 timeout 放在 deadline 终止层。

2

守住唯一预算

理解 transport timeout、Retry wait、poll sleep 都消费同一 poll_timeout。

3

读懂嵌套尝试

区分外层 PollingTransition 与内层 HTTP Retry attempt。

4

管理流式生命周期

解释为何禁用响应体日志、如何识别 [DONE]，以及为何必须 finally close。

TOC 因果链：把每次 GET、Retry 和 sleep 各自设置超时 → 三套局部时间都“合理”但总和失控 → deadline 后仍发请求或接受迟到成功 → 用例拖长且最终事实错误。解除约束的方法是先建立一个绝对 deadline，再让所有内部动作只消费剩余预算。

02 · Two axes

响应状态描述“看到了什么”，终止结果描述“为什么结束”

状态机轴：PollingState

每个被成功解析并评估的响应，只会映射到四种状态之一。

pendingsuccessfailureunknown

生命周期轴：Polling outcome

一次 Polling 会话可以因状态、预算或外部中断而结束。

successfailureunknowntimeoutinterrupted
timeout ≠ PollingState它表示“deadline 已耗尽”，可以发生在已经观测到若干 pending 之后，甚至发生在迟到的 succeeded 响应被观测之后。
关键合同：响应先被解析并记入 transitions，随后检查剩余预算；若此时 remaining ≤ 0，立即抛 PollingTimeoutError。即使 raw status 是 succeeded，也不能把越过 deadline 的结果改写为成功。

03 · Policy contract

PollingPolicy 把业务状态翻译成稳定框架状态

直接调用 poll_get() 必须显式传入冻结的 PollingPolicy。媒体 Task 已通过公共能力提供 DEFAULT_MEDIA_POLLING_POLICY，业务用例不要再复制轮询循环。

字段默认值含义
status_json_path$.status提取原始业务状态；路径必须以 $ 开头。
pendingqueued, running继续等待并进入下一轮。
successsucceeded返回最终 Response。
failurefailed, cancelled抛 PollingFailedError。
result_json_pathNone提取值不为 None 时直接判成功，优先于 status 集合。
error_json_path$.error提取值不为 None 时优先判失败，优先级最高。
unknownfailfail 产生 UNKNOWN；pending 与 ignore 当前都映射为 PENDING。

直接调用的标准写法

from common import PollingPolicy

policy = PollingPolicy(
    status_json_path="$.status",
    pending={"queued", "running"},
    success={"succeeded"},
    failure={"failed", "cancelled"},
)

response = self.request.poll_get(
    f"/v1/tasks/{task_id}",
    poll_interval=2,
    poll_timeout=900,
    polling_policy=policy,
)
输入门禁：poll_interval 和最终 timeout 必须大于 0；旧的 success_json_path/failure_json_path 参数不再是入口。状态字段、结果字段和错误字段都由 Policy 统一描述。

04 · Evaluation priority

先看 error，再看 result，最后才查 status 集合

1. 解析 JSON非法 JSON 抛脱敏 AssertionError
→
2. error_json_path值非 None：FAILURE
→
3. result_json_path值非 None：SUCCESS
→
4. status setspending / success / failure
→
5. unknown ruleUNKNOWN 或 PENDING
为什么 error 优先：若响应同时出现 status="succeeded" 与值不为 None 的 error，不能因状态文字好看就忽略明确错误。相反，值不为 None 的 result 可以把仍为 running 的响应提升为 success，但前提是没有 error。

分类实验

按默认路径与题目给定 unknown 规则，选择评估结果。

status=succeeded，result 有值，error 有值：错误字段优先。
status=running，result.urls 有值，无 error：结果字段优先于状态集合。
status=queued，无 result/error：命中 pending 集合。
status=paused，unknown=fail：默认拒绝未知状态。
status=paused，unknown=pending：继续观察但保留 raw_status。

05 · State transition player

三条状态路径 + 一条 deadline 终止路径

PENDING

继续观察

记录 transition，sleep 不超过 remaining，然后尝试下一轮。

SUCCESS

正常返回

附加完整 transitions 与最终响应，结束 Polling。

FAILURE

业务失败

抛 PollingFailedError，保留 error_value、最后响应与迁移。

UNKNOWN

协议漂移

默认抛 PollingUnknownStateError，避免把新状态无限当作等待。

画图规则：success、failure、unknown 都能画成 PollingState 迁移；timeout 应画成“已观测状态序列 → deadline 边界 → PollingTimeoutError”，不能伪造一个 PollingState.TIMEOUT。

06 · One budget

总 deadline 是唯一账本，内部动作只能花剩余额度

deadline = started_at + poll_timeout；remaining = deadline - monotonic_now任何 transport、Retry wait 或 poll sleep 都不能拥有独立于 remaining 的额外时间。

请求前

若 remaining ≤ 0，RetryExecutor/timeout clamp 在 transport 前终止，不发送网络请求。

请求中

单次 timeout 被截断为配置值与 remaining 的较小值；tuple timeout 的每一项同样截断。

响应后

先记录评估结果，再检查 remaining；迟到的 success 仍是 timeout。

等待前

Retry wait 必须严格小于 remaining；poll sleep 使用 min(interval, remaining)。

停止证明：timeout 用例在抛错后连续读取两次服务计数，第二次必须与第一次相等。这证明 deadline 终止后没有后台轮询继续发送请求。

07 · Nested attempts

Polling 的一次观察，内部可以包含多个 HTTP Retry attempts

外层 Polling attempt

目标是得到一个可评估的业务状态响应。每个评估结果生成一个 PollingTransition。

  • 编号：PollingTransition.attempt_index
  • 等待：poll_interval
  • 结果：PollingState
包含
→

内层 Request Group / Retry

目标是从瞬时 HTTP 故障中恢复。一个外层观察可能实际发送多次 HTTP。

  • 编号：RequestContext attempt_index
  • 等待：Retry backoff / Retry-After
  • 结果：最终 Response 或异常
离线成功场景：服务端实际返回 503、queued、running、succeeded，共 4 个 HTTP 响应；503 在首个 Request Group 内被 Retry 挽救，因此 PollingSession 只观测到 pending、pending、success 三个状态。HTTP attempt 数不等于 Polling transition 数。
预算协作：内层 RetryExecutor 接收同一个 absolute deadline。候选 backoff 若不落在剩余时间内，会抛 RetryDeadlineExceeded，由外层转换成 PollingTimeoutError；不会先睡完再发现超时。

08 · Evidence

迁移序列既是诊断证据，也是异常上下文

PollingTransition

保存外层 attempt_index、相对耗时、PollingState、raw_status 和 HTTP 状态码。

用于重建状态轨迹。

PollingFailedError

保存 path、last_status、last_response、transitions 与 error_value。

用于解释业务终态失败。

PollingUnknownStateError

保存未知 raw_status 与完整迁移，暴露服务端协议漂移。

默认不静默等待。

PollingTimeoutError

保存 timeout、最后状态/响应和迁移；响应文本统一脱敏并截断。

用于证明预算终止位置。
日志边界：中间 poll 响应不逐个作为最终附件挂载；结束时在最后 logger 上挂完整 transitions 与最终响应。观察/附件失败仍不应改写业务状态机事实。

09 · Streaming lifecycle

SSE 是一条长响应：Header 成功不代表流已经完成

POST stream=True只获取响应头与流句柄
→
绑定 Stream leaseoperation 暂不完成
→
iter_sse_lines逐行 UTF-8 解码与观察
→
[DONE] / 中断 / 错误确定 stream outcome
→
finally close释放连接资源

为何 _attach_log=False

普通响应日志可能读取 response.text/content。对流式响应这样做会提前消费 body，导致业务消费者读不到 chunk。

iter_sse_lines 做什么

跳过空行；bytes 用 UTF-8 replacement 解码；逐行发中性观察事件；识别 data: [DONE]。

它不做什么

不替业务解析 JSON、不验证每个 chunk 契约，也不自动关闭 Response。Task/用例仍是资源所有者。

为何必须 finally close

正常完成、非法 chunk、提前断流、主动中断都必须释放底层连接，不能遗留到 teardown 后。

Request：不要提前读 body

return self.post(
    "/v1/chat/completions",
    json=payload,
    stream=True,
    headers={"Accept": "text/event-stream"},
    _attach_log=False,
    runtime_metadata=runtime_metadata(
        RuntimeOperationKind.SSE,
        name="chat_completion_stream",
        role=RuntimeTrafficRole.WORKLOAD,
    ),
)

Task：消费与关闭同一所有者

try:
    for line in iter_sse_lines(response):
        assert line.startswith("data:")
        if line == "data: [DONE]":
            break
finally:
    response.close()
消费事实Stream outcome要求
观测到 data: [DONE]complete业务仍需完成断言并关闭 Response。
流自然耗尽但没有 [DONE]interrupted业务应明确断言缺失终止标记。
消费者提前 close iteratorinterrupted保留主动中断事实。
读取中抛 ChunkedEncodingError 等error原异常继续抛出，Response finally 关闭。
成功响应从未消费not_consumed运行收口时记录完整性问题。
非 2xx 流式响应error / failed在响应头阶段完成失败，不消费 body。

11 · Knowledge check

知识自测

答对 5 题视为达标。重点判断事实层级和预算归属。

1. timeout 在当前 Polling 模型中是什么？
答案 C。状态只有 pending/success/failure/unknown。
2. 响应同时有非空 error、非空 result 和 status=succeeded，判定为何？
答案 A。error_json_path 的优先级最高。
3. succeeded 响应返回时已经超过 deadline，应如何处理？
答案 B。deadline 事实优先，不能事后扩展合同。
4. Retry backoff 为2秒，但 Polling 只剩1秒，会发生什么？
答案 C。Retry wait 必须严格落在同一 deadline 内。
5. 流式 Request 为什么使用 _attach_log=False？
答案 A。状态、Header、终态仍可记录，body 由业务消费者逐行读取。
6. iter_sse_lines 自然耗尽但未看到 [DONE]，且调用方应做什么？
答案 B。SSE 与 Polling 是不同控制流，但都必须保留真实终止事实。

12 · Exit gate

本课门禁：能证明停止，才进入上下文与并发

一句话验收：Polling 用状态机解释离散观察，用一个绝对 deadline 约束所有内部时间；SSE 用一个显式所有者消费并关闭长响应。两者都不能用“最终看起来成功”覆盖真实终止边界。
