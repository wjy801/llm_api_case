WEEK 4 · DAY 20

综合实践与结业评审

结业项目只做一个小而完整的离线扩展：范围可控、职责归位、结果确定、资源可回收，并能用collect、Runner、JUnit、Allure、Quality与Pipeline Summary组成证据闭环。

Small complete changeDeterministic offlineCorrect classificationEvidence chainArchitecture gate
最终交付：不是“写了多少代码”，而是能证明扩展没有复制核心实现、没有污染黄金路径、没有越过依赖边界，并在离线门禁中稳定通过。

01 · Graduation contract

结业合同：一个扩展，七份成果，六组门禁

第一性原理：框架能力的价值来自可重复验证，而不是代码存在。结业项目必须同时证明需求、设计、实现、执行和证据都闭环。

1

范围小

只选择一个独立场景或一个缺失边界，不把结业项目变成框架重写。

2

链路完整

从测试数据、Task、Request、本地服务、断言到Runner和报告都能解释。

3

证据可审计

每个结论都有命令输出或机器产物，不用“我认为应该通过”代替验证。

TOC约束：范围过大 → 修改所有权扩散 → 分类与黄金路径混乱 → 门禁失败难以定位 → 结业证据无法闭环。最优策略不是增加功能，而是缩小到一个能完整证明的变化。

必须提交的七项成果

① 完整调用链图标出同步主链和Quality旁路。
② 修改位置与原因每个文件都能对应一个单一职责。
③ 对应分类用例互斥边界不塞入黄金路径。
④ collect与分池说明证明nodeid唯一及并串行理由。
⑤ 离线执行结果本地服务、Runner与回归有真实结果。
⑥ 多层证据解释区分JUnit、Allure、Quality和Summary。
⑦ 安全与架构自检脱敏、关闭、依赖方向和无重复实现。
明确禁止：不得新增第二套Request、Retry、Polling、Runner或Quality实现；不得为了展示“综合”而把失败、未知、超时等互斥场景全部塞进黄金路径。

先选最小可验证问题，再决定写代码

03 · Full call chain

调用链图必须同时画主链、生命周期和观察旁路

pytest case / fixture → Test Data（Python类型、稳定参数ID） → OfflineFrameworkTask（payload、策略、业务动作） → OfflineFrameworkRequest（相对路径、runtime_metadata） → common Request / Middleware / Retry / Polling → 127.0.0.1 随机端口的OfflineService → Response → Assertions / Schema / Capture / TestContext cleanup → pytest exit + Runner execution-result.json 中性旁路：common.runtime_hooks → Quality Case / Request facts（仅开启时） → Semantic / Metrics / Flaky → PipelineReport → Markdown / JSON / Email
链路必须说明禁止做法
业务主链谁构造数据、谁发请求、谁解析业务状态、谁断言。测试直接拼装重复的底层HTTP与重试实现。
资源生命周期服务、Session、Response、线程、临时目录和cleanup何时关闭。依赖进程退出回收资源。
运行编排collect如何形成计划、并串行如何互斥、每个nodeid执行几次。用控制台文本代替权威计划。
观察旁路Runtime Hooks保持中性，Quality关闭时不创建身份和产物。业务分类用例直接导入Quality、Metrics或Flaky内部实现。
报告下钻Summary如何回到JUnit、Allure和Quality机器证据。新增第二份人工汇总报告。
图的验收方式：随机指向任意箭头，都能回答“输入是什么、所有者是谁、失败如何传播、资源由谁收尾、证据写到哪里”。答不出的位置就是设计债务。

04 · Classification routing

用例文件回答“哪一项职责失效”，黄金路径只回答“组合能否成立”

要验证的能力首选归属原因
本地服务协议、实例隔离、线程回收tests/test_offline_service.py先证明测试替身本身可信。
Request、Middleware、Header和payload不变性test_request_pipeline.py定位请求管线单一职责。
重试资格、Retry-After、幂等POSTtest_retry.py互斥重试规则不污染其他分类。
轮询成功、失败、未知和deadlinetest_polling.py状态机边界集中可读。
提取、转换、LIFO cleanup和多错误test_context_cleanup.py上下文与资源收尾有独立失败语义。
Capture、Schema、脱敏诊断test_capture_assertions.py输出和断言边界集中。
ContextVar、Session和Header并发隔离test_concurrency_context.py专门验证并发所有权。
稳定成功主链组合test_full_framework_flow.py黄金路径只保留唯一稳定成功链。

05 · Deterministic scenario

离线场景必须冻结输入、序列、时间和资源

当前OfflineService使用Python标准库在127.0.0.1随机端口启动，九个冻结场景覆盖Echo、429/503、幂等POST、Polling和超限下载；状态按服务实例隔离。

场景合同

  • 请求输入固定，ID与参数名稳定；
  • HTTP和业务状态序列明确；
  • 调用次数与重试次数可断言；
  • 等待由记录器或小而有界的deadline控制；
  • 输出bytes、Hash和Schema固定。

资源合同

  • 只绑定IPv4 loopback随机端口；
  • 服务状态不跨实例共享；
  • 并发计数使用锁保护；
  • Session、Response、线程和服务显式关闭；
  • fixture teardown即使断言失败也执行。

场景设计模板

场景名称：稳定、唯一、可读
初始状态：计数器 / task状态 / 固定资源
输入：相对路径 + Python payload + 请求级Header
响应序列：HTTP状态 + 业务状态 + 固定body
预期：调用次数、状态迁移、Capture、Runtime事件
时间：无随机sleep；明确retry wait或poll deadline
收尾：Response / Session / Thread / Service / TempDir
失败证据：断言消息脱敏且能定位字段路径
反模式为什么不确定正确替代
依赖公网服务或真实账号网络、余额、数据和服务版本不可控。本地确定性服务模拟最小协议。
用随机sleep等待状态机器负载变化导致偶发超时。固定序列、记录等待或总deadline。
模块级可变计数器用例顺序和并发会互相污染。状态归属于每个OfflineService实例。
失败时跳过close后续测试继承连接和线程。fixture yield、finally或cleanup栈。

06 · Ownership and dependencies

修改最少文件，但每个职责必须有唯一所有者

变更类型典型修改位置边界
新增服务场景offline_service.py + 对应服务/分类测试不复制HTTP Server、状态仓库或fixture生命周期。
新增分类边界一个既有test_*.py，必要时复用Task/Assertion不要为了单条测试扩张公共Base类。
新增模块骨架__init__.py/request.py/assertions.py/decorators.py/task.py/test_*.py四件套是真实类，复用公共实现与离线服务。
新增通用断言或Schema现有公共断言/Schema所有者先证明是跨场景稳定合同，不把业务特例上移。

依赖方向

业务模块依赖common公共API；不得导入Quality或Runner内部实现。手动观察使用中性Runtime Hooks。

安全与脱敏

相对路径、无真实Key、无完整域名；Header、URL查询、body和诊断遵守脱敏策略。

资源所有权

谁创建Request、Session、Response、线程或临时目录，谁必须明确关闭或注册cleanup。

架构红线：第二套pytest生命周期、第二套Runner、第二套重试器、业务用例直接写Quality事实、简单别名伪装四件套类、或新增并行人工报告，任一项出现都应退回设计阶段。

修改说明模板

文件：workspace-relative/path.py
职责：该文件唯一拥有的行为
原因：为什么现有公共API不足以仅通过测试表达
复用：使用了哪些已有Request / Task capability / fixture
不修改：明确哪些核心所有者保持不变
验证：由哪条分类测试与哪组门禁保护

07 · Collection and pools

先证明收集计划正确，再允许Runner真正执行

all collected nodeids = parallel pool ∪ serial pool parallel pool ∩ serial pool = ∅ 每个nodeid最多执行一次 expected_case_count = 最终权威计划数量
场景属性池选择理由
实例隔离、本地服务、独立Sessionparallel无共享可变业务状态，优先并发。
账单、余额、共享账号、延迟结算serial存在跨用例共享状态或顺序约束。
专门验证线程并发隔离parallel测试内部并发不代表Runner外层必须串行，前提是实例独立。
无法说明资源所有权阻断不能用serial掩盖未知竞争，应先修设计。

08 · Evidence stack

不同证据回答不同问题，不能互相替代

Source + 分类测试
collect / execution-result
JUnit + Allure
Quality + Pipeline Summary
证据回答的问题不能证明
调用链图与修改说明设计是否符合所有权与依赖方向。代码真实可收集、可执行。
collect-onlynodeid、导入、分类、并串行计划是否正确。请求和断言实际通过。
Runner execution-result最终计划、池级原始退出码和执行次数。具体断言为何失败。
JUnit总数、通过、失败、错误、跳过与失败详情。业务步骤、请求附件和完整质量语义。
Allure用例步骤、请求、响应、附件和人工排查上下文。权威pytest退出码和跨run历史。
Quality / Semantic / Metrics / FlakyCase、Request、Operation、完整性、指标和稳定性诊断。改写用例通过或Jenkins结果。
Pipeline Summary本轮参数、阶段、直接观测结论和下钻入口。替代机器事实或建立第二套结果。

证据下钻顺序

Pipeline Summary→JUnit统计→Allure具体用例→Quality Manifest与JSONL→Runner原始退出事实
不要反向推导：Pipeline Summary显示PASS，不代表所有Request都成功；JUnit用例通过，不代表负向用例中的业务请求成功；Metrics缺失也不能被写成0。

结业证据清单

设计证据调用链、范围、修改理由、依赖方向。
收集证据总数、parallel/serial、黄金nodeid次数。
执行证据离线服务、Runner、Quality和完整回归结果。
诊断证据JUnit、Allure、Quality与Summary职责说明。

结业评审先看硬门禁，再看100分质量量表

15安全与可维护性
维度满分标准常见扣分
架构边界复用现有Request/Retry/Polling/Runner/Quality，依赖方向正确。重复实现、业务反向依赖内部模块。
分类准确边界归入正确分类，黄金路径只含稳定成功链。所有场景堆入一个文件或黄金路径。
确定性与资源固定输入与序列、实例隔离、无随机等待、资源全关闭。共享计数、睡眠竞态、线程或Session泄漏。
验证与证据六组命令通过，能从Summary下钻到机器事实。只运行单条用例，未做collect或完整回归。
安全与可维护性无真实Key/域名，诊断脱敏，nodeid稳定，修改说明清楚。硬编码敏感信息、参数ID漂移、无变更理由。
硬门禁优先：出现第二套核心实现、未经授权的真实调用、敏感信息、资源泄漏、collect失败、完整回归失败或架构反向依赖时，不计算总分，结论直接为未通过。

10 · Default acceptance

六组默认验收命令：从最小协议到完整回归

按失败定位成本从低到高执行。任何一步失败都先修复根因，不要跳到后续命令用更多输出掩盖第一个约束。

环境准备：离线模块只访问loopback，但导入配置仍要求语法合法的环境文件。若本地没有.env，先从.env.example复制；不要填入或提交真实密钥。
if (-not (Test-Path -LiteralPath '.env')) {
  Copy-Item -LiteralPath '.env.example' -Destination '.env'
}

1. 确定性服务协议与资源回收

.\.venv\Scripts\python.exe -m pytest tests/test_offline_service.py -q

2. 离线分类收集与分池

.\.venv\Scripts\python.exe run_master.py `
  module/offline_framework_example `
  --collect-only -q

3. Runner并发执行离线分类

.\.venv\Scripts\python.exe run_master.py `
  module/offline_framework_example -n 2

4. Quality专项回归

.\.venv\Scripts\python.exe -m pytest tests/quality -q

5. 完整框架回归

.\.venv\Scripts\python.exe -m pytest tests -q

6. 真实Smoke只收集不执行

.\.venv\Scripts\python.exe run_master.py module/smoke --collect-only -q
不可越界：module/smoke --collect-only只能验证收集和分池。除非明确获得真实环境、账号、费用和风险授权，否则不得去掉--collect-only。
命令通过时证明失败时优先检查
offline service本地协议、实例隔离和线程回收可信。场景合同、端口、锁、shutdown。
offline collect导入、nodeid、分类和分池正确。pytest收集规则、marker、初始化副作用。
offline run四件套与公共核心在真实Runner链上成立。Request所有权、断言、资源和池退出码。
quality tests观察、归并、Metrics、Flaky和Reporting边界未回退。来源合同、依赖方向、版本与Hash。
tests扩展没有破坏完整框架合同。第一个失败，而不是最后一个摘要。
smoke collect真实业务模块仍可收集且分池。导入、marker和环境配置；绝不真实执行。
基线解释：2026-08-06快照为离线23项并发/0串行、完整tests 686项、Smoke collect 40项（15并发/25串行）。结业扩展可能合理改变数量，评审关注集合守恒、职责边界和文档同步。
