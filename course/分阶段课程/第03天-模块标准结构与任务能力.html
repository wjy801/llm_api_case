Week 1 · Day 3

模块标准结构与任务能力

第2课让你看懂一个模块内的职责交接；今天再向前一步：把这些职责组织成稳定骨架，并学会判断一个新能力应该留在模块Task、复用BaseTask，还是进入窄能力对象。

建议用时 120～150分钟 难度：进阶入门 实践：纯设计、零真实接口 前置：掌握模块四件套
本课结果：你将完成一个虚构example_model的模块蓝图，并能用一套稳定决策解释路径、payload、Schema、公共能力与报告字段各自应该落在哪里。

从一个组合动作看清BaseTask为什么不自己实现全部业务

2

BaseTask门面保留稳定调用名

门面不重复流程，而是把模块可覆盖的方法注入Capability。

common/base_task.py::BaseTask.create_and_poll_media_generation
def create_and_poll_media_generation(
        self,
        request_client: BaseRequest,
        payload: dict[str, Any],
        *,
        poll_interval: float = 2,
        poll_timeout: float | None = None,
        polling_policy: PollingPolicy = DEFAULT_MEDIA_POLLING_POLICY,
        retry_policy: RetryPolicy | None = None,
    ) -> requests.Response:
        return self._media_capability().create_and_poll_media_generation(
            request_client,
            payload,
            poll_interval=poll_interval,
            poll_timeout=poll_timeout,
            polling_policy=polling_policy,
            retry_policy=retry_policy,
            create=self.create_media_generation,
            extract_task_id=self.extract_task_id,
            poll=self.poll_media_generation_result,
        )

门面做了两件事

稳定入口

调用方继续使用BaseTask.create_and_poll_media_generation()，不需要知道Capability文件位置。

参数透传

轮询间隔、总超时和两类策略完整交给能力对象。

保留扩展点

注入self.create_media_generation等绑定方法，使子类覆盖仍能生效。

3

_media_capability()把模块配置变成能力对象

路径和任务ID字段由门面类提供，流程实现由Capability持有。

配置与行为在这里连接

来自门面

不同module可通过类属性提供自己的路径模板和任务ID字段。

Capability获得执行流程所需配置，但不依赖具体模块类。

4

Capability拥有真正的组合流程

它选择可注入调用点，并在一个异步任务Operation中完成三段业务。

common/task_capabilities/media_generation.py::MediaGenerationCapability.create_and_poll_media_generation
def create_and_poll_media_generation(
        self,
        request_client: BaseRequest,
        payload: dict[str, Any],
        *,
        poll_interval: float = 2,
        poll_timeout: float | None = None,
        polling_policy: PollingPolicy = DEFAULT_MEDIA_POLLING_POLICY,
        retry_policy: RetryPolicy | None = None,
        create: Callable[[BaseRequest, dict[str, Any]], requests.Response] | None = None,
        extract_task_id: Callable[[requests.Response], str] | None = None,
        poll: Callable[..., requests.Response] | None = None,
    ) -> requests.Response:
        create_call = create or self.create_media_generation
        extract_call = extract_task_id or self.extract_task_id
        poll_call = poll or self.poll_media_generation_result
        with operation_scope(
            RuntimeOperationKind.ASYNC_TASK,
            name="media_generation",
            role=RuntimeTrafficRole.WORKLOAD,
            model_id=model_id_from_kwargs({"json": payload}),
        ):
            create_response = create_call(request_client, payload)
            task_id = extract_call(create_response)
            return poll_call(
                request_client,
                task_id,
                poll_interval=poll_interval,
                poll_timeout=poll_timeout,
                polling_policy=polling_policy,
                retry_policy=retry_policy,
            )

组合流程只有三个业务节点

选择调用点

有注入函数就使用注入函数，否则回退到Capability默认实现。

状态流

创建Response被转换成task_id，再成为轮询输入。

结果

函数直接返回最终轮询Response；中间创建Response不作为最终返回值。

概念从代码中长出来

后面的“稳定身份、Task门面、能力对象和复用决策”是对这条链的复盘：门面保护调用方，Capability集中可复用流程，注入的绑定方法保留模块差异。

02 · 六文件模块骨架

最小结构不是六个空文件，而是六个稳定责任位

点击文件查看允许职责与禁止事项。第一次设计模块时，先填满责任位，再决定是否添加可选文件。

module/example_model/

最小必需：始终创建

  • __init__.py
  • Request / Assertions / Decorators / Task四件套
  • 至少一个test_*.py业务入口

按需增加：有拆分理由才创建

  • 稳定响应结构较多：response_schemas.py
  • payload多到Task职责变模糊：payloads.py
  • 模块专用fixture：conftest.py
  • 复用Python数据：test_data.py
避免机械分层单个常量不值得新建文件；JSON、YAML、Excel也不是默认用例入口。拆分只有在降低变化耦合时才有价值。

03 · 真实类与稳定导出

模块合同由“真实类型 + 公开入口”共同组成

第2课解释了空子类的价值；今天把它放进完整模块合同：调用方从模块包导入，不依赖内部文件布局。

公共基类BaseRequest / BaseTask等
→
模块真实子类ExampleModelRequest / Task等
→
模块公开入口__init__.py + __all__
类型身份__name__和__module__明确表达所属模块。
继承关系MRO保留公共能力来源，也允许模块以后覆写。
稳定导入测试从module.example_model导入，不绑定内部文件路径。
演进隔离内部文件可重构，只要公开类合同保持稳定，调用方无需迁移。

推荐公开入口

from module.example_model.assertions import ExampleModelAssertions
from module.example_model.decorators import ExampleModelDecorators
from module.example_model.request import ExampleModelRequest
from module.example_model.task import ExampleModelTask

__all__ = [
    "ExampleModelAssertions",
    "ExampleModelDecorators",
    "ExampleModelRequest",
    "ExampleModelTask",
]
使用简单别名
失去模块身份
导入绑定公共实现
模块扩展需换类型
调用方批量迁移
禁止替代ExampleModelTask = BaseTask复用了行为，却破坏了类型与演进边界。正确做法是定义真实子类，即使初始类体只有pass。

04 · Task门面与能力对象

BaseTask保留入口，task_capabilities承载真实领域实现

这是一个“兼容门面 + 窄能力对象”结构。点击能力查看入口、委托对象与当前边界。

模块Task

保存模块差异、payload builder与独有业务动作；继承稳定公共入口。

继承 / 调用 →

BaseTask兼容门面

保留现有方法、Allure业务步骤与动态覆写入口，把工作委托给窄能力对象。

委托 →

task_capabilities

MediaGenerationCapability与BillingCapability分别实现媒体、账单能力。

为什么不把所有新动作继续加进BaseTask

所有领域都加方法
BaseTask持续膨胀
修改影响所有模块
测试边界变宽
公共层成为瓶颈
第一性原理结论兼容门面的目标是保持已有调用稳定，不是成为所有业务动作的永久收纳箱。新领域逻辑默认进入所属模块Task；只有被多个独立模块稳定复用的机制，才考虑建立窄能力对象。

05 · 复用决策阶梯

新增Task能力前，依次通过四道门

这套顺序把“我应该把方法写在哪”变成可重复决策，而不是凭目录熟悉程度做选择。

1
BaseTask已有稳定入口吗？

例如同步图片、文本对话、异步媒体创建与轮询、余额和usage查询。

有：直接复用，停止新增
2
现有窄能力对象已经表达该机制吗？

检查MediaGenerationCapability或BillingCapability，不要复制实现。

有：通过门面或能力对象组合
3
它只服务当前业务模块吗？

模型特有payload、接口组合和业务动作属于模块自己的变化方向。

是：写入模块Task
4
已有多个模块证明需要同一机制吗？

先有真实复用证据，再建立职责窄、可单测的公共能力对象。

否：不要提前公共化
黄金路径实例OfflineFrameworkTask只覆写媒体路径并提供确定性策略，然后直接调用继承的create_and_poll_media_generation()。创建、提取task_id和轮询的组合仍只有一个实现源。

08 · TOC与变化位置映射

当前约束：能写模块，但公共化时机判断不稳

过早公共化和重复实现是同一问题的两端。最有效的控制点，是让每个变化先落到最窄、最稳定的所有者。

TOC约束链
新需求到来
未判断变化范围
塞入BaseTask
公共门面膨胀
所有模块受影响

解除约束：默认选择最窄责任位；只有真实跨模块证据出现，才把稳定机制下沉为窄能力。

Design Choice · Boundary

设计选择与适用边界：模块保留稳定身份，能力只在证据充分时下沉

现
当前方案

模块暴露真实Request、Task、Assertions、Decorators类型；BaseTask保留兼容门面，跨模块实现进入窄task_capabilities。

替
替代方案

把新动作都塞进BaseTask，或每个模块复制一份相同helper而不保留稳定公开导出。

因
选择理由

真实类型维持模块身份和导入合同；窄能力对象避免公共门面无限膨胀，同时让复用建立在已观察到的跨模块变化上。

界
不适用条件

能力只服务单一模块、语义尚未稳定时不应下沉；反之若多个模块已共享同一合同和生命周期，继续复制模块实现也不再适用。

阅读问题真正的领域流程如何组合默认实现与注入实现？

    def create_and_poll_media_generation(
        self,
        request_client: BaseRequest,
        payload: dict[str, Any],
        *,
        poll_interval: float = 2,
        poll_timeout: float | None = None,
        polling_policy: PollingPolicy = DEFAULT_MEDIA_POLLING_POLICY,
        retry_policy: RetryPolicy | None = None,
        create: Callable[[BaseRequest, dict[str, Any]], requests.Response] | None = None,
        extract_task_id: Callable[[requests.Response], str] | None = None,
        poll: Callable[..., requests.Response] | None = None,
    ) -> requests.Response:
        create_call = create or self.create_media_generation
        extract_call = extract_task_id or self.extract_task_id
        poll_call = poll or self.poll_media_generation_result
        with operation_scope(
            RuntimeOperationKind.ASYNC_TASK,
            name="media_generation",
            role=RuntimeTrafficRole.WORKLOAD,
            model_id=model_id_from_kwargs({"json": payload}),
        ):
            create_response = create_call(request_client, payload)
            task_id = extract_call(create_response)
            return poll_call(
                request_client,
                task_id,
                poll_interval=poll_interval,
                poll_timeout=poll_timeout,
                polling_policy=polling_policy,
                retry_policy=retry_policy,
            )
阅读答案

Capability 对 create、extract_task_id、poll 分别采用“传入实现优先，否则用自身默认方法”。随后在 ASYNC_TASK 操作域内依次创建任务、提取 task_id、轮询，并把间隔、超时、轮询策略和重试策略完整传给轮询调用。

源码执行依据

选择create/extract/poll调用点，进入ASYNC_TASK操作作用域，依次创建、提取task_id并轮询。

状态结果

创建运行时操作作用域并执行请求/轮询调用。

证据结论

Capability拥有create-extract-poll组合流程；BaseTask仍拥有稳定入口、配置和调用点注入。

答案边界

不展开操作作用域记录器、重试和轮询状态机内部。

课后总结 · 调用、配置与状态流

一个组合任务如何跨过门面与Capability

1

测试调用BaseTask

传入Fake Request、payload和poll timeout。

→

场景输入

业务数据与控制参数仍由测试拥有；Fake Request只记录下游调用。

2

BaseTask门面

保持稳定方法名，并收集可覆盖的create/extract/poll绑定方法。

→

扩展点集合

模块差异以绑定方法和类属性形式进入公共能力流程。

3

_media_capability()

用路径模板和任务ID字段创建能力对象。

→

配置快照

Capability得到执行所需配置，但不持有具体测试场景。

4

Capability组合流程

依次调用create、extract task_id、poll。

→

状态转换

payload → 创建Response → task_id → 最终Response；poll参数原样传递。

5

测试读取记录

检查POST路径、poll路径、超时和最终响应。

→

证据边界

证明组合与参数透传，不证明真实HTTP、Retry或Polling算法。

最小记忆单元

门面解决“调用方依赖谁”，Capability解决“公共流程放哪里”，绑定方法解决“模块差异怎样继续生效”。
