Week 1 · Day 3

模块标准结构与任务能力

第2课让你看懂一个模块内的职责交接；今天再向前一步：把这些职责组织成稳定骨架，并学会判断一个新能力应该留在模块Task、复用BaseTask，还是进入窄能力对象。

建议用时 120～150分钟 难度：进阶入门 实践：纯设计、零真实接口 前置：掌握模块四件套
本课结果：你将完成一个虚构example_model的模块蓝图，并能用一套稳定决策解释路径、payload、Schema、公共能力与报告字段各自应该落在哪里。

01 · 目标与能力桥接

从“知道四层”升级为“能设计模块”

模块化的本质不是创建文件，而是让每种变化有稳定所有者。今天的产出必须能接受未来需求变化，而不只是看起来目录完整。

1

搭出最小骨架

知道6个必需文件、4个真实子类以及按需文件的创建条件。

2

建立稳定公开入口

理解真实类身份、MRO与__init__.py导出共同形成模块合同。

3

识别两层Task架构

区分BaseTask兼容门面与Media/Billing能力对象的实现职责。

4

做出扩展决策

能判断复用现有入口、写模块Task或建立窄能力对象，避免继续膨胀BaseTask。

三天的能力递进

第1天
看懂项目层级
第2天
看懂模块交接
第3天
设计模块骨架
第4天
管理测试生命周期
第5天
建立测试分层
本课范围护栏会提到Allure步骤、Polling和账单结算，但只用于识别“能力归谁”。fixture、setup/teardown、断言细节与Allure附件边界留到第4课。

02 · 六文件模块骨架

最小结构不是六个空文件，而是六个稳定责任位

点击文件查看允许职责与禁止事项。第一次设计模块时，先填满责任位，再决定是否添加可选文件。

module/example_model/

最小必需：始终创建

  • __init__.py
  • Request / Assertions / Decorators / Task四件套
  • 至少一个test_*.py业务入口

按需增加：有拆分理由才创建

  • 稳定响应结构较多：response_schemas.py
  • payload多到Task职责变模糊：payloads.py
  • 模块专用fixture：conftest.py
  • 复用Python数据：test_data.py
避免机械分层单个常量不值得新建文件；JSON、YAML、Excel也不是默认用例入口。拆分只有在降低变化耦合时才有价值。

03 · 真实类与稳定导出

模块合同由“真实类型 + 公开入口”共同组成

第2课解释了空子类的价值；今天把它放进完整模块合同：调用方从模块包导入，不依赖内部文件布局。

公共基类BaseRequest / BaseTask等
→
模块真实子类ExampleModelRequest / Task等
→
模块公开入口__init__.py + __all__
类型身份__name__和__module__明确表达所属模块。
继承关系MRO保留公共能力来源，也允许模块以后覆写。
稳定导入测试从module.example_model导入，不绑定内部文件路径。
演进隔离内部文件可重构，只要公开类合同保持稳定，调用方无需迁移。

推荐公开入口

from module.example_model.assertions import ExampleModelAssertions
from module.example_model.decorators import ExampleModelDecorators
from module.example_model.request import ExampleModelRequest
from module.example_model.task import ExampleModelTask

__all__ = [
    "ExampleModelAssertions",
    "ExampleModelDecorators",
    "ExampleModelRequest",
    "ExampleModelTask",
]
使用简单别名
失去模块身份
导入绑定公共实现
模块扩展需换类型
调用方批量迁移
禁止替代ExampleModelTask = BaseTask复用了行为，却破坏了类型与演进边界。正确做法是定义真实子类，即使初始类体只有pass。

04 · Task门面与能力对象

BaseTask保留入口，task_capabilities承载真实领域实现

这是一个“兼容门面 + 窄能力对象”结构。点击能力查看入口、委托对象与当前边界。

模块Task

保存模块差异、payload builder与独有业务动作；继承稳定公共入口。

继承 / 调用 →

BaseTask兼容门面

保留现有方法、Allure业务步骤与动态覆写入口，把工作委托给窄能力对象。

委托 →

task_capabilities

MediaGenerationCapability与BillingCapability分别实现媒体、账单能力。

为什么不把所有新动作继续加进BaseTask

所有领域都加方法
BaseTask持续膨胀
修改影响所有模块
测试边界变宽
公共层成为瓶颈
第一性原理结论兼容门面的目标是保持已有调用稳定，不是成为所有业务动作的永久收纳箱。新领域逻辑默认进入所属模块Task；只有被多个独立模块稳定复用的机制，才考虑建立窄能力对象。

05 · 复用决策阶梯

新增Task能力前，依次通过四道门

这套顺序把“我应该把方法写在哪”变成可重复决策，而不是凭目录熟悉程度做选择。

1
BaseTask已有稳定入口吗？

例如同步图片、文本对话、异步媒体创建与轮询、余额和usage查询。

有：直接复用，停止新增
2
现有窄能力对象已经表达该机制吗？

检查MediaGenerationCapability或BillingCapability，不要复制实现。

有：通过门面或能力对象组合
3
它只服务当前业务模块吗？

模型特有payload、接口组合和业务动作属于模块自己的变化方向。

是：写入模块Task
4
已有多个模块证明需要同一机制吗？

先有真实复用证据，再建立职责窄、可单测的公共能力对象。

否：不要提前公共化
黄金路径实例OfflineFrameworkTask只覆写媒体路径并提供确定性策略，然后直接调用继承的create_and_poll_media_generation()。创建、提取task_id和轮询的组合仍只有一个实现源。

新建example_model

应从规范和离线示范提炼，而不是机械复制现有薄模块；最小payload builder优先放在模块Task。

  • 从六文件骨架起步
  • 四个真实类
  • 测试只编排场景

07 · 模块设计工作台

为虚构example_model完成一份模块蓝图

本实践不创建仓库代码、不连接接口。为每个责任位写一句“允许做什么”和一句“禁止做什么”；内容自动保存在浏览器本地。

module/example_model/

目标场景：提交一个最小生成请求，返回非空id与status。

提示：稳定导出四个模块类；不放业务流程。
提示：相对路径、POST、稳定runtime metadata。
提示：组合通用断言，校验非空生成ID。
提示：保留真实子类；公共步骤优先用allure_step。
提示：payload builder和模块业务动作；不扩张BaseTask。
提示：场景编排和最终断言；不拼URL或底层HTTP。

设计记录保存在浏览器本地。

最小payload builder

class ExampleModelTask(BaseTask):
    @staticmethod
    def build_generation_payload(
        model_id: str = "example-model",
    ) -> dict[str, object]:
        return {
            "model": model_id,
            "prompt": "用于接口自动化验证的最小提示词",
        }
每次返回新字典
避免用例间共享可变对象。
只表达业务数据
URL、鉴权和Session不进入payload。
保持最小输入
先覆盖稳定合同，再按场景增加字段。

08 · TOC与变化位置映射

当前约束：能写模块，但公共化时机判断不稳

过早公共化和重复实现是同一问题的两端。最有效的控制点，是让每个变化先落到最窄、最稳定的所有者。

TOC约束链
新需求到来
未判断变化范围
塞入BaseTask
公共门面膨胀
所有模块受影响

解除约束：默认选择最窄责任位；只有真实跨模块证据出现，才把稳定机制下沉为窄能力。

需求变化到修改位置

需求变化选择主要修改位置结果
example_model新增生成接口相对路径
新增最小generation payload builder
新增稳定成功响应JSON Schema
修改所有模块共用的Retry资格算法
修改跨模块账单结算与usage查询机制
Pipeline Summary新增一个展示字段

09 · 知识自测

确认你掌握的是扩展原则

建议达到4/5再进入门禁。答错时回到六文件责任位与复用决策阶梯，而不是记文件名。

1. 规范化新模块的最小结构是什么？
正确答案是B。Schema、payloads、conftest和test_data按实际职责增加，不机械创建。
2. BaseTask在当前架构中的主要定位是什么？
正确答案是C。真实媒体和账单实现分别位于对应task_capabilities中。
3. 一个新动作只服务example_model，且没有跨模块复用证据，应放在哪里？
正确答案是A。默认从最窄责任位开始，避免提前公共化。
4. payload builder最重要的可变性规则是什么？
正确答案是B。测试数据应隔离，鉴权与环境地址也不属于业务payload。
5. 从image_model和video_model只读对比时，最正确的结论是什么？
正确答案是C。历史快照证明兼容性，不代表每个细节都是推荐写法。
