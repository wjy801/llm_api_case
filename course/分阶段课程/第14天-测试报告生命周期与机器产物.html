WEEK 3 · DAY 14

Allure单一生命周期与机器产物

今天不只学习“怎样生成报告”，而是追问更底层的问题：直接pytest与多池Runner怎样在不互相清理、不重复生成、不改写测试结果的前提下，共享同一套Allure规则。

建议时长 2小时只运行离线用例主文件 allure_lifecycle.py前置：第12～13天
今日验收：能够判断谁拥有Allure生命周期、raw写到哪里、何时合并与生成，以及Allure失败为什么只能降级证据。

01 · Objective

目标与核心约束

1

识别所有者

区分直接pytest、Runner、xdist worker与collect-only。

2

解释多池合并

说明每池为何使用独立临时raw并最终生成一次。

3

区分机器产物

不把Allure raw、HTML、JUnit和execution-result混为一谈。

4

守住事实优先级

报告失败不能覆盖pytest退出码。

TOC约束：瓶颈不是不会生成HTML，而是多个潜在所有者可能同时清理或生成同一目录。
多池共享最终目录每池都清理
→
后池删除前池raw证据丢失
→
HTML不完整无法下钻
→
报告不可信生命周期冲突
单一所有者 + 每池raw隔离 + 最终一次合并/生成 = 可信生命周期

02 · Artifact model

先区分四类机器产物

Allure raw

allure-results/** 的结果JSON和附件，是HTML输入及请求下钻证据。

Allure HTML/history

allure-report/ 与可选history是阅读视图；生成失败不等于测试失败。

JUnit XML

提供统计与失败详情，由pytest参数或Quality启用，不由Allure隐式创建。

Runner执行事实

reports/execution-result.json 保存计划、池级原码与最终码。

责任边界：Allure拥有raw清理、池目录、合并和HTML/history；不拥有选测、pytest退出码、JUnit、Quality与Jenkins结论。

03 · Ownership

同一实现，按执行画像选择唯一所有者

直接pytest

module/conftest.py 在主进程session start/finish委托生命周期；xdist worker跳过。

Runner

Runner执行池前prepare、每池分配和合并raw、finally中finalize一次。

Runner内部pytest

API_CASE_RUNNER_MANAGED_ALLURE=1 阻止conftest重复接管。

collect-only或无alluredir

不创建直接生命周期，不清理、不创建、不生成制品。

module/conftest.py 只做Hook适配；文件操作和subprocess的单一实现源是 run_orchestration/allure_lifecycle.py。

04 · Direct pytest

直接pytest：一个session，一次prepare与finalize

session start检查跳过条件
→
prepare清理最终raw目录
→
pytest执行插件写raw与附件
→
session finish按开关生成HTML/history
跳过条件：workerinput 存在
        或 collectonly == True
        或 RUNNER_MANAGED == "1"
        或没有 --alluredir
注意：直接pytest生成Allure，不代表会生成execution-result；后者只属于Runner。

05 · Pooled Runner

Runner：池内隔离，池后合并，全局只生成一次

prepare清理最终目录、建临时根
→
parallel-pool独立raw
→
serial-pool独立raw
→
merge_pool合并到最终目录
→
finalize一次HTML/history

pool_args

移除原alluredir与clean参数，为当前stage注入唯一临时目录。

merge_pool在finally

即使pytest调用异常，也尝试保全当前池已写出的raw。

自定义alluredir

只改变最终raw目录；池内仍写临时目录再合并回来。

固定HTML路径

HTML仍在allure-report/，history仍在history_report/。

集合合同：最终raw是所有已执行池raw的并集；NOT_RUN池不伪造结果。

06 · Zero side effect

collect-only：只形成计划，不启动制品生命周期

权威收集nodeid与marker
→
打印分池parallel/serial数量
→
提前返回不创建生命周期

不清理

不删除已有raw或HTML。

不创建

不创建raw、临时池、HTML、history或JUnit。

不写执行事实

不生成新的execution-result。

不消费旧产物

旧文件不能解释为本轮执行。

collect-only若生成报告，会把“未执行”伪装成“已执行”；若清理目录，则产生无关破坏性副作用。

07 · Failure semantics

fail-open不等于成功：测试事实保留，报告能力降级

prepare失败

记录异常并继续，Allure可能不完整。

测试结果照常，证据降级。
池合并失败

记录stage，不覆盖池级pytest原码。

优先保留执行事实。
CLI或Java不可用

HTML跳过或失败，raw仍可保留。

视图缺失不是用例失败。
同名不同内容冲突

不覆盖最终文件，并保留临时目录。

显式保全，不静默改写。
同名且bytes一致可视为重复；内容不同必须报告冲突，存在冲突时临时根不自动删除。

08 · Profiles

执行画像对照

观察项直接pytestRunner正式执行Runner collect-only
所有者conftest委托Runner全局无
池级临时raw无每池独立无
最终raw直接写池raw合并不创建、不清理
HTML/history按配置最终一次不生成
JUnit仅显式参数显式参数或Quality不生成
execution-result无正式执行写入不写
Allure完整不能反推Runner成功；Runner final也不能证明HTML一定生成。它们是不同事实层级。

09 · Offline practice

离线实践：从产物反推生命周期

命令只访问loopback服务，但会清理目标Allure目录，并让Runner更新execution-result；需要保留本地证据时先备份。

步骤1：生命周期单测

.\.venv\Scripts\python.exe -m pytest tests/test_allure_run_lifecycle.py tests/test_allure_history_report.py -q

观察池目录互异、自定义路径保留、生成次数与latest清理。

步骤2：直接pytest与Runner

.\.venv\Scripts\python.exe -m pytest module/offline_framework_example/test_request_pipeline.py -q
.\.venv\Scripts\python.exe run_master.py module/offline_framework_example -n 2

解释哪个入口拥有清理、隔离、合并和最终生成，不只比较文件数量。

步骤3：collect-only

.\.venv\Scripts\python.exe run_master.py module/offline_framework_example --collect-only -q

确认目标目录未被清理，也没有新Allure或Runner执行事实。

10 · Knowledge check

知识自测

答对5题视为达标。

1. Runner执行两池时谁生成最终HTML？
答案B。池内conftest被Runner标记阻止接管。
2. collect-only如何处理已有raw？
答案C。收集与制品生命周期解耦。
3. Allure CLI缺失但用例全通过，结果是什么？
答案A。Allure没有测试结果解释权。
4. 自定义alluredir后池内写到哪里？
答案B。自定义路径是最终raw目录。
5. execution-result由谁产生？
答案C。它与Allure职责独立。
6. 同名不同内容raw如何处理？
答案A。保全冲突证据但不篡改结果。

11 · Exit gate

本课门禁：制品只有一个生命周期所有者

一句话验收：直接pytest与Runner委托同一个实现，但每轮只能有一个所有者；Runner隔离每池raw、最终合并并生成一次，报告故障只能降级证据。
