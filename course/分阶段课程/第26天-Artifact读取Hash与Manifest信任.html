CODE · 代码先行精讲

先证明Hash对应磁盘原始字节，再比较三个消费者的准入策略

信任链有两条：Manifest自身必须先通过身份、版本、状态和完整性准入；目标Artifact再按原始bytes核对Manifest声明的Hash。只有两条链都成立，领域解析器才有资格读取内容。

本节唯一主线：一个CRLF JSON文件的字节级校验

用例文件：tests/test_artifact_io.py；测试函数：test_file_sha256_and_comparison_use_original_bytes；pytest nodeid：tests/test_artifact_io.py::test_file_sha256_and_comparison_use_original_bytes。

阅读规则Hash回答“当前字节是否等于声明字节”，不回答“谁发布了Manifest”；先分清完整性和真实性。
字节测试→file_sha256→compare_file_sha256→Manifest准入→Metrics/Flaky/Pipeline消费者
1

测试冻结“原始字节”而不是重序列化JSON

同一个JSON对象使用不同换行或空白时，领域值可相同，但磁盘字节Hash不同。

tests/test_artifact_io.py::test_file_sha256_and_comparison_use_original_bytes · 完整测试函数
def test_file_sha256_and_comparison_use_original_bytes(tmp_path):
    artifact = tmp_path / "artifact.json"
    content = b'{"value": 1}\r\n'
    artifact.write_bytes(content)
    expected = hashlib.sha256(content).hexdigest()

    assert file_sha256(artifact) == expected
    assert compare_file_sha256(artifact, expected).matches is True
    assert compare_file_sha256(artifact, "0" * 64).matches is False
    assert compare_file_sha256(artifact, None).matches is False

验证事实

输入事实

文件用write_bytes()写入包含CRLF的确切字节，expected直接对这组bytes求SHA-256。

验证

正确Hash匹配；错误Hash和缺失Hash都不匹配，消费者不能把None当成“无需验证”。

状态变化

测试不修改Artifact内容，只生成比较结果。

失败边界

先解析再重新dump会改变字节表达，无法证明磁盘文件与Manifest声明一致。

2

通用I/O层只报告机械事实，不替消费者做领域决策

read_json_object()验证顶层形状，read_jsonl_values()保留行号，Hash函数只处理bytes。

util/artifact_io.py::read_json_object / read_jsonl_values / file_sha256 / compare_file_sha256 · 非连续选段：四个完整函数
def read_json_object(path: str | Path) -> dict[str, Any]:
    source = Path(path)
    value = json.loads(source.read_text(encoding="utf-8"))
    if not isinstance(value, dict):
        raise ArtifactFormatError(f"JSON object required: {source}")
    return value

def read_jsonl_values(path: str | Path) -> Iterator[JsonLine]:
    source = Path(path)
    with source.open("r", encoding="utf-8") as handle:
        for line_number, line in enumerate(handle, start=1):
            if not line.strip():
                continue
            try:
                value = json.loads(line)
            except json.JSONDecodeError as error:
                raise ArtifactJsonLineError(line_number, error) from error
            yield JsonLine(line_number, value)

def file_sha256(path: str | Path) -> str:
    digest = hashlib.sha256()
    with Path(path).open("rb") as handle:
        for chunk in iter(lambda: handle.read(1024 * 1024), b""):
            digest.update(chunk)
    return digest.hexdigest()

def compare_file_sha256(
    path: str | Path,
    expected: object,
) -> HashComparison:
    normalized = expected if isinstance(expected, str) and expected else None
    return HashComparison(expected=normalized, actual=file_sha256(path))

通用层边界

输入验证

JSON对象与JSONL行只做语法/形状检查；错误行号被保留给上层错误信息。

产物

HashComparison保存expected和actual，领域消费者决定不匹配时是抛错、降级还是警告。

所有权

util层拥有机械读取与字节完整性，不拥有run_id、status或Manifest version语义。

失败边界

文件不可读、JSON非法或顶层不是对象时抛机械异常；上层必须保留原因而非伪造空对象。

领域准入

Metrics输入

P0 request facts与Semantic关系事实都必须可信，任一链断裂则抛MetricsSourceError。

Flaky输入

只需要P0 Case/Failure/Integrity链；run必须FINISHED，Manifest必须complete。

状态变化

验证成功只产生领域模型或PreparedImport，仍不修改上游Artifact。

失败边界

消费者可以有不同错误码和准入策略，但都不能在Hash失败后继续领域解析。

def _artifact_hash_matches(
    path: Path,
    expected_hash: Any,
    warnings: list[str],
    label: str,
) -> bool:
    if not path.is_file():
        warnings.append(f"{label}文件缺失")
        return False
    expected = _text(expected_hash)
    if expected is None:
        warnings.append(f"{label}缺少可信哈希")
        return False
    try:
        actual = compare_file_sha256(path, expected).actual
    except OSError as error:
        warnings.append(f"{label}不可读：{type(error).__name__}")
        return False
    if actual != expected:
        warnings.append(f"{label}哈希与清单不一致")
        return False
    return True

报告消费边界

验证

Reporting仍按run、Manifest版本、Schema、complete状态和Hash顺序准入。

状态变化

失败被追加到warnings，相应Quality/Metrics/Flaky分区返回不可用；Jenkins原始结果不被改写。

产物所有权

Reporting只拥有PipelineReport及Markdown/JSON/Email视图，不拥有源Manifest和源Artifact。

真实性边界

Hash只能证明目标字节与Manifest一致；若Manifest来自不可信渠道，仍需签名、公钥或可信发布链。

01 · First principles

Manifest与目标产物必须沿两条不同链验证

消费者为了知道目标文件的期望Hash，必须先对Manifest做最小JSON解析；但目标产物不能先做Schema或领域解析再补Hash验证，否则未验证内容已经进入解析器。

Manifest准入链

Manifest bytes→最小JSON解析→身份/版本/status/integrity策略→签名或可信分发渠道边界

目标产物消费链

目标产物bytes→与已接受Manifest核对Hash→Schema解析→领域关系验证
TOC约束：最窄约束是Manifest本身的真实性。当前仓库实现身份、版本、状态与Hash完整性校验，但没有完整的发布者数字签名体系；因此不能把Hash匹配宣传成来源真实性证明。

02 · Bytes

先读取磁盘事实，再谈对象语义

通用入口

util/artifact_io.py集中处理JSON/JSONL读取、文件Hash和字段精确比较。

原始事实

路径、存在性、读取错误和原始bytes属于机械层，不携带Metrics、Flaky或Reporting结论。

消费者

quality/metrics/sources.py、quality/flaky_importer.py、pipeline_reporting/quality_sources.py各自收紧合同。

边界

通用工具不能因为文件名像Manifest，就假定其run_id、版本或提交状态可信。

03 · Parse

只允许先最小解析Manifest，目标产物应先验Hash再做领域解析

对象允许的第一步下一步
Manifestread_json_object做最小结构解析，取得身份、版本、status、integrity与output_hashes执行消费者准入及外部真实性边界判断
目标JSON/JSONL以原始bytes计算Hash并与已接受Manifest比较Hash通过后才调用JSON/JSONL与Pydantic领域解析
字段比较exact_field_mismatches只报告值差异由领域消费者决定拒绝、降级或NO_DATA

ArtifactJsonLineError仍负责解析阶段的行号证据，但该阶段必须位于目标产物Hash准入之后。不能对解析对象重新序列化后冒充原文件Hash。

04 · Hash

SHA-256比较的是磁盘原始bytes

file_sha256以二进制分块读取；CRLF、空格、键顺序或编码变化都会改变Hash，即使解析后的JSON对象看起来等价。compare_file_sha256只返回expected、actual与matches。

证明范围：Hash匹配能证明当前bytes与期望bytes一致，不能单独证明期望值由可信发布者产生。

05 · Manifest

Manifest先通过自身准入，才有资格提供目标Hash

身份与版本

run_id及manifest/schema/merge或aggregation版本必须与请求和消费者支持范围一致。

提交状态

status=complete或write_status=complete只表示写入事务完成，不等于integrity通过。

完整性策略

complete可正常进入后续检查；degraded是否允许由消费者决定；failed阻断消费。

来源与Hash绑定

通过准入的output_hashes和上游Manifest Hash把消费者固定到同一份bytes，但不自动证明Manifest发布者身份。

06 · Hash versus signature

Hash校验内容一致性，签名或可信渠道才补发布者真实性

机制能证明不能证明
Hash目标bytes是否与Manifest声明一致Manifest由谁发布、Manifest与Hash是否被一并替换

07 · Domain consumers

相同Manifest基础证据，由不同消费者执行不同准入策略

消费者准入条件与失败动作
Semantic当前只检查P0 run_id、status=complete和request-metrics Hash；不检查P0版本或integrity_status，因此只能证明有限来源绑定。
Metrics验证P0/Semantic身份、版本、status、integrity、目标Hash和成员关系；FAILED阻断，其他状态按Metrics合同处理，失败转为MetricsSourceError。
Flaky验证run、Manifest、integrity、Case/Failure/Issue Hash与来源一致性；FAILED阻断，DEGRADED可形成降级导入状态，硬失败不写入历史。
Reporting验证Quality来源身份、状态和Hash；不可用时记录warning并表达NO_DATA，不读取历史文件补值。

11 · Design choice

设计选择与适用边界

现方案最小解析Manifest并验证身份、版本、提交与完整性策略；目标产物先按原始bytes核对Hash，再做Schema和领域解析。
替代方案先解析目标文件后再Hash，或把文件可解析直接当作可信；更高保障方案是签名Manifest并建立公钥信任链。
选择理由双链避免未验证目标内容提前进入领域解析器，原始bytes Hash精确对应磁盘事实，消费者策略保留complete/degraded/failed差异。
不适用条件产物经过不可信渠道、跨组织发布或要求不可抵赖时，当前Hash与未签名Manifest不足，必须采用数字签名、可信时间与密钥生命周期管理。
