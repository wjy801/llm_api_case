WEEK 4 · DAY 17

测试报告生命周期与机器产物

追踪AllureRunLifecycle如何在直接pytest和Runner池化两种执行画像下选择唯一所有者，完成清理、池级隔离、原始结果合并、HTML生成、history快照与latest更新。

建议时长 2.5～3 小时Allure raw单一生命周期history
可核验产出：一张两种执行画像生命周期图、一张机器产物职责矩阵，以及本轮Allure raw与Runner事实对照记录。

01 · First principles

报告问题的本质是所有权，不是文件复制

只要同一个结果目录可能被多个pytest session、xdist worker或Runner池同时清理和生成，制品就会丢失、覆盖或重复生成。因此实现首先确定唯一生命周期所有者，再讨论目录操作。

产生

pytest与allure插件为每个测试写原始JSON和附件。

汇总

Runner把不同池的raw结果隔离后合并到唯一最终目录。

呈现

Allure CLI从raw结果生成HTML；history是额外快照，不是原始事实。

TOC约束：报告生命周期的瓶颈是“谁可以清理和最终生成”，不是“能否调用Allure CLI”。所有者不唯一，后续所有制品都不可信。

02 · Artifact model

先区分四类产物，再追踪生命周期

产物默认位置职责所有者
JUnit XML参数指定或Quality目录pytest用例与阶段结果，供Quality对账pytest执行阶段
Allure rawallure-results/或自定义--alluredirAllure JSON、container与附件的原始输入allure插件写，生命周期负责目录
Allure HTMLallure-report/可浏览报告AllureRunLifecycle.finalize()
Runner事实reports/execution-result.json计划、池状态、原始退出码和JUnit路径Runner，不属于Allure

四类产物可以引用同一轮运行，但不能互相替代。Allure HTML缺失不等于测试未执行；JUnit成功也不能证明Allure附件完整；Runner事实只描述编排，不渲染用例详情。

03 · Ownership selection

同一实现按执行画像选择唯一所有者

执行画像生命周期所有者跳过条件
直接pytestmodule/conftest.py的session hookscollect-only、xdist worker、Runner托管环境
Runner无并发Runner创建的pooled生命周期module hooks通过环境变量让权
Runner并发/串行池同一个Runner全局生命周期每个池只写独立raw目录，不单独生成HTML
collect-only没有制品生命周期只收集计划，禁止清理和生成副作用

RUNNER_MANAGED_ALLURE_ENV是所有权信号：池内pytest看到该变量后，module/conftest.py不再创建直接模式生命周期，避免同一目录被重复清理。

04 · Direct pytest

直接pytest只有一个session，一次prepare与finalize

  1. pytest_sessionstart先检查是否为worker、collect-only或Runner托管。
  2. 解析--alluredir；未显式启用Allure raw时不创建生命周期。
  3. 创建非pooled的AllureRunLifecycle，prepare()清理本轮结果目录。
  4. pytest session正常写入raw结果和附件。
  5. pytest_sessionfinish调用finalize()，按配置生成HTML与history。
sessionstart→clean raw→pytest writes→sessionfinish→generate once

05 · Pooled Runner

池级写入隔离，全局只合并和生成一次

runner.run()创建pooled=True的生命周期并先调用prepare()。生命周期清理最终raw目录，同时在同级建立临时根目录。

  1. pool_args(stage_id, pytest_args)把每个池的--alluredir替换为独立临时目录。
  2. execute_pool()设置Runner托管环境，让池内session不重复接管。
  3. 池完成后merge_pool(stage_id)把该池文件移动到最终raw目录。
  4. 所有池结束后只调用一次finalize()，生成一份全局HTML和history。
守恒关系：最终raw集合 = 所有已执行池raw集合的无损并集；空池和NOT_RUN池不产生伪造结果。

06 · Isolation and merge

同名冲突不覆盖，保留现场并报告降级

merge_pool()具有幂等保护：同一stage_id只合并一次。源文件不存在时直接跳过；目标不存在时移动；源和目标内容相同则视为可接受重复；同名但内容不同则不覆盖，设置冲突标记并把现场留在池目录。

情形处理原因
目标不存在移动到最终raw目录建立唯一汇总集合
目标同名且同内容跳过重复事实不需要复制
目标同名但内容不同保留池目录并记录冲突不能静默覆盖任一事实
合并异常记录fail-open信息报告能力不能改写pytest结果

只有没有冲突时，finalize()才删除临时根目录。发生冲突时保留目录，是为了让使用者能够核验原始证据。

07 · Finalize

HTML和history是同一raw事实的两种呈现

  1. 若GENERATE_ALLURE_REPORT=FALSE，明确跳过HTML生成。
  2. 查找Allure可执行文件；不存在时记录跳过，不改变测试退出码。
  3. 调用Allure CLI把最终raw目录生成到allure-report/。
  4. 只有HTML成功且history开关开启时，再生成带时间戳的单文件历史快照。
  5. 更新history_report/latest别名，并按history_keep_limit清理旧快照；latest不计入历史数量。
merged raw→allure-report→timestamped history→latest→retention
fail-open边界：Allure CLI缺失或生成失败会被报告，但不能把已形成的pytest退出码改成另一种测试事实；报告降级与测试失败必须分开表达。

08 · Zero side effect

collect-only与机器产物边界必须保持干净

collect-only

Runner在准备Allure前返回；module session hook也检查collectonly。因此不清理raw、不创建临时池目录、不生成HTML或history。

execution-result

由Runner独立写入，记录池事实和JUnit路径。Allure生命周期既不拥有它，也不从它推导报告成功。

tests/conftest.py还会在框架自身测试中关闭隐式Allure目录，防止开发测试的raw结果混入业务报告。只有调用者显式传递--alluredir时才保留。

09 · Existing tests

运行Allure生命周期专项测试

.\.venv\Scripts\python.exe -m pytest `
  tests/test_allure_run_lifecycle.py `
  tests/test_allure_history_report.py `
  tests/test_run_orchestration_boundaries.py `

测试证据对应合同
不同池使用独立目录并行与串行raw不会互相清理
所有池只生成一次全局生命周期是唯一最终所有者
自定义alluredir解析两种参数写法都能定位最终目录
history保留与latest旧快照按数量清理，latest持续指向最新成功快照
静态所有权门禁pytest主调用和Allure文件系统生命周期没有第二所有者

Design decision

设计选择与适用边界

现方案替代方案选择理由不适用条件
按执行画像选择唯一Allure生命周期所有者，池级raw目录隔离，全局只合并并生成一次HTML/history。每个池直接写同一raw目录并各自生成报告，或由Runner和pytest插件同时prepare/finalize。单一所有者消除清理竞态和重复finalize；池级隔离允许冲突保留现场，最终报告仍来自同一组原始事实。使用具备事务、幂等键和远程合并能力的托管结果后端时，可由后端承担隔离与归并，本地目录生命周期需要重新定义。

10 · Current-run artifact

生成本轮raw结果并与Runner事实对照

$python = '.\.venv\Scripts\python.exe'
$raw = 'reports/course/day17-allure-results'
$oldQuality = $env:QUALITY_ENABLE
$oldAllure = $env:GENERATE_ALLURE_REPORT
$oldHistory = $env:GENERATE_HISTORY_REPORT
try {
  $env:QUALITY_ENABLE = '0'
  $env:GENERATE_ALLURE_REPORT = 'FALSE'
  $env:GENERATE_HISTORY_REPORT = 'FALSE'
  & $python run_master.py module/offline_framework_example -n 2 --alluredir=$raw
  if ($LASTEXITCODE -ne 0) { throw ('Runner exit=' + $LASTEXITCODE) }
  $runner = Get-Content -LiteralPath 'reports/execution-result.json' -Raw | ConvertFrom-Json
  $rawFiles = @(Get-ChildItem -LiteralPath $raw -File -ErrorAction Stop)
  [pscustomobject]@{
    PlannedCases = $runner.planned_case_count
    Pools = @($runner.pool_results).Count
    FinalExit = $runner.final_exit_code
    AllureRawFiles = $rawFiles.Count
    ResultJson = @($rawFiles | Where-Object Name -like '*-result.json').Count
    Containers = @($rawFiles | Where-Object Name -like '*-container.json').Count
  }
}
finally {
  $env:QUALITY_ENABLE = $oldQuality
  $env:GENERATE_ALLURE_REPORT = $oldAllure
  $env:GENERATE_HISTORY_REPORT = $oldHistory
}

本实践故意关闭HTML和history，只验证无需外部Allure CLI即可核验的raw事实。专项测试已覆盖HTML、history、latest和保留策略。
