BaseRequest.poll_get()建立一次Polling会话

连续源码覆盖参数门禁、总timeout、运行事实开始以及成功/异常收口。

common/base_request.py::BaseRequest.poll_get · 连续选段
    @download_links_from_poll_get
    def poll_get(
        self,
        path: str,
        *,
        poll_interval: float = 2,
        poll_timeout: float | None = None,
        polling_policy: PollingPolicy,
        retry_policy: RetryPolicy | None = None,
        **kwargs: Any,
    ) -> requests.Response:
        if poll_interval <= 0:
            raise ValueError("poll_interval must be greater than 0")

        timeout = self.config.timeout if poll_timeout is None else poll_timeout
        if timeout <= 0:
            raise ValueError("poll_timeout must be greater than 0")

        metadata = self._runtime_observer.normalize_metadata(
            kwargs,
            kind=RuntimeOperationKind.POLLING,
            default_name="polling",
        )
        polling = self._runtime_observer.start_polling(metadata)
        try:
            response = self._poll_get_with_policy(
                path,
                poll_interval=poll_interval,
                timeout=timeout,
                polling_policy=polling_policy,
                retry_policy=retry_policy,
                runtime_polling=polling,
                **kwargs,
            )
        except BaseException as error:
            polling.finish_error(error)
            raise
        polling.finish_success()
        return response

公共入口统一会话边界

输入与消费

它消费模块路径、时间参数与两类策略；非法间隔或超时在发送前立即失败。

状态与收口

运行观察先开始；内部循环成功则finish_success()，任意异常则finish_error(error)后原样重抛。

易混点

Retry处理一次逻辑GET内部的传输attempt；Polling处理多个业务状态GET，两者不是同一个循环。

每轮产出两类事实

输入与消费

循环消费路径、deadline和策略；_request_without_attach()负责一次逻辑GET，evaluate_polling_response()负责业务状态分类。

输出与状态

每轮写入last_response、last_status与PollingTransition，运行观察同步记录pending/success等状态。

失败与易混点

传输Retry耗尽deadline会转换为PollingTimeoutError；状态评估异常则先保留最后Response证据再重抛。

谁负责最终收口

成功

SUCCESS附加完整迁移证据并返回最后Response，回到测试的Assertions。

失败与降级

FAILURE、UNKNOWN、TIMEOUT都携带最后状态、Response与迁移序列抛出；PENDING只计算不越过deadline的等待时间。

初学者易混点

HTTP 200不等于Polling成功；真正终态由PollingPolicy对响应JSON的评估结果决定。

现在再谈“测试分层”

这条分类用例把故障域限定在Polling：Task只翻译领域输入，BaseRequest统一循环与异常，Assertions只验证最终合同。后续概念章节据此解释为什么局部反例不应先进入黄金路径。

03 · 三层验证模型

证明范围越大，反馈与归因成本越高

三层不是成熟度排名，而是不同故障域的分工。点击查看每层消费什么输入、产出什么证据以及不能证明什么。

从刚才代码回看evaluate_polling_response()适合L1精确穷举状态；test_polling_reaches_success_with_complete_transitions属于L2；完整创建、轮询、上下文与清理组合才属于L3。

04 · 最低成本决策

选择足以暴露目标故障的最低层

三问决策
1. 只涉及状态映射或时间计算吗？优先单元合同，直接制造输入并断言返回值或异常。
2. 必须经过Task → Request → BaseRequest吗？进入对应能力分类，验证普通module过程与运行事实。
3. 必须证明多个成熟能力共同工作吗？才进入黄金路径，并只保留稳定成功主链。
局部故障
误放完整组合
依赖与证据增多
根因空间扩大
反馈变慢
TOC判断当前约束不是测试数量，而是局部故障被高组合用例包裹。先缩小故障域，才能提高整套回归的有效吞吐。

补充 · 普通module合同

能力分类仍然复用同一公共实现

1

Test定义目标

Act与断言围绕一个主要故障域，不把无关能力加入归因空间。

2

Task翻译领域输入

模块层只组织payload、ID和路径，不复制公共状态机。

3

BaseRequest拥有机制

请求、Retry、Polling、Middleware与运行事实继续走公共实现。

4

Assertions收口证据

只断言测试目标需要的Response、状态、异常与运行事实。

05 · 分类用例地图

每个文件只保护一个主要故障域

分类边界一个用例可以经过公共Request、Middleware与Runtime Hooks，但它的主要断言只能服务一个故障目标；否则失败后无法确定应由哪个能力所有者修复。

06 · 分类与黄金路径

黄金路径证明组合，不负责穷举反例

分类用例

  • 一个主要能力与少量直接协作者
  • 包含成功或明确失败分支
  • 失败后能快速指向函数与状态

黄金路径

  • 串联已经稳定的能力
  • 只保护代表性的成功主链
  • 失败时回到分类用例缩小根因
回看入口今天选择Polling分类而非完整黄金路径，因为目标是理解状态循环与终态分支，不需要让Context、Capture和资源清理同时参与归因。

09 · TOC层级选择练习

不要用最完整的测试解决最局部的问题

核心约束

如果目标故障只能在大量协作者同时运行时才被看到，定位吞吐就会被最慢的组合测试限制。先把问题放到最低充分层。

验证Polling状态字符串到枚举的映射
验证模块payload经Request后保持不变
验证带幂等条件的POST是否进入Retry
验证unknown状态抛出领域异常
验证两个worker的请求级Header互不泄漏
验证创建、轮询、上下文、捕获与清理稳定组合

Design Choice · Boundary

设计选择与适用边界：让故障在最低成本层先暴露

现
当前方案

单元合同保护算法，能力分类保护普通module故障域，黄金路径保护成熟能力组合。

替
替代方案

所有变化都塞进一条端到端用例，或只按文件位置增加测试而不声明证明目标。

因
选择理由

较低层反馈更快、失败归因更窄；较高层只承担无法由低层证明的组合风险。

界
不适用条件

新能力合同尚未稳定时，先建立最小可执行证据，不机械补齐所有层。

Polling分类用例如何从输入走到终态证据

1

test_polling_reaches_success_with_complete_transitions()

Act把request、task_id、时间参数与两类策略交给Task。

→

测试目标被限定

目标是得到终态Response并验证状态码、任务ID、succeeded与Schema；其他失败分支由兄弟分类用例负责。

2

poll_media_generation_result()

Task格式化任务路径并建立Polling operation语义。

→

领域输入变为请求输入

task_id变成路径；interval、timeout、PollingPolicy与RetryPolicy原样进入BaseRequest.poll_get()。

3

BaseRequest.poll_get()

校验时间参数，启动Polling观察并调用内部循环。

→

会话状态建立

成功写finish_success()并返回Response；任意异常写finish_error(error)后保持原异常语义。

4

_poll_get_with_policy() + evaluate_polling_response()

循环发送逻辑GET，评估JSON业务状态并追加transition。

→

Response变为状态证据

每轮形成raw_status、PollingState、HTTP状态码与elapsed；传输Retry只影响单轮GET内部attempt。

5

终态分支 → Assertions

SUCCESS返回，FAILURE/UNKNOWN/TIMEOUT抛带迁移证据的领域异常，PENDING继续等待。

→

门禁终点

成功最终Response回到测试并由Assertions收口。
失败分类异常保留最后Response和迁移序列，测试应在对应兄弟用例断言。
最小记忆单元

Test定义证明目标，Task翻译领域输入，BaseRequest拥有循环，PollingPolicy决定状态，Assertions只收口可观察合同。
