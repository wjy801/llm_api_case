def _run_audit_workers(
    service: OfflineService,
    audit_names: tuple[str, str],
    *,
    owner_var: ContextVar[str] | None = None,
) -> tuple[list[_OfflineAuditWorkerResult], set[int]]:
    barrier = Barrier(2)
    closed_session_ids: set[int] = set()
    closed_session_lock = Lock()
    with ThreadPoolExecutor(max_workers=2) as executor:
        futures = [
            submit_with_context(
                executor,
                _query_audit_worker,
                service.base_url,
                audit_name,
                barrier=barrier,
                owner_var=owner_var,
                closed_session_ids=closed_session_ids,
                closed_session_lock=closed_session_lock,
            )
            for audit_name in audit_names
        ]
        results = [future.result(timeout=2) for future in futures]
    return results, closed_session_ids

编排边界

输入从哪里来

服务地址、两个名称和可选owner变量来自测试。

当前消费什么

编排器消费任务列表，创建同步Barrier、关闭集合和保护集合的Lock。

输出写到哪里

Future结果汇总为列表，关闭过的Session id汇总为集合。

谁负责收口

ThreadPoolExecutor上下文管理器收口线程池；每个Future必须在timeout内给出结果或异常。

失败边界

Future异常会在result()重新抛出；编排器不伪造成功结果。

3

submit_with_context()在每次提交时复制当前Context

复制发生在调用线程，执行发生在worker线程。

common/context_executor.py::submit_with_context · 连续源码第12至20行
def submit_with_context(
    executor: Executor,
    function: Callable[P, T],
    /,
    *args: P.args,
    **kwargs: P.kwargs,
) -> Future[T]:
    context = copy_context()
    return executor.submit(context.run, function, *args, **kwargs)

传播只做一件事

输入从哪里来

Executor、目标函数及参数来自编排器，当前ContextVar状态来自提交线程。

当前消费什么

copy_context()冻结当前逻辑上下文，context.run包装真实worker。

输出写到哪里

返回的Future进入编排器；上下文值在worker执行期间可读取，不写入全局变量。

谁负责收口

Executor负责调度Future；目标函数负责自己的业务和资源清理。

易混点

不能在循环外复制一次并让多个线程同时进入同一个Context对象；每次submit必须独立复制。

4

worker创建自己的请求实例，并在finally中关闭Session

传播解决“我是谁”，独立Client与Session解决“我会污染谁”。

module/offline_framework_example/test_concurrency_context.py::_query_audit_worker · 连续源码第32至61行
def _query_audit_worker(
    base_url: str,
    audit_name: str,
    *,
    barrier: Barrier,
    owner_var: ContextVar[str] | None,
    closed_session_ids: set[int],
    closed_session_lock: Lock,
) -> _OfflineAuditWorkerResult:
    request_client = OfflineFrameworkRequest(
        base_url,
        capture_policy=CapturePolicy.disabled(),
    )
    session_id = id(request_client.session)
    try:
        barrier.wait(timeout=1)
        inherited_owner = owner_var.get() if owner_var is not None else None
        response = OfflineFrameworkTask().query_audit(request_client, audit_name)
        return _OfflineAuditWorkerResult(
            audit_name=audit_name,
            response=response,
            session_id=session_id,
            inherited_owner=inherited_owner,
            trust_env=request_client.session.trust_env,
            audit_header_in_session="X-Audit-Name" in request_client.session.headers,
        )
    finally:
        request_client.close()
        with closed_session_lock:
            closed_session_ids.add(session_id)

资源隔离与收口

输入从哪里来

base_url与audit_name来自编排器，owner值来自刚复制的逻辑上下文。

当前消费什么

worker创建独立请求实例，等待并发起点，读取owner并发出请求。

输出写到哪里

响应、owner、Session id和Header泄漏事实封装到不可变结果对象。

谁负责收口

worker的finally无条件关闭自己的请求实例；加锁后记录关闭事实。

成功/失败分支

请求成功返回结果；Barrier、请求或构造结果失败都会越过return，但仍执行close后把异常交给Future。

代码先行结论

  1. ContextVar的所有者是逻辑执行链，因此在submit时复制。
  2. Session的所有者是worker请求实例，因此每个worker独立创建并在finally关闭。
  3. serial只能保护仍无法隔离的共享业务状态，不能替代传播与资源所有权设计。

01 · Question

并发后证据为什么可能失去用例归属

ContextVar只在当前执行上下文中有效，普通线程池不会自动继承提交线程状态。若同时共享可变Session或Header，业务请求和观察事实都会发生串线。

本课边界：学习仓库现有传播与隔离实现，不通过sleep、竞态或故意共享对象制造失败。

03 · Context

ContextVar不是跨线程全局变量

它表达当前逻辑执行链的上下文。进入新线程时必须显式复制，否则worker看到默认值或错误用例身份。

用例上下文→提交位置→copy_context→worker执行

04 · Submit

每次submit都需要独立快照

同一个Context对象不能被多个线程同时进入。正确实现是在每次提交任务时复制当前context，再让该副本包装worker函数。

因果链：复用一个快照 → 多worker竞争进入 → 上下文错误或运行时异常；每次提交复制 → worker拥有独立执行上下文。

05 · Ownership

Client、Session和请求Header属于三个层级

对象建议所有权原因
Client配置业务能力或调用方保存稳定配置，不承载worker可变状态。
Sessionworker或独立请求实例连接池和Cookie等状态不能跨并发任务污染。
单次Header当前请求通过请求参数传递，不能写回共享默认Header。

06 · Isolation

独立Session和请求级Header共同阻断泄漏

并发测试应证明每个worker使用自己的Session，且一次请求附加的Header不会出现在其他worker或下一次请求中。隔离事实比“命令执行很快”更重要。

正确

worker独占Session，请求Header使用局部副本。

危险

多个worker修改同一个Session.headers或共享Cookie状态。

07 · Serial boundary

serial只保护无法隔离的共享业务状态

独立loopback服务、独立账号和独立Session可以并发；余额、同一账号结算顺序或进程环境等共享可变状态需要串行或显式恢复。

判断顺序：先尝试资源隔离 → 再证明是否仍有共享状态 → 最后决定serial。不能用serial长期掩盖Session或Context泄漏。

Design decision

设计选择与适用边界

现方案替代方案选择理由不适用条件
每次提交都用copy_context()生成独立快照，同时让每个worker拥有独立Session，请求级Header只存在于本次调用。共享一个Context快照或Session并加锁，或者把所有用例都标记为serial。上下文归属、连接状态和请求元数据在三层分别隔离，既消除串线又保留可并行部分，不用全局锁掩盖所有权错误。跨进程传播需要显式序列化上下文；真实共享业务资源无法隔离时仍应使用serial或外部租约，而不是强行并发。

from __future__ import annotations

from contextvars import ContextVar, Token

from common.runtime_hooks.noop import NoopRuntimeHooks
from common.runtime_hooks.protocol import RuntimeHooks


_NOOP_RUNTIME_HOOKS = NoopRuntimeHooks()
_RUNTIME_HOOKS: ContextVar[RuntimeHooks] = ContextVar(
    "common_runtime_hooks",
    default=_NOOP_RUNTIME_HOOKS,
)


def get_runtime_hooks() -> RuntimeHooks:
    return _RUNTIME_HOOKS.get()


def bind_runtime_hooks(hooks: RuntimeHooks) -> Token[RuntimeHooks]:
    if hooks is None:
        raise TypeError("hooks must not be None")
    return _RUNTIME_HOOKS.set(hooks)


def reset_runtime_hooks(token: Token[RuntimeHooks]) -> None:
    _RUNTIME_HOOKS.reset(token)
阅读答案

结论：Runtime Hooks通过ContextVar绑定和恢复逻辑状态，不创建或关闭请求资源。机制：未绑定时返回单例Noop Provider；bind校验非None后set并返回Token，reset用该Token恢复先前值。

源码执行依据

ContextVar提供Noop默认值，bind设置并返回Token，reset使用Token恢复先前绑定。

状态结果

改变当前逻辑上下文中的RuntimeHooks绑定。

证据结论

Provider绑定属于ContextVar逻辑状态，并可通过Token恢复。

答案边界

Provider传播不创建请求Session，也不提供资源关闭。

                closed_session_lock=closed_session_lock,
            )
            for audit_name in audit_names
        ]
        results = [future.result(timeout=2) for future in futures]
