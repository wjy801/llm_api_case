DAY 12 · AUTHORITATIVE PLAN, CONSERVED SETS

权威收集与并串行集合守恒

调度器的第一责任不是尽量并发，而是证明每个被选中的 nodeid 恰好出现一次：要么进入并发池，要么进入串行池，绝不能两边都进或两边都不进。

建议 1.5～2.5 小时前置：第11天参数计划实践只做离线收集核心：pytest_execution.py / scheduling.py
完成标志：能解释 Runner 为何只权威收集一次；能从 pytest item 得到 nodeid/marker 计划；能用互斥并集证明分池守恒，并区分“不传 -n 的全量串行”与“传 -n 的并发优先、串行收尾”。

01 · First principles & TOC

先证明“一个不丢、一个不重”，再优化速度

测试计划是一个有限集合。任何调度优化都只能改变执行位置与顺序，不能改变成员身份。若计划集合不可信，JUnit、Allure、Quality再精细也只是在报告错误的样本。

Plan = Parallel ∪ Serial　且　Parallel ∩ Serial = ∅附加不变量：authoritative plan 内 nodeid 唯一，因此每个 nodeid 最多执行一次。
1

唯一权威

只让 pytest 解释收集路径、选择表达式与marker继承。

2

身份冻结

把最终item映射为不可变nodeid与markers事实。

3

纯函数分池

调度算法不导入pytest，不扫描文件，只消费计划。

4

失败优先

重复、交集或并集不等立即拒绝，不带病执行。

多次重新收集插件/环境/选择条件可能变化
→

→
遗漏或重复执行数量表面相近也可能错
→

TOC 当前约束：吞吐量不是首要瓶颈，计划的单一真相源才是。先冻结 nodeid/marker 计划并证明集合守恒，xdist worker 数才有优化意义。

02 · Authoritative collection

为什么权威收集只能发生一次

pytest 拥有参数表达式、fixture导入、插件钩子、marker继承和nodeid生成规则。Runner不能用文件扫描模拟这些语义，只能让pytest给出最终items。

唯一解释器：pytest

输入target + -k/-m/--ignore/--deselect + 插件参数固定收集模式--collect-only -q -o addopts=输出session.items中的最终nodeid与全部markers

03 · Identity facts

CollectedTestCase 只冻结调度真正需要的事实

数据模型只有 nodeid 和 frozenset[str] markers。这让调度输入不可变、可比较，也避免把pytest Item对象和插件内部状态泄漏到纯算法。

稳定数据模型

@dataclass(frozen=True)
class CollectedTestCase:
    nodeid: str
    markers: frozenset[str]

    @property
    def is_serial(self) -> bool:
        return "serial" in self.markers

从item提取事实

for item in session.items:
    collector.items.append(
        CollectedTestCase(
            nodeid=item.nodeid,
            markers=frozenset(
                marker.name
                for marker in item.iter_markers()
            ),
        )
    )
NODEID

精确执行身份

包含文件、类、函数与参数化ID；Runner后续直接使用它执行，不再依赖文件名猜测。

MARKERS

完整marker视图

iter_markers() 包含函数、类和文件级marker继承，调度不只看函数装饰器。

FROZEN

计划不可变

dataclass冻结且markers为frozenset，分池阶段不能偷偷修改收集事实。

ORDER

相对顺序保留

算法单次遍历，分别向两池append，因此每个池内保持权威收集相对顺序。

事实拥有者调度用途不承担
nodeidpytest collection唯一身份、精确执行参数、重复检测。不表示通过/失败。
markerspytest iter_markers按serial_marker二选一归池。不决定worker数。
collection exitpytest0继续，5为空集合，其他为收集失败。不等于业务用例结果。
stdout/stderrpytest collection失败时格式化诊断。不作为分池输入。

04 · Duplicate defense

重复nodeid必须在执行前失败

相同nodeid出现两次意味着“身份”已经无法区分两项。框架设置两层防线：收集器发现pytest items重复时拒绝；纯调度器再次验证输入计划，防止其他调用方注入重复项。

防线一：收集边界

_CaseCollector 用本地seen记录item.nodeid；重复项加入 duplicate_nodeids，不重复追加到items。

收集结束后抛 RuntimeError，并列出重复身份。

防线二：调度边界

split_test_cases() 再用seen校验每个case；同一nodeid第二次出现立即抛 ValueError。

纯函数不信任调用来源。

为何不能静默去重

静默去重会隐藏参数化ID冲突、插件重复注册或上游计划损坏，只留下“少跑一条”的假正常结果。

失败比猜测哪条是真的更安全。

为何数量相等仍不够

计划为 {a,b}，若分池为 {a,c}，数量仍是2，但b丢失且c越界。必须比较集合成员，不只比较count。

集合等式优先于计数相等。
身份原则：若两个逻辑用例需要分别执行，它们必须拥有不同且稳定的nodeid；参数化用例应提供稳定、可读、不含密钥的参数ID。

05 · Pure scheduling

分池算法只做marker成员判断

scheduling.py 不导入pytest、不读取配置文件、不启动线程。它输入一串不可变case，输出两个nodeid元组，便于独立推理和测试。

真实算法的核心
parallel_cases = []
serial_cases = []
seen = set()

for case in cases:
    if case.nodeid in seen:
        raise ValueError("duplicate nodeid ...")
    seen.add(case.nodeid)
    if serial_marker in case.markers:
        serial_cases.append(case.nodeid)
    else:
        parallel_cases.append(case.nodeid)

parallel = tuple(parallel_cases)
serial = tuple(serial_cases)

四个决策

只遍历一次分类与重复检测同一趟完成。
严格二选一命中serial_marker进串行，否则进并发。
返回tuple输出计划不可由调用方原地追加。
marker可配置默认serial，也可由CLI传入其他marker名。
case Amarkers={smoke}
→
Parallel未命中serial
　
case Bmarkers={billing, serial}
→
Serial命中serial
不要过度推断：进入parallel_pool只表示“允许并发”，不保证它一定与另一条同时运行；worker数、xdist调度和机器资源决定实际并行度。is_serial 是默认 serial marker 的便利属性，实际分池以调用时传入的 serial_marker 为准。

06 · Conservation proof

互斥并集是调度器的可执行证明

算法构造结束后仍显式验证两条集合等式。即使当前if/else天然满足，也要把长期合同写成机器可检查的防线，抵抗未来重构回退。

并集覆盖全部计划

set(P) | set(S) == seen
Parallel
Serial
圆的覆盖范围合起来必须恰好等于权威计划：不能缺成员，也不能多成员。

交集必须为空

set(P) & set(S) == ∅
P
S
两个圆不能共享nodeid；否则同一身份可能执行两次。
坏计划示例违反合同风险
重复输入A=[a,b,b]nodeid唯一性b身份冲突，次数不可信。
两池重叠P=[a,b], S=[b]P ∩ S = ∅b可能执行两次。
遗漏A=[a,b,c], P=[a], S=[b]P ∪ S = Ac被选中却从未执行。
越界新增A=[a,b], P=[a,x], S=[b]P ∪ S = Ax没有权威收集依据。
计数推论：在nodeid唯一且两池互斥的前提下，len(plan) = len(parallel) + len(serial)。计数相等是守恒的可观察结果，但不能替代集合成员等式。

07 · Runtime shapes

marker分类存在，不代表一定启用并发

Runner总会先计算parallel/serial分类。是否使用两个执行池，由 numprocesses 决定。

不传 -n

输出“Parallel test execution disabled”，然后把全部 case_nodeids 按权威收集顺序交给一个 serial-pool。

A → B → C

传 -n 2

先把parallel_cases交给xdist并发池；并发池结束后，再把serial_cases交给不含xdist参数的串行池。

P(A,C) → S(B)
权威计划[A parallel, B serial, C parallel]
→
Parallel poolA、C；注入-n和--dist
→
Serial poolB；移除xdist参数
→
最终事实两池各自保留planned nodeids

空并发池

打印skip，生成 NOT_RUN 结果，不调用pytest；串行池照常执行。

空串行池

并发池执行完成后打印skip，串行阶段为 NOT_RUN。

parallel exit 1

用例失败但不是终止型事实，仍可执行串行池以收集更多失败证据。

parallel exit 2/3/4/5

属于终止型事实，跳过串行池；退出码细节在第13天展开。

08 · Evidence boundary

collect-only能证明什么，不能证明什么

计划证据和执行证据必须分层。collect-only在Quality生命周期与执行事实写入前返回，因此它非常适合证明收集和分池，却不能冒充正式运行产物。

可以从输出核对

  • 打印nodeid总数和每个具体nodeid。
  • parallel/serial分类数量。
  • 总数 = 并发数 + 串行数。
  • nodeid文本是否唯一。
  • 黄金nodeid是否只出现一次。
  • 空选择返回pytest exit 5。

不能从输出声称

  • 用例通过或失败。
  • 两个池实际启动和完成。
  • xdist真正同时运行了多少任务。
  • Quality expected_case_count 已写入证据。
  • execution-result.json 已生成。
  • Allure/JUnit产物完整。

12 · Exit gate

本课门禁：能证明计划，才允许执行计划

一句话验收：pytest只收集一次并冻结nodeid/marker计划；纯调度器拒绝重复后严格二选一归池，以互斥并集证明无遗漏、无越界、无重复；collect-only只能证明计划，不能冒充执行结果。
