01 · First principles

归并不是拼文件，而是证明输出来自哪些可信输入

worker JSONL只是局部事实。P0归并必须回答：是否属于当前run、结构是否有效、身份是否冲突、预期execution是否到齐、Case与JUnit是否一致、输出是否可被后续阶段验证。

恢复

逐行读取，尽可能保留有效记录。

判定

无损去重、冲突识别、JUnit对账和失败分类。

提交

先写输出，再以Hash和计数完成Manifest。

TOC约束：可信P0是分叉约束点：它同时直接供Semantic与Flaky Import消费，Metrics再消费Semantic结果。P0若无法表达缺失和冲突，两条支线都会在错误前提上产生精确但不可信的结论。

02 · Merge request and state

QualityMergeRequest声明本轮期望边界

字段作用
run_id过滤当前run并写入所有归并结果
output_dir定位shards、junit和merged目录
expected_execution_ids验证每个已执行池至少有Case分片
expected_case_count对账最终invocation数量
junit_files提供pytest独立证据
run_start_time支持时间范围与运行身份判断

内部_MergeState分别维护cases、requests、integrity、failures、generated issues、source stats和JUnit evidence。不同事实集合使用不同主键，不能用一个通用字典粗暴归并。

03 · Stable identities

去重键由事实语义决定

事实归并键原因
CaseResult(invocation_id, phase)同一参数化调用有setup/call/teardown三个阶段
RequestMetricrequest_event_id每次真实attempt必须唯一
IntegrityIssuesource、code、related_id、message组合相同问题可无损折叠，不同问题必须保留
FailureRecordinvocation、phase与failure身份保留一次具体失败发生

身份稳定的目的不是追求短ID，而是让不同worker、不同文件顺序下得到确定性输出。所有最终列表还会按固定键排序，保证同一输入重复归并得到同一内容。

04 · Shard scan

按二进制逐行扫描，同时记录来源统计

_scan_shards()按cases、requests、integrity三类glob读取。每个文件先计算SHA-256，再以二进制逐行处理，统计物理非空行、当前run记录、外来run、无效JSON、无效Schema、精确重复和冲突重复。

  1. 分片目录不存在时生成ERROR级shards_dir_missing。
  2. 空行忽略；JSON解析失败只影响该行，并生成完整性问题。
  3. Pydantic模型验证失败记录invalid_schema，不把坏记录放入状态。
  4. run_id不匹配计入foreign_run_records，当前run输出不接纳。
  5. 扫描结束后检查每个expected execution是否存在Case分片。

逐行恢复使一个坏行不会吞掉同文件其他有效事实；来源统计又让这种降级不会被隐藏。

05 · Duplicate semantics

精确重复可折叠，身份冲突必须显式失败

Exact duplicate

相同主键且规范化内容完全一致，只增加exact_duplicates计数，不重复输出。

Conflict duplicate

相同主键但内容不同，增加conflict_duplicates并生成ERROR级Issue，不能任取一条。

规范化比较使用稳定JSON表达，而不是对象地址或原始行文本。因此字段顺序不同但语义相同仍可识别为精确重复。

归并原则：无损重复可以折叠；有损选择必须拒绝。归并器不能靠文件顺序决定哪个worker事实胜出。

06 · JUnit reconcile

Case分片与JUnit是两套独立证据

_read_junit()解析调用者提供的JUnit文件，读取Quality写入的case_id和invocation_id properties、pytest状态和失败摘要。_reconcile()再执行三类对账：

  1. 按invocation聚合setup、call、teardown，通过fold_case_status()计算用例终态。
  2. 检查expected_case_count与实际invocation数量。
  3. 双向检查CaseResult是否有JUnit证据、JUnit invocation是否有CaseResult，并比较兼容状态。

兼容规则不是字符串相等：failed与error互相兼容；skipped与xfailed对应JUnit skipped；其他通过态对应JUnit passed。这样保留pytest语义差异，又避免错误告警。

07 · Failure classification

失败分类只处理已经失败的Case事实

_classify_failures()先按invocation聚合RequestMetric和相关完整性code。只有raw或final状态属于FAILED/ERROR的Case才进入分类器。

证据用途
JUnit error_type、message、assert_location提供失败文本与断言位置
该invocation的请求事实区分HTTP、业务、超时等上下文
相关完整性code说明证据是否缺失或降级
classifier/fingerprint版本让分类规则和稳定指纹可审计

分类器生成FailureRecord，并把failure_id回填到对应CaseResult。分类不改变pytest通过/失败事实，只为失败增加可比较身份和证据摘要。

08 · Commit manifest

Manifest先标记merging，成功后提交Hash

  1. 归并开始即写status=merging的Manifest，表示本轮尚未提交。
  2. 原子写出case-results.jsonl、request-metrics.jsonl、failures.jsonl和integrity-issues.jsonl。
  3. 对四个最终输出计算SHA-256。
  4. 重写Manifest为status=complete，包含版本、来源分片统计、JUnit证据、输出计数、Hash和integrity_status。
  5. 未捕获异常时尽力写status=failed，返回FAILED结果。
integrity_status判定
complete没有WARN或ERROR Issue
degraded存在WARN，但没有ERROR
failed至少一个ERROR，或归并过程异常

Manifest中的output_hashes是Semantic与Flaky Import各自读取P0的信任入口；Metrics通过已提交的Semantic产物继续推导。仅仅“文件存在”不构成提交成功。

10 · Current-run merge

生成并核对本轮P0提交清单

$python = '.\.venv\Scripts\python.exe'
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$root = Join-Path 'reports/course' ('day21-quality-' + $stamp)
$names = @('QUALITY_ENABLE','QUALITY_SEMANTIC_ENABLE','QUALITY_METRICS_ENABLE','QUALITY_FLAKY_HISTORY_ENABLE','QUALITY_FLAKY_STATE_ENABLE','QUALITY_OUTPUT_DIR','QUALITY_RUN_ID','GENERATE_ALLURE_REPORT','GENERATE_HISTORY_REPORT')
$old = @{}; foreach ($name in $names) { $old[$name] = [Environment]::GetEnvironmentVariable($name) }
try {
  $env:QUALITY_ENABLE = '1'; $env:QUALITY_SEMANTIC_ENABLE = '0'; $env:QUALITY_METRICS_ENABLE = '0'
  $env:QUALITY_FLAKY_HISTORY_ENABLE = '0'; $env:QUALITY_FLAKY_STATE_ENABLE = '0'
  $env:QUALITY_OUTPUT_DIR = $root; $env:QUALITY_RUN_ID = 'course-day21-' + $stamp
  $env:GENERATE_ALLURE_REPORT = 'FALSE'; $env:GENERATE_HISTORY_REPORT = 'FALSE'
  $allure = Join-Path $root 'allure-results'
  & $python run_master.py module/offline_framework_example -n 2 --alluredir=$allure
  if ($LASTEXITCODE -ne 0) { throw ('Runner exit=' + $LASTEXITCODE) }
  $manifest = Get-Content -LiteralPath (Join-Path $root 'merged/manifest.json') -Raw | ConvertFrom-Json
  $manifest | Select-Object run_id,status,merge_version,classifier_rule_version,fingerprint_version,integrity_status
  $manifest.output_counts
  $manifest.source_shards | Select-Object path,type,current_run_records,foreign_run_records,invalid_json,invalid_schema,exact_duplicates,conflict_duplicates
  if ($manifest.status -ne 'complete') { throw 'P0 manifest is not committed' }
  if (@($manifest.output_hashes.PSObject.Properties).Count -ne 4) { throw 'P0 output hashes are incomplete' }
}
finally { foreach ($name in $names) { [Environment]::SetEnvironmentVariable($name,$old[$name]) } }

11 · Design choice

设计选择与适用边界

现方案按事实类型使用独立身份键，区分精确重复与冲突重复，再用JUnit做独立对账，最终原子提交Manifest。
替代方案直接拼接JSONL，并以“最后一条覆盖前一条”的通用字典完成归并。
选择理由保留来源统计与冲突证据，避免相同身份的不同内容被静默覆盖；Manifest提交点让下游只消费完整快照。
不适用条件单轮事实量大到无法在内存维护状态，或要求跨run持续流式聚合时，需要外部排序、流处理与增量检查点。
