2

Task把“我要做什么”写成业务动作

它接收Request对象和payload，不持有HTTP细节。

module/offline_framework_example/task.py::OfflineFrameworkTask.submit_echo
def submit_echo(
        self,
        request_client: OfflineFrameworkRequest,
        payload: dict[str, Any],
    ) -> requests.Response:
        return request_client.echo(payload)

薄函数仍然有边界价值

输入

业务payload和模块Request实例。

职责

把测试语言“提交Echo”转交给Request语言echo()，不重复协议配置。

不负责

不拼接/v1/echo，不选择POST，也不判断响应是否accepted。

3

Request把业务动作翻译成HTTP协议

路径、method、body位置和运行时元数据在这里被确定。

module/offline_framework_example/request.py::OfflineFrameworkRequest.echo
def echo(self, payload: dict[str, Any]) -> requests.Response:
        return self.post(
            self.echo_path,
            json=payload,
            runtime_metadata=runtime_metadata(
                RuntimeOperationKind.HTTP,
                name="offline_echo",
                role=RuntimeTrafficRole.WORKLOAD,
            ),
        )

这里发生协议翻译

业务名

echo(payload)对上层保持领域可读。

HTTP事实

下层收到POST、echo_path和json=payload。

证据标签

runtime_metadata描述Operation身份；具体消费过程留到后续课程。

4

Assertions把Response解释成领域结论

通用断言被组合成Echo接口的完整成功合同。

module/offline_framework_example/assertions.py::OfflineFrameworkAssertions.assert_echo_accepted
def assert_echo_accepted(
        self,
        response: requests.Response,
        expected_payload: dict[str, Any],
    ) -> requests.Response:
        self.assert_status_code(response, 200)
        self.assert_json_value(response, "$.status", "accepted")
        self.assert_json_value(response, "$.authorization_present", True)
        self.assert_json_value(response, "$.received", expected_payload)
        return response

断言为什么不散落在Test里

传输层

状态码必须是200。

领域层

状态、鉴权存在性和回显payload共同定义“Echo已接受”。

返回原对象

成功后返回同一个Response，便于继续链式核对其他事实。

概念章节现在是第二遍复盘

接下来的“四件套、黄金路径和调用链”不再是需要先背的定义，而是对刚才四段代码的归纳：Test组织、Task表达、Request翻译、Assertions解释。

02 · 模块四件套

先问“为什么会变化”，再决定代码放哪里

点击四件套查看职责、输入输出和禁止事项。这里把 Test 单独作为场景入口；Decorators 是模块稳定身份的一部分，将在第5节解释。

变化信号优先归属本模块中的真实例子判断依据
新增完整用户旅程Test异步媒体黄金流程它要串联多个动作与最终证据。
新增可复用业务动作Task构造媒体payload、提交审计查询动作可被多个场景复用，但不应持有HTTP底层细节。
端点或header变化Request媒体路径、Idempotency-Key、runtime metadata它属于接口协议合同。
“成功”业务定义变化Assertions状态必须为succeeded、审计名称集合相等它把低层字段检查翻译成领域结论。
常见误区Task不是“所有非测试代码”的收纳箱，Assertions也不是发请求后的附属步骤。每层都必须有稳定输入输出，才能让变化局部化。

04 · 调用链与所有权

请求向下执行，响应向上解释

一条清晰调用链必须能同时回答两个问题：动作从哪里发出，结果由谁解释。

Test选择场景
Task组织业务动作
Request描述接口协议
BaseRequest统一HTTP管线
Response返回事实
Assertions解释业务结果
Test拥有场景顺序创建服务、调用Task、组合跨步骤证据、登记cleanup，并断言最终副作用。
Task拥有业务动作build_media_generation_payload()每次返回新字典；create_and_poll_media_generation()直接继承BaseTask，不复制异步算法。
Request拥有协议使用相对路径，选择GET/POST/DELETE，传递payload、headers、RetryPolicy和中性runtime metadata。
BaseRequest拥有执行统一session、鉴权、重试、响应捕获与运行时事件；模块Request只调用公开能力。
Assertions拥有解释复用状态码、JSONPath和Schema公共断言，组合成“任务成功”“审计集合正确”等领域结论。

为什么黄金路径复用BaseTask，而不是在离线Task重写轮询

复制异步流程
两份状态机
修复不同步
模块行为分叉
证据不可比较
第一性原理结论业务模块只提供差异：路径、payload、策略和业务断言；跨模块相同的执行机制只有一个实现源。

06 · Schema与领域断言

一个回答“长什么样”，一个回答“业务是否成立”

Schema和Assertions并非重复校验。它们保护的是不同合同，黄金路径会把两者组合使用。

Schema：结构合同

描述必填字段、类型、常量和嵌套结构。例如创建响应必须包含task_id、status、model、trace_id，且status固定为queued。

response_schemas.py

成功Schema：完整结果

最终响应除公共字段外必须包含result.url，status固定为succeeded。这能快速发现响应形状漂移。

OFFLINE_POLLING_SUCCESS_SCHEMA

领域断言：语义合同

assert_task_id()不仅检查字段存在，还比较是否等于预期任务；assert_task_status()表达任务状态结论。

集合断言：跨响应合同

assert_audit_names()逐个验证响应后，再比较实际审计名称集合与期望集合。

要验证的问题优先工具例子
响应字段与类型是否完整？JSON Schemaresult必须是对象，且包含非空url。
某字段是否等于当前场景的动态值？领域断言最终task_id等于创建阶段提取的task_id。
多个响应组合后是否满足业务集合关系？领域断言两条审计记录的名称集合等于audit-a、audit-b。
是否既要结构稳定又要业务正确？两者组合最终响应先校验成功Schema，再校验task_id和status。
链式使用合同大多数Assertions方法返回传入的原Response。黄金用例用is response确认对象身份没有被替换，后续步骤可继续使用同一个响应。

08 · TOC与归属练习

当前学习约束：会写代码，但需求容易落错层

层级错位不会立刻报错，却会让后续每次变化都扩大回归范围。解除约束的关键是把“需求句子”翻译成“变化原因”。

错误归属的因果链
需求未分类
就近塞进Test
协议与业务耦合
复用开始复制
维护成本放大

决策顺序：先问变化原因，再问输入输出，最后才选具体文件。

需求应该放在哪一层？

选择最主要的归属。真实改动可能涉及多层，但需求的核心责任只有一个起点。

审计接口新增必传header：X-Audit-Source
新增一个可复用的“构造视频生成payload”动作
业务规定成功响应中的模型必须等于提交模型
新增“创建媒体后并发审计，最后删除资源”的端到端场景
把媒体任务查询路径从v1调整到v2

Design Choice · Boundary

设计选择与适用边界：用模块四件套隔离四种变化

现
当前方案

Test组织场景，Task组织业务动作，Request描述协议，Assertions表达领域结果，并沿黄金路径组合。

替
替代方案

在一个pytest函数里直接拼URL、发HTTP、解析字段并写全部断言。

因
选择理由

协议、动作、场景和业务语义的变化频率不同；分层后能缩小回归范围，也能让同一Request或Assertions被多个场景稳定复用。

界
不适用条件

一次性探索脚本且明确不会进入回归体系时可暂不构建四件套；一旦成为公开模块用例，就必须恢复真实类型和稳定入口。

状态结果

通过离线服务完成一次POST，并在运行时记录器中留下HTTP操作与请求组事实。

证据结论

Test负责场景编排和证据组合，不直接实现HTTP发送。

答案边界

不展开BaseRequest内部中间件、Retry或Quality事件。

阅读问题领域响应合同由哪些基础断言组合而成？

    @allure_step("校验离线Echo响应")
    def assert_echo_accepted(
        self,
        response: requests.Response,
        expected_payload: dict[str, Any],
    ) -> requests.Response:
        self.assert_status_code(response, 200)
        self.assert_json_value(response, "$.status", "accepted")
        self.assert_json_value(response, "$.authorization_present", True)
        self.assert_json_value(response, "$.received", expected_payload)

课后总结 · 函数与业务数据流

payload怎样向下，Response怎样向上

一条业务链包含两个方向：调用向下进入公共执行层，含义向上被领域断言解释。

1

Test Arrange / Act

构造payload并调用Task.submit_echo()。

→

业务场景

输入是业务字段；测试只声明要执行Echo，不拥有method和path。

2

Task.submit_echo()

把业务动作委托给模块Request。

→

领域调用

payload不改变；调用语言从“提交Echo”转成request.echo(payload)。

3

Request.echo()

选择POST、路径、JSON body和Operation元数据。

→

HTTP描述

业务数据进入json参数；协议事实交给BaseRequest统一执行。

4

BaseRequest / Session

公共层构造请求上下文并完成HTTP传输。

→

Response事实

下行参数变成一次请求；返回值是尚未被领域解释的Response。

5

Assertions.assert_echo_accepted()

组合状态码与JSON字段断言。

→

领域结论与证据

Response被解释为“Echo接受且未改变payload”；失败时断言指出具体合同位置。

最小记忆单元

四件套不是文件数量约定，而是变化隔离：场景变化留在Test，动作变化留在Task，协议变化留在Request，合同变化留在Assertions。
