WEEK 4 · DAY 16

Runtime Hooks与Quality事实采集

业务请求必须在Quality关闭时照常运行，也必须在观察器故障时保留原响应与原异常。今天沿一条真实请求追踪：中性metadata如何经过Middleware和Runtime Hooks，被Quality Adapter翻译为RequestMetric，并最终写入worker分片。

建议时长 2.5小时先单测后运行级证据核心边界 common -X→ quality证据供第17～19天使用
今日验收：能够解释Noop、Provider、Lease、Observer、Adapter和Collector各自职责，并证明Hook失败只能留下完整性问题，不能改变业务控制流。

01 · Objective

目标与核心约束

1

守住依赖方向

业务和common只认识中性模型，不导入Quality。

2

掌握生命周期

理解Operation、Request Group、Polling与Stream lease。

3

追踪事实翻译

从runtime_metadata走到RequestMetric和JSONL分片。

4

解释失败语义

区分业务失败、观察失败与完整性问题。

TOC约束：观察链最危险的瓶颈是“观察器变成控制器”。如果Hook异常能覆盖response、网络异常或KeyboardInterrupt，测试框架就会开始验证观察系统，而不是被测业务。
业务请求拥有原始结果
→
观察器抛异常诊断路径故障
→
若覆盖业务结果根因被替换
→
测试结论失真观察绑架控制流
中性事件 + Lease归属 + safe call + 完整性记录 = 观察不干预

02 · Dependency boundary

四层观察边界：谁产生事件，谁翻译事实

业务/Task

只提供稳定operation name、kind、role和可选model_id。

common

定义中性模型、Protocol、Noop、Provider和生命周期，不知道质量Schema。

Quality Adapter

把中性事件翻译为Semantic handle与RequestMetric采集动作。

Collector

把Case、Request和Integrity事实写入execution-worker分片。

runtime_metadata业务稳定语义
→
RuntimeObservationMiddleware请求开始/成功/异常
→
common Runtime Hooks中性Protocol
→
QualityRuntimeHooks领域翻译
→
RequestMetric / shard机器事实
不可反向：quality -> common.runtime_hooks，但common -X-> quality。业务用例也不得直接调用Collector或Metrics builder。

03 · Neutral hooks

Protocol定义能力，Noop保证默认可运行，Provider决定当前实现

Models

冻结metadata、outcome和lease；kind包含HTTP、SSE、Polling与Async Task，role区分workload/control。

RuntimeHooks

定义operation、request group、attempt、polling和stream事件，不规定如何存储。

NoopRuntimeHooks

所有方法返回空handle或None，使Quality关闭路径无需条件分支。

Provider

ContextVar默认绑定Noop；enabled worker临时绑定QualityRuntimeHooks。

runtime_metadata

构造中性对象，不导入backend；控制参数在传输前从kwargs移除。

Context传播

线程池必须用submit_with_context，否则worker看见默认Noop，事实失去归属。

runtime_metadata(
    RuntimeOperationKind.HTTP,
    name="create_asset_video",
    role=RuntimeTrafficRole.WORKLOAD,
    model_id=model_id,
)
operation name必须稳定，不能包含request ID、task ID或时间戳；payload中的model可由当前Hooks推断，但显式metadata优先。

04 · Lease ownership

Lease把“开始时的Hooks”带到正确的结束点

Operation lease

保存hooks、native handle、owned和ContextVar token；嵌套operation复用父handle且不重复finish。

Request Group lease

覆盖一次逻辑请求的全部attempt，累积Retry等待并在组结束时收口。

Polling lease

保存状态序列、sleep与success/failure/unknown/timeout结果。

Stream lease

HTTP响应返回后operation detach，lease挂到response，直到消费完成或中断才finish。

用Hooks A开始lease保存A
→
Provider切到B全局当前实现变化
→
仍由A结束不会把半条生命周期交给B
幂等收尾：Observation对象使用_finished防止重复finish；common安全包装器吞掉普通Hook异常，并在finally重置ContextVar。

05 · Request lifecycle

HTTP、Retry、Polling和SSE共享事实骨架，但终态不同

单次HTTPoperation → request group → attempt start → response/exception2xx为operation success，非2xx为failed。
Retry一个request group包含多个真实attempt，每个attempt都有独立request_event_id。503→200记录failed、success两条RequestMetric及总retry wait。
Pollingoperation + polling session + 多个request group/attempt + 状态与sleep。区分failure、unknown、timeout，不把timeout伪装成第五种业务状态。
SSEHTTP成功后绑定stream lease并detach operation。不提前读取body；消费终态为complete/interrupted/error/not_consumed。
默认Middleware顺序：RuntimeObservation → MediaResource → Redaction → Logging。观察开始先保存“本次请求使用的hooks”，成功或异常时继续使用同一实例。

06 · Pytest worker binding

Quality开启后，runtime plugin在当前worker建立事实归属

pytest_configure解析run/execution/worker
→
configure collectorsCase、Request、Semantic分片
→
bind_runtime_hooks绑定QualityRuntimeHooks
→
用例执行case context包围setup/call/teardown
→
pytest_unconfigurefinalize pending并按层重置

Controller与worker

xdist controller传播配置，不写重复case事实；每个gw worker拥有独立collector和分片。

释放顺序

先完成pending semantic，再reset runtime hooks、run context、semantic collector和P0 collector。

初始化失败

逐项回滚已绑定token和collector，再写告警；不得留下半初始化全局状态。

Case context

每个pytest invocation提供case_id与invocation_id；缺失时RequestMetric跳过并记录integrity。

07 · Adapter mapping

QualityRuntimeHooks只做翻译，不重新拥有HTTP控制流

中性事件Quality翻译输出关系
begin/finish operationsemantic_context OperationHandle与Outcome形成逻辑调用边界
start/finish request grouprequest_group_id、attempt关联与retry wait多个attempt归属一个逻辑请求
request started/succeeded/failedrequest_metrics start/response/exception写一条真实attempt的RequestMetric
polling state/sleep/outcomePollingSessionHandle与PollingOutcome状态序列与等待耗时
stream line/outcomestream operation ID与StreamOutcomeSSE消费完整性
双层防护：common生命周期使用safe call防止Hook异常外泄；Adapter捕获request_metrics异常并尽量写request_capture_failed完整性问题。两层都失败时仍不能覆盖业务结果。

08 · Facts and shards

RequestMetric回答“一次真实attempt发生了什么”

身份run、execution、worker、case、invocation、request_event。
接口method、脱敏url_template、interface_id、protocol。
执行attempt_index、status_code、duration、timeout、retryable。
业务success/failed/unknown与error_type。
用量input/output token和明确媒体结果数量；缺失保持None。
服务身份优先响应Header，再读取非SSE body request_id。

每个execution-worker固定三类P0分片

cases-*.jsonl

pytest setup/call/teardown事实与稳定身份。

requests-*.jsonl

每个真实HTTP attempt一条RequestMetric。

integrity-*.jsonl

采集、归属或写入失败的可审计问题。

Collector初始化时按execution_id-worker_id建空分片，写入由RLock保护；主事实写失败会尝试转成ERROR级integrity，warning文本统一脱敏。

09 · Failure semantics

fail-open不是“采集成功”，而是“不改变业务结果”

Hook方法抛异常

common safe call返回默认值或忽略。

原response、网络异常和业务异常保持不变。
request_metrics抛异常

Adapter尝试写request_capture_failed。

完整性问题脱敏，不泄露token。
缺失Case context

不伪造case归属，也不写RequestMetric。

写missing_case_context警告。
分片写入失败

主事实失败后尝试写ERROR级integrity。

最终完整性可能降级，pytest仍由原事实决定。

11 · Knowledge check

知识自测

答对5题视为达标。

1. Quality关闭时get_runtime_hooks()默认返回什么？
答案B。调用方无需为关闭状态写条件分支。
2. operation用Hooks A开始后Provider切到B，谁负责finish？
答案C。生命周期不能跨backend断裂。
3. 503→200重试应产生多少条RequestMetric？
答案A。每次真实HTTP attempt都是事实。
4. 缺少case context时应怎样处理请求事实？
答案B。不能伪造归属，也不能绑架业务。
5. Adapter采集异常时业务response怎样处理？
答案C。观察不拥有业务结果。
6. SSE为什么在HTTP成功后detach operation？
答案A。收到响应头不等于流式调用完成。

12 · Exit gate

本课门禁：观察不能改变被观察对象

一句话验收：common以Noop、ContextVar、lease和safe call提供中性观察；Quality开启后Adapter才把事件翻译为Semantic与RequestMetric，Collector按execution-worker写Case/Request/Integrity分片；任何观察故障只影响证据完整性，不能改写业务响应、异常或pytest事实。
