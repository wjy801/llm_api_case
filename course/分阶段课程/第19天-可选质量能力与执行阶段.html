WEEK 4 · DAY 19

可选质量能力与执行阶段

承接Day18发出的中性事件，Day19只管理Quality接入：Runner依赖QualityRunLifecycle选择disabled、collect-only或enabled画像，在开启后才延迟导入配置、建立运行身份并收口质量阶段；事件如何翻译成采集事实留给Day20。

建议时长 2.5～3 小时NoopLazy LoadingStage Ordering
可核验产出：disabled、collect-only、enabled三路径生命周期图，开关与副作用对照表，以及本轮Quality P0产物核验记录。

01 · First principles

可选能力的首要合同是关闭时不改变主路径

Quality不是Runner执行测试的必要条件。只要关闭Quality仍触发重依赖导入、环境变量注入、JUnit改写或目录写入，它就不再是可选扩展。

关闭

不加载运行时实现，不创建质量目录，不改变pytest参数。

只收集

即使环境开关为真，也不启动执行期采集和归并。

开启

显式建立run、execution和worker身份，按依赖顺序生成事实。

TOC约束：核心约束是可逆性：移除或关闭Quality后，Runner和common仍能独立执行同一批测试。

02 · Execution profiles

先判断执行画像，再讨论Quality行为

画像生命周期对象副作用期望产物
QUALITY_ENABLE=0NoopQualityRunLifecycle无参数、环境和文件变更无Quality目录
Runner collect-only在创建生命周期前返回仅打印收集与分池计划无Quality执行产物
Quality开启正式执行EnabledQualityRunLifecyclerun记录、JUnit、阶段环境、采集与归并run.json、shards、merged等

Quality子能力还有独立开关：Semantic依赖Quality；Metrics依赖Quality与Semantic；Flaky history依赖Quality；Flaky state又依赖history。配置对象把无效组合转换为关闭状态和warning，而不是偷偷执行半条链。

03 · Neutral protocol

Runner只认识四个中性动作

协议方法Runner调用时机中性语义
prepare(start_time)Allure准备后、池执行前建立可选运行身份
ensure_junit_args(args)每个执行池构造参数时需要时补充可对账JUnit
stage_environment(execution_id)包围每个池注入并恢复阶段身份
finalize(...)Runner finally阶段消费已执行池事实并收口

RunLifecycleStatus只有finished、partial和interrupted，描述本轮Runner完成程度；它由Runner映射给Quality的RunStatus，而不是让Quality反向控制pytest。

04 · Factory and lazy loading

先读轻量配置，确认开启后才进入重实现

  1. create_quality_run_lifecycle()首先延迟导入quality.config.load_quality_config。
  2. 配置解析异常或enabled=False立即返回Noop。
  3. 确认开启后再导入resolve_parent_quality_config()，建立父运行配置与run_id。
  4. 运行配置仍未开启时继续返回Noop；只有两次判断都通过才创建Enabled。

稳定插件入口quality/pytest_plugin.py同样保持轻量：collect-only直接返回，关闭时不导入quality.pytest_plugin_runtime，开启后才动态注册quality-runtime。

依赖方向：Runner → 中性生命周期；轻量插件 → 配置预览；只有显式开启后 → Quality运行时实现。

05 · Noop contract

Noop承诺的是零质量副作用

参数不变

ensure_junit_args()返回原参数的列表副本，不擅自添加JUnit。

环境不变

stage_environment()返回nullcontext()，不注入run_id或execution_id。

文件不变

prepare()与finalize()均无写入。

控制流不变

Runner不需要到处判断Quality开关，统一调用协议即可。

Noop不是“空实现凑接口”，而是可选架构的可执行证明：主路径只依赖协议，不依赖质量业务对象。

06 · Enabled lifecycle

Enabled从父运行身份延伸到每个执行池

  1. prepare()写入初始run.json，记录run_id、开始时间和运行配置。
  2. ensure_junit_args()尊重调用者已有--junitxml；缺失时补充output_dir/junit/quality.xml。
  3. stage_environment(execution_id)在上下文中设置QUALITY_RUN_ID、当前池QUALITY_EXECUTION_ID和输出目录，退出后恢复原环境。
  4. finalize()过滤NOT_RUN池，只把实际执行的stage_id和JUnit路径交给质量管线。

同一个run下，parallel-pool与serial-pool共享run_id，但拥有不同execution_id；xdist worker再增加worker_id。三层身份共同决定分片文件名，避免并发写入互相覆盖。

07 · Pytest loading

插件在controller传配置，在worker建立采集上下文

位置实现行为原因
稳定插件入口判断collect-only与开关，动态注册runtime插件关闭时不加载重实现
xdist controller通过pytest_configure_node把运行配置放入workerinputworker使用同一run与execution身份
xdist worker或非并发进程创建RunContext、Collector、可选SemanticCollector并绑定Runtime Hooks事实由实际执行测试的进程拥有
pytest_unconfigure完成pending语义记录，按逆序reset hooks、context与collector防止上下文泄漏到下一次session

collect-only在轻量插件和runtime插件两处都有保护，保证即使环境开关开启，也不会把“收集计划”误当成“执行事实”。

08 · Ordered finalization

先证明P0事实可信，再从同一提交点分叉推导

P0 fact merge→final run record→可信P0分叉

语义指标支线

P0→Semantic→Metrics

Flaky治理支线

P0→Flaky Import→State→Governance

finalize_quality_run()先调用quality_fact_merge_stage。若P0归并返回None，两个高阶分支都短路；只有得到归并结果，才写最终run记录并进入后续阶段。当前代码在final run record后的调用顺序确实是Semantic、Metrics、Flaky Import、State，但调用顺序只是编排顺序，不等于数据依赖：Metrics消费Semantic产物，而Flaky Import直接消费可信P0，State消费导入结果，Governance建立在State之上。

fail-open

生命周期准备、环境或finalize异常被警告，不覆盖pytest退出码。

依赖短路

上游事实未形成时不继续推导，防止产生貌似完整的下游产物。

两者解决不同问题：fail-open保护核心测试控制流，依赖短路保护质量证据可信度。

Design decision

设计选择与适用边界

现方案替代方案选择理由不适用条件
Runner只依赖QualityRunLifecycle，由工厂按执行画像返回Noop或Enabled，并在确认开启后延迟加载重实现。Runner直接导入Quality模块并散布开关判断，或无论是否启用都初始化配置、目录和插件。disabled与collect-only可证明零质量副作用；Enabled集中管理run/execution/worker身份和阶段顺序，接入点单一可替换。若质量能力是法规要求且缺失必须阻止执行，应采用fail-closed的强依赖启动检查，而不是Noop可选合同。

10 · Three-profile practice

用同一离线目标核对关闭、只收集和开启

$python = '.\.venv\Scripts\python.exe'
$root = Join-Path 'reports/course' ('day19-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
$names = @('QUALITY_ENABLE','QUALITY_SEMANTIC_ENABLE','QUALITY_METRICS_ENABLE','QUALITY_OUTPUT_DIR','QUALITY_RUN_ID','GENERATE_ALLURE_REPORT','GENERATE_HISTORY_REPORT')
$old = @{}; foreach ($name in $names) { $old[$name] = [Environment]::GetEnvironmentVariable($name) }
try {
  $env:QUALITY_OUTPUT_DIR = $root
  $env:QUALITY_SEMANTIC_ENABLE = '0'
  $env:QUALITY_METRICS_ENABLE = '0'
  $env:GENERATE_ALLURE_REPORT = 'FALSE'
  $env:GENERATE_HISTORY_REPORT = 'FALSE'

  $env:QUALITY_ENABLE = '0'
  & $python run_master.py module/offline_framework_example --collect-only -q
  if (Test-Path -LiteralPath $root) { throw 'disabled collect-only created quality artifacts' }

  $env:QUALITY_ENABLE = '1'
  $env:QUALITY_RUN_ID = 'course-day19-collect-only'
  & $python run_master.py module/offline_framework_example --collect-only -q
  if (Test-Path -LiteralPath $root) { throw 'enabled collect-only created quality artifacts' }

  $env:QUALITY_RUN_ID = 'course-day19-enabled'
  $allure = Join-Path $root 'allure-results'
  & $python run_master.py module/offline_framework_example -n 2 --alluredir=$allure
  if ($LASTEXITCODE -ne 0) { throw ('Runner exit=' + $LASTEXITCODE) }
  $run = Get-Content -LiteralPath (Join-Path $root 'run.json') -Raw | ConvertFrom-Json
  $manifest = Get-Content -LiteralPath (Join-Path $root 'merged/manifest.json') -Raw | ConvertFrom-Json
  [pscustomobject]@{ RunId=$run.run_id; RunStatus=$run.status; MergeStatus=$manifest.status; Integrity=$manifest.integrity_status; Cases=$manifest.output_counts.case_results }
}
finally { foreach ($name in $names) { [Environment]::SetEnvironmentVariable($name,$old[$name]) } }
