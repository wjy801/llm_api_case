DAY 14 · ONE STABLE ENTRY, ONE PARAMETER AUTHORITY

稳定入口与命令行参数

Runner 的第一职责不是“启动 pytest”，而是把用户意图变成唯一、可解释的参数计划：哪些参数决定编排，哪些参数决定选测，哪些参数只在正式执行生效。

建议 1.5～2 小时前置：完成第2周门禁实践只做离线收集核心：run_master.py / cli.py / pytest_execution.py
完成标志：能解释根入口为何保持薄；能把 target、-n、-k、-m、--ignore、--collect-only 路由到正确层；能画出用户参数到最终 pytest 收集参数和不可变用例计划的转换。

01 · First principles & TOC

参数不是字符串列表，而是用户对执行边界的声明

同一个 -k polling 如果收集时用一次、执行时又解释一次，最终执行集可能随插件、环境和文件变化而漂移。可靠 Runner 必须让选测只发生一次，然后只消费计划。

1

入口稳定

外部只依赖少量公共符号，内部拆分不迫使 Jenkins 和用户改命令。

2

参数有主

编排参数由 CLI 消费，pytest 参数透传后再按阶段分配。

3

选测唯一

target、-k、-m、--ignore 共同进入同一次权威收集。

4

预检无副作用

collect-only 只形成并展示计划，不进入正式执行与质量生命周期。

参数被多层重复解释CLI、Runner、pytest各猜一次
→
收集集与执行集漂移条件或插件行为不一致
→
报告数量无法守恒计划与事实对不上
→
结果不可审计无法回答“为什么跑了它”
TOC 当前约束：不是 pytest 启动速度，而是“参数权威来源”不清。先固定根入口与参数所有者，再讨论第15天的权威收集和并串行集合守恒。

02 · Stable facade

run_master.py 为什么必须薄

它是本地用户和 Jenkins 共同依赖的门牌号。门牌稳定，房间内部才能持续重构。当前根文件只做公共重导出、UTF-8进程默认值和退出码交还。

架构门禁验证什么

# 根入口不得直接导入 pytest 或 quality 实现
薄不等于无价值：根入口冻结的是外部合同和依赖方向。若把收集、Allure、Quality、分池逻辑塞回这里，每个内部变化都会放大成入口变化。

03 · Call flow

从命令行到不可变 nodeid 计划

每一层只做一种翻译。识别到职责所有者，比记住文件名更重要。

run_master.py传入 sys.argv[1:]
cli.mainparse_args + 调 runner.run
argparse框架参数 / pytest余量
partition收集相 / 执行相
pytest collect唯一选择与marker读取
Runner plan最终nodeid/marker
用户输入
→ main(argv)
→ parse_known_args(argv)
→ runner.run(test_path, extra_pytest_args, numprocesses, dist, serial_marker)
→ partition_pytest_args(extra_pytest_args)
→ collect_test_case_items(test_path, collection_args)
→ tuple[CollectedTestCase(nodeid, markers)]
→ 后续执行只消费 nodeid 计划
两个公开入口：命令行走 main(argv)；Python 调用可直接使用 run(test_path, extra_pytest_args, ...)。二者最终进入同一个 Runner，不建立第二套执行逻辑。

04 · Parser boundary

parse_known_args() 划分框架参数与 pytest 参数

框架只声明自己必须拥有的参数；未识别的余量原样交给 pytest 参数规划器。这样不需要复制 pytest 的完整 parser，也能继续支持插件参数。

框架/编排层消费

决定收集根、并发池和串行标记，pytest 不能替 Runner 决定这些。

target--test-path-n / --numprocesses--dist--serial-marker--parallel-first

pytest余量

选择、显示、插件和产物参数先进入 extra_pytest_args，再按收集相和执行相分配。

-k-m--ignore--collect-only-q--alluredir
参数第一所有者为什么最终去向
target / --test-pathCLI定义权威收集根目录。runner.run(test_path=...)
-n / --numprocessesCLI + Runner启用parallel-first并决定worker数。仅并发执行池重新注入pytest。
--distCLI + Runner只对xdist并发池有意义。并发池执行参数。
--serial-markerCLI + scheduling决定哪种marker进入串行池。分池算法，不发给pytest。
--parallel-firstCLI兼容标志；当前传入-n已启用并发优先。不改变额外行为。
-k / -m / --ignorepytest collection必须参与最终用例选择。只进收集相。
-q / 插件未知参数pytestRunner不重写未知插件合同。默认同时进入收集与执行相。
边界代价：框架未知的拼写错误也会透传给 pytest，最终由 pytest 返回 usage error。parse_known_args() 的目标是兼容 pytest 生态，不是静默接受错误。

05 · Target resolution

目标优先级很简单，默认值却可能很昂贵

parsed_args.test_path = parsed_args.test_path or parsed_args.target or "module"。显式选项优先于位置参数；两者都没有时收集整个业务模块目录。

1 · --test-path最高优先级，适合显式配置调用
否则 →
2 · positional target日常命令最简写法
否则 →
3 · module默认收集全部业务模块

显式离线目标

run_master.py module/offline_framework_example --collect-only -q

学习环境推荐。只收集确定性loopback业务用例。

选项覆盖位置参数

run_master.py module/smoke --test-path module/offline_framework_example --collect-only

最终 test_path 是 module/offline_framework_example。

安全门：不要在学习或未授权环境裸跑 run_master.py。默认 module/ 可能包含真实接口、付费调用、账号余额和共享状态场景。当前课程实践必须显式指定离线模块并使用 --collect-only。

06 · Phase partition

同一参数列表为什么必须拆成收集相与执行相

收集相回答“跑谁”，执行相回答“怎么跑、产物写哪”。如果把选择条件再次带入执行相，就出现第二次选测；如果把 Allure/JUnit 参数带入收集相，就可能产生预检副作用。

Collection args

选择条件和通用pytest参数。

-k selected-m smoke--ignore=x-q
collector 自己固定加入 --collect-only -q -o addopts=。

Execution args

产物、xdist和通用pytest参数。

--junitxml=x--alluredir=x--dist=load-q
正式执行前面直接放已计划 nodeid，不再附加 selection args。
类别收集相执行相另存事实设计原因
-k / -m / --ignore / --deselect✓—selection_args唯一选测并写入执行事实。
--junitxml / --alluredir / -n / --dist—✓—只影响执行和产物。
--clean-alluredir—✓—预检不得清理产物。
--collect-only / --co / --collectonly控制位—collect_only=TrueRunner短路，不进入执行池。
未知/插件参数，例如 -q✓✓—不重实现pytest完整parser。

输入

[
  "-q", "-k", "selected",
  "--ignore=tests/ignored",
  "--junitxml=reports/result.xml",
  "--alluredir", "custom-allure",
  "--collect-only",
]

输出计划

collect_only = True
selection_args = (
  "-k", "selected", "--ignore=tests/ignored"
)
collection_args = (
  "-q", "-k", "selected", "--ignore=tests/ignored"
)
execution_args = (
  "-q", "--junitxml=reports/result.xml",
  "--alluredir", "custom-allure"
)

07 · Selection authority

target、选择表达式与marker在一次收集中汇合

pytest 才是 nodeid 和 marker 的权威解释器。Runner 不用文件扫描或正则猜用例；它调用一次 pytest.main() 并通过 collector 插件读取最终 items。

target收集根路径
+
-k / -m关键词与marker表达式
+
--ignore / deselect排除条件
→
pytest items最终nodeid与markers
→
immutable plan执行只消费nodeid

收集器真实调用

固定安全参数--collect-only -q -o addopts=：关闭项目pytest.ini的默认addopts干扰。
用户选择参数*collection_args：包含 -k、-m、--ignore 等。
目标str(test_path)：作为最终收集根放在参数末尾。
插件事实每个 item 记录 nodeid 和 iter_markers() 的 marker 集合；重复 nodeid 直接报错。
守恒前提：正式执行参数是 [*planned_nodeids, *execution_args]，不再放 -k/-m/--ignore。第15天的并串行分池只能划分这份计划，不能重新选测。
三个真实门禁：临时创建两条用例后，-k selected 只收集一条；-m serial 只收集marker用例；--ignore=path 排除指定文件。三者都由权威pytest收集证明。

08 · Safe preflight

--collect-only 是执行前安全门，不是“先跑一遍但不算”

收集成功后 Runner 打印全部 nodeid、并发池数量和串行池数量，然后立即返回 0。短路发生在 Allure 和 Quality 生命周期创建之前。

解析参数识别collect_only
权威收集得到case/marker
分池计算只计算不执行
打印计划总数/parallel/serial
RETURN 0在执行生命周期前停止
不启动业务执行池
不创建Quality run_id
不准备/合并Allure
不写execution-result.json
仍可能失败：collect-only 会真实导入测试模块并执行 pytest 收集钩子；语法错误、缺依赖、配置校验失败或空集合仍返回相应 pytest 退出码。它保证“不执行测试函数”，不保证“任何代码都不导入”。

Design decision

设计选择与适用边界

现方案替代方案选择理由不适用条件
根入口保持薄，CLI用parse_known_args()只消费编排参数，选择条件在一次收集中编译为不可变nodeid计划。把完整argv反复交给pytest，或让CLI、Runner和执行池分别解释target、-k与-m。单一参数权威能证明收集集与执行集一致，未知插件参数仍可透传，collect-only也能在副作用前短路。若入口是进程内服务API而非命令行，应提供类型化调用对象；一次性无编排脚本可简化，但不能再宣称跨阶段计划可审计。

10 · Offline practice

比较完整计划与关键词子集

两条命令都只做收集，不运行HTTP业务。观察第二条如何在同一target上通过 -k polling 缩小nodeid计划，同时保持pool统计自洽。

完整离线业务计划大纲指定
.\.venv\Scripts\python.exe run_master.py module/offline_framework_example --collect-only -q
Polling关键词子集大纲指定
.\.venv\Scripts\python.exe run_master.py module/offline_framework_example -k polling --collect-only -q
补充：入口与参数分相门禁建议
.\.venv\Scripts\python.exe -m pytest tests/test_run_orchestration_public_contract.py tests/test_master_service_parallel_serial.py -q
完整计划应记录

Collected test cases、每条nodeid、Parallel pool cases、Serial pool cases，以及最终“tests collected”。

关键词计划应解释

-k polling 位于 selection_args/collection_args；执行计划只保留被选中的明确nodeid。

当前快照：完整离线计划为 23 项（23 parallel / 0 serial）；-k polling 后为 4 项（4 parallel / 0 serial）。数量用于发现意外丢失，长期合同仍是参数路由正确、计划唯一且集合自洽。
