Code-first walkthrough

从中途断流测试追到异常传播与Response关闭

第一性原理看，流式正确性不是“拿到200”或“读到一行”，而是同一份Response在所有路径上都满足三条守恒约束：真实bytes只被业务链消费一次，原始异常不被改写，资源所有权最终落到明确的close()。

本节真实入口：中途断流故障测试

先看测试要求“同一个异常对象继续抛出且Response已关闭”，再逆向进入SSE请求准入、逐行解码、事件解析与collect聚合。

iter_sse_lines()把网络bytes解码成行，并保留读取异常

这一层只做消费原语：跳过空chunk、UTF-8 replacement解码、观察实际行、识别[DONE]并把每一行yield给业务解析层。

common/streaming.py::iter_sse_lines · 连续源码第15至48行
def iter_sse_lines(response: requests.Response) -> Iterator[str]:
    """Iterate decoded SSE lines while emitting fail-open lifecycle facts."""
    stream_lease = get_stream_lease(response)
    completed = False
    exhausted = False
    try:
        for raw_line in response.iter_lines(decode_unicode=False):
            if not raw_line:
                continue
            line = (
                raw_line.decode("utf-8", errors="replace")
                if isinstance(raw_line, bytes)
                else str(raw_line)
            )
            observe_stream_line(stream_lease, line)
            if line.strip() == "data: [DONE]":
                completed = True
            yield line
        exhausted = True
    except GeneratorExit:
        raise
    except (KeyboardInterrupt, SystemExit):
        finish_stream(stream_lease, RuntimeStreamOutcome.INTERRUPTED)
        raise
    except BaseException:
        finish_stream(stream_lease, RuntimeStreamOutcome.ERROR)
        raise
    finally:
        if completed:
            finish_stream(stream_lease, RuntimeStreamOutcome.COMPLETE)
        elif exhausted:
            finish_stream(stream_lease, RuntimeStreamOutcome.INTERRUPTED)
        else:
            finish_stream(stream_lease, RuntimeStreamOutcome.INTERRUPTED)

bytes到line

输入从哪里来

response.iter_lines(decode_unicode=False)交出原始bytes或字符串chunk。

当前消费什么

空chunk被跳过；非空bytes被解码为SSE文本行。

输出写到哪里

line先进入只观察事实的runtime hook，再yield给collect。

谁负责收口

本函数只收口流终态，不调用response.close()。

异常分支

读取异常先标记ERROR，再用裸raise继续抛出原异常。

def collect_stream_chat_completion_chunks(self, response: requests.Response) -> StreamChatCompletionChunks:
    raw_data_lines: list[str] = []
    chunks: list[dict[str, Any]] = []

    try:
        for line in self.iter_stream_lines(response):
            if not line:
                continue
            self.print_stream_raw_line(line)
            assert line.startswith("data:"), f"Stream chunk should start with 'data:', actual: {line!r}"
            raw_data_lines.append(line)

            data = line.removeprefix("data:").strip()
            if data == "[DONE]":
                break

            try:
                chunk = json.loads(data)
            except ValueError as exc:
                raise AssertionError(f"Stream data chunk is not valid JSON: {data}") from exc

            chunks.append(chunk)

line到event/chunk

输入从哪里来

输入是iter_sse_lines()产出的已解码文本行。

当前消费什么

先验证data事件前缀，再剥离字段名与空白，区分终止事件和JSON数据事件。

输出写到哪里

原始事件行进入raw_data_lines，解析后的业务chunk进入chunks。

谁负责收口

collect拥有聚合状态，也拥有包围整个消费循环的Response关闭责任。

词义区分

网络bytes/chunk、SSE data event、JSON chunk是三层对象，不能混成一个“流块”。

5

中途读取异常没有被collect捕获，因此先执行response.close()，随后原异常继续上抛；只有无异常退出时才执行[DONE]和chunks断言。

最终收口

输入从哪里来

输入可能是完整事件序列，也可能是迭代中途抛出的底层读取异常。

当前消费什么

finally不判断成功失败，只消费当前Response的关闭责任。

输出写到哪里

成功路径返回两个聚合列表；错误路径把原异常交还测试。

谁负责收口

collect是Response资源所有者；runtime hook只记录终态，不能替代close。

终态分支

完整流要求最后一行是[DONE]且至少一个JSON chunk；中途断流则关闭后直接结束于ERROR。

01 · Question

Header成功为什么不等于流式调用完成

普通响应返回时主体通常已经可读；SSE返回的是仍待消费的Response句柄。若此时直接记录成功或让日志预读body，就会丢失真实消费事实。

学习边界：只学习仓库现有SSE实现，不新增协议、不连接真实模型接口；Quality语义留到第19～20天。

04 · Consume

iter_sse_lines只负责安全逐行原语

负责

  • 迭代Response行。
  • 跳过空行。
  • bytes使用UTF-8 replacement解码。
  • 识别data: [DONE]。

不负责

  • 不验证业务JSON字段。
  • 不替用例判断内容正确性。
  • 不伪造终止标记。
  • 不自动关闭Response。

05 · Outcome

终态由真实消费事实决定

事实终态说明
读到[DONE]complete终止标记到达，业务仍需断言内容。
自然耗尽但无[DONE]interrupted连接结束不等于协议完整。
消费者主动停止interrupted保留主动中断事实。
读取抛异常error原异常继续传播。
从未消费not_consumed运行收口时暴露完整性问题。

06 · Ownership

消费方在finally关闭同一个Response

try:
    for line in iter_sse_lines(response):
        if line == "data: [DONE]":
            break
finally:
    response.close()

进入try后的正常完成、断言失败、主动中断和读取错误会经过同一关闭路径；但interrupt在try前提取request ID，Header缺失时可能绕过finally。关闭责任仍属于持有并消费Response的Task或用例。

07 · Boundary

观察不能为了记录而再次消费业务流

诊断逻辑只能接收业务实际读到的行，不能预读、重放或替换原迭代器。观察失败也不能覆盖原始chunk、读取异常或消费者终止事实。

边界：业务消费者决定解析和断言，流式原语提供迭代，资源所有者负责关闭，观察层只记录已经发生的事实。

Design decision

设计选择与适用边界

现方案替代方案选择理由不适用条件
请求层返回未消费的流式Response，消费方逐行读取并在finally关闭同一对象。请求层一次性缓冲全部body后返回列表，或由日志/观察器代替业务方消费。保留背压和到达顺序，能分别证明Header建立、消费终态与资源关闭，观察也不会偷走业务数据。响应体确定很小且无需流式语义时可直接缓冲；调用方无法承担关闭责任时应改用内部封装的上下文管理器。

阅读答案

结论：该迭代器只收口Runtime流终态，不负责关闭Response。机制：见到[DONE]记COMPLETE；无完成标志的耗尽或停止消费记INTERRUPTED，键盘或系统中断先记INTERRUPTED，其他异常先记ERROR并继续抛出。

源码执行依据

取得stream lease，逐行观察并识别[DONE]；异常或finally调用finish_stream收口Runtime终态。

状态结果

更新Runtime stream outcome；函数内没有调用response.close()。

证据结论

iter_sse_lines只收口Runtime stream outcome并传播异常，不拥有Response关闭责任。

答案边界

finish_stream不等于关闭HTTP Response；读取到[DONE]也不能证明连接已关闭。

阅读答案

结论：合法Header进入try后必经finally关闭，但Header缺失可能泄漏Response。机制：request_id在try之前提取，提取断言若先抛错就不会进入finally；只有随后消费或中断路径由finally执行close。
