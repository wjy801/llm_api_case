WEEK 6 · DAY 27

流水线报告事实与多视图

Reporting不重新执行测试。它读取阶段、Runner、JUnit、收集清单与Quality事实，构造一个PipelineReport，再从同一对象生成Markdown、机器JSON和邮件视图。

SourcePipelineReportMarkdownJSONEmail
当日产出：来源优先级表、一个Report到多视图关系图，以及供Day29复用的机器产物矩阵。

CODE · 代码先行精讲

先证明四种视图共享一个PipelineReport，再追来源优先级

Reporting的约束不是模板，而是“唯一结论对象”。阶段状态、Runner退出事实、JUnit统计、Quality/Metrics/Flaky各自有所有者；Reporting只能读取、排序优先级并投影为多种视图。

本节唯一主线：Markdown、JSON与Email共享同一结论

用例文件：tests/quality/test_pipeline_reporting.py；测试函数：test_markdown_machine_summary_and_email_share_one_report；pytest nodeid：tests/quality/test_pipeline_reporting.py::test_markdown_machine_summary_and_email_share_one_report。

先运行这个真实Quality测试python -m pytest -q tests/quality/test_pipeline_reporting.py::test_markdown_machine_summary_and_email_share_one_report
阅读规则先定位report = build_pipeline_report(...)，再看所有Renderer只消费report；任何视图自行重读JUnit都意味着规则复制。

1

测试同时读取机器视图和邮件视图核对同一Report

用例只写一个JUnit输入，随后要求返回对象、JSON、主题和HTML表达同一测试数量与结论。

tests/quality/test_pipeline_reporting.py::test_markdown_machine_summary_and_email_share_one_report · 完整测试函数
def test_markdown_machine_summary_and_email_share_one_report(tmp_path):
    reports = tmp_path / "reports"
    reports.mkdir()
    _write_junit(
        reports / "unit-tests.xml",
        [("tests.test_demo", "test_ok", "passed", None)],
    )

    report = generate_pipeline_summary(
        tmp_path,
        environment=_environment(RUN_FRAMEWORK_TESTS="true"),
        machine_output_path="reports/pipeline-summary.json",
        email_subject_path="reports/pipeline-email-subject.txt",
        email_html_path="reports/pipeline-email.html",
    )

    assert report is not None
    payload = json.loads(
        (reports / "pipeline-summary.json").read_text(encoding="utf-8")
    )
    assert payload["conclusion"] == report.conclusion.value
    assert payload["unit_tests"]["total"] == report.unit_tests.total == 1
    assert "0 失败 / 1 项" in (
        reports / "pipeline-email-subject.txt"
    ).read_text(encoding="utf-8")
    assert "1 总计 / 1 通过 / 0 失败 / 0 跳过" in (
        reports / "pipeline-email.html"
    ).read_text(encoding="utf-8")

合同与证据

输入事实

唯一事实源是JUnit文件与环境开关；测试未让邮件Renderer自行读取XML。

验证

返回的PipelineReport与机器JSON结论、测试总数一致，邮件只验证同一统计的表现形式。

产物

Markdown、JSON、邮件主题和HTML属于同一次生成调用。

失败边界

多文件同时存在不自动证明逐字段一致；该测试冻结关键共享字段和同一对象生成路径。

服务所有权

输入验证

配置关闭时删除陈旧视图并返回None，避免历史报告冒充本轮产物。

状态变化

一次调用只构造一个PipelineReport；后续写文件不再改变结论。

产物所有权

Service拥有Markdown、机器JSON、邮件主题和HTML的原子写入路径。

失败边界

Renderer失败可以由Jenkins兜底，但Reporting不得修改原始stage、JUnit、Quality或Metrics事实。

3

Source Loader按事实所有者读取，并把缺失转换成显式状态

阶段JSON、Runner execution、JUnit、collect文本和Quality目录分别加载，warnings集中归并。

pipeline_reporting/sources.py::load_pipeline_sources · 完整函数
def load_pipeline_sources(
    workspace: str | Path,
    *,
    include_quality: bool = True,
) -> LoadedPipelineSources:
    root = Path(workspace)
    reports = root / "reports"
    warnings: list[str] = []

    try:
        stage_statuses = load_stage_statuses(reports / "pipeline-stage-status.json")
    except (OSError, ValueError, json.JSONDecodeError) as error:
        stage_statuses = {}
        warnings.append(f"阶段状态不可用：{type(error).__name__}")

    unit_tests = load_junit_summary((reports / "unit-tests.xml",), warnings=warnings)
    smoke_paths = tuple(sorted(reports.glob("smoke-tests*.xml")))
    smoke_tests = load_junit_summary(smoke_paths, warnings=warnings)
    smoke_collect = load_collect_summary(reports / "smoke-collect.txt", warnings=warnings)
    execution = load_execution_summary(
        reports / "execution-result.json", warnings=warnings
    )

    quality_sources = LoadedQualitySources()
    if include_quality:
        try:
            from pipeline_reporting.quality_sources import load_quality_sources

            quality_sources = load_quality_sources(
                reports / "quality",
                warnings=warnings,
            )
        except Exception as error:
            warnings.append(f"质量观测数据源不可用：{type(error).__name__}")

    return LoadedPipelineSources(
        stage_statuses=stage_statuses,
        unit_tests=unit_tests,
        smoke_tests=smoke_tests,
        smoke_collect=smoke_collect,
        execution=execution,
        quality_facts_available=quality_sources.facts_available,
        quality_run_id=quality_sources.run_id,
        request_health=quality_sources.request_health,
        retry_health=quality_sources.retry_health,
        interface_timings=quality_sources.interface_timings,
        flaky=quality_sources.flaky,
        warnings=tuple(warnings),
    )
pipeline_reporting/quality_sources.py::load_quality_sources · 完整函数
def load_quality_sources(
    quality_dir: str | Path,
    *,
    warnings: list[str],
) -> LoadedQualitySources:
    quality = Path(quality_dir)
    run_id, manifest, facts_available = _load_quality_facts(quality, warnings)
    request_health = RequestHealth()
    if run_id and manifest:
        request_path = quality / "merged" / "request-metrics.jsonl"
        expected_hash = _mapping(manifest.get("output_hashes")).get(
            "request-metrics"
        )
        if _artifact_hash_matches(
            request_path,
            expected_hash,
            warnings,
            "请求指标",
        ):
            request_health = load_request_health(
                request_path,
                run_id=run_id,
                warnings=warnings,
            )

    metrics_payload = (
        _load_metrics_payload(quality, run_id, warnings) if run_id else None
    )
    retry_health = (
        _retry_health(metrics_payload) if metrics_payload else RetryHealth()
    )
    timings = _interface_timings(metrics_payload) if metrics_payload else ()

    flaky_payload = (
        _load_flaky_payload(quality, run_id, warnings) if run_id else None
    )
    flaky = _flaky_summary(flaky_payload) if flaky_payload else FlakySummary()

来源优先级

输入事实

stage status表示编排选择，execution-result表示Runner执行，JUnit表示测试统计，Quality目录表示观测事实。

验证

Quality、Metrics、Flaky都先走Manifest/Hash准入；不可用分区返回空模型并记录warning。

状态表达

缺文件不自动等于0；Builder据开关、stage status和来源可用性区分NOT_RUN、NO_DATA与FAILED。

失败边界

Source Loader不能根据Markdown或文件名猜成功，也不能让陈旧Quality覆盖本轮未执行状态。

4

Builder集中结论，Renderer只做无副作用投影

build_pipeline_report()生成阶段结果、总评和建议；Markdown/JSON/Email都消费同一不可变对象。

pipeline_reporting/builder.py::build_pipeline_report · 完整函数
def build_pipeline_report(
    context: PipelineContext,
    sources: LoadedPipelineSources,
) -> PipelineReport:
    framework = _test_stage(
        "框架单测",
        "framework_tests",
        context.framework_tests_enabled,
        sources.unit_tests,
        sources,
    )
    collect = _collect_stage(context, sources)
    real_smoke = _test_stage(
        "接口测试",
        "real_smoke",
        context.real_smoke_enabled,
        sources.smoke_tests,
        sources,
    )
    quality = _quality_stage(context, sources, real_smoke.status)
    stages = (framework, collect, real_smoke, quality)
    conclusion = _conclusion(context, sources, stages)
    actions = _actions(context, sources, stages)
    return PipelineReport(
        context=context,
        conclusion=conclusion,
        conclusion_text=_conclusion_text(conclusion, context, sources, stages),
        stages=stages,
        unit_tests=sources.unit_tests,
        smoke_tests=sources.smoke_tests,
        smoke_collect=sources.smoke_collect,
        execution=sources.execution,
        request_health=sources.request_health,
        retry_health=sources.retry_health,
        interface_timings=sources.interface_timings,
        flaky=sources.flaky,
        actions=actions,
        warnings=sources.warnings,
    )

结论与视图

状态变化

Builder是唯一把source facts转换成StageResult、PipelineConclusion和actions的函数。

数据合流

Runner/JUnit与Metrics/Flaky在PipelineReport中汇合，但字段仍保留各自来源语义。

产物所有权

Renderer只读取Report生成文本，无权回写source或改变conclusion。

失败边界

不同视图若出现不一致，应修复共享Report或Renderer，不应新增第二套判断规则。

01 · Question

报告只能解释事实，不能发明事实

阶段状态、pytest退出码、JUnit统计、Quality指标各自回答不同问题。若Renderer各自读取文件，就可能产生多个互相矛盾的结论；项目因此先集中构建不可变Report对象。

边界：本课只运行Reporting帮助与专项测试，不触发Smoke，不把历史reports当作本轮证据。

02 · Source entry

五个模块完成事实到视图的单向转换

合同

pipeline_reporting/contracts.py定义状态、Source摘要与PipelineReport。

来源适配

sources.py和quality_sources.py读取机器事实。

结论构建

builder.py计算StageResult、Conclusion和Actions。

服务与视图

service.py协调，renderer.py生成Markdown。

03 · Call chain

CLI只负责调度一次纯生成流程

环境与开关→PipelineContext→load_pipeline_sources→build_pipeline_report→同一Report→Markdown/JSON/邮件

python -m pipeline_reporting generate通过service.generate_pipeline_summary完成读取、构建和原子写入。

04 · Sources

来源不是平级字段，存在判定顺序

来源回答的问题使用原则
pipeline-stage-status.json阶段是否启用、失败或被阻断显式FAILED/BLOCKED优先。
execution-result.jsonRunner计划、分池与最终退出码接口阶段非零退出码可直接判失败。
JUnit用例总数、失败、错误、跳过用于统计和明细。
smoke-collect.txt收集与并串行分池数量只描述collect-only结果。
reports/quality请求、重试、耗时和Flaky事实仅在接口阶段与Quality都开启时加载。

05 · State semantics

NOT_RUN、BLOCKED与NO_DATA不可混用

NOT_RUN

本轮参数未启用该阶段。

BLOCKED

阶段被前序失败或中断阻止。

NO_DATA

选择了执行，但应有的机器产物不可用。

FAILED表示已得到明确失败事实；PASSED表示已取得足以证明通过的事实。状态语义决定最终PASS/WARN/FAIL，而不是简单看“有没有文件”。

06 · PipelineReport

一个结论对象集中所有判断

PipelineReport保存context、conclusion、stages、测试摘要、执行摘要、请求健康、重试健康、接口耗时、Flaky变化、actions和warnings。Builder只接收已适配的Source模型，不直接操作文件。

结论规则：阶段失败或Jenkins失败得到FAIL；阻断、缺数据、跳过、重试挽救或待治理Flaky通常得到WARN；事实完整且无关注项才是PASS。

07 · Views

Markdown、JSON和邮件共享同一Report

Markdown

面向人阅读完整阶段、统计、行动和警告。

机器JSON

把dataclass与Enum转为可核验结构，保留同一结论。

邮件

主题与HTML压缩为通知视图，链接回详细产物。

Renderer不应再次读取JUnit或Quality；否则“一个事实对象，多种展示”的约束就会失效。

11 · Design choice

设计选择与适用边界

现方案先按来源优先级构造唯一PipelineReport，再从同一对象渲染Markdown、机器JSON和邮件视图。
替代方案每个视图独立读取JUnit、阶段文件和Quality产物，并各自判断状态与结论。
选择理由结论集中在一个领域对象中，可避免人读、机器读和通知渠道因读取时机或规则复制而漂移。
不适用条件超大规模交互式分析、按需切片或持续流式报表需要查询层与投影存储，不能把全部明细塞入单个内存Report。
