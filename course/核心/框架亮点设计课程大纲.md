# 框架亮点设计课程大纲

## 1. 课程定位

这是一门“亮点设计课”，不是完整框架源码课。课程围绕一个核心问题展开：

> 当一次 LLM 业务调用被拆成重试、轮询、并发执行和多份机器产物后，框架怎样仍然形成可信、可解释、可治理的结论？

课程目标是让初学者理解六项关键设计为什么存在、解决什么约束、依赖什么事实、不能保证什么。Task、BaseTask、Capability、Request Client、BaseRequest 等对象只在 10 分钟基线案例中出现，用于建立上下文，不要求学习者追踪完整调用链或记忆文件与函数。

课程不安排离线测试、编码作业、练习关卡或学习门禁。讲解以因果链、对比表、状态边界和真实实现事实为主。

SSE 不进入当前八课与 10 小时主线。其协议终态、读取超时和消费边界由独立的“扩展课：SSE 流式调用的终态与时间边界”承接，建议在第 2 课之后学习，不占第 3～8 课编号。

## 2. 课程总目标

完成课程后，学习者应能够：

1. 解释各项核心亮点解决的真实问题。
2. 说明关键设计机制及其依赖关系。
3. 区分执行事实、质量诊断和报告结论的所有权。
4. 说明每项设计的收益、代价和能力边界。
5. 判断这些设计适用于什么场景。

本课程不以系统掌握全部源码为目标，不要求记忆完整类、函数、文件和调用链，也不展开与亮点设计无直接关系的实现细节。源码仅作为证明设计思路的代表性证据。

## 3. 第一性原理与 TOC 决策

### 3.1 任务本质

接口测试的最终产物不是 HTTP Response，而是一个可复核的事实判定。LLM API 的特殊之处在于，一次用户动作可能对应多次网络发送、多个执行进程和多层派生产物。

~~~text
一次业务动作被拆成多次请求与多份产物
-> 请求成功、业务成功、Case 通过和构建成功不再是同一件事
-> 如果身份、终态或事实来源不清，统计分母就不可信
-> 指标和报告越精细，错误结论反而越像真的
~~~

因此，真正需要解决的问题不是“怎样封装更多请求方法”，而是：

1. 复杂调用怎样正确结束。
2. 并发执行后事实怎样不丢、不重、不串线。
3. 观察能力怎样接入而不控制业务。
4. 原始账本怎样经过有限且明确的信任判断。
5. 网络请求怎样还原为用户关心的业务动作。
6. 单轮结果怎样进入跨运行治理，而不覆盖原始事实。

### 3.2 当前 TOC 约束

当前课程的首要约束是“覆盖面过大”。如果按目录、类和函数逐层讲解，学习者会在真正理解可信账本前消耗大量注意力。

本版采用以下裁剪规则：

- 一个设计问题只占一课，不按实现模块拆课。
- 普通 Chat 只作为 10 分钟基线，不成为独立课程。
- 概念地图压缩成一页，只保留理解六项亮点所需术语。
- Middleware 只解释为什么 Hooks 需要中性接入点。
- Reporting 只用于最终事实所有权收束，不作为独立亮点。
- 源码只承担“证明设计事实”的作用，不承担课程导航主线。

## 4. 核心实现思路与思维导图

框架先为 Retry 与 Polling 定义不同的继续条件、完成条件与时间边界；Runner 再以权威 Case 集合和稳定身份控制并发执行事实；Runtime Hooks 通过中性协议、Noop 和 fail-open 让质量观察旁路接入；worker 记录原始事实后，Aggregator 对 run、Schema、重复冲突、预期 execution、Case 数量和 JUnit identity 进行对账，并为归并结果建立哈希证据；Semantic 在可信请求事实之上恢复 Operation、Request Group 和 Polling Session，Metrics 才能按业务粒度解释耗时与用量；Flaky 独立消费可信 Case 历史，将自动检测、人工治理和执行行为分开；最终报告只汇总这些事实，不反向改写 pytest 或 Jenkins 的结论。

~~~mermaid
flowchart TD
    A[复杂 LLM 业务动作] --> B[正确结束]
    B --> B1[Retry]
    B --> B2[Polling]

    A --> C[可信执行]
    C --> C1[Runner 权威集合]
    C1 --> C2[稳定身份]

    C2 --> D[非侵入观察]
    D --> D1[Runtime Hooks / Noop / fail-open]
    D1 --> E[worker 原始事实]
    E --> F[Aggregator 可信账本]

    F --> G[Semantic 业务分组]
    G --> H[单轮 Metrics]
    F --> I[P0 Case 历史]
    I --> J[Flaky 检测与治理]

    C --> K[事实所有权收束]
    F --> K
    H --> K
    J --> K
    K --> L[PipelineReport 派生视图]
~~~

真实依赖必须记住：Metrics 依赖可信 P0 与 Semantic；Flaky 直接消费可信 P0 Case 历史，不依赖 Metrics。

## 5. 一页术语图

| 术语 | 本课程只需掌握的含义 |
| --- | --- |
| Case | 一次 pytest 用例调用及其最终测试事实 |
| Operation | 用户关心的一次逻辑业务动作 |
| Request Group | 一次请求意图及其全部 Retry Attempt |
| Request Event | 一次客户端发送事件；前置处理失败时可能没有真正联网 |

| P0 | Aggregator 归并后的 Case、Request、Failure 与 Integrity 基础事实层 |
| Semantic | 在可信 P0 请求事实之上恢复业务归属的派生层 |
| Metrics | 基于可信 P0 与 Semantic 计算的单轮指标层 |
| Flaky | 基于可信 P0 Case 历史形成的跨运行检测与治理层 |

对象关系只保留这一张图：

~~~text
Case
└─ Operation
   ├─ Request Group
   │  └─ Attempt / Request Event 1..N
   └─ Polling Session
      └─ Request Group 0..N（正常入场后 N 至少为 1）
~~~

## 7. 课程正文

### 第 1 课：复杂 LLM 调用为什么需要可信事实链

**核心问题**：为什么“请求成功”不能直接推出“测试结论可信”？

**核心实现思路**：

先用普通 Chat 建立最小基线，再逐步加入 Retry、Polling、并发 worker 和派生产物。每增加一种复杂性，就会新增一种事实错位风险，因此框架必须先定义终态与身份，再谈指标和报告。

**10 分钟基线案例**：

~~~text
module Test
-> Task / Capability
-> Request Client / BaseRequest
-> HTTP Response
-> Assertion
~~~

这条链只用于说明“一个简单调用怎样完成”，不展开同名方法、兼容门面和内部函数。随后立即加入复杂性：

~~~text
Retry：一次请求意图对应多次发送
Polling：一次业务动作对应一轮或多轮独立查询
并发：同一轮运行产生多份 worker 事实
~~~

**关键因果链**：

~~~text
执行被拆分
-> 事实需要稳定身份和明确终态
-> 原始账页需要归并与完整性判断
-> 业务语义必须建立在可信事实之上
-> 指标和历史治理才有可靠分母
~~~

**讲解边界**：

- 框架具备某项能力，不代表当前业务模块已经启用。
- 类中存在某个方法，不代表当前调用链实际经过它。
- 本课不讲完整源码链，只建立后续六项亮点共享的问题模型。

**本课收束**：可信不是一个报告字段，而是一条从执行边界到事实来源的因果链。

---

### 第 2 课：Retry 与 Polling 的正确性边界

**核心问题**：两层都会再次发送请求的循环，为什么不能共用一个“成功返回”定义？

**核心实现思路**：

Retry 在同一 Request Group 内重复 Attempt；Polling 正常入场后在同一 Polling Session 内发起一个或多个独立 GET Request Group，每轮 GET 又可以可选嵌套 Retry。首轮 Group 创建前失败时，Session 可以包含零个 Group 并标记不完整。正确性来自明确区分 Session、Group 与 Attempt，并让两层分别拥有继续条件、终态和预算。

| 机制 | 循环单位 | 继续条件 | 完成条件 | 核心时间边界 |
| --- | --- | --- | --- | --- |
| Retry | 同一 Request Group 的 Attempt | Attempt 入场先检查 deadline；已有可重试结果且次数允许时，再检查 `max_elapsed` 与 deadline | 返回最终 Response，或抛最终原始异常 / `RetryDeadlineExceeded` | `max_attempts`、`max_elapsed`、可选外层 deadline |
| Polling | 正常入场后一个或多个独立 GET Request Group | 当前业务状态为 pending 且唯一 deadline 未耗尽 | success 返回；failure、unknown、timeout 或原始异常退出 | 各轮 GET、GET 内 Retry 与 Polling sleep 共用 `poll_get` 总预算 |

POST 可通过 `allowed_methods`、`allow_post=True` 或 `Idempotency-Key` 获得客户端重试资格，但客户端不能证明服务端幂等。Retry 有两个 deadline 检查点：Attempt 入场前先检查 deadline；只有已有可重试结果后的继续准入，才按 `max_elapsed → deadline` 判断。任一检查点抛出的 `RetryDeadlineExceeded` 都会在 Polling 内转换为 `PollingTimeoutError`。

Polling 的通用 `result_json_path` 默认为 `None`；`$.result.urls` 只属于媒体默认策略。各轮 GET、GET 内 Retry 及 Polling sleep 共用同一 deadline；`poll_timeout=None` 回退到 `config.timeout`。创建任务 POST 在进入 `poll_get` 前完成，成功后的可选结果下载也不属于该 deadline。

**必要实现证据**：方法资格与默认策略由 `common/retry.py` 决定；Retry 出口顺序由 `common/retry_executor.py` 决定；Polling 状态与媒体策略由 `common/polling.py` 区分；总循环由 `BaseRequest.poll_get` 管理。这里只用模块级精简教学代码证明整体转换，不做逐函数导读。

**设计优点与代价**：

- 优点：瞬时请求故障与异步业务等待各自拥有可解释终态。
- 代价：两层预算和异常转换必须按真实顺序讲解，错误接入仍可能绕过保护。

### 第 3 课：Runner 权威执行与稳定身份

**核心问题**：并行与串行混合执行时，怎样证明 Case 没有丢、没有重复、也没有串到别的运行？

**核心实现思路**：

Runner 先形成权威 Case 集合，再派生并行池与串行池；Quality 随后用五级身份标记每条事实。权威集合解决“谁应该执行”，稳定身份解决“这条事实属于谁”，两者是一条连续因果链。

**集合守恒**：

设权威 Case 集合为 C，并行池为 P，串行池为 S：

~~~text
P ∩ S = ∅
P ∪ S = C
~~~

只比较数量不能证明集合守恒，必须比较 nodeid 集合。每个池还要保留原始 pytest 退出码，Quality 或报告不能覆盖它。

**五级身份**：

| 身份 | 解决的问题 |
| --- | --- |
| run_id | 事实属于哪一轮运行 |
| execution_id | 事实来自哪个执行池或阶段 |
| worker_id | 事实由哪个 pytest worker 写出 |
| case_id | 跨运行比较时是哪一个稳定 Case |
| invocation_id | 本轮具体参数化调用是哪一次 |

**从身份到原始账页**：

~~~text
权威 Case 集合
-> execution 与 worker 分配
-> Case / Request / Integrity JSONL 分片
-> JUnit identity properties
-> Aggregator 才能按身份对账
~~~

**设计优点与代价**：

- 优点：并发事实可以归属，池执行和最终退出事实可以审计。
- 代价：身份规则必须长期稳定，参数、环境和执行画像需要明确边界。

### 第 4 课：Runtime Hooks 的非侵入观察

**核心问题**：Quality 怎样看到请求与轮询生命周期，却不成为业务请求的硬依赖？

**核心实现思路**：

common 只依赖中性的 Runtime Hooks 协议，默认使用 Noop；Quality 开启时才绑定 Adapter。Middleware 在这里仅承担“提供统一中性接入点”的作用，不展开请求复制、日志、Header 或完整中间件生命周期。

**依赖方向**：

~~~text
quality -> common.runtime_hooks
common -X-> quality
~~~

**三个设计支点**：

1. Protocol：业务核心只认识观察接口，不认识质量实现。
2. Noop：Quality 关闭时调用仍成立，但不创建质量身份和产物。
3. fail-open：观察故障不替换业务 Response、原始异常或 pytest 结果。

**为什么需要 lease**：

Operation 和 Polling 可能跨越多次函数调用。开始和结束必须由同一 Hooks 实例负责，否则运行中切换 provider 会让生命周期无法闭合。lease 保存开始时的观察者和结束责任。

**准确边界**：

- 当前保证：观察故障不覆盖业务 Response、原始异常或 pytest 结果。
- 当前边界：通用 Hook 安全层本身会静默吞掉回调异常；Quality 的 Request 与 Semantic 路径会对多类已知采集失败尽力记录 Integrity，但不能保证所有 Hook 异常都有可见证据。
- 改进目标：让所有观察故障都具有可见的 Integrity 证据；这不是当前实现已经提供的保证。
- 裸线程切换可能丢失上下文归属，因此并发传播也是身份正确性的一部分。

**设计优点与代价**：

- 优点：Quality 可选，common 与 quality 可以独立演进。
- 代价：Protocol、Noop、Adapter、上下文传播和生命周期收口增加抽象成本。

### 第 5 课：Aggregator 与可信账本

**核心问题**：worker 文件已经存在，为什么还不能直接计算成功率？

**核心实现思路**：

JSONL 分片只是原始账页。Aggregator 负责在有限边界内检查身份、结构、重复冲突、预期 execution、Case 数量和 JUnit 对账，再输出带 manifest 与 integrity status 的 P0 基础事实。它不是简单 concat，也不能声称检查了实现中不存在的条件。

**实际归并边界**：

Aggregator 明确处理：

- 过滤当前 run，校验 JSON 与 Schema。
- 折叠完全相同的重复记录，暴露同身份冲突。
- 检查每个预期 execution 是否至少存在 Case 分片。
- 核对 expected Case count、JUnit identity 与状态兼容性。
- 派生 FailureRecord，原子写 merged 产物。

Aggregator 不保证：

- 发现每个 worker 的所有缺失分片。
- 在归并前把源分片 SHA256 与某个预期值比较。

**哈希的真实时点**：

~~~text
扫描源分片
-> 计算并记录源分片当前 SHA256
-> 不进行预期源哈希比对

写完 merged 输出
-> 生成 output SHA256
-> Semantic、Metrics、Reporting 等下游消费前验证
~~~

**两种状态不能混淆**：

- `manifest.status=complete`：归并流程完成并提交输出。
- `integrity_status`：归并结果被判断为 COMPLETE、DEGRADED 或 FAILED。

流程成功完成，仍然可以得出“账本不可信”的 FAILED 判断。

**设计优点与代价**：

- 优点：错误 run、坏 Schema、身份冲突、数量不符和 JUnit 不一致不会被静默统计。
- 代价：不能把“记录哈希”夸大为“验证全部来源”；Schema、manifest 和版本需要长期维护。

### 第 6 课：Semantic 与业务指标

**核心问题**：为什么统计 HTTP 次数，不能回答一次异步图片生成真实花了多久？

**核心实现思路**：

P0 Request Event 是客户端发送边界事实；前置处理失败时，它不保证已经真正联网。Operation 才是用户关心的业务事实。Semantic 先用 Request Group 和 Polling Session 恢复请求归属；Metrics 再在正确业务粒度上计算耗时、用量和重试效果。Semantic 不是可选美化，而是 Metrics 获得正确分母的前提。

**业务分组示例**：

~~~text
异步图片 Operation
├─ 创建任务 Request Group
└─ Polling Session
   ├─ 查询 Request Group 1
   ├─ 查询 Request Group 2
   └─ 查询 Request Group 3
~~~

Retry Attempt 归入同一个 Request Group；Polling Session 正常入场后归入一轮或多轮查询，首轮 Group 前失败时可为零并标记不完整；创建与轮询再归入同一个 Operation。

**依赖顺序**：

~~~text
可信 P0 Request facts + Semantic shards
-> Semantic 引用与身份验证
-> Operation / Request Group / Polling Session

可信 P0 + Semantic
-> Metrics
~~~

**指标只保留四种必要粒度**：

- Case：本轮测试结果。
- Operation：用户业务动作。
- Request Group：一次请求意图及其 Retry。
- Request Event：一次客户端发送事件；前置处理失败时可能没有真正联网。

**零、未知和不适用**：

~~~text
known zero       已确认值为 0
unknown          应该有值，但当前未知
no_data          没有可用样本
not_applicable   当前对象不适用该指标
~~~

缺少 Token、媒体数量或 timing 不能自动写成 0；平均值也必须和样本数、completeness 一起解释。

**设计优点与代价**：

- 优点：指标能够解释一次业务动作，而不是只数 HTTP 请求。
- 代价：标准入口和上下文归属必须被遵守，缺失语义时只能降级而不能猜测。

### 第 7 课：Flaky 检测和治理

**核心问题**：一个 Case 今天失败，为什么不能马上标记为 Flaky？

**核心因果链**：

~~~text
单次失败只描述本轮
-> Flaky 需要可比较的跨运行历史
-> 连续同一失败可能是稳定产品缺陷
-> 只有结果签名发生有证据的切换，才进入疑似或确认
-> 自动检测、人工治理和执行行为必须分层
~~~

**事实来源**：

Flaky 直接消费可信 P0 Case 历史，不依赖 Metrics，也不要求先经过 Semantic。结果签名只需要表达：

- `pass`
- `fail:{failure_id}`

**三层职责**：

| 层次 | 当前职责 | 不能混入的职责 |
| --- | --- | --- |
| 自动检测 | 根据历史产生 OBSERVING、STABLE、SUSPECTED、CONFIRMED | 不自动决定是否跳过 Case |
| 人工治理 | 记录隔离、恢复、owner、reason、expiry 和审计信息 | 不伪装成自动检测结果 |
| 执行行为 | pytest 按 Runner 计划执行 | `QUARANTINED` 当前不会自动跳过用例 |

**为什么仍需要持久化**：

跨运行历史必须保存 Observation、当前 Projection、Transition 和 Governance，才能回答“状态为什么变化”。SQLite、事务、Migration checksum 和 Epoch 是实现长期审计所付出的工程成本，本课只说明其设计作用，不展开 repository、迁移脚本或内部函数。

**设计优点与代价**：

- 优点：稳定失败与不稳定失败得到区分，检测与治理责任清楚。
- 代价：只有积累足够历史后才有价值，持久化与规则版本需要维护。

### 第 8 课：事实所有权、能力边界与设计取舍

**核心问题**：当 Runner、JUnit、Quality、Metrics、Flaky 和 Jenkins 都有结论时，谁有权决定什么？

**核心实现思路**：

最终收束不是再增加一个“总控制器”，而是明确事实所有权。Pipeline Reporting 读取并呈现已有事实，Markdown、JSON 和邮件共享同一个派生模型；它不能把诊断层变成第二套测试结论。

**事实所有权表**：

| 事实 | 所有者 | 回答的问题 | 下游权限 |
| --- | --- | --- | --- |
| 收集、执行及原始退出码 | pytest | 哪些 Case 被收集和执行、pytest 进程怎样退出 | Runner 读取，不改写 |
| 权威计划、分池、池结果及项目级 `final_exit_code` | Runner | 本轮怎样编排，以及项目级执行事实是什么 | Reporting 读取，不改写 |
| Jenkins build 与 stage status | Jenkins | CI 阶段和构建结果是什么 | 作为外部事实读取 |
| JUnit | pytest JUnit 产物 | Case 数量、状态和错误证据 | 对账与展示，不覆盖退出码 |
| P0 / Metrics / Flaky | 各质量模块 | 完整性、单轮指标和跨轮治理 | 作为可选诊断，失败时局部降级 |
| PipelineReport | pipeline_reporting | 怎样统一呈现上述来源 | 生成派生视图，不制造第二套事实 |

Semantic 是 Metrics 的上游业务分组与证据层，主要经 Metrics 间接进入 Pipeline Reporting；它不是与 Metrics 并列的直接报告结论来源。

**五条能力边界**：

1. 框架能力不等于当前模块已经启用。
2. 方法存在不等于真实调用链经过。
3. 客户端允许 POST 重试不等于服务端保证幂等。
4. fail-open 只保证不覆盖业务事实，不代表观测成功；当前仍可能发生静默诊断降级。
5. 数据缺失不等于数值为 0。

**六项亮点的整体取舍**：

| 亮点 | 主要收益 | 主要代价或边界 |
| --- | --- | --- |
| Retry / Polling | 复杂调用具有明确终态和预算 | 策略必须由业务入口正确接入 |
| Runner 与稳定身份 | 并发事实可归属、可对账 | 身份和集合合同需要长期稳定 |
| Runtime Hooks | Quality 可选且不控制业务 | 部分观察故障可能静默降级，需要额外可见性治理 |
| Aggregator | 原始账页经过有限信任判断 | 不验证所有 worker，也没有预期源哈希 |
| Semantic / Metrics | 指标理解业务动作并保留 completeness | 依赖标准入口和可信上游 |
| Flaky | 跨运行检测与人工治理可审计 | 不自动跳过用例，历史存储有维护成本 |

**适用场景判断**：

| 判断 | 典型场景 |
| --- | --- |
| 适合 | 异步 API；存在重试计费风险；需要并发执行、机器证据审计或跨运行治理 |
| 可能过重 | 少量同步 CRUD；一次性接口脚本；无并发且不需要历史质量治理 |

**Pipeline Reporting 的准确位置**：

~~~text
上游事实
-> PipelineReport 派生视图
-> Markdown / JSON / Email

PipelineReport -X-> 改写 pytest、Jenkins 或 P0
~~~

**最终收束**：

> 这套框架的亮点不是拥有更多封装，而是让复杂执行先正确结束，让并发事实可归属，让观察保持非侵入，让账本经过有边界的信任判断，再把可信事实解释成业务指标和长期治理信息。
