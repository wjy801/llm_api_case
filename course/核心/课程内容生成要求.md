# 课程内容生成要求

## 1. 内容依据

1. 基于用户指定文档和仓库当前实际代码讲解。
2. 不脱离当前实现自由发挥，不把规划中的能力写成已经落地的事实。
3. 必须区分：
   - 框架具备的能力。
   - 当前业务模块实际启用的能力。
   - 类中存在的方法。
   - 当前用例真正调用的方法。
4. 真实调用关系以源码为准，不能只根据文件名、类名或同名方法推断。

## 2. 目标学习者

1. 面向初学者设计，不要求预先学习项目其他课程。
2. 新概念必须在第一次使用前得到解释。
3. 先使用通俗语言和场景建立直觉，再回到准确的代码对象。
4. 不假设学习者已经理解 pytest 插件、ContextVar、JSONL、JUnit、状态机或 SQLite。

## 3. 内容组织顺序

课程必须遵循以下渐进顺序：

~~~text
业务场景与问题本质
-> Retry、Polling、SSE 的正确性边界
-> Runner 权威集合与稳定身份
-> Runtime Hooks 非侵入观察
-> Aggregator 可信归并
-> Semantic 与 Metrics 的业务分组
-> Flaky 历史治理
-> 事实所有权与设计取舍
~~~

不能从 Metrics、Flaky 等下游模块直接开始，也不能按源码目录从头到尾机械讲解。普通 Chat 只作为 10 分钟基线，术语只保留一页，Middleware 和 Reporting 不占独立课次。

## 4. 思考与分析要求

1. 使用第一性原理解释为什么需要当前设计。
2. 先识别目标障碍，再把障碍转化为真正需要解决的问题。
3. 原因分析至少形成清晰因果链，避免只罗列功能。
4. 使用 TOC 识别当前最大的理解约束。
5. 每次只引入解除当前约束所必需的新对象，避免概念一次性涌入。
6. 先讲事实来源，再讲指标和结论。

## 5. 讲解要求

每项亮点应先提供一段核心实现思路摘要，再展开以下内容：

1. 设计目标和适用场景。
2. 当前实现解决的具体问题。
3. 从障碍到设计的因果链。
4. 必要对象、依赖方向和事实所有权。
5. 正常终态、失败出口和能力边界。
6. 降级、缺失和异常时的行为。
7. 设计优点、缺点和工程代价。
8. 一至三个能够证明设计事实的最小代码锚点；不展开源码导航。

## 6. 实践形式限制

1. 不设计离线测试。
2. 不设计练习、作业或代码提交任务。
3. 不设计学习门禁或验收标准。
4. 不以执行命令或完成活动作为课程目标。
5. 课程只负责尽可能把设计问题、因果链、事实边界和取舍讲明白。
6. module 真实业务模块只用于建立基线或说明边界，不作为逐文件讲解主线。

## 7. 可视化与最小代码证据

1. 提供整体思维导图或依赖关系图。
2. 复杂生命周期、状态变化和事实流转应使用适合的流程图。
3. 代码只用于证明关键设计事实，不要求每课列文件、类和函数。
4. 不设计原文章节映射、持续源码主线、核心文件索引或完整源码复述。
5. 图示必须反映真实依赖，不能为了整齐把并行分支画成错误的串行关系。

## 8. 必须保持的架构事实

1. Semantic 依赖可信 P0 事实。
2. Metrics 依赖可信 P0 与 Semantic。
3. Flaky 直接消费可信 P0 Case 历史，不依赖 Metrics。
4. Pipeline Reporting 汇总 Runner、JUnit 和可选质量事实，不改写上游结论。
5. common 只依赖中性的 Runtime Hooks，不反向依赖 quality。
6. Quality 关闭时使用 Noop，不应创建新的质量身份和产物。
7. Quality、Metrics 和 Flaky 只提供诊断，不能覆盖 pytest 或 Jenkins 的原始事实。
8. manifest 提交状态与 integrity status 是两个不同维度。
9. 缺失数据不能按零值解释。
10. 单次失败不能直接认定为 Flaky。
11. POST 在 allowed_methods 中、allow_post=True 或存在 Idempotency-Key 都可以获得客户端重试资格，但客户端不能保证服务端幂等。
12. Aggregator 记录源分片哈希，merged 输出完成后才生成 output SHA256；它只明确检查预期 execution 的 Case 分片。
13. Flaky 自动检测、人工治理和执行行为必须分层；QUARANTINED 当前不会自动跳过用例。
14. `poll_get` 总预算只覆盖各轮 GET、GET 内部 Retry 和 Polling sleep；创建任务 POST 在进入 `poll_get` 前完成，不属于该 deadline。
15. fail-open 当前只保证观察故障不覆盖业务事实；通用 Hook 安全层会静默吞掉逃逸异常，Quality 的 Request 与 Semantic 路径会对多类已知采集失败尽力记录 Integrity，但不能保证所有 Hook 异常都有可见证据。
16. pytest 拥有收集、执行和原始退出码；Runner 拥有权威计划、分池、池结果保存及项目级 final_exit_code。
17. Semantic 主要作为 Metrics 的上游业务分组与证据层，经 Metrics 间接进入 Pipeline Reporting，不应描述为并列的直接报告结论来源。

## 9. 核心知识范围

课程内容只覆盖理解六项亮点所需知识：

- 一页术语图：Case、Operation、Request Group、Request Event、Polling Session、P0。
- Retry、Polling、SSE 的循环单位、终态、预算和客户端幂等边界。
- Runner 权威集合、并行/串行集合守恒、pytest 退出事实和五级身份。
- Runtime Hooks、Noop、Adapter、lease、ContextVar 与 fail-open 边界。
- worker 原始分片，以及 Aggregator 对 run、Schema、冲突、数量、JUnit 和哈希的实际处理边界。
- Semantic 业务分组、Metrics 四种粒度及 completeness。
- known zero、unknown、no_data 和 not_applicable。
- Flaky 结果签名、跨运行历史、自动检测、人工治理和执行行为。
- pytest、Runner、Jenkins、JUnit、质量事实和 PipelineReport 的所有权。

不展开 RequestContext、Header、脱敏、Allure 内部生命周期、SQLite repository、迁移脚本、完整函数调用链或全目录源码阅读。

## 10. 推荐课程结构

课程最多 8 课，总时长控制在 10 小时左右：

1. 复杂 LLM 调用为什么需要可信事实链。
2. Retry、Polling、SSE 的正确性边界。
3. Runner 权威执行与稳定身份。
4. Runtime Hooks 的非侵入观察。
5. Aggregator 与可信账本。
6. Semantic 与业务指标。
7. Flaky 检测和治理。
8. 事实所有权、能力边界与设计取舍。

## 11. 输出风格

1. 专业、准确，但不过于学术。
2. 避免官话、套话和纯概念堆砌。
3. 先说结论，再解释原因和实现。
4. 通俗类比只能用于建立直觉，最终必须回到准确代码对象。
5. 复杂概念用短句、因果链、表格或图示表达。
6. 每课都要有清晰主线，不能成为孤立模块介绍。
7. 明确说明当前实现事实、设计意图和未来扩展建议之间的区别。

## 12. 最终总线

课程最终应能用以下设计主线复述六项亮点：

~~~text
复杂调用先获得明确终态
-> Runner 权威集合与稳定身份保护执行事实
-> Runtime Hooks 非侵入地产生旁路观察
-> worker 原始账页进入 Aggregator 有限信任判断
-> 可信 P0 与 Semantic 形成单轮 Metrics
-> 可信 P0 Case 历史独立进入 Flaky 治理
-> 事实所有权约束最终派生视图
~~~

最终目标不是让学习者记住大量文件名，而是让其理解每项亮点为什么存在、解决什么约束、依赖什么事实、不能保证什么，以及失败或缺失时怎样保持结论可信。
