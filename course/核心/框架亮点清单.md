# API 测试框架亮点清单

## 一句话定位

这不是单纯的 HTTP 请求封装，而是一套面向 LLM API 的可信测试事实生产线：先约束复杂执行，再保护事实归属，最后形成可解释、可治理的质量信息。

## 第一性原理判断

一次 LLM 业务调用可能包含重试、异步轮询和并发 worker。如果没有明确终态、稳定身份和事实边界，会形成以下因果链：

```text
一次业务动作产生多次请求与多份产物
-> 事实可能重复、缺失或串线
-> 指标失去可靠分母
-> 报告无法形成可信结论
```

框架真正解决的核心约束不是“能否发送请求”，而是“复杂执行结束后，事实是否仍可归属、可核对、可追溯”。

## 六项核心亮点

优先级含义：S 表示对外核心价值，A 表示支撑这些价值成立的设计。该标记用于表达价值层级，不代表教学先后；课程按依赖关系从 A 级支撑设计逐步进入 S 级核心价值。

| 优先级 | 亮点 | 当前实现能够承诺的价值 | 对应课程 |
| --- | --- | --- | --- |
| S | 可信质量账本 | Worker 独立记录事实分片；归并时校验当前 run、Schema、重复冲突、预期 execution 的 Case 分片、预期 Case 数量和 JUnit identity；记录源分片哈希，归并完成后为输出生成 SHA256，供下游消费前验证 | 第 5 课 |
| S | LLM 业务语义指标 | 用 Operation、Request Group、Polling Session 和 Request Event 区分业务动作与发送事件；解释异步轮询、重试挽救及 Token/媒体用量 | 第 6 课 |
| S | Flaky 检测与治理 | 自动检测、人工治理和执行行为分层；可信 Case 历史通过持久化与审计支持长期治理，`QUARANTINED` 当前不会自动跳过用例 | 第 7 课 |
| A | 非侵入式质量观测 | 请求核心只依赖中性 Runtime Hooks；Quality 关闭时使用 Noop，观察异常采用 fail-open，不覆盖业务响应、原始异常或 pytest 结果 | 第 4 课 |
| A | 有正确性边界的 Retry/Polling | Retry 方法资格、结果资格和两个 deadline 检查点显式化；Polling 使用业务状态机与唯一 deadline，降低重复提交与无界等待带来的计费风险 | 第 2 课 |
| A | 单一权威执行事实 | Runner 先形成权威 Case 集合，再划分并行与串行池；五级身份支持 worker 事实归属，并保留 pytest 原始退出事实 | 第 3 课 |

SSE 不映射到第 2 课或当前八课主线；其协议终态、读取超时与消费边界由独立扩展课“扩展课：SSE 流式调用的终态与时间边界”承接。

## 必须保留的能力边界

1. 框架具备某项能力，不等于当前业务模块已经启用。
2. 类中存在某个方法，不等于当前用例真实调用链经过该方法。
3. POST 在 `allowed_methods` 中、`allow_post=True` 或存在 `Idempotency-Key` 都可以获得客户端重试资格；服务端是否真正幂等仍由外部契约决定，因此只能降低重复计费风险。
4. Aggregator 只明确检查预期 execution 的 Case 分片，不保证发现每个 worker 的全部缺失分片。
5. 源分片 SHA256 在归并时主要用于记录；merged 输出写完后才生成 output SHA256，由 Semantic、Metrics、Reporting 等下游消费前验证。
6. Flaky 直接消费可信 P0 Case 历史，不依赖 Metrics；治理隔离当前不会自动改变 pytest 选例。
7. fail-open 不等于诊断事实完整；通用 Hook 异常仍可能静默降级。
8. Semantic/Metrics 依赖标准入口和上下文传播；缺失数据不能按零解释。

## TOC 讲解顺序

先用总览建立“可信事实链”问题，再依次讲复杂调用终态、Runner 与身份、Runtime Hooks、Aggregator、Semantic/Metrics 和 Flaky，最后用事实所有权与设计取舍收束。普通 Chat、Middleware 和 Reporting 只承担辅助说明，不再占用独立课次。
