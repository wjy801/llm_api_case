# 框架亮点设计零基础详解

## 1. 这份文档要讲清楚什么

这份文档不把框架亮点拆成孤立功能，也不要求先学习原有课程。它直接从 module 目录中的真实业务模块出发，沿一次调用实际经过的代码，解释框架为什么要这样设计、每层解决什么问题、事实如何流动、设计有什么收益和代价。

全文围绕六个最有辨识度的亮点展开：

1. Retry、Polling 与 SSE 不是循环技巧，而是有正确性边界的执行语义。
2. Runner 先形成唯一权威计划，再进行并行和串行调度。
3. Runtime Hooks 让 Quality 成为旁观者，而不是请求主链的控制者。
4. pytest worker 先写原始账本，Aggregator 再判断账本能不能信。
5. Semantic 和 Metrics 按 LLM 业务调用理解数据，而不是只统计 HTTP 次数。
6. Flaky 不止做识别，还形成历史、状态、隔离、恢复和审计闭环。

初学者只需要先记住一句话：

> 这个框架的核心不是“发出更多请求”，而是让复杂请求执行后仍能得到可信、可解释、可治理的结论。

## 2. 第一性原理：为什么普通接口框架不够

### 2.1 普通同步接口的最小模型

最简单的接口测试可以表示为：

~~~text
发送一次请求
-> 得到一次响应
-> 断言状态码和响应体
-> pytest 给出通过或失败
~~~

如果所有接口都是同步、无状态、无计费、无需并发，这种模型已经足够。

### 2.2 LLM API 改变了问题

LLM、图片和视频接口通常同时具备以下特征：

- 一次业务动作可能包含创建请求和多次状态查询。
- 流式响应在收到 HTTP headers 后仍未结束。
- 429、503 或网络超时可能需要重试。
- POST 重试可能造成重复生成和重复计费。
- 并行 worker 会同时产生用例、请求和附件事实。
- Token、媒体数量和生成时长可能只在部分响应中出现。
- 同一个用例今天失败，不代表它就是 Flaky。

由此产生一条关键因果链：

~~~text
一次业务动作被拆成多个网络事件
-> 网络事件又分散到不同 worker 和不同产物
-> 如果没有稳定身份和完整性校验
-> 请求次数、成功率、耗时和用量都会被错误解释
-> 报告虽然有数字，但数字未必可信
~~~

### 2.3 TOC 视角下的真正约束

系统的瓶颈不是请求发送速度，而是“事实可信度”。因此整个框架按下面的约束顺序组织：

~~~text
先保证请求执行有明确边界
-> 再保证用例调度有唯一计划
-> 再给每条事实稳定身份
-> 再验证事实完整可信
-> 最后才计算指标和历史状态
~~~

如果顺序颠倒，例如在分片缺失时直接计算成功率，后面的 Metrics 和 Flaky 做得越复杂，错误结论反而越像真的。

## 3. 核心实现思路

框架先由 BaseRequest、RetryExecutor、PollingPolicy 和 SSE 消费器定义单次请求、重复尝试、异步查询和流式消费的正确出口；Runner 通过一次权威 pytest 收集形成完整 Case 集合，再划分并行池与串行池并保存原始退出事实；common 只调用中性的 Runtime Hooks，Quality 关闭时由 Noop 接收这些调用，开启时才由 QualityRuntimeHooks 把事件映射为质量事实；pytest 插件为 run、execution、worker、case 和 invocation 建立身份，并让每个 worker 独立写 Case、Request、Integrity 账本；Aggregator 对分片、JUnit、Schema、数量、身份和哈希进行核对，形成带完整性状态的可信 P0 事实；Semantic 再把 Retry Attempt、Polling Session 和 Stream 生命周期还原成 Request Group 与 Operation；Metrics 只消费经过验证的 P0 与 Semantic 产物，并明确区分零值、未知、无数据和不适用；Flaky 把可比较的 Case 结果持久化到 SQLite，通过状态机、Epoch、事务和人工审计动作形成治理闭环；Pipeline Reporting 最后汇总这些来源，但不反向修改 pytest 或 Jenkins 已经确定的事实。

## 5. 初学者先建立的几个概念

| 概念 | 通俗解释 | 在框架中的位置 |
| --- | --- | --- |
| Case | pytest 实际执行的一次测试实例 | quality.models.CaseResult |
| Attempt | 一次真实网络发送 | quality.models.RequestMetric |
| Retry | 某次 Attempt 后决定再发送一次 | common.retry、common.retry_executor |
| Polling | 为等待异步终态而进行的多次查询 | common.polling、BaseRequest.poll_get |
| SSE | 一个连接上持续到达的多段数据 | common.streaming.iter_sse_lines |
| Request Group | 首次发送与它的重试 Attempt 所属的一组 | quality.semantic_models.RequestGroupRecord |
| Polling Session | 多轮状态查询与等待构成的过程 | PollingSessionRecord |
| Operation | 对用户有意义的一次逻辑业务动作 | OperationRecord |
| Worker Shard | 某个执行进程独立写出的原始事实文件 | reports/quality/shards |
| JUnit | pytest 的标准测试结果和身份辅助证据 | quality.junit |
| Manifest | 声明版本、来源、状态、数量和哈希的清单 | merged/manifest.json |
| Integrity | 事实是否完整、可关联、未冲突 | COMPLETE、DEGRADED、FAILED |
| Noop | 接口存在，但不采集质量数据的空实现 | NoopRuntimeHooks、NoopQualityRunLifecycle |
| fail-open | 观察失败时保留原业务结果 | Runtime Hooks 与 Quality stages |
| Completeness | 指标证据完整程度 | complete、partial、no_data、not_applicable |
| Flaky | 同一可比较范围内结果发生不稳定变化 | quality.flaky、quality.flaky_store |

这里最容易混淆的是四层对象：

~~~text
Case
└─ Operation：一次业务调用
   ├─ Request Group：一次请求及其重试
   │  ├─ Request Event / Attempt 1
   │  └─ Request Event / Attempt 2
   └─ Polling Session：多轮查询组成的等待过程
~~~

一个 Case 可以包含多个 Operation；一个 Operation 可以包含多个 Request Group；一个 Request Group 可以包含多个 Attempt。

## 6. 用三条真实 module 链路理解框架

### 6.1 普通 Chat：最短主链

真实入口位于 module/smoke/test_response_body_validation.py：

~~~text
TestResponseBodyValidation.test_chat_completions_response_body
-> SmokeTask.build_chat_completions_payload
-> BaseTask.create_chat_completion
-> MediaGenerationCapability.create_chat_completion
-> operation_scope(HTTP, chat_completion, workload)
-> 对 SmokeRequest 实例调用继承的 BaseRequest.post
-> BaseRequest.request
-> RuntimeObserver.start_operation
-> BaseRequest._send_single_group
-> Middleware before_request
-> requests.Session.request
-> Middleware after_response
-> RuntimeObserver.finish_response
-> SmokeAssertions
-> pytest Case 结果
~~~

SmokeTask 没有重新定义 create_chat_completion；它继承 BaseTask 的兼容门面。BaseTask 再把动作委托给 MediaGenerationCapability，Capability 通过 operation_scope 声明业务语义，最终对实际传入的 SmokeRequest 对象调用其继承自 BaseRequest 的 post。

这条链把职责分成五层：

- Test 决定场景和预期。
- SmokeTask 构造当前模块的 payload，并复用 BaseTask 兼容门面。
- BaseTask 保持旧调用方可继续使用的稳定 API。
- MediaGenerationCapability 承担可组合的媒体与聊天领域能力，并声明 operation 元数据。
- SmokeRequest 是实际 Request Client，提供 Session、配置和 BaseRequest 能力。
- BaseRequest 统一处理 Session、Header、Middleware、Retry 和观察生命周期。

当前 Test 并没有调用 SmokeRequest.create_chat_completion。该方法是另一条可直接使用的领域 Request 路径；当前兼容调用链的语义元数据来自 MediaGenerationCapability.operation_scope。两种路径同时存在，是“稳定兼容门面逐步迁移到窄 Capability”的现实结果，阅读源码时不能只凭同名方法推断调用关系。

当前 Capability 声明：

- operation name：chat_completion。
- traffic role：workload。
- payload 中的 model。

这些字段不会改变 HTTP 业务语义，但会帮助 Semantic 和 Metrics 判断“这是一条工作负载调用，属于哪个模型和操作”。

### 6.2 SSE Chat：Response 返回不代表业务结束

真实入口同样位于 module/smoke/test_response_body_validation.py：

~~~text
test_stream_chat_completions_chunk_fields
-> SmokeTask.create_small_stream_chat_completion
-> SmokeRequest.create_stream_chat_completion
-> BaseRequest.request(stream=True)
-> HTTP headers 到达
-> Runtime Hooks 把 stream lease 绑定到 Response
-> SmokeTask.collect_stream_chat_completion_chunks
-> common.streaming.iter_sse_lines
-> 每行 observe_stream_line
-> [DONE] 或异常
-> finish_stream
-> Response.close
~~~

普通响应在收到完整 Response 后即可收口；SSE 不行。对 SSE 来说，HTTP 200 只证明连接和 headers 已经建立，不能证明：

- 收到了任何数据。
- 收到了业务内容。
- 收到了 usage。
- 收到了 [DONE]。
- 流没有中途断开。

因此框架把 Operation 暂时从普通请求生命周期中“分离”，由 stream lease 持有，等消费者真正读完或中断时再记录终态。

### 6.3 异步图片：一次业务动作包含创建与多轮查询

真实入口位于 module/smoke/test_图片生成异步调用.py：

~~~text
test_f8_09_async_image_generation_task_succeeds_with_result
-> BaseTask.create_and_poll_media_generation
-> MediaGenerationCapability.create_and_poll_media_generation
-> operation_scope(ASYNC_TASK, media_generation, workload)
-> create 回调：BaseTask.create_media_generation
-> MediaGenerationCapability.create_media_generation
-> 对 SmokeRequest 实例调用继承的 post
-> 提取 task_id
-> poll 回调：BaseTask.poll_media_generation_result
-> MediaGenerationCapability.poll_media_generation_result
-> 对 SmokeRequest 实例调用继承的 poll_get
-> pending 时等待
-> 再次查询 /v1/media/tasks/{task_id}
-> success / failure / unknown / timeout
-> 返回最终 Response
~~~

这里同样没有调用 SmokeRequest.create_media_generation 或 SmokeRequest.poll_media_generation_result 的同名领域方法。BaseTask 把自身方法作为 create、extract_task_id 和 poll 回调交给 Capability；Capability 最终使用传入的 SmokeRequest 作为 BaseRequest Client。外层 ASYNC_TASK operation 把创建与轮询包成一个逻辑业务动作，内层 operation_scope 会复用父级上下文，避免重复制造互不相关的 Operation。

这里至少存在三种时间：

- 创建请求耗时。
- 多轮查询的网络耗时。
- 两次查询之间主动 sleep 的等待时间。

如果只把所有 GET 耗时相加，就无法回答用户真正关心的“从提交任务到拿到结果用了多久”。这正是 Semantic 和 Operation timing 存在的原因。

## 7. 亮点一：Retry 是决策系统，不是 while 循环

### 7.1 Retry 真正要防止什么

简单地“失败就再请求一次”会产生严重问题：

~~~text
客户端超时
-> 服务端可能已经创建任务或完成扣费
-> 客户端误以为没有执行
-> 再次 POST
-> 生成两个任务或重复计费
~~~

因此 Retry 必须回答四个问题：

1. 这个 HTTP 方法允许重复吗？
2. 当前 Response 或 Exception 值得重试吗？
3. 还有尝试次数和时间预算吗？
4. 如果停止，应该返回最后一个 Response，还是重新抛出原始 Exception？

### 7.2 RetryPolicy 只是规则快照

common/retry.py 中的 RetryPolicy 是冻结的 Pydantic 模型，主要规则包括：

- 默认最多 3 次 Attempt。
- 默认只允许 GET 和 HEAD。
- 默认可重试状态码为 429、500、502、503、504。
- 默认可重试异常为 ConnectionError 和 Timeout。
- SSL 错误和重定向过多明确不重试。
- 支持 fixed 或 exponential backoff。
- 支持 jitter。
- 支持 Retry-After。
- 默认 max_elapsed 为 30 秒。
- POST 默认不允许重试。

Policy 只表达规则，不拥有循环。真正的循环属于 RetryExecutor.execute。

### 7.3 三道决策门

第一道是方法资格：

~~~text
GET / HEAD
-> 默认允许

POST
-> allow_post=True
   或存在 Idempotency-Key
-> 才允许

其他方法
-> 除非显式加入 allowed_methods
-> 默认不允许
~~~

第二道是结果资格：

- Response 的 status_code 必须在 retry_statuses 中。
- Exception 必须属于 retry_exceptions。
- SSLError 和 TooManyRedirects 即使属于 ConnectionError 体系，也被明确排除。

第三道是预算：

- max_attempts 限制发送次数。
- max_elapsed 限制本次 Request Group 的总重试时间。
- 外层 deadline 限制更大的业务过程，例如整个 Polling。
- 下一次 sleep 如果已经越过 deadline，就不能先睡再说。

### 7.4 Response 路径和 Exception 路径不同

如果最后拿到的是 503 Response，框架通常返回最后一个 Response，由调用方断言失败。

如果最后发生的是 Timeout Exception，框架重新抛出原始异常，而不是伪造一个 Response。

这一区分很重要：

~~~text
HTTP 503
-> 服务端给出了协议层响应

Timeout
-> 客户端没有得到可用的协议层响应
~~~

### 7.5 每个 Attempt 为什么要有独立 RequestContext

每次 Attempt 都重新构造 RequestContext，并重新经过 Middleware。这样才能分别记录：

- 第几次 Attempt。
- 每次发送的开始和结束时间。
- 每次 Response 或 Exception。
- 哪次结果触发了下一次 Retry。
- Retry 等待了多久。

如果三次 Attempt 共用一个可变 Context，后一次发送会覆盖前一次事实。

### 7.6 当前真实 module 的接入事实

框架已经具备 RetryPolicy 和 RetryExecutor，但是否实际启用要沿真实调用链判断：

- SmokeRequest 的 create_chat_completion、create_image_generation、create_media_generation、get_media_generation_task 等直接领域方法没有显式传入 retry_policy。
- BaseTask.poll_media_generation_result 和 create_and_poll_media_generation 暴露了可选 retry_policy，并把它传给 Polling 内部的 GET。
- 当前 module 用例调用 create_and_poll_media_generation 时没有提供 retry_policy，因此实际值为 None。
- 创建任务的 POST 分支没有接收这个 polling retry_policy，不会随 GET 查询一起自动重试。

这意味着：

> 框架支持 Retry，不等于所有 module 请求默认自动 Retry。

当前设计选择“显式启用”，优点是不会在不了解幂等性的情况下悄悄重复业务动作；代价是每个领域 Request 必须经过接口语义审查后，决定是否暴露和传递 RetryPolicy。

### 7.8 设计收益与代价

优点：

- 把幂等风险变成显式决策。
- Response、Exception、等待和预算都有独立证据。
- Retry 可以嵌入 Polling，并受外层 deadline 控制。
- Policy 是不可变规则，便于审计。

代价：

- 调用方需要理解接口幂等性。
- 领域 Request 需要显式透传 Policy。
- 真实环境不一定稳定出现 429 或 503，很多分支只能通过源码和历史产物确认。

## 8. 亮点二：Polling 与 SSE 对“完成”的定义不同

### 8.1 三种响应形态

| 类型 | HTTP 请求次数 | 数据到达方式 | 完成条件 |
| --- | ---: | --- | --- |
| 普通 JSON | 通常 1 次 | 一次读取完整 Body | Response 完整返回 |
| Polling | 多次 | 每次得到一个状态快照 | 业务状态进入终态 |
| SSE | 通常 1 次连接 | 同一 Response 持续到达数据行 | 协议终止标记、关闭或异常 |

### 8.2 PollingPolicy 把业务状态写成合同

common/polling.py 中的 PollingPolicy 定义：

- status_json_path：从响应哪里读取状态。
- pending_values：哪些状态继续等待。
- success_values：哪些状态成功结束。
- failure_values：哪些状态立即失败。
- result_json_path：某些响应可由结果字段判定成功。
- error_json_path：某些响应可由错误字段判定失败。
- unknown：陌生状态按 fail、pending 或 ignore 处理。

evaluate_polling_response 只负责把一个 Response 分类为 PollingEvaluation，不负责 sleep，也不负责下一次 HTTP 请求。这样把“状态判断”和“循环编排”分开。

### 8.3 Polling 的四个出口

~~~text
pending
-> 记录 transition
-> 计算剩余预算
-> sleep
-> 下一轮查询

success
-> 返回当前 Response

failure
-> 抛出 PollingFailedError

unknown
-> 根据 Policy 决定继续或抛出 PollingUnknownStateError

deadline exhausted
-> 抛出 PollingTimeoutError
~~~

异常对象会保留 path、最后状态、最后 Response 和 transitions，使失败不是一句“超时”，而是一条可解释状态轨迹。

### 8.4 为什么整个过程只能有一个总 deadline

一次 Polling 可能包含：

~~~text
GET Attempt
-> GET 内部 Retry backoff
-> Retry-After
-> transport timeout
-> Polling sleep
-> 下一轮 GET
~~~

如果每一层都使用自己的完整 timeout，外层配置 60 秒，实际可能执行几分钟。框架在 poll_get 开始时计算绝对 deadline，并把它传给 RetryExecutor：

- 每次 transport timeout 被截断到剩余时间。
- Retry sleep 不得跨过 deadline。
- Polling sleep 使用 min(poll_interval, remaining)。
- 已经耗尽预算时不得再发送一次请求。

### 8.5 SSE 为什么需要 lease

BaseRequest.request 在 stream=True 时把 Operation 类型设为 SSE。收到 2xx Response 后，不立刻 finish Operation，而是：

1. 把 stream lease 绑定到 Response。
2. 由 iter_sse_lines 在每条数据到达时通知 Hooks。
3. 在正常结束、主动中断或异常时调用 finish_stream。

lease 保存“由哪一套 Hooks 开始的生命周期”。即使读取过程中当前 provider 发生变化，也应由最初的 Hooks 完成原生命周期，避免开始和结束写入不同后端。

## 9. 亮点三：Runner 拥有唯一权威执行计划

### 9.1 为什么不能让每个池自己决定跑什么

如果并行池和串行池分别执行一次 pytest 选择表达式，它们可能因为插件参数、marker、文件变化或收集错误得到不同集合：

~~~text
并行池自己收集
串行池自己收集
-> 两边都认为自己结果正确
-> 某些 Case 被重复执行或完全遗漏
~~~

Runner 的解决方式是先形成唯一权威集合 C，再从 C 派生：

~~~text
C = 本轮全部最终 nodeid
P = C 中不带 serial marker 的 Case
S = C 中带 serial marker 的 Case
~~~

并保持：

- P ∪ S = C。
- P ∩ S = 空集。
- 每个集合内部没有重复 nodeid。

### 9.2 权威收集与执行池的区别

collect_test_case_items 调用 pytest 完成权威收集，保存 nodeid 和 markers。

执行池仍会让 pytest 解析这些 nodeid，但不能重新决定本轮业务集合。换句话说：

- 权威收集决定“应该执行谁”。
- 执行池只负责“怎样执行已经分配的人”。

### 9.3 真实 module 中的 serial

module/smoke/test_key_api.py 使用模块级 serial marker。

module/smoke/test_call_billing_correctness.py 也使用 serial，因为余额、用量和共享账户状态不能被其他计费 Case 并发污染。

普通响应合同 Case 可以进入并行池。

这体现了 serial 的真实含义：

> serial 不是“这个测试比较慢”，而是“它与其他测试并发时会破坏事实独立性”。

### 9.4 原始退出码为什么必须保留

pytest 不只有通过和失败：

- 0：执行成功。
- 1：存在测试失败。
- 2：用户中断。
- 3：内部错误。
- 4：命令行使用错误。
- 5：没有收集到测试。

Runner 不能把 2、3、4、5 都压成普通失败，否则无法区分：

- 产品或断言失败。
- 执行系统损坏。
- 参数错误。
- 本轮根本没有 Case。

某些终止型退出码出现后，Runner 会停止后续池，避免在不可信的执行状态下继续。

### 9.5 Allure 为什么需要单一生命周期所有者

并行池和串行池分别产生 Allure raw 文件。AllureRunLifecycle：

1. 为不同池分配临时结果目录。
2. 每个池完成后合并 raw 产物。
3. 检测同名冲突。
4. 最后只生成一次 HTML 和 history。

如果每个池都自行清理和生成报告，后运行的池可能删除前一个池的结果。

## 10. 亮点四：Runtime Hooks 让 Quality 成为旁观者

### 10.1 最危险的依赖方向

一种直接但危险的写法是：

~~~text
common/base_request.py
-> import quality.collector
-> 每次请求直接写质量数据
~~~

这样会导致：

- Quality 包不可用时，请求核心无法导入。
- Quality 模型变化迫使 common 跟着变化。
- 采集异常可能覆盖业务 Response。
- 关闭 Quality 仍然加载所有质量实现。

框架规定依赖方向：

~~~text
quality -> common.runtime_hooks
common -X-> quality
~~~

common 只知道中性协议，不知道事实最终写入 JSONL、数据库还是其他后端。

### 10.2 四个关键角色

RuntimeHooks Protocol：

- 定义 Operation、Request Group、Request、Polling 和 Stream 的观察接口。
- 不包含 Quality 数据模型。

NoopRuntimeHooks：

- 默认实现。
- 所有调用保持合法。
- 不创建质量身份、目录和产物。

RuntimeObserver：

- 位于 common。
- 管理 begin/finish、lease 和幂等收口。
- 不拥有 HTTP 控制流。

QualityRuntimeHooks：

- 位于 quality/runtime_adapter.py。
- 把中性事件映射到 request_metrics 和 semantic_context。

### 10.3 fail-open 的准确含义

fail-open 不是“吞掉所有错误”，而是：

~~~text
业务请求或原始异常已经产生
-> 观察回调失败
-> 记录质量降级信息
-> 保留原业务结果
~~~

例如网络请求抛出 Timeout，同时 Hook 写入失败，调用方最终必须看到 Timeout，而不是 Hook 的文件错误。

但 fail-open 也有代价：如果没有监控 warning、integrity status 和 NO_DATA，质量链可能长期降级而业务用例仍然通过。因此 fail-open 必须和产物完整性报告配套。

### 10.4 lease 为什么存在

Operation、Request Group、Polling 和 Stream 都可能跨越多次函数调用。lease 保存：

- 哪个 Hooks 实例开始了生命周期。
- 原生后端 handle。
- 当前对象是否拥有结束责任。

它解决两个问题：

1. 嵌套 Operation 不重复创建业务调用。
2. 开始与结束始终交给同一个观察后端。

### 10.5 ContextVar 与线程

Quality 的 run、case、operation 和 hooks 归属保存在 ContextVar 中。普通函数调用会自然继承，但 ThreadPoolExecutor 的新线程不会自动继承完整上下文。

因此并发业务代码使用 common.submit_with_context，而不是裸 executor.submit。否则请求虽然成功，却可能失去当前 Case 或 Operation 归属，最终形成孤立 RequestMetric 或 IntegrityIssue。

### 10.6 Quality 生命周期也使用 Noop

Runner 只依赖中性的 QualityRunLifecycle：

- Quality 关闭时返回 NoopQualityRunLifecycle。
- Quality 开启时返回 EnabledQualityRunLifecycle。
- Enabled 生命周期才创建 run record、补充 JUnit 参数、注入 execution 环境并执行最终质量阶段。

这使 Quality 开关不改变 Runner 的核心结构。

优点：

## 11. 亮点五：pytest worker 写原始账本

### 11.1 为什么需要五级身份

并发执行时，仅有测试名称不够。

| 身份 | 作用域 | 解决的问题 |
| --- | --- | --- |
| run_id | 整轮运行 | 区分不同构建或本地运行 |
| execution_id | 一个真实执行池 | 区分 parallel-pool、serial-pool |
| worker_id | 一个 pytest 工作进程 | 区分 gw0、gw1 和 master |
| case_id | 稳定 Case 语义 | 跨运行识别同一用例 |
| invocation_id | 本轮具体调用 | 区分参数化实例和本轮执行 |

没有这些身份会出现：

- 不知道某条 Request 属于哪次运行。
- 并行池和串行池的同名 Case 无法区分。
- 参数化 Case 被错误合并。
- JUnit 结果无法与 JSONL CaseResult 对账。

### 11.2 pytest 插件怎样捕获生命周期

quality/pytest_plugin.py 是轻量入口。只有 Quality 开启时才延迟加载 quality/pytest_plugin_runtime.py。

runtime 插件使用：

- pytest_configure：建立 run/worker 上下文和 Collector。
- pytest_configure_node：把父级 run/execution 配置传给 xdist worker。
- pytest_collection_modifyitems：建立 Case identity。
- pytest_runtest_protocol：绑定和清理 CaseContext。
- pytest_runtest_logreport：记录 setup、call、teardown 事实。
- pytest_collectreport：记录收集错误。
- pytest_unconfigure：收口未完成语义对象并清理上下文。

### 11.3 为什么要记录 setup、call、teardown

一个 Case 可能：

- setup 失败，call 根本没有执行。
- call 通过，但 teardown 失败。
- setup skip。
- xfail 或 xpass。

如果只记录测试函数返回值，会把这些不同事实折叠成错误结论。CaseResult 保留 phase，后续 Aggregator 和 Flaky importer 再按规则折叠。

### 11.4 为什么每个 worker 独立写 JSONL

如果所有 worker 同时写一个 JSON 文件，需要复杂锁和重写；进程崩溃还可能破坏整份文件。

当前设计让每个 execution/worker 写：

- cases-{execution_id}-{worker_id}.jsonl
- requests-{execution_id}-{worker_id}.jsonl
- integrity-{execution_id}-{worker_id}.jsonl

JSONL 的优势：

- 一条事实一行。
- 可以追加，不必重写整个数组。
- 某行损坏时仍有机会恢复其他有效行。
- 文件名本身包含执行归属。

### 11.5 Case、Request、Integrity 为什么分开

Case shard：

- pytest 生命周期事实。
- setup/call/teardown 状态。
- nodeid、参数和失败引用。

Request shard：

- 每个真实 Attempt 的 HTTP、异常、耗时、usage 和 retry 信息。

Integrity shard：

- 采集过程中无法归类为正常业务记录的问题。
- 例如 CaseContext 缺失或写入失败。

把 IntegrityIssue 单独保存的价值是：采集失败不会被伪装成“没有请求”。

### 11.6 JUnit identity 是第二条对账证据

插件把 quality_case_id 和 quality_invocation_id 写入 JUnit testcase properties。

JUnit 和 worker JSONL 不是两套竞争结论：

- worker JSONL 提供细粒度质量事实。
- JUnit 提供 pytest 标准状态和错误证据。
- Aggregator 通过 invocation identity 对账。

## 12. 亮点六：Aggregator 先判断账本能不能信

### 12.1 文件存在为什么还不够

看到 cases-gw0.jsonl 并不能证明：

- 它属于当前 run。
- 每一行都是合法 JSON。
- 字段符合当前 Schema。
- 没有漏掉 gw1。
- 没有重复或冲突记录。
- JUnit 中存在对应 invocation。

因此 Aggregator 的本质不是“拼接文件”，而是“执行对账与信任判定”。

### 12.2 merge_quality_run 的主要阶段

~~~text
写 manifest.status = merging
-> 扫描 Case / Request / Integrity shards
-> 统计物理行、当前 run、外部 run、坏 JSON、坏 Schema
-> 去重并识别同 ID 冲突
-> 读取 JUnit
-> 按 invocation_id 对账
-> 检查 expected execution 与 expected case count
-> 为失败 Case 派生 FailureRecord
-> 原子写 merged JSONL
-> 计算输出 SHA256
-> 写 manifest.status = complete
-> 计算 integrity_status
~~~

### 12.3 manifest complete 不等于账本完整

这是整个设计中最重要的区分之一：

- manifest.status=complete：归并流程完成并提交了输出。
- integrity_status=COMPLETE：没有发现完整性问题。
- integrity_status=DEGRADED：发现警告，部分数据仍可用。
- integrity_status=FAILED：发现严重信任问题。

因此可能出现：

~~~text
manifest.status = complete
integrity_status = FAILED
~~~

它表示“归并程序成功完成，但它判定输入账本不可信”，不是程序崩溃。

### 12.4 merge result 为 None 又是另一件事

run_orchestration/quality_fact_merge_stage.py 提供 fail-open wrapper：

- merge_quality_run 正常返回 QualityMergeResult，即使 integrity FAILED，仍然有结构化结果。
- 如果 merge 函数本身发生未处理异常，wrapper 返回 None。

这两者不能混为一谈：

- FAILED 是明确的完整性判断。
- None 是归并阶段没有形成可用判断结果。

### 12.5 去重与冲突

同一身份出现两次时：

- 内容完全相同：记录 exact duplicate，可安全折叠。
- 身份相同但内容不同：记录 conflict duplicate，属于信任问题。

“数量相同”不能证明账本正确；必须比较稳定身份和规范化内容。

### 12.6 JUnit 对账

Aggregator 读取：

- JUnit status。
- quality_case_id。
- quality_invocation_id。
- error type。
- message。
- assert location。

然后检查：

- JUnit 是否缺少身份。
- invocation 是否存在于 CaseResult。
- 同一 invocation 是否冲突。
- JUnit 与 CaseResult 状态是否兼容。

### 12.7 FailureRecord 是派生事实

worker 不直接决定失败属于配置、环境、产品还是测试缺陷。

Aggregator 汇总 CaseResult、JUnit 和相关 RequestMetric 后，调用 classifier 生成 FailureRecord。这样：

- worker 只负责记录原始事实。
- Aggregator 负责组织证据。
- Classifier 负责应用分类规则。

三者不会形成一个难以审计的黑盒。

## 13. 亮点七：Semantic 按业务动作理解请求

### 13.1 为什么 RequestMetric 不够

RequestMetric 能告诉我们：

- 某次 HTTP Attempt 的状态码。
- 是否超时。
- 耗时多少。
- 是否带 usage。

但它无法单独回答：

- 三次 Attempt 是否属于同一次 Retry。
- 五次 GET 是否属于同一次 Polling。
- 一个 POST 和后续 Polling 是否属于一次媒体生成。
- SSE 的首包与完整流耗时属于哪个业务动作。

Semantic 的职责就是补上这些关系。

### 13.2 四层语义模型

Request Event：

- 一次真实 Attempt。
- 来源是 P0 RequestMetric。

Request Group：

- 一次请求意图及其所有 Retry Attempt。
- 保存 configured_max_attempts、attempt_event_ids、final_request_event_id、retry_wait_ms。

Polling Session：

- 多轮状态查询与 sleep。
- 保存状态序列、首次出现偏移、总等待和终态。

Operation：

- 一次用户可理解的逻辑动作。
- 类型可以是 HTTP、SSE 或 POLLING。
- 保存业务名称、流量角色、模型、Request Group、Polling Session、Timing 和 Usage。

### 13.3 真实 module 怎样提供语义

当前框架中有两种语义声明路径：

- SmokeRequest 的直接领域方法通过 _quality_operation_name 和 _quality_traffic_role 传入元数据。
- BaseTask 兼容门面委托 MediaGenerationCapability，由 Capability 的 operation_scope 声明类型、名称、角色和模型。

例如：

- _quality_operation_name。
- _quality_traffic_role。

例如：

- chat_completion：workload。
- chat_completion_stream：workload。
- media_generation_create：workload。
- media_generation_polling：workload。
- account_balance：control。
- usage_records：control。

workload 与 control 的区分很关键。模型调用是被测工作负载；余额和用量查询是控制面辅助请求。若混在一起，接口成功率和耗时 Top 会被控制查询污染。

### 13.4 嵌套 Operation 为什么不能重复创建

BaseTask 的复合动作会通过 MediaGenerationCapability 建立外层 ASYNC_TASK operation，随后调用带有各自 operation_scope 的创建和轮询方法。Runtime Hooks 会复用当前父 Operation，并通过 owned 标志明确谁有结束责任，避免：

~~~text
外层 create_and_poll
-> 内层 create request 再创建一个互不相关 Operation
-> polling 又创建若干孤立 Operation
-> 无法还原一次业务动作
~~~

### 13.5 Semantic Aggregator 仍然要做信任校验

Semantic 不是看到 ID 就直接关联。merge_semantic_run 会：

## 14. 亮点八：Metrics 明确区分“零”和“没有证据”

### 14.1 最危险的统计错误

如果响应中没有 input_tokens，直接写成 0，会产生错误结论：

~~~text
字段缺失
-> 被解释成消耗为 0
-> 平均 Token 降低
-> 成本和容量判断失真
~~~

因此框架不只保存数值，还保存证据覆盖情况。

### 14.2 NumericAggregate

numeric_aggregate 接收数值或 None：

- eligible_count：理论上应观察多少个样本。
- sample_size：实际有数值的样本数。
- missing_count：缺失多少。
- total、mean、minimum、maximum。
- completeness。

如果一个值明确为 0，它属于 known sample。

如果所有值都是 None：

- total 和 mean 都是 None。
- completeness 是 NO_DATA。

如果部分有值、部分缺失：

- 只对 known samples 计算。
- completeness 是 PARTIAL。

如果该指标对当前类型本就不适用：

- completeness 是 NOT_APPLICABLE。

### 14.3 RatioAggregate

比率的输入是 True、False 或 None：

- True 进入分子和分母。
- False 只进入分母。
- None 进入 unknown_count，不进入分母。

因此未知请求不会被强行解释成失败或成功。

### 14.4 四种粒度

Case 粒度：

- pytest 调用结果。
- 参数化 invocation。

Operation 粒度：

- 业务调用总耗时。
- SSE headers、first_data、first_content、stream duration。
- 异步 create_request、polling_total、polling_sleep。
- Token 与媒体 usage。

Request Group 粒度：

- Attempt 数量。
- Retry rate。
- 首次与最终 HTTP/业务成功率。
- Retry rescue rate。
- Retry wait。

Request Event 粒度：

- 2xx、3xx、4xx、5xx、429。
- timeout 与 transport error。
- 单次 Attempt duration。
- 单次 usage coverage。

### 14.5 重试挽救率为什么分两种

HTTP retry rescue：

- 第一次 Attempt 非 HTTP 成功。
- 最终 Attempt HTTP 成功。

Business retry rescue：

- 第一次 Attempt 业务失败。
- 最终 Attempt 业务成功。

HTTP 2xx 不一定代表业务成功，因此两者不能合并。

### 14.6 Metrics 为什么再次验证来源

Metrics 不因为文件位于 reports/quality 就自动信任。load_sources 和 validation 会检查：

- P0 manifest run_id、版本、status 和 integrity。
- Semantic manifest run_id、版本、status 和 integrity。
- output_hashes。
- Request Group 引用的 Request Event 是否存在。
- Attempt index 是否连续。
- Usage 证据是否重叠或越界。

Metrics 的原则是：

> 宁可输出 NO_DATA 或 FAILED，也不从不可信来源计算一个看似精确的数字。

## 15. 亮点九：Flaky 是历史状态与治理流程

### 15.1 单次失败不等于 Flaky

三个概念必须分开：

- 测试失败：本轮结果是 fail。
- 稳定失败：多轮都是同一个 failure fingerprint。
- Flaky：可比较运行之间发生通过/失败切换，或失败签名不稳定变化。

如果一个产品缺陷连续失败十次，它很严重，但不一定 Flaky。

### 15.2 结果签名

quality/flaky.py 的 build_result_signature：

- pass 结果签名为 pass。
- fail 结果签名为 fail:{failure_id}。

failure_id 来自前面 Classifier 派生的稳定失败指纹。因此 Flaky 不只比较 pass/fail，还能识别“失败原因发生变化”。

### 15.3 当前默认自动状态规则

状态包括：

- OBSERVING：样本不足，继续观察。
- STABLE：达到一致签名阈值。
- SUSPECTED：稳定签名被打破或发生切换。
- CONFIRMED：满足确认 Flaky 的通过、失败和切换证据。
- QUARANTINED：人工隔离。
- RECOVERING：人工启动恢复观察。

当前默认规则包括：

- 最近最多观察 20 个样本。
- 3 个一致签名可以进入 STABLE。
- 确认至少需要 4 个样本，其中至少 2 pass、2 fail，并至少发生 2 次结果切换。
- SUSPECTED 连续 5 个相同签名可以重新稳定。
- RECOVERING 连续 5 个相同签名可以恢复。

CONFIRMED 自动状态是 sticky 的，不会仅因几次通过自动消失；恢复必须进入有审计信息的治理流程。

### 15.4 为什么要分四类存储

Observation：

- 每轮导入的原始可比较结果。
- 历史事实，不应被后续状态覆盖。

Projection：

- 根据当前规则对全部历史重放得到的当前状态。

Transition：

- 从什么状态变到什么状态。
- 由哪条 observation 或人工动作触发。
- 使用哪个规则版本。

Governance：

- 隔离负责人、操作者、原因、到期时间。
- 恢复开始时间和观察锚点。
- 最终 recovered、regressed 或 cancelled。

如果只保存 current_state，就无法回答状态为什么变化，也无法在规则升级后重放。

### 15.5 SQLite 为什么需要严格事务边界

一次状态更新可能同时写：

- 新 Observation。
- 当前 Projection。
- Transition。
- Governance。
- Epoch override。

其中任意一步失败都不能留下半套状态。因此 FlakyStore 门面控制事务，领域服务不自己创建连接或提交。

### 15.6 Migration checksum

数据库迁移文件具有版本和 checksum。已经应用的同一版本如果内容发生变化，框架拒绝继续使用数据库。

原因是：

~~~text
数据库声称执行过 migration 0001
-> 仓库里的 0001 内容被悄悄修改
-> 新旧环境的“同版本 Schema”实际不同
-> 历史和状态结论不可比较
~~~

### 15.7 Epoch 解决“用例已经不是原来的用例”

当 Case 语义、比较规则或实现边界明确变化时，旧历史不应和新实现继续混算。

Epoch reset：

- 不删除旧 Observation。
- 将同一 scope 的当前 epoch 加一。
- 要求 actor 和 reason。
- 新运行进入新 epoch。
- 有 ACTIVE 或 RECOVERING 治理时禁止 reset。

这比清空数据库更可审计。

### 15.8 自动检测与人工治理为什么分开

自动规则可以发现 SUSPECTED 或 CONFIRMED，但隔离会影响交付流程，必须要求人工信息：

- owner。
- actor。
- reason。
- expires_at。

恢复也需要新的 observation anchor，确保只用恢复动作之后的样本判断。

## 16. 亮点十：报告只汇总事实，不制造第二结论

### 16.1 不同产物各自回答什么

| 产物 | 回答的问题 |
| --- | --- |
| pytest exit code | 测试进程如何结束 |
| execution-result.json | Runner 收集、分池和最终退出事实 |
| JUnit | Case 数量、状态和错误证据 |
| Allure | 步骤、请求、响应和附件下钻 |
| reports/quality | P0、Semantic、Metrics、Flaky 机器证据 |
| pipeline-summary.md | 人工快速判断本轮风险 |

这些产物不是互相覆盖，而是不同粒度。

### 16.2 事实优先级

~~~text
pytest 原始退出码
-> 决定测试进程事实

Runner pool 与 final exit
-> 决定项目级执行事实

Jenkins stage status
-> 决定流水线事实

JUnit
-> 提供测试统计和失败细节

Quality / Metrics / Flaky
-> 提供诊断和治理信息

PipelineReport
-> 汇总以上来源
-> 不修改前面任何事实
~~~

例如：

- Quality 关闭：显示 NOT_RUN，不读取旧 Quality 产物。
- Quality 开启但核心产物缺失：显示 NO_DATA，不写成请求数 0。
- Metrics hash 不匹配：只降级 Metrics 章节，不把 pytest 改成失败或成功。
- Jenkins 显式阶段失败：优先于一份看似通过的 JUnit。

### 16.3 单一 Report Model

pipeline_reporting 的流程是：

~~~text
Sources
-> PipelineReport
-> Markdown Renderer
-> JSON
-> Email subject
-> Email HTML
~~~

Markdown、JSON 和邮件共享同一个 PipelineReport，不在 Jenkins Groovy 中再次用正则解析 JUnit，避免多个渠道得出不同数字。

## 17. 整体设计的优点与缺点

| 设计 | 主要优点 | 主要缺点或代价 |
| --- | --- | --- |
| 显式 RetryPolicy | 不会在未知幂等性下自动重复业务 | 领域 Request 需要逐接口接入 |
| Polling 状态机与总 deadline | 异步调用有终点，Retry 不会突破总预算 | 状态合同和时间计算更复杂 |
| SSE lease | 能区分 headers 到达与流真正完成 | 消费者必须走标准 helper |
| Runner 单一权威收集 | Case 不丢不重，退出码可解释 | 比直接 pytest 多一层编排 |
| Runtime Hooks 依赖倒置 | Quality 可选，观察失败不阻断业务 | Protocol、Adapter、lease 增加抽象 |
| worker 独立 JSONL | 适合并发，单行损坏可局部恢复 | 产物数量多，必须归并 |
| Aggregator 信任判定 | 缺失、冲突、陈旧和篡改不会静默进入指标 | Schema、版本和哈希维护成本高 |
| Semantic 业务语义层 | Retry、Polling、SSE 可以按逻辑调用统计 | 要求标准入口和上下文传播 |
| Metrics completeness | 缺失不会被当成零 | 报告和使用方需要理解更多状态 |
| Flaky 状态与治理分离 | 识别、隔离、恢复都有证据和审计 | 状态机、SQLite 和规则维护复杂 |
| fail-open | 诊断故障不掩盖业务结果 | 如果忽略 warning，可能长期降级 |
| 单一 PipelineReport | Markdown、JSON 和邮件结论一致 | 来源适配层需要持续维护 |

## 19. 最值得记住的十条结论

1. 框架支持 Retry，但真实业务方法是否启用 Retry 必须看它有没有传 RetryPolicy。
2. POST 失败后不能因为“看起来没成功”就自动再发一次。
3. Polling 的 timeout 是整个过程的预算，不是每次 GET 都重新获得一份预算。
4. SSE 收到 HTTP 200 只代表连接建立，不代表流已经成功完成。
5. Runner 必须先知道完整 Case 集合，才能正确划分并行与串行池。
6. Quality 是观察者，不能成为业务请求的硬依赖，也不能覆盖原始异常。
7. worker 写出的 JSONL 只是原始账页，必须经过身份、JUnit、Schema、数量和哈希对账。
8. Request Event 是网络事实，Operation 才是用户真正关心的业务事实。
9. 没有数据不是 0；未知值不能偷偷进入成功率分母。
10. 单次失败不是 Flaky，Flaky 必须由可比较历史、状态规则和可审计治理共同定义。

## 20. 用一条总线复述整个框架

真实业务用例从 module 中的 Test 进入 Task；Task 可能调用领域 Request 方法，也可能经 BaseTask 兼容门面委托窄 Capability，再对实际 Request Client 使用 BaseRequest 能力；BaseRequest 用 Middleware、Retry、Polling 和 SSE 生命周期保证请求执行有明确边界，同时通过中性 Runtime Hooks 发出观察事件；Runner 在执行前形成唯一 Case 集合，划分 parallel-pool 和 serial-pool，并为每个执行池建立 execution identity；Quality 开启后，pytest 插件在每个 worker 中建立 CaseContext，把 Case、Request 和 Integrity 事实写成独立 JSONL，并把身份写入 JUnit；Aggregator 不直接相信这些文件，而是校验当前 run、Schema、重复冲突、预期 execution、Case 数量、JUnit identity 和 SHA256，形成带 integrity status 的 P0 账本；Semantic 在可信 P0 上把多个 Attempt 归入 Request Group，把多轮查询归入 Polling Session，再把它们归入 Operation；Metrics 从 Case、Operation、Request Group 和 Request Event 四个粒度计算成功率、重试挽救、流式与异步耗时、Token 和媒体用量，并保留 completeness；Flaky 将可信 Case 结果按稳定比较维度写入 SQLite，通过结果签名、自动状态、人工隔离、恢复、事务、迁移和 Epoch 形成长期治理；Pipeline Reporting 最后把 Runner、JUnit、Quality、Metrics 和 Flaky 汇入一个 Report Model，但任何诊断层都不能反向改写 pytest 和 Jenkins 已经确定的原始事实。
