### 0.1 一个 Context 对象存在，不等于 worker 能看见它

## 1. 第一性原理：传播与隔离是两个问题

### 1.1 传播回答“worker 应该知道什么”

例如：

- 当前测试身份。
- 当前运行观察者。
- 当前逻辑 owner。

### 1.2 隔离回答“worker 不应该共享什么”

例如：

- 可变 Session。
- Request 实例。
- 单次请求 Header。
- TestContext 内部变量字典。

```mermaid
flowchart LR
    CONTEXT[传播逻辑绑定] --> KNOW[worker知道当前身份]
    INSTANCE[隔离可变实例] --> SAFE[worker不污染其他任务]
```

### 1.3 TOC 因果链

如果把传播误认为实例复制：

```mermaid
flowchart TD
    A[ContextVar值传播成功] --> B[误以为Session也自动复制]
    B --> C[多个worker共享可变实例]
    C --> D[Header或连接状态串线]
    D --> E[并发事实无法解释]
```

所以本课必须同时回答两条链，但不能把它们合成一个机制。

## 2. 四个容易混淆的对象

| 对象 | 保存什么 | 典型作用域 | 是否由 `copy_context()` 创建新实例 |
| --- | --- | --- | --- |
| ContextVar 绑定 | 当前执行上下文中的逻辑值 | 执行上下文 | 复制绑定关系 |
| TestContext | 变量字典与清理栈 | 一次测试或显式实例 | 否 |
| Request 对象 | 配置、Session、Middleware | worker 或调用方实例 | 否 |
| Session | Header 与连接复用状态 | 随 Request 实例 | 否 |

```mermaid
classDiagram
    class ExecutionContext {
      ContextVar bindings
    }
    class TestContext {
      variables
      cleanup stack
    }
    class RequestInstance {
      config
      session
    }
    class Session {
      headers
      connection state
    }
    ExecutionContext ..> TestContext : 可以绑定引用但不自动复制
    RequestInstance *-- Session : 实例拥有
```

### 2.1 隔离不是同一个词的重复

可以同时出现：

- 两个 worker 读取相同 owner 字符串。
- 两个 worker 使用不同 Request 实例。
- 两个 worker 使用不同 Session。

相同逻辑身份与独立资源并不矛盾。

## 3. ContextVar 表达当前逻辑绑定

`common/runtime_hooks/provider.py` 定义一个 ContextVar：

先看绑定、读取与恢复怎样形成一个最小闭环。下面是 `common/runtime_hooks/provider.py` 中的完整实现：

```python
_NOOP_RUNTIME_HOOKS = NoopRuntimeHooks()
_RUNTIME_HOOKS: ContextVar[RuntimeHooks] = ContextVar(
    "common_runtime_hooks",
    default=_NOOP_RUNTIME_HOOKS,
)


def get_runtime_hooks() -> RuntimeHooks:
    return _RUNTIME_HOOKS.get()


def bind_runtime_hooks(hooks: RuntimeHooks) -> Token[RuntimeHooks]:
    if hooks is None:
        raise TypeError("hooks must not be None")
    return _RUNTIME_HOOKS.set(hooks)


def reset_runtime_hooks(token: Token[RuntimeHooks]) -> None:
    _RUNTIME_HOOKS.reset(token)
```

输入方面，`bind_runtime_hooks()` 接收新的 Hooks 对象，`reset_runtime_hooks()` 接收本次 `set()` 返回的 Token。状态变化发生在当前执行 Context 的 `_RUNTIME_HOOKS` 绑定上；`get_runtime_hooks()` 只读取，未绑定时返回 Noop 默认值。输出方面，bind 返回恢复点，get 返回当前对象，reset 不返回业务值。

这三个函数只管理“当前执行流应该看到哪个 Hooks 引用”。它们不复制 Hooks 对象，也不创建线程，更不负责 Request 或 Session 的生命周期。

```mermaid
flowchart LR
    D[默认Noop绑定] --> B[bind返回Token]
    B --> G[get读取当前绑定]
    G --> R[reset使用Token恢复]
```

### 3.1 Token 表示恢复点

`set()` 返回 Token。

后续 `reset(token)` 恢复之前的绑定。

这与修改模块全局变量不同：

```mermaid
flowchart TD
    A[进入局部执行域] --> B[set新绑定]
    B --> C[在当前Context中读取]
    C --> D[reset token]
    D --> E[恢复先前绑定]
```

### 3.2 本课不展开 Runtime Hooks

这里使用 provider 只为证明：

- 某类运行观察者存放在 ContextVar 中。
- 绑定可以被提交时上下文传播。

Hook 如何记录 Operation、Group 与结果属于 Day 18。

## 4. `submit_with_context()` 的全部核心只有两步

传播发生在线程池提交边界。打开 `common/context_executor.py`，`submit_with_context()` 的完整实现如下：

```python
def submit_with_context(
    executor: Executor,
    function: Callable[P, T],
    /,
    *args: P.args,
    **kwargs: P.kwargs,
) -> Future[T]:
    context = copy_context()
    return executor.submit(context.run, function, *args, **kwargs)
```

输入是 Executor、目标函数及其参数。第一行在调用 `submit_with_context()` 的线程中复制当前 Context 绑定；第二行把 `context.run` 作为真正提交给 Executor 的 callable，让目标函数稍后在该快照中运行。返回值仍是 Executor 创建的 `Future[T]`。

这个函数的责任边界非常窄：增加上下文传播，不创建业务资源、不复制参数对象、不等待执行完成，也不处理目标函数异常。

```mermaid
sequenceDiagram
    participant P as 父执行流
    participant H as submit_with_context
    participant C as Context副本
    participant E as Executor
    participant W as Worker
    P->>H: 提交function和参数
    H->>C: copy_context()
    H->>E: submit(context.run, function...)
    E->>W: 调度任务
    W->>C: 在副本中运行function
```

### 4.1 快照在提交时创建

不是 worker 真正开始时才复制。

```mermaid
flowchart LR
    A[父Context值=first] --> S1[submit任务1并复制]
    S1 --> B[父Context改为second]
    B --> S2[submit任务2并复制]
    S1 --> W1[任务1读取first]
    S2 --> W2[任务2读取second]
```

### 4.2 `Future` 语义不被替换

helper 返回 Executor 的 `Future`。

因此：

- 函数返回值仍通过 `future.result()` 获得。
- 函数异常仍通过 `future.result()` 重新抛出。
- helper 不吞掉业务异常。

## 5. 原生 `executor.submit()` 与显式传播

当前项目明确提供 `submit_with_context()`。

课程不能写成：

> 任何线程池提交都会自动传播 ContextVar。

准确边界是：

```mermaid
flowchart TB
    A[提交线程任务]
    A --> B{使用哪个入口}
    B -- submit_with_context --> C[显式copy_context]
    B -- executor.submit --> D[本项目没有附加传播步骤]
```

### 5.1 为什么使用包装入口

包装入口把传播责任固定在提交边界，而不是要求每个 worker 自己猜测父 Context。

### 5.2 现有证据只覆盖线程池

测试使用 `ThreadPoolExecutor`。

不能据此声称：

- `ProcessPoolExecutor` 受支持。
- Context 对象可以跨进程序列化。
- 任意自定义 Executor 都有相同语义。

## 6. `copy_context()` 不深复制绑定值

Context 快照复制的是绑定关系。

如果某个 ContextVar 绑定的是可变 list：

```text
ContextVar → list对象
```

两个 Context 可能仍引用同一个 list。

```mermaid
flowchart TB
    P[父Context] --> L[同一个可变list]
    C1[Context副本A] --> L
    C2[Context副本B] --> L
```

### 6.1 字符串测试不能证明深复制

现有传播测试使用字符串值。

字符串不可变，所以测试能够证明：

- 提交时值被正确读取。

它不能证明：

- 可变值会自动复制。
- worker 修改 list 不影响其他 Context。

### 6.2 项目中确有可变 ContextVar 值

媒体下载任务与模型结果文件收集等位置使用 ContextVar 保存 list。

本课只把它们作为“不能假定深复制”的边界，不展开其业务生命周期。

## 7. 实现事实与测试证据必须分层

### 7.1 每次提交都会创建新的 Context 快照

`context = copy_context()` 位于 `submit_with_context()` 函数体内，因此每调用一次包装入口，就会在该次提交边界复制一次绑定关系。这是可以直接从源码读取的实现事实。

当前仓库没有一个独立测试专门构造 `first → submit → second → submit` 的对照，所以不能把这个示例写成“已有测试结论”。如果未来要防止快照时点回归，应再增加对应测试。

### 7.2 离线测试怎样证明绑定进入 worker

真实证据位于 `module/offline_framework_example/test_concurrency_context.py` 的 `test_submit_with_context_preserves_case_ownership()`。测试先绑定 owner，再调用并发编排函数，最后无论成功失败都用 Token 恢复父 Context：

```python
owner_var: ContextVar[str] = ContextVar("offline_concurrency_owner")
token = owner_var.set("offline-concurrency-owner")
try:
    results, closed_session_ids = _run_audit_workers(
        offline_service,
        audit_names,
        owner_var=owner_var,
    )
finally:
    owner_var.reset(token)

assert {result.inherited_owner for result in results} == {
    "offline-concurrency-owner"
}
```

输入是父执行流中的字符串绑定。`_run_audit_workers()` 内部通过 `submit_with_context()` 提交任务，worker 再读取同一个 `owner_var`；输出结果中的 `inherited_owner` 必须等于父执行流绑定值。`finally` 只负责恢复测试线程原绑定，不负责撤销已提交任务的快照。

这个测试证明 owner 能进入两个线程池任务，但没有证明 ContextVar 绑定的可变对象会被深复制。

### 7.3 `Future` 合同来自直接转交

`submit_with_context()` 直接返回 `executor.submit(...)` 的结果，离线编排随后调用 `future.result(timeout=2)` 取得 worker 返回值。因此 helper 没有创建另一套结果容器。

按照 `Future` 自身合同，worker 异常会在 `result()` 时重新抛出；当前第13天相关测试没有单独构造失败 worker 验证异常类型，因此这里应区分“库与实现合同”和“本课已有回归证据”。

## 8. TestContext 隔离来自独立实例

`tests/test_test_context.py` 的线程测试在每个 worker 内：

1. 新建 `TestContext()`。
2. 写入自己的 request_id。
3. 读取自己的值。

把这三步落到真实测试 `test_threaded_context_instances_are_isolated()` 中：

```python
def test_threaded_context_instances_are_isolated():
    def worker(index: int) -> str:
        context = TestContext()
        context.set("request_id", f"request-{index}")
        return context.require("request_id", expected_type=str)

    with ThreadPoolExecutor(max_workers=8) as executor:
        values = list(executor.map(worker, range(20)))

    assert values == [f"request-{index}" for index in range(20)]
```

每个任务的输入是独立 index，worker 内部状态是新建 `TestContext` 的变量字典，输出是从同一实例读回的 request ID。父执行流只收集字符串列表，不接触 worker 内部字典。

隔离成立的直接原因是 `TestContext()` 位于 worker 函数内，而不是 `ThreadPoolExecutor` 自动复制了一个共享实例。

```mermaid
flowchart TB
    W1[Worker 1] --> T1[TestContext 1]
    W2[Worker 2] --> T2[TestContext 2]
    WN[Worker n] --> TN[TestContext n]
```

### 8.1 测试没有做什么

它没有让多个线程同时写同一个 TestContext。

所以不能声称：

- 同一 `_variables` 字典支持并发写。
- 同一 cleanup 栈支持并发 push/pop。
- TestContext 内置锁或事务。

### 8.2 ContextVar 与 TestContext 的关系

ContextVar 可以绑定一个 TestContext 引用。

但绑定引用不等于复制实例。

```mermaid
flowchart LR
    CV[ContextVar] --> REF[TestContext引用]
    REF -.copy_context只复制绑定.-> SAME[可能仍是同一实例]
```

如果需要 TestContext 数据隔离，仍要控制实例创建边界。

## 9. Offline 并发场景的 worker 所有权

真正的资源所有权边界位于 `module/offline_framework_example/test_concurrency_context.py` 的 `_query_audit_worker()`。先看一个 worker 从创建客户端到释放资源的完整过程：

```python
def _query_audit_worker(
    base_url: str,
    audit_name: str,
    *,
    barrier: Barrier,
    owner_var: ContextVar[str] | None,
    closed_session_ids: set[int],
    closed_session_lock: Lock,
) -> _OfflineAuditWorkerResult:
    request_client = OfflineFrameworkRequest(
        base_url,
        capture_policy=CapturePolicy.disabled(),
    )
    session_id = id(request_client.session)
    try:
        barrier.wait(timeout=1)
        inherited_owner = owner_var.get() if owner_var is not None else None
        response = OfflineFrameworkTask().query_audit(request_client, audit_name)
        return _OfflineAuditWorkerResult(
            audit_name=audit_name,
            response=response,
            session_id=session_id,
            inherited_owner=inherited_owner,
            trust_env=request_client.session.trust_env,
            audit_header_in_session="X-Audit-Name" in request_client.session.headers,
        )
    finally:
        request_client.close()
        with closed_session_lock:
            closed_session_ids.add(session_id)
```

输入分成三类：业务输入是 `base_url` 与 `audit_name`，并发协调输入是 `barrier`，证据收集输入是 owner、关闭集合与对应的 Lock。状态变化从 worker 内部创建 `OfflineFrameworkRequest` 开始；该构造过程创建新的 Session，发送请求后，`finally` 关闭客户端并登记 Session ID。

正常输出是 `_OfflineAuditWorkerResult`，同时携带响应、继承到的 owner、Session 身份、`trust_env` 与 Header 残留事实。即使等待、读取 owner、发送请求或构造结果失败，`finally` 仍会走关闭路径。该函数拥有自己的 Request/Session，但不拥有线程池，也不负责聚合其他 worker 的结果。

```mermaid
sequenceDiagram
    participant W as Worker
    participant R as OfflineFrameworkRequest
    participant S as Session
    participant API as OfflineService
    W->>R: 创建独立实例
    R->>S: 创建独立Session
    W->>API: 发起audit请求
    API-->>W: Response
    W->>R: finally close
    R->>S: close
```

### 9.1 Session 隔离的来源

不是：

```text
copy_context() 复制 Session
```

而是：

```text
每个 worker 新建 Request
→ 每个 Request 新建 Session
→ 每个 worker finally 关闭自己的 Session
```

### 9.2 相同 owner 与不同 Session 同时成立

两个 worker 都可以继承：

```text
offline-concurrency-owner
```

同时拥有不同 Session ID。

```mermaid
flowchart TB
    OWNER[相同逻辑owner]
    OWNER --> W1[Worker A]
    OWNER --> W2[Worker B]
    W1 --> S1[Session A]
    W2 --> S2[Session B]
    S1 -.不同对象.-> S2
```

这正是逻辑传播与资源隔离的组合。

## 10. 并发编排怎样提交 worker

worker 的资源边界明确后，再看它如何被调度。`_run_audit_workers()` 是本例的并发编排函数：

```python
def _run_audit_workers(
    service: OfflineService,
    audit_names: tuple[str, str],
    *,
    owner_var: ContextVar[str] | None = None,
) -> tuple[list[_OfflineAuditWorkerResult], set[int]]:
    barrier = Barrier(2)
    closed_session_ids: set[int] = set()
    closed_session_lock = Lock()
    with ThreadPoolExecutor(max_workers=2) as executor:
        futures = [
            submit_with_context(
                executor,
                _query_audit_worker,
                service.base_url,
                audit_name,
                barrier=barrier,
                owner_var=owner_var,
                closed_session_ids=closed_session_ids,
                closed_session_lock=closed_session_lock,
            )
            for audit_name in audit_names
        ]
        results = [future.result(timeout=2) for future in futures]
    return results, closed_session_ids
```

输入是离线服务、恰好两个 audit name，以及可选 owner ContextVar。函数创建两个参与者的 Barrier、关闭记录集合和只保护该集合的 Lock，再用两个线程执行 worker。每次循环都调用 `submit_with_context()`，所以每个任务各自在提交时捕获父 Context；`future.result(timeout=2)` 把异步结果收回父执行流。

输出同时保留业务结果列表和关闭证据集合。`with ThreadPoolExecutor(...)` 管理线程池生命周期，但各个 Request/Session 仍由 worker 的 `finally` 管理；编排函数不会替 worker 关闭客户端。

```mermaid
flowchart TB
    P[父执行流] --> E[ThreadPoolExecutor]
    P --> H1[submit_with_context audit-a]
    P --> H2[submit_with_context audit-b]
    H1 --> W1[Worker A]
    H2 --> W2[Worker B]
```

### 10.1 Barrier 的责任

Barrier 让两个 worker 在发送前相遇，提高并发重叠概率。

它不负责：

- ContextVar 传播。
- Session 创建。
- Header 合并。

### 10.2 Lock 的责任

Lock 只保护 `closed_session_ids.add(...)`。

它不能被解释成整个 Request 或 Session 的线程安全锁。

```mermaid
flowchart LR
    LOCK[Lock] --> SET[closed_session_ids集合写入]
    LOCK -.不保护.-> SESSION[Session内部状态]
    LOCK -.不保护.-> CONTEXT[ContextVar绑定]
```

## 11. 并发测试证明的 Session 事实

### 11.1 两个 Session ID 不同

测试收集两个 worker 的 `session_id`，断言集合长度为 2。

### 11.2 两个 Session 都进入关闭记录

测试断言：

```text
closed_session_ids == session_ids
```

这证明 worker finally 记录到两个实例的 close 路径。

它不证明底层所有连接资源都已经物理释放。

### 11.3 `trust_env` 事实

测试断言两个 Session 的 `trust_env` 都为 False。

这个状态来自 `module/offline_framework_example/request.py` 的 `OfflineFrameworkRequest.__init__()`：

```python
def __init__(
    self,
    base_url: str,
    *,
    timeout: float = 1,
    capture_policy: CapturePolicy | None = None,
) -> None:
    assert_loopback_url(base_url)
    offline_config = Settings(
        timeout=timeout,
        generate_allure_report=False,
        generate_history_report=False,
        history_report_keep_limit=1,
        base_url=base_url.rstrip("/"),
        api_key=OFFLINE_API_KEY,
        environment_name="offline",
    )
    super().__init__(config=offline_config, capture_policy=capture_policy)
    self.session.trust_env = False
```

输入是已通过 loopback 校验的离线服务地址和可选超时、捕获策略。`super().__init__()` 为当前 Request 实例创建 Session，随后将该 Session 的 `trust_env` 改为 False。输出是初始化完成的客户端实例状态；它不读取 ContextVar，因此 `trust_env=False` 不是上下文传播的结果。

## 12. 单次 Header 为什么不应残留到 Session

Header 的第一站是 `module/offline_framework_example/request.py` 的 `get_audit()`。它把 audit name 放入本次 `get()` 调用参数，而不是写入 Session：

```python
def get_audit(self, audit_name: str) -> requests.Response:
    return self.get(
        self.audit_path,
        headers={"X-Audit-Name": audit_name},
        runtime_metadata=runtime_metadata(
            RuntimeOperationKind.HTTP,
            name="offline_audit_query",
            role=RuntimeTrafficRole.CONTROL,
        ),
    )
```

输入是 audit name，输出是请求响应。函数的状态责任只是构造本次调用参数与运行时元数据；它没有调用 `self.session.headers.update(...)`，因此不会在这里把 `X-Audit-Name` 变成客户端长期状态。

Header 的第二站是 `common/base_request.py` 的 `_build_request_context()`。它先复制请求参数，再取出本次 Header，最后调用 `_merge_headers()`：

```python
request_kwargs = self._copy_request_kwargs(kwargs)
request_kwargs.setdefault("timeout", self.config.timeout)
request_kwargs["timeout"] = self.retry_executor.clamp_timeout(
    request_kwargs["timeout"],
    deadline,
)

headers = dict(request_kwargs.pop("headers", None) or {})
request_kwargs["headers"] = self._merge_headers(
    headers,
    inherit_session_headers=inherit_session_headers,
)
```

这段代码的输入是 `get_audit()` 传下来的 kwargs。状态变化只发生在新建的 `request_kwargs` 及其 Header 字典中，输出最终进入 `RequestContext.kwargs`；原始 kwargs 和 `session.headers` 都不是这里的写入目标。

真正的合并规则由同文件的 `_merge_headers()` 定义：

```python
def _merge_headers(
    self,
    headers: dict[str, Any],
    *,
    inherit_session_headers: bool = True,
) -> dict[str, Any]:
    merged: dict[str, Any]
    if inherit_session_headers:
        merged = dict(self.session.headers)
    else:
        merged = {str(name): None for name in self.session.headers}
    merged.update(headers)
    return merged
```

输入是本次 Header 与是否继承 Session Header 的开关。默认分支先复制 Session Header，再用本次 Header 覆盖副本；输出是新的合并字典。即使关闭继承，也只是生成以 `None` 覆盖 Session Header 名称的新字典。两个分支都不反向修改 `self.session.headers`。

```mermaid
flowchart LR
    SH[Session headers] --> COPY[dict副本]
    RH[本次请求headers] --> MERGE[更新副本]
    COPY --> MERGE
    MERGE --> CH[Context kwargs headers]
    CH --> SEND[Session.request]
```

### 12.1 关键不是 Header 名称

关键是本次 Header 进入请求参数副本，而不是调用 `session.headers.update(...)`。

### 12.2 测试直接断言

worker 已把表达式 `"X-Audit-Name" in request_client.session.headers` 保存为 `audit_header_in_session`。`test_single_request_headers_do_not_leak_between_workers()` 再逐项验证：

```python
for audit_name in audit_names:
    result = result_by_name[audit_name]
    self.assertions.assert_status_code(result.response, 200)
    self.assertions.assert_json_value(
        result.response,
        "$.audit_name",
        audit_name,
    )
    assert result.audit_header_in_session is False
```

输入是两个 worker 返回的结果对象。断言既确认服务端分别收到正确 audit name，也确认每个 worker 检查自己的 Session 时都没有发现该 Header；测试不读取另一个 worker 的 Session 内部状态。

这证明该特定单次 Header 没有残留在 worker 的 Session Header 中。

## 13. Protocol Header 的共享实例边界

ProtocolRequest 的 Anthropic Header 也采用“为本次调用构造字典”的策略。先看 `module/protocol_testing/request.py` 的 `_build_anthropic_headers()`：

```python
def _build_anthropic_headers(
    self,
    *,
    headers: dict[str, str] | None = None,
    anthropic_beta: str | None = None,
) -> dict[str, str]:
    anthropic_headers = {
        "Content-Type": "application/json",
        ANTHROPIC_API_KEY_HEADER: self.config.api_key,
        ANTHROPIC_VERSION_HEADER: ANTHROPIC_VERSION,
    }
    if anthropic_beta:
        anthropic_headers[ANTHROPIC_BETA_HEADER] = anthropic_beta
    if headers:
        anthropic_headers.update(headers)
        anthropic_headers["Content-Type"] = "application/json"
        anthropic_headers[ANTHROPIC_API_KEY_HEADER] = self.config.api_key
        anthropic_headers[ANTHROPIC_VERSION_HEADER] = ANTHROPIC_VERSION
    return anthropic_headers
```

输入是可选调用级 Header 与 beta 标识，状态变化发生在函数内新建的 `anthropic_headers` 字典。输出是完整的本次请求 Header；必需协议字段在合并自定义 Header 后被再次固定。该函数读取 API Key，但不更新 `self.session.headers`。

接下来 `_post_with_anthropic_headers()` 把这个新字典交给 `post()`，并显式关闭 Session Header 继承：

```python
def _post_with_anthropic_headers(
    self,
    path: str,
    payload: dict[str, Any],
    *,
    headers: dict[str, str] | None = None,
    anthropic_beta: str | None = None,
) -> requests.Response:
    return self.post(
        path,
        json=payload,
        headers=self._build_anthropic_headers(
            headers=headers,
            anthropic_beta=anthropic_beta,
        ),
        _inherit_session_headers=False,
    )
```

输入是协议路径、请求体与 Header 选项，输出是 `post()` 的响应。函数负责把协议 Header 作为本次请求参数向下传递，不临时改写再恢复共享 Session。

BaseRequest 在关闭 Session Header 继承时，先用 Session Header 名称构造 None 覆盖，再更新本次 Header。

```mermaid
flowchart TB
    S[共享Session默认Header] --> N[名称映射为None]
    A[Anthropic本次Header] --> M[更新请求Header副本]
    N --> M
    M --> R[仅本次Anthropic请求]
```

### 13.1 已知缺陷回归测试证明什么

测试在同一个 ProtocolRequest 上并发发起：

- Anthropic message。
- OpenAI chat completion。

最终观察 OpenAI 请求看到的 Session Header，不包含 Anthropic 专用 Header。

### 13.2 不能扩大成通用线程安全

这个测试证明特定 Header 路径没有通过 Session Header 污染另一个调用。

它不证明：

- requests.Session 的任意并发操作都线程安全。
- 同一 Session 的 cookie、adapter、连接状态都隔离。
- 任意自定义 Middleware 都不会修改共享状态。

## 14. 三种隔离合同

### 14.1 逻辑隔离

ContextVar 绑定决定 worker 当前看到哪个逻辑 owner 或观察者。

### 14.2 数据隔离

TestContext 通过独立实例拥有不同变量字典与清理栈。

### 14.3 资源隔离

Request 实例通过独立 Session 拥有传输资源，并由 worker finally 关闭。

```mermaid
flowchart TB
    ISO[并发隔离]
    ISO --> L[逻辑隔离<br/>ContextVar]
    ISO --> D[数据隔离<br/>TestContext实例]
    ISO --> R[资源隔离<br/>Request与Session实例]
```

任何一层缺失，都可能产生不同类型的串线。

## 16. 明确未被证明的合同

### 16.1 ProcessPool

没有现有证据证明：

- Context 可以跨进程序列化。
- Request 或 Session 可以跨进程传播。
- `submit_with_context()` 适配 ProcessPoolExecutor。

### 16.2 可变 ContextVar 值

没有测试证明 list、dict 或自定义对象在 Context 副本间深复制。

### 16.3 同一 TestContext 并发写

线程测试使用独立实例。

没有证据证明一个 TestContext 可被多个 worker 同时修改。

### 16.4 共享 Session 的完整线程安全

特定 Header 测试不能覆盖：

- cookie 修改。
- adapter 修改。
- 认证状态修改。
- 自定义 Middleware 写共享状态。

## 17. 常见误解与正确边界

| 常见误解 | 正确理解 |
| --- | --- |
| ContextVar 会复制所有对象 | 它复制执行上下文绑定，不深复制绑定值 |
| 原生 executor.submit 自动传播 | 项目通过 submit_with_context 显式传播 |
| ContextVar 传播创建 TestContext | TestContext 仍需独立实例化或显式绑定 |
| 相同 owner 表示共享同一 Session | 逻辑值可相同，Session 仍可独立 |
| Lock 保护了整个 Request | 当前 Lock 只保护关闭 ID 集合写入 |
| Header 不泄漏表示 Session 完全线程安全 | 只能证明特定 Header 路径 |
| worker 返回表示 Session 一定关闭 | 当前 worker finally 负责 close；其他 worker 函数未必相同 |
| ThreadPool 证据可以推广到 ProcessPool | 进程边界没有现有支持证据 |

## 18. 设计选择与适用边界

### 18.1 提交时复制 Context

收益：

- 每个任务拥有明确快照。
- 父 Context 后续变化不改写已提交任务。
- Future 行为保持原样。

代价：

- 可变绑定值仍可能共享。
- 必须使用包装入口。

### 18.2 worker 内创建 Request

收益：

- Session 所有权清晰。
- close 可以放在同一 worker finally。
- 单次 Header 不需要写入共享 Session。

代价：

- 每个 worker 创建独立客户端与 Session。
- 连接复用范围缩小。

```mermaid
flowchart TB
    CHOICE[并发设计选择]
    CHOICE --> SNAP[提交时Context快照]
    CHOICE --> INST[worker独立Request]
    SNAP --> TRADE[传播确定性与可变值风险]
    INST --> TRADE2[资源隔离与复用代价]
```

## 19. TOC 清晰思考：真正瓶颈是共享可变所有权

只增加线程数量不会自动产生安全并发。

```mermaid
flowchart TD
    A[更多worker] --> B{状态所有权清晰吗}
    B -- 否 --> C[共享Session Header Context混杂]
    C --> D[并发扩大串线概率]
    B -- 是 --> E[逻辑传播与资源隔离分开]
    E --> F[并发事实可解释]
```

本课的 TOC 结论是：

> 并发系统的主要约束不是 worker 数量，而是可变对象是否有唯一、可关闭、可审计的所有者。

因果链可以压缩为：

```text
提交时复制逻辑绑定
→ worker 读取正确身份
→ worker 创建自己的 Request
→ Request 拥有自己的 Session
→ 本次 Header 进入请求副本
→ worker finally 关闭自己的实例
```
