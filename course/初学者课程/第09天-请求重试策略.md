## 0. 从第 8 天读取什么模型

第 8 天已经解释了单次 attempt 可能产生的附加资源生命周期：

- Request 发送一次请求。
- Middleware 可在 POST 发送前触发输入 Capture；`poll_get()` 外层装饰器可在内层成功返回后触发输出 Capture。
- Response、下载文件、临时文件和 worker 各有关闭边界。
- 一次 attempt 结束，不代表同一业务动作一定结束。

Day 9 增加的问题是：

> 如果一次 attempt 遇到可恢复失败，框架是否应该创建下一次 attempt？

```mermaid
flowchart LR
    A[一个业务动作] --> B[attempt 1]
    B --> C{结果是否可恢复}
    C -- 否 --> D[业务动作结束]
    C -- 是 --> E[等待]
    E --> F[attempt 2]
```

本课只解释 Retry。业务状态尚未到终态而继续查询，属于 Day 10 的 Polling。

## 1. 第一性原理：重试是在复制副作用风险

### 1.1 为什么不能看到失败就重试

重试会重复发送请求。对于读取动作，重复通常风险较低；对于写入动作，重复可能造成：

- 重复创建任务。
- 重复扣费。
- 重复写入数据。
- 重复触发外部通知。

```mermaid
flowchart TD
    A[第一次请求结果不确定] --> B[直接再次发送]
    B --> C{服务端是否已完成第一次动作}
    C -- 是 --> D[可能产生重复副作用]
    C -- 否 --> E[第二次请求可能挽救失败]
```

所以 Retry 的第一个问题不是“失败是否暂时”，而是“重复发送是否安全”。

### 1.2 TOC 约束：失败分类与幂等性混在一起

```mermaid
flowchart TD
    A[只判断状态码可重试] --> B[忽略方法副作用]
    B --> C[非幂等写请求被重复]
    C --> D[产生业务污染]
```

正确决策至少需要四个维度：

1. 方法是否允许重试。
2. 失败是否属于可恢复类别。
3. attempt 数量是否还有余额。
4. 等待是否仍在时间预算内。

### 1.3 Retry 的最小决策式

```text
允许创建下一次 attempt
= 方法具备重试资格
∩ 失败属于可恢复条件
∩ attempt 尚未耗尽
∩ 等待仍在预算内
```

```mermaid
flowchart LR
    M[方法资格] --> R{可以重试}
    F[失败分类] --> R
    A[attempt余额] --> R
    B[时间预算] --> R
```

## 2. 业务动作与 attempt

### 2.1 两个粒度不能混淆

| 粒度 | 含义 |
| --- | --- |
| 业务动作 | 调用方希望完成的一次业务意图 |
| attempt | 为完成该意图而进行的一次实际 HTTP 发送 |

```mermaid
flowchart TB
    O[一次业务动作]
    O --> A1[attempt 1]
    O --> A2[attempt 2]
    O --> A3[attempt 3]
```

多个 attempt 可以属于同一个业务动作，但每个实际发送的 attempt 都使用自己的 RequestContext。

### 2.2 为什么每次 attempt 需要独立上下文

不同 attempt 可能具有不同：

- 开始时间。
- 响应或异常。
- 日志记录。
- `attempt_index`。
- 中间件前后状态。

如果复用同一个可变上下文，后一次 attempt 会覆盖前一次事实。

要确认独立 Context 在哪里创建，打开 `common/base_request.py` 的 `_send_with_retry()`。下面是其中的 attempt 工厂聚焦摘录，外层 Group 与 Executor 调用将在第8节继续出现：

```python
def context_factory(attempt_index: int) -> RequestContext:
    context = self._build_request_context(
        method,
        path,
        attach_log=attach_log,
        request_step_name=request_step_name,
        response_step_name=response_step_name,
        protocol=protocol,
        retry_policy=retry_policy,
        polling_policy=polling_policy,
        inherit_session_headers=inherit_session_headers,
        deadline=deadline,
        **kwargs,
    )
    context.attributes["attempt_index"] = attempt_index
    context.attributes["max_attempts"] = retry_policy.max_attempts
    group.bind(context)
    return context
```

输入是当前 attempt 序号和 `_send_with_retry()` 闭包中的请求参数。每次调用都重新执行 `_build_request_context()`，再写入 attempt 属性并绑定 Group，输出一个新的 Context。工厂不发送请求；它只拥有单次 attempt 事实的创建，真实传输仍由随后注入的 `send_once` 完成。

Retry 记录可以共享为同一业务动作的历史列表，但 attempt 的请求事实应独立。

## 3. `RetryPolicy`：冻结的决策输入

### 3.1 Policy 为什么要独立

Retry 决策不应散落在 while 循环的多个条件中。`RetryPolicy` 把决策输入冻结为一个对象。

打开 `common/retry.py`，先看策略字段本身：

```python
class RetryPolicy(BaseModel):
    model_config = ConfigDict(frozen=True, arbitrary_types_allowed=True)

    max_attempts: int = 3
    retry_statuses: frozenset[int] = DEFAULT_RETRY_STATUSES
    retry_exceptions: tuple[type[BaseException], ...] = (
        requests.ConnectionError,
        requests.Timeout,
    )
    backoff: str = "exponential"
    base_delay: float = 0.5
    max_delay: float = 10.0
    jitter: bool = True
    respect_retry_after: bool = True
    max_elapsed: float | None = 30.0
    allowed_methods: frozenset[str] = DEFAULT_ALLOWED_METHODS
    allow_post: bool = False
    idempotency_header: str = "Idempotency-Key"
```

输入是调用方覆盖的策略值，其余字段使用默认值；输出是冻结的Pydantic模型。该对象只表达决策输入，不保存当前attempt、Response、异常或计时状态。

| 字段 | 主要含义 |
| --- | --- |
| `max_attempts` | 最多创建多少次 attempt |
| `retry_statuses` | 哪些 HTTP 状态可恢复 |
| `retry_exceptions` | 哪些异常可恢复 |
| `backoff` | fixed 或 exponential |
| `base_delay` / `max_delay` | 等待计算边界 |
| `jitter` | 是否引入随机抖动 |
| `respect_retry_after` | 是否尊重服务端等待建议 |
| `max_elapsed` | Retry 自身最大经过时间 |
| `allowed_methods` | 默认允许的方法 |
| `allow_post` | 是否显式允许 POST |
| `idempotency_header` | POST 幂等键 Header 名称 |

### 3.2 默认策略表达什么

当前默认可重试状态码为：

```text
429, 500, 502, 503, 504
```

默认允许方法为：

```text
GET, HEAD
```

默认可重试异常包括连接错误和超时，但 SSL 错误与重定向过多会被显式排除。

### 3.3 Policy 验证保护什么

字段校验在策略进入执行器前拒绝无效输入。以 attempt 数量为例：

```python
@field_validator("max_attempts")
@classmethod
def _validate_max_attempts(cls, value: int) -> int:
    if value < 1:
        raise ValueError("max_attempts must be greater than or equal to 1")
    return value
```

输入是构造阶段的 `max_attempts`，输出是验证后的同一个值；小于1时直接阻止Policy创建，因此执行器不需要处理“零次attempt”合同。

字段之间的关系由模型级校验负责：

```python
@model_validator(mode="after")
def _validate_delay_range(self) -> RetryPolicy:
    if self.max_delay < self.base_delay:
        raise ValueError("max_delay must be greater than or equal to base_delay")
    return self
```

这里比较已经完成字段解析的 `base_delay` 与 `max_delay`，保证后续等待截断不会得到自相矛盾的范围。其他验证器继续约束非负delay、正数`max_elapsed`、backoff枚举和非空幂等Header；这些校验只保护策略一致性，不证明请求适合重试。

```mermaid
flowchart TD
    P[RetryPolicy输入] --> A{max_attempts >= 1}
    A --> B{delay范围有效}
    B --> C{backoff类型有效}
    C --> D{idempotency_header非空}
    D --> E[冻结策略对象]
```

Policy 冻结后，一次业务动作中的所有 attempt 读取同一套决策合同。

## 4. 方法与幂等边界

### 4.1 默认允许读取方法

`GET` 和 `HEAD` 默认进入重试资格判断，因为它们通常不应改变服务端业务状态。

### 4.2 非 POST 的其他方法

如果方法不在 `allowed_methods` 中，且不是 POST，当前实现直接判定为不允许重试。

### 4.3 POST 的三条合法路径

POST 只有满足以下任一条件才允许重试：

1. POST 已被加入 `allowed_methods`。
2. `allow_post=True`。
3. 请求 Header 中存在配置的幂等键。

打开 `common/retry.py` 中的 `is_method_retry_allowed()`，可以看到三条路径的实际优先级：

```python
def is_method_retry_allowed(method: str, kwargs: Mapping[str, Any], policy: RetryPolicy) -> bool:
    normalized_method = method.upper()
    if normalized_method in {name.upper() for name in policy.allowed_methods}:
        return True

    if normalized_method != "POST":
        return False

    if policy.allow_post:
        return True

    headers = kwargs.get("headers") or {}
    header_names = {str(name).lower() for name in dict(headers).keys()}
    return policy.idempotency_header.lower() in header_names
```

输入是method、最终请求kwargs和Policy。方法名与Header名都按大小写无关方式比较；输出只是一项客户端资格判断。函数不检查Header值，也不与服务端确认幂等实现，所以`True`只表示允许Executor进入多attempt决策。

### 4.4 幂等键证明到什么程度

框架只能观察 Header 是否存在，不能仅凭 Header 证明服务端真的实现了幂等语义。

```mermaid
flowchart LR
    A[请求携带幂等键] --> B[客户端允许重试]
    B -.不能自动证明.-> C[服务端绝不会重复副作用]
```

服务端幂等合同仍属于业务协议责任。

## 5. 失败分类：Response 与 Exception

### 5.1 Response 路径

请求成功返回 Response 后，`should_retry_response` 只检查状态码是否在 `retry_statuses` 中。

```python
def should_retry_response(response: requests.Response, policy: RetryPolicy) -> bool:
    return response.status_code in policy.retry_statuses
```

输入是当前Response和Policy，输出是布尔分类。函数不关闭Response、不等待，也不解释业务Body；即使返回`True`，attempt数量和时间预算仍可能阻止下一次发送。

```mermaid
flowchart LR
    A[收到Response] --> B{状态码可重试}
    B -- 否 --> C[返回当前Response]
    B -- 是 --> D[评估attempt和时间预算]
```

Response 路径已经拥有一个可返回的结果，因此预算耗尽时可能返回当前或最后一个 Response。

### 5.2 Exception 路径

发送过程抛出异常后，`should_retry_exception` 判断异常类型。

```python
def should_retry_exception(error: BaseException, policy: RetryPolicy) -> bool:
    if isinstance(error, (requests.exceptions.SSLError, requests.exceptions.TooManyRedirects)):
        return False
    return isinstance(error, policy.retry_exceptions)
```

输入是当前传输异常与Policy。SSL错误和重定向过多先被显式否决，其余异常才按配置元组分类；输出仍只是资格，不吞掉或替换原异常。

```mermaid
flowchart TD
    A[发送抛异常] --> B{SSL或重定向过多}
    B -- 是 --> C[不可重试并重新抛出]
    B -- 否 --> D{属于retry_exceptions}
    D -- 否 --> C
    D -- 是 --> E[评估attempt和时间预算]
```

### 5.3 为什么两条路径终态不同

| 路径 | 已有结果 | 耗尽时常见终态 |
| --- | --- | --- |
| Response | 有最后 Response | 返回最后或当前 Response |
| Exception | 没有 Response | 重新抛出原异常 |

外部 deadline 被耗尽时会使用 `RetryDeadlineExceeded` 表达预算终止，并可携带 `last_response`。

## 6. 等待如何计算

### 6.1 `Retry-After` 优先

如果启用 `respect_retry_after` 且 Response 提供合法 `Retry-After`，等待优先采用服务端建议。

要确认“合法”如何判定，打开 `common/retry.py` 中的 `parse_retry_after()`：

```python
def parse_retry_after(value: str | None, *, now: datetime | None = None) -> float | None:
    if value is None:
        return None

    stripped_value = value.strip()
    if not stripped_value:
        return None

    try:
        delay = float(stripped_value)
    except ValueError:
        delay = None
    if delay is not None:
        if delay < 0:
            return None
        return delay

    try:
        retry_datetime = parsedate_to_datetime(stripped_value)
    except (TypeError, ValueError, IndexError, OverflowError):
        return None

    if retry_datetime.tzinfo is None:
        retry_datetime = retry_datetime.replace(tzinfo=UTC)

    now_datetime = now or datetime.now(UTC)
    if now_datetime.tzinfo is None:
        now_datetime = now_datetime.replace(tzinfo=UTC)

    return max(0.0, (retry_datetime - now_datetime).total_seconds())
```

输入是Header文本与可注入的当前时间。函数先尝试非负秒数，再尝试HTTP日期；空值、负数与解析失败返回`None`，过去日期被夹到0秒。输出只是等待建议或无建议，不执行sleep，也不决定是否还有预算。

`Retry-After` 可以是：

- 秒数。
- HTTP 日期。

非法值会回退到本地 backoff。

### 6.2 fixed 与 exponential

```text
fixed:
delay = base_delay

exponential:
delay = base_delay × 2^(attempt_index - 1)
```

等待规则集中在 `calculate_retry_delay()`。先看从服务端建议到本地delay上限的部分；jitter尾部留到下一小节：

```python
def calculate_retry_delay(
    policy: RetryPolicy,
    attempt_index: int,
    *,
    response: requests.Response | None = None,
    random_uniform: Callable[[float, float], float] = random.uniform,
    now: datetime | None = None,
) -> float:
    retry_after_delay = None
    if policy.respect_retry_after and response is not None:
        retry_after_delay = parse_retry_after(response.headers.get("Retry-After"), now=now)

    use_jitter = policy.jitter
    if retry_after_delay is not None:
        delay = retry_after_delay
        use_jitter = False
    elif policy.backoff == "fixed":
        delay = policy.base_delay
    else:
        delay = policy.base_delay * (2 ** max(0, attempt_index - 1))

    delay = min(policy.max_delay, delay)
```

输入是Policy、当前attempt序号和可选Response。合法`Retry-After`优先并关闭jitter；否则选择fixed或exponential，最后统一受`max_delay`限制。该摘录尚未返回结果，最终随机化与非负保护由紧接着的源码完成。

```mermaid
flowchart TD
    A[计算等待] --> B{存在合法Retry-After}
    B -- 是 --> C[采用服务端等待且不加jitter]
    B -- 否 --> D{fixed或exponential}
    D --> E[得到本地delay]
    E --> F[限制到max_delay]
    F --> G{是否jitter}
    G -- 是 --> H[在0到delay之间取值]
    G -- 否 --> I[使用delay]
```

### 6.3 jitter 的作用

当大量客户端同时失败时，如果等待完全一致，它们可能再次同时发起请求。jitter 用于打散下一次 attempt 时间。

`calculate_retry_delay()` 的尾部是：

```python
if use_jitter and delay > 0:
    delay = random_uniform(0, delay)
return max(0.0, delay)
```

输入是前一小节得到的delay和`use_jitter`标志。启用时使用可注入随机函数在0到delay之间取值，最后保证非负并返回秒数。函数仍不sleep；真正等待由RetryExecutor拥有。

```mermaid
flowchart LR
    A[多个客户端同时失败] --> B[相同固定等待]
    B --> C[再次同时请求]
    C --> D[形成流量尖峰]
    A --> E[加入jitter]
    E --> F[请求时间分散]
```

## 7. 三种预算

### 7.1 attempt 数量预算

`max_attempts` 包含第一次发送，而不是“额外重试次数”。

```mermaid
flowchart LR
    A[max_attempts = 3] --> B[attempt 1]
    B --> C[attempt 2]
    C --> D[attempt 3]
```

### 7.2 Retry 自身经过时间

`max_elapsed` 从 Retry 开始时计时，评估“当前已耗时 + 下一次等待”是否仍在限制内。

```text
当前经过时间 + wait_seconds <= max_elapsed
```

对应判断位于 `RetryExecutor._can_retry_within_elapsed()`：

```python
def _can_retry_within_elapsed(
    self,
    policy: RetryPolicy,
    started_at: float,
    wait_seconds: float,
) -> bool:
    if policy.max_elapsed is None:
        return True
    return (self.monotonic() - started_at + wait_seconds) <= policy.max_elapsed
```

输入是Retry开始时刻与下一次等待。函数通过注入的单调时钟计算“已耗时+将等待”，输出是否仍在Policy局部预算内；它不扣减外部deadline，也不执行等待。

Response 路径若不再允许等待，会返回当前 Response；Exception 路径会重新抛出当前异常。

### 7.3 外部 deadline

RetryExecutor 还可以接收外部绝对 deadline。这个 deadline 不属于 RetryPolicy，而是上层调用者给出的更强时间边界。

剩余时间的计算与入口门禁由两个函数完成：

```python
def remaining(self, deadline: float | None) -> float | None:
    if deadline is None:
        return None
    return deadline - self.monotonic()


def require_remaining(
    self,
    deadline: float | None,
    *,
    last_response: requests.Response | None = None,
) -> float | None:
    remaining = self.remaining(deadline)
    if remaining is not None and remaining <= 0:
        raise RetryDeadlineExceeded(last_response=last_response)
    return remaining
```

输入是绝对deadline和可选的最后Response。`remaining()`只计算差值；`require_remaining()`在无正剩余时间时抛出带`last_response`的终止异常。它们在创建实际attempt前执行，因此外部预算可以阻止新的发送。

```mermaid
flowchart TB
    P[RetryPolicy.max_elapsed] --> R[Retry局部预算]
    D[外部deadline] --> G[上层总预算]
    R --> A[能否创建下一attempt]
    G --> A
```

Day 10 的 Polling 会把统一 deadline 传入每次轮询请求内部的 Retry。

### 7.4 为什么等待必须小于剩余时间

当前实现要求 `wait_seconds < remaining`。如果等待已经等于或超过剩余时间，继续 sleep 只会确定性越界。

```python
def _can_wait_within_deadline(
    self,
    deadline: float | None,
    wait_seconds: float,
) -> bool:
    remaining = self.remaining(deadline)
    return remaining is None or wait_seconds < remaining
```

输入是绝对deadline与即将发生的等待。没有外部deadline时返回`True`，否则使用严格小于比较；函数不sleep，只给Executor返回是否允许等待。

### 7.5 超时参数也要被 deadline 截断

`clamp_timeout` 会把单次发送 timeout 限制在剩余时间内；元组 timeout 的每个值也分别被截断。

```python
def clamp_timeout(
    self,
    timeout: Any,
    deadline: float | None,
) -> Any:
    remaining = self.require_remaining(deadline)
    if remaining is None:
        return timeout
    if isinstance(timeout, tuple):
        return tuple(
            remaining if value is None else min(float(value), remaining)
            for value in timeout
        )
    if timeout is None:
        return remaining
    return min(float(timeout), remaining)
```

输入是单次请求timeout和外部deadline。无deadline时原样返回；有deadline时，标量、`None`和元组分别转换为不超过剩余时间的值。输出会进入新Context的`kwargs["timeout"]`，函数本身不创建Context或执行网络请求。

```mermaid
flowchart LR
    A[请求原timeout] --> B[与deadline剩余时间比较]
    B --> C[采用较小值]
```

这避免单个 attempt 的网络 timeout 超过上层总预算。

## 8. `RetryExecutor` 的所有权

### 8.1 它负责什么

`RetryExecutor` 只拥有重试编排：

- 判断方法资格。
- 创建 attempt 循环。
- 调用 `context_factory`。
- 调用 `send_once`。
- 记录重试原因与等待。
- 检查 attempt 和时间预算。
- sleep 后进入下一 attempt。

### 8.2 它不负责什么

- 构造业务 payload。
- 实现 Middleware。
- 直接调用 `requests.Session`。
- 解释业务成功。
- 管理 Polling 业务状态。

```mermaid
flowchart LR
    B[BaseRequest] -->|注入context_factory与send_once| R[RetryExecutor]
    R -->|每次attempt| S[单次发送主线]
    S -->|Response或异常| R
```

### 8.3 为什么使用注入函数

RetryExecutor 不需要知道 RequestContext 具体如何构造，也不需要知道 Middleware 和 transport 如何工作。它只调用稳定的函数边界。

这组边界由 `BaseRequest._send_with_retry()` 在调用Executor时显式传入：

```python
return self.retry_executor.execute(
    method=first_context.method,
    request_kwargs=self._kwargs_with_session_headers(first_context.kwargs),
    policy=retry_policy,
    context_factory=context_factory,
    send_once=self._send,
    attach_records=self._attach_retry_records,
    context_recorder=context_recorder,
    on_wait=group.add_retry_wait,
    deadline=deadline,
)
```

输入包括规范化method与kwargs、Policy，以及Context工厂、单次发送、记录附加和等待观察函数。Executor编排这些能力，但不知道Session与Middleware细节；Response或异常仍由`self._send`产生。输出是Executor选定的最终Response，异常终态则沿调用边界抛回BaseRequest。

这保持了依赖方向：Retry 编排依赖抽象调用点，而不是反向拥有 BaseRequest。

## 9. 一次执行的真实顺序

要把前面的资格、预算和注入边界连接起来，打开 `RetryExecutor.execute()`。先看从方法门禁到单次发送的前半段；Response与Exception分支留到第10节：

```python
retry_records: list[RetryAttemptRecord] = []

if not is_method_retry_allowed(method, request_kwargs, policy):
    self.require_remaining(deadline)
    context = context_factory(1)
    self._prepare_context(context, policy, 1, retry_records)
    self._record_context(context_recorder, context)
    return send_once(context)

started_at = self.monotonic()
last_response: requests.Response | None = None

for attempt_index in range(1, policy.max_attempts + 1):
    self.require_remaining(deadline, last_response=last_response)
    context = context_factory(attempt_index)
    self._prepare_context(context, policy, attempt_index, retry_records)
    self._record_context(context_recorder, context)

    try:
        response = send_once(context)
```

输入是BaseRequest注入的请求事实和函数边界。方法不允许时仍先检查deadline、创建一个实际Context并发送一次；允许时才启动Retry局部计时，并在每轮发送前检查外部deadline、创建独立Context、写入共享记录引用。摘录停在单次发送结果产生处，接下来必须分别处理Exception与Response，不能把两条终态合并。

### 9.1 RetryAttemptRecord

每次决定继续时，记录包含：

```python
class RetryAttemptRecord(BaseModel):
    model_config = ConfigDict(frozen=True)

    attempt_index: int
    max_attempts: int
    reason: str
    wait_seconds: float
    response_status_code: int | None = None
    exception_type: str | None = None
    exception_message: str | None = None
```

构造输入是本次继续重试的序号、原因、计划等待及Response或Exception诊断字段，输出是冻结记录。它描述“为什么准备进入下一attempt”，不代表下一attempt已经创建或等待已经完成。

- `attempt_index`。
- `max_attempts`。
- 原因文本。
- 等待秒数。
- Response 状态码，或异常类型与消息。

### 9.2 记录附加到哪个上下文

当前 attempt 的 RequestContext 会保存共享的 `retry_records` 列表，并附加到日志观察接口。

`context_recorder` 只保留最新上下文，使 BaseRequest 在 Retry 完成后能够读取最后 attempt 的事实。

对应写入由Executor的两个辅助函数完成：

```python
@staticmethod
def _prepare_context(
    context: RequestContext,
    policy: RetryPolicy,
    attempt_index: int,
    retry_records: list[RetryAttemptRecord],
) -> None:
    context.attributes["attempt_index"] = attempt_index
    context.attributes["max_attempts"] = policy.max_attempts
    context.attributes["retry_records"] = retry_records


@staticmethod
def _record_context(
    context_recorder: list[RequestContext] | None,
    context: RequestContext,
) -> None:
    if context_recorder is not None:
        context_recorder[:] = [context]
```

`_prepare_context()`把同一记录列表引用放入每个独立Context，`_record_context()`则用切片赋值把外部列表更新为仅含最新Context。前者保存业务动作内的共享历史，后者提供最终观察入口；两者都不创建attempt或执行发送。

## 10. 终态决策

### 10.1 方法不允许重试

即使传入 RetryPolicy，RetryExecutor 也只执行一次实际发送。实现层仍会先构造一个不发送的 `first_context`，随后由 `context_factory` 创建唯一的实际 attempt Context；因此是“两个 Context 对象、一次 Session 发送”，而不是“只创建一个 Context”。

`first_context` 在 `BaseRequest._send_with_retry()` 中先于Executor创建：

```python
first_context = self._build_request_context(
    method,
    path,
    attach_log=attach_log,
    request_step_name=request_step_name,
    response_step_name=response_step_name,
    protocol=protocol,
    retry_policy=retry_policy,
    polling_policy=polling_policy,
    inherit_session_headers=inherit_session_headers,
    deadline=deadline,
    **kwargs,
)
```

输入与实际attempt工厂相同，但这个对象只向Group和Executor提供规范化method、path、protocol与kwargs，没有调用`group.bind(first_context)`，也没有传给`self._send`。因此不能把每个被构造的Context都计为一次实际发送。

Policy 的存在不等于一定发生重试，attempt 数量必须按实际 Session 发送次数计算。

### 10.2 第一次成功

Response 不在 `retry_statuses` 中，立即返回。

Response路径的完整决策片段位于`execute()`中：

```python
last_response = response
if attempt_index >= policy.max_attempts or not should_retry_response(response, policy):
    attach_records(context, retry_records)
    return response

wait_seconds = calculate_retry_delay(policy, attempt_index, response=response)
retry_records.append(
    RetryAttemptRecord(
        attempt_index=attempt_index,
        max_attempts=policy.max_attempts,
        reason=retry_reason_for_response(response),
        wait_seconds=wait_seconds,
        response_status_code=response.status_code,
    )
)
attach_records(context, retry_records)
if not self._can_retry_within_elapsed(policy, started_at, wait_seconds):
    return response
if not self._can_wait_within_deadline(deadline, wait_seconds):
    raise RetryDeadlineExceeded(last_response=response)
self.sleeper(wait_seconds)
self._notify_wait(on_wait, wait_seconds)
```

输入是当前Response、attempt序号和两个时间预算。不可重试或数量耗尽时直接返回；可重试时先创建记录，再分别检查`max_elapsed`与外部deadline，只有两者都允许才sleep。Response路径始终保有可返回对象，所以Policy局部预算不足时返回当前Response，而外部deadline不足时抛出携带该Response的专用异常。

### 10.3 重试后成功

某次 attempt 返回不可重试状态，例如 200，Retry 返回该 Response。

### 10.4 Response 耗尽

达到 `max_attempts` 时，即使最后 Response 仍属于可重试状态，也返回最后 Response，由上层决定是否接受。

### 10.5 Exception 耗尽

达到最大 attempt 或异常不可重试时，重新抛出原异常。

Exception路径位于`send_once(context)`的`except`中：

```python
except Exception as error:
    if attempt_index >= policy.max_attempts or not should_retry_exception(error, policy):
        attach_records(context, retry_records)
        raise

    wait_seconds = calculate_retry_delay(policy, attempt_index)
    retry_records.append(
        RetryAttemptRecord(
            attempt_index=attempt_index,
            max_attempts=policy.max_attempts,
            reason=retry_reason_for_exception(error),
            wait_seconds=wait_seconds,
            exception_type=type(error).__name__,
            exception_message=str(error),
        )
    )
    attach_records(context, retry_records)
    if not self._can_retry_within_elapsed(policy, started_at, wait_seconds):
        raise
    if not self._can_wait_within_deadline(deadline, wait_seconds):
        raise RetryDeadlineExceeded(last_response=last_response) from error
    self.sleeper(wait_seconds)
    self._notify_wait(on_wait, wait_seconds)
    continue
```

输入是`send_once`抛出的原普通异常。不可重试、数量耗尽或Policy局部预算不足时都使用裸`raise`保留当前异常；只有外部deadline阻止等待时，才转换为`RetryDeadlineExceeded`并保留异常因果链。等待完成后`continue`进入下一轮，而不是复用当前Context。

### 10.6 外部 deadline 耗尽

在发送前无剩余时间，或下一次等待无法放入 deadline 时，抛出 `RetryDeadlineExceeded`；如果已有 Response，会携带 `last_response`。

```python
class RetryDeadlineExceeded(TimeoutError):
    def __init__(
        self,
        *,
        last_response: requests.Response | None = None,
    ) -> None:
        super().__init__("retry deadline exhausted")
        self.last_response = last_response
```

构造输入是可选的最后Response，输出是一个明确的预算终止异常。它不把最后Response解释成成功，也不关闭该Response；上层Polling可以读取这个事实并决定自己的终态。

```mermaid
flowchart TD
    A[attempt结果] --> B{Response还是Exception}
    B -- Response --> C{成功/不可重试/耗尽}
    C -- 是 --> D[返回当前或最后Response]
    C -- 否 --> E[等待并下一attempt]
    B -- Exception --> F{不可重试或耗尽}
    F -- 是 --> G[重新抛原异常]
    F -- 否 --> E
    E --> H{外部deadline允许}
    H -- 否 --> I[RetryDeadlineExceeded]
```

## 11. Retry 与 Polling 的边界

### 11.1 Retry 的问题

> 同一次业务动作中的单次请求失败，是否值得重新发送？

### 11.2 Polling 的问题

> 请求成功返回了业务状态，但任务尚未到终态，是否应该再次查询？

```mermaid
flowchart TB
    P[Polling业务状态循环]
    P --> Q1[第1次查询]
    P --> Q2[第2次查询]
    Q1 --> R1[查询内部Retry attempts]
    Q2 --> R2[查询内部Retry attempts]
```

Retry 可以嵌套在每次 Polling 请求内部，但不能替代 Polling。

| 维度 | Retry | Polling |
| --- | --- | --- |
| 触发原因 | 请求失败或可重试状态码 | 业务状态仍为 pending |
| 循环对象 | 同一 HTTP 动作的 attempt | 多次业务状态查询 |
| 等待依据 | Retry-After 或 backoff | poll_interval |
| 终态 | Response、异常、耗尽 | success、failure、unknown、timeout |

## 12. 证据边界

### 12.1 Policy 单元测试证明

- 字段验证和冻结合同。
- Retry-After 解析。
- backoff、max_delay 和 jitter。
- 方法与幂等资格。
- Response 与异常分类。

### 12.2 Executor 测试证明

- 可重试 Response 或异常进入下一 attempt。
- 最大 attempt 的 Response/异常终态。
- `max_elapsed` 阻止等待。
- 每次 attempt 使用独立上下文。

### 12.3 离线分类测试证明

- transient GET 在真实 loopback 链路中被挽救。
- Retry-After 被尊重。
- 幂等 POST 可以重试。
- 非幂等 POST 保持单次发送。

### 12.4 不能证明什么

- 所有服务端都正确实现幂等键。
- Retry 可以修复业务失败。
- Polling 的状态迁移与总 deadline 正确。
- 重试一定比快速失败更合适。

```mermaid
flowchart TB
    E[Retry证据]
    E --> P1[证明客户端重试决策]
    E --> P2[证明attempt与等待边界]
    E -.不能证明.-> N1[服务端幂等实现]
    E -.不能证明.-> N2[业务状态最终成功]
```

## 13. 常见误解与向第 10 天交付

### 13.1 常见误解

| 误解 | 准确解释 |
| --- | --- |
| `max_attempts=3` 表示重试三次 | 它包含第一次发送，总共最多三次 attempt |
| POST 永远不能重试 | 显式允许或存在幂等键时可以进入资格 |
| 503 一定会重试 | 还需要方法、attempt 和时间预算同时允许 |
| Retry-After 一定有效 | 非法值会回退到本地 backoff |
| 最后一个 503 会抛异常 | Response 路径耗尽时返回最后 Response |
| Retry 就是 Polling | Retry恢复请求，Polling等待业务终态 |
