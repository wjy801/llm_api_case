# 接口测试框架源码架构与证据链六周课程

**课程副标题：基于现有项目实现的调用链、状态、资源所有权与机器证据学习。**

## 1. 课程定位

本文档是当前仓库接口测试框架课程的**唯一课程合同**。课程共6周、30个学习日，面向具备基础接口自动化经验的中级测试开发工程师，学习对象仅限仓库中已经存在并通过公开入口使用的实现。

课程目标不是重新开发一套框架，而是建立可复述、可核验的实现模型：

1. 从公开入口定位到真实实现文件。
2. 沿调用链解释对象、状态、数据和资源如何流转。
3. 使用已有离线测试、collect-only和机器产物验证当前实现合同。
4. 区分业务执行事实、Runner事实、Quality事实和Reporting视图。
5. 解释依赖方向、资源所有权、安全边界和产物职责。

### 明确边界

- **只学习现有实现，不要求新增业务功能或框架能力。**
- **不做故障注入，不故意改坏代码、Manifest、JSONL、数据库或报告文件。**
- 不要求重新实现Request、Retry、Polling、Runner、Quality或Reporting。
- 不把修复仓库已知缺陷作为结业门禁。
- 不执行未经授权的真实Smoke、付费接口或共享业务状态用例。
- 不直接修改Jenkins使用的持久化Flaky数据库。

### 目标学员与建议前置能力

- 能独立使用Python虚拟环境并阅读类型标注、上下文管理器和基础并发代码。
- 能使用pytest运行测试、选择nodeid，并解释fixture与setup/call/teardown基础生命周期。
- 能使用requests或同类HTTP客户端区分请求、响应、传输异常和业务断言失败。
- 能阅读JSON、JSONL、JUnit XML和基础SQLite结构。
- 对ContextVar、状态机、Hash、Manifest或Jenkins不熟悉时可以学习，但必须先通过准备度检查并按周门禁推进。

### Day 0准备度检查

Day 0不是新增学习日，而是进入课程前的准备度门禁。学员应完成以下六项检查：

1. 使用nodeid运行一个指定pytest用例，并说明选择范围。
2. 解释一个fixture的创建、使用和清理时机。
3. 区分HTTP业务失败、传输异常和断言失败。
4. 阅读一段包含类型标注和上下文管理器的Python代码。
5. 区分JSON对象、JSONL记录流和JUnit XML测试结果。
6. 说明线程共享对象可能产生的数据竞争或资源污染。

准备度不足不阻止阅读第1～3周，但进入第4周前必须补齐对应基础能力。

## 2. 第一性原理学习模型

复杂框架学习的本质不是记住文件名，而是回答七个稳定问题：

```text
问题由谁接收
→ 数据经过哪些对象
→ 状态由谁维护
→ 副作用由谁拥有
→ 结果由什么证据证明
→ 哪些层不能互相替代
→ 为什么选择当前方案，何时应换方案
```

当前项目的主链路为：

```text
module业务用例
→ common请求、可靠性、上下文和中性观察接口
→ run_master.py / run_orchestration执行编排
→ quality事实、语义、指标和Flaky状态
→ pipeline_reporting / Jenkins报告与发布
```

必须保持的核心依赖方向：

```text
module -> common
quality -> common.runtime_hooks
run_master -> run_orchestration
common -X-> quality
```

每天使用同一学习闭环：

```text
限定一个实现问题
→ 找到公开入口
→ 沿真实调用顺序阅读
→ 标注对象、状态、资源与副作用
→ 运行已有离线验证
→ 把测试或产物映射回实现节点
→ 对比一个替代方案与不适用条件
→ 输出图表并迁移到相邻现有场景
```

## 3. TOC学习策略

当前学习约束是抽象模型固化速度，而不是技术内容不足：

```text
第4～6周抽象概念连续输入
→ 前一模型尚未固化就进入下一证据层
→ 术语、关系和证据同时累积
→ 学员依赖模板完成图表
→ 能复述当前实现但难以独立迁移
```

当前更直接的TOC约束已经转为：

```text
每日成果输入过多
→ 时间被表格、重复制图和记录占用
→ 源码追踪与测试证据核对时间下降
→ 学员重新依赖模板完成课程
→ 看似产出完整，但无法独立解释真实实现
```

课程按实现所有权拆成30天，每天只建立一个主要模型，最多包含一个强相关辅助模型。每课只要求一个主成果，图、表、状态说明和设计取舍均作为同一成果的章节；页面中的其他输入只作为可选草稿。每周最后一天在本周已有主成果中完成一次综合更新，不新增四份独立提交物。

| 环节 | 建议时间 |
| --- | --- |
| 实现问题、公开入口与文件地图 | 15～20分钟 |
| 源码调用链、对象、状态与所有权追踪 | 60～80分钟 |
| 现有测试或机器产物验证 | 25～35分钟 |
| 设计选择与适用边界 | 10～15分钟 |
| 主成果增量与证据位置记录 | 10～20分钟 |
| 自测与退出门禁 | 5～10分钟 |

普通日总预算为2～3小时。Day5、10、15、20和25的30～45分钟复盘包含在当天2.5～3小时内，不再叠加到日课之外；Day29与Day30安排3～4小时，并分别包含材料整合和最终复盘答辩。

## 5. 学习规则、设计边界与评分

- 默认只执行`tests/`和`module/offline_framework_example/`中的确定性离线内容。
- `module/smoke`默认只执行collect-only，不调用真实业务接口。
- 阅读代码时沿调用链进入下一层，不按目录从头到尾背诵。
- 现有测试、页面推演器和机器产物用于验证实现，不用于人为制造异常。
- Flaky课程只使用CLI帮助、已有专项测试、测试夹具或临时SQLite数据库。
- Day30操作`reports/`前必须先备份需要保留的本地产物，完成后恢复。
- 不把`.env`、API Key、真实响应、数据库或账号数据写入学习成果。
- 测试数量是日期化快照，用于识别变化，不是永远不变的业务合同。
- `README.md`是架构基线，`FRAMEWORK_TEST_SPEC.md`是用例与质量语义基线。

### 5.1 每课设计选择与适用边界

30个日课都必须回答一个关键设计选择：当前方案是什么、替代方案是什么、为什么在本仓库采用当前方案、什么条件下当前方案不再适用。对于事实读取类课程，可以比较“由当前层负责”与“交给相邻层负责”的后果，不强行扩展新的技术产品。

### 5.2 每周复盘产出

Day5、10、15、20和25末尾预留30～45分钟，但复盘时间已经包含在当天总预算内。复盘不新增独立成果：学员只需在本周已有主成果中完成一次综合更新，至少包含一处关系修正、一处相邻场景迁移和必要的术语关系变化。Day30在同一答辩包中完成第6周及全课程关系复盘。

30个日课各保留一条强制成果证据记录，用于填写成果路径，或记录口头验收时间、追问与一个可核对事实。其他页面输入统一标记为可选草稿并默认折叠；空白不会阻断门禁。文件成果与口头记录二选一，不要求重复填写两份证明。

### 5.3 六维评分量表

| 维度 | 0分 | 1分 | 2分 |
| --- | --- | --- | --- |
| 源码定位 | 无法找到入口或实现 | 可按材料找到 | 可从测试或公开入口独立追踪 |
| 调用链与状态 | 只能复述名词 | 能说明主路径 | 能解释分支、终态和终止责任 |
| 所有权 | 状态和资源归属混乱 | 能列出主要所有者 | 能解释转移、清理和禁止越权 |

# 第1周：建立项目实现地图

## 本周目标

从框架使用者视角理解一条离线业务用例如何组合Test、Task、Request和Assertions，并建立业务层、公共层、编排层、质量层和报告层的总体边界。

## Day 1：项目边界与执行主线

- **实现问题**：一个测试目标如何从稳定入口进入业务用例、公共能力和执行编排。
- **核心入口**：`README.md`、`FRAMEWORK_TEST_SPEC.md`、`run_master.py`。
- **离线验证**：对`module/offline_framework_example`执行collect-only，观察入口提前返回和分池摘要。
- **术语使用**：学习统一术语表的所属层、首次学习日和“不等同于”字段，本日只要求掌握首周术语。
- **可核验产出**：五层架构图、稳定入口表、collect-only提前返回位置和准备度检查记录。

## Day 2：离线黄金路径与模块四件套

- **实现问题**：Test、Task、Request、Assertions如何完成一次规范离线业务调用。
- **核心入口**：`module/offline_framework_example/`中的黄金路径文件。
- **离线验证**：运行黄金nodeid和对应离线服务测试。
- **可核验产出**：四件套完整调用链、输入输出表和资源所有权表。

## Day 3：模块标准结构与任务能力

- **实现问题**：模块目录如何分配公开用例、任务编排和请求能力。
- **核心入口**：`common/base_task.py`、模块Task与模块公开导出。
- **离线验证**：运行现有模块结构与Task相关测试。
- **可核验产出**：模块目录职责表、Task能力路由图和禁止越层清单。

## Day 4：测试生命周期断言与报告步骤

- **实现问题**：pytest的setup、call、teardown如何与断言及Allure步骤对应。
- **核心入口**：fixtures、`common/base_assertions.py`、模块断言和报告步骤。
- **离线验证**：运行已有断言与报告相关离线测试并查看原始Allure结果。
- **可核验产出**：pytest生命周期与报告步骤对照表、断言职责边界。

## Day 5：离线测试分层与分类用例

- **实现问题**：服务级、能力级和分类级测试分别证明什么。
- **核心入口**：`tests/test_offline_service.py`及离线分类测试。
- **离线验证**：运行离线服务测试并对分类测试执行collect-only。
- **可核验产出**：三层测试策略图、分类文件职责表和第1周完整调用链。
- **周复盘30～45分钟**：补充首周术语关系、至少一条错误订正，并把黄金路径迁移到另一个现有离线分类场景。

- [ ] 能解释业务层为什么不能直接承担Runner或Quality职责。

# 9. 结业能力评估

5. 解释Quality开启时Runtime Hooks、Adapter、分片、归并、Semantic和Metrics链路。
6. 区分JUnit、Allure、Quality和Pipeline Summary分别回答的问题。

# 10. 课程使用建议

- 按周推进，不建议跳过周门禁直接进入Quality或Reporting。
- 每天先确定一个实现问题，再打开3～6个核心文件，避免无边界遍历目录。
- 命令执行后必须把输出映射回对象、状态或产物节点，不能只记录“运行成功”。
- 页面中的数量与状态以本轮实际输出为准，历史快照只用于比较。
- 当仓库并行更新时，以当前`README.md`、`FRAMEWORK_TEST_SPEC.md`和公开接口为准，记录日期与工作树状态。
- 旧四周总纲仅提供迁移链接，不再承担课程内容合同。
