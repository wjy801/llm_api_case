## 核心问题

> Flaky 数据库突然不可用时，原始 pytest 结果、历史、状态和 Pipeline Summary 分别会发生什么？

## 从统一案例中的一个现象开始

Case C 已由 pytest 完成执行并产生原始 FAIL。Quality 正在收尾：

```text
pytest 原始结果已确定：FAIL
P0 事实已归并
→ Flaky History 准备连接数据库
→ 数据库抛出 OSError("database unavailable")
```

此时有两个风险：

- 如果 Flaky 异常覆盖主测试结果，诊断子系统会改变 pytest 的事实所有权。
- 如果摘要把缺失 Flaky 报告显示为 0 个问题，又会把诊断失败伪装成健康。

## 先做判断

请先写下答案和理由：

1. 数据库失败后，Case C 的 pytest FAIL 应改成 PASS、ERROR，还是保持 FAIL？
2. History 导入未返回可评估结果时，State 阶段应该继续读取数据库吗？
3. `flaky-evaluation.json` 缺失时，Summary 能否显示“0 个 Flaky 变化”？

## 为什么已有解释不够

前面各课从模块内部解释了正确行为，却默认入口会被调用、数据库可用、报告会生成。真实框架还需要控制：

- 功能是否启用，以及 State 是否具备 History 前置。
- 多个 Quality 阶段的执行顺序与数据依赖是否被混淆。
- Flaky 自身异常是否向外破坏 pytest 主结果。
- 报告消费者如何保留“不可用”而不是填充零。

这些系统边界决定 Flaky 是观察与治理子系统，而不是测试执行权威。

## 核心概念

### 1. 功能开关（Feature Switch）

当前相关开关默认都关闭，并具有依赖关系：

```text
QUALITY_ENABLE
└─ QUALITY_FLAKY_HISTORY_ENABLE
   └─ QUALITY_FLAKY_STATE_ENABLE
```

- History 只有在总 Quality 和 History 开关都启用时才启用。
- State 只有在 History 已启用且 State 开关请求启用时才启用。
- History 还要求一个绝对、持久化且通过校验的数据库路径；配置无效时产生 warning/NO_DATA，不回退到随意的临时数据库。

### 2. Fail-open（故障开放）

在本框架中，fail-open 表示 Flaky 导入或评估出现未处理异常时：

```text
捕获异常并输出诊断消息
→ 不向上覆盖 pytest 已确定的原始结果
→ Quality 收尾继续返回
```

它保护执行事实所有权，不承诺诊断数据完整。数据库故障可能导致当前 Run 没有历史 Observation、没有新 State，甚至没有可读取报告。

### 3. 事实所有权与可用性（Fact Ownership / Availability）

不同层次拥有不同事实：

| 层次 | 拥有什么 | 不拥有什么 |
| --- | --- | --- |
| pytest / Runner | Case 是否执行、原始 PASS/FAIL、退出结果 | 长期 Flaky 治理结论 |
| P0 | 本轮可信执行事实 | 长期状态 |
| Flaky | Observation 历史、自动状态、人工治理 | 改写 pytest 结果或自动选例 |
| Pipeline Summary | 展示可信产物的摘要及 available 状态 | 猜测缺失报告中的零值 |

`available=false` 与“available=true 且 count=0”是两个不同事实。

## 最小规则

1. Quality、Flaky History、Flaky State 默认关闭；State 依赖 History 已启用。
2. 正常收尾顺序是 P0 归并 → 最终 RunRecord → Semantic → Metrics → History → State，但 History 直接读取 P0，不读取 Metrics；执行在后不等于数据依赖。
3. State 只在 History 返回 `IMPORTED/NOOP/DEGRADED` 时评估；否则生成 NO_DATA 语义。
4. History 或 State 抛出异常时 fail-open，不改写 pytest 原始结果。
5. Summary 只有在评估文件存在、Run/Schema/状态可信且必要列表有效时才令 `flaky.available=true`；不可用不等于计数 0。

## 完整运行过程

```text
pytest / Runner 完成执行并决定原始结果
→ Quality 归并 P0 事实
→ 写最终 RunRecord
→ 运行 Semantic 与 Metrics 阶段
→ 若 History 开关有效：从 P0 准备并导入历史
→ 若 State 开关有效且导入可评估：评估状态
→ 写 flaky-import.json / flaky-evaluation.json（若相应路径完成）
→ Pipeline Summary 独立校验评估报告
→ 展示可信计数或“不可用”
```

Semantic/Metrics 在调用顺序上更早，但不向 Flaky 提供输入；测试证明 Semantic 失败也不会阻止 Flaky History 执行。

## 正常路径

配置：

```text
QUALITY_ENABLE=1
QUALITY_FLAKY_HISTORY_ENABLE=1
QUALITY_FLAKY_STATE_ENABLE=1
QUALITY_FLAKY_DB_PATH=<有效绝对持久路径>
```

执行结果：

1. P0 完成归并并写最终 RunRecord。
2. History 通过第 9～11 课规则导入，返回 `IMPORTED`。
3. State 在已提交历史之后运行，生成可信 `flaky-evaluation.json`。
4. Summary 校验相同 `run_id`、受支持 Schema 和可用状态。
5. 若所有 Flaky 列表确为空，显示“本轮无 Flaky 状态迁移”，此时可信计数可以是 0。

## 复杂路径

只改变一个变量：测试注入使 `import_flaky_history()` 向 Stage 抛出一个未在导入器内部转换为结果的 `OSError("database unavailable")`。

逐步结果：

1. pytest 的原始 PASS/FAIL 已经确定，保持不变。
2. `run_flaky_history_stage()` 捕获异常，输出 `Quality Flaky history import failed open`，返回 `None`。
3. State 收到不可评估的导入结果；若进入阶段，会写 NO_DATA，若写报告本身也失败，外层仍捕获异常。
4. 没有新的可信历史或状态可以据此宣称成功。
5. Summary 若找不到可信 `flaky-evaluation.json`，令 `flaky.available=false`，显示“本轮未启用或未生成 Flaky 评估”。

Fail-open 的正确读法是“测试结果不受诊断故障影响”，不是“诊断故障等于无 Flaky”。

## 对应的框架实现

### 先看测试断言

[Run Master 测试](../../../tests/quality/test_flaky_run_master.py)固定 History 与 State 的顺序：

```python
assert events == ["run-record", "semantic", "history", "state"]
```

数据库异常测试验证 fail-open 消息，而函数没有向调用者重新抛出：

```python
assert "Quality Flaky history import failed open" in capsys.readouterr().out
```

[Pipeline Reporting 测试](../../../tests/quality/test_pipeline_reporting.py)删除评估报告后验证：

```python
assert report.flaky.available is False

```

另一个测试保留可信报告、清空所有列表，才断言 `transition_count == 0` 并显示“本轮无 Flaky 状态迁移”。

### 再看生产代码

[quality_pipeline.py](../../../run_orchestration/quality_pipeline.py)按顺序调用：

```python
write_final_run_record(...)
run_semantic_stage(...)
run_metrics_stage(...)
flaky_import_result = run_flaky_history_stage(...)
run_flaky_state_stage(quality_config, flaky_import_result)
```

[quality_flaky_stage.py](../../../run_orchestration/quality_flaky_stage.py)在两个阶段外分别使用 `try/except Exception`，记录 failed-open 消息。State 还显式检查 History 状态是否属于可评估集合。

[quality_sources.py](../../../pipeline_reporting/quality_sources.py)只将 `EVALUATED/NOOP/DEGRADED` 评估报告视为可用；缺失、不匹配或 FAILED/NO_DATA 都保持 `FlakySummary.available=False`。

## 能够保证什么

- 默认配置不会意外启用 Flaky History 或 State。
- State 不会在 History 未启用或未产生可评估结果时假装正常评估。
- 未处理的 Flaky 阶段异常不会覆盖 pytest 已确定的原始结果。
- 报告消费者区分可信零计数和评估不可用。

## 保证成立的前提

- 主执行链通过 `finalize_quality_run()` 和 `quality_flaky_stage` 接入 Flaky。
- pytest 原始结果已在 Quality 收尾前由执行层确定。
- Summary 使用当前 `quality_sources.py` 校验报告，不绕过它读取任意 JSON。
- 配置和数据库路径使用当前 `QualityRuntimeConfig` 规则解析。

## 不能保证什么

- Fail-open 不保证 Flaky 历史、状态或报告完整；它只隔离诊断故障对主结果的影响。
- `QUARANTINED` 不会自动跳过 pytest Case，当前没有 Enforce/Skip 链路。
- Flaky 不依赖 Metrics，也不会使用 Token、成本、请求次数或轮询耗时判断状态。
- 报告缺失、NO_DATA 或不可用不能解释成零个 Flaky 问题。

## 本课小结

Flaky 通过默认关闭且有依赖的功能开关接入 Quality 收尾链。它直接消费 P0，History 提交后 State 才评估；Semantic/Metrics 只是执行顺序更早，不是 Flaky 数据依赖。数据库故障时 fail-open 保留 pytest 原始结果，但诊断数据可能缺失，所以 Summary 必须显示 unavailable，而不是伪造零。

```text
pytest 事实
→ P0
→（开关允许）History → State
→ 可信报告：展示真实计数
→ 阶段故障/报告缺失：保留 pytest，诊断标为不可用
```

## 课末自测

请先独立作答，再查看解析。

1. **依赖题**：只设置 `QUALITY_FLAKY_STATE_ENABLE=1`、未启用 History，State 实际会启用吗？
2. **解释题**：Metrics 在 History 之前运行，为什么不能据此说 Flaky 依赖 Metrics？
3. **故障题**：数据库异常后，pytest 原始 FAIL 和 Flaky 报告可用性分别怎样？
4. **辨析题**：什么条件下“0 个 Transition”才是可信结论？
5. **边界题**：State 为 `QUARANTINED` 时，谁仍拥有下一轮是否执行 Case 的决定权？

<details>
<summary>查看答案与解析</summary>

1. 不会。State 依赖 Quality 与 History 已启用；配置会给出依赖 warning。
2. 执行顺序不等于数据依赖。History 直接读取 P0 文件，代码不读取 Metrics；测试还证明 Semantic 失败不阻止 History。
3. pytest FAIL 保持不变；Flaky 历史/状态可能没有形成，评估报告应视为不可用而非零问题。
4. 只有评估报告存在、身份/Schema/状态可信、必要列表字段有效且列表确为空时，才能说本轮 0 个 Transition。
5. pytest、Runner 和 Jenkins 执行层；当前 Governance 记录没有自动 Skip 权力。

常见错误是把 fail-open 理解为“忽略问题”，或把阶段先后关系误读成数据依赖。

</details>
