# 第 0 单元：按需解锁的最小前置知识

## 使用方式

本单元不是一堂需要一次学完的“大前置课”。它由三张 15～20 分钟的知识卡组成，只在对应课程开始前阅读：

| 知识卡 | 何时阅读 | 只需掌握 |
| --- | --- | --- |
| A：执行对象 | 第 1 课前 | Run、Case、Invocation |
| B：阶段事实 | 第 7 课前 | CaseResult、FailureRecord、P0 输入包 |
| C：持久化词汇 | 第 11 课前 | 表、唯一约束、事务 |

学习第 1～6 课时，不要求知道 P0 的具体文件名；学习第 1～10 课时，不要求知道数据库表结构。

## 知识卡 A：一次执行中有哪三个对象

### 从现象开始

假设异步图像生成测试今天失败：

```text
test_async_image_generation → FAILED
```

这只能说明今天的一次执行失败，不能说明它长期不稳定。先区分三个对象：

| 概念 | 本课程中的含义 |
| --- | --- |
| Run | 一轮完整测试运行，例如今天的 CI 构建 |
| Case | 一条稳定的测试定义，例如异步图像生成测试 |
| Invocation | 某个 Case 在某个 Run 中的一次实际执行 |

可以先用下面的关系理解：

```text
一个 Run
└─ 包含多个 Case 的 Invocation
```

此时只需记住：Flaky 判断需要比较多个 Run 中属于同一测试对象的 Invocation。

### 完成标志

- 能解释“一次失败”为什么不是 Flaky。
- 能区分 Case 和 Case 的某次 Invocation。

## 知识卡 B：一次 Invocation 怎样留下事实

一次普通 pytest Invocation 通常经历：

```text
setup → call → teardown
```

本卡只引入三个概念：

| 概念 | 本课程中的含义 |
| --- | --- |
| CaseResult | setup、call 或 teardown 某个阶段的执行事实 |
| FailureRecord | 与失败阶段关联的规范化失败证据 |
| P0 输入包 | 上游归并后的 Run、Case、Failure 和完整性事实集合 |

三个阶段回答的问题不同：

- `setup`：准备是否成功。
- `call`：测试主体是否成功。
- `teardown`：清理是否成功。

所以一条 `call passed` 还不能单独代表整个 Invocation 通过。例如随后出现 teardown error 时，最终样本不能记成 PASS。

在第 7～8 课，课程会把这些阶段事实折叠为一条 Observation；在第 9 课，才展开 P0 输入包的文件、版本、哈希与完整性校验。

### 完成标志

- 知道一个 Invocation 可能包含多条 CaseResult。
- 知道失败结果必须有可关联的 FailureRecord，不能根据异常文本猜测。
- 知道 P0 是输入事实，不是 Flaky 结论。

## 知识卡 C：持久化只需要三个词

本卡在第 11 课前阅读，不要求预先掌握 SQL：

| 概念 | 最小含义 |
| --- | --- |
| 表 | 按固定字段长期保存记录 |
| 唯一约束 | 阻止同一身份的记录被重复写入 |
| 事务 | 一组写入要么全部成功，要么全部撤销 |

第 11 课只会用这三个概念解释“重复导入”和“写到一半失败”。Repository、建表 SQL、Schema migration 与备份属于进阶内容。

## 贯穿全课程的一条边界

始终按下面四层理解系统：

```text
pytest / P0 执行事实
→ Flaky 自动检测结论
→ 人工治理决定
→ Runner / pytest 实际执行行为
```

当前基准中的 Flaky 不会把 pytest 失败改成通过，也不会因为状态是 `QUARANTINED` 就自动跳过 Case。前置阶段只需要记住这条边界，不需要记忆任何状态枚举或治理动作。

## 是否可以独立学习

可以。最低外部要求只有：

- 能阅读 Python 函数、类、枚举、列表和字典。
- 知道 pytest 可以执行测试，并能区分最基本的 pass 与 fail。
- 能阅读简单 JSON。

error、skip、xfail/xpass 会在第 8 课结合实例解释。LLM API、Retry、Polling、Metrics、Jenkins、并发调度和完整 Quality 归并实现都不是本课程的前置知识。
