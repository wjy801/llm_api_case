# 统一案例与按课解锁的教学数据

## 使用规则

全部课程固定使用同一个异步 LLM 图像生成 Case，但不要在开课前一次读完本文件。每节课只打开标注给该课的数据包，先预测结果，再查看后续解释。

```text
Case C：提交图像生成任务，轮询到成功状态，并验证输出地址存在
```

所有 Run、时间和失败原因都是离线教学数据，不代表外部 LLM 服务真实发生过这些结果。

## 数据包 A1：第 1 课——一次结果与历史

先只比较两组最小历史，不引入状态名称：

```text
历史一：PASS → PASS → PASS
历史二：FAIL → FAIL → FAIL
```

本课唯一变化是从“一次结果”增加到“三次结果”。学习者只判断结果是否一致，不讨论数据库、阈值或失败原因。

第 1～6 课暂时把每个 PASS/FAIL 当作一条已经形成的 `Observation`（可比较的单轮样本）；第 7～8 课再解释它怎样从 pytest Phase 事实产生。

## 数据包 A2：第 2 课——结果签名

现在才区分不同失败原因：

```text
PASS                     → pass
FAIL，failure_id 为 A    → fail:A
FAIL，failure_id 为 B    → fail:B
```

对比：

- `pass → fail:A`：执行结果和签名都变化。
- `fail:A → fail:B`：仍然失败，但签名已经变化。
- `fail:A → fail:A`：结果持续失败，签名没有变化。

本课把 Failure ID 当作已经给定的规范化标签；它如何与 FailureRecord 关联，延后到第 7 课。

## 数据包 A3：第 3 课——只计算证据

暂时遮住状态答案，只计算样本数、PASS/FAIL 数量、签名切换次数和尾部连续签名数：

| Run | 新增签名 | 到当前 Run 的历史 |
| --- | --- | --- |
| R1 | `pass` | `pass` |
| R2 | `pass` | `pass pass` |
| R3 | `pass` | `pass pass pass` |
| R4 | `fail:A` | `pass pass pass fail:A` |
| R5 | `pass` | `pass pass pass fail:A pass` |
| R6 | `fail:A` | `pass pass pass fail:A pass fail:A` |

## 数据包 A4：第 4 课——再揭示状态

只有完成第 3 课的证据计算后，才使用下面的答案表：

| Run | 当前状态 | 判断理由 |
| --- | --- | --- |
| R1 | `OBSERVING` | 只有一个样本 |
| R2 | `OBSERVING` | 一致但不足 3 个样本 |
| R3 | `STABLE` | 连续 3 个相同签名 |
| R4 | `SUSPECTED` | 稳定签名被打破 |
| R5 | `SUSPECTED` | 只有 1 个失败，不满足确认门槛 |
| R6 | `CONFIRMED` | 至少 2 PASS、2 FAIL 和 2 次结果切换 |

稳定失败对照也在本课揭示：

```text
fail:A → fail:A → fail:A → STABLE
```

这里的 `STABLE` 只表示签名一致，不表示 Case 健康。

## 数据包 B：第 5～6 课——逐层展开身份

### 第 5 课只看测试对象

| 字段 | 固定值 |
| --- | --- |
| `case_id` | `module/smoke/test_image_generation.py::test_async_generation` |
| `param_hash` | `param-demo-v1` |

只改变 `param_hash`，观察两个参数实例为什么不能共用历史。

### 第 6 课再看比较作用域

| 字段 | 固定值 |
| --- | --- |
| `environment` | `overseas` |
| `execution_profile` | `serial` |
| `state_epoch` | `1` |

每次只改变一个值：先改为 `china`，再单独改为 `parallel`，最后演示开启新 Epoch。五个字段共同生成最终 `flaky_key`，但不要求学习者手算哈希。

## 数据包 C1：第 7 课——正常 Invocation 折叠

正常通过：

```text
setup    PASSED
call     PASSED
teardown PASSED
→ PASS Observation Candidate
```

测试主体失败且证据唯一：

```text
setup    PASSED
call     FAILED，failure_id=A
teardown PASSED
FailureRecord(A) 唯一存在
→ FAIL:A Observation Candidate
```

## 数据包 C2：第 8 课——为什么不能形成样本

核心推导只使用“失败证据缺失”这一种复杂路径：

```text
call FAILED，failure_id=A
FailureRecord(A) 不存在
→ 排除，不猜测失败签名
```

完成核心推导后，再用同一条“事实是否足以形成唯一结果”的规则做巩固练习：

| 变化 | 预期处理 |
| --- | --- |
| setup error，且存在唯一失败证据 | 形成 FAIL，由 setup 决定结果 |
| teardown error，且存在唯一失败证据 | 形成 FAIL，不能因 call passed 记为 PASS |
| 没有 failure/error 的 skip/xfail/xpass | 排除 |
| 生命周期残缺 | 排除 |
| 同一失败阶段存在冲突证据 | 排除 |

这些练习不引入新状态，只判断“能否形成 Observation Candidate”。

## 数据包 D：第 9～11 课——可信且可重复的历史

### 第 9 课：P0 可信门禁

当前实现读取：

```text
reports/quality/run.json
reports/quality/merged/manifest.json
reports/quality/merged/case-results.jsonl
reports/quality/merged/failures.jsonl
reports/quality/merged/integrity-issues.jsonl
```

核心对照只改变“文件内容是否仍与 manifest 一致”：

```text
正常：manifest SHA256 = 当前文件 SHA256 → 继续
篡改：manifest SHA256 ≠ 当前文件 SHA256 → 拒绝整个来源
```

版本、完成状态、Schema 和 Integrity 检查作为同一可信门禁的检查清单，在核心对照之后阅读。

### 第 10 课：重复导入

```text
第一次导入 R3                  → IMPORTED
再次导入相同 R3、相同 digest  → NOOP
再次导入相同 R3、不同 digest  → conflict
```

“不同 run_id 却出现相同 digest”只作为课末唯一约束参考，不与核心重复导入路径同时推导。

### 第 11 课：事务回滚

```text
写入 Run 账本
→ 写入 Observation 时模拟失败
→ 整个事务回滚
→ 不留下“已导入但没有样本”的半成品
```

## 数据包 E：第 12～14 课——投影与治理

### 第 12 课：历史与当前投影

继续使用 R1～R6，但第一次只按正常到达顺序观察：

```text
Observation 历史 → 自动计算 State → 记录 Transition
```

晚到数据和全量 rebuild 不在主课中展开，放入进阶专题。

### 第 13 课：人工动作

核心路径只增加一次人工确认：

```text
current_state / detected_state = SUSPECTED
→ 人工确认
→ manual Transition + Override 保存原状态、操作者与理由
→ current_state / detected_state = CONFIRMED
→ Observation 不变
```

当前实现不会在确认后保留 `detected_state=SUSPECTED`；两个字段主要在后续 `QUARANTINED/RECOVERING` 阶段分开。“标记非 Flaky”作为动作对照，不与核心路径同时推导。

### 第 14 课：隔离与恢复

```text
CONFIRMED
→ 人工登记隔离信息
→ QUARANTINED
→ 人工开始恢复
→ 保存当前最新 Observation 作为 Anchor
→ 只读取 Anchor 之后的新样本
→ 连续 5 个相同签名：STABLE / recovered
→ 出现签名切换：CONFIRMED / regressed
```

当前算法判断的是签名稳定性，不额外要求恢复样本一定为 PASS。取消隔离作为本课最后的动作对照。

## 数据包 F：第 15 课——系统边界

唯一故障变量是 Flaky 数据库不可用：

```text
pytest 已产生原始结果
→ Flaky 导入或评估异常
→ fail-open 保留 pytest 结果
→ Flaky 报告可能缺失
```

报告缺失表示“没有可用诊断数据”，不能解释为零个 Flaky 问题；`QUARANTINED` 也不会自动改变 pytest 选例。

## 数据包 G：三个进阶专题

### 进阶 A：Schema migration 与备份

```text
数据库已有 v1 历史
→ 当前代码提供 v2 migration
→ 迁移前备份
→ 全部 pending SQL 与账本记录共同提交或回滚
```

核心复杂变量是 v2 中途出现非法 SQL；它只用于观察 migration 批次回滚，不改变主线 Run 数据。

### 进阶 B：独立乱序历史

为避免改写主线 R1～R6，本专题为同一个 Case C 新建独立教学数据库。这里的小写 `run-1`～`run-4` 是专项测试标识，不是主线大写 R1～R6 的延续：

```text
先到达：run-2 PASS → run-3 PASS → run-4 PASS → STABLE
后到达：run-1 FAIL
固定排序：run-1 FAIL → run-2 PASS → run-3 PASS → run-4 PASS
重投影：SUSPECTED
```

时间字段在专项 fixture 中相同，所以 `run_id` 负责打破平局。迁移审计应为 `reprojection / late_observation_reprojection`，触发 Run 是 `run-1`。

### 进阶 C：三种独立规模

先用真实测试中的 25 条 Observation 区分：

```text
total_observation_count = 25
sample_size = 20
```

再分别改变当前 Run 的 JSONL 行数、单 Key 历史长度和所选 Key 数量。10,000 条历史或 1,000 个 Key 只作教学示例，不是当前实现声明的容量阈值。

## 数据使用边界

- 缺失 Observation 只能解释为“没有可用样本”，不能解释为 PASS。
- Metrics、Token、请求次数和轮询耗时不进入当前 Flaky 判定。
- 进阶专题才修改到达顺序、Schema 版本或历史规模，主课不要提前混入这些变量。
