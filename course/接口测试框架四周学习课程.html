#接口测试框架四周项目学习课程

#1. 课程定位

本课程面向已经能够使用 Python、pytest 和 requests 搭建简单接口自动化，但第一次系统接触中高级测试框架的测试开发工程师。

课程以当前仓库代码为唯一实践对象，不另造一套演示框架。学习主线从 module/offline_framework_example/ 的确定性离线用例开始，逐步进入 common/、run_orchestration/、quality/、pipeline_reporting/ 和 Jenkinsfile。

建议学习周期为 4 周，每周 5 个学习日，每天 1.5～2.5 小时，总投入约 40 小时。周末用于复盘或补齐门禁，不强行增加新知识。

完成课程后，应具备以下能力：

  • 能沿完整调用链解释一条业务用例如何执行。
  • 能判断新需求应该落在 Test、Task、Request、Assertions、common/ 还是质量层。
  • 能排查中间件、重试、轮询、上下文、并发隔离和资源清理问题。
  • 能解释 Runner 的权威收集、并串行分池、退出码和执行事实。
  • 能区分 pytest/JUnit 事实与 Quality、Metrics、Flaky 诊断信息。
  • 能阅读 Pipeline Summary、Allure、JUnit 和 Jenkins 构建结果。
  • 能在不破坏依赖方向和安全边界的前提下扩展框架。

#2. 第一性原理学习模型

一个成熟接口测试框架，本质上需要同时解决五类问题：

业务表达：测试到底验证什么
请求执行：HTTP/SSE/异步任务如何可靠运行
执行编排：哪些用例执行、如何并发、何时停止
事实观察：一次执行实际发生了什么
持续治理：如何报告、比较历史并进入 Jenkins

当前项目对应的核心链路是：

module 业务用例
→ common 请求、断言、重试、轮询、上下文和 Runtime Hooks
→ run_master.py / run_orchestration 执行编排
→ quality 事实、语义、Metrics 和 Flaky
→ pipeline_reporting / Jenkins 发布与人工阅读

必须始终保持以下依赖方向：

module -> common
quality -> common.runtime_hooks
run_master -> run_orchestration
common -X-> quality

#3. TOC 学习策略

初学这个框架的主要约束不是 Python 语法，而是同时接触太多层后无法判断责任边界。典型因果链为：

文件数量多
→ 按目录漫无目的阅读
→ 请求、调度、质量和报告概念混在一起
→ 看懂局部代码但无法解释完整执行
→ 修改时不知道应该落在哪一层

课程用以下方式解除约束：

  1. 固定一条离线黄金路径作为学习锚点。
  2. 先学习业务分层，再进入请求内核。
  3. 先理解一次用例执行，再学习多用例调度。
  4. 先建立 pytest 原始事实，再学习 Quality 诊断。
  5. 每周设置门禁，未达到门禁时不继续堆叠新概念。

#4. 学习规则与安全边界

  • 默认只执行 tests/ 和 module/offline_framework_example/。
  • 未明确准备真实环境、账号和费用预算时，不执行真实 Smoke。
  • module/smoke 只进行 collect-only，用于学习收集与分池。
  • 不将 .env、API Key、真实响应、数据库或账号数据写入学习笔记。
  • 不为了练习复制 BaseRequest、Retry、Polling、Runner 或 Quality 实现。
  • 阅读代码时沿调用链进入下一层，不按目录从头到尾背诵。
  • 快照数量用于发现意外丢失，不作为永远不变的业务合同。
  • README.md 是架构基线，FRAMEWORK_TEST_SPEC.md 是用例规范基线。

每天采用相同的学习闭环：

运行一个最小场景
→ 定位公开入口
→ 跟踪调用链
→ 制造或观察一个失败
→ 找到错误归属和证据
→ 用自己的语言解释设计原因

pytest case
└─ logical operation
   ├─ request group(s)
   │  └─ request attempt event(s)
   └─ polling session(s)
      └─ polling request group(s)
         └─ request attempt event(s)

Operation timing / retry / usage completeness
