# LLM API 测试框架课程内容审阅规范

> 本规范用于审阅 `course/LLM_API测试框架课程大纲.md` 及各节独立讲义。当前课程共 4 周 28 课，每课建议 60～90 分钟，定位固定为“重讲解、轻实践”：通过真实代码、因果链和累积总图建立框架心智模型，不以大量编码练习作为主要学习手段。当前只有第 25 课包含唯一必做实现。

## 1. 审阅目标

课程审阅不是检查“内容写得多不多”，而是确认以下结果能否同时成立：

1. 学习者获得的事实与当前项目代码一致。
2. 每节课只解决一个主要认知障碍。
3. 讲解足够深入，但不提前展开尚未需要的机制。
4. 学习者能够解释因果关系、职责边界和对象变化，而不是只记文件名。
5. 实践用于验证理解，不演变成连续编码任务。
6. 命令、测试和演示不会意外发送真实 API 请求、产生费用或泄露凭据。
7. 本课可以自然承接前课，并为下一课提供清晰接口。

最终审阅对象不是文档本身，而是学习者形成的心智模型。

## 2. 第一性原理与 TOC 审阅方法

### 2.1 第一性原理

审阅每节课前，先回答四个问题：

1. 本课最终希望学习者具备什么判断或解释能力？
2. 达成该能力所需的最小事实集合是什么？
3. 哪些内容虽然正确，但当前并非必要？
4. 用什么证据可以证明学习目标已经达成？

“内容全面”不等于“把所有相关机制放进同一课”。课程整体应全面，单课应聚焦。

### 2.2 TOC 约束识别

每节课必须明确一个主要认知约束，例如：

- 缺少项目全局地图；
- 不会沿单一分支追踪调用；
- 混淆 Test、Task 和 Request 的变化边界；
- 不理解 Retry、Polling 或 SSE 的终止条件；
- 分不清测试事实、质量事实和报告摘要的权威边界。

审阅时使用以下因果链：

```text
学习目标
-> 当前主要认知约束
-> 解除约束所需的最小概念和证据
-> 讲解顺序
-> 轻量验证
-> 可复述的验收结果
```

如果某一章节不能直接帮助解除本课约束，应执行以下选择之一：

1. 删除；
2. 移到后续课程；
3. 折叠为虚线接口；
4. 标记为教师备注或选读材料。

## 3. 不可妥协的审阅底线

以下任一问题存在时，课程不得直接判定为通过：

1. 文件路径、类名、函数名、参数名或调用关系与当前代码不一致。
2. 将可选旁路能力描述成业务执行的必经节点。
3. 混淆 pytest、Runner、JUnit、Allure、Quality 和 Pipeline Summary 的事实所有权。
4. 把调用链、继承关系、对象流和控制结果画成同一种箭头关系。
5. 在没有明确安全边界时要求执行可能访问真实接口的命令。
6. 将 `collect-only` 描述成已经执行测试体或已经验证接口成功。
7. 将未生成、缺失或不可用的数据解释为零。
8. 大纲与独立讲义的目标、代码入口、课次引用或实践要求相互冲突。
9. 除课程明确指定的唯一必做实现外，连续布置编码任务。
10. 一节课同时展开多个尚未建立前置知识的复杂机制。

## 4. 事实核验规范

### 4.1 证据优先级

不同问题使用不同的第一证据：

| 要核验的问题 | 第一证据 | 辅助证据 |
| --- | --- | --- |
| 路径当前是否存在 | 当前文件系统 | README、课程大纲 |
| 函数实际调用谁 | 当前源码 | 离线测试、类型声明 |
| 配置当前怎样生效 | 配置文件与加载代码 | `.env.example`、README |
| 公共合同是否稳定 | 当前离线测试 | SPEC、源码 |
| 架构设计意图 | 当前源码与测试 | README、FRAMEWORK_TEST_SPEC |
| 命令是否安全 | pytest 收集行为、fixture 和配置 | 文档说明 |
| 产物由谁生成 | 生成器源码与流水线配置 | README、示例产物 |

文档表达设计意图，当前文件树和源码确认事实，测试冻结公共合同。三者冲突时不得凭印象裁决，必须在审阅结论中指出冲突。

### 4.2 必查项目

凡讲义中出现以下内容，必须逐项核验：

- 文件和目录路径；
- 类、函数、fixture、marker 和参数化 ID；
- 继承关系与依赖方向；
- 请求方法、相对路径、payload 和 header 传递方式；
- 返回对象类型和异常行为；
- pytest 收集、setup、call、teardown 的阶段归属；
- 默认配置、环境开关和产物目录；
- 命令引用的 nodeid 和测试文件；
- 课程编号和前后课引用；
- Mermaid 图中的每一条关键实线。

### 4.3 命令验证

命令验证遵循最小风险原则：

1. 优先做静态源码核对。
2. 需要验证收集时，使用精确 nodeid 和 `--collect-only -q`。
3. 需要验证行为时，只运行明确的离线测试。
4. 不运行无目标的 `pytest` 或 `run_master.py`。
5. 不运行真实业务用例、付费模型请求或依赖外部状态的流程。
6. 如果测试环境需要临时目录，应使用明确、独立、可清理的路径。
7. 测试失败时先区分代码失败、环境失败和权限失败，不得把环境错误写成课程事实错误。

验证结论必须说明命令证明了什么，以及不能证明什么。

## 5. 当前架构关键不变量

以下内容是课程当前应维持的统一表述。项目架构变化后，应先重新核验并更新本节。

### 5.1 目录职责

| 目录 | 核心职责 |
| --- | --- |
| `module/` | 具体业务、模型和协议场景，以及领域动作与验收条件 |
| `common/` | 跨模块复用的中性公共能力 |
| `run_orchestration/` | pytest 权威收集基础上的计划、分池、执行和运行产物生命周期 |
| `quality/` | 启用时记录、归并、分析和治理质量事实 |
| `pipeline_reporting/` | 读取已有可信事实并生成人工流水线摘要 |
| `tests/` | 离线验证框架公共能力、合同和依赖边界 |

### 5.2 三条主线

```text
业务执行链：测试场景怎样变成 API 交互和业务判断
运行编排链：本轮测试怎样被权威收集、计划、执行和收口
质量治理链：执行事实怎样被旁路观察、校验、分析和治理
```

三条主线是变化方向，不是一个固定线性流水线。

### 5.3 业务链路的表达

必须区分链路范围，并避免把对象继承关系写成函数调用：

```text
领域 Request 方法路径：
Test -> Task -> ProtocolRequest.create_xxx()
-> BaseRequest.post() / request()

Request Client 路径：
Test -> Task 或 Capability
-> Request Client.post() / request()
   （Request Client 是 BaseRequest 或其子类）

完整用例链：
Case / 输入
-> payload 构造
-> 场景分发
-> 上述两种请求路径之一
-> Response
-> Assertions
-> 资源清理
```

具体课程应使用当前切片的真实函数名替换抽象节点。抽象链不得冒充所有模块都完全相同的实现模板。

### 5.4 事实和报告边界

| 对象 | 当前权威边界 |
| --- | --- |
| pytest | 测试收集、测试执行和池级原始退出事实 |
| Runner | 组织执行计划和执行池，保存原始事实并形成项目级最终执行事实 |
| JUnit | 标准测试统计和失败详情 |
| Allure | 用例步骤、请求响应和附件明细 |
| Quality | 可选的完整性、分类、指标和 Flaky 诊断 |
| Pipeline Summary | 面向人的统一阅读入口，不覆盖上游明确事实 |

### 5.5 依赖与可选能力边界

- `common` 不静态依赖 `quality`。
- `quality` 通过 `common.runtime_hooks` 和 pytest 生命周期接入。
- Quality 默认可关闭；关闭或观察失败不得改变业务响应和 pytest 原始结果。
- TestContext 是用例级状态与清理容器，不是固定请求管线节点。
- BaseTask 是兼容门面，新领域逻辑默认进入领域 Task。
- 只有确有跨模块复用时才建立窄 Task Capability。
- Capture 的输入资源和输出结果是共享策略与下载原语下的两条分支，不是固定线性先后步骤。

## 6. 单课范围与知识前置审阅

### 6.1 单课必须回答的问题

每节课应明确：

1. 一个核心问题；
2. 一个主要认知约束；
3. 三至五个可验收学习目标；
4. 本课新增的最小节点；
5. 本课刻意不展开的内容；
6. 一项主要课后产出；
7. 下一课要打开的虚线接口。

### 6.2 前置知识检查

每个新概念都要回答：

- 学习者是否已经见过其上游输入？
- 是否已经知道它解决什么问题？
- 当前是否需要理解内部算法？
- 如果只保留名称，是否会制造额外认知负担？

尚不具备前置知识时，只允许：

```text
显示名称 + 一句话职责 + 虚线后续课次
```

不得提前展开内部状态、异常分支和实现文件清单。

### 6.3 单课新增量

审阅时不机械限制名词数量，但应检查工作记忆负荷。出现以下信号时通常需要收缩：

- 同时出现三条以上新的复杂分支；
- 一张主图中新增大量尚未讲解的函数节点；
- 为解释一个概念又连续引入多个后续概念；
- 学习目标超过六项；
- 同一主链使用多张图重复表达，却没有增加新的判断能力；
- “本课不展开”中的术语在正文被详细解释。

## 7. 重讲解、轻实践标准

### 7.1 “重讲解”的含义

重讲解是对少量核心关系讲深，不是扩大单课知识面。每个核心概念至少应解释：

1. 它解决什么问题；
2. 没有它会导致什么后果；
3. 它接收什么输入；
4. 它产生什么输出或影响；
5. 它调用谁、被谁调用；
6. 它不负责什么；
7. 失败或关闭时系统怎样表现。

优先使用“问题 → 原因 → 机制 → 边界 → 证据”的讲解顺序。

### 7.2 “轻实践”的含义

实践用于验证理解，默认分为：

| 级别 | 使用方式 | 是否要求提交代码 |
| --- | --- | --- |
| 教师演示 | 学习者先预测，再解释输出 | 否 |
| 代码阅读 | 追踪现有代码的输入、调用和返回 | 否 |
| 纸面设计 | 补图、分类、写测试场景或伪代码 | 否 |
| 轻量验证 | collect-only 或单个现有离线测试 | 否 |
| 唯一必做实现 | 当前第 25 课指定的一次最小离线测试 | 是，仅第 25 课 |
| 选做扩展 | 原型、骨架或更多测试 | 否，不影响课程完成 |

除唯一必做实现外，不得把 pytest 命令默认解释为学习者必须逐条运行并提交。

### 7.3 单课时间预算

每课建议 60～90 分钟，可按以下范围审阅：

| 环节 | 建议时间 |
| --- | --- |
| 问题场景与生活类比 | 10～15 分钟 |
| 核心代码、对象和因果链讲解 | 30～40 分钟 |
| 证据观察与教师演示 | 10～15 分钟 |
| 轻量验证或纸面判断 | 5～10 分钟 |
| 总图更新与三分钟复述 | 5～10 分钟 |

全部必讲内容、活动和复述的时间上限不得明显超过 90 分钟。超出的内容应标记为选讲、课后阅读或附录。

### 7.4 课后任务上限

单课必做任务原则上不超过三项：

1. 更新本课新增节点的累积总图；
2. 完成三分钟因果链复述；
3. 完成一项证据判断、职责分类或指定实现。

重复抄写完整图、同时提交多张同义图、长篇文字稿和多组练习，不应全部设为必做。

## 8. 因果链、对象流和图示规范

### 8.1 四类关系必须分开

| 关系 | 回答的问题 | 示例 |
| --- | --- | --- |
| 函数调用链 | 谁调用谁 | `Task.create -> Request.create` |
| 继承或依赖关系 | 能力从哪里获得 | `ProtocolRequest -> BaseRequest` |
| 对象流 | 数据怎样变化 | `Case -> payload -> Response` |
| 控制结果 | 成功、失败或跳过怎样发生 | `断言通过 / AssertionError` |

不得把“断言结果”虚构为新数据对象；如果断言返回原 Response，应明确说明调用方是否接收该返回值。

### 8.2 Mermaid 图规则

- 实线：本课已经确认的主要调用或产物流向。
- 虚线：可选能力、配置条件、观察关系或后续课程接口。
- 节点名称同时写对象和职责，不只写缩写。
- 可选 Quality 不得画在 HTTP 与 Assertions 之间。
- 源码目录不得按目录顺序画成固定调用顺序。
- pytest 原始退出事实与 Runner 最终执行事实不得合并成含义不明的“退出码”。
- 输入 Capture 和输出 Capture 应画成并列分支。
- 图中的每条关键边都必须能在正文或代码中找到证据。

### 8.3 累积总图规则

每节课只展开本课新增节点：

1. 已掌握内容保持稳定；
2. 尚未学习的机制保持折叠；
3. 新分支标明触发条件；
4. 对象节点标明输入或输出；
5. 后续课程入口使用虚线和课次编号；
6. 图与正文使用相同术语。

## 9. 内容完整性审阅

独立讲义不要求机械包含固定数量的章节，但应覆盖以下功能：

1. 课程信息和安全边界；
2. 可验收学习目标；
3. 前课承接与本课范围；
4. 核心问题、认知障碍和因果链；
5. 生活类比及其适用边界；
6. 真实代码入口；
7. 角色、调用关系和对象变化；
8. 至少一种可核验的现有证据；
9. 轻量课堂活动；
10. 累积总图增量；
11. 常见误区；
12. 三分钟复述与验收问题；
13. 有限的课后任务；
14. 下一课接口。

完整性审阅同时检查两个方向：

- 缺失：是否缺少理解核心因果链所需的事实；
- 过量：是否加入了不能帮助本课达标的正确内容。

## 10. 跨课程一致性审阅

### 10.1 大纲与讲义

逐项核对：

- 课名和课次；
- 核心问题；
- 学习内容；
- 代码入口；
- 课堂实践级别；
- 课后产出；
- 后续课次引用。

详细讲义可以增加解释，但不能悄悄扩大大纲规定的必学和必做范围。

### 10.2 前课与后课

本课开头声称“已经掌握”的内容，必须确实在前课讲过并验收。本课结尾预告的链路，必须与下一课的术语和范围一致。

特别检查：

- 同一条链是否在不同课程使用不同名称；
- 同一角色的职责是否前后变化；
- 后续机制是否在前课被提前展开；
- 课次引用是否因大纲调整而失效；
- 累积总图是否无解释地改变已有节点。

### 10.3 术语一致性

以下术语不得混用：

- 收集与执行；
- 测试失败与请求失败；
- pytest 原始退出码与 Runner 最终退出码；
- JUnit 统计与 Allure 明细；
- Quality 机器证据与 Pipeline Summary 人工摘要；
- 请求上下文与 TestContext；
- Retry 单次请求尝试与 Polling 多次状态查询；
- 函数调用链与对象流；
- 缺失数据与零值。

## 11. 实践与安全审阅

### 11.1 默认安全实践

优先级从高到低：

1. 阅读源码并预测；
2. 纸面补图或职责判断；
3. 精确 nodeid 的 collect-only；
4. 单个现有离线测试；
5. 教师演示多文件离线测试；
6. 课程指定的唯一离线实现。

### 11.2 禁止默认执行的命令

以下命令不得作为普通课堂必做项：

- 不带目标的 `pytest`；
- 不带目标的 `run_master.py`；
- 真实模型或业务 smoke 用例；
- 可能创建、删除或修改外部资源的用例；
- 需要真实 API Key、计费账号或外部共享状态的流程；
- 无法证明不会访问外部网络的脚本。

如课程确需介绍真实执行，只能解释执行条件、风险和证据，不得在默认课堂流程中实际运行。

### 11.3 凭据与输出

- 讲义不得写入真实密钥、账号或可复用令牌。
- 示例输出不得包含未脱敏请求头、URL 查询参数或响应敏感内容。
- 不要求学习者上传 `.env`、完整日志或真实响应体。
- 报错示例应保留诊断价值，同时去除凭据和业务敏感信息。

## 12. 问题分级与审阅结论

### 12.1 P0：阻断教学

包括：

- 关键事实或调用链错误；
- 危险命令可能访问真实接口或破坏数据；
- 证据权威边界颠倒；
- 当前代码中不存在的路径被当作必学入口；
- 核心架构方向被错误描述。

结论必须为“不通过，修正后复审”。

### 12.2 P1：教学前必须修改

包括：

- 大纲与讲义不一致；
- 前置知识缺失；
- 主链定义前后不一致；
- 对象流、控制流或继承关系混淆；
- 60～90 分钟内明显无法完成必讲内容；
- 必做实践超过“轻实践”边界。

### 12.3 P2：建议优化

包括：

- 重复图表或重复复述；
- 类比过长；
- 示例可以更贴近当前切片；
- 非核心内容更适合作为附录；
- 表述可以更精确或更通俗。

P2 不阻断使用，但应说明优化收益。

## 13. 标准审阅流程

每次审阅按以下顺序执行：

1. 复述审阅对象、课程定位和本次边界。
2. 阅读大纲中对应课次及前后相邻课次。
3. 完整阅读独立讲义。
4. 提取事实声明、调用链、对象流、命令和课次引用。
5. 使用当前文件树、源码、配置和离线测试逐项核验。
6. 确认一个主要学习约束及其解除路径。
7. 检查内容缺失、内容过量和知识前置。
8. 估算课堂必讲、活动和复述所需时间。
9. 检查实践级别与安全边界。
10. 检查大纲、前课、后课和累积总图一致性。
11. 按 P0、P1、P2 输出问题和修改方向。
12. 给出“通过、修改后通过或不通过”的最终判断。

审阅只发现问题时不得直接修改课程文件；只有用户明确要求修改时才实施编辑。

## 15. 课程通过标准

一节课只有同时满足以下条件，才可判定为“通过”：

- [ ] 核心事实均与当前项目一致。
- [ ] 所有关键路径、符号和课次引用有效。
- [ ] 只有一个清晰的主要认知约束。
- [ ] 学习目标可以通过解释、判断或有限产出验收。
- [ ] 本课新增内容具有必要前置知识。
- [ ] 调用链、继承关系、对象流和控制结果没有混淆。
- [ ] Quality、Runner 和报告边界表述正确。
- [ ] 必讲内容可在 60～90 分钟内完成。
- [ ] 实践以教师演示、阅读、纸面设计或轻量验证为主。
- [ ] 默认命令不会访问真实 API 或产生费用。
- [ ] 必做课后任务不超过三项核心产出。
- [ ] 大纲、讲义、前课、后课和累积总图保持一致。
- [ ] 学习者能够完成三分钟因果链复述。

## 16. 规范维护

出现以下情况时应更新本规范：

- 项目目录或分层职责改变；
- BaseTask、Capability 或领域 Task 边界改变；
- Runner、Quality 或 Reporting 的事实所有权改变；
- pytest 默认配置或安全执行入口改变；
- 课程总课次、唯一必做实现或考核方式改变。

更新时仍以当前文件系统、源码、配置和离线测试为事实基础，不能仅根据旧课程或历史文档延续结论。
